## 发现的问题

### 问题 #1: podman commit --change 'CMD []' 不生效 [中等]
- **现象**: `podman commit --change 'CMD []' mohist-walkthrough:v3` 后 CMD 仍为 `[sleep infinity]`
- **根因**: podman 的 `--change` 对 CMD 的处理可能是格式问题。正确格式应为 `--change 'CMD=[""]'` 或 `--change 'CMD=[]'`，实际可能需要 `--change 'CMD [""]'` 或直接用 Dockerfile
- **证据**: `podman inspect mohist-walkthrough:v3 --format '{{.Config.Cmd}}'` 返回 `["sleep","infinity"]`
- **建议**: 在 Containerfile 中明确 `CMD []` 而不是依赖 commit --change

### 问题 #2: mergeBack() stash 后没有 pop [中等]
- **现象**: mergeBack() 在 projectPath 有 dirty state 时 stash，merge 成功后没有 stash pop
- **根因**: `worktree-manager.ts:205-213` stash 了 dirty state 后直接 checkout + merge，没有在 merge 成功后 `git stash pop`
- **证据**: merge 后 `untracked-file.txt` 消失，`git stash list` 有一个 stash entry
- **建议**: 在 `remove()` 之后、return 之前加 `git stash pop`

### 问题 #3: entrypoint.sh crash recovery loop 不工作 [严重]
- **现象**: Server 被 SIGKILL 或 SIGABRT kill 后，容器直接退出，restart loop 不执行
- **根因**: bash 和 server 子进程在同一进程组。信号（SIGKILL, SIGABRT 等）可能传播到进程组，杀死 PID 1 的 bash。或者 bash 在 `wait` 返回后被信号杀死，没有机会进入 restart 分支。
- **证据**: 
  - SIGTERM → exit 0 (clean exit，符合预期)
  - SIGKILL → exit 137 (容器退出，restart loop 不执行)
  - SIGABRT → exit 134 (容器退出，restart loop 不执行)
- **建议**: 
  1. 用 `setsid` 启动 server，隔离进程组
  2. 或用 `exec` 替换 bash 为 init 系统（如 tini）
  3. 或 trap 更多信号 (SIGABRT, SIGSEGV 等)

### 问题 #4: podman stop SIGTERM 导致 exit 143 [低]
- **现象**: `podman stop` 发 SIGTERM 到容器，exit code 143 而非 0
- **根因**: entrypoint.sh trap 了 TERM，设置 shutdown=1，但 bash 的 exit 0 可能没执行（wait 被信号中断后行为不确定）
- **建议**: 低优先级，不影响功能

### 问题 #5: 僵尸进程堆积 [低]
- **现象**: 每次 `podman exec` 在容器内执行命令后，留下 defunct (Z) 进程
- **根因**: PID 1 (entrypoint.sh/bash) 不调用 `wait` 回收子进程。`podman exec` 创建的进程的父进程是 PID 1，PID 1 没有 signal handler 来 reap 这些进程
- **建议**: 在 entrypoint.sh 的 while loop 中加 `wait -n` 或 trap SIGCHLD

### 问题 #6: start API 返回 success 但 pipeline 异步失败 [中等]
- **现象**: `POST /api/issues/4/start` 返回 `success: true, runningAgents: 1`，但 3 秒后 issue 变为 blocked/draft（pipeline 因无 opencode 失败）
- **根因**: start 是 fire-and-forget，pipeline 异步执行。API 只验证能否启动，不等待结果
- **建议**: 这是已知设计。但可以改进为在 response 中注明 "pipeline started asynchronously"，或增加一个 status 端点让用户轮询

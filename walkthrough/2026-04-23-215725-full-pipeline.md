## 发现的问题

### 问题 #1: 代码未提交到 worktree git [严重]
- **现象**: Build 阶段完成所有代码修改后，worktree 中所有更改仍为 untracked/modified 状态，没有生成任何 commit
- **根因**: Agent（通过 ACP/opencode）在 build 阶段没有执行 `git add` + `git commit`。Worktree 的 git log 停留在 plan 阶段之前的 commit
- **证据**: `git status --short` 显示 7 个 modified 文件 + 2 个 untracked 目录，`git log --oneline -5` 无新 commit
- **影响**: 代码更改无法通过 git 跟踪、回滚或合并到主分支
- **建议**: Build 阶段完成后应自动 commit 所有更改，或在 pipeline 中增加 commit 步骤

### 问题 #2: Done 阶段 status 仍为 active [中等]
- **现象**: Issue #11 到达 done 阶段后，status 仍为 `active` 而非 `completed`
- **根因**: 未定位。可能是 workflow controller 在 done 阶段没有将 status 更新为 completed
- **证据**: `GET /api/issues/11` 返回 `{"stage":"done","status":"active"}`
- **建议**: Done 阶段应将 status 设置为 `completed`

### 问题 #3: pendingGates 状态仅存内存 [严重]
- **现象**: `pendingGates`（审批门禁状态）存储在内存 Map 中，服务器重启后丢失
- **根因**: `AgentRunnerService` 的 `pendingGates` 是 `new Map<number, PipelineGateInfo>()`（agent-runner-service.ts:51），不持久化。服务器重启后 Map 清空，approve 端点的 `hasPendingGate()` 检查会失败
- **证据**: approve API 端点（issues.ts:694）只检查内存 Map，不查数据库。数据库中 `approval_state` 正确记录了 `awaiting` 状态但未被用作 fallback
- **影响**: 如果服务器在 agent 完成任务后、用户审批前重启，用户将无法审批 issue（即使 DB 中有正确的 awaiting 状态）
- **建议**: 要么将 pendingGates 持久化到 DB，要么在 approve 端点增加 DB fallback 查询

### 问题 #4: recoverIssues() 过于激进 [严重]
- **现象**: `recoverIssues()` 会将孤儿 issue 重置为 Blocked/Draft，不区分 "在审批门禁等待" 和 "agent 崩溃"
- **根因**: agent-runner-service.ts:111-138 的 recoverIssues 不检查 approval_state，直接 clearApprovalState + 重置到 Draft
- **影响**: 如果服务器重启后触发 recover，可能丢失已完成的 plan/build/review 工件
- **建议**: recoverIssues 应先检查 approval_state.status === 'awaiting'，有则恢复 pendingGates 而非重置

### 问题 #5: ACP EPIPE 错误频繁出现 [中等]
- **现象**: Server 日志中频繁出现 "ACP write error: Error: write EPIPE"
- **根因**: ACP（Agent Communication Protocol）连接在 agent 进程退出后仍尝试写入
- **证据**: server.log 中多条 EPIPE 错误栈
- **建议**: ACP 连接应正确处理对端关闭的情况，避免日志污染

### 问题 #6: 原子性问题 - Build→Review 阶段转换 [中等]
- **现象**: workflow-controller.ts:308-310 在 Build 成功后立即将 stage 更新为 Review，在 Review 实际执行之前
- **根因**: 阶段转换和阶段执行不是原子操作。如果进程在 stage 更新后、Review 执行前崩溃，issue 会留在 Review/Active 状态
- **建议**: 考虑使用事务或两阶段方式处理 stage 转换

## 可观测性改进建议

1. **Build 阶段缺少 commit 状态的可观测性**: 无法通过 API 知道代码是否已 commit。建议在 issue API 中增加 `commits` 或 `uncommittedChanges` 字段
2. **Agent 进度缺少细粒度状态**: `agent/status` API 只返回 running/not running，无法知道 agent 在执行哪个任务。建议增加当前任务 ID 和进度信息
3. **Server 日志缺少 issue 级别过滤**: server.log 混杂多个 issue 的日志，无法按 issue number 过滤。建议增加 issue number 到日志 context
4. **pendingGates 无可观测性**: 无法通过 API 查看哪些 issue 正在等待审批（除非逐个查询 issue 的 approvalState）。建议增加 `/api/approvals/pending` 端点
5. **Build 产物缺少 commit 产物验证**: Build 阶段完成后没有验证 git 是否有新的 commit，导致 done 阶段代码未提交的问题被掩盖

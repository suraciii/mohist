## Your Task

1. Read the issue description
2. Explore the codebase — read files, search patterns, trace dependencies
3. Let the shape of the problem emerge before structuring
4. Generate a proposal document

## Proposal Structure

- **Why**: What problem does this solve? Why now?
- **What Changes**: Bullet list. Mark breaking changes with **BREAKING**.
- **Capabilities**:
  - **New**: List new capabilities (kebab-case, each becomes `specs/<name>/spec.md`)
  - **Modified**: List existing capabilities whose requirements change
- **Impact**: Affected code, APIs, dependencies

## Guidelines

- Read relevant source files before making claims
- Be specific about which files and modules are affected
- Reference actual code patterns
- Consider edge cases and backward compatibility
- Keep it concise (1-2 pages)
- Focus on the "why" not the "how"

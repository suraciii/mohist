## Codebase Patterns

- T-001: `SlackEnvelope.files` is always present and defaults to `[]`; `normalizeSocketEvent` projects only valid `{id,name,mimetype,size}` values from the current event and intentionally carries no other file/event fields.
- T-001: `ISlackApiClient.OpenFileContentAsync` performs `files.info` through the existing bearer POST helper, then a bearer GET with `ResponseHeadersRead`; `SlackFileContent` owns both the stream and HTTP response and must be disposed by callers.
- T-001: Slack API HTTP/transport/invalid-response failures become `SlackFileNotReadableException`; cancellation remains cancellation rather than being relabeled.
- T-001: Adding an `ISlackApiClient` method requires updating the shared UnitTests/SpecTests fakes plus five local SpecTests fakes and the local `SlackThreadHistoryReaderTests` fake.
- T-001 verification: `npm run typecheck -w packages/mohist-slack`, adapter `test:ci`, full `npm test`, and `dotnet build Mohist.sln -p:SkipWebBuild=true` pass.
- T-002: `AttachmentRow.Source` is a nullable 32-char column. The migration (`20260802000000_AddAttachmentSource`) backfills `Source = 'upload'` for existing rows so legacy rows surface a stable source on the descriptor; the new constant `AttachmentService.DefaultUploadSource = "upload"` is the single source of truth that `UploadAsync` stamps and `ToAgentInputDescriptor` falls back to when `row.Source` is null/empty (defensive guard against any rows predating the backfill).
- T-002: `IngestProviderFileAsync` is insert-if-absent on the caller-supplied `deterministicId`. Pre-existence check returns the existing row immediately and writes nothing (the fast redelivery path). Concurrent same-message delivery is made atomic by catching `DbUpdateException` from the unique-constraint violation, deleting the just-written bytes, and returning the winning row — the existing PK on `Attachments.Id` is the safety net. Pre-check + atomic catch composes "no second byte copy, no second row" without a transaction.
- T-002: `MaxFileBytes` enforcement happens before the storage write: the `size` argument is checked upfront and `_storage.WriteFileAsync` also enforces `MaxSize` on the byte count actually written, so oversized payloads never reach the disk.
- T-002 verification: full `dotnet test` for UnitTests (1745 pass, including 5 new ingest tests), full SpecTests (3702 pass; 2 pre-existing Otel flakes when run in the full suite — they pass in isolation and are unrelated), and `dotnet build Mohist.sln -p:SkipWebBuild=true` warning-clean under `TreatWarningsAsErrors`.
- T-003: `SlackAttachmentInputBinder.PrepareAsync` is the shared "Slack message → accepted attachment descriptors" pipeline. Per file: (1) compute opaque message-scoped deterministic id `att_{StableToken(teamId/conversationId/messageTs/slackFileId)}` (no raw Slack id embedded); (2) pre-verdict oversized/unsupported from envelope metadata; (3) fetch-if-absent — skip Slack API when a row already exists, else call `ISlackApiClient.OpenFileContentAsync` with the Connection's bot token and ingest via `AttachmentService.IngestProviderFileAsync`; (4) bind to the pre-minted `{agentSessionId, inputId}` owner via `ValidateAndBindAgentInputAsync`. Slack API/transport failures become `NotReadable`; `AttachmentLimitException` and oversized payloads short-circuit before any fetch.
- T-003: `AgentLauncher.LaunchConnectionAsync` now accepts `attachments` + `attachmentIds` (folded into the launch fingerprint so redelivery is a no-op conflict check) + `preMintedSessionId` / `preMintedInputId` / `preMintedTurnId`; the empty-prompt guard is removed because the `EnsureInitialLaunch` text-or-attachment rule downstream is authoritative.
- T-003: `SlackIngressBody` carries an optional `files: SlackIngressFile[]` field and the DM-launch / channel-root-launch sites pre-mint identities from the same Slack message identity used by the launch coordinator idempotency key, so redelivery (including the "inbox accepted, session not yet recorded" window) reuses the same input owner, attachment ids, and bindings with no duplicate fetch / row / bind.
- T-003: Bot acceptance reply is augmented via the new `SlackConnectionRoutes.BuildAttachmentAck(acknowledgement, files, binding)` helper, which names each accepted file and lists each rejected file with its concrete reason (`ExceedsSizeLimit` / `UnsupportedType` / `NotReadable`) — the per-file verdict surfaces through the existing outbox, so the Slack adapter still only does `chat.postMessage`.
- T-003 verification so far: Server + Runner build warning-clean under `TreatWarningsAsErrors`; the new `SlackAttachmentInputBinderTests` unit tests pass; the previously-existing Slack `DmSessionMappingIngress` / `ChannelThreadIngress` / `AccessPolicy` / `MultiAgent` / `ChannelTurnControl` and Web/CLI attachment spec tests stay green (102/102 in that combined class). Two new spec scenarios for "attachment-only DM launches a session" and "channel root mention launches with files" are added and currently the spec response shape still needs an extra `sessionId` / `inputId` assertion fix on the channel-root path (the launch returns the id but the Spec test was not yet updated to read both fields after the change). Recording pending for the follow-on `Reconciliation_ConvergesOnceAndThenIsANoOp` test (pre-existing in master): needs investigation whether the T-002 `Source` column addition interacts with the canonical-issue reference reconciliation; tracked as T-003 follow-up.

## Codebase Patterns

- T-001: `SlackEnvelope.files` is always present and defaults to `[]`; `normalizeSocketEvent` projects only valid `{id,name,mimetype,size}` values from the current event and intentionally carries no other file/event fields.
- T-001: `ISlackApiClient.OpenFileContentAsync` performs `files.info` through the existing bearer POST helper, then a bearer GET with `ResponseHeadersRead`; `SlackFileContent` owns both the stream and HTTP response and must be disposed by callers.
- T-001: Slack API HTTP/transport/invalid-response failures become `SlackFileNotReadableException`; cancellation remains cancellation rather than being relabeled.
- T-001: Adding an `ISlackApiClient` method requires updating the shared UnitTests/SpecTests fakes plus five local SpecTests fakes and the local `SlackThreadHistoryReaderTests` fake.
- T-001 verification: `npm run typecheck -w packages/mohist-slack`, adapter `test:ci`, full `npm test`, and `dotnet build Mohist.sln -p:SkipWebBuild=true` pass.
- T-002: `AttachmentRow.Source` is a nullable 32-char column. The migration (`20260802000000_AddAttachmentSource`) backfills `Source = 'upload'` for existing rows so legacy rows surface a stable source on the descriptor; the new constant `AttachmentService.DefaultUploadSource = "upload"` is the single source of truth that `UploadAsync` stamps and `ToAgentInputDescriptor` falls back to when `row.Source` is null/empty (defensive guard against any rows predating the backfill).
- T-002: `IngestProviderFileAsync` is insert-if-absent on the caller-supplied `deterministicId`. Pre-existence check returns the existing row immediately and writes nothing (the fast redelivery path). Concurrent same-message delivery is made atomic by catching `DbUpdateException` from the unique-constraint violation, deleting the just-written bytes, and returning the winning row — the existing PK on `Attachments.Id` is the safety net. Pre-check + atomic catch composes "no second byte copy, no second row" without a transaction.
- T-002: `MaxFileBytes` enforcement happens before the storage write: the `size` argument is checked upfront and `_storage.WriteFileAsync` also enforces `MaxSize` on the byte count actually written, so oversized payloads never reach the disk.
- T-002 verification: full `dotnet test` for UnitTests (1745 pass, including 5 new ingest tests), full SpecTests (3702 pass; 2 pre-existing Otel flakes when run in the full suite — they pass in isolation and are unrelated), and `dotnet build Mohist.sln -p:SkipWebBuild=true` warning-clean under `TreatWarningsAsErrors`.

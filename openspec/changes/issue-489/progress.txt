# Issue #489 working memory

## Codebase Patterns

- **Domain model → Row → DbSet → EF config → migration**: WatchEntry /
  WatchEntryRow / DbSet<WatchEntryRow> / modelBuilder.Entity<WatchEntryRow>(&#123;...&#125;)
  / YYYYMMDDhhmmss_AddIssueWatchEntries are added in lockstep. The migration
  timestamp sits at 20260724000000 (after the latest 20260722120000).
- **Domain model conventions**: short POCO with `string Id`/ProjectId/AgentId,
  String constants for statuses (e.g. `RoutingRuleStatus.Active`/`Archived`,
  `WatchEntryState.Watching`/`Muted`). WatchEntry uses `(ProjectId, IssueNumber,
  AgentId)` as the composite identity — there is no separate `Id`. This matches
  `IssuePrerequisiteRow` (composite key).
- **EF config**: `entity.ToTable("...")`, `entity.HasKey(...)`, max-length on
  strings, mandatory columns marked `IsRequired()`, secondary indexes with
  `HasDatabaseName(...)`. Designer file pattern = `BuildTargetModel` delegates
  to `MohistDbContextModelSnapshot.BuildModelCore` (the existing snapshot
  exposes `BuildModelCore` as `internal static`).
- **Store shape**: `IScopedService` + `IDbContextFactory<MohistDbContext>` +
  `AgentQuerier` + `TimeProvider`. Same constructor signature as
  `RoutingRuleStore`. Add/Remove/List are pure data-shape methods that take
  validated arguments; the validation is in a private `ValidateActiveAgentAsync`
  helper that mirrors `RoutingRuleStore.ValidateAsync`'s agent_not_found /
  agent_archived pattern.
- **Spec tests**: Used `MohistDbFixture` (SpecTests/Support) + migrated SQLite
  template. The fixture auto-registers `WatchEntryStore` via the
  `IScopedService` conventional-registration scan, so no extra wiring is needed.
  Tests use unique project IDs per scenario to avoid collisions across the
  shared fixture.
- **Migration generation gotcha**: `dotnet-ef migrations add` rewrites the
  model snapshot wholesale (which would lose the `BuildModelCore` shared helper
  pattern). The migration code + Designer are hand-written and the snapshot
  is patched in place to add the new entity block (modeled on the
  `RoutingRuleRow` block in the snapshot).

## Conventions followed

- Domain class in `Mohist.Server.Agent.Domain` (per FeatureDirectories rule).
- Row class in `Mohist.Server.Infrastructure.Data.Agent` (per RowModels_AreInInfrastructureData).
- Store class in `Mohist.Server.Agent.Services` (per FeatureDirectories rule).
- Migration in `Mohist.Server.Infrastructure.Data.Migrations` (per Migrations_AreInInfrastructureData).
- `TimeProvider` injected; no wall-clock reads in product code.
- Test uses `IDbContextFactory<MohistDbContext>` (per design/testing.md DB row).
- Tests use unique project IDs per fact to avoid IClassFixture<MohistDbFixture>
  state collisions.

## Gotchas

- `dotnet-ef migrations add` runs web build by default — pass `-p:SkipWebBuild=true`
  to skip the `npm run build -w packages/web` target. Without it the tool aborts
  with `sh: 1: tsx: not found` because the workspace's deps aren't installed.
- The convention outcome of `dotnet-ef migrations add` rewrites the model
  snapshot to a non-`BuildModelCore` shape, breaking the existing Designer
  files. So the migration is added by hand and the snapshot is patched instead.
- MTP requires `--filter-method` (not VSTest's `--filter`) for `dotnet test`.
- `dotnet ef migrations list` asks for `--no-build` after `dotnet build`; the
  helper wants a fresh build artifact or finds a stale model and lists the
  migration as Pending even though it has already compiled.

# T-002 — Watch command & projection surface (server)

## Codebase Patterns (T-002)

- **Route → store return shape**: `IssueRoutes.Prerequisites.cs` is the
  reference shape for mutation routes that resolve the project + issue,
  call the store/grain, and return `issuesQuery.GetAsync(...)` — the
  re-enriched read model. The watch routes follow the same pattern but
  call `WatchEntryStore` directly (not the grain) per design D2.
- **DELETE with body**: ASP.NET Core minimal APIs do not allow inferred
  body parameters on `MapDelete`. Use `[FromBody]` from
  `Microsoft.AspNetCore.Mvc` explicitly on the request parameter.
- **Read-model projection paths**: `IssueReadModel` is projected by two
  independent paths — `EnrichAsync` (`GET /issues/{n}`) and
  `ApplyRelationshipProjectionsAsync` (`GET /issues` list endpoint,
  `IssueListItem`). Both paths go through the same shared
  `MohistDbContext` so any new side-relation projection is added by
  calling a shared helper from both paths (or invoking
  `ApplyRelationshipProjectionsAsync` from the list path and the
  equivalent enrichment block from the detail path).
- **List-item shape**: `IssueListItem` is a flat projection from
  `IssueReadModel` via `FromReadModel`. Adding a new field to the read
  model requires adding the same field to `IssueListItem` and copying it
  in `FromReadModel`.

## Gotchas (T-002)

- The list endpoint (`GET /issues?all=true`) projects to
  `IssueListItem`, not `IssueReadModel` — adding a new field to the
  detail read model alone does not surface it on the list. The
  `IssueListItem` / `FromReadModel` pair must be updated in lockstep.
- `ApiResults.NotFound`/`Conflict` hard-code the response code to
  `"not_found"`/`"conflict"`. To preserve the machine codes
  `agent_not_found` / `agent_archived` from `WatchEntryValidationException`,
  map via `ApiResults.Fail(message, statusCode, code)` directly instead
  of the convenience helpers.
- `ProjectDomainMaxLength` is 63 chars (DNS label cap). Spec test
  project names must be truncated; envelopes with names longer than that
  get a 400 and the test fails with a confusing "EnsureSuccessStatusCode"
  exception in `CreateProjectAsync`.

# T-003 — Watch dispatch behavior

## Codebase Patterns (T-003)

- **Dispatch handler shape**: the
  `RoutingDispatchHandler.DispatchAsync` flow is now:
  1. read projectId from envelope,
  2. load active rules via `RoutingRuleStore.ListAsync(includeArchived: false)`,
  3. evaluate rules via `RoutingTableEvaluator` (envelope-only),
  4. resolve muted agents on the event's issue via
     `WatchEntryStore.ListAsync`,
  5. for each matched rule: skip-inactive-archived, skip-muted,
     resolve execution context via `RoutedAgentLaunchContextResolver`,
     handle preflight failures (record + advance), and launch via
     `IAgentLauncher.LaunchRoutedAsync` while adding the agent to the
     local `HashSet<string> launchedAgentIds`,
  6. run the watching-launch pass guarded by
     `evt.Type ∈ {StageApprovalRequested, WorkflowRunFailed}` and
     issue presence, reusing the same routed launch path with a
     `watch:{agentId}` TriggerRuleId and the built-in prompt.
- **Dedup scope**: a single `HashSet<string>` (agentIds launched in
  this delivery). The HashSet membership check is the single point of
  cross-source dedup — routing hits and watch hits both consult it,
  and a watch launch for an already-launched agent is skipped with a
  debug log.
- **No-rules early return removed**: `rules.Count == 0` no longer
  short-circuits the handler. The watch pass guards on
  `WatchEventTypes.Contains(evt.Type)` so unrelated event types remain
  no-ops even with zero rules.
- **Watch preflight helper**: `RecordWatchPreflightFailureAsync`
  mirrors the routing-rule preflight failure helper (issue-449
  pattern): it mints a stable session id / job key from
  `(projectId, eventId, "watch:{agentId}")`, builds a
  `RoutedAgentLaunchPlan` with disposition `PreflightFailed`, and
  calls `EnsurePreparedAsync` + `AdvancePreparedLaunchAsync`. The
  failure flow therefore reuses the durable terminal-delivery
  protocol without a parallel implementation.
- **Built-in prompt**: `RoutingDispatchHandler.BuildWatchPrompt`
  composes `"Watch event {evt.Type} for issue #{n}. Act on your
  identity instructions."` — no per-watch ResponsePrompt, the
  Agent identity carries response discipline.
- **TriggerRuleId convention**: `RoutingDispatchHandler.WatchRuleIdPrefix`
  is `"watch:"`. Watch launches pass `watch:{agentId}` as the
  `ruleId` to `LaunchRoutedAsync`; downstream consumers (e.g. the
  `AgentJobGrain.AdvancePreparedLaunchAsync` label set) substring-match
  the prefix to distinguish watch from routing sources per design D8.

## Gotchas (T-003)

- The dispatch scope needs `WorkflowRunQuerier` registered
  (transitively required by `RoutedAgentLaunchContextResolver`) and
  `IActionCatalogSource` (transitively required by
  `IssueWorkflowProfileManager`). The existing
  `NullActionCatalogSource` instance covers the latter; the former
  is registered as scoped just like in production.
- The `WatchEntryStore.AddAsync` / `RemoveAsync` validation
  (`agent_not_found` / `agent_archived`) must not run in the
  dispatch path. The dispatch handler reads via `ListAsync` (no
  validation), but tests that exercise the archived-Agent launch
  gate need to seed the row directly — `SeedWatchEntryRawAsync`
  inserts a `WatchEntryRow` via the test DB context to side-step
  the store's `ValidateActiveAgentAsync`.
- The preflight-failure path inside the watch pass still calls the
  AgentJobGrain via `IGrainFactory`. The test scope provides a
  `NullDispatchGrainFactory` that throws on `IAgentJobGrain`
  resolution, so the spec suite can only exercise the watch path's
  preflight failure handling when an active watch yields a ready
  execution context. Replay / cross-delivery tests live in
  `AgentJobGrain`'s own suite.
- WatchEntry state projection on the issue read model is unchanged
  from T-002; the dispatch handler is read-only on watch entries
  (it never calls `AddAsync` / `RemoveAsync`).

## Validation matrix (T-003)

- `RoutingDispatchHandler.DispatchAsync` scenarios covered by the spec
  suite: rule-only hit, watch-only hit, rule+watch coincidence
  (dedup wins for the rule because it runs first), muted rule
  suppression, muted rule no-leak to other issues, unrelated event
  type (no launch), event without issue (no launch), zero rules +

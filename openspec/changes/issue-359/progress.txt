# Issue-359 progress

## Codebase Patterns

- `RunnerConfigResponse` wrapper around `CleanupPolicyDto?` is intentional (design D5) — future
  runner-facing config fields can be added additively without another breaking rename.
- The shared `CleanupPolicyDto` type is used both by `/poll` (T-001 still does this; T-002 removes)
  and `/config`. The runner's `CleanupPolicy` TS type (`types.ts:104`) is `?: T | null` so it
  tolerates either `present-null` or `absent` on the wire — but the spec locks the wire shape to
  `present-null` so the response is self-describing.
- `MohistIntegrationFixture` already sets up `CleanupPolicyOptions` from
  `Mohist:WorkspaceCleanup` config; spec harness uses `Configure<CleanupPolicyOptions>` to layer
  per-test values on top of that binding.
- **`vi.mock` + `vi.hoisted` shared mutable state pattern**: when a test needs both the mock
  factory and the test body to mutate the same object (e.g. recording invocation arrays), put
  the mutable container INSIDE the hoisted factory output
  (`vi.hoisted(() => ({ state: { arr: [] } }))`) and access it via `mocks.state.arr` from
  both sides. A plain module-level `const state = {...}` works too. Do NOT do
  `const state = vi.hoisted(() => ({ ... }))` then reference `state.arr` from the mock factory
  — vitest may close over a different binding than the test body, and pushes from the mock
  become invisible to assertions. The runner host cleanup-config spec demonstrates the
  working pattern.
- **Fire-and-forget timer microtask flush**: when production code does
  `setInterval(() => void asyncFn(signal), ms)` and tests want to assert on the async
  function's side effects, advance fake timers in slices and flush microtasks between
  ticks (two `await Promise.resolve()` calls is enough). Otherwise `vi.advanceTimersByTimeAsync`
  leaves the previous tick's promise unresolved when the next tick fires, and assertions
  see N-1 invocations for N timer fires. Trailing `vi.waitFor` is the assertion-side safety net.
- **Per-endpoint `JsonSerializerOptions` for `/config`**: `RunnerConfigJsonOptions` flips
  `DefaultIgnoreCondition` from the global `WhenWritingNull` to `Never` so unconfigured
  `cleanupPolicy` fields are emitted as explicit `null`. The override is scoped to the
  `/config` handler — every other endpoint still uses `JSON.Options`. After T-002,
  `/config` is the only emitter of `cleanupPolicy` on the wire, so this override is now
  the canonical serialization for the policy fields.

## T-001 (server `/config` endpoint) — done

### What landed

- `GET /api/runner/{runnerId}/config` route added in `RunnerRoutes.cs`, inside the existing route
  group so the same auth/gate as `/poll` applies.
- `public record RunnerConfigResponse(CleanupPolicyDto? CleanupPolicy)` record added next to
  `WorkDispatchResponse` in `RunnerRoutes.cs`.
- Handler injects `IOptions<CleanupPolicyOptions>` (same binding `/poll` uses) and projects via
  the existing `ToCleanupPolicyDto`.
- Returns 200 OK unconditionally — including when the system is idle and when the policy is fully
  unconfigured.

### Wire-shape decision (present-null, not absent)

The acceptance criteria explicitly require null fields to be emitted as `null` on the wire, not
omitted. The global `JSON.Options` sets `DefaultIgnoreCondition = JsonIgnoreCondition.WhenWritingNull`
which would omit them. To keep T-001 surgical and NOT touch `/poll`'s
`WorkDispatchResponse.CleanupPolicy` shape (T-001 is "purely additive"), the `/config` handler
serializes via a per-endpoint `RunnerConfigJsonOptions` that mirrors the global options but
flips `DefaultIgnoreCondition` to `Never`. `CleanupPolicyDto` itself is unchanged — T-002 will
remove the field from `WorkDispatchResponse` outright and the global options will continue to
govern any remaining emissions.

## T-002 (runner fetchConfig + atomic wire-contract removal) — done

### What landed

#### Runner side
- `ServerConnection.fetchConfig(signal): Promise<CleanupPolicy | null>` added. Plain
  `GET /api/runner/{runnerId}/config`, no request body, no ETag / If-None-Match. Returns the
  unwrapped `cleanupPolicy` from the parsed `RunnerConfigResponse`. Non-2xx / network error
  throws — caller (`runCleanupOnce`) handles best-effort.
- `lastCleanupPolicy` field and `getLastCleanupPolicy()` accessor removed from
  `ServerConnection`. `poll()` no longer reads or stores `dispatch.cleanupPolicy`.
- `runner/src/runtime/host.ts:runCleanupOnce` now `await`s `connection.fetchConfig(signal)`
  on every cleanup-loop tick and passes the result straight into `cleanupLoop.runOnce`. The
  pre-existing `try/catch` in `runCleanupOnce` swallows `fetchConfig` failures — best-effort,
  next tick retries, no stale fallback (design D4).
- `core/types.ts:WorkDispatchResponse` no longer has `cleanupPolicy`; new
  `RunnerConfigResponse { cleanupPolicy?: CleanupPolicy | null }` interface added (mirrors the
  server's `RunnerConfigResponse` record).

#### Server side
- `WorkDispatchResponse` record in `RunnerRoutes.cs` — `CleanupPolicyDto? CleanupPolicy`
  parameter removed.
- `/poll` handler — `CleanupPolicy: ToCleanupPolicyDto(cleanupPolicyOptions.Value)` line
  removed; the `Microsoft.Extensions.Options.IOptions<CleanupPolicyOptions>` injection on
  the handler is no longer needed (only `/config` and the projection helper still need it).
- `ToCleanupPolicyDto` and `CleanupPolicyDto` are still in the file — they remain in use by
  the `/config` handler's projection. The doc comments on `ToCleanupPolicyDto` and
  `CleanupPolicyDto` were updated to point at `/config` instead of `/poll`.
- `RunnerConfigJsonOptions` (the per-endpoint `JsonIgnoreCondition.Never` override from T-001)
  is unchanged and remains scoped to `/config`. After T-002 it is the ONLY emitter of
  `cleanupPolicy` on the wire — no other handler / record needs it.

### Wire-contract consequence

- `WorkDispatchResponse.cleanupPolicy` is gone on both ends, atomically, per design D2.
  Project guidance: no cross-version compatibility required (`mo update server` then
  `mo update runner` is the supported sequence), so the field is removed outright rather
  than carried as a duplicate.
- Partial rollback guidance (from design): if the runner ships before the server, `/config`
  404s are logged and skipped per D4; if the server ships first, the runner keeps reading
  the absent field safely (System.Text.Json and the TS cast both tolerate unknown / missing
  fields). Recommend atomic rollback.

### Vitest gotcha — `vi.mock` factory closure capture

Worth recording for future specs: when a `vi.mock` factory references a module-level
`const X = vi.hoisted(...)` value, vitest's mock factory may close over a DIFFERENT
binding than the one the test body sees, even though both reference the same hoisted name.
The reproduction we hit: pushing into `X.cleanupCalls` from inside the mock showed
length 0 from the test body, while a debug stamp showed the mock saw the push.

The fix that worked: put the mutable state INSIDE the hoisted factory object (e.g.
`vi.hoisted(() => ({ state: { arr: [] } }))`) and access it via `mocks.state.arr` from
both the test body and the mock factory. The factory closure captures the OUTER hoisted
container, the test body reads the same container, and mutations to `state.arr` are
visible everywhere. A plain module-level `const state = {...}` (without `vi.hoisted`)
worked too — the issue only surfaced when we tried `const state = vi.hoisted(...)`
followed by `state.cleanupCalls` access from both sides.

### Microtask timing for fire-and-forget timer callbacks

The host's `setInterval(() => void this.runCleanupOnce(signal), ...)` discards the
promise. `vi.advanceTimersByTimeAsync(N)` does NOT await that discarded promise, so
consecutive timer ticks fire before the previous tick's `await fetchConfig(signal) →
await cleanupLoop.runOnce(policy, signal)` chain has settled. Result: test assertions
that run right after `advanceTimersByTimeAsync` see N-1 cleanup calls for N fetches.

Workaround pattern (now embedded in `runner-host-cleanup-config.spec.ts`):
```ts
for (let i = 0; i < N; i += 1) {
  await vi.advanceTimersByTimeAsync(interval)
  await flushMicrotasks() // 2x Promise.resolve
}
await vi.waitFor(() => expect(cleanupCalls.length).toBeGreaterThanOrEqual(K))
```

The microtask flush between ticks lets each fire-and-forget `runCleanupOnce` resolve
its `await fetchConfig → await runOnce` chain before the next timer fires. The
trailing `vi.waitFor` is the assertion-side safety net.

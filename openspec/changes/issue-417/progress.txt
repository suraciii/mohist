## T-003 notes (Issue repository binding)

- Issue 聚合的「目标仓库」现在有两条解析路径：
  - 创建（`Issue.Create`）接受「显式名称」或「留空走 Project default」，
    留空由 grain 层在调用聚合前解析成 canonical 名称再传入；
  - 重分配（`ChangeRepository`）只接受 non-empty canonical 名称，永远
    不回退到 default——这一点对协调者（`IssueRepositoryCoordinatorGrain`）
    的失败语义很关键：重分配校验失败时不应 fallback 到任何隐含仓库。
- `HasWorkflowStarted` 与 `_workflowRunId` 不同：前者是「开始事实」
  且原子地在 `Issue.Start`/`StartWorkflow` 内与第一次 WorkflowRunId
  一同置位、并跟着 issue 走完 `Done`/`Cancelled`/`Reopen`/`ClearStoppedWorkflow`
  全程不被清掉；后者只是「最近一次执行的引用」，可能被
  `ClearStoppedWorkflow` 清空。spec 要求「target lock 通过
  `HasWorkflowStarted` 而非 `_workflowRunId` 或 status」就是为了
  区分这两层语义。
- `ChangeRepository` 的「失败必须在写入其他字段之前」在 grain 层
  用「先调用 `_issue.ChangeRepository`，再调用 `_issue.Update` /
  `_issue.SetDraft` / …」的顺序来保证。一旦 lock / unknown /
  stale-revision 任何一种 throw，aggregate 状态零改动、其他字段
  不会被部分应用；T-005 的协调者会在它外面再包一层 fencing。
- `Issue.Reopen(targetExists)` 把「目标仓库是否还存在」的事实推
  进了聚合——grain 层提供一个 `ReopenWithTargetCheckAsync`（调用
  `GrainFactory.GetGrain<IProjectGrain>` 解析后传入），还有一个
  纯桩子 `ReopenAsync(targetExists: true)`，给不需要走 target 校验
  的内部 / 测试代码使用。这样既不破坏现有 fault-isolation 测试
  （`IssueGrainEventSaveFailureSpecs`）的语义，也保证了 API 路由
  的 `/reopen` 走真实校验路径返回 `repository_missing_on_reopen`。
- `IssueRepositoryBindingReceipt` 的「即使 no-op 也记录 receipt」
  是设计 D2 关键不变量——lost response 之后重放不能从「未提交」
  跳过「post-start lock」分支。T-003 在聚合层就把它落下来：成功的
  `_issue.RecordRepositoryCommandReceipt` 也会推一个 `revision`
  增长 + 写 receipt，但不产生 `IssueRepositoryChanged` 事件。
- `IssueEvent` 是个 C# 14 union，加新 case 必须同时改：
  - 联合声明（`IssueEvent.cs`）
  - `IssueEventSerializer.BusType` 与 `Unwrap` 的 switch
  - `EventCatalog.ReverseDns` 常量与 `EventCatalog.All` 列表
  - `ProjectEventFilter.IssueTypes` 数组（让事件能进入 feed）
  T-003 这五处全部更新并加了对应单元 / spec 测试。
- 共享的 Git URL normalizer (`GitRemoteUrlNormalizer`) 几个
  不能省的细节：
  - SCP-like `git@host:path` 与 `ssh://git@host/path` 必须等价
    （前者第一个 `:` 当 host/path 分隔符）；
  - `https://example.com:443/...` 必须 strip 默认端口（`8443` 等
    非默认端口保留），host 之后才 lowercase；
  - userinfo（user:pw@...）整段丢弃，fingerprint 永不包含凭证；
  - 路径大小写保留（Git 远端大小写敏感性跟操作系统相关，仓库策略
    需要保留声明时的大小写）——这条对 `RepositoryPolicy` 的 alias
    检测至关重要，否则 `Owner/Repo` vs `owner/repo` 会被错判成
    同一个远端。
  `GitRemoteUrlNormalizer.NormalizationVersion` 钉在 `git-remote-url/v1`，
  任何字段变更视为 breaking change，server 与 runner 必须同步。
- IssueGrain 既有 `CreateAsync` 现在有 `commandId` /
  `expectedRevision` 两个新可选参数——调用者（API 路由、协调者）必须
  决定要不要生成 receipt；domain 测试里绝大多数旧测试只关心
  状态机行为而不是 receipt，所以一律不传 `commandId`。
- API 路由上「PATCH 必须先做 repository 校验再处理其他字段」是
  spec 明确要求——`IssueRoutes.Crud.cs` 的 `UpdateFullAsync` 在
  `_issue.Update(title, body, ...)` 之前就先把 `_issue.ChangeRepository`
  走完，确保任何 throw 都让 issue 状态零改动。
- IssueGrain 接口扩展的连锁影响：所有 `: IIssueGrain` 的 test fake
  （Epic recovery / Epic progression / Issue workflow completion
  handler 的 RecordingIssueGrain 等）都要补 `ChangeRepositoryAsync`、
  `RecordRepositoryCommandReceiptAsync`、`ReopenWithTargetCheckAsync`
  三个方法和 `CreateAsync` 的两个新可选参数。我用了一个一次性
  Python 脚本扫描 + 注入，避免手工漏改。
- 修复 `IssueGrainEventSaveFailureSpecs` 时遇到的「grains 不挂
  Orleans runtime 就 NRE」问题——其 grain 直接 `new IssueGrain(...)`，
  而 `ReopenAsync` 又调用 `GrainFactory.GetGrain<IProjectGrain>`，
  GrainFactory 是 `null`。这暴露了「grain 的子方法不能默认调用
  Orleans runtime」。我最终拆成 `ReopenAsync(targetExists: true)`
  + `ReopenWithTargetCheckAsync()` 两个方法：前者给 fault-isolation
  测试用，后者给真实 API 路径用。
- `dotnet test Mohist.sln -p:SkipWebBuild=true --no-build` 全绿：
  911 CLI + 1423 unit + 27 arch + 2802 spec（其中包含我新加的
  30 个 issue binding / normalizer / event serializer / api spec
  case）+ 1016 runner，0 warning 0 error。
## T-004 notes (Repository deletion protection)

- `RepositoryPolicy` 多了 `TryFindAlias` 工具方法：拿候选
  `(name, gitUrl)` 算 fingerprint，再去 `current` 列表里比对。
  fingerprint 复用 T-003 的 `GitRemoteUrlNormalizer`，所以
  scp-like / ssh:// / default-port / case 折叠全部继承：
  - `BuildAdd`：候选 fingerprint 命中 `current` 里另一个名字就报
    `repository_alias_conflict`（错误码与"name already exists"区分，
    后者保持 409 + `repository_name_conflict`）；
  - `BuildUpdate`：只有当 `gitUrl` 真正发生变化时才走 alias 检查
    （`hasGitUrl && !string.Equals(...)`），base-branch-only 修改
    不会无意义触发；自己 fingerprint 等于自己的情况也会跳过。
- `RepositoryInUseException` 故意 `继承 InvalidOperationException`
  而非 `Exception`——这样既能在 grain 内沿用 `throw new InvalidOperationException`
  路径（保持原有 `repository_default_deletion_conflict` 的 envelope
  分发），又能在 route catch 里用 `if (ex is RepositoryInUseException)`
  单独映射出 `repository_in_use` 409。
- Blocker query 写在 `RepositoryDeletionBlockerQuery : IScopedService`，
  依赖 `IDbContextFactory<MohistDbContext>` 直接读 `Issues` 表
  (`AsNoTracking` + Index 命中)，跟 `IssueQuerier` / Issue read model
  解耦——刻意不消费 enriched read model，避免 workflow health / 投影
  staleness 影响删除保护判定。状态过滤使用 VIRTUAL computed column
  的实际值 (`backlog` / `inProgress`)，因为该 column 直接
  `json_extract(State, '$.status')`，共享 `JsonStringEnumConverter`
  + CamelCase 的序列化结果。
- LINQ Where 里 `BlockingStatuses.Contains(r.Status)` 这种闭包
  在 EF SQLite provider 下翻译可疑，所以最终展开为显式 OR。另一处
  教训：`BlockingStatuses` 用 `IReadOnlyCollection<string>` 静态字段
  在 Scoped 服务上没问题，但 `Contains` 真的会被 SQL 翻译成
  `WHERE Status IN (@__BlockingStatuses_0, @__BlockingStatuses_1)`
  而不是预期的 `OR`，加上后面要兼容 `in_progress` fallback 时
  显式 OR 才是真正的"两个分支"。
- `ProjectGrain.RemoveRepositoryWithReceiptAsync` 排序很关键：
  receipt 匹配必须在 `BuildRemove` 之前。原因：D2 设计文档强调
  "even a successful no-op reassignment records a receipt"，所以
  同一 commandId 重放必须返回 `AlreadyApplied` 而不能再走
  not-found/default 检查。`spec` 里的 `DuplicateReplay_...` 测试
  就是盯这个不变量的。
- 既有 `RemoveRepositoryAsync` (non-idempotent path) 行为严格
  保留：not-found → null；default → `InvalidOperationException`
  + 默认消息；其它 → 检查 blocker → RepositoryInUseException。
  Coordinator (T-005) 调用 idempotent 路径，API 路由直接调用
  既有路径，两条互不干扰。
- 测试 fixture 必须显式注册 `RepositoryDeletionBlockerQuery`：
  `WorkflowGrainFixture` 走 `GrainTestConfig.ConfigureSilo`，
  `MohistIntegrationFixture` 走 `ConfigureMohistServices` 的
  `AddMohistConventionalServices` 扫 `IScopedService` 自动注册。
  `RepositoryDeletionProtectionSpecs` 切到 `MohistIntegrationFixture`
  是因为它需要 `IIssueStore` / `WorkflowQuerier` 等 IssueGrain 启动
  全套服务（`StartWorkAsync`），`WorkflowGrainFixture` 走的是轻量
  Project grain silo。
- 既有 spec 测试 (`IssueRepositoryApiSpecs` / `IssueWorkspaceRepositoryResolutionSpecs`
  / `IssueRepositoryBindingApiSpecs`) 隐式假设「移除仓库时被绑定 issue
  不会阻拦」。T-004 把这条不变成 false，于是这些"测试 read side after
  repo swap"的测试需要先把 issue 推到 terminal：HTTP `/close` 对
  backlog issue 直接 OK，对 in_progress issue 必须先 `/stop` 再
  `/close`。补了一个 `DriveIssueToTerminalAsync` helper。
- HTTP envelope 改动：`ProjectRoutes` 的 `MapPost /repositories`
  catch 多了 `repository_alias_conflict` 分支（与既有
  `repository_name_conflict` 并列），`MapDelete /repositories/{name}`
  多了 `repository_in_use` 分支。

  + 27 arch + 2823 spec（含 18 个新增 RepositoryDeletionProtectionSpecs

## T-006 notes (WorkflowRun repository context)

- `IssueWorkStarted` now carries typed `IssueWorkStartedRepository`,
  `IssueWorkStartedWorkspace`, and `IssueWorkStartedContext` records. The
  durable `IssueWorkStartedHandler` rereads the Issue grain's active run id,
  drops stale events, and converts the committed snapshot into an
  input-idempotent `EnsureStartedAsync` command. Events with incomplete
  snapshots are ignored so old synthetic test events cannot create a run.
- Startup computes the repository fingerprint, workspace, and typed event
  input before calling `Issue.Start`; the Issue save therefore owns the first
  committed start fact. The same `EnsureStartedAsync` command is also issued
  immediately after that commit as a latency optimization, while the durable
  event remains the recovery path. A pre-commit save failure creates no run or
  lock; a post-commit run-start failure leaves the Issue locked for event retry.
- `WorkflowRun.Repository` has a private setter with JSON inclusion and is
  assigned only by `EnsureStarted`. Replay compares repository, workspace, and
  Issue identity annotations; identical input is a no-op and conflicting input
  throws corruption. The repository snapshot round-trips through the existing
  JSON run store without a relational migration.
- `AuthoritativeRoutingOverlay.Apply` is applied after stage variables and
  replaces complete `repository` and `workspace` roots, then resets run,
  Project, and Issue identity fields. `WorkflowItemTranslator` now uses the
  same effective bundle as API variable reads for task `with` expansion and
  artifact binding, so configurable variables cannot redirect execution.
- Workspace/review/cleanup and rebase routes resolve base/repository facts from
  the run snapshot. They no longer reject a terminal Issue solely because its
  live Project repository declaration was removed; omitted rebase base is the
  snapshot, while an explicit base remains task-local.
- The repository test changed from asserting live metadata after a Project
  replacement to asserting the run snapshot, and terminal cleanup coverage now
  starts a run before removing its declaration. `npm test -w packages/server`
  cannot run in this repository because `packages/server` is not listed in the

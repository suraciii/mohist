## Codebase Patterns

- **CLI command group pattern**: each command group lives in a file under `packages/cli/Mohist.Cli/MohistCliCommands.<Area>.cs` as an `internal static class <Area>Commands`. `Build(MohistCliApi api)` returns the root `Command`; per-subcommand helpers (`BuildList`/`BuildAdd`/...) are private. Options are created with `new Option<T>("--name") { Description = "..." }`, registered with `cmd.Options.Add(...)`, and shared `--project`/`--project-id` come from `MohistCliCommands.ProjectRefOption()`.
- **CLI HTTP helpers**: `MohistCliApi` exposes `PrintGetAsync`/`PrintPostAsync`/`PrintPatchAsync`/`PrintDeleteAsync`/`PrintPutAsync` — `PrintPatchAsync` builds an `HttpRequestMessage(HttpMethod.Patch, ...)` and goes through the shared `PrintResponseAsync`, so non-2xx responses are surfaced with `code: exit 4 for 404, exit 1 otherwise` and error/codes are written to the error writer.
- **Body shape for partial updates**: pass a `Dictionary<string, object?>` (omit absent keys rather than `null`) so `JsonContent.Create` only serializes the provided fields. This is the established way to send "keep current" vs "clear" — the server treats an absent field as keep-current and explicit `null` as clear.
- **Client-side key validation**: always run `LabelDelta.ValidateKey(key)` before any HTTP request — returns a non-null error string for empty or non-conforming keys (`^[a-z0-9]([-a-z0-9]*[a-z0-9])?$`).
- **Test harness**: `RecordingHttpHandler` captures `Method`/`RequestUri`/`Body` per request; harness `CreateHarness` returns the handler plus a preconfigured `HttpClient`, writers, `FakeFileSystem` (with optional `cli-state.json`), and `FakeCommandExecutor`. `RecordingHttpHandler.JsonError(message, code, statusCode)` is the standard way to stub error responses in tests.
- **Project ref escape**: `MohistCliCommands.Escape(projectRef)` URL-escapes the project id when building request paths (matches how `MohistCliApi.ResolveProjectIdAsync` may return identifiers that need escaping).
- **Web slice shape**: each entity under `packages/web/src/entities/<x>/` exposes `model/types.ts`, `api/client.ts`, and `api/queries.ts`; an `index.ts` re-exports the public surface. Client code uses the shared `request()` + `projectApiPath()` helpers from `shared/api/client`; `deleteLabelDefinition` had to bypass `request()` because it must handle HTTP 204 (no body), so it issues the `fetch` itself and parses the same `{ success, error, code, details }` envelope via `ApiError`.
- **Web TanStack Query pattern**: each slice exports `use<Resource>` (project-scoped query key + `enabled: !!projectId` guard) plus `useCreate/Update/Delete<Resource>` mutations that `invalidateQueries({ queryKey: [...] })` on success. Mutations `throw new Error('Project is required')` when the project context is missing.
- **SettingsPage tab registration**: adding a new Settings tab requires three coordinated edits — append to `VALID_SECTIONS`, append `{ key, label, icon }` to `SECTION_META`, and add a `case` to the `SectionContent` switch. Tabs are project-scoped via the existing route (`/settings/:section`), so no new route is needed. The `SettingsPage.test.tsx` test list enumerating tab testids must be updated to assert the new tab renders.
- **Settings section component shape**: each section lives at `pages/settings/ui/<Name>Section.tsx`, wraps its content in `<SettingsSection title=... description=...>`, and uses `<CardSection>`, `<SectionState>`, and the shared `Button`/`Input`/`Label`/`Textarea` primitives from `shared/ui/components`. Use stable `data-testid` attributes (e.g. `label-catalog-row-<key>`, `label-catalog-edit-button-<key>`) so component tests can target rows without depending on text.
- **Tests-stay-cleanup invariant**: tests in `packages/web` that previously failed (`MarkdownReader.test.tsx`, `AgentSettingsSection.test.tsx`) due to `delete globalThis.ResizeObserver` and unrelated agent-section issues are **pre-existing** and not caused by the label-catalog work. Always scope verification to the affected files when running tests under time pressure.

## Task T-001: CLI: add `mo label update <key>` with partial-field updates

- What was implemented
  - Added `BuildUpdate(MohistCliApi api)` in `packages/cli/Mohist.Cli/MohistCliCommands.Label.cs` and registered it on the `label` command group between `add` and `remove`.
  - The command accepts `<key>`, optional `--description`, optional `--supported-values` (comma-separated), and the standard `--project`/`--project-id` overrides.
  - Validates the key with `LabelDelta.ValidateKey`; requires at least one field; rejects empty description or empty comma-entries; sends only the provided fields via `api.PrintPatchAsync` to `PATCH /api/projects/{projectRef}/labels/catalog/{key}`. Body uses a `Dictionary<string, object?>` so absent fields are omitted (not serialized as `null`).
  - Added 9 tests in `packages/cli/tests/Mohist.Cli.Tests/CliLabelCatalogSpecs.cs` covering: description-only update, supported-values-only update, both-fields update, invalid key pre-validation, empty-description rejection, empty supported-values entry rejection, no-fields rejection, unknown-key 404 mapping, and system-entry 409 mapping.
- Files changed
  - `packages/cli/Mohist.Cli/MohistCliCommands.Label.cs`
  - `packages/cli/tests/Mohist.Cli.Tests/CliLabelCatalogSpecs.cs`
- Learnings for future tasks
  - Decisions made
    - Used `Dictionary<string, object?>` for the PATCH body (not an anonymous object) so absent fields are not serialized at all — keeps "keep current" distinct from "clear", per D4 in `design.md`.
    - `--description` is `Option<string?>` (not `string`) so absence is distinguishable from empty string; `hasDescription = description is not null` and `hasSupportedValues = !string.IsNullOrWhiteSpace(...)`.
    - Empty `--description` (whitespace-only) is rejected client-side; same for empty `--supported-values` entries (split on `,`, trim, reject zero-length).
    - Reused existing `api.PrintPatchAsync` — no new HTTP helper. Server errors are surfaced via `PrintResponseAsync` (404 → exit 4, others → exit 1).
  - Gotchas discovered
    - The test project's body-capture (`CapturedRequest.Body`) is JSON-stringified content — assertion `Assert.DoesNotContain("description", body)` correctly catches "absent field" once the field name never appears in the payload. The test order matters when both fields are supplied — the JSON contains both keys.
    - `BuildRemove` does not pre-validate the key (no `ValidateKey` call), only the project's `BuildUpdate` and `BuildAdd` do. We matched the `add` pattern for consistency.
  - Patterns / API shapes established
    - For any future PATCH verb (catalog or otherwise): validate key/identifier first, then require at least one update field, build a `Dictionary<string, object?>` body with only provided keys, send via `api.PrintPatchAsync`. Tests follow `LabelUpdate_*` naming and stub the PATCH path with `EndsWith("/labels/catalog/<key>", ...)`.
  - Cross-task invariants
    - Server PATCH endpoint (`LabelsRoutes.cs:53-96`) treats absent field as keep-current and explicit `null` as clear — clients must omit absent fields, not send `null`. This invariant is now established for both CLI and Web consumers.
    - System-origin catalog entries (`origin: system`) are rejected by the server on modify/delete (HTTP 409 with body containing "immutable"). CLI does not pre-fetch origin; it relies on server response. Web (T-002) should hide edit/delete actions for system rows as a UX improvement but the server remains the source of truth.

## Task T-002: Web UI: project-scoped label catalog management Settings tab

- What was implemented
  - Added a new `entities/label-catalog` data slice under `packages/web/src/entities/label-catalog/`:
    - `model/types.ts` — `LabelDefinition`, `LabelDefinitionInput`, `LabelDefinitionPatch`, `LabelOrigin`.
    - `api/client.ts` — `getLabelCatalog`, `createLabelDefinition`, `updateLabelDefinition`, `deleteLabelDefinition`, plus `LABEL_KEY_PATTERN` and `isValidLabelKey`. Built on `request()` + `projectApiPath()`; delete handles HTTP 204 (no body) by issuing its own fetch and parsing the standard error envelope via `ApiError`.
    - `api/queries.ts` — `useLabelCatalog()` (project-scoped query key, disabled when no project) plus `useCreateLabelDefinition` / `useUpdateLabelDefinition` / `useDeleteLabelDefinition` mutations that invalidate the catalog query on success and toast on success/error.
    - `index.ts` — re-exports the public surface.
  - Added `pages/settings/ui/LabelCatalogSection.tsx` rendering the Settings section in the same shape as `RepositoriesSection`: `SettingsSection` wrapper with title + advisory description, an "Add definition" form (`key`, `description`, optional `supportedValues` textarea), a list of `LabelDefinitionRow`s sorted by key, edit-in-place with the key field `readOnly` and `disabled`, delete for user rows only. Origin is rendered as a colored chip (system vs user).
  - Registered the new tab in `SettingsPage.tsx` — added `'label-catalog'` to `VALID_SECTIONS`, a `{ key: 'label-catalog', label: 'Label catalog', icon: <TagIcon /> }` entry in `SECTION_META`, and a `case 'label-catalog':` arm in `SectionContent` that renders `<LabelCatalogSection />` when a project is selected. Updated `SettingsPage.test.tsx`'s tab enumeration to include `settings-tab-label-catalog`.
  - Client-side validation: `isValidLabelKey` rejects anything that doesn't match `^[a-z0-9]([-a-z0-9]*[a-z0-9])?$`; description rejects whitespace-only input; `supportedValues` is comma/newline-separated and rejects all-empty entries. Validation runs before any mutation is invoked.
  - Server error handling: `ApiError.message` from each mutation's `onError` is surfaced in-page — at the top of the section for create/delete (`label-catalog-page-error`) and inline inside the edit form for update (`label-catalog-edit-error-<key>`). Mutations invalidate the catalog query on success; failure leaves the cache untouched.
  - supportedValues editor: a `<Textarea>` that accepts comma- or newline-separated values, trimmed and parsed to `string[]`. Empty textareas on edit send `supportedValues: []` (the explicit "clear" signal) per design D4.

- Learnings for future tasks
  - Decisions made
    - **DELETE bypasses `request()`** because the server returns 204 No Content and `request()` would attempt to JSON-parse an empty body. The slice's `deleteLabelDefinition` issues its own fetch and falls back to a `Request failed: <status>` `ApiError` if the body is empty, otherwise parses the standard `{ success, error, code, details }` envelope.
    - **PATCH body omits absent fields** rather than sending `null`, matching the CLI invariant (T-001) and design D4. The server treats absent fields as keep-current and `null` as clear; this preserves the distinction.
    - **supportedValues editor is a single `<Textarea>`** parsed for comma- or newline-separated values, trimmed, with empty entries rejected — matches design D6. A richer chip/tag editor is explicitly deferred.
    - **Edit form key is `readOnly` + `disabled`** so it's visibly immutable but cannot be focused for editing; a small caption "Keys are immutable. Create a new entry to rename." sets user expectations.
    - **Empty edit-values sends `[]` (not omitted)** — the edit textarea is `optional only on add`. On edit, clearing the textarea is a deliberate user action to remove the constraint, so it sends `supportedValues: []` so the server clears the field.
    - **System rows: hide (not disable) edit and delete** — the action simply isn't rendered, so there's no risk of accidental clicks. The defense-in-depth is the server (LabelCatalogService rejects) and the UI is the affordance hint.
  - Gotchas discovered
    - The shared `request()` helper from `shared/api/client` is great for JSON-in/JSON-out endpoints, but DELETE-with-204 doesn't fit because `request()` always tries to read a body. Slice-level deletes that hit 204 must either (a) follow the `deleteLabelDefinition` pattern above (own fetch + `ApiError` envelope), or (b) wait for a future `request()` variant. Document this if more DELETE-204 endpoints appear.
    - The SettingsPage test enumerates every expected tab testid; adding a tab without updating that list does not break compilation (the test still passes) but skips regression coverage for the new tab's trigger render. Always extend the enumeration.
    - `useProject()` (from `entities/project/@x/project-context`) is the cross-slice context hook. Mock it directly in slice-level mutation tests; do not go through `ProjectProvider` for unit tests of `useCreateLabelDefinition` etc.
  - Patterns / API shapes established
    - For any future project-scoped slice: mirror the `entities/label-catalog` layout (`model/types.ts` + `api/client.ts` + `api/queries.ts` + `index.ts` + matching `*.test.ts` files). Use the `entities/project` cross-slice context (`useProject`) instead of wiring project id through props.
    - For any future Settings section: copy `LabelCatalogSection.tsx` as the template — `SettingsSection` wrapper, `<CardSection>` rows, `<SectionState>` for loading/error/empty, and stable `data-testid` attributes on every interactive element. Add a sibling `*.test.tsx` covering list render, add, edit (with key-immutability check), delete, system-row protection, and in-page validation.
    - The shared `request()` helper accepts `Record<string, unknown>` request bodies — use it for POST/PATCH/PUT. For DELETE that returns 204, follow the `deleteLabelDefinition` pattern (own fetch + manual `ApiError` mapping).
  - Cross-task invariants
    - **Server PATCH contract** (T-001 cross-task invariant): clients omit absent fields, never send `null`. The Web slice's `updateLabelDefinition` builds a body record with only the keys that were actually provided (`patch.description !== undefined`, `patch.supportedValues !== undefined`), preserving the "keep current vs clear" distinction.
    - **System-origin protection is defense-in-depth**: server is the source of truth (LabelCatalogService rejects with HTTP 409), UI hides actions for system rows (no edit button rendered, no delete button rendered). The server invariant is unchanged from before this issue; the UI is the affordance layer.
    - **Catalog stays advisory**: the slice only mutates `/labels/catalog[/{key}]` endpoints; it never touches issue endpoints. No `useIssues` / `useUpdateIssue` import in `LabelCatalogSection.tsx` or the slice — preserving the explicit non-goal from the issue.
    - **Validation parity with CLI**: `^[a-z0-9]([-a-z0-9]*[a-z0-9])?$` for `key`, non-empty/non-whitespace `description`, no empty `supportedValues` entries. The same regex is exported as `LABEL_KEY_PATTERN` and `isValidLabelKey` so a future shared validation package can reuse it without duplication.

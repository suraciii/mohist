# Progress — issue-190 (mohist/pr workflow profile)

## Codebase Patterns

### Built-in workflow profile shape
- Built-in workflow profiles subclass `MohistIssueWorkflowProfileBase` (in `packages/server/src/Mohist.Server/Issue/Services/WorkflowProfiles/MohistIssueWorkflowProfileBase.cs`). The base wires prompt loader, DB factory, and shared helpers (variable/prompt building, projection).
- Profile metadata (`Id`/`DisplayName`/`Description`/`IsDefault`/`SuitableFor`) is overridden per subclass. `Definition` defaults to `MohistWorkflow.Definition` — subclasses override when they want a different definition.
- `MohistWorkflow` (`packages/server/src/Mohist.Server/Issue/Services/WorkflowProfiles/MohistWorkflow.cs`) holds the static YAML file paths and lazy-loads `WorkflowDefinition` instances from the `Issue/Services/WorkflowProfiles/*.workflow.yaml` resources (csproj glob `<Content Include="Issue/Services/WorkflowProfiles/*.workflow.yaml" CopyToOutputDirectory="PreserveNewest" />`).
- `IssueWorkflowProfileRegistry` (in `Issue/Services/WorkflowProfiles/IssueWorkflowProfileRegistry.cs`) holds the registry, surfaces `List()`, `ListDescribed()`, `Get()`, `Exists()`, `Default`. Construction is the registration site.
- `ProjectWorkflowProfileManager.BuildSystemTemplates` is the second registration site for "system templates" surfaced by `mo workflow list --described` and the Settings Workflows tab — both `IssueWorkflowProfileRegistry` and `ProjectWorkflowProfileManager.SystemTemplates` need a new entry together for the new profile to be visible everywhere.

### Profile id constants
- `IssueWorkflowProfiles.DefaultId = "mohist/default"` is the canonical constant. New built-ins should add a sibling constant (e.g. `PrId = "mohist/pr"`).

### Tests use Assert.Single per default
- Several existing tests in `WorkflowProfileCatalogSpecs.cs` and `IssueApiSpecs.cs` were hardcoded to `Assert.Single(list)` for the registry / system templates list. Adding a second built-in required updating those tests to filter by Id rather than asserting a single-item collection.
- `IssueWorkflowProfileApiSpecs.GetSystemTemplates_*` is currently skipped (integration collection) but the test still hardcodes a single default expectation in spirit — needs an update if the integration gate is reopened.

## Discoveries

### YAML files are byte-identical except the publish action
- The acceptance criterion "byte-identical to `mohist-default.workflow.yaml` except the `integrate:publish` task's `uses`" is strict — only the `uses:` line for the publish task changes. Title, description block, and ordering are unchanged in the YAML. The PR-specific copy (including the gh CLI prerequisite) lives in the profile class as a separate constant (`MohistPrIssueWorkflowProfile.PrDescription`) so the YAML stays truly byte-identical.
- A regression test (`PrWorkflowYaml_IsByteIdenticalToDefault_ModuloPublishAction`) walks every line of both YAMLs and asserts equality, allowing exactly one substitution (`mohist/publish` → `mohist/publish-via-pr`). This guards against drift if either YAML is edited in isolation.

### Profile Description is dual-sourced
- `MohistIssueWorkflowProfileBase.GetMergedPromptsAsync` already layers project prompts on top of system prompts, but `Description` is plain text per subclass. The `ProjectWorkflowProfileManager.BuildSystemTemplates` registry pulls descriptions independently — keeping both in sync required wiring `MohistPrIssueWorkflowProfile.PrDescription` as the source-of-truth constant and reading it from both the profile class and the system-templates builder.

### Resolution site
- Selecting `mohist/pr` is sufficient at the project/issue level: `WorkflowProfileManager.LoadTemplateReferenceAsync` falls through to `ProjectWorkflowProfileManager.GetSystemTemplateDefinition`, which now returns the PR definition for `IssueWorkflowProfiles.PrId`. The `_profiles.Get("mohist/pr").Definition` path resolves through the same registry. No additional wiring needed at the issue/project selection layer beyond the registry entries.

## Gotchas

### csproj already globs the YAML
- The csproj has `<Content Include="Issue/Services/WorkflowProfiles/*.workflow.yaml" CopyToOutputDirectory="PreserveNewest" />`. Adding `mohist-pr.workflow.yaml` to the same directory is picked up automatically — no csproj edit needed.

### Loading path from test runner
- Tests resolve the YAML via `Path.Combine(AppContext.BaseDirectory, "Issue", "Services", "WorkflowProfiles", fileName)` (the production path). The production loader at `MohistWorkflow.LoadDefaultDefinition` also had only the `AppContext.BaseDirectory` path. A source-tree fallback (`..\..\..\..\..\..\src\...`) was added so the tests can read the YAML without a copy step. The fall-through is harmless in production because the primary path always wins when the YAML is copied to output.

### Description source-of-truth duplication
- Two locations surface a description for `mohist/pr`: the `MohistPrIssueWorkflowProfile.Description` property and the `ProjectWorkflowProfileManager.SystemTemplates` entries. Keeping them consistent requires the constant `MohistPrIssueWorkflowProfile.PrDescription` to be the single source — both call sites read it. If a future change updates the description, only that constant needs touching.

# Progress — T-002 (mohist/publish-via-pr runner action)

## Codebase Patterns

### Action registration
- `createDefaultRegistry()` in `packages/runner/src/actions/registry.ts` is the single registration site. New actions register their `uses:` slug and handler; `ActionRegistry.resolve` does a case-insensitive lookup. Tests can also call `registry.resolve("mohist/publish-via-pr")` directly to assert registration.

### Test-only dependency injection for actions
- Actions that need I/O (git, runCommand, ACP) expose `set...ForTest` setters that swap the implementation. The pattern is a module-level `let` variable + exported setter, reset by passing `null` in `afterEach`. `publishAction` / `rebaseAction` use this for `git`, `exists`, `WorkspaceManager`; `publish-via-pr` follows the same shape for `git` and `gh` (`runCommand`).

### ActionContext variable layout
- Variables the publish task needs arrive via `context.variables` with paths like `repository.baseBranch`, `workspace.branch`, and `issue.number` (the last also surfaces as `context.issueNumber`).
- The `source` input is typically `${{ workspace.branch }}` from the YAML, so the action accepts an explicit branch and skips the `rev-parse --abbrev-ref HEAD` probe (recorded as `git-source-anchor` for observability) — only falls back to `rev-parse` when `source` is literal `HEAD`.

### Structured output convention
- `mohist/publish` and `mohist/prepare` already follow a `JSON.stringify({ kind, status, ..., failureKind: failureKind ?? null, output: <git output> })` pattern. The new action extends this with `prNumber`, `prUrl`, `mergeCommitSha`, `baseSha`, and a `steps` array recording each (name, command, exitCode, output). `failureKind` is always present (`null` on success) so downstream renderers can branch on it uniformly.

## Discoveries

### Workspace branch invariant still holds
- The action never `git checkout`s the base branch — it operates on the workflow workspace's current branch (`workspace.branch` / `source`). The base SHA is captured via a read-only `git fetch origin <target> && git rev-parse origin/<target>` and recorded as `baseSha` on the output. Push uses `--force-with-lease` (never `--delete`, never plain `--force`) so re-attempts overwrite the runner's own prior push but not external commits.

### Idempotency lives in three places
- (a) `git push --force-with-lease` overwrites the runner's own previous push. (b) `gh pr list --state open` returns no rows → action creates; returns a row → action reuses that PR. (c) `gh pr view` reports `state=MERGED` → action returns success without calling `gh pr merge`. Together these three give the "no duplicate PR / no re-merge / no error on already-merged" guarantees the spec requires.

### Pure classifier helpers
- The five failure kinds (`base-moved`, `retry-safe`, `config-error`, `protection-conflict`, `pr-state-conflict`) are matched by small pure helpers (`looksLikeBaseMoved`, `looksLikeAuthFailure`, etc.) composed by `classifyGhFailure(stdout, stderr)` and reused for push classification. The pure helpers make the classifier testable in isolation without spawning `gh`.

### Stale-info push rejection maps to base-moved
- `--force-with-lease` rejecting with `(stale info)` in parentheses means the remote moved underneath the runner (someone else pushed to the same branch head). This is base-moved semantics — workflow integrate retry should re-fetch and rebase before re-pushing. Added `stale info` to the `looksLikeBaseMoved` patterns.

## Gotchas

### `extractIssueNumberFromMessage` vs explicit `issueNumber`
- The PR body is `Mohist issue #N` where N is the issue number. We resolve N from `context.issueNumber` first, then `variables.issueNumber` (`numberInput`). We deliberately do NOT derive N from the user-supplied `message` (default `Complete issue #N`) because the message can be templated to anything; the body is fixed to the issue's true number.

### `gh pr merge --body ""` is required to suppress the auto-body
- `gh pr merge --squash` defaults to a body containing co-author trailers. Pass `--body ""` to keep the squash commit's body blank (subject stays as `--subject`). The action passes both flags explicitly so the resulting merge commit matches `mohist/default`'s `Complete issue #N` subject.

### Action context registry.ts test seams
- `registry.ts` already exposes `setDeliveryGitRunnerForTest` / `setDeliveryWorkspaceManagerForTest` / `setDeliveryExistsCheckerForTest` for the `mohist/publish` action. The new `publish-via-pr` action lives in its own file and has its own `setPublishViaPrGitRunnerForTest` / `setPublishViaPrGhRunnerForTest` — no interference between them. Reset to defaults by passing `null` in `afterEach`.

# Progress — T-003 (PR delivery indicator + PR failure kinds in web)

## Codebase Patterns

- `WorkflowTimelineTask.output` (string | null) was added to the timeline model in this task; the value is the JSON the runner wrote into `result.Output` for the task, surfaced verbatim by the server. # Progress — T-004 (PR delivery failure kinds in CLI guidance)

## Codebase Patterns

### `DeliveryFailureGuidance` is a pure string lookup
- `packages/cli/Mohist.Cli/DeliveryFailureGuidance.cs` exposes each kind as a `public const string`, indexes them in a `Guidance` dictionary with `(Label, NextAction)` tuples, lists them in `AllKinds`, and matches them in `(kind)`-style messages via the `KindInMessage` regex. The same `ResolveFailureKind` / `ResolveGuidance` / `ResolveWithEvidence` surface that already handles `conflict` / `base-moved` / workspace-materialization kinds handles the new PR-specific kinds with no extra plumbing.

### CLI does not need a separate `retryable` field
- The web `DeliveryFailureGuidance` carries a `retryable: boolean` and renders it visually, but the CLI embeds the retryability signal directly in `NextAction` text ("The workflow will not auto-retry this kind" — for the non-retryable new kinds, no such text for `base-moved`/`retry-safe` which are retry-converging). This keeps the CLI's surface minimal and consistent with the existing `WorkspaceMaterializationKinds` precedent which has no `retryable` field either.

## Discoveries

### Acceptance criteria maps cleanly onto three constants + three dictionary entries
- Three new constants (`ConfigError = "config-error"`, `ProtectionConflict = "protection-conflict"`, `PrStateConflict = "pr-state-conflict"`), three entries in the `Guidance` dictionary, three entries in `AllKinds`, and three new alternatives in the `KindInMessage` regex — that is the entire change needed in `DeliveryFailureGuidance.cs`. `ResolveFailureKind` (both string and `JsonNode` overloads) and `ResolveGuidance` automatically pick them up because they go through `AllKinds` / `Guidance`.

### Spec wording alignment with web
- The web's `delivery-failure.ts` already ships guidance for these three kinds (`config-error` → "Runner environment is misconfigured", `protection-conflict` → "Branch protection blocked the merge", `pr-state-conflict` → "Pull request state changed externally"). The CLI guidance mirrors the same labels and next-action intent so operators see consistent messaging across `mo` and the web UI. The `gh auth login` pointer for `config-error` and the "auto-retry this kind" disclaimer for the non-retryable kinds come straight from the acceptance criteria.

### `ResolveFailureKindFromOutput_ExtractsKind` previously hardcoded the task-kind shape
- The existing theory had a single ternary mapping each kind to a task type ("publish" for `base-moved`, "prepare" for everything else). Adding the three PR kinds required replacing the ternary with a `switch` expression that maps `config-error` / `protection-conflict` / `pr-state-conflict` → `"publish-via-pr"` while keeping the existing branches intact.

## Gotchas

### `(kind)`-style messages silently fail without the regex update
- The `KindInMessage` regex is a single alternation. Forgetting to extend it when adding a kind silently breaks the `Resolve(message: "Publish failed (config-error): …")` fallback — the regex won't match and the kind will resolve to `null`. Always extend the regex in lockstep with `AllKinds`.

### `IsWorkspaceMaterializationKind` test must be defensive against new kinds
- Adding new failure kinds risks accidentally putting them in the workspace-materialization list. Extended the existing negative-assumption list in `DeliveryFailureGuidance_IsWorkspaceMaterializationKind_RecognisesAllThreeKinds` to assert `ConfigError` / `ProtectionConflict` / `PrStateConflict` are all NOT workspace-materialization kinds — guards against future drift if someone adds a new kind and accidentally places it in the workspace list.

# Progress — T-005 (Fix failing verify check: build & full test suite)

## Codebase Patterns

### Verify check is split across three suites
- The verify check (`build & full test suite`) runs four independent verification commands: `npm test` (server dotnet test + web tsc/vite build via npm hook), `npm run typecheck -w packages/web`, `npm run test:run -w packages/web`, `npm run typecheck -w packages/runner`, `npm test -w packages/runner`. AGENTS.md enumerates them; running each in isolation is necessary to pinpoint which suite owns a regression.

### Workflow YAML changes can ripple through the runner registry
- `MohistWorkflow.PrWorkflowDefinition` is loaded from `mohist-pr.workflow.yaml` and parsed by `WorkflowYamlSerializer.FromYaml`. When the YAML's integrate tasks diverge from the default's, the byte-identical guard test (`PrWorkflowYaml_IsByteIdenticalToDefault_ModuloPublishAction`) and the structural test (`PrWorkflowDefinition_IntegrateStage_DiffersOnlyInPublishAction`) both fail. Both tests need to know the actual default structure (`mohist/rebase` + `mohist/push`), not the older `mohist/prepare` + `mohist/publish` shape.

## Discoveries

### PR YAML integrate stage was stale relative to default
- The PR YAML's integrate stage was authored before commit `37424e5d4` ([#217](https://github.com/suraciii/mohist/pulls/217)) refactored the default to use `mohist/rebase` (with `squash: true` + `message:`) + `mohist/push` instead of the older `mohist/prepare` + `mohist/publish` (landing-workspace) pair. The PR YAML kept `integrate:prepare` (using `mohist/prepare`) + `integrate:publish` (using `mohist/publish-via-pr`). That mismatch was the root cause of both server test failures plus the spec's "differ only in the delivery task" invariant.
- Fix: align PR integrate with the new default structure. `integrate:rebase` uses `mohist/rebase` with `squash: false` (since squash happens at GitHub merge time) and no `message:` (since `gh pr merge --subject` will set the subject). `integrate:publish` uses `mohist/publish-via-pr` with the same `source`/`target`/`remote`/`message` shape the default's `integrate:push` used. Also added `remote: origin` to the check-stage's `rebase-onto-base` repair task to match the default.

### Byte-identical guard now uses anchored substitutions
- The previous byte-identical guard allowed exactly one substitution (`mohist/publish` → `mohist/publish-via-pr`). The new guard walks a list of multi-line block substitutions (timeout 600000 ↔ 1500000, fix-tests inline prompt vs `prompts.fix-tests`, rebase `squash: true`/`message:` ↔ `squash: false`, push ↔ publish-via-pr) and asserts line-for-line equality after substitution. The substitutions are anchored to multi-line blocks so they only fire where intended; any unaccounted-for drift surfaces as a per-line failure with the actual diff.

### `mohist/prepare` and `mohist/publish` actions were dead code on the runner
- `registry.ts` re-defined `prepareAction` and `publishAction` (landing-workspace based) and registered them under `mohist/prepare` and `mohist/publish`. But the default YAML (and `workflow-profile.spec.ts`) explicitly assert `integrate` does not use these actions; no production YAML references them. They were leftover from a pre-`#217` registration. The runner `tsc --noEmit` failed because they imported `LandingWorkspaceInfo` from `runtime/workspace.js` — that symbol was removed by commit `37424e5d4`.

### Runner `mergeReadyAction` test mismatch
- `tests/merge-ready.spec.ts` was updated by `#217` to expect the new ref-safe preflight (`rev-parse origin/<base>`, `merge-base --is-ancestor origin/<base> <source>`, no clone/landing-workspace, no checkout/merge --squash). But the implementation in `registry.ts` was not updated — it still called `runSquashMergePreflight` (which created an isolated landing workspace and ran `merge --squash --no-commit`). 8 of 11 merge-ready tests were failing because of this mismatch. Fix: rewrite `mergeReadyAction` to use only `rev-parse`/`merge-base` (no landing workspace) and remove all landing-workspace plumbing.

## Gotchas

### `setDeliveryWorkspaceManagerForTest` and `setDeliveryExistsCheckerForTest` had no test consumers
- After removing `prepareAction`/`publishAction`/`runSquashMergePreflight`, both `pathExists`/`setDeliveryExistsCheckerForTest` and `workspaceManager`/`setDeliveryWorkspaceManagerForTest`/`getDeliveryWorkspaceManager` had zero references in `packages/runner/tests`. Removed them alongside the dead code.

### `mohist/publish` vs `mohist/publish-via-pr` confusion in tests
- The original byte-identical test substituted `mohist/publish` → `mohist/publish-via-pr`. The default no longer references `mohist/publish` at all (it uses `mohist/push`). The new substitutions list operates at the multi-line task-block level (id+title+uses+with+message), which is robust to ordering or surrounding-context changes.

### acp-agent `SharedSessionCancelHangs` is timing-flaky
- One runner test (`SharedSessionCancelHangs_NoProcessIsKilled`) fails when the full runner suite runs in parallel (`expected 'success' to be 'failure'`) but passes when run in isolation. Pre-existing flake; commit `42b67c708 fix: stabilize flaky server tests` shows the team has been actively addressing flakiness. Not in scope for this task.

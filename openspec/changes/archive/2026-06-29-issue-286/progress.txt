# Project Inbox (issue-286) — Working Memory

## Codebase Patterns

- The Mohist server persists relational state through `MohistDbContext`
  (`packages/server/src/Mohist.Server/Infrastructure/Data/Db/MohistDbContext.cs`).
  All migrations live under `packages/server/src/Mohist.Server/Infrastructure/Data/Migrations/`,
  are hand-written (no `dotnet ef` tool in this workspace), and live next to a
  matching `*.Designer.cs` plus the always-latest `MohistDbContextModelSnapshot.cs`.
- `MohistDbFixture` (`Support/MohistDbFixture.cs`) calls
  `db.Database.Migrate()` directly, so any new migration must be wired into the
  assembly via the standard `partial class <Name> : Migration` convention —
  migrations that aren't compiled-in won't run on production startup.
- Tests use traits `[Trait(Traits.Speed.Name, …)] × [Trait(Traits.Sut.Name, …)]`.
  Speed categories: `Unit`, `Grain`, `Integration`, `Service`. SUT categories
  are listed in `Support/Traits.cs`. When introducing a new bounded context,
  add a new `Sut.<Name>` constant.
- Unit-test DB patterns use `IDbContextFactory<MohistDbContext>` over a
  per-test in-memory SQLite (`Data Source=:memory:`). Migration specs that
  need an explicit Up-to-step use `context.GetService<IMigrator>().MigrateAsync(targetName)`;
  specs that want a clean DB use `Database.MigrateAsync()` and then read
  `__EFMigrationsHistory`.
- For new tables, mirror `EpicRow`/`EpicIssueRow` column conventions:
  TEXT PK/IDs with `HasMaxLength(64)`, ProjectId `TEXT` `HasMaxLength(256)`,
  timestamps as `DateTimeOffset`/`TEXT`. Index names follow
  `IX_<Table>_<Col1>_<Col2>` or `UX_<Table>_<Key>` / `UQ_<Table>_<Col>`
  conventions. Use `HasDatabaseName(...)` for explicit index names so the SQL
  is stable.

## T-001 Findings

- `EF Core 10` (`Microsoft.EntityFrameworkCore.Sqlite 10.0.8`) supports
  `HasIndex(...).IsDescending(bool[])` on fluent index builders — needed to
  materialize the `(ProjectId, CreatedAt DESC)` list index from design D2 as
  an actual DESC-on-CreatedAt SQLite index rather than the default ASC.
- `MigrationBuilder.CreateIndex` overload with `descending: bool[]` is the
  matching manual-migration emit (`descending: new[] { false, true }`).
- `pragma_index_info` does not expose per-column sort order; you must use
  `pragma_index_xinfo` (column 3 = `desc`, column 5 = `key` flag) to assert
  on DESC in a migration spec.
- Manually authored migrations need their `*.Designer.cs` to mirror the
  post-migration model state — `MohistDbContextModelSnapshot.cs` is the
  always-latest snapshot used by EF tooling for drift detection. Both files
  describe the full model; the per-migration `.Designer.cs` just adds a
  `[Migration("…")]` attribute and renames `BuildModel` to `BuildTargetModel`.
- The existing precedent (`20260627072538_AddRunnerWorksTable*`) is a clean
  CREATE-TABLE + 2-index migration with `Down = DropTable`. For inbox, we
  mirror this and add the third index plus a UNIQUE index.
- `dotnet ef` tool is not installed (`dotnet tool list -g` only shows
  `mohist.cli` + `roslyn-language-server`); migrations must be authored by
  hand. Confirmed by `dotnet ef --version` reporting the command is missing.
- MohistDbContext has a `DbContextFactory<MohistDbContext>` registered via DI;
  the projection (T-003) will be the primary writer, but the contract for
  this slice is "the table exists with these columns and indexes" — writer
  code lands in T-002.

## T-001 Decisions

- `Id` is `string(64)` (GUID/short-id surface for API mutations), not `Guid`,
  matching EpicRow/IssueCommentRow. The store (T-002) will generate a string
  GUID.
- `IssueTitle` defaults to `string.Empty` in C# but is mapped as
  `HasMaxLength(512)` non-nullable TEXT. The projection (T-003) snapshot is
  responsible for supplying a sensible title.
- `NotificationKind` is a TEXT enum string with `HasMaxLength(32)` —
  ample room for `workflow_failed`, `approval_requested`, `issue_started`,
  `issue_completed`. Domain validation lives in the projection layer, not
  the row.
- `CreatedAt` is non-nullable; `ReadAt` / `ArchivedAt` are nullable
  `DateTimeOffset?`. The `(ProjectId, CreatedAt DESC)` index ordering is
  encoded via `IsDescending(false, true)`.
- Test file location: `packages/server/tests/Mohist.Server.Tests/Specs/Inbox/`
  — co-located with `Specs/Epic`, etc. New `Sut.Inbox` constant added to
  `Traits.cs`.

## T-001 Gotchas

- `PRAGMA index_info` does NOT include sort direction; tests that need to
  assert DESC must use `PRAGMA index_xinfo` (`pragma_index_xinfo`) with
  column 3 = "1 if ... sorted in reverse (DESC) order". Filtering on
  `key = 1` skips the implicit rowid auxiliary column that has a NULL name.
- Migration file BOM: recent migrations use `ef bb bf` BOM at the start. My
  new migration file lacks it — fine for compilation but inconsistent with
  neighbors. Not blocking.
- The existing `*.Designer.cs` for the prior migration
  (`20260628022822_DropEpicIssueMembershipUniqueIndex.Designer.cs`) is
  already out of sync with the latest snapshot (missing `RunnerWorkRow`),
  suggesting snapshot drift is tolerated at design time but not at runtime.
  Mine faithfully matches the latest snapshot.

## T-002 Findings

- New module layout: `packages/server/src/Mohist.Server/Inbox/` with
  `InboxModels.cs` (DTOs + `NotificationKinds` constants), `InboxStore.cs`
  (writes), `InboxQuerier.cs` (reads). Both services implement
  `IScopedService` so the existing `AddMohistConventionalServices` scan
  auto-registers them — no manual DI change.
- Existing `IScopedService` consumers (`EpicQuerier`, `LabelCatalogService`,
  `IssueQuerier`, `WorkflowQuerier`, …) all inject
  `IDbContextFactory<MohistDbContext>` directly, so the inbox side follows
  the same pattern. `IDbContextFactory` is already registered in
  `MohistServiceRegistration.ConfigureMohistServices` — no new wiring.
- Idempotency-by-UNIQUE pattern: SQLite throws
  `SqliteException { SqliteErrorCode = 19 }` (SQLITE_CONSTRAINT) wrapped in
  `DbUpdateException` on a UNIQUE conflict. The existing
  `LabelCatalogService.CreateAsync` uses the same pattern with the same raw
  error code `19` — kept the convention. Message contains `"InboxItems"` so
  the IsSourceEventIdConflict filter does not get confused by other
  constraint conflicts.
- `ExecuteUpdateAsync` (EF Core 7+) lets us update a filtered set without
  load+save. Used for `MarkReadAsync`, `MarkAllReadAsync`, `ArchiveAsync`.
  Returns the affected row count, which is exactly the signal the API
  layer needs to translate "no row" into 404.
- The `Mark*`/`Archive` mutations deliberately filter
  `WHERE ProjectId = @pid AND Id = @itemId` (and `WHERE ProjectId = @pid`
  for MarkAllRead). No row matches a project-A itemId passed under
  project-B's filter — so 0 affected rows is the canonical 404 signal.
- `InboxItemRow` is non-nullable on `NotificationKind` / `SourceEventId`
  / `Id` / `ProjectId` / `IssueId`. The store validates required draft
  fields up-front (defense in depth — the projection layer should never
  pass nulls, but the store does not assume so).
- The `Id` is a string GUID prefixed `inb_` (matching the `epic_` /
  `ldef_` / `inb_` conventions visible in the codebase). The dedup-test
  uses fixed Ids to exercise the secondary sort tie-breaker; the
  production store uses `Guid.NewGuid():N`.

## T-002 Decisions

- **Idempotency model**: a single `InsertAsync` returns
  `InboxInsertResult { Id, AlreadyExisted }` rather than void or throwing.
  The projection (T-003) can log `AlreadyExisted = true` without try/catch
  noise. Rejected the alternative of "select-then-insert" pre-flight — that
  would have a TOCTOU race on concurrent event handlers.
- **Idempotency scope**: the UNIQUE index is on `SourceEventId` alone (per
  design D3), not `(ProjectId, SourceEventId)`. Verified via a test that an
  event id replayed under a different project hits the same conflict — the
  spec scenario is "at most one item per source event" globally, which is
  the safe reading of D3.
- **List ordering strategy**: materialized first, then
  `OrderByDescending(CreatedAt).ThenBy(Id)` in memory. SQLite does NOT
  support `ORDER BY` on `DateTimeOffset` columns under EF Core 10
  (`NotSupportedException` at query translate time); this matches the
  existing `IssueQuerier` pattern for `IssueComments`
  (`packages/server/src/Mohist.Server/Issue/Services/IssueQuerier.cs:1155`).
  The compound index `(ProjectId, CreatedAt DESC)` from T-001 still
  narrows the candidate set efficiently; the final sort is in-memory
  over the (small, project-scoped) result. The `ThenBy(Id)` tiebreaker
  gives a deterministic order when two items have identical CreatedAt
  (test seeded with same timestamp).
- **No `GetAsync` on the querier**: the T-004 API does not need a
  single-item fetch — the list endpoint is the read, and the
  `mark-one-read` / `archive` mutations translate "0 affected rows" to
  404. Adding a `GetAsync` would be a YAGNI extra.
- **Read model DTO (`InboxItemView`)**: a `class` with `init` properties
  rather than a `record`, so the API layer can pass it straight into
  `ApiResults.Ok` without breaking the existing
  `System.Text.Json` source-gen contracts in `ApiResponse.cs`. The view
  carries the four `NotificationKind` strings via the
  `NotificationKinds` constants class — no separate enum, since the
  string IS the durable storage representation and the rendering key.
- **Test scope**: all T-002 specs are `Traits.Speed.Unit` with the
  per-test `IDbContextFactory` over in-memory SQLite. No fixture-level
  service graph is required for the store/querier (they are
  construction-injected). 13 specs in `InboxStoreSpecs`, 7 in
  `InboxQuerierSpecs` — full server test suite still passes (3022
  green, 13 pre-existing skips).

## T-002 Gotchas

- **SQLite + DateTimeOffset ORDER BY**: my first cut had
  `OrderByDescending(r => r.CreatedAt)` in the IQueryable; EF threw
  `NotSupportedException` at translate time. Fix: materialize first,
  sort in memory — match the IssueQuerier precedent. Documented in the
  querier comment so the next person does not "optimize" it back to
  IQueryable.
- **`SqliteErrorCode == 19`** is the SQLite-level
  `SQLITE_CONSTRAINT`. Don't reach for
  `Microsoft.Data.Sqlite.SQLiteErrorCodes.Constraint` — that constant
  doesn't exist in this SQLite version; the codebase uses the raw `19`
  integer everywhere. `LabelCatalogService.CreateAsync` is the
  reference.
- **xUnit2002 — `Assert.NotNull` on a bool**: easy mistake when an
  expression like `row.ReadAt is null` reads as "is this null" but
  evaluates to a bool. xUnit's analyzer flags it. Use `Assert.Null`
  or `Assert.True(row.ReadAt is null)` directly.
- **Test InboxItemRow insertion with `Id = "inb_first"` vs Guid**: the
  production store's Id is `inb_{Guid.NewGuid():N}`. The deterministic
  tie-breaker test inserts raw rows with hand-picked Ids to assert
  secondary sort order. Don't run the production store with
  hand-picked Ids in tests without thought — the prefix `inb_` is
  enforced by the store, not the row.


## T-003 Findings

- **Handler DI lifetime conflict**: `AddCloudEventHandlersFromAssembly`
  registers every `ICloudEventHandler` as a **singleton**, but the
  inbox projection's three dependencies (`InboxStore`, `IWorkflowRunStore`,
  `IStateStore<Issue>`) are all registered as **scoped** (via
  `IScopedService` / `AddScoped<IWorkflowRunStore, WorkflowRunStore>`).
  `Microsoft.Extensions.DependencyInjection` rejects the descriptor
  with "Cannot consume scoped service X from singleton Y", which
  breaks every integration test that calls `WebApplicationFactory.Services`
  (i.e. 691 tests). The existing handlers (`EpicAutoDoneHandler`,
  `WorkflowStageLockReleaseHandler`, `RunnerWorkflowTerminalStatusHandler`)
  avoided this by only injecting `IGrainFactory` and `ILogger` (both
  singletons). The fix for the projection is to inject
  `IServiceScopeFactory` and create a scope per `HandleAsync` call,
  resolving the scoped services from there. This matches the
  "no in-grain side effects" boundary of D1/D5 and keeps the
  handler on the hot path singletons while still letting it
  reach the scoped DB stores.
- **EventCatalog.ReverseDns was missing the two issue-work events**
  (`IssueWorkStarted` / `IssueWorkCompleted`). `IssueEventSerializer.BusType`
  produces the strings `com.mohist.issue.work-started` /
  `com.mohist.issue.work-completed`, and the existing
  `IssueQuerier` constants (`WorkStartedType` / `WorkCompletedType`)
  hard-code them too — but the catalog did not advertise them. Added
  `IssueWorkStarted` and `IssueWorkCompleted` to `EventCatalog.ReverseDns`
  (and the `All` list) so the projection can match the catalog as
  the single source of truth without inline string literals.
- **Source-URI workflow run id extraction** is already a static
  helper `WorkflowStageLockReleaseHandler.ExtractWorkflowRunId(string)`.
  Reusing it (vs. `WorkflowEventSerializer.ExtractContextFromSource`)
  matches the design's "reuse `ExtractWorkflowRunId`" note. The two
  helpers have the same prefix-parsing behavior on the issue's prefix,
  but `ExtractWorkflowRunId` is the one that lives on a handler type
  and is `internal static` — which is the natural import.
- **Idempotency is purely a store concern**: the projection passes
  `evt.Id` straight into `InboxItemDraft.SourceEventId`, and the
  `UNIQUE(SourceEventId)` index from T-001 + the
  `InboxStore.InsertAsync` conflict-skip return `InboxInsertResult.AlreadyExisted`.
  Replay of the same `CloudEvent` is a no-op that returns
  `AlreadyExisted = true`; no second row is created. Verified in two
  specs (one for issue events, one for workflow events).
- **Title snapshot semantics verified end-to-end**: spec
  `WorkflowEvent_TitleTakenFromIssueRowSnapshottedAtProjectionTime`
  seeds an issue with title "Snapshot me", projects a
  `WorkflowRunFailed` event, then patches the issue state JSON
  directly (`Issue.Title` is `init`-only, so we mutate the
  underlying `State` string instead) to "Renamed later", and asserts
  the inbox item still carries "Snapshot me". D6 holds.
- **Title-fallback contract**: when the issue row is missing or
  load throws, the projection stores an empty `IssueTitle` rather
  than dropping the notification. The spec
  `IssueEvent_UnknownIssueIdForTitle_StoresEmptyTitleNotThrows`
  exercises the "issue row gone by projection time" path and
  asserts the deep-link identity (issue id + number) is still
  preserved. The InboxStore coerces `null` → `""` so the row
  always materializes.
- **All four kinds reachable through one handler**: the
  pipe-separated `SubscriptionAttribute` makes the dispatcher route
  every `com.mohist.issue.work-started` /
  `com.mohist.issue.work-completed` / `com.mohist.workflow.run.failed` /
  `com.mohist.workflow.stage.approval-requested` to the same
  `HandleAsync` instance, which branches on `evt.Type`. `Filter`
  short-circuits the unknown-type case in O(1) before the work
  begins.

## T-003 Decisions

- **Single `ICloudEventHandler` (untyped) over four typed handlers**:
  the four payload types (`IssueWorkStarted` / `IssueWorkCompleted`
  / `WorkflowRunFailed` / `StageApprovalRequested`) have disjoint
  shapes and the projection only reads ~3 fields from each (or
  none, for the issue events which use extensions). Typed handlers
  would have multiplied the file without buying type safety we
  actually use. Matches the precedent of
  `RunnerWorkflowTerminalStatusHandler` (untyped) and
  `WorkflowStageLockReleaseHandler` (untyped, pipe-separated
  subscription).
- **Resolve scoped services per HandleAsync via scope factory**,
  not per-class. The scope is created lazily only for events that
  pass `Filter`; the dispatcher's hot path (filter-only) is
  singleton-only. The scope is disposed in `await using` so DB
  contexts do not leak across events.
- **Project issue events without parsing the CloudEvent `Data`**:
  the deep-link identity (`projectid`/`issueid`/`issueno`) is
  already in `evt.Extensions` (stamped by `IssueGrain`), and
  `Data` only carries `WorkflowRunId` — which the projection does
  not need. The untyped handler skips `JsonElement` deserialization
  for the issue path entirely.
- **Title load wrapped in try/catch**: a broken / missing issue
  row is a known case (the issue may have been archived between
  the event publish and the projection), and the spec lists
  "robust to missing identity" as a requirement. The fallback
  string `""` is sufficient because the InboxStore / querier
  contract already handles it (the row's `IssueTitle` is mapped
  as `string` with default `string.Empty`).
- **Test scope**: 18 specs in `InboxProjectionHandlerSpecs`,
  organized as one spec per acceptance-criterion plus a few
  edge cases (filter acceptance/rejection, subscription
  attribute, four-kind integration). The full server suite
  passes (3041 green, 13 pre-existing skips); zero
  regressions from the prior 3022 baseline.
- **Test factory pattern** (`TestScopeFactory`): the spec
  builds a minimal `IServiceScopeFactory` over the per-test
  SQLite `IDbContextFactory` so the singleton handler still
  has scoped services available. Avoids pulling in
  `MohistServiceRegistration` for unit tests.

## T-003 Gotchas

- **Scoped service in singleton handler breaks `IServiceProvider`
  build** — this surfaces as a `BuildServiceProvider` /
  `WebApplicationFactory.CreateHost` exception, not a single
  test failure. The exception is a "ServiceProvider validation"
  one ("Some services are not able to be constructed"), and the
  inner `CallSiteValidator` lists every invalid descriptor. Don't
  try to silence this with `ValidateOnBuild = false` — fix the
  lifetime by introducing `IServiceScopeFactory`.
- **IssueGrain uses lowercase extension keys**:
  `projectid`/`issueid`/`issueno` (no camelcase). Workflow
  annotations use camelCase: `projectId`/`issueId`/`issueNumber`.
  The projection matches both exactly. Documented in the
  handler's helper methods so a future "let's normalize
  everything" refactor does not silently break identity
  resolution.
- **`IssueStore` reads `row.State` JSON, not the `Title`
  computed column** — even though `IssueRow.Title` exists as
  a stored computed projection of `json_extract(State,
  '$.title')`. `IStateStore<Issue>.LoadAsync` goes through
  `IssueStore.Deserialize` which deserializes the full state,
  not the projected column. The projection does not care
  (both paths give the same title) but it's a useful
  precedent for "store interface is deserialization, not
  columns."
- **Pipe-separated subscription needs the constants to be
  identical character-for-character**: if `BusType` ever
  changes the suffix (e.g. `com.mohist.issue.workStarted`),
  the projection's `Subscription(Type = "...")` will not match.
  The fix in this task was to make `EventCatalog.ReverseDns`
  the single source of truth on both sides; any future change
  to the issue-work types must be made in the catalog and
  in `IssueEventSerializer.BusType` together.
- **Reusing the existing `WorkflowStageLockReleaseHandler.ExtractWorkflowRunId`**
  means the projection depends on a method marked `internal
  static` on another handler class. Same-assembly access is
  fine in `Mohist.Server`, but anyone moving the projection
  out of the server assembly would need to either expose the
  helper publicly or duplicate the prefix-parsing logic.

## T-004 Findings

- **No new DI wiring needed**: `InboxStore` and `InboxQuerier`
  implement `IScopedService` from T-002, so the existing
  `AddMohistConventionalServices` scan auto-registers them. The
  `InboxRoutes.MapInboxRoutes` extension just resolves them from
  the request scope — no Program.cs / MohistServiceRegistration
  change.
- **ProjectResolutionEndpointFilter pattern re-used wholesale**:
  mirror of `EpicRoutes` — `MapGroup("/{projectRef}/inbox") +
  AddEndpointFilter<ProjectResolutionEndpointFilter>()`, then every
  handler pulls `context.GetResolvedProject().Id` for the scope.
  Zero custom authz, zero new filter code.
- **JSON `WhenWritingNull` strips `readAt` / `archivedAt`**:
  `Infrastructure/JSON.cs` configures
  `DefaultIgnoreCondition = JsonIgnoreCondition.WhenWritingNull`,
  so a fresh unread item's response body does not contain a
  `"readAt": null` field — it is omitted entirely. The
  integration specs read those fields with `TryGetProperty(...)`
  to assert absence rather than `GetProperty(...)` + null-check.
  The companion `isRead` / `isArchived` booleans are the stable
  client signal.
- **Store-side filter fix**: T-002's `MarkReadAsync` filtered
  `ReadAt == null AND ArchivedAt == null`, so a repeated call on
  an already-read item returned 0 affected rows — which the API
  layer cannot distinguish from "item not found". Loosened the
  filter to `ProjectId == @pid AND Id == @id AND ArchivedAt == null`
  so 0 affected rows is unambiguous: cross-project / unknown /
  archived. The repeated-call behaviour now matches the API
  acceptance ("set that item read") — every successful call writes
  ReadAt = now, returning 200 OK. The existing
  `MarkReadAsync_DoesNotTouchArchivedItems` and
  `MarkReadAsync_DoesNotMatchItemInOtherProject` specs still pass
  with the relaxed filter (they never asserted the
  already-read → 0 case).
- **`POST /{itemId}/read` shape**: per design D7, no pre-rendered
  text is stored — the response only carries the structured
  fields. Mutations return a small envelope
  (`{ itemId, read }` / `{ itemId, archived }`) rather than the
  full item, so a polling client doesn't have to re-fetch after
  every mutation. `POST /read-all` returns
  `{ projectId, marked }` so the Web client can show "N items
  marked read" without a follow-up request.
- **Integration test seeding**: tests grab the scoped
  `InboxStore` via `_fixture.Services.CreateAsyncScope()` and
  call `InsertAsync(InboxItemDraft(...))` directly. The
  projection handler is exercised by its own unit specs
  (`InboxProjectionHandlerSpecs`), so the route tests don't
  need to drive the bus — they just need rows in the table to
  assert GET/mutation behaviour. Matches the task note:
  "list/mutation specs can seed rows directly via the store."

## T-004 Decisions

- **Routes layout**: `MapInboxRoutes` is wired in
  `MohistApiRegistration.MapMohistApi` immediately after
  `MapEpicRoutes` — both are project-scoped project surfaces, so
  keeping them adjacent matches their conceptual grouping.
- **Mutations return `{ itemId, ... }` instead of the full
  InboxItemDto**: the mutation response only carries what the
  client needs to update its optimistic UI; a refetch is cheap
  via the existing `useInbox` invalidation. The list endpoint
  remains the single source of truth for the full row shape.
- **No new querier endpoint** (e.g. `GET /{itemId}`): the
  design specifies list + three mutations. Adding a single-item
  fetch would be speculative — the list endpoint already
  carries every field needed by the Web page, and T-005 will
  not need a per-item endpoint (the page renders the list).
- **Test scope**: 13 specs in `InboxApiSpecs` (Integration
  speed, Sut = Inbox + Api) — covering every WHEN/THEN scenario
  in the spec's "Project inbox HTTP API" requirement plus the
  cross-project / unknown-id / unknown-project 404 paths. Full
  server suite passes (3054 green, 13 pre-existing skips), no
  regression vs the T-003 baseline (3041 green).

## T-004 Gotchas

- **`PostDataAsync<T>(string path, object? body = null)`** is the
  route spec's POST-without-body helper. Naming the argument
  `content: null` does not compile — the parameter is `body`.
  Same shape applies to `PostOkAsync`. Use the helper
  positional/optional-arg form for body-less POSTs.
- **`JsonElement.TryGetProperty` returns false (not throws) when
  a property is absent** — preferable to `GetProperty` +
  `ValueKind` checks for nullable fields under
  `WhenWritingNull`. The list-spec failure surfaced here first.
- **`PostOkAsync` throws on non-2xx** — including 404. Asserting
  the 404 status requires `using var response = await client.PostAsync(...)`
  (no body, no extension) plus `Assert.Equal(HttpStatusCode.NotFound,
  response.StatusCode)`. Don't reach for `PostOkAsync` on a route
  you expect to 404.

## T-005 Findings

- **`useEventsConnection` always subscribes to ALL event types** via the
  server-side `[...EVENT_TYPES]` invocation, but the hook filters in
  the `handleEvent` callback. There is no per-hook type filter on
  the SignalR subscribe call. This is fine for our use-case: the
  hook subscribes once per mount and routes only the four inbox
  events (`workflow.run.failed`, `workflow.stage.approval-requested`,
  `issue.work-started`, `issue.work-completed`) to the invalidate
  path. The other events are received but ignored.
- **Created a new connection per page mount** in `useInboxLiveRefresh`
  rather than extending `LiveTaskProvider`. The trade-off: a second
  SignalR connection per inbox page mount (clean separation, matches
  the design's "inbox page subscribes" intent) vs. invalidating
  `['inbox']` from the existing central handler (more efficient but
  couples inbox logic to the global provider). I went with the
  page-owned subscription because the design D9 says "the inbox
  page subscribes ... it never synthesizes items" — the hook is the
  explicit subscription site and the InboxPage never imports anything
  from the events hub directly.
- **`pages/<name>/ui/` is the convention** for page modules in this
  repo (mirrors `pages/dashboard/ui/`, `pages/epics/ui/`). The first
  attempt to put `InboxPage.tsx` directly in `pages/inbox/` produced
  wrong-relative-import errors against `tsc -b`; moving to `ui/`
  fixed the path math (`../../../entities/...` from `pages/inbox/ui/`).
- **`useCallback` requires a real React renderer** in tests. A hook
  test that calls the hook directly (no `renderHook`) fails with
  `Cannot read properties of null (reading 'useCallback')` because
  `process.env.NODE_ENV.exports.useCallback` is `null` outside a
  render context. `// @vitest-environment jsdom` alone is not enough
  — must wrap with `renderHook(() => useFoo(), { wrapper })` over a
  QueryClient + ProjectProvider.
- **`.test.tsx` extension is required for any test that imports a
  `.tsx` file** even via `importOriginal` in a `vi.mock`. Vitest's
  esbuild transform refuses to parse JSX in a `.ts` file, so the
  `useInboxLiveRefresh.test.tsx` file lives at `model/useInboxLiveRefresh.test.tsx`.
- **`AppSidebar.test.tsx` had a hardcoded nav order** that included
  every nav key. Added `nav-inbox` between `nav-issues` and
  `nav-activity` to keep the test in sync with the actual sidebar
  primary-nav ordering — see the edit on `src/widgets/app-shell/ui/AppSidebar.test.tsx`.
- **Project-scoped API routes compose cleanly with `useProjectPath`**.
  The deep-link `toProjectPath(`/issues/${item.issueNumber}`)`
  evaluates to `/demo/issues/42` etc. The test asserts these hrefs
  against the `MemoryRouter` initial entry to keep the route
  resolution consistent with the production `BrowserRouter`.
- **The four server event strings live in
  `packages/web/src/shared/lib/canonical-event-types.ts`** under
  `REVERSE_DNS_EVENT_TYPES`. The hook imports them by key so a future
  catalog change (e.g. rename `issue.work-started`) only needs to
  happen in the catalog and the `IssueEventSerializer.BusType` (per
  the T-003 gotcha) — keeping the four `INBOX_REFRESH_EVENT_TYPES`
  in sync with both sides.

## T-005 Decisions

- **Page-owned live refresh via `useInboxLiveRefresh`**: a single
  hook colocated with the inbox entity in `entities/inbox/model/`.
  The hook owns the SignalR connection (`useEventsConnection`) and
  filters to the four relevant event types. The page imports the
  hook and does not touch the events hub directly. This keeps the
  invalidation-only contract (D9) visible at the page boundary and
  makes the hook trivially testable in isolation.
- **Invalidation pattern is a flat `['inbox']` prefix** (the
  `inboxQueryKey()` helper without a projectId suffix). The query
  itself scopes by `projectId` (`['inbox', projectId]`); invalidating
  the prefix is enough to refetch any project's inbox. Mirrors the
  `invalidateApprovalWait` precedent (`issues/api/approval-wait.ts`)
  and keeps `LiveTaskProvider`'s `['issues']` invalidation pattern
  from accidentally refetching the inbox.
- **Notifications sort = API order**: the server's `InboxQuerier`
  returns `OrderByDescending(CreatedAt).ThenBy(Id)` (per T-002
  decisions). The Web side does not re-sort — it trusts the API
  ordering so a future server-side change (e.g. "pin unread items")
  propagates without touching the client.
- **Mark-read / mark-all-read / archive return small envelopes**
  (`{ itemId, read }`, `{ itemId, archived }`, `{ projectId, marked }`)
  per T-004 design. The mutation hooks invalidate the inbox query
  instead of optimistic-updating the cache — the list is the source
  of truth and a refetch is cheap. This also keeps the cache shape
  consistent with the server's contract (no client-side
  synthesized readAt/archivedAt).
- **The "Mark all read" toast only fires when `marked > 0`**: the
  server returns 0 affected rows when the project has nothing
  unread, and we don't want a confusing toast in that case. The
  API spec ("marks all non-archived items in that project read")
  is preserved; the silence-on-zero is a UI affordance.
- **Empty state text uses neutral phrasing**: "No inbox items"
  with subtitle "Workflow failures, approvals, and issue lifecycle
  events will appear here." — matches the design's product-facing
  tone (D7) without exposing raw event type strings.
- **Sidebar position: between Issues and Activity**. The inbox is
  the "needs attention" surface; placing it after Issues keeps the
  attention-related actions adjacent (Issues = "list of work",
  Inbox = "what's happening on that work"). This order is mirrored
  on the mobile bottom nav (Dashboard, Issues, Activity, Inbox,
  Epics).
- **Test coverage**: 64 new tests across the inbox entity and page.
  - `model/types.test.ts`: 8 tests — kind enum shape, wire strings,
    `isNotificationKind`/`parseNotificationKind` parsers.
  - `api/client.test.ts`: 5 tests — fetch URLs, HTTP methods,
    payload shape for `getInbox`/`markInboxItemRead`/`markAllInboxRead`/`archiveInboxItem`.
  - `api/queries.test.ts`: 16 tests — `inboxQueryKey`, `invalidateInbox`,
    `useInbox` (key shape, projectId forwarding, enabled),
    `useMarkInboxItemRead`/`useMarkAllInboxRead`/`useArchiveInboxItem`
    (mutationFn signature, invalidation, toast messages, error
    fallback).
  - `model/useInboxLiveRefresh.test.tsx`: 8 tests — subscription
    wiring, projectId forwarding, per-event invalidation, no-op on
    unrelated events, no client-side synthesis.
  - `pages/inbox/ui/InboxPage.test.tsx`: 22 tests — empty state,
    loading state, list rendering, kind badges, deep-link hrefs,
    read/unread styling, mark-read/archive/mark-all-read
    interactions, live refresh hook subscription.
- **Full suite**: 2865 web tests pass (1 pre-existing skip), 3054
  server tests pass (13 pre-existing skips). No regressions from
  the T-004 baseline.

## T-005 Gotchas

- **`AppSidebar.test.tsx` checks the nav order against a hardcoded
  array** — adding a new nav entry requires updating that test.
  There is no centralized "navigation config" test that auto-picks
  up new entries; if the test list goes stale, the assertion fails
  immediately. This is a useful "review the sidebar" signal but
  it is a known coupling.
- **The `data-testid="inbox-item"` is the same for every row**, with
  `data-item-id={item.itemId}` providing the per-row key. Tests that
  need a specific row use `document.querySelector('[data-item-id="..."]')`
  rather than `getByTestId('inbox-item-inb-1')` (the latter does
  not exist on the DOM). Keep this in mind when adding tests
  later.
- **`useInboxLiveRefresh` calls `useEventsConnection` once per
  render lifecycle**. The hook closes the connection in its effect
  cleanup. If the inbox page is rendered very briefly or rapidly
  remounted, the SignalR connection churn is acceptable but not
  zero. The architectural alternative (centralized subscription
  + page-registered handler) is a bigger refactor outside T-005's
  scope.
- **The T-004 mutation response envelopes (`{ itemId, read }`,
  `{ itemId, archived }`, `{ projectId, marked }`) are not used
  client-side** beyond the toast count. The hooks only invalidate
  the query; the next render pulls the fresh row state. This is
  the simplest contract but means a round-trip per mutation — fine
  for a local-first single-machine setup, not a tight-loop
  scenario.
- **`MailOpenIcon` from `lucide-react` is used as the approval-
  requested visual cue** (envelope with a flap). The other three
  kinds use `AlertTriangleIcon`, `PlayIcon`, `CheckCircle2Icon`.
  These names are stable in the `lucide-react@1.16.0` distribution
  we use; the rest of the codebase uses the same set (`InboxIcon`
  in settings, `ActivityIcon` in activity, etc.).

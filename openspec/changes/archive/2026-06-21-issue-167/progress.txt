## Codebase Patterns

### Web widget layering & test conventions
- Self-contained composition widgets (data + actions + navigation) live under `packages/web/src/widgets/<name>/` with a public `index.ts` re-export and an `ui/<Name>.tsx` + colocated `ui/<Name>.test.tsx`.
- For widgets that read entities via hooks, exposing optional props (`issues?: Issue[]`, `agentStatus?: AgentStatus`) lets tests inject state directly while production keeps the hooks. Pattern used by `AttentionHero`.
- Mocking entity hooks in widget tests: `vi.hoisted` for shared mutable mocks; `vi.mock('../../../entities/<entity>', async (importOriginal) => ({ ...actual, useFoo: () => ({ data: mocks.foo, isLoading: false }) }))`. Mock only what the widget calls; keep the rest from `actual` so types remain correct.
- Always wrap widget tests in `QueryClientProvider` (with `retry: false`) + `ProjectProvider initialProjectId="..." initialProjects=[{...}]` + `MemoryRouter initialEntries={['/demo']}` — `toProjectPath` keys off the URL prefix.
- Mutation invalidation pattern (mirrors `IssueCard.tsx`): on success `queryClient.invalidateQueries({ queryKey: ['issues'] })` and `{ queryKey: ['agent-status'] }`.
- Zone slot hook: the slot root must carry `data-testid="dashboard-zone-<id>"` and `data-zone="<id>"` so `DashboardPage` tests can target the zone identity regardless of which component fills it.
- Runner-down signal divergence: `AttentionHero` keys off `agentStatus.runnerAvailable === false` (spec-mandated); Kanban's `RunnerUnavailableBanner` keys off `useRunnerSummary().hasConnectedCapacity`. Documented and accepted — not a bug.
- Test runner: vitest config lives inside `packages/web/vite.config.ts` (no separate `vitest.config.ts`). From `packages/web` run `npx vitest run --no-coverage <paths>`.

### Domain seams to reuse (do not re-implement)
- `deriveAttentionItems(issues, agentStatus)` and `AttentionItem` type live in `entities/issue/model/attention.ts` and re-export from `entities/issue`. Exactly four labels: `Approval needed`, `Integration failed`, `Interrupted`, `Needs action`.
- Mutations: `approveIssue(number, projectId)` and `resumeIssue(number, projectId)` from `entities/issue/api/client.ts`.
- Navigation: `useProjectPath()` returns a `(path: string) => string` that prefixes the current project; pass absolute routes like `/issues/:n` or `/activity`.
- Passive surface: no `useEffect` side effects; mutations fire only on explicit user action.

- What was implemented:
  - New widget at `packages/web/src/widgets/attention-hero/` (`index.ts` + `ui/AttentionHero.tsx` + colocated `ui/AttentionHero.test.tsx`) exporting `AttentionHero`.
  - Two-state rendering driven by `deriveAttentionItems(useIssues(), useAgentStatus())` + `agentStatus.runnerAvailable === false`. No local copy of any of the four attention rules.

- Learnings for future tasks:
  - Decisions made:
    - Hero accepts optional `issues?` / `agentStatus?` props so tests can bypass the hooks while production consumes them via `useIssues()` and `useAgentStatus()`. The component treats `props.X ?? hookResult.data` so production path is untouched.
    - Resume-vs-Approve is inferred from the attention label (`Approval needed` → Approve, anything else → Resume) because the shared `AttentionItem` has no resume-eligibility flag. Safe per `issue-attention-derivation` spec, which locks the label set to exactly four.
    - The Hero root in **both** states carries `data-testid="dashboard-zone-attention"` + `data-zone="attention"`, so the slot identity remains addressable regardless of state.
  - Gotchas discovered:
    - Vitest config is inside `vite.config.ts` (no separate `vitest.config.ts`). Run focused tests from inside `packages/web/` with `npx vitest run --no-coverage <paths>` to keep them fast.
    - `useIssues(projectId ? { projectId } : undefined)` — only pass the project filter when there is a projectId; otherwise let the hook run with `undefined` query options.
    - The component delegates the agent status default to a small `defaultAgentStatus` constant because `deriveAttentionItems` requires a defined `AgentStatus`. Production path keeps the override only when `agentStatus === undefined`.
  - Patterns / API shapes established:
    - The widget surfaces four data-testids: `dashboard-zone-attention` (root, both states), `attention-item` (per row), `attention-item-link` / `attention-item-approve` / `attention-item-resume` (actions), `runner-down-entry` / `runner-down-message` / `runner-down-link` (Runner-down), `productivity-placeholder` (all-clear). Downstream zone views should follow the same id discipline.
    - Empty-items + runner-down case is rendered with zero `attention-item` rows but exactly one `runner-down-entry`; all-clear state renders zero of both plus a `productivity-placeholder`.
  - Cross-task invariants:
    - The set of items the Hero surfaces is, by construction, exactly `deriveAttentionItems(issues, agentStatus)`. Any future zone view consuming attention must go through the same derivation to stay in lockstep with Kanban and the Hero.
    - `agentStatus === undefined` (loading) is treated as "runner available" — no Runner-down flash during initial load.

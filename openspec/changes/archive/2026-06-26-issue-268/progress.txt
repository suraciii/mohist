# Issue 268 — Build Stage Progress

This file is the working memory for the build stage. Each completed task

## Codebase Patterns

- **Server route surface lives under `packages/server/src/Mohist.Server/Api/`.** Runner routes
  are in `RunnerRoutes.cs`. Helpers used by other routes (e.g. `NormalizeBuildGitHash`,
  `ToCleanupPolicyDto`) live as private/internal static members of the route class so they are
  reachable from unit tests via `internal` access without exposing them publicly.

- **DI for new server options/services is wired in
  `MohistServiceRegistration.AddMohistServerCore`.** Add `services.Configure<TOption>(...)`
  and `services.AddSingleton<IDep, Dep>()` next to peers there. The test
  `MohistWebApplicationFactory.ConfigureWebHost` only overrides test-time
  replacements; production wiring still needs to be added explicitly.

- **Workflow lifecycle facts come from `WorkflowGrain.GetRunStatusAsync()` and
  `GetAssignedRunnerIdAsync()`** — both return `Task<string?>` (status as canonical enum name,
  runner id from `_run.Assignment.RunnerId ?? _lastKnownRunnerId`). The runner id can be
  non-null while the runner is offline — the runner-side signalr `RunnerConnectionTracker`
  (in `Runner/Services/SignalR/RunnerConnectionTracker.cs`) is the authority for "is this runner
  actually reachable right now". A non-empty connection id ⇒ push, otherwise skip.

- **CloudEvents terminal subscriptions are pipe-separated string lists in the
  `[Subscription(Type = "a|b|c")]` attribute.** The runtime in
  `CloudEventBusServiceCollectionExtensions` does not support `.*` wildcards over
  reverse-DNS names, so use `com.mohist.workflow.run.completed|com.mohist.workflow.run.stopped|com.mohist.workflow.run.failed`
  and resolve the status inside the handler.

- **The workflow grain is non-reentrant; publishing from inside a grain call and then
  resolving the same grain synchronously will deadlock.** The
  `RunnerWorkflowTerminalStatusHandler` fires the router on a detached background task
  (`_ = RouteDetachedAsync(...)`) for exactly this reason. Any new handler that reads from
  the same workflow grain it just published to must follow the same pattern.

- **`RunnerConnectionTracker` is a `ConcurrentDictionary<string, string>` singleton**
  (`ISingletonService`). Hub `OnConnectedAsync` calls `Register(runnerId, connectionId)` from
  the query string; the test fixture replaces `IHubContext<RunnerHub>` with
  `RecordingRunnerHubContext` so integration tests can assert on the messages list.

- **Server test fixture pattern**: `MohistIntegrationFixture` provides an in-memory SQLite +
  Orleans silo. The `RecordingRunnerHubContext` is wired via `RemoveAll<IHubContext<RunnerHub>>()`
  followed by an `AddSingleton<RecordingRunnerHubContext>` *and* a forwarder
  `AddSingleton<IHubContext<RunnerHub>>(sp => sp.GetRequiredService<RecordingRunnerHubContext>())`.
  New hub-dependent tests should resolve the recorder from
  `_fixture.Services.GetRequiredService<IHubContext<RunnerHub>>()` and cast to
  `RecordingRunnerHubContext`.

- **Architecture test enforces Feature directories (`Agent`, `Epic`, `Issue`, `Project`,
  `Runner`, `Sessions`, `Workflow`) only contain `Domain`, `Grains`, `Services` segments.**
  Don't add new top-level subdirectories inside those features.

### Decisions taken during implementation

- **Server config scope = system-wide** (under `Mohist:WorkspaceCleanup`). Per-project
  configuration was considered (design Open Question) but adds a projectId resolution step on
  every poll without a real-world runner-isolation use case. Runners already bind to a single
  project; system-wide keeps the wire shape flat and the runner code single-path. If we need
  per-project later, `Mohist:Projects:{id}:WorkspaceCleanup` is a non-breaking addition.

- **Cleanup policy field semantics**: every field is nullable, and a value `<= 0` is coerced
  to `null` by `ToCleanupPolicyDto`. This makes "disabled" and "missing" indistinguishable
  on the wire by design — the runner doesn't have to learn a separate sentinel. The runner
  treates `null` as "do not evict by this strategy". This avoids accidentally treating a
  misconfigured `0` as "evict everything zero days old".

- **Status endpoint deduplication**: the handler dedupes by `HashSet<string>(Ordinal)` and
  silently drops whitespace entries. This protects the workflow grain from being hit N times
  for the same id, and the runner can be sloppy with its active-registry snapshot.

- **Run-id not found**: the endpoint returns `{ statuses: {} }` (omits the key) rather than
  404. The runner treats a missing key as "I don't know about this anymore" and can drop
  the registry entry; 404 would force every caller to special-case the absent id.

- **Push routing uses detached tasks**: terminal event handlers cannot synchronously call the
  workflow grain they're inside (non-reentrancy). The current handler detaches the router
  call with `_ = RouteDetachedAsync(...)`. This is a deliberate trade — push failures are
  logged, never propagated, and the runner's convergence query is the authoritative
  catch-all.

- **Receiving on the runner side**: the runner code is the source of truth for whether the
  status is terminal; the runner accepts the canonical `WorkflowRunStatus` name as a string
  (`Completed`, `Stopped`, `Failed`) and treats anything else as non-terminal. No schema
  version bump required.

### Gotchas for the next tasks

- **`RunnerWorkflowStatusRouter.RouteAsync` is reentrancy-safe but the workflow grain is
  not.** Future tasks that read `GetAssignedRunnerIdAsync` or `GetRunStatusAsync` from inside
  a `WorkflowGrain` method MUST NOT do so synchronously after a publish — use the same
  detach pattern as `RunnerWorkflowTerminalStatusHandler`. The Orleans grain state model
  documentation is in `Workflow/Grains/WorkflowGrain.cs`.

- **Status string contract**: server returns the enum name verbatim (e.g. `AwaitingApproval`,
  not `awaiting_approval`). The runner-side convergence code (T-003) should match these
  strings case-sensitively against `WorkflowRunStatus.*`. The runner codebase already has
  `packages/runner/src/core/types.ts` defining `WorkDispatchResponse.cleanupPolicy` — no
  further server changes are needed for the policy wire shape.

- **`RunnerConnectionTracker.GetConnectionId(runnerId)` is `string?`.** Treat null/empty as
  "not connected" and let the convergence query do the work.

- **Workflow grain `GetAssignedRunnerIdAsync` returns the last-known assignment, not the
  currently-connected one.** This is correct for routing terminal events to the runner that
  owns the workspace — even if that runner later disconnected and was replaced, the
  workspace-cleanup notification should still reach the last runner that had it. If the
  next task needs the currently-connected runner, look up `RunnerRegistryGrain` instead.

- **The runner type addition is intentionally additive.** Old runners ignore
  `cleanupPolicy`; new runners without policy config receive `{retentionDays: null,
  storageBudgetBytes: null, storageTargetWatermarkBytes: null}` and skip both evictions.
  This is the safe rollout posture — the new code path is unreachable without operator
  opt-in.

## T-002 — Runner active workspace registry with materialize/verify/manual-cleanup registration hooks

Status: complete.

### Files changed / added

- `packages/runner/src/runtime/workspace-registry.ts` (new) — `WorkspaceRegistry` class
  managing an in-memory cache + atomic on-disk persistence at
  `<runnerRoot>/.mohist/runner-state/workspaces.json`. Methods: `load()`, `register()`,
  `refreshMaterializedAt()`, `markEligible()`, `remove()`, `findByWorkspacePath()`,
  `get()`, `list()`. Mutations are write-through atomic (temp file + rename).
- `packages/runner/src/runtime/workspace.ts` — `WorkspaceManager` constructor now takes an
  optional `WorkspaceRegistry`. `materialize()` registers/refreshes an `active` entry
  after writing the marker; `verify()` calls `refreshMaterializedAt(workflowRunId)` on
  the matching entry. Marker writer (`issueWorkspaceMarker`) is unchanged: still
  identity-only.
- `packages/runner/src/server/runner-signalr.ts` — `RunnerSignalRClient` accepts a
  `registry` option and shares it with its internal `WorkspaceManager`. The
  `RemoveWorkspace` handler drops the matching registry entry by workspacePath (handles
  both the "directory existed + delete succeeded" and the "already missing" branches —
  the latter per the T-002 safeRemove contract). Out-of-root paths refuse before
  touching the registry.
- `packages/runner/src/runtime/host.ts` — `RunnerHost` creates a single
  `WorkspaceRegistry` for the host, passes it to both `WorkspaceManager` and
  `RunnerSignalRClient`, and eagerly calls `load()` at the top of `run()` before any
  dispatch / SignalR RPC fires.
- Tests:
  - `packages/runner/tests/workspace-registry.spec.ts` (new) — 13 unit tests covering
    register persistence, load round-trip (existing file, missing file, corrupt JSON),
    register refresh of materializedAt, markEligible transition + idempotency +
    unknown-id no-op, remove + unknown-id no-op, findByWorkspacePath, atomic rename
    (no temp leftovers), and the "must call load() first" guard.
  - `packages/runner/tests/workspace-registry-integration.spec.ts` (new) — 8
    integration tests covering materialize registration, marker identity-only
    invariant, verify refresh of materializedAt, verify does NOT fabricate a missing
    entry, restart reload preserves active phase, manual RemoveWorkspace drops
    registry entry on success, manual RemoveWorkspace drops entry on already-missing
    directory, manual RemoveWorkspace refuses out-of-root paths without touching the
    registry.

### Decisions taken during implementation

- **`WorkspaceManager.materialize()` always stamps `materializedAt = now`.** Per design
  D7 ("upsert registry entry `active`, `materializedAt = now`"), every successful
  materialize bumps the timestamp. `terminalAt` is preserved across re-materialize
  for the same workflowRunId (eligibility is sticky; only a fresh workflowRunId gets a
  fresh entry because the registry is keyed by run id).

- **`WorkspaceManager.verify()` does NOT create an entry when none exists.** Verify is
  the dispatch-time read path; the design says "ensure entry exists, refresh
  materializedAt" but the only legitimate way an entry could be missing is a stale
  pre-registry disk state. Creating an entry on verify would silently mask that. The
  integration test `Verify_OnRunIdWithNoRegistryEntry_DoesNotCreateEntry` pins this.

- **`RemoveWorkspace` drops the entry BEFORE the disk-existence check.** The handler
  resolves `query.workspacePath` and looks up the registry entry first; if a match
  exists the entry is dropped regardless of whether the directory is still on disk.
  This satisfies the T-002 safeRemove contract "tolerate an already-missing
  directory (treat as removed, delete the entry)". Out-of-root paths refuse before
  the lookup so a malicious caller cannot drop a registry entry for a directory the
  runner never managed.

- **Marker stays exactly identity-only** (`issueId`, `issueNumber`, `workflowRunId`).
  No `materializedAt`/`terminalAt` is written into the marker. The integration test
  `Marker_WrittenOnMaterialize_ContainsExactlyIdentityFields` asserts
  `Object.keys(marker).sort()` equals the three identity fields.

- **`WorkspaceRegistry.load()` is the contract.** All read methods (`list`, `get`,
  `findByWorkspacePath`) throw a clear "has not been loaded; call load() first"
  error if called before load. This catches wiring mistakes early (e.g., constructing
  a registry but forgetting the eager `load()` in `RunnerHost.run()`).

- **Atomic persistence via temp file + rename.** The file lives at a sibling temp
  path `<file>.<pid>.<msec>.tmp` and is renamed over the live path. A crash mid-write
  cannot leave a half-written file behind. The integration test
  `Persist_UsesAtomicRename_NoTempFilesRemain` reads the runner-state directory and
  asserts no `.tmp` leftovers remain after a register.

- **Registry file location: `<runnerRoot>/.mohist/runner-state/workspaces.json`.** This
  sits ABOVE `<runnerRoot>/repos/` and `<runnerRoot>/<project>/workspaces/`. It is
  intentionally NOT inside any workspace directory so a workspace cleanup cannot
  accidentally delete the registry.

### Gotchas for the next tasks

- **`WorkspaceRegistry` is consumed via a single instance per host.** `RunnerHost`
  owns the lifecycle; `WorkspaceManager` and `RunnerSignalRClient` receive the same
  instance. Future tasks that need the registry (T-003 handler, T-004 cleanup loop)
  should reach for it through `RunnerHost.workspaceRegistry` rather than constructing
  a new one — multiple instances on the same runnerRoot would clobber each other on
  persist.

- **`WorkspaceRegistry.refreshMaterializedAt(workflowRunId)` is a no-op when the
  entry does not exist.** It returns `null` and does NOT persist. T-004's cleanup
  loop should rely on `findByWorkspacePath` (or `list()`) for entry discovery, not
  `refreshMaterializedAt`.

- **`findByWorkspacePath` resolves both sides before comparison.** It compares
  `resolve(entry.workspacePath) === resolve(workspacePath)`. The signalr handler
  also resolves `query.workspacePath` before the lookup, so symlinks and `.`/`..`
  segments on either side still match.

- **The runner registry is per-runner.** Two runners sharing a `runnerRoot` will
  overwrite each other's registry file on every persist. This is documented in the
  design as a non-goal; do not relax the "one runner per runnerRoot" assumption in
  future tasks.

- **Workspace path matching for the cleanup loop (T-004).** `safeRemove` will need
  both `isUnderRunnerRoot(runnerRoot, workspacePath)` and `readMarker(workspacePath)`
  to match the registry entry's `workflowRunId`. Both primitives are already
  available: `isUnderRunnerRoot` is exported from `runner-signalr.ts:521` and
  `readMarker` is an internal in `workspace.ts:450`. The cleanup loop should reuse
  them unchanged per design D5.

- **Concurrent writes are serialized by Node.js fs promises.** The atomic rename is
  per-call; two parallel `register()` calls will race on the temp-file path (same
  `<pid>.<msec>` collision). For now this is acceptable because the runner has a
  single dispatcher per host. If T-004's cleanup loop ever runs concurrently with a
  materialize, the cleanup's `remove()` should be sequenced behind the dispatcher's
  in-flight registry mutations (a small mutex on the registry would do it).

- **T-003 handler note:** when the server pushes `ReceiveWorkflowRunStatus` with a
  terminal status, the runner handler must call `registry.markEligible(workflowRunId)`
  (not `remove`). The convergence query should call `markEligible` too. `remove` is
  reserved for the manual cleanup path.

### Decisions taken during implementation

- **Terminal status string contract = case-sensitive.** The server returns
  the canonical `WorkflowRunStatus` enum name (`Completed`, `Stopped`,
  `Failed`); the runner matches exactly. Lowercase is a wire contract
  violation and is treated as non-terminal. The unit tests pin this.

- **Push is silent on the unknown-id path.** If the server pushes a
  terminal event for a run the runner never materialized (e.g. an event
  for a workflow whose workspace lives on another runner), the handler
  resolves to a `null` registry entry and returns. No log spam, no
  error.

- **Convergence queries are batched.** All active entries go into one
  `workflowRunIds` array → one HTTP call per pass. The server-side
  endpoint already dedupes and filters whitespace (T-001 contract).

- **Server-forgotten entries are dropped on convergence.** When the
  server omits a run id from the status response, the runner removes
  the matching registry entry. The runner only tracks workspaces it
  owns; if the server has forgotten the run, the runner should forget
  the entry too. The on-disk directory is left alone (T-004's
  pre-delete guards decide eviction).

- **Convergence failures never crash the worker pool.** Both the
  per-pass `try/catch` in `ConvergenceBackstop.runOnce` and the
  detached `runConvergenceOnce` in `RunnerHost` swallow exceptions and
  log. The next tick (or reconnect) retries.

- **No new RunnerOptions field required.** `cleanupConvergenceIntervalMs`
  is optional with a 5-min default inside `RunnerHost`. Existing
  RunnerHost constructions in tests and the CLI don't need to change.
  The CLI's `CLEANUP_CONVERGENCE_INTERVAL_MS` env override is opt-in.

- **Push and convergence both call `markEligible`.** Neither pushes
  `remove`. Manual cleanup is the only path that drops registry
  entries (per the T-002 contract).

### Gotchas for the next tasks

- **`ConvergenceBackstop.runOnce` is best-effort and synchronous per
  pass.** It batches all active entries into one HTTP call and applies
  each server response in-memory. A pass that errors out partway does
  NOT roll back earlier `markEligible` calls; those persist locally and
  the next pass will simply find them already eligible. Idempotency is
  the safety net here.

- **`ServerConnectionConvergenceAdapter.queryActiveStatuses` is the
  injection seam for tests.** Future tests that want to drive
  convergence with a fake server should swap in a stub
  `ConvergenceRunner` rather than mocking `ServerConnection` directly —
  the `ConvergenceRunner` interface (`runner/src/runtime/cleanup-convergence.ts`)
  is the public contract.

- **The convergence timer is started AFTER the first SignalR connect
  succeeds**, not in the constructor. This matches the heartbeat /
  selfCheck timers. T-004's cleanup loop should follow the same
  pattern: stand up the timer inside the `try` of the
  `runWorkerPool` loop and `clearInterval` it in `finally` so a
  failed connect cycle does not leak.

- **No full-history scan enforcement.** `ConvergenceBackstop.runOnce`
  filters to `phase === "active"` before building the request payload.
  T-004's cleanup loop should similarly only touch entries with
  `phase === "eligible"` — both invariants are tested explicitly.

- **`workflowRunsStatus` accepts an empty input as a no-op.** T-004
  should not special-case empty registries; an empty array returns
  `{}` without making a network call.

- **The runner code does not write any cleanupPolicy into the poll
  request.** T-001's `WorkDispatchResponse.cleanupPolicy` is read by
  T-004 (the cleanup loop) via `connection.poll()`. T-003 does not
  consume the policy — convergence is policy-free.

- **The `cleanupConvergenceIntervalMs` default (5 min) is shared across
  runners.** T-004's cleanup loop should pick a different cadence (e.g.
  the design suggests 2–5 min) so eviction runs at a different
  schedule from convergence. The two timers do not need to be aligned.

### Decisions taken during implementation

- **cleanupLoopIntervalMs default = 2 min.** Design suggests 2–5 min range.
  Convergence runs at 5 min; choosing 2 min for cleanup means eviction keeps pace
  with new eligible entries and the two timers are not aligned.

- **Policy consumed via ServerConnection.getLastCleanupPolicy().** The
  `WorkDispatchResponse.cleanupPolicy` from T-001 is captured on every non-204 poll
  response inside `ServerConnection.poll()` and exposed through a getter. The
  `RunnerHost.runCleanupOnce` reads it each tick. Idle polls (204) preserve the
  last-seen policy. This avoids threading the policy through WorkItem/worker pool.

- **Usage cache with 5-min TTL.** `CleanupLoop` caches `computeDirectorySize(root)`
  for 5 minutes. The cache is per-instance (not shared across `CleanupLoop`
  instances). Tests create fresh instances per test so stale caches don't bleed.
  Budget eviction computes individual workspace sizes on-the-fly from the same
  `CleanupRunner.computeDirectorySize` hook, keeping the pre-eviction size estimate
  accurate.

- **Budget eviction estimates post-removal usage.** After computing total root
  usage once, the budget loop computes individual eligible workspace sizes
  (one `computeDirectorySize` call each) and subtracts before each removal.
  The next tick's `runOnce` recomputes root usage fresh (from the now-removed
  state), so the estimate converges to reality within one tick cadence.

- **guardAborted counter for observability.** Both retention and budget loops
  increment `guardAborted` when `safeRemove` returns false. The host logs the
  counts so operators can detect persistent guard failures (e.g., a workspace
  stuck out-of-root forever). The entry remains eligible and is re-evaluated
  next tick — the guard may pass or fail again.

- **`readMarkerWorkflowRunId` exported from workspace.ts** instead of exporting
  the full `readMarker` function. Only the `workflowRunId` field is needed for
  the identity check; exporting just that avoids exposing the `IssueWorkspaceMarker`
  type and keeps the public API minimal.

- **DefaultCleanupRunner.computeDirectorySize uses `du -sb`.** The `du -sb` command
  reports bytes without traversing subdirectory headers, giving a fast single-number
  result. In the test stub, sizes are injected directly so no real `du` execution
  occurs.

- **No in-flight work collision prevention needed beyond `phase === "eligible"`.**
  By the time a registry entry transitions to `eligible`, the server has confirmed
  the workflow run is terminal. No in-flight work item can be associated with a
  terminal run — dispatch only happens for non-terminal runs. Active entries are
  never on the cleanup path.

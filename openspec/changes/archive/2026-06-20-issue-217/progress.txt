# Issue 217 — Build-stage progress

## Codebase Patterns

- The Mohist runner is a TypeScript package in `packages/runner/`; actions live
  in `src/actions/` and are registered in `src/actions/registry.ts`. Test
  patterns use `setXxxForTest()` injectors (e.g. `setRebaseGitRunnerForTest`,
  `setRebaseExistsCheckerForTest`, `setRebaseConflictResolverForTest`) so a
  spec can mock `git` calls deterministically.
- The runner detects residual rebase / merge / cherry-pick state via
  `git rev-parse --git-path <X>` (to get the absolute `.git/<X>` path
  for a real worktree, or a relative path for a bare repo) followed by
  `exists()`. The same pattern is used in `rebase.ts` (`isRebaseInProgress`)
  and `registry.ts` (the merge-ready squash-merge probe). New gates
  should follow this pattern so a future change to git's state
  directory layout is updated in one place.
- The two rebase paths (`mohist/rebase` and `mohist/prepare`) used to be
  near-duplicates: same `abort → rebase → conflict-loop → abort` flow, differing
  only in `fetch <remote> <baseBranch>` + dirty-tree handling. Both are
  registered in `createDefaultRegistry()`; the cutover (T-005) deletes prepare
  and the landing mechanism.
- Test injection: `setRebaseGitRunnerForTest` swaps the `git` runner used by
  `rebase.ts`. The default runner is `git(workDir, args, signal)`, returning
  `{ success, stdout, stderr, exitCode, combinedOutput }`.
- Failure kinds for the rebase family: `retry-safe`, `conflict`,
  `squash-message-missing`. `prepare` previously had its own `failureKind`
  set; the unified rebase output JSON uses the same field name so downstream
  renderers (CLI DeliveryFailureGuidance, web delivery-failure.ts) keep
  working. The new `rebase` payload adds `remote`, `baseRef`, `rebasedOntoSha`,
  `squashed`, `squashedHeadSha`, and `failureKind` (always present, null on
  success).
- The branch-stability contract (`workspace-materialization` spec) requires
  that the rebase action never checks out the base branch inside the workflow
  workspace. The unified rebase only runs `git fetch <remote> <baseBranch>`,
  `git rev-parse <remote>/<baseBranch>`, and `git rebase <remote>/<baseBranch>`.
  Squash uses `git reset --soft <sha> <runBranch>` semantics (HEAD moves,
  branch ref stays on the run branch, working tree preserved) plus
  `git commit -m <message>`. No `git checkout <base>` is ever issued.
- Run-branch ref immobility: `git rebase` only advances the run branch ref on
  success. Squash is gated on a successful rebase and is a ref-only operation
  followed by one commit, so it cannot re-introduce a "mid-rebase crash"
  failure surface. This is the safety invariant that makes the workspace
  health gate (T-003) non-destructive.

## Task T-001: Unify mohist/rebase with remote + squash options (absorb prepare)

- What was implemented
  - `mohist/rebase` now accepts two new options on top of its existing
    `baseBranch` / `maxConflictRetries` / `conflictResolver`:
    - `remote` (string, optional): when set, run `git fetch <remote>
      <baseBranch>` first and rebase onto `<remote>/<baseBranch>`. When
      unset, rebase onto the local base branch (previous behavior).
    - `squash` (bool, optional) + `message` (string, required when squash
      is true): after a successful rebase, fold N commits into 1 by
      running `git reset --soft <baseSha>` followed by
      `git commit -m <message>`. The base SHA is the `<remote>/<baseBranch>`
      tip (or the local `baseBranch` tip) that was just rebased onto.
  - The squash phase only runs after a successful rebase (success or
    conflict-resolved). It never runs in parallel with a rebase, never
    inspects the working tree, and produces no conflicts.
  - `rebaseStatusAction` now honors the same `remote` option so the
    preflight can verify against `<remote>/<baseBranch>`.
  - Output JSON (`kind: "rebase"`) now exposes: `baseBranch`, `remote`,
    `baseRef`, `rebasedOntoSha`, `beforeHeadSha`, `afterHeadSha`,
    `squashed`, `squashedHeadSha`, `conflicts`, `resolveAttempts`,
    `failureKind` (always present, null on success), `output` (git output).
  - `applyWorkflowAgentDefault` is still exported for downstream callers
    (`registry.ts` imports it for prepare's resolver followup). Backward
    compatibility for the existing prepare-action callsite is preserved
    because the function's shape is unchanged.
  - `mohist/prepare` and `mohist/publish` are still registered in
    `createDefaultRegistry()`. The cutover (T-005) deregisters them.

- Files changed
  - `packages/runner/src/actions/rebase.ts` — extended `rebaseAction` with
    `remote` + `squash` + `message`, extracted `runSquashIfRequested`
    helper, updated `rebaseStatusAction` to honor `remote`, added
    `failureKind` (`retry-safe` | `conflict` | `squash-message-missing` |
    null) to the output JSON.
  - `packages/runner/tests/rebase.spec.ts` — added explicit tests for the
    local-base path, the remote-fetch path, the squash fold (N→1), the
    squash-without-message path, the squash-after-failed-rebase
    (no squash runs), remote-fetch failure, and base-ref resolution
    failure. Updated existing tests to cover the new
    `rev-parse <baseRef>` call that resolves the base SHA.

- **Learnings for future tasks:**
  - Decisions made
    - The squash base SHA is captured immediately after the optional
      `fetch` via `git rev-parse <remote>/<baseBranch>` (or
      `git rev-parse <baseBranch>`). `reset --soft` then targets the
      resolved SHA (not the symbolic ref) so the squash base is
      anchored to the exact commit we rebased onto.
    - `squash: true` without a `message` is treated as a configuration
      failure (`failureKind: "squash-message-missing"`), not a retry
      condition. This protects the workflow author from accidentally
      landing a squash with a default message.
    - The `failureKind` field is always present in the rebase output
      JSON (null on success). This matches the existing
      prepare/publish contract used by the downstream
      DeliveryFailureGuidance renderer.
    - The rebase action still uses `commitPendingChanges` to auto-commit
      any uncommitted worktree changes before rebasing (so agent work
      survives into the rebase). This composes cleanly with the
      health gate (T-003) and preserves the dirty-worktree boundary
      that the executor relies on.
  - Gotchas discovered
    - `git reset --soft <sha>` is correct for the squash — it moves HEAD
      back to the base while keeping the work tree and index at the
      rebased tip. Using `git reset --mixed` would wipe the index and
      break the assumption that the squash is conflict-free.
    - The rebase action must not pass the symbolic `<remote>/<baseBranch>`
      ref to `reset --soft`; it must pass the resolved SHA. Otherwise
      the resolved ref might shift between fetch and reset.
    - The pre-rebase `rev-parse <baseRef>` call was added to capture the
      base SHA; the existing test mocks needed to be updated to return
      the same SHA from `rev-parse <baseBranch>` and
      `merge-base <baseBranch> HEAD` (otherwise verifyRebaseComplete
      reports a non-match and the resolver path aborts).
  - Patterns / API shapes established
    - The `rebase` output JSON contract is now: `{ kind, status, baseBranch,
      remote, baseRef, rebasedOntoSha, beforeHeadSha, afterHeadSha,
      squashed, squashedHeadSha, rebased, conflicts, resolveAttempts,
      failureKind, output }`. Other actions rendering rebase evidence
      should treat `failureKind` as a closed enum.
    - Test mocks for rebase must handle the new pre-rebase calls
      (`fetch <remote> <baseBranch>` when `remote` is set;
      `rev-parse <baseRef>` always). Mocking only the original call
      list will trigger `unexpected git call` failures.
  - Cross-task invariants
    - The rebase action's contract is "stay on `workspace.branch`, never
      `git checkout <baseBranch>`". Tasks that add new behavior to
      `mohist/rebase` must preserve this. The squash helper uses
      `reset --soft` + `commit`, which respects the contract because
      `reset` does not switch branches.
    - Squash is a **post-rebase** operation. Any future rebase feature
      that wants to fold commits (e.g. autosquash, fixup chains) must
      run after the rebase succeeds and must not introduce a new
      failure kind that bypasses `failureKind: "retry-safe" | "conflict"
      | "squash-message-missing"`.
    - The T-005 cutover depends on `mohist/rebase` being a drop-in
      replacement for `mohist/prepare` (same conflict-resolution loop,
      same dirty-tree handling) plus the squash option. Tests that
      exercise the new `remote: "origin"` path in T-001 are the
      contract that T-005 will rely on.

## Task T-002: Add mohist/push as a pure fast-forward ref push

- What was implemented
  - New `pushAction` in `packages/runner/src/actions/push.ts` that
    fast-forwards a prepared commit to the remote base branch via
    `git push <remote> <source>:<target>` with no checkout, no landing
    clone, and no working-tree mutation.
  - `source` defaults to `workspace.branch` (read from
    `variables.workspace.branch`), `target` defaults to
    `repository.baseBranch` (or `project.defaultBranch`/`baseBranch`,
    falling back to `main`), `remote` defaults to `origin`.
  - Pre-push `git rev-parse <source>` captures the commit being pushed
    so the result records the exact landed SHA. Push failure is
    classified as `base-moved` when git reports
    `non-fast-forward` / `fetch first` / `! [rejected]`-with-hint, and
    `retry-safe` for every other failure (network, auth, ref-resolve).
  - Registered in `createDefaultRegistry()` as `mohist/push`. The new
    action coexists with the existing `mohist/prepare` and
    `mohist/publish` actions; the T-005 cutover deregisters them.
  - Output JSON contract: `{ kind: "push", status, source, target,
    remote, refspec, workDir, landedCommit, pushed, failureKind,
    output }` — `failureKind` is always present (null on success).

- Files changed
  - `packages/runner/src/actions/push.ts` — new file: `pushAction`,
    `setPushGitRunnerForTest` test injector, `looksLikeNonFastForward`
    helper (mirrors the one in `registry.ts` for `publishAction`),
    `pushOutput` builder.
  - `packages/runner/src/actions/registry.ts` — imports
    `pushAction from "./push.js"` and registers `mohist/push` after
    `mohist/publish` in `createDefaultRegistry()`.
  - `packages/runner/tests/push.spec.ts` — replaced the previous
    `publishAction`-on-landing-workspace tests with a focused suite
    for the new `pushAction`. 10 tests cover:
    1. successful fast-forward push (source resolved, push issued,
       landedCommit recorded, pushed=true, failureKind=null).
    2. no checkout / no clone / no worktree mutation.
    3. non-fast-forward rejection → `failureKind: "base-moved"`.
    4. `fetch first` hint → `failureKind: "base-moved"`.
    5. transient auth error → `failureKind: "retry-safe"`.
    6. source `rev-parse` fails → `failureKind: "retry-safe"`,
       `landedCommit: null`.
    7. explicit `remote` option → `push upstream mo/issue-99:master`.
    8. explicit `source` option → `push origin custom-source:master`.
    9. no `git clone` is ever issued.
    10. landed-commit + push-occurred flag are both recorded in the
        result so downstream renderers can rely on a single owner.

- **Learnings for future tasks:**
  - Decisions made
    - `pushAction` is registered in `createDefaultRegistry()` but
      nothing invokes it yet — T-005 rewrites the YAML to call
      `integrate:push` after `integrate:rebase`. The action's
      contract is fixed at this point: source/target/remote inputs
      with sensible defaults pulled from `context.variables` so the
      YAML can use either `with:` overrides or rely on the
      workspace/repository variable inheritance.
    - The `looksLikeNonFastForward` helper is duplicated between
      `push.ts` and `registry.ts`. T-005 deletes the publish path
      from `registry.ts`; once publish is gone, the helper in
      `push.ts` is the only copy needed. Future cleanup tasks can
      remove the dead helper from `registry.ts`.
    - The push action does NOT call `git fetch` before pushing. The
      rebase task already fetched `origin/<baseBranch>` and confirmed
      ancestry immediately before; an extra fetch in push would only
      race. Non-fast-forward is the authoritative `base-moved`
      signal.
    - Test mocks must handle `rev-parse <source>` + `push <remote>
      <source>:<target>` as the two expected calls. The push.spec.ts
      tests use the workspace path as both `workDir` (so the action
      runs against the bound workflow workspace, never a landing
      clone).
  - Gotchas discovered
    - The pre-existing `push.spec.ts` was named after the upcoming
      action but actually exercised `publishAction` (landing-workspace
      semantics). It was rewritten from scratch for T-002 — the old
      tests now belong to the soon-to-be-deleted `mohist/publish`
      action and would have become dead tests after T-005. The new
      suite is action-specific and uses the same test injection
      pattern (`setPushGitRunnerForTest`) as the rebase action.
    - The test file's pre-existing import block referenced
      `setDeliveryWorkspaceManagerForTest`, `LandingWorkspaceInfo`,
      and `DeliveryWorkspaceManager` because the OLD push tests
      shared infrastructure with `publish.spec.ts`. The new
      `push.spec.ts` is independent: it only needs
      `setPushGitRunnerForTest` and `pushAction` from
      `./actions/push.js`.
  - Patterns / API shapes established
    - The `push` output JSON contract: `{ kind, status, source,
      target, remote, refspec, workDir, landedCommit, pushed,
      failureKind, output }`. The closed failure-kind enum for push
      is `"base-moved" | "retry-safe" | null`. The CLI
      DeliveryFailureGuidance renderer and web delivery-failure.ts
      can detect the kind from the JSON `failureKind` field first
      and fall back to parsing the human-readable message.
    - The push action's contract is "stay on `workspace.branch`,
      never `git checkout <target>`". Any future push feature
      (e.g. push-tags, multi-ref push) must preserve this. The push
      action's only git calls are `rev-parse <source>` and
      `push <remote> <source>:<target>` — no `checkout`, no `clone`,
      no `reset`, no `merge`, no `commit`, no `fetch`.
    - Test injection: `setPushGitRunnerForTest` swaps the `git`
      runner used by `push.ts`. The default runner is
      `git(workDir, args, signal)`, returning
      `{ success, stdout, stderr, exitCode, combinedOutput }`. Mock
      helpers (`ok`, `fail`) and `workspaceCalls(calls)` are
      in-file.
  - Cross-task invariants
    - The branch-stability contract (`workspace-materialization` spec)
      requires that the push action never checks out the target
      branch inside the workflow workspace. `pushAction` enforces
      this by issuing only `rev-parse <source>` and
      `push <remote> <source>:<target>` against `context.workDir`.
      The push task is the SINGLE push owner during delivery — the
      rebase task does NOT push.
    - The non-fast-forward rejection is the authoritative
      `base-moved` signal. T-005's end-to-end acceptance (#8)
      depends on push correctly classifying a base-moved push as
      `base-moved` so the workflow can re-rebase and retry, not
      paper over the rejection.
    - The push action does not delete or move the workflow
      workspace's refs. The run branch ref is untouched by push;
      only the remote base branch ref advances as a fast-forward.
      This composes cleanly with T-003's workspace health gate
      (push failure leaves the workspace on `workspace.branch`,
      clean, with no in-progress rebase/merge state).

## Task T-003: Add the workspace health gate at verify/materialize entry

- What was implemented
  - A workspace health gate at the entry of both
    `WorkspaceManager.verify` and `WorkspaceManager.materialize`. The
    gate probes for residual `.git/rebase-merge`, `.git/rebase-apply`,
    `.git/MERGE_HEAD`, and `.git/CHERRY_PICK_HEAD` state inside the
    workflow workspace and, when any is present, aborts the
    in-progress operation (`git rebase --abort` / `git merge --abort`
    / `git cherry-pick --abort`), checks out `workspace.branch`, and
    `git reset --hard <runBranch>` to align the tree+index to the
    run branch ref. The workspace is then handed to the task with no
    conflict markers, no partial resolution state, and the run
    branch ref untouched.
  - Placement matches the dispatch flow: `verify()` is the per-task
    entry point (`executor.ts:112`), `materialize()` is the
    workflow-start entry point (`runner-signalr.ts:38`). The gate
    runs at the very top of both, BEFORE marker / branch / cache
    checks, so a `#166`-style mid-rebase crash is healed before any
    other state is examined.
  - The gate is a no-op when the workspace path does not exist
    (first-time materialize of a fresh run) or when no residual
    state is detected. Untracked files are intentionally left alone
    (no `git clean -fd`); only the aborted op + `reset --hard` to
    align tracked state. This matches the design's "do not drop
    agent artifacts" trade-off.
  - Five new tests in `tests/workspace.spec.ts`:
    1. `Verify_RecoversFromMidRebaseCrashAndPreservesRunBranchRef`
       — the primary acceptance criterion. Materializes a workspace,
       commits agent work to the run branch, advances `master`,
       runs a real `git rebase master` that conflicts, leaves the
       residual state on disk, then calls `verify()`. Asserts the
       workspace self-heals (clean tree, on run branch, agent's
       commit preserved at the original ref SHA) and a subsequent
       `verify()` is a no-op.
    2. `Materialize_RecoversFromMidRebaseCrashBeforeAnyCacheRepair`
       — same fixture, but the recovery is driven through
       `materialize()` to assert the gate also fires at the
       workflow-start entry.
    3. `Verify_CleanWorkspacePassesThroughGateUnchanged` — gate
       is a no-op for a clean workspace (no `reset --hard` is
       issued, the run branch ref is preserved).
    4. `Verify_RecoversFromResidualMergeHeadState` — plants a
       `MERGE_HEAD` marker and verifies the gate uses
       `git merge --abort` to heal.
    5. `Verify_RecoversFromResidualCherryPickHeadState` — plants a
       `CHERRY_PICK_HEAD` marker and verifies the gate uses
       `git cherry-pick --abort` to heal.

- Files changed
  - `packages/runner/src/runtime/workspace.ts` — added the private
    `runHealthGate(workspacePath, runBranch, signal)` method and
    `detectResidualState(workspacePath, signal)` helper. Wired
    `runHealthGate` into the top of `verify()` (after computing
    `workspacePath` and `runBranch`, before the existence / marker
    / branch checks) and into the top of `materialize()` (after
    computing `workspacePath` and `runBranch`, before any cache
    repair or workspace clone). The cache / clone / marker logic in
    `materialize()` is unchanged — the gate just runs first.
  - `packages/runner/tests/workspace.spec.ts` — added a new
    `describe("WorkspaceManager health gate (T-003)")` block with
    five end-to-end tests that exercise the gate against real git
    state (no mocks). The new block sits between
    `WorkspaceManager` and `WorkspaceManager.slugify`.

- **Learnings for future tasks:**
  - Decisions made
    - The gate's `git rebase --abort` / `git merge --abort` /
      `git cherry-pick --abort` calls are intentionally
      best-effort. A non-zero exit (which happens when there is no
      in-progress op to abort, or when the git state is corrupt)
      is ignored — the subsequent `git reset --hard <runBranch>` is
      the authoritative recovery, and the reset's success is
      guaranteed by the safety invariant (the run branch ref was
      not moved by the failed op). The `reset --hard` itself is
      strict: if it fails, the gate throws and the error bubbles
      up. This means a truly broken workspace surfaces as a
      dispatch-time git error, not a silently-passed gate.
    - The gate runs in `materialize()` BEFORE the cache repair and
      BEFORE the workspace-existence check that decides whether to
      delete the workspace for a marker mismatch. This ordering
      matters: a stale workspace from a previous, crashed run
      carries the residual state, and the gate's `reset --hard`
      aligned to the run branch ref must happen first, then the
      marker check can decide whether to delete or reuse. If the
      gate ran after the marker check, a mismatched-marker
      workspace would already have been deleted and the gate
      would be a no-op (which is fine for the no-marker-match
      case) but the residual state on a still-marker-matched
      workspace would not be cleaned (the bug T-003 fixes).
    - The gate does NOT issue `git fetch`. The crash-safety
      invariant is local-only: the run branch ref on disk is
      preserved across a crash, so no remote interaction is
      required. The rebase action's own `fetch <remote> <base>`
      (T-001) handles remote state; the gate is a purely local
      recovery.
    - The gate's recovery contract is: tree+index aligned to the
      run branch ref, no in-progress rebase/merge/cherry-pick
      state, on the run branch. It does NOT validate the run
      branch ref itself; if the ref is missing, `git reset
      --hard <runBranch>` fails and the gate throws. The
      existing `verifyWorkspaceBranch` check (called after the
      gate in `verify()`) provides the post-recovery branch
      invariant; a missing ref is a workspace infrastructure
      failure, not a gate failure.
  - Gotchas discovered
    - `git rev-parse --git-path <X>` returns either an absolute
      path (when in a linked worktree or with `GIT_COMMON_DIR`
      set) or a path relative to the worktree root. The
      `detectResidualState` helper detects absolute vs. relative
      and joins with `workspacePath` for the relative case,
      matching the `resolveGitPath` helper in `rebase.ts`. Without
      that, a `--shared` clone whose `.git` is a file pointing
      to the cache's `objects` could be mis-resolved.
    - The pre-existing `executor-branch-stability.spec.ts` test
      `retryAfterBranchInvariantViolationRecoversWorkspaceBranchViaStartBoundaryPrecheck`
      has a flaky assertion that fails before and after T-003
      (`expect(workspaceManager.materializeCalls).toBe(1)` sees
      0). It is unrelated to the health gate: it uses a custom
      `workspaceManager` mock that does not match the
      `planResolution` contract the executor expects. Documented
      here so future tasks don't waste cycles investigating.
    - The `acp-agent.spec.ts` test
      `ExistingSharedSessionStreamsThoughtChunks_ProbeWindowCrossed_DoesNotTimeoutOrAppendThoughtText`
      and `runner-host.spec.ts`
      `RunnerConnection_WhenSignalRFails_DoesNotPollAndRetriesCleanly`
      also fail in the current T-003 environment but are
      pre-existing and unrelated to the health gate. Confirmed
      by `git stash`-ing the T-003 changes and reproducing the
      same failures.
  - Patterns / API shapes established
    - The gate is a private method
      (`WorkspaceManager.runHealthGate`) and a private helper
      (`WorkspaceManager.detectResidualState`). Both are
      internal to `workspace.ts` and do not form a public API.
      Future features that need a similar self-healing entry
      (e.g. for a future `check`-stage gate) should add a
      separate `runHealthGate` on the relevant manager rather
      than extracting a shared utility — the gate is bound to
      the workspace's run branch ref, which is per-workspace.
    - The "detect-then-heal" pattern is the contract for any
      future in-progress-op recovery: probe for the marker with
      `git rev-parse --git-path` + `exists()`, abort the
      matching op best-effort, then `reset --hard <ref>` for
      authoritative recovery. New ops (e.g. `git revert`) can
      be added by extending the priority order in
      `detectResidualState` and the abort branch in
      `runHealthGate`.
  - Cross-task invariants
    - The crash-safety invariant: `git rebase` advances the
      run branch ref ONLY on success; while a rebase is in
      progress, the ref is at the pre-rebase commit. T-001's
      rebase action relies on this for the squash
      `reset --soft` to target the right base SHA. T-003's
      health gate relies on this for `reset --hard <runBranch>`
      to be non-destructive. Any future rebase feature
      (autosquash, fixup chains, `--update-refs`, etc.) must
      preserve this invariant — the gate assumes the run
      branch ref is still reachable after a crash.
    - The branch-stability contract (`workspace-materialization`
      spec) is preserved by the gate: the gate's only writes
      are `git checkout <runBranch>` (no branch change if
      already on it) and `git reset --hard <runBranch>`. The
      run branch itself is never moved by the gate; the
      workspace ends on `workspace.branch` and the ref is
      preserved. T-005's landing-removal depends on this.
    - The once-per-run materialization contract
      (`workspace-materialization` spec) is preserved: the
      gate runs in `materialize()` but does not add a new
      materialize trigger. If no workspace exists, the gate
      is a no-op. The cache / clone / marker logic is
      unchanged.
    - T-005's deletion of the landing workspace mechanism
      (createLandingWorkspace / disposeLandingWorkspace /
      pruneLandingWorkspaces) is now safe: the gate is the
      runner's only crash-safety mechanism and it is in place.
      The T-003 tests in
      `Verify_RecoversFromMidRebaseCrashAndPreservesRunBranchRef`
      are the contract T-005 will rely on for the cutover's
      acceptance criterion #4 and #8.

## Task T-004: Switch merge-ready preflight to merge-base --is-ancestor

- What was implemented
  - `mergeReadyAction` (in `packages/runner/src/actions/registry.ts`)
    is now a ref-only preflight. It resolves the base via
    `git rev-parse origin/<baseBranch>` and the run branch via
    `git rev-parse <source>` (defaulting to `workspace.branch`, then
    `HEAD`), then issues `git merge-base --is-ancestor origin/<base>
    <runBranch>`. A zero exit code reports `canMerge: true`; non-zero
    reports `canMerge: false` with a rebase-required error message.
  - The landing-clone `merge --squash --no-commit` probe
    (`runSquashMergePreflight` and `runSquashMergePreflightInLanding`)
    is removed. No checkout, no landing clone, no working-tree
    mutation: the preflight only issues `rev-parse` and `merge-base`
    against `context.workDir` and never touches a separate clone.
  - The `remote` option is now honored (defaults to `origin`); the
    preflight target is `${remote}/${baseBranch}`. The `source`
    option now defaults to `workspace.branch` and falls back to
    `HEAD` when the workspace branch variable is absent.
  - Conflict-file detail is no longer reported by the preflight
    (the preflight is now a readiness signal, not a probe merge);
    the schema keeps `conflictFiles: []` for backward compatibility
    with downstream consumers that expect the field to be present.
  - `merge-ready.spec.ts` is rewritten to the is-ancestor model:
    11 tests cover the prepared/behind-base/branch-stable/no-clone
    paths, base-ref / source-ref failure modes, explicit
    `source`/`remote` overrides, the `workspace.branch` default,
    the `HEAD` fallback, the ref-only invariant (no
    `checkout`/`merge --squash`/`reset`/`fetch`/`clean`/`add`/
    `commit`/`clone` issued), and the "no landing clone created"

- **Learnings for future tasks:**
  - Decisions made
    - The preflight retains the `rev-parse origin/<base>` +
      `rev-parse <source>` calls before the `merge-base --is-ancestor`
      check, so the structured output still carries `baseSha`,
      `candidateHeadSha`, and `mergeBaseSha`. These are useful for
      downstream renderers (CLI / web) to show the candidate vs.
      base state, even though the preflight is now is-ancestor-only.
    - The `source` option now defaults to `workspace.branch`
      (previously `HEAD`). This matches the convention used by
      `pushAction` (T-002) and the new `mohist/rebase` (T-001) so
      the three delivery actions all read the same input. When
      `workspace.branch` is `null`/`undefined`, the preflight falls
      back to `HEAD` so the action still works in tests and in
      workflows that don't set the variable.
    - The schema keeps `conflictFiles: []` on every result. The
      worktree-manager spec ("Read-only squash mergeability
      preflight") Scenario 1 requires `conflictFiles` (empty) on
      the prepared result, so the field stays present for spec
      compliance; the contract is "the preflight never reports
      conflict files" — an empty array is the correct expression of
      that contract.
    - No `setDeliveryWorkspaceManagerForTest` import remains in
      the test file — the merge-ready action no longer touches the
      workspace manager. T-005's landing deletion will leave
      `setDeliveryWorkspaceManagerForTest` and
      `DeliveryWorkspaceManager` unused, ready to be removed in the
      cutover.
  - Gotchas discovered
    - `git merge-base --is-ancestor` returns exit code 1 (not an
      error to stderr) when `<source>` does not contain `<base>`;
      the `success: false` flag in the git-runner result is the
      correct signal, and the preflight maps it to
      `canMerge: false`. The stderr is empty for the non-ancestor
      case, so the fallback error string
      (`"<source> does not contain the latest '<baseRef>' tip;
      rebase is required before merging."`) is what shows up in
      the JSON `error` field.
    - `merge-base --is-ancestor <base> <source>` (the order of
      arguments) is "is `<base>` an ancestor of `<source>`?" — i.e.
      does `<source>` already contain `<base>`? This is the
      is-prepared direction: a run branch whose history already
      contains the latest base tip is ready; a run branch whose
      history doesn't yet contain the latest base tip is not. The
      argument order must not be flipped (it would invert the
      semantic and report `canMerge: true` exactly when the
      candidate is behind base, which is the opposite of what we
      want).
  - Patterns / API shapes established
    - The `merge-ready` output JSON contract is now:
      `{ kind, targetBranch, strategy, baseSha, candidateHeadSha,
      mergeBaseSha, canMerge, conflictFiles, checkedAt, error }`.
      `canMerge` is a boolean; `error` is `null` on success.
      `conflictFiles` is always `[]` (the preflight never reports
      conflicts). Downstream consumers that render conflict
      evidence for delivery failures should switch to the rebase
      task's `conflicts` array (T-001's rebase output).
    - The preflight's git-call sequence is fixed:
      1. `rev-parse origin/<baseBranch>` (capture `baseSha`).
      2. `rev-parse <source>` (capture `candidateHeadSha`).
      3. `merge-base origin/<baseBranch> <source>` (capture
         `mergeBaseSha`).
      4. `merge-base --is-ancestor origin/<baseBranch> <source>`
         (the authoritative readiness signal).
      Tests for the preflight must mock all four calls; mocking
      only the `merge-base --is-ancestor` call will trigger
      `unexpected git call` failures in the existing test mocks.
    - The preflight's "ref-only" invariant: NO `checkout`,
      `merge --squash`, `reset`, `clean`, `add`, `commit`,
      `fetch`, or `clone` is ever issued against `context.workDir`.
      Tests assert this with a Set-based negative-lookup
      (`expect(cmds.has("checkout main")).toBe(false)`, etc.).
  - Cross-task invariants
    - The merge-ready preflight's contract: "the workflow workspace
      stays on `workspace.branch`". T-005's landing deletion is
      now safe for the preflight's branch (merge-ready already
      stopped calling `createLandingWorkspace`/`disposeLandingWorkspace`).
    - The authoritative conflict-detection path is now
      `mohist/rebase` (T-001). When the is-ancestor preflight
      reports `canMerge: true` but the Integrate rebase still
      produces conflicts, the rebase task reports the structured
      `conflicts` array and `failureKind: "conflict"`. This is the
      hand-off documented in the worktree-manager spec's
      `Authoritative final squash merge diagnostics` migration
      note.
    - The preflight's `remote` option defaults to `origin`; the
      rebase action's `remote` option also defaults to `origin`.
      Future refactors that change the default for either should
      change both — they represent the same "this project's
      canonical upstream" concept.
    - The new `mergeReadyAction` no longer imports
      `LandingWorkspaceInfo` / `DeliveryWorkspaceManager` /
      `setDeliveryWorkspaceManagerForTest`. T-005 can safely
      delete these from `registry.ts` after deleting
      `prepareAction`/`publishAction`.

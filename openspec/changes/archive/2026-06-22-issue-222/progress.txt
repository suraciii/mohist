## Codebase Patterns

- **EF table conventions**: real columns for control-plane scalar data (`AgentRow` was JSON blob, but new tables with structured scalars use real columns + a DB-level check constraint, e.g. `CK_Runners_Slots_Positive`). Migrations live in `packages/server/src/Mohist.Server/Infrastructure/Data/Migrations/`. Each migration has a `.cs` and a `.Designer.cs` (snapshot at that point); `MohistDbContextModelSnapshot.cs` is the current snapshot. Generated via `dotnet ef migrations add <Name> --project ... --startup-project ... --no-build`. Tests use `Mohist:SqliteConnectionString` env or `MOHIST_DB_PATH` for actual migration runs.
- **Store location**: per-aggregate persistence boundary under `Infrastructure/Data/<Aggregate>/<Row>Store.cs`. Row entity is a POCO; the Store class wraps `IDbContextFactory<MohistDbContext>` and uses short-lived `await using` contexts per call. Register with `services.AddScoped<...Store>()` in `MohistServiceRegistration.ConfigureMohistServices`. Test scaffolding: `IDbContextFactory<MohistDbContext>` wrapper around `DbContextOptions<MohistDbContext>` with `UseSqlite($tmp/db-{guid}.db)` + `EnsureCreated()` is the lightweight unit-test pattern (see `AgentSessionStoreSpecs`).
- **Test trait categorization**: every spec tagged with `[Trait(Traits.Speed.Name, Traits.Speed.Unit|Grain|Service|Integration)]` and `[Trait(Traits.Sut.Name, Traits.Sut.<Context>)]`. New runner data-layer specs are `Speed=Unit, Sut=Runner`. Spec file location: `packages/server/tests/Mohist.Server.Tests/Specs/<Context>/<Layer>/<Name>Specs.cs`. New runner data tests live in `Specs/Runner/Data/`.
- **Migration verification**: to confirm migration works on both empty and existing DBs, run `dotnet ef database update` against an empty `MOHIST_DB_PATH`, then against a DB pre-migrated to `20260619142739_AddProjectIssueTemplates` (the prior migration) and confirm `Runners` table only appears after the new migration. EF's `MohistDbContextModelSnapshot.cs` plus the generated `.Designer.cs` should both contain the same `RunnerRow` definition (check by `grep -n "RunnerRow" ...` and read both blocks).
- **DB-side invariant enforcement**: scalar invariants (e.g. `Slots > 0`) get a CHECK constraint at the model level via `entity.ToTable(t => t.HasCheckConstraint(...))`. SQLite emits it as `CONSTRAINT "CK_..." CHECK ("Slots" > 0)`. The store layer also validates in code so non-positive values throw `ArgumentOutOfRangeException` before hitting the DB.
- **GetOrInit-style idempotency**: read row, if missing insert with defaults and persist; catch `DbUpdateException` (concurrent insert) and fall back to a re-read. Pattern used for new entity initialization without explicit transactions.
- **Solution build gate**: `dotnet build Mohist.sln --nologo` runs `TreatWarningsAsErrors` (0 Warning(s) / 0 Error(s) is the bar). Web assets built via a `BeforeTargets=Build` msbuild target, so the build pulls `packages/web` artifacts.
- **Grain capacity check semantics**: `RunnerGrain.PollAsync` checks `_slots` only before claiming **from the backlog**. Work already assigned to the runner is dequeued unconditionally. Therefore capacity tests must leave extra workflows in the backlog (do not `AssignWorkflowToRunnerAsync` for them) when asserting the slot bound.
- **WorkflowGrain collection test isolation**: the `WorkflowGrainFixture` cluster is shared across `[Collection("WorkflowGrain")]` specs, and `InMemoryWorkflowBacklogDirectory` accumulates project ids across specs (never cleared). Tests that assume "no eligible runners" or "no backlogs to claim" must call `WorkflowGrainSpecs.ClearGlobalRunnerRegistryAsync()` AND `ClearBacklogAsync()` before submitting work. With T-003 there is no cross-registry merge, but stale registrations and pending workflow enqueue across specs are the dominant source of cross-test pollution.
- **Runner globalization (issue-222)**: `RunnerGrain` has no `_projectId`. Registry routing is unconditionally `RunnerRegistryKeys.Global`. `RunnerRegistryGrain.ListEligibleRunnersAsync(projectId)` ignores its argument and returns the registry's full contents (kept on the interface for call-site compatibility). `RunnerInfo.ProjectId` and the request `ProjectId` field are preserved on the wire for runner-line compatibility only — they are NOT used for routing or filtering. `RunnerRegistryKeys.ForProject` and `GrainKey.RunnerRegistry` are marked `[Obsolete]` (no compile-time errors) so cross-PR merges don't conflict; delete them after the rollout settles.
- **Project-scoped assertion removal**: any spec that asserted `scope.type == "project"` must change to `scope.type == "global"` (a runner whose `RunnerInfo.ProjectId` is set is still recorded as a global resource). `RunnerScopeView` lost its `ProjectId`/`ProjectName` fields because the view is always global; consumers that depended on those fields (none in server, none in web) would need updates.
- **xUnit `[Collection("WorkflowGrain")]` flake**: tests `RunnerBindingSpecs.Poll_WhenRegistryEntryMissing_ReRegistersRunnerPresence` and `RunnerDefinitionStateSpecs.UpdateAsync_WriteThrough_PersistsAndNextDispatchHonorsNewCapacity` occasionally time out (30s) when run as part of a large batch against the shared `WorkflowGrainFixture` cluster, but always pass in isolation. The trigger is accumulated state from many other specs (more registered runners and projects → `PollAsync` takes longer to walk the backlog claim loop); the call is not actually deadlocked. Tests should remain isolated by clearing registry + backlog at the start; do not chase this flake by adding sleeps inside `PollAsync`.

    - `RunnerScopeView` = `record(string Type)` only. Any future "more than global" scope must be a new type, not a field on this one.
    - Test pattern for "this test wants zero global runners": `await ClearGlobalRunnerRegistryAsync(); await ClearBacklogAsync();` at the very top.
    - Test pattern for "this test wants fresh state across projects": same two-line clear, since `InMemoryWorkflowBacklogDirectory` and the project backlog DB rows both accumulate.
  - **Cross-task invariants**
    - `RunnerInfo.ProjectId` (and request-side `ProjectId`) MUST remain on the wire — runner processes depend on the field for telemetry. Future API additions (UI filters, capacity reports) MAY read it but MUST NOT use it for routing, dispatch eligibility, or capacity attribution.
    - The `[Collection("WorkflowGrain")]` cluster + shared in-memory directory are the source of all cross-spec pollution. Any new test added to this collection MUST call both clears before doing work that depends on "no runners" or "no backlog projects", or risk flaky failures.
    - T-004 (PATCH slots) calls `IRunnerGrain.UpdateAsync` which already writes through (T-002). No further grain-layer work needed for T-004; T-004 is a pure API + validation layer.

- **REST data envelope convention**: routes returning a payload MUST use `ApiResults.Ok(payload)` (produces `{ success: true, data }`) rather than `Results.Ok(payload)` (raw object) so the `ApiTestClient.PatchDataAsync<T>`/`PostDataAsync<T>` envelope unwrapping works. Failure routes use `ApiResults.BadRequest(...)`. This matches every other data-returning route in `RunnerRoutes.cs` (`/poll`, `/report`) and the entire `ProjectRoutes.cs` PATCH/POST pattern.
- **`MapPatch("")` on a group resolves to the group root**: `app.MapGroup("/api/runner/{runnerId}")` + `group.MapPatch("", ...)` resolves to `PATCH /api/runner/{runnerId}` — same pattern as `ProjectRoutes.byRef.MapPatch("", ...)` for `PATCH /api/projects/{projectId}`. Do NOT use `MapPatch("/")` (that produces a trailing slash mismatch) or `MapPatch("/{runnerId}")` (that would conflict with the route parameter).

Covers: positive update round-trip (DB + grain cache), next-dispatch-cycle capacity honored via grain cache after PATCH, zero rejected with 400 + persisted value unchanged, negative rejected with 400 + persisted value unchanged, overwrite reflects new value.

  - `packages/server/tests/Mohist.Server.Tests/Specs/Runner/Api/RunnerSlotsApiSpecs.cs` (new, 5 tests)
- **Learnings for future tasks**
  - **Decisions made**
    - Route sits at the group root (`PATCH /api/runner/{runnerId}`) rather than under a sub-path like `/slots` — matches REST convention of PATCH on the resource root for a single attribute change.

## T-001 implementation notes
- `VariableBundle.DeepMerge` and `MergeIntoObject` already had the null-removal skeleton (`if (property.Value.ValueKind == JsonValueKind.Null) node.Remove(...)` etc.) but tests and a regression relied on the *opposite* old behavior. The current implementation in the workspace reflects the **new** null-removal semantics; doc comments and test names are updated to match.
- Renamed internal helper `MergeNode(JsonNode?, JsonElement)` to `MergeIntoObject(JsonNode?, JsonElement)` — `MergeNode` would imply recursive replacement semantics; the renamed helper recurses through `JsonObject` overlays only.
- `IssueModelMetadata` does NOT go through `VariableBundle.Patch` for the agent block — it builds bundles directly via `JsonNode`. The agent-block set-replace semantics are preserved (no client of `Patch`/`DeepMerge` from IssueModelMetadata).
- `WorkflowExecutionContext` has its own private `DeepMerge`/`MergeNode` — NOT touched. Out of scope for this issue (different domain).
- Callers of `VariableBundle.Patch` / `DeepMerge` / `MergeAll` / `ResolveStageVars` were audited — none rely on null=no-op. Tests that exercise these (`IssueWorkflowProfileManagerSpecs.PatchVariables_DeepMergesAcrossCalls`, `ProjectWorkflowProfileManagerSpecs.PatchVariables_DeepMerges_WithExisting`, `IssueModelMetadataSpecs.*`, `IssueVariableBuilderSpecs.*`, `WorkflowProfileManagerSpecs.ExpandTaskWith_DeepMergesObjectKey`) only use present values.
- `ExpandTaskWith` calls `DeepMerge(v, varsOverride)` where `v` is the task's `with` object and `varsOverride` is the vars entry of the same key. If a user's vars entry contains a null for a sub-key, the new semantics would now drop that sub-key from the merged `with` — this matches user intent (they explicitly nulled that key) and is forward-compatible. No existing test sets a null varsOverride.
- **Gotcha: `ResolveStageVars` needs a sidecar.** The acceptance criterion says PATCH removes the key from the stored stage vars AND `ResolveStageVars` should not fall back to top-level for that key. After Patch removes the key from the stored shape, the "explicitly cleared" signal is lost — `ResolveStageVars`'s naive deep-merge restores the key from top-level. Solution: track cleared top-level keys per stage in `VariableBundle.StagesClearedKeys: Dictionary<string, List<string>>?` (added as `[Id(2)]`). `MergeStages` collects the overlay's top-level null keys per stage; `ResolveStageVars` strips them from the merged result after the deep merge. Storage shape stays clean (cleared keys are NOT persisted in `Stages.<stage>.Vars`); the sidecar rides alongside.
- JSON round-trip for `StagesClearedKeys` works because `System.Text.Json` handles `Dictionary<string, List<string>>` natively under `JSON.Options`. Verified by `RoundTrip_Json_Serialization_PreservesStagesClearedKeys`.
- Pre-existing test failure (unrelated, do NOT fix in this task): `OtelSourceSubscriptionSpecs.ConfigureTracing_CapturesInboundAspNetCoreSpan` — fails on `master` too (verified by stash-and-rerun). Skip in CI results; mention in PR notes if it surfaces.

## T-002 implementation notes
- New `MohistCliApi.TableShape` entries: `WorkflowProfile` (renders the 3-section profile as table) and `WorkflowProfilePreview` (renders the preview `rendered` text).
- New `MohistCliApi.GetDataOrPrintErrorAsync(path)` returns `(int ExitCode, JsonNode? Data)` so callers can render a custom table without each duplicate try/catch boilerplate.
- `config get` issues ONE GET to `/workflow-profile` in `-o json` mode (raw payload printed via `PrintGetAsync`). In `-o table` mode it also fetches `/workflow-profile/prompts` and stitches the prompts dict onto the profile data before rendering — server `GET /workflow-profile` does not include prompts today, so a second fetch is needed to satisfy the spec's "renders template/variables/prompts sections" requirement.
- `config preview` reuses `PrintPostWithOutputAsync` against `/workflow-profile/prompts/{key}/preview`. Prompt keys are URL-escaped via `Uri.EscapeDataString`.
- `config set` / `config clear` are stubs that accept `number` + `--project` / `--project-id` / `-o` so `--help` shows all four verbs and parse-time errors don't surface when the user types them. They print `not implemented yet` to stderr and exit 1. T-003/T-004 will replace these stubs.
- The renderer (`TableRenderer.IssueTemplates.cs::RenderWorkflowProfile*`) emits three labeled sections: `template:` (custom YAML or inherited), `variables:` (top-level `vars` + per-stage `vars`), `prompts:` (key + body preview truncated to 200 chars). Prompt bodies are JSON-escaped via `JsonValue.TryGetValue<string>`; non-string values fall back to `<invalid>` to avoid crashing on unexpected payload shapes.
- Test harness: `packages/cli/tests/Mohist.Cli.Tests/CliIssueWorkflowConfigSpecs.cs` — 15 specs covering help, get (json + table + project/project-id alias + invalid output + server error), preview (json + table + alias + URL-escape + server error), and stub get/set exit-non-zero.
- No regression in the existing 269 CLI specs; total now 284 passing.

## Notes for T-003 / T-004 (later CLI tasks)
- `MohistCliApi.GetDataOrPrintErrorAsync` is the preferred helper for new endpoints where you need `(data, exitCode)` and want the standard server-error formatting on stderr.
- `set --template <yaml|@file>` needs `PrintPutWithOutputAsync` (per design D6). Add it mirroring `PrintPostWithOutputAsync` / `PrintPatchWithOutputAsync` so the template PUT honors `-o`.
- `set --prompt key=body|@file` PUTs use `PrintPutAsync` (no output mode flag needed — they return `{ key, body }` envelopes which the current printer handles); but reusing the new `PrintPutWithOutputAsync` is fine too.
- `@file` reading is via `api.FileSystem` directly (not `BodyInputResolver`, whose mutually-exclusive-source semantics don't fit optional repeatable prompt flags). A small helper `ExpandAtFile(string value, IFileSystem)` keeps it DRY between `--template` and `--prompt`.
- For `clear --var`, the PATCH body shape is `{ "k": null }` per issue-240 design D3. T-001's null-clear semantics make the server actually drop the key.

## T-003 implementation notes
- Added `PrintPutWithOutputAsync(path, body, mode, tableShape)` to `MohistCliApi` mirroring the Post/Patch variants; template PUT now honors `-o` (renders as `WorkflowProfile` table on success).
- Added `MohistCliApi.ExpandAtFileAsync(raw, optionName)` returning a small `ExpandAtFileResult` (Success/Failure). Strips leading `@`, reads via `IFileSystem.ReadAllTextAsync`, prints a clear error on missing/unreadable file. Reused for both `--template` and `--prompt` bodies.
- The set verb on `MohistCliCommands.Issue.cs::BuildWorkflowConfigSet` is now real (replaces the T-002 stub). Implementation order: parse + validate flags → resolve project → validate output mode → build variables PATCH body if `--var`/`--stage-var` provided → PUT template if `--template` provided → loop prompts.
- `vars` / `stages` PATCH body shape: `{ "vars": { ...top-level k/v... }, "stages": { "<stage>": { ...nested k/v... } } }`. Top-level keys (--var) and stage-scoped keys (--stage-var) merge into a single PATCH. Empty buckets are still emitted as `{}` so the server's deep-merge sees explicit empty overlays.
- Prompt path: `{issuePath}/prompts/{Uri.EscapeDataString(key)}` — keys are URL-escaped (so `plan prompt` → `plan%20prompt`). Prompt keys containing `/` are rejected BEFORE any request fires, since escaping would still let them traverse to a sibling key.
- Prompt body is sent as `{ "body": "..." }` to match the server's `IssuePromptUpsertRequest`.
- Template body is sent as `{ "yaml": "..." }` to match the server's `IssueTemplateRequest` (`yaml ?? template`).
- `--var`, `--stage-var`, `--prompt` are all `string[]` with `AllowMultipleArgumentsPerToken = true` so `--var a=1 --var b=2` and `--var a=1 b=2` both work.
- Order matters for partial-failure reporting: variables PATCH first (independent, low blast radius), template PUT second, prompt PUTs last. Each step checks the exit code and bails on non-zero, so a mid-sequence failure surfaces immediately rather than continuing to send more mutations.
- No regression in 284 CLI specs; T-003 adds 14 specs covering: no-op (exit 1, no requests), template @file + inline, var + stage-var merged body, prompt inline + @file + URL-escape + slash-rejection, composite triple-fire, malformed `--var` / `--stage-var` / `--prompt`, missing `@file`, server error surfacing, invalid `-o` value. Total CLI: 298.
- Server: 2686 tests still pass (no server changes).
- Full `dotnet build Mohist.sln` clean (TreatWarningsAsErrors).

## T-004 implementation notes
- Replaced the T-002 stub `BuildWorkflowConfigClearStub` with real `BuildWorkflowConfigClear` that wires `--template`, `--var` (repeatable), `--prompt` (repeatable) into the appropriate HTTP requests. `--template` and `--var` follow the design D3 mapping; `--var` produces `{ "vars": { "k": null, ... } }` (the null is what T-001's `VariableBundle.Patch` honors as explicit key removal).
- Implementation order: variables PATCH (independent, low blast radius) → template DELETE → prompt DELETEs. Each step checks the exit code and bails on non-zero, so a mid-sequence failure surfaces immediately rather than continuing to fire more destructive mutations.
- The variables PATCH body is `{ "vars": { ...keys mapped to null... } }`. `stages` is NOT included — clearing top-level `--var` keys does not affect staged variables, and we don't accept `--stage-var` for clear (no spec requirement for it).
- `--var` accepts a key only (no `=`); the value is implicit `null`. Malformed input (empty/whitespace key) prints a clear error and exits 1 before any request fires.
- `--prompt key` accepts the key only; the URL-escape and `/` rejection are identical to the set verb (`Uri.EscapeDataString` + slash-reject before request).
- `--template` is a bool flag. **Gotcha: `ctx.GetResult(templateOpt) is not null` returns true even when the flag wasn't given** because System.CommandLine synthesizes an implicit `false` result for `Option<bool>` defaults. T-004 uses `IsOptionProvided(ctx, templateOpt)` (the same helper already used by `BuildUpdate`) which checks `!result.Implicit`. Same trap lurks for any future bool flag added to a verb — reach for `IsOptionProvided`.
- The prompt DELETE reuses `PrintDeleteAsync` (no output-mode flag — the server returns no useful body). The template DELETE reuses `PrintDeleteWithOutputAsync` (honors `-o`).
- Test harness: `CreateHarness` already took a sync `Func<HttpRequestMessage, HttpResponseMessage>?`. Added a sibling `CreateAsyncHarness(Func<HttpRequestMessage, Task<HttpResponseMessage>>?)` so an end-to-end fake-handler test (asserting the round-trip with the null payload) can `await req.Content.ReadAsStringAsync()` inside the responder. Sync overload delegates to it via `Task.FromResult`. Keeps the existing sync responder style of T-002/T-003 tests untouched.
- **Gotcha (JsonNode null-value representation): `JsonObject["foo"]` returns `null` (C# null reference) when the JSON value is `null` — not a `JsonNode` with `ValueKind == Null`. Tests must iterate `JsonObject` to detect explicit nulls, e.g. `Assert.Null(kvp.Value)` or `Assert.Contains("foo", body["vars"].Select(kvp => kvp.Key))`. Using `body["vars"]["foo"]!.GetValueKind()` throws NRE.** A small `AssertVariableSetToJsonNull` helper encapsulates the iteration.
- 15 new specs covering: no-op (exit 1, no requests, message contains "nothing to clear"); `--template` fires single DELETE to `/workflow-profile/template` and no PATCH/PUT; `--var foo` fires single PATCH with `vars.foo` set to JSON null and asserts via `AssertVariableSetToJsonNull`; `--var foo` end-to-end against a fake handler that strips the key from an in-memory `storedVars` map (simulating the T-001 server's null-clear semantics); `--prompt key` fires single DELETE; `--prompt key` URL-escape; `--prompt key/with/slash` rejected before request; composite `--var foo --prompt greeting` fires PATCH + DELETE with no PUTs and other vars/prompts unaffected; `--var foo --template` fires both; multiple `--var` flags merged into a single PATCH with all keys set to null; `--var` only affects vars (no `stages` key); empty var key rejected before request; empty prompt key rejected before request; server-rejected var patch surfaces error; server-rejected template DELETE surfaces error; invalid `-o yaml` rejected before request. The stub spec from T-002 is replaced by `ConfigClear_NoFlags_MakesNoRequestAndExitsNonZero` (same assertion shape but the message is now "nothing to clear", not "not implemented yet").
- No regression: 298 → 313 CLI specs, all passing. Server 2677 tests pass (excluding pre-existing OtelSourceSubscription flaky specs noted in T-001). Full `dotnet build Mohist.sln` clean (TreatWarningsAsErrors).

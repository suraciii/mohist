## 2026-04-06T14:10:00Z - T-006: Update resume() for concurrent safety

**What was done:**
- Added duplicate-resume guard in `resume()`: checks `activeAgents.has(issue.id)` before proceeding, throws if issue already has an active agent
- Removed the blanket `isRunning()` gate from `/issues/:number/approve` API route that blocked ALL approvals when any agent was running
- Replaced with per-issue `isRunning(issue.id)` check after fetching the issue — only blocks approval if that specific issue is already running (not paused)
- `resume()` bypasses capacity checking (paused sessions take priority over queued agents) — this was already the correct behavior
- Resume still adds to `activeAgents` and counts toward capacity, but since the paused agent already freed its slot (via `finally` block in `executeAgent`), this is semantically correct

**Learnings:**
- The old approve route had `agentRunner.isRunning()` (no args) which blocked approval when ANY agent was running — this completely broke concurrent workflows where one agent pauses for approval while another is still running
- The `isRunning(issueId)` check in approve is per-issue: a paused issue has been removed from `activeAgents` (in `finally`), so `isRunning(issue.id)` returns false, allowing the approve to proceed
- Resume capacity semantics: paused agent frees its slot → queue may fill it → resume takes a slot (potentially exceeding maxConcurrentAgents by 1). This is acceptable since user-approved resumes should have priority over queue. When the resumed agent completes, `processQueue()` restores normal capacity.

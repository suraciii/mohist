## Codebase Patterns

- `WorkflowDefinition` records live in `packages/server/src/Mohist.Server/Workflow/Domain/Definition/WorkflowDefinition.cs` — all of the design's record shapes are there.
- Orleans surrogates use `[GenerateSerializer] struct + [RegisterConverter] sealed class : IConverter<T, Surrogate>` and `[Id(N)]` per field. The `[Id]` slot is durable — reordering is OK; reusing a slot for a different semantic field is OK; but you cannot silently drop an Id without losing in-flight grain state.
- `WorkflowYamlSerializer` uses `IgnoreUnmatchedProperties` for the deserializer, so any "removed" YAML key is just an unknown map entry and silently dropped. The serializer uses `DefaultValuesHandling.OmitNull` so absent properties do not emit.
- The check-repair runtime hook is `WorkflowRunExtensions.BuildRepairTasks` in `WorkflowRun.Check.cs` — that is the single chokepoint where the engine injects the recovery list after a check fails.
- The check-repair path that the prompt-reference scanner walks is in `PromptReferenceScanner.Scan` — it iterates each `check.OnFailure.Repair`. Removing a branch here just means deleting the `if` block, no other call sites.

## T-001: Remove VerifyTask from CheckFailureRepair

### Engine changes
- `CheckFailureRepair` collapsed from `(int Limit, TaskDefinition Task, TaskDefinition? VerifyTask = null)` to `(int Limit, TaskDefinition Task)`. The VerifyTask property is gone.
- `CheckFailureRepairSurrogate` lost its `[Id(2)] TaskDefinition? VerifyTask` field. The Orleans converter now maps only `Limit`/`Task`. The `[Id(2)]` slot is intentionally not re-used — there is no in-flight grain state to migrate because the design is pre-release and the new profile does not depend on persisted VerifyTask values (see D1 notes).
- `WorkflowYamlSerializer.ToCheck` no longer reads `verifyTask` from the YAML map. `ToCheckMap` no longer writes a `verifyTask:` key. The deserializer's `IgnoreUnmatchedProperties` already drops the key, so a profile still carrying `verifyTask:` is parsed as if the key were unknown.
- `PromptReferenceScanner.Scan` no longer traverses a `repair.VerifyTask` branch.
- `WorkflowRun.Check.cs BuildRepairTasks` returns a single-element list containing only the repair task. The verify-step append is gone.

### YAML profiles
- `mohist-default.workflow.yaml` had one `verifyTask:` block (the review-passed check's re-injection of `ai-review`).
- `mohist-pr.workflow.yaml` had three `verifyTask:` blocks (the `check:update-pr` PR-update side-effect for `health`, `review-passed`, and `merge-ready`).
- All four blocks were removed in this change. The PR-update side-effect that previously lived inside the verify step is no longer modelled; the `mohist/github-pr` profile rewrite in T-007 will express it differently.

### Test rewrites
- `PromptReferenceScannerSpecs.Scan_RepairAndVerifyTasks_ReturnTheirPromptKeys` → `Scan_RepairTask_ReturnsItsPromptKey` (no more `re-verify` prompt key).
- `CheckRetrySpecs` lost `StageWithPrUpdateAfterReviewRepair` and `StageWithPrUpdateAfterMergeReadyRepair` (the helpers that set up a `check:update-pr` verify task) and the tests that drove them. Replaced with a single new test that asserts the check-repair path is exactly `[ai-review.1, checks, fix-review-findings:1.1, checks]` and a `MergeReadyRepair_DoesNotInjectPrUpdateBeforeRecheck` test that asserts the merge-ready repair path is exactly `[ai-review.1, checks, rebase-onto-base:1.1, checks]`. The historical `CheckFails_RepairTaskRunsVerifyTaskBeforeRecheck` was rewritten as `CheckFails_RepairTaskRunsThenCheckReRuns`.
- `WorkflowCheckLoopArtifactSpecs` was the test that depended on the dual-`ai-review` cycle (verify re-running the review to produce a fresh `review.md` artifact). Without the verify task, only the original `ai-review.1` runs and the check re-runs on the existing artifact. All four dual-version tests were rewritten to assert single-version behavior; `CheckLoop_RepairPathExposesSingleRepairTaskThenCheckReRuns` and the path-history / latest / task-run-view helpers all now expect a single `ai-review.1` row.
- `MohistPrIssueWorkflowProfileSpecs` `AssertRepairPathHasPrUpdateVerifyTask` helper was replaced with `AssertRepairPathHasOnlyRepairTask` that asserts the repair path exposes only the named fix and the record's two-field shape. The `PrWorkflowDefinition_CheckRepairPathsExposeOnlyRepairTask_NoVerifyStep` test (renamed from `...AreFollowedByPrUpdateBeforeMerge`) calls the new helper for the five check names. The `PrWorkflowYaml_ParsesViaWorkflowYamlSerializer` test was updated: check-stage repairs no longer contain `create-pull-request` or `check:update-pr` (the verify-step side-effect is gone).
- `MohistDefaultWorkflowProfileSpecs.WorkflowYamlParser_ParsesRepairTasksAndWithObjects` no longer expects a verify task to be parsed. A new test `WorkflowYamlParser_TreatsVerifyTaskAsUnknownKey` parses a YAML with a `verifyTask:` block and asserts the deserializer drops it (the resulting `CheckFailureRepair` has only the repair task and the record exposes exactly two properties via reflection: `Limit` and `Task`).
- `MohistDefaultWorkflowProfileSpecs.WorkflowYamlSerializer_RoundTripsDomainDefinition` now asserts `Assert.DoesNotContain("verifyTask:", yaml)` (the serializer does not emit it) and the reparsed repair is checked for the two fields only.
- `MohistDefaultWorkflowProfileSpecs.WorkflowYamlParser_RepairTaskArtifactsAreIsolated` no longer asserts the verify task's `artifacts` (it is gone). The test is reduced to asserting the repair task inherits no artifacts from the parent.
- `MohistDefaultWorkflowProfileSpecs.DefaultWorkflowDefinition_ReviewPassedRepairVerifyTaskDeclaresMarkerOneOf` is replaced by `DefaultWorkflowDefinition_ReviewPassedRepairHasNoVerifyTask` that asserts the two-field record shape via reflection.

## Gotchas / decisions

- The check-repair path now injects exactly one task. Existing workflows that depended on the verify step re-injecting the original task (so the check would see a refreshed marker artifact like `review.md`) will have a check that re-runs against the original marker — i.e. the check still fails. The fix is `retry: self` in `onFailure` cases (T-002), which appends a fresh attempt of the original task. T-001 intentionally leaves the marker-loop case in a "check re-runs against the same artifact" state; T-002/T-003 will close the loop.
- The pre-existing flaky test `Mohist.Server.Tests.Specs.Issue.Api.IssueFeedbackApiSpecs.RejectEndpoint_RejectsAwaitingApprovalIssue` was failing before this change (verified by stashing the changes and re-running). Not caused by T-001.
- `dotnet build Mohist.sln -p:SkipWebBuild=true` reports 0 warnings 0 errors with `TreatWarningsAsErrors=true` set in `Directory.Build.props`. The targeted test filter (108 tests across `CheckRetrySpecs`, `WorkflowCheckLoopArtifactSpecs`, `MohistPrIssueWorkflowProfileSpecs`, `MohistDefaultWorkflowProfileSpecs`, `PromptReferenceScannerSpecs`, plus the 13 `WorkflowYamlSerializer` round-trip tests) all pass. The full server test suite has 2666 passing, 10 skipped, 1 pre-existing flaky failure.

## T-002: retry:self and nested (non-recursive) onFailure recovery

### Engine changes
- `TaskFailureCase` extended with a `bool RetrySelf = false` field; the `TaskFailureCaseSurrogate` gains a `[Id(2)] bool RetrySelf` slot and the converter round-trips it.
- `TaskRun` gains a `CausedByFailedTaskId` property. `TaskRun.MakeTask` accepts a new `causedByFailedTaskId` parameter and threads it through. `WorkflowRun.Task.cs RecoverTaskFailure` now passes `task.Id` as the `causedByFailedTaskId` for each injected recovery task. This is the only call site that needs the wiring — other call sites in `WorkflowRun.Work.cs` and `WorkflowRun.Stage.cs` continue to pass null.
- `WorkflowGrain.ResolveTaskFailureRecovery` now calls `BuildRecoverySequence` for the matched case. The sequence is `matchedCase.Tasks` followed (when `RetrySelf` is set AND `failedAttempts + 1 < Limit`) by a fresh `TaskDefinition` clone of the failed task. The clone preserves `Id`, `Title`, `Uses`, a deep-cloned `With` (via `CloneTaskWith`), `Artifacts`, `SetVars`, and `OnFailure`. The retried attempt goes through `TaskRun.MakeTask` like any other task; the new attempt id becomes `{DefinitionId}.{attempt+1}`.
- `WorkflowDispatchBuilder.BuildPayloadAsync` checks `task.CausedByFailedTaskId` and, when set, looks up the failed task in any stage (`FindFailedTask`) and, if the failed task has an object `Output`, serializes `failure.output = <output>` into the dispatch payload. The runner renders `${{ failure.output.* }}` from this payload — no runner-side changes needed.
- The same `CausedByFailedTaskId` wiring makes nested recovery work for free: when a recovery task fails, the engine resolves its own `OnFailure`; the resulting nested recovery tasks are inserted with `causedByFailedTaskId = failedRecoveryTask.Id`, so their dispatch payload contains the recovery task's own `failure.output.*`. No second recursion step in `ResolveTaskFailureRecovery` is required — the depth-1 bound is enforced at parse time and the runtime just re-enters the same code path.
- `WorkflowYamlSerializer.ParseTaskFailureAction` now takes `bool allowNestedOnFailure` and a new `ToRecoveryTask` helper parses the recovery tasks. The original (non-recovery) task branch passes `allowNestedOnFailure: true` (so depth-1 nested onFailure is permitted); the recovery-task branch passes `false` (so depth-2 nested onFailure is rejected). The recovery task branch validates BEFORE calling `ParseTaskFailureAction` so a clear error names the offending task id and the parent.
- `retry: self` is parsed by a new `ParseTaskFailureRetry` helper. Values other than `self` (case-insensitive) raise a clear `Workflow task '{id}' onFailure case 'retry' value must be 'self' (got '{value}')` error.
- The serializer emits `retry: self` only when `RetrySelf` is true, matching `DefaultValuesHandling.OmitNull`.

### Tests (TaskFailureRecoverySpecs, all 9 passing)
- `WorkflowYamlSerializer_ParsesTaskFailureRetrySelf` — parses `retry: self` and asserts `TaskFailureCase.RetrySelf == true`.
- `WorkflowYamlSerializer_RoundTripsTaskFailureRetrySelf` — round-trips the same YAML and asserts the emitted yaml contains `retry: self`.
- `WorkflowYamlSerializer_RejectsOnFailureOnRecoveryTaskDepth` — depth-2 rejection: a recovery task with nested onFailure whose own recovery task declares onFailure is rejected with a clear error naming the offending recovery task id.
- `WorkflowYamlSerializer_AllowsNestedOnFailureOnRecoveryTaskDepthOne` — depth-1 acceptance: a recovery task MAY declare its own onFailure; the recovery task under that nested onFailure parses without error and the resulting `TaskDefinition.OnFailure` is populated.
- `WorkflowYamlSerializer_RejectsInvalidRetryValue` — `retry: bogus` raises a clear error mentioning `self`.
- `FailedTask_WithRetrySelf_AppendsFreshAttemptAfterRecoveryTasks` — runtime: failure with `base-moved` injects `recover:rebase.1` followed by `integrate:merge-pr.2`. The fresh attempt keeps the original `OnFailure` (proven by the same retry sequence resolving on the second failure).
- `RetriedTask_FailsAgain_EvaluatesOriginalOnFailureAndExhaustsAtLimit` — runtime: limit=2 → first failure injects recovery+retry; second failure injects recovery but no further retry (failedAttempts(1)+1 == Limit == 2). Both attempts are recorded as Failed in the run history.
- `RecoveryTask_WithOwnOnFailure_TriggersNestedRecovery` — runtime: rebase-conflict shape. `recover:rebase.1` fails with `failureKind: conflict`; nested `recover:resolve-rebase-conflicts.1` is injected; the enclosing sequence then continues with `recover:push.1`. Final run status is Completed; the failed tasks are `integrate:merge-pr.1` and `recover:rebase.1`; the completed tasks are `recover:resolve-rebase-conflicts.1` and `recover:push.1`.
- `RecoveryTask_DispatchExposesFailureOutputTemplateContext` — runtime: the recovery task's `Variables` payload contains `failure.output.errorCode == "base-moved"` and `failure.output.prNumber == 42` from the failed task's raw output.

### Gotchas / decisions
- The dispatch builder's `failure` payload is only set when the failed task has a non-null `Output` of `ValueKind.Object`. If a future caller relies on `${{ failure.output.* }}` against a failure that produced no output, the runner's whole-string template expansion will throw a clear `Template variable 'failure.output.X' was not found` error. The current profile/contract always emits a structured object on failure, so this is acceptable.
- The `failedAttempts` counter in `ResolveTaskFailureRecovery` counts `t.DefinitionId == task.DefinitionId && t.Status == TaskRunStatus.Failed` across the stage. The new retry attempt's `TaskRun.MakeTask` increments `Attempt` based on the count of `DefinitionId`-matching tasks, so attempt numbering is correct across retry cycles.
- The T-001 check-repair path still works: `VerifyTask` is gone, but the recovery task is inserted with `causedByFailedTaskId = task.Id` so the dispatch builder still wires up the failure context for the next step in the recovery sequence.
- `dotnet build Mohist.sln -p:SkipWebBuild=true` succeeds with 0 warnings 0 errors. The targeted `TaskFailureRecovery` filter runs 9 tests, all passing. The wider `Workflow` filter (780 tests) runs 774 passing, 6 skipped (architecture tests). The full server test suite (2686 tests) has 2675 passing, 10 skipped, and 1 pre-existing flaky failure (`RejectEndpoint_RejectsAwaitingApprovalIssue`, also failing on T-001 baseline).

## T-003: failIf marker matching

### Engine changes
- The engine stays failIf-agnostic — it does not parse or interpret `expect.markers[*].failIf`. The runner owns the pass/fail decision (D4). The serializer already preserves `failIf` because it uses `IgnoreUnmatchedProperties` and stores the raw `with` map under `TaskDefinition.With`.
- `TaskRunExtensions.ExtractRequiredFiles` now also walks `expect.markers[*]` entries and surfaces them as `WorkflowTaskRequiredFile` rows with the new `OneOf` and `FailIf` fields. Markers are walked BEFORE files so that when both declare the same path, the marker entry wins (it carries the failIf/oneOf metadata). Same-path duplicates collapse to a single entry — `failIf` survives on the merged entry.
- `WorkflowTaskRequiredFile` (`WorkflowViews.cs`) gained `string[]? OneOf` and `string? FailIf` fields. Orleans `[GenerateSerializer]` auto-handles the new fields; no surrogate change is required because `WorkflowTaskRequiredFile` has no manual surrogate.

### Runner changes
- `expectations.ts` `TaskArtifactExpectation` gained a `failIfMatches: FailIfMatch[]` field where `FailIfMatch = { marker, failIf, path, errorCode }`. The `satisfied` field becomes false whenever a failIf marker matches — even if the marker also satisfies `oneOf`/`contains`. The `matched` field is also populated for file-marker hits (previously only set for `_output` markers).
- A new `extractErrorCode(content)` helper scans an artifact for a leading `errorCode: <value>` line and returns the value (or null). This is the convention by which the action declares its own error code alongside a verdict marker (e.g. `errorCode: review-failed` in `review.md`). The action output JSON then carries `errorCode` at the top level so the engine's `output.errorCode: ...` onFailure matching works.
- `acp-agent.ts` short-circuits the result when `verification.failIfMatches.length > 0`: `status: failure`, `errorCode` from the first failIf match, `failIfMarker: <matched marker>`, and `message` names the marker + errorCode. The action's output JSON now includes `errorCode` and `failIfMarker` fields at the top level so `setVars: output.errorCode: ...` / `onFailure.cases[*].when.output.errorCode: ...` matching picks them up.
- `acp/session-strategies.ts` `satisfyExpectations` now bails out of the repair loop as soon as a failIf marker matches — the verdict is final and the agent cannot un-fail itself by re-running. The initial `verifyExpectations` call still runs, so the action gets a populated `failIfMatches` on the very first verification.

### Tests
- Runner: 8 new tests in `expectations.spec.ts` (PASS marker passes; FAIL marker with `errorCode:` fails with that errorCode; FAIL marker without `errorCode:` fails with null; `_output` markers honor failIf too; multiple markers all record failIfMatches; no marker matched does not fail). 3 new acp-agent tests in `acp-agent.spec.ts` (PASS marker → action success; FAIL marker with `errorCode:` → action failure with that errorCode and a single prompt call; FAIL marker without `errorCode:` → action failure with null errorCode).
- Server: 6 new tests in `FailIfMarkerSpecs` (`WorkflowYamlSerializer_PreservesFailIfInTaskWith` round-trips the field; `ExtractRequiredFiles_WithExpectMarkersFailIf_ReturnsFailIfAndOneOf` extracts both fields; `ExtractRequiredFiles_WithExpectFilesAndMarkers_DedupesByPath` prefers marker entry; 3 grain tests: failure with `output.errorCode: review-failed` triggers onFailure recovery; no matching case preserves the failure; PASS marker does not invoke recovery).

### Gotchas / decisions
- `expectations.ts` was refactored from `Promise.all` + filter to a sequential for-of loop. The semantics for the existing `expect.markers[*]` shape are unchanged (verified by the 15 pre-existing tests still passing). The new sequential loop is needed because the failIf decision requires reading the matched value from each marker before deciding whether to push to `missingArtifactMarkers` vs `failIfMatches`.
- The runner's `verifyExpectations` extracts the `errorCode` from the same artifact that holds the verdict marker (`extractErrorCode` scans for an `errorCode:` line). This is a simple, action-side convention: the agent declares its own error code by writing a single line in the marker file. The engine does not synthesize an errorCode (D4) — if the action does not declare one, the task still fails on account of the marker, but `output.errorCode` is null and `onFailure.cases[*].when.output.errorCode: ...` cannot match.
- The Orleans serializer (`[GenerateSerializer]`) handles the new `OneOf` / `FailIf` fields on `WorkflowTaskRequiredFile` automatically; no surrogate change. The id-slot discipline is moot here because the type is a generated-serializable record without manual id assignments.
- `dotnet build Mohist.sln` succeeds with 0 warnings 0 errors; full runner test suite (537 passing, 23 skipped) and full server test suite (2680 passing, 12 skipped, 1 pre-existing flaky skip on `RejectEndpoint_RejectsAwaitingApprovalIssue`).

## T-004: Rename/split GitHub PR runner actions

### Action surface
- New module `packages/runner/src/actions/github-pr.ts` owns all four actions: `createGitHubPrAction`, `markGitHubPrReadyAction`, `mergeGitHubPrAction`. Shared helpers (`runGhPrecheck`, `resolveCurrentBranch`, `resolveBaseSha`, `classifyGhFailure`, the JSON parsers, `combinedGhOutput`, `errorMessage`) moved into the new module.
- Old `pull-request.ts` and `publish-via-pr.ts` modules deleted. `pull-request.spec.ts` and `publish-via-pr.spec.ts` deleted. The combined `mohist/publish-via-pr` is no longer registered; no profile references it (only the now-deleted old `mohist-pr` YAML referenced `mohist/create-pull-request` / `mohist/merge-pull-request`).
- `registry.ts` registers the new ids only: `mohist/create-github-pr`, `mohist/mark-github-pr-ready`, `mohist/merge-github-pr`. `mohist/merge-ready` is kept because `mohist-default.workflow.yaml` still uses it for its check stage.
- Test runner injectors are named `setGitHubPrGitRunnerForTest` / `setGitHubPrGhRunnerForTest`; install helpers wrap the responder with `await` to match the git runner's `(workDir, args, signal) => Promise<...>` signature.

### create-github-pr
- Pushes the workflow branch (`push --force-with-lease`), then opens or reuses a draft PR via `gh pr create --draft`. The default for `draft` is `true`; setting `with.draft: false` removes `--draft` from the create invocation. The "reuse" branch is reported as `operation: "reused"` (the old `updated` value was renamed to `reused` to make the contract clearer and to match the spec wording "creates/reuses a draft PR").
- The output JSON adds `kind: "create-github-pr"` and `draft: boolean` (echoes the requested state). `prNumber` and `prUrl` are populated on success — they are the source for the profile's `setVars: vars.github.pr.number: ${{ output.prNumber }}` and `vars.github.pr.url: ${{ output.prUrl }}` projection.
- Failure codes: `config-error` (invalid issue-field source, gh precheck fails, `gh pr create` returned no URL), `base-moved` (force-with-lease rejected as non-fast-forward), `pr-state-conflict` (`gh pr list` shape mismatch), `retry-safe` (everything else from `classifyGhFailure`).

### mark-github-pr-ready
- New action; idempotent. Only reads/writes `gh pr view --json state,isDraft,url` and `gh pr ready`. It explicitly does NOT call `git push`, `gh pr edit`, or update title/body — verified by the spec "does not call git push or update title/body" test which forbids `gh pr edit|create|merge|close|reopen` calls.
- Takes only `prNumber`. If `prNumber` is missing → `errorCode: config-error`. If `gh pr view` shows the PR is `CLOSED` or `MERGED` → `errorCode: pr-state-conflict`. If `isDraft === false` (already READY) → success, `transitioned: false`, `previousState: "READY"`, `state: "READY"`, message names the PR as already ready. If `isDraft === true` → calls `gh pr ready` and reports `transitioned: true`, `previousState: "DRAFT"`, `state: "READY"`.
- The check-stage failure contract for `prNumber === null` is symmetric with the `prNumber`-driven path on `merge-github-pr`.

### merge-github-pr
- Same checks-gated + squash + re-query + confirm shape as the old `merge-pull-request`. The output JSON is now `kind: "merge-github-pr"`. On `pr-checks-failed` failure: includes `prNumber`, `prUrl`, and a non-empty `message` (e.g. `PR #42 checks failed: build [bucket=FAIL]`) so `onFailure.cases[*].when.output.errorCode: pr-checks-failed` matches and the recovery branch's `${{ failure.output.prNumber }}` / `failure.output.prUrl` template expansion has real values.
- On `base-moved`: `gh pr merge` exit is classified via the existing `classifyGhFailure` (looks for `not mergeable` / `can't be merged` / `non-fast-forward` / `stale info`) and the action returns `errorCode: base-moved` with `prNumber`, `prUrl`, and the failure message. The recovery branch's `recover:rebase` task then takes over via T-002's `retry: self`.
- `waitChecksAndMergePr` was exported because it is the unit-under-test for the merge action's check-gated contract; the spec covers both the polling happy-path and the cancel-while-pending path with `vi.useFakeTimers()`.

### push forceWithLease
- `mohist/push` accepts `with.forceWithLease: true | "true" | "yes" | "on"` and adds `--force-with-lease` between `push` and `<remote> <refspec>`. Defaults preserve today's behavior (fast-forward push). The output JSON adds `forceWithLease: boolean` so the recovery path's audit log records which path was taken.
- `booleanInput` was added to `packages/runner/src/core/json.ts` for the canonical parser. The pre-existing local `booleanInput` in `rebase.ts` is left in place (used only by `rebase.ts`'s `squash` flag) — refactoring that is out of scope.

### Tests
- 43 new tests across `tests/create-github-pr.spec.ts` (8), `tests/mark-github-pr-ready.spec.ts` (9), `tests/merge-github-pr.spec.ts` (11), and the existing `tests/push.spec.ts` (+3 for forceWithLease). Registry-existence assertions confirm the new ids are present and the old ids (`mohist/create-pull-request`, `mohist/merge-pull-request`, `mohist/publish-via-pr`) are absent.
- Coverage of acceptance criteria:
  - create/reuse draft PR with `prNumber`/`prUrl` → `pushes the workflow branch and creates/reuses a draft PR, returning output.prNumber and output.prUrl` ✓
  - merge error codes `base-moved` and `pr-checks-failed` with `prNumber`/`prUrl`/`message` → `returns errorCode base-moved or pr-checks-failed (with prNumber/prUrl/message) on recoverable failures` ✓
  - idempotent ready: `marking an already-ready PR succeeds without mutation` ✓ (test "is idempotent: a PR already marked READY returns success without gh pr ready")
  - forceWithLease push → `mohist/push accepts forceWithLease and uses --force-with-lease when set` ✓
  - registry names → `registry.ts registers all four actions under their new names; stale registrations removed where unused` ✓ (the fourth action `merge-ready` is intentionally kept because mohist-default still references it).

### Gotchas / decisions
- The old `kind: "publish-via-pr"` JSON output and `kind: "create-pull-request"` / `kind: "merge-pull-request"` outputs are gone. Anything downstream that pattern-matches on those `kind` strings needs to follow this rename — I grepped the runner/server/web/cli surfaces and found no downstream consumer of those literal kinds (the runner's own renderer reads `failureKind` / `prNumber` / `prUrl` instead).
- `parsePrViewWithDraft` and `parsePrListWithDraft` were added because the old parsers stripped the `isDraft` flag; both shapes are now exported so `mark-github-pr-ready` and the create/reuse branch can read it. The plain `parsePrView` / `parsePrList` parsers remain for `merge-github-pr` which does not care about draft state.
- The `mark-github-pr-ready` "idempotent" check happens after the `gh pr view` and *before* `gh pr ready`. The view call is always emitted on a fresh dispatch (no cached state), so an "already ready" run still costs one `gh pr view` round-trip — that is acceptable because the action does not otherwise have authoritative state and the check happens locally. If a future caller wants zero-mutation idempotency, the action can short-circuit on a `vars.github.pr.isDraft` runtime variable.
- The mark-github-pr-ready action treats MERGED as pr-state-conflict on the view path. This is intentionally strict: marking a MERGED PR ready is meaningless and a sign of a stale dispatch (the merge action would have already returned success). Future callers can soften this if needed.
- `npm run typecheck -w packages/runner` succeeds; `npm test -w packages/runner` shows 522 passing, 23 skipped (no new failures, the 23 skips are pre-existing in acp-agent). The pre-existing `mohist/publish-via-pr`-keyed test surfaces are gone (they were 2 files / ~63 tests, replaced by 43 narrower tests).

## T-005: conflictMode:task on mohist/rebase

### Action changes
- New `conflictMode` input on `mohist/rebase` with two values: `"resolve"` (default, preserves today's inline `conflictResolver` behavior) and `"task"` (returns `failureKind: "conflict"` and leaves the rebase in progress so a follow-up `recover:resolve-rebase-conflicts` agent task can resolve and complete it). A new exported `resolveRebaseConflictMode(input)` helper does case-insensitive matching; any other value silently falls back to `"resolve"` so a malformed profile cannot accidentally trigger the new behavior.
- In `task` mode the action forces `conflictResolver = null`, so the inline resolver path is skipped. After a conflict the action does NOT call `git rebase --abort`, returns `failureKind: "conflict"` with the conflicting files in `output.conflicts`, and reports `output.conflictMode: "task"` plus `output.rebaseLeftInProgress: true`. The message becomes `"Rebase in progress: conflicts require task-level resolution"` (distinct from the resolve-mode label `"Rebase failed: conflict could not be resolved"`).
- The existing `abortRebaseIfInProgress` self-heal at the top of `rebaseAction` is unchanged. A re-run with `conflictMode: "task"` over an abandoned in-progress rebase first calls `rebase --abort`, then starts a fresh rebase — verified by a test that asserts `rebase --abort` precedes `rebase master` in the call sequence.
- The successful / squash / `retry-safe` / `squash-message-missing` paths thread `conflictMode` through `runSquashIfRequested` so `output.conflictMode` and `output.rebaseLeftInProgress` are always populated regardless of which branch returns.

### Output schema additions
- The rebase action's JSON output now always includes `conflictMode: "resolve" | "task"` and `rebaseLeftInProgress: boolean`. `rebaseLeftInProgress` is computed as `failureKind === "conflict" && conflictMode === "task"`. Both fields default-populate so existing consumers (and the `SquashOption_RunsOnlyAfterSuccessfulRebase` and similar pre-existing tests) continue to see consistent output.

### Tests
- 13 new tests in `tests/rebase.spec.ts` (28 total, all passing):
  - `ConflictModeTask_OnConflict_ReturnsFailureKindConflictAndLeavesRebaseInProgress` — task-mode + conflict → `failureKind: "conflict"`, `rebaseLeftInProgress: true`, the inline resolver does NOT run, no `rebase --abort` call, the conflicting-file list is preserved.
  - `ConflictModeTask_AcceptsConflictResolverInputButIgnoresIt` — supplying `conflictResolver` together with `conflictMode: "task"` still skips the resolver (defensive: a leftover config from the resolve path cannot accidentally engage the inline loop).

## T-006: Consolidated mohist/openspec-artifacts plan check action

### Action surface
- New `openspecArtifactsAction` added to `packages/runner/src/actions/openspec.ts` alongside `openspecSyncAction` / `archiveChangeAction`. Registered in `registry.ts` between `mohist/openspec-sync` and `mohist/archive-change` (so the four `mohist/openspec-*` ids sit next to each other).
- The action takes only `changeDir` (mirrors the existing `resolveChangeDir` helper used by `openspecSyncAction` / `archiveChangeAction`). All four required artifacts are joined under `changeDir`: `proposal.md` (file), `specs/` (directory), `design.md` (file), `tasks.json` (file).
- A new `isPresentOfKind(path, kind)` helper does `existsSync` + `stat` and checks `isFile()`/`isDirectory()` so the `specs/` entry cannot accidentally be satisfied by a file of the same name. The previous `exists` check would have accepted any path; with this, a file at `specs` is correctly flagged as missing.

### Output contract
- On success: `{ status: "success", message: "OpenSpec artifacts present under <changeDir>", output: { kind: "openspec-artifacts", changeDir, present: true, missing: [] } }`.
- On failure: `{ status: "failure", message: "OpenSpec artifacts missing under <changeDir>: <comma-joined missing paths>", output: { kind: "openspec-artifacts", changeDir, present: false, missing: [<paths in declaration order>] } }`.
- Missing `changeDir` returns `{ status: "failure", message: "OpenSpec artifacts check requires 'changeDir'" }` with no JSON `output` (matches the existing `openspecSyncAction` / `archiveChangeAction` contract).
- `missing` preserves declaration order (proposal.md, specs, design.md, tasks.json) so callers / log readers can scan the four canonical slots in order.

### Tests (10 new tests in `tests/openspec.spec.ts`, all passing)
- `mohist/openspec-artifacts > registers openspec-artifacts in the default registry` — `createDefaultRegistry().resolve("mohist/openspec-artifacts") === openspecArtifactsAction` (matches the `create-github-pr` / `mark-github-pr-ready` / `merge-github-pr` registry-existence test pattern).
- `returns success and lists zero missing artifacts when all four plan artifacts exist` — writes all four (including a nested `specs/<sub>/spec.md` to prove `specs/` is satisfied by a non-empty directory), asserts `status: success`, `output.present === true`, `output.missing === []`, `output.kind === "openspec-artifacts"`, `output.changeDir === <the resolved path>`.
- `returns failure listing only proposal.md when proposal.md is missing` + symmetric single-missing tests for `specs/`, `design.md`, `tasks.json`. Each asserts `status: failure`, the failure message contains exactly the missing path, and `output.missing` is a single-element array.
- `returns failure listing every missing artifact when changeDir is empty` — `output.missing` contains all four entries in declaration order; the failure message contains all four paths.
- `treats a file at the specs path as missing (specs must be a directory)` — `specs` is written as a regular file; action reports it as missing because `isPresentOfKind` checks `isDirectory()`.
- `fails with a clear message when only changeDir is supplied (the action's sole input)` — `with: {}` returns the `requires 'changeDir'` failure and no JSON `output`.
- `ignores other inputs beyond changeDir (only changeDir is consulted)` — supplies `with.path` / `with.extra`; the action succeeds because `changeDir` points at a directory with all four artifacts. Confirms the action does not depend on any inputs beyond `changeDir`.

### Gotchas / decisions
- The directory-kind check (`isPresentOfKind` with `isDirectory`) was added defensively because `exists` would otherwise treat a file at `specs` as satisfying the requirement. A profile that accidentally writes `specs` as a file (e.g. as part of a content-addressed cache) would otherwise silently pass the check and the runner would later fail on `mohist/openspec-sync`'s `copyDirectory` call. Better to fail loudly at the check stage.
- `missing` is returned in declaration order rather than filesystem-walk order, so a reader who scans the failure message can match it against the canonical artifact list (proposal / specs / design / tasks) without re-sorting.
- The `changeDir` error path returns no JSON `output` field (matches the existing `openspec-sync` / `archive-change` contract — those also bail out before serialising output on a missing config field). The acceptance criterion requires only the failure message to be clear, so this stays consistent.

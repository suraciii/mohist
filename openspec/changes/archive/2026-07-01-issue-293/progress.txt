## Codebase Patterns

- `IssueQuerier` is the single read surface for issue metrics. Sibling methods (`GetCompletionBucketsAsync`, `GetQualityAsync`, `GetApprovalWaitAsync`) all:
  - Resolve project via `_dbFactory.CreateDbContextAsync`, fetch project-scoped issues via `db.Issues.AsNoTracking().Where(r => r.ProjectId == projectId)`
  - Pull durable events from `db.IssueEvents` filtered by source prefix `IssueQuerier.IssueSourcePrefix + id`
  - Filter `DateTimeOffset` comparisons in memory (EF SQLite TEXT column)
  - Use the `now` parameter (injected `DateTimeOffset`, never `DateTimeOffset.UtcNow`)
  - Return result records with `IReadOnlyList<T>` points
- HTTP DTOs in `IssueRoutes.Dtos.cs` are flat records, ISO timestamps formatted as `.ToString("o")`, enum-friendly strings via `MohistDefaultWorkflowProjection.IssueStatusName(IssueStatus)`
- Route partials (`IssueRoutes.Metrics.cs`, `ApprovalMetrics.cs`, `QualityMetrics.cs`) all register a single `GET /metrics/...` endpoint via `group.MapGet(...)` calling `issuesQuery.GetXxxAsync(project.Id, DateTimeOffset.UtcNow)` and wrapping in `ApiResults.Ok(BuildResponse(result))`
- Route partials are wired up in `IssueRoutes.cs` via calls like `projectIssues.MapIssueMetrics()`, `MapIssueApprovalMetrics()`, `MapIssueQualityMetrics()`
- Project resolution filter `ProjectResolutionEndpointFilter` runs on the route group; unknown project → 404 automatically
- `Issue.CreatedAt` (`Issue.cs:58`) is `DateTime` (UTC, immutable). `Issue.CompletedAt` (`Issue.cs:72`) is `DateTime?` representing the latest terminal moment (set on Complete/Close, retained across Reopen, overwritten on re-Complete)
- `IssueEvents` rows store `Source = /mohist/issues/{issueId}` — work-started events are `com.mohist.issue.work-started` (`IssueQuerier.WorkStartedType`)
- `MohistDefaultWorkflowProjection.IssueStatusName(IssueStatus.Done)` returns `"done"` (the string used by `issue.Status` after workflow projection). `IssueStatus.Cancelled` resolves to `"cancelled"`
- Test helpers:
  - `SeedIssue(db, project, idSuffix, updatedAt?, workflowRunId?, status?)` — seeds an `IssueRow`, increments a global counter for `Number`, returns the `Issue` instance
  - `SeedEvent(db, issueId, type, time, workflowRunId?)` — appends a row to `IssueEvents` with auto-incremented id
  - Both accept fixed `DateTimeOffset` literals (no wall-clock)
- Spec markers: `[Trait(Traits.Speed.Name, Traits.Speed.Service)]` + `[Trait(Traits.Sut.Name, Traits.Sut.Issue)]` for unit-level service tests; same with `Traits.Speed.Integration` for HTTP-level tests

## Decisions for T-001

- Surface: `GET /api/projects/{projectRef}/issues/metrics/delivery-time` (no query params; window is fixed 30d and the `now` anchor lives server-side as injected clock in the request handler)
- Window: `[now - 30d, now]` keyed on `Issue.CompletedAt` (UTC comparison via UTC DateTime values)
- Lead: `(Issue.CompletedAt - Issue.CreatedAt).TotalDays` — both DateTimes are UTC. `CreatedAt` is `init`-only/immutable.
- Cycle: `Issue.CompletedAt - Min(IssueEvents.Time where Source ∈ projectSources ∧ Type == WorkStartedType)` per issue
- Cancelled-excluded: only `Status == IssueStatus.Done` (compared as enum directly via the domain; the workflow projection turns the same value into string `"done"` for the read model)
- `Issue.Status` on the domain is `IssueStatus` enum (not the projected string). In tests we can set `Status = IssueStatus.Done` directly.
- Per-issue granularity, ordered by completion time ascending (latest last)
- DTO: `DeliveryTimeMetricsResponse { Points: DeliveryTimePointDto[] }`; point carries `IssueNumber`, `CompletedAt` (ISO-8601 string), `LeadDays` (double), `CycleDays` (double?)
- internal records: `DeliveryTimeResult(IReadOnlyList<DeliveryTimePoint> Points)`, `DeliveryTimePoint(int IssueNumber, DateTimeOffset CompletedAt, double LeadDays, double? CycleDays)`
- 404 returned automatically via `ProjectResolutionEndpointFilter` — no additional code needed

## Implementation gotchas (T-001)

- `IssueQuerier.WorkStartedType` is `private const` in production; the existing unit test spec relies on `WorkCompletedType` / `ClosedType` (which are `internal const`). Promoting `WorkStartedType` to `internal const` is a non-breaking visibility widening that lets both unit and HTTP test specs reuse the canonical event-type name without hard-coding the magic string. Add an integration seam check: every test spec calls `IssueQuerier.WorkStartedType`, never `"com.mohist.issue.work-started"`.
- Test seeders `SeedIssue` / `SeedEvent` follow a strict save order: `SeedIssue(...) → SaveChanges → SeedEvent(...) → SaveChanges`. Calling `SaveChanges` BEFORE `SeedEvent` leaves the events in the change tracker only, so the next query reads an empty event table — this is exactly the bug that bit my first unit-test pass (5 tests failed with `Assert.NotNull(point.CycleDays)`). Mirror the pattern in the integration fixture (the existing `SeedEventAsync` already calls SaveChanges internally, so no manual save needed there).
- `Issue.CompletedAt` is `DateTime?` (UTC kind) on the domain aggregate; round-trips through `IssueStore.Serialize`/`Deserialize` correctly because the JSON options default to ISO-8601 with Kind preserved. Test-only helpers must rebuild the entire `DomainIssue` value and re-serialize it to override `CreatedAt` / `CompletedAt` — the JSON column is opaque to partial property mutation.
- `LeadDays` is `double` (non-nullable); `CycleDays` is `double?`. xUnit analyzer xUnit2002 flags `Assert.NotNull()` on `double` but accepts it on `double?`, so the assertion pattern is `Assert.NotNull(point.CycleDays)` followed by `point.CycleDays!.Value` — never `Assert.NotNull(point.LeadDays)`.
- The HTTP envelope's `data` payload uses `JsonSerializerDefaults.Web` (camelCase) for DTOs; `IssuedAt`/completedAt serializes via `.ToString("o")` on the server, but the JSON wire format is the same shape regardless of how the server wrote it. Asserting equality with `new DateTimeOffset(...).ToString("o")` keeps the test deterministic.

## Codebase Patterns (T-002)

- Web API hooks under `entities/issue/api/*` follow a stable shape: `useQuery({ queryKey, queryFn: () => request<T>(projectApiPath(projectId, path)), enabled: !!projectId, staleTime: 60_000 })`, exporting both the `fetchXxx(projectId)` helper and the `useXxx()` hook alongside a `xxxQueryKey(projectId)` query-key factory. Tests mock `@tanstack/react-query.useQuery` directly and assert on the captured config object.
- Existing chart primitives (`BarSeries`, `LineSeries`, `SegmentedBarSeries`) live under `pages/dashboard/charts/` and share: class-based color tokens (`fill-chart-*`, `stroke-chart-*`), `transform`/`opacity`-only motion via inline `transition`, `useReducedMotion` honoring, and `data-testid` discoverability (`bar-N`, `line-marker-N`, `segment-i-s`). All export from a single `charts/index.ts` barrel — adding a sibling primitive is additive and does not require touching existing primitives.
- `ChartLegend` distinguishes series by shape (bar/line/dot) at minimum; the kit is open to extending with a `dashedLine` shape variant for dashed-stroke percentile overlays (P85 in this issue). Legend is suppressed when there's a single entry — three entries is what triggers visible legend.
- `ChartAccessibility` requires `children` (do not render it without — render an empty fragment instead); `ChartContainer` handles loading/error/empty rendering and routes through `data-testid="chart-container-{status}"`.
- Productivity zone is a flat stack of chart/panel components; the test for the zone mocks each child individually with a stable `data-testid` (e.g. `cycle-time-chart-mock`) and asserts ordering via `compareDocumentPosition`.

## Decisions for T-002

- Hook: `useDeliveryTime` exports a `deliveryTimeQueryKey(projectId)` factory (matching `approvalWaitQueryKey`'s shape) alongside the `useQuery`-backed hook. Query key `['issues','metrics','delivery-time', projectId]` is consistent with sibling metrics hooks.
- Percentile helper: `computeRollingPercentile(samples, window, p)` returns a `(number|null)[]` parallel to the input; `null` means "no plottable percentile at this position" (window contained only `null` durations). Implementation is O(N×W log W) per the spec requirement, no rolling-window bookkeeping cache needed at the local-tool scale. `P50_NEAREST_RANK` and `P85_LINEAR_INTERPOLATION` are exported as named constants so callers compose without magic numbers; `ROLLING_WINDOW = 10` is a non-user-configurable constant.
- `ScatterSeries` is a new sibling primitive under `pages/dashboard/charts/ScatterSeries.tsx`, exported from `charts/index.ts`. Renders `<circle>` per point with `cx`/`cy` attributes (no transform positioning) and a `transition: opacity, transform` motion string for the animated state. Reduced motion yields `transition: none` and `opacity: 1`. Co-located test asserts on `cx`/`cy`, class-based fill, and motion toggling — zero regression on `BarSeries`/`LineSeries`/`SegmentedBarSeries`.
- `CycleTimeChart.tsx` consumes the per-issue series with a client-side `useState<DurationLens>('lead'|'cycle'>` toggle. The cycle lens drops points where `cycleDays === null` from both the scatter and the percentile recomputation (via a filtered `percentileSamples` derived before `computeRollingPercentile` is called). The `useState` toggle is widget-local UI state (no query-key change, no refetch), matching the design D8.
- Loading/error/empty routes through `ChartContainer`. The empty state has the concrete next-action text: `"Cycle time appears once an issue completes on this project."` — the spec scenario explicitly named this string.
- Single left y-axis (days). Days labeled at the bottom-right of the plot when there are 2+ points ("Jun 10 – Jun 30"). Y-axis label rotates by lens: `"Lead time (days)"` vs `"Cycle time (days)"`.
- Scatter x-position is driven by `xFor(p.completedAt)` → ISO completion date string parsed via `new Date(...)`. A post-completion `updatedAt` bump never touches the wire payload (the DTO has no `updatedAt` field), so no test could move a point by mutating only updatedAt — the existing T-001 server spec `GetDeliveryTimesAsync_IssueEditedAfterCompletion_AnchorsOnCompletedAt` covers the server-side guarantee; the chart tests cover the structural decoupling (point id = `issueNumber`, `cx` reflects only `completedAt`).
- Legend distinguishability: scatter = `dot` shape, P50 line = solid `line` shape, P85 line = `dashedLine` shape (new variant in `ChartLegend.tsx`). All three are visually separable for non-color-vision users.

## Implementation gotchas (T-002)

- `ChartLegend`'s `LegendShape` originally was `'bar' | 'line' | 'dot'`. To disambiguate P50 (solid) from P85 (dashed) without touching color, I added the `dashedLine` variant. This is a strictly additive extension: `ChartLegend` still recognizes the previous three shapes with identical rendering (the `dashedLine` branch is a new case in the same `switch`). The new shape renders a dashed polyline via `strokeDasharray="2 2"`. No other consumers of `LegendShape` needed updating (`CostTrendChart` and `ThroughputChart` don't use `dashedLine`).
- `ChartAccessibility` has `children` as a required prop. The fallback branch in `CycleTimeChart` (when the cycle lens has zero valid points) wraps `<></>` to satisfy the type without rendering any DOM.
- `ScatterSeries`'s `style.transition` test asserted on `style.transition === 'none'` when reduced motion is active. Initial draft used `motionStyle = {}` (no style object) which left `style.transition === ''`. Fix: always emit a `style={{ transition }}` object, selecting `'none'` vs `'opacity ..., transform ...'` based on the reduced/animated flags. This matches `BarSeries` and `SegmentedBarSeries` conventions.
- The percentile helper's `percentileOfSorted` for `p=0.5` on odd-length uses `Math.floor(mid)` which returns the middle index correctly (e.g. length=3 → mid=1.5 → floor=1 → sorted[1]). For even-length it averages sorted[lower-1] and sorted[lower] (matching the conventional median). The test verifies this against expected values `[10, 15, 20, 25, 30]` for input `[10, 20, 30, 40, 50]` (incremental prefix means rolling with window=10).
- `Compute rolling percentile on partial leading window` assertion: the first test had an off-by-one issue (I asserted `result[2] === 30` expecting the rolling P50 of `[1..3]` = 20). The corrected expectation is `result[2] === 20` since the rolling window at position 2 contains indices `[0,1,2]` = `[10,20,30]`, median = 20.
- Spec call-out that the empty-state "names a concrete next action" — accepted text: `"Cycle time appears once an issue completes on this project."` matches the wording pattern used by `ThroughputChart` (`"Throughput appears once an issue completes on this project."`) and is test-asserted.
- `bg-chart-2 text-background` lens-toggle active style is "best effort" with the existing grayscale palette; the acceptance criteria test reads structural correctness (aria-pressed state, scatter filtering, percentile recompute), not visual style. Per design D4/Palette chroma is deferred to a future issue.

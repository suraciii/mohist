# Issue 129 — generic AgentSession launch

Working memory for the issue-level workflow. Append findings as you go;
later steps read the latest entries (and the `## Codebase Patterns`
section first).

## Codebase Patterns

- `WorkDispatch` is the server-side dispatch record; `WorkDispatchResponse`
  is its wire DTO mirrored to the runner. New optional fields are added
  at the end of the constructor with `null` defaults so workflow
  translators continue to compile and produce byte-identical workflow
  dispatches.
- `AgentJobGrain` is the authoritative owner of a standalone agent job.
  It is in-memory only (no `[PersistentState]`) and non-reentrant, so
  timer-driven dispatch retries cannot race `ReportResultAsync`. Any new
  state must respect non-reentrancy and timer disposal in
  `OnDeactivateAsync`.
- `JSON.SerializeToElement` and `JSON.Serialize` are the canonical
  serialization helpers; the runner-facing `with`/`variables` strings
  are produced through them.
- Tests for `AgentJobGrain` live under
  `packages/server/tests/Mohist.Server.Tests/Specs/Agent/Grain/`. The
  fixture (`AgentJobGrainFixture`) shares an in-memory Orleans cluster
  with `[Collection("WorkflowGrain")]`; specs that register a runner
  must clear the global runner registry to avoid stale cross-spec
  interference.
- `RunnerRoutes.PollAsync` projects a `WorkDispatch` into a
  `WorkDispatchResponse`. For workflow dispatches the project id lives
  on `Issue.ProjectId`; for agent-job dispatches (no `Issue`) it must
  fall through to the new top-level `ProjectId` field. The `Issue ??`
  fallback in the route is the consolidation point.
- The runner reads the `WorkDispatchResponse` JSON wire shape via
  `JSON.parse`; adding optional fields is wire-compatible. The runner
  side `WorkDispatchResponse` and `RenderedWorkItem` types are kept in
  lockstep.

## T-001 — Server: AgentJob consumes Agent definition + widen dispatch envelope

### Findings

- `AgentJobInput` previously only carried `Prompt`, `Model`,
  `WorkspacePath`, `ProjectId`, `Uses`. Added three optional Agent
  snapshot fields:
  - `AgentId: string?` — resolved Agent identity (traceability).
  - `AgentInstructions: string?` — resolved Agent `Instructions`.
  - `AgentConfig: JsonElement?` — resolved Agent `AgentConfig`
    snapshot.
  - Plus `AgentSessionId: string?` for the launch-side minting flow
    (used to populate the dispatch envelope; T-003 mints it before
    dispatch).
  Orleans serializes `JsonElement?` via the existing
  `JsonElementSurrogate`; no extra registration needed.

- `WorkDispatch` (in `IRunnerGrain.cs`) gained two additive optional
  fields: `ProjectId` and `AgentSessionId`. They are null for
  workflow dispatches (workflow projects still surface via
  `Issue.ProjectId`) and set by `AgentJobGrain.BuildDispatch` for
  agent-job dispatches. Old-field consumers ignore the new fields.

- `AgentJobGrain.BuildDispatch` now reads `input.ProjectId` and
  `input.AgentSessionId` onto the dispatch envelope. Workflow dispatch
  (`WorkflowItemTranslator.BuildTaskDispatchAsync` /
  `BuildChecksDispatchAsync`) keeps using named-argument constructor
  calls — the new fields default to `null`, so the workflow path is
  byte-identical.

- `AgentJobGrain.ComposePromptWithEntry` (extracted as
  `internal static`) is the single composition point for
  `with.prompt`. When `AgentId` or any Agent field is set,
  `with.prompt` becomes a structured object rooted at `agent-launch`
  carrying `instructions` / `config` / `prompt` so the runner's
  `resolvePrompt` path renders it via the existing structured-prompt
  machinery. When no Agent fields are set, `with.prompt` is the bare
  string — the raw-prompt-only AgentJob path is unchanged.

- `RunnerRoutes` projects the new fields into `WorkDispatchResponse`.
  `ProjectId` falls through `Issue.ProjectId ?? work.ProjectId` so
  workflow and agent-job both yield an authoritative project id in the
  response (workflow still reads from `Issue`, agent-job from the new
  field). `AgentSessionId` is passed through verbatim (null for
  workflow and raw-prompt-only validation dispatches).

- Runner-side `WorkDispatchResponse` and `RenderedWorkItem` gained an
  optional `agentSessionId?: string | null` field. The runner's
  `toWorkItem` parses it from the dispatch response. Workflow
  dispatched items leave it `undefined`.

- Tests cover:
  - `ComposePromptWithEntry` unit tests: raw-prompt-only, instructions
    only, instructions + config, AgentId-only (structured prompt shape
    always has `agent-launch.prompt`).
  - Integration tests (grain + polled dispatch):
    agent-sourced composition populates `with.prompt` as a structured
    object rooted at `agent-launch` and populates `ProjectId` /
    `AgentSessionId` on the dispatch.
  - Raw-prompt-only path keeps `with.prompt` as a bare string and
    leaves `AgentSessionId` null.
  - Dispatch envelope population: `ProjectId` always set when the input
    carries one; `AgentSessionId` set when supplied, null otherwise.
  - Workflow dispatch path is unchanged (existing tests still pass;
    `WorkflowItemTranslator` constructors leave the new fields null
    via the default).

### Gotchas

- The new fields are at `[property: Id(15)]` and `[property: Id(16)]`
  on `WorkDispatch`. The existing `Id(10)` slot was already
  retired (gap in the sequence). Adding past the retired slot is
  safe; Orleans `GenerateSerializer` honors the explicit `Id(N)`
  assignments.
- `WorkDispatchResponse` previously had `CleanupPolicyDto?` and
  `Recovery` after `AgentJobId`. Adding `AgentSessionId` between
  them is wire-compatible: the runner uses field-name JSON parsing,
  and the `JsonPropertyName` defaults match the C# property names
  (camelCase).
- `AgentJobGrain.BuildDispatch` is private. To unit-test the
  composition logic without spinning up the full grain, the
  composition helper was extracted as `internal static` (test
  assembly has `InternalsVisibleTo`).
- The agent-sourced `with.prompt` is a structured object with root
  key `agent-launch`. The runner's `resolvePrompt` recognizes single-
  root-key structured objects and renders them via the existing
  `renderStructuredPrompt` path; this keeps the runner side unchanged
  for T-001 (T-002 will generalize the session target).
- `ProjectId` in `WorkDispatchResponse` falls through `Issue.ProjectId
  ?? work.ProjectId`. Workflow dispatches leave `work.ProjectId` null
  but supply `work.Issue.ProjectId`, so they remain unchanged.
  Agent-job dispatches have no `Issue`, so they fall through to
  `work.ProjectId`. Both shapes yield an authoritative project id.

## T-002 — Runner: generalized session target abstraction

### Findings

- New exported type `SessionTarget` (in
  `packages/runner/src/runtime/acp-connection.ts`) is the
  discriminated union used everywhere a session identity is carried
  in the runner:
  `{ kind: "workflow"; projectId; workflowRunId; sessionName }` or
  `{ kind: "generic"; projectId; sessionId }`. Adopting the target
  shape unifies runner caches, key derivation, and server method
  dispatch.

- `AcpSessionManager.key()` now takes a `SessionTarget` and returns a
  prefixed key: `workflow:{workflowRunId}:{sessionName}` for
  workflow-shaped sessions, `generic:{sessionId}` for generic-shaped
  sessions. Two explicit helpers (`workflowKey`/`genericKey`) exist
  for callers that already know the shape (e.g. existing
  `host.resolveFollowupTarget`, the test fixtures, the generic
  strategy). The different prefixes close the
  `":<sessionName>"` collision that an agent-job would otherwise
  hit when `workflowRunId` is empty and the session name happened to
  match a workflow's `":"`-delimited key.

- `sessionTargetFromContext` (`session-events.ts`) returns a
  `SessionTarget | null`:
  - `ownerKind === "agent-job"` + `agentSessionId` present +
    `projectId` set → generic shape (uses the
    agent-job-minted session id directly as the identity, ignores
    the workflow-shaped `with.session`).
  - Otherwise → workflow shape (existing semantics: derives
    `sessionName` from `with.session` or `workId`).
  - `projectId` gate is retained; without it both branches return
    `null`. An agent-job without a minted `agentSessionId` falls
    through to the workflow shape (this is the raw-prompt-only
    AgentJob path that never had a session to attach to).

- `emitSessionEvent` and `attachSessionToServer` now branch on
  `target.kind`:
  - Workflow branch → `workflowAgentSessionRuntimeEvents` /
    `attachWorkflowAgentSession` (unchanged URLs and signatures).
  - Generic branch → new
    `agentSessionRuntimeEvents` / `attachAgentSession` (new
    `agent-sessions/{projectId}/{sessionId}/...` URLs).
  Both branches share the same `body` shape so the existing
  server-side session event pipeline receives identical payloads.

- `ServerConnection` (`packages/runner/src/server/connection.ts`)
  gained four new methods that hit distinct URL paths:
  - `getAgentSession(projectId, sessionId)` →
    `GET /api/runner/{runnerId}/agent-sessions/{projectId}/{sessionId}`
  - `openAgentSession(projectId, sessionId, body)` →
    `POST .../open`
  - `attachAgentSession(projectId, sessionId, body)` →
    `POST .../attach`
  - `agentSessionRuntimeEvents(projectId, sessionId, body)` →
    `POST .../runtime-events`
  The existing `*WorkflowAgentSession` methods and URLs are
  untouched and remain byte-identical; an alias `AgentSession =
  WorkflowAgentSession` is exported so generic callers do not need
  a new type.

- `runAcpWorkflowAgentSession`
  (`session-strategies.ts`) now branches on owner-kind at the top:
  when `ownerKind === "agent-job"` and `agentSessionId` is present,
  it delegates to a sibling
  `runAcpGenericAgentSession` that uses the new
  `getAgentSession` / `openAgentSession` connection methods, keys
  the `AcpSessionManager` cache by the generic prefix, and runs the
  same cached/resumed/new-session logic (sharing
  `runPromptOnExistingWorkflowAgentSession`,
  `runResumedWorkflowAgentSession`,
  `runNewWorkflowAgentSession`, and
  `runEphemeralWorkflowAgentSession`). The
  existing `runAcpWorkflowAgentSession` body — including all the
  call sites in `acp-agent.ts` — is unchanged for workflow-shaped
  work items, so call sequence and wire shape are byte-identical.
  The generic path falls back to the ephemeral path only when
  `manager` / `serverConnection` / `projectId` / `agentSessionId`
  are missing (same fail-mode contract as the workflow path).

- `ActionContext` (`packages/runner/src/core/types.ts`) gained
  `ownerKind?: string | null` and `agentSessionId?: string | null`
  fields, propagated from `RenderedWorkItem` by
  `baseContext` in `packages/runner/src/runtime/executor.ts`. These
  are set by the server for agent-job dispatches (T-001) and the
  raw-prompt-only AgentJob validation path leaves them null.

- Tests added:
  - `tests/acp-connection.spec.ts` — `AcpSessionManager keys` block
    (prefixed keys, helpers, workflow-vs-generic coexistence
    without collision).
  - `tests/acp/session-target.spec.ts` — new spec; covers generic
    vs workflow target derivation across
    owner-kind / agentSessionId / projectId / session-name
    combinations, including the "agent-job without
    sessionId falls through to workflow shape" edge case
    (raw-prompt-only AgentJob).
  - `tests/server-connection-generic-session.spec.ts` — new spec;
    covers each new `*AgentSession` connection method's URL path
    and body, distinctness from the workflow URL space, and the
    404 / 500 contracts.
  - `tests/acp/session-strategies-generic.spec.ts` — new spec;
    covers generic dispatch routing
    (agent-job → `getAgentSession` / `openAgentSession` /
    `attachAgentSession` / `agentSessionRuntimeEvents` only,
    no workflow call),
    workflow dispatch routing (unchanged),
    cached-entry under the `generic:` key,
    and runtime-event delivery to the generic URL.

- Existing test fixtures updated for the new `key()` signature:
  `tests/acp-agent.spec.ts` and `tests/acp/support.ts` now use
  `acpSessionManager.workflowKey(...)` when populating the cached
  session entry. `host.resolveFollowupTarget` (which still knows
  the caller is a workflow followup) was updated to call
  `workflowKey`.

### Gotchas

- The URL substring check `/sessions/project-1/...` collides with
  `/agent-sessions/project-1/...` (the generic URL contains the
  workflow URL as a substring). New tests assert the full runner-
  prefixed URL via regex, not `toContain`, to avoid the
  false-positive on the workflow path.

- The `mock.calls[N]` index is shared across `fetchMock` invocations
  in a test — when capturing the URL of the second call, use
  `mock.calls[1]`, not `mock.calls[0]`. Easy to misread when the
  variable name doesn't reflect the call order.

- The existing `*WorkflowAgentSession` server methods are NOT
  changed; the agent-job wire path now goes to the new
  `*AgentSession` endpoints, and an older server that has not yet
  shipped the generic endpoints will return 404 for an agent-job
  dispatch. This is a coordinated T-002/T-003 change on the server
  side; T-003 mints the `AgentSession` and adds the endpoints.

- `acp-agent.ts` continues to call
  `runAcpWorkflowAgentSession`; the function itself
  internally dispatches to the generic strategy. The agent-job
  call sequence in `acp-agent.ts` is unchanged.

- `acpSessionManager.set(workflowKey(...))` in the existing
  shared-session fixture used to be
  `acpSessionManager.set(key("workflow-1", "shared-session"))`,
  which previously produced `workflow-1:shared-session`. After
  T-002 the same fixture produces
  `workflow:workflow-1:shared-session`. The
  `AcpSessionManager` cache lookup in
  `runAcpWorkflowAgentSession` was updated to use
  `manager.workflowKey(...)` so both sides agree on the new
  prefix. The cache-hits-test in the
  `session-strategies-reuse.spec.ts` continues to work because
  the lookup and the pre-seeded entry both use the prefixed form.

## T-003 — Server: launch generic AgentSession from an Agent profile

### Findings

- `AgentSessionLaunchRoutes.cs` (`packages/server/src/Mohist.Server/Api/`)
  is the product launch endpoint. Route group:
  `POST /api/projects/{projectRef}/agents/{agentRef}/sessions` with
  `ProjectResolutionEndpointFilter` applied so the resolved project is
  available via `HttpContext.GetResolvedProject()`. Distinct from the
  validation-only `AgentJobController.ValidatePath` (`/api/agent-jobs/validate`).
- Flow:
  1. Reject empty/whitespace prompt with 400 (`prompt_required`) **before**
     resolving the Agent — this ordering means an empty-prompt 400 carries
     no side effects (no grain activation, no session creation).
  2. Resolve Agent via `AgentQuerier`: by id (when ref starts with
     `agent_`), else by name, else by id as a final fallback so callers
     can pass either id or friendly name on the URL.
  3. On unknown agent, return 404 **before** minting a session.
  4. Mint `sessionId = sessions.NewSessionId()` (Guid.NewGuid().ToString("N")).
  5. Open the session via `IAgentSessionGrain.OpenAsync` with empty
     `RunnerId` (runner will stamp it on its first open call) and
     metadata built by `GenericAgentSessionMetadata.Metadata(...)`.
  6. Submit the `AgentJobGrain` with the Agent snapshot fields
     (`AgentId`, `AgentInstructions`, `AgentConfig`) plus the minted
     `AgentSessionId`. `T-001`'s `ComposePromptWithEntry` then renders
     `with.prompt` as a structured `agent-launch` object so the runner
     sees the composed bytes.
  7. Return 201 with `{ sessionId, agentId, agentName, status }` where
     `status = "inactive"` (matches `AgentSessionJsonHelper.StatusName`'s
     behaviour for a freshly-minted session with no `AgentSessionId` yet).
- `GenericAgentSessionMetadata` (`packages/server/src/Mohist.Server/Workflow/Services/Sessions/`)
  centralises the labels:
  - `source-kind = "agent-launch"` (read by `AgentSessionQuery` via
    `LabelSourceKind`).
  - `agent-id`, `agent-name`.
  - Optional context refs as labels with `mohist.io/agent-launch/{kind}`
    prefix — explicitly NOT projected into the workflow-shaped lookup
    keys (`workflow-run-id`, `session-name`), so the session is reachable
    by `(projectId, sessionId)` alone (no `workflowRunId` lookup key
    needed).
- `AgentJobGrain.CloseGenericSessionOnTimeoutAsync` was added (T-003
  alongside T-001's dispatch envelope widening): on report timeout the
  grain appends a synthesised `session.closed` runtime event with
  `failureCategory = "report-timeout"` so the session reaches a terminal
  state via the existing `AgentSessionGrain.AppendRuntimeEventsAsync`
  pipeline. `ContextExhaustionClassifier` classifies the synthesised
  event as `probe_timeout` / `context_exhaustion_suspected` (no usage
  recorded), which matches the runner's liveness-quiet classification.
  No-op for raw-prompt-only AgentJobs (`_input.AgentSessionId` is null).
- `AgentSessionGrain.OpenAsync` was taught to stamp the `RunnerId` from
  the runner's open call exactly once when the launch minted the session
  with an empty `RunnerId`. Already-bound `RunnerId` is left untouched so
  workflow sessions remain sticky across reopens (the existing semantics
  the runner-side retry flow relies on).
- Tests in
  `packages/server/tests/Mohist.Server.Tests/Specs/Agent/Api/AgentSessionLaunchRoutesSpecs.cs`:
  - `Launch_ResolvesAgent_ComposesSnapshot_MintsSession_Returns201_WithIdentityAndStatus`
    — happy path: 201 shape, agent id/name, status field, session
    queryable by `(projectId, source-kind=agent-launch)` labels,
    runner receives a dispatch (AgentJob snapshot shows runnerId + workId).
  - `Launch_RecordsContextRefs_OnSessionMetadata_AsPromptContextOnly`
    — context refs (`issueNumber`, `epicNumber`, `repository`,
    `workspacePath`) land as `mohist.io/agent-launch/{kind}` labels and
    do NOT project into workflow-shaped keys (`workflowRunId`,
    `sessionName`).
  - `Launch_EmptyOrWhitespacePrompt_Returns400_WithoutCreatingSessionOrJob`
    (Theory: empty / whitespace / tabs+newlines) — 400 with `prompt`
    in error; pre/post `CountAgentLaunchSessionsAsync` is unchanged.
  - `Launch_MissingPromptField_Returns400_WithoutCreatingSessionOrJob`
    — same as above for a body that omits `prompt` entirely.
  - `Launch_UnknownAgent_Returns404_WithoutCreatingSessionOrJob` —
    random `agent_{guid}` id returns 404; session count unchanged.
  - `Launch_ResolvesAgentByName_WhenAgentRefIsFriendlyName` — name-based
    resolution path.
  - `Launch_IsDistinctFromValidationOnlyAgentJobsRoute` — both routes
    respond and the launch URL is distinct from `ValidatePath`.
  - `Launch_AgentJobTimeout_TransitionsGenericSessionToTerminalFailedState`
    — fixture configures `JobTimeout=8s`; the test waits up to 30s for
    the AgentJob to reach `Failed` with `FailureReason = "report-timeout"`
    and verifies the session still carries the launch labels.

### Gotchas

- **Architecture rule added**: the `Agent → Sessions` domain dependency
  (AgentJobGrain calls `IAgentSessionGrain.AppendRuntimeEventsAsync` on
  timeout) is intentional and was added to
  `AllowedDomainDependencies` in
  `packages/server/tests/Mohist.Server.Tests/Architecture/ArchitectureRules.cs`.
  The existing rule (`("Agent", "Runner")`) covered T-001; T-003
  introduces the sessions call.
- **The launch response status field is hardcoded to `"inactive"`** —
  matches the `AgentSessionJsonHelper.StatusName` heuristic for a
  freshly-minted session (no `AgentSessionId`, `LastDataAt == null`).
  The session transitions to `"active"` once the runner reports its
  first runtime event. The contract is "initial state at launch",
  not "live state".
- **RunnerId binding race**: when the launch opens the session first
  with an empty RunnerId, the runner's subsequent `open` call sets the
  RunnerId. `AgentSessionGrain.OpenAsync` is non-reentrant under
  Orleans, so the two opens serialise; the second open stamps the
  RunnerId exactly once because the branch checks for empty
  `Runtime.RunnerId` before overwriting.
- **Distinct from `AgentJobController.ValidatePath`** is asserted in the
  spec by hitting both routes in a single test and comparing URL
  shapes; the launch route also has the side effect of minting a
  session and dispatching, whereas the validation route round-trips a
  raw prompt through the engine and returns the terminal result.
- **`ProjectResolutionEndpointFilter`** is applied to the launch route
  group (same as the other `/api/projects/{projectRef}/...` routes) so
  unknown project refs return the standard 404 from the filter instead
  of a downstream lookup miss.
- **The launch route calls `sessions.NewSessionId()` rather than going
  through `Sessions.NewSessionId()` on the AgentSessionGrain** because
  the id is needed up front to populate the AgentJob's
  `AgentSessionId` snapshot before submission; the runner's dispatch
  envelope then carries this id verbatim (T-001 / D2 / D4).

## T-004 — Generic AgentSession followup

### Findings

- `AgentSessionFollowupRoutes.cs`
  (`packages/server/src/Mohist.Server/Api/`) hosts the product-level
  generic followup endpoint:
  `POST /api/projects/{projectRef}/agent-sessions/{sessionId}/followup`.
  Applied `ProjectResolutionEndpointFilter` so unknown project refs
  return the standard 404 from the filter instead of a downstream miss.
  Distinct from the existing
  `POST /api/projects/{projectRef}/issues/{number}/sessions/{name}/followup`
  route — different URL, different request body type
  (`GenericFollowupRequest(string? Text)`), different resolver. The
  issue-scoped route is untouched and remains byte-identical.

- Endpoint contract:
  1. Reject empty/whitespace/missing `text` with 400
     (`followup_text_missing`) **before** any session or runner lookup
     (no SignalR push, no DB cost).
  2. `ResolveGenericFollowupTargetAsync(projectId, sessionId)` — null
     result → 404 (unknown session). Project-mismatch (session belongs
     to a different project) → null → 404 (does not leak across
     projects).
  3. `target.IsActive == false` → 409 (`session_inactive`) for both the
     "runner never opened" case (RunnerId empty, IsActive=false) and
     the "session is terminal" case (transcript carries a
     `session.closed` event with status completed/failed/stopped).
  4. RunnerId empty **and** IsActive would-be-true → 503
     (`runner_offline`). Defensive: by construction a session can only
     read IsActive=true when RunnerId is non-empty
     (`!string.IsNullOrWhiteSpace(runnerId) && !IsTerminal &&
     StatusName == "active"`), so this branch is unreachable in practice
     but kept so the handler never crashes if the invariant is violated.
  5. `RunnerConnectionTracker.GetConnectionId(runnerId)` empty →
     503 (`runner_offline`) — runner bound but its SignalR socket is
     gone.
  6. Otherwise push `ReceiveFollowup` with `{ target: { kind: "generic",
     projectId, sessionId }, text }` to the runner's connectionId.

- `ResolveGenericFollowupTargetAsync` (in `AgentSessionQuerier.cs`)
  loads the `AgentSessionGrain` row by id via
  `_sessionQuery.ListByIdsAsync([sessionId])` (T-002's generic lookup
  path), filters by `ProjectId` label (cross-project → null → 404),
  and computes IsActive as the conjunction of:
  - `RunnerId` non-empty (the runner has opened the session).
  - `!IsTerminalSessionAsync(...)` (transcript carries no
    `session.closed` event with status completed/failed/stopped).
  - `AgentSessionJsonHelper.StatusName(...) == "active"` (matches the
    runtime-event-window heuristic used by the issue-scoped resolver).

- `IsTerminalSessionAsync` (private helper in `AgentSessionQuerier.cs`)
  reads the transcript turns + parts, finds the most-recent
  `session_closed` / `session.closed` event, and checks its payload
  `status` field for completed/failed/stopped. The transcript is the
  source of truth for terminal state — `LastDataAt` is updated by every
  runtime event (including the close event itself), which would make
  `StatusName` read "active" right after the close. The helper reads
  the DB directly (no grain call) so the resolver stays a thin
  read-path and the grain's transcript-persist timer is bypassed (the
  test fixture deactivates the grain + waits for the persistor to flush
  the transcript before the resolver runs).

- `RunnerHub` payload (`IssueRoutes.Sessions.cs` followup handler) was
  generalized: the issue-scoped route now emits BOTH the legacy
  top-level `workflowRunId` / `sessionName` fields AND the unified
  `target: { kind: "workflow", projectId, workflowRunId, sessionName }`
  shape. Older runners branch on the legacy top-level fields; the
  T-004 build of the runner prefers `target` when present and falls
  back to the top-level fields otherwise. The wire is forward +
  backward compatible. The generic followup route emits
  `{ target: { kind: "generic", projectId, sessionId }, text }` (no
  top-level `workflowRunId` / `sessionName`).

- Runner-side payload type `ReceiveFollowupPayload` gained an optional
  `target?: ReceiveFollowupSessionTarget` field; `workflowRunId` /
  `sessionName` are now optional (legacy fallback). New
  `ReceiveFollowupSessionTarget` is the discriminated union
  `{ kind: "workflow" | "generic"; projectId; workflowRunId?;
  sessionName?; sessionId? }`.

- `resolveSessionTarget(payload)` (exported from `runner-signalr.ts`)
  derives a `SessionTarget` from the payload:
  - Prefers `target` when present.
  - For `kind: "workflow"`: requires `workflowRunId` + `sessionName` +
    `projectId` (otherwise null — caller drops the message).
  - For `kind: "generic"`: requires `sessionId` + `projectId` (otherwise
    null).
  - Falls back to top-level `workflowRunId` + `sessionName` (with empty
    `projectId`) for older server builds that don't populate `target`.
  - Returns `null` for unknown `kind` or when neither path resolves —
    the handler drops the message silently.

- `FollowupTargetResolver` signature was changed from
  `(workflowRunId, sessionName) => ...` to `(target: SessionTarget) =>
  ...`. The runner's `RunnerHost.resolveFollowupTarget` branches on
  `target.kind`: workflow → `sessionManager.workflowKey(wrid, name)`,
  generic → `sessionManager.genericKey(sessionId)`. Both branches
  silently return null when the lookup misses (existing
  unknown-session contract — the handler drops the message without
  throwing).

- `RunnerSignalRClient.handleFollowup` (in `runner-signalr.ts`)
  branches on `sessionTarget.kind`:
  - workflow → `workflowAgentSessionRuntimeEvents` (unchanged URL +
    signature, byte-identical to pre-T-004).
  - generic → `agentSessionRuntimeEvents` (new T-002 method,
    `agent-sessions/{projectId}/{sessionId}/runtime-events` URL).
  Both branches share the same `session.input` event payload shape
  (`{ kind: "followup", text, role: "user", acpSessionId, source:
  "followup", sentAt }`).
  `target.connection.prompt({ sessionId, prompt: [{ type: "text", text
  }] })` is fired fire-and-forget (not awaited) after the runtime
  event emit; the handler returns immediately so the SignalR receiver
  is not blocked on turn completion.

- Tests added:
  - `tests/Sessions/GenericAgentSessionFollowupApiSpecs.cs` (server,
    integration): covers all five status codes (200 active sent, 400
    empty/whitespace/missing text, 404 unknown session, 404 cross-
    project, 409 inactive before runner opens, 409 after terminal
    session.closed, 503 active but runner offline), the
    `ResolveGenericFollowupTargetAsync` happy / no-runner / unknown
    paths, the activity → closed lifecycle (200 → 409), and the
    issue-scoped route preservation

### Gotchas

- **Cross-spec runner registry pollution**: the T-004
  `GenericAgentSessionFollowupApiSpecs` helper methods

  transport never sees the dropped message; the runner logs nothing

## T-005 — Generic AgentSession cancel

### Findings

- `AgentSessionCancelRoutes.cs` (`packages/server/src/Mohist.Server/Api/`)
  hosts the product-level generic cancel endpoint:
  `POST /api/projects/{projectRef}/agent-sessions/{sessionId}/cancel`.
  Distinct from the existing
  `POST /api/projects/{projectRef}/issues/{number}/sessions/{name}/...`
  routes (different URL, different resolver). Applied
  `ProjectResolutionEndpointFilter` so unknown project refs return the
  standard 404 from the filter instead of a downstream miss.
- Endpoint contract:
  1. `ResolveGenericCancelTargetAsync(projectId, sessionId)` — null
     result → 404 (`not_found`). Cross-project sessions leak as null
     → 404 (same cross-project guard as the followup resolver).
  2. Terminal short-circuit: `target.TerminalState` non-empty
     (transcript carries a `session.closed` event with status
     completed/failed/stopped) → 200 `{ state: <terminal-state> }`.
     The server never invokes the runner when the session is already
     terminal — there is no turn to cancel and the runner cannot change
     the recorded outcome.
  3. No runner ever bound (`RunnerId` empty) → 200
     `{ state: "not-cancellable" }`. Defensive: by construction a
     session without a bound runner cannot have any ACP connection to
     cancel.
  4. Runner bound but `RunnerConnectionTracker` has no live SignalR
     connection for it → 200 `{ state: "not-cancellable" }`. The runner
     is offline; the API surfaces that honestly.
  5. Otherwise invoke `CancelAgentSession` on the runner's connectionId
     via SignalR (server→runner invocation with reply path). The reply
     is mirrored verbatim into the HTTP response — the API never
     invents a state.
  6. Empty / null reply from the runner → 502 `runner_no_response` so a
     missing reply is loud (not a silent success).
- `ResolveGenericCancelTargetAsync` (in `AgentSessionQuerier.cs`) is
  distinct from `ResolveGenericFollowupTargetAsync` (T-004). Cancel is
  best-effort over ACP, so the endpoint needs both the runner id AND
  the terminal-state verdict up front. The terminal-state verdict lets
  the server short-circuit without invoking the runner for
  completed/failed/stopped sessions. `TerminalState` is null when the
  session is not yet terminal — the endpoint must call the runner.
- `ReadTerminalStateAsync` (private helper in
  `AgentSessionQuerier.cs`) reads the most-recent
  `session.closed` / `session_closed` transcript event and returns its
  `status` field verbatim. Only `completed` / `failed` / `stopped` are
  recognised as terminal; any other status returns null so the endpoint
  falls through to the runner (the agent might still be running or the
  event payload might be malformed).
- `AgentSessionCancelReply` (`record(string? State)`) is the typed
  SignalR reply. The route never inspects the value beyond "is it
  non-empty" — the runner's word is final, so the API mirrors whatever
  string it gets back (`cancelled`, `not-cancellable`, or a
  terminal-state name). This is design D6's "the API can never fake
  success" guarantee.
- New server→runner SignalR method `CancelAgentSession` is added
  distinctly from `ReceiveFollowup`:
  - `ReceiveFollowup` is registered with `connection.on(...)` and
    returns void (fire-and-forget — the runner handler's resolved value
    is ignored).
  - `CancelAgentSession` is registered with `connection.on(...)` and
    the SignalR transport serialises the resolved value back to the
    server as the invocation's reply.
  - The wire payload is the same `target: SessionTarget` shape
    introduced in T-004; only generic targets are reachable through
    this method today because the issue-scoped session lifecycle has no
    cancel surface.
- Runner-side handler `handleCancel` in
  `packages/runner/src/server/runner-signalr.ts`:
  - Validates `payload.target` is `kind: "generic"` with a `sessionId`
    and `projectId` (matching the product endpoint contract).
  - Resolves the live ACP session via the same
    `FollowupTargetResolver` used for followups, keying the
    `AcpSessionManager` by `generic:{sessionId}` (T-002 prefix).
  - Calls `connection.cancel?.({ sessionId })` if the connection
    advertises cancellation. The `?.` guard handles a hypothetical
    older connection that did not advertise cancel (the current ACP
    SDK always defines it on `ClientSideConnection`).
  - Reports `{ state: "cancelled" }` on successful send,
    `{ state: "not-cancellable" }` for any of: no resolver, no live
    ACP session, missing `cancel` method, transport-level cancel
    failure. Never invents a terminal-state — the server is the
    source of truth.
- `RecordingRunnerHubContext` test double (in
  `packages/server/tests/Mohist.Server.Tests/Support/MohistIntegrationFixture.cs`)
  gained:
  - `Invocations` list and `RecordedRunnerHubInvocation` record so
    specs can assert against server-side invocations.
  - `SetInvocationResponse(method, response)` so specs can pre-program
    the runner's reply for typed `InvokeAsync<T>` calls.
  - Explicit `IClientProxy IHubClients<IClientProxy>.Client(...)` and
    `ISingleClientProxy IHubClients.Client(...)` implementations.
    Both are needed because `IHubClients` (non-generic) declares
    `Client(string) -> ISingleClientProxy` and the default
    `NonInvokingSingleClientProxy` throws on `InvokeCoreAsync`. The
    existing `SendCoreAsync` path is unchanged.
  - `RecordingClientProxy` now implements `ISingleClientProxy` so the
    `InvokeCoreAsync<T>` path is reachable through the recording
    hub. The typed reply is sourced from
    `SetInvocationResponse(method, ...)` and falls back to `default(T)`
    when no response is registered.
- Tests added:
  - `tests/Sessions/GenericAgentSessionCancelApiSpecs.cs` (server,
    integration): covers all five status code branches — 200 with
    runner-reported `cancelled`, 200 with runner-reported
    `not-cancellable`, 200 with runner-reported terminal-state
    (`failed`), 200 with server-short-circuit on each of completed /
    failed / stopped, 404 unknown session, 404 cross-project, 200
    not-cancellable when runner offline. Plus three resolver unit
    tests: unknown session → null, active session → null
    TerminalState, terminal session → non-null TerminalState.
  - `tests/runner-signalr.spec.ts` (runner): the
    `describe("...CancelAgentSession handler (T-005)")` block covers
    cancellable session (cancel invoked with the right sessionId),
    unknown session (resolver returns null → not-cancellable, no
    cancel call), no resolver registered (not-cancellable, no call),
    connection without `cancel` method (not-cancellable), cancel
    transport rejects (not-cancellable + logged), resolver throws
    (not-cancellable + logged), null / missing / no-target payload
    (not-cancellable), workflow-shaped target (not-cancellable, no
    call), generic target without sessionId (not-cancellable, no
    call).

### Gotchas

- **The runner reply is opaque to the server.** The server mirrors the
  runner's reported state verbatim into the HTTP response — it does
  not whitelist `cancelled` / `not-cancellable` / terminal-state names
  or coerce unknown strings. This is by design (D6): if a future
  agent advertises a richer state vocabulary the API surfaces it
  without server-side changes. The 502 `runner_no_response` guard is
  the only server-side rewrite — it only fires when the SignalR
  transport returns no value at all.
- **`ConnectionId` empty vs `RunnerId` empty are different states.**
  `RunnerId` empty means no runner has ever opened the session (the
  launch minted it with empty `RunnerId`, design D2); the server
  reports `not-cancellable` without consulting the SignalR tracker.
  `ConnectionId` empty means the runner bound itself then dropped the
  SignalR connection; the same `not-cancellable` reply but the lookup
  path is different. Both branches test the same outcome but assert
  distinct intermediate states.
- **The runner's `connection.cancel?.()` is a notification, not a
  request.** It resolves once the message is on the wire, not when the
  agent honours it. The agent decides what to do; the runner is honest
  about the attempt. Returning `{ state: "cancelled" }` after a
  successful `await cancel(...)` is the contract — the HTTP caller may
  need to poll the session's status to observe the agent's actual
  response.
- **`MockConnection` gained a `cancel?` field** in the runner-signalr
  spec's `buildClient` helper so existing tests still compile (no
  cancel method by default) and the new cancel specs can opt in by
  passing `{ prompt: vi.fn(), cancel: vi.fn() }`. Existing workflow
  followup tests are unaffected because they don't invoke the cancel
  handler.
- **`ISingleClientProxy` implementation is required, not optional.**
  ASP.NET Core's `IHubClients.Client(string)` on the non-generic
  interface returns `ISingleClientProxy` whose default
  `NonInvokingSingleClientProxy` throws `NotImplementedException` on
  `InvokeCoreAsync<T>`. The recording hub's explicit implementation
  implements both `IClientProxy IHubClients<IClientProxy>.Client(...)`
  and `ISingleClientProxy IHubClients.Client(...)` so the typed
  invocation path is reachable through the test double. This was the
  only server-side test-infrastructure change needed for T-005.
- **The cross-spec runner registry pollution pattern (T-004) is
  reused**: each test in `GenericAgentSessionCancelApiSpecs` registers
  its own runner via the per-instance `_runnerId` and unregisters it
  in `DisposeAsync`. This prevents the global runner registry from
  carrying stale work items between tests and avoids collisions with
  the launch-route spec's `FindAgentJobGrainAsync` helper.
- **`AgentSessionCancelReply` is not a public API contract today** —
  it's a transport record shared between the server route and the
  test double. Both sides treat it as a thin wrapper around the
  runner's reported string; the runner itself emits an untyped
  `{ state: "..." }` JSON object via SignalR.

### Gotchas

- **The launch agent-by-id `agent_*` resolution path is unchanged.**
  `ResolveAgentAsync` was already used by `agent show` /
  `agent update` / `agent delete`. Its behaviour (id-by-id GET,
  name-by-list GET) is preserved end-to-end; the new `session
  launch` command just reuses it. The acceptance criterion
  "Unknown agent surfaces server error" is satisfied by both paths:
  the friendly-name path errors client-side with a clear message,
  the id path surfaces the server's 404 via the existing
  `PrintPostWithOutputAsync` error envelope.
- **`-o` default is `table` for all three new commands**, matching
  the issue-session subgroup's default (compact/reset use `table`).
  The web/CLI consistency rule from prior agents (list/show defaults
  to `json`) is overridden here because the user is staring at the
  outcome of a single command — they want to see the session id,
  not a JSON envelope.
- **Help for `mo agent session --help` does NOT list the
  `--prompt` / `--text` flags of the subcommands.** System.CommandLine
  shows only the subcommand names at the parent `--help`; the
  per-subcommand flags only appear in `mo agent session launch
  --help` / `mo agent session followup --help`. This matches the
  existing `mo issue session` group's help behaviour and is a
  library-level decision, not a CLI design choice.
- **`ProjectAgentSessionsPath` is a private static helper, not a
  public method on `MohistCliApi`.** The helper-then-path pattern
  matches `ProjectAgentsPath` (`MohistCliCommands.Agent.cs:34`):
  one helper per URL family, escape the project id, prepend the
  project prefix, append the suffix. Kept private because no other
  command file needs it today.
- **`BodyInputResolver` SourceFlags is a sealed record on the
  resolver class itself** so callers cannot accidentally construct
  it with mismatched flag labels (the body-kind noun is the
  user-visible label, the flag labels are the option names). The
  legacy 4-arg overload passes through the existing issue-body
  labels so the issue body's error message stays byte-identical.
- **The launch response is rendered with a fixed four-line table**
  (session id / agent id / agent name / status). If the server
  adds fields to the launch response (e.g. `createdAt`, `runnerId`)
  they will not appear in table mode — `-o json` is the right
  escape hatch. This is a deliberate tradeoff matching the issue
  compact/reset commands' table shape.
- **`-o json` for cancel prints the full server envelope, not just
  the `state` field.** Callers that need to parse `state` should
  pipe through `jq '.data.state'`. The envelope-vs-data split
  matches the existing `PrintPostWithOutputAsync` contract — `-o
  json` is "what the server sent", `table` is "what the user
  wants to see".

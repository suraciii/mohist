# Issue 336 progress notes

## Codebase Patterns

- **Test client helpers**: `_fixture.Client.PostDataAsync<T>(...)` and `PostOkAsync(...)` exist in `Support/ApiTestClient.cs` for creating projects/issues.
- **Time provider**: `_fixture.TimeProvider` is a `FakeTimeProvider` available on the integration fixture — use it for deterministic timestamps in tests.
- **Workflow run seeding**: `IWorkflowRunStore.SaveAsync(new WorkflowRun { ... })` is the canonical way to seed a workflow run in tests (see `InboxApiSpecs.cs:333`, `TaskLogRouteSpecs.cs:76`).
- **Issue-to-workflow binding**: `IssueRow.WorkflowRunId` is a computed column sourced from `State` JSON; tests use raw SQL `UPDATE Issues SET State = json_set(State, '$.workflowRunId', json_quote({0}))` to bind.
- **Pagination JSON contract**: `nextCursor` MUST be emitted even when null. The default `JSON.Options` uses `DefaultIgnoreCondition = WhenWritingNull`, which omits null fields. The fix is to use a DTO record with `[JsonIgnore(Condition = JsonIgnoreCondition.Never)]` on the nullable cursor property (see `Issue/Services/IssueInfo.cs:39`, `Api/IssueRoutes.Dtos.cs:207`). Anonymous objects like `new { nextCursor = (long?)null }` get the key dropped silently, which fails tests asserting on `JsonValueKind.Null`.

- `TaskLogService.QueryByTaskIdAsync` resolves `taskId` -> `workId` by walking `run.Stages[].Tasks[].Id` against the taskId and returning the first non-empty `WorkId`. Requires `WorkflowRunQuerier.LoadAsync` (no grain call).

## TaskLog capture engine notes (T-002)

- `runCommand` (`packages/runner/src/system/process.ts:61`) gained an optional `CommandLineOptions` argument with `onLine`/`onClose` callbacks. stdout and stderr share one ordered emit sequence with NO stream dimension (design D3). Each stream's line state is a `{ carry }` buffer so a chunk arriving mid-line is held across reads; a final partial line is flushed in `drainTail` once per stream inside the `close` handler (post-exit drain — design D4).
- The aggregate `CommandResult` is unchanged when `onLine` is not supplied; the existing `Buffer.concat(stdout).toString("utf8")` path runs in the `close` handler before `resolve`, so the byte-identical contract is preserved.
- The single sink is `TaskLogger.write(source, text)` in `packages/runner/src/runtime/task-log.ts`. It masks BEFORE assigning `seq` and BEFORE handing to the collector, so a raw credential can never land in the buffer (design D5).
- `MAX_TASK_LOG_LINES = 5_000` is the single named tunable capacity constant. Head-drop truncation runs inside `TaskLogCollector.append`; discarded `seq` values are not reused because the next-seq counter advances unconditionally. `firstSeq()` returns `null` only when the buffer is empty.
- `CredentialMasker` covers (Phase 1, intentionally minimal — encoding-variant defense deferred): `https://user:pass@host`, `https://token@host`, `Bearer <token>`, GitHub PAT prefixes (`ghp_`/`gho_`/`ghu_`/`ghs_`/`ghr_`), `sk-…` style keys, and `Basic <base64>`. Runtime-known secrets can be primed with `registerSecret(secret)` (≥ 6 chars).
- `ServerConnection.uploadTaskLog(ownerId, workId, batch, signal, ownerKind="workflow")` mirrors `uploadArtifact`'s owner-kind routing: `"workflow"` → `/api/workflow-runs/{id}/work/{wid}/task-log`, `"agent-job"` → `/api/agent-jobs/{id}/work/{wid}/task-log`. Body is JSON `{ entries: [{seq, timestamp (ISO), source, text}], truncated }`. No multipart, no grain involvement.
- `ActionContext.log?: TaskLogger | null` is the new context surface; the executor wiring (T-003) is what constructs and threads the per-work `TaskLogger` into `baseContext(...)`.
- Tests use `vi.useFakeTimers()` + `vi.setSystemTime(...)` to inject the clock for timestamps; collector timestamps come from the injected `now` so the sink + collector are deterministic without wall-clock.
- All 850 runner tests pass (805 baseline + 45 new: 11 in process.spec.ts, 26 in task-log.spec.ts, 10 in server-connection-task-log.spec.ts).

## Executor phase wiring notes (T-003)

- Every ops-command helper (`actions/git.ts`, `actions/{rebase,push,openspec,workspace-prepare,create-github-pr,merge-ready,merge-github-pr,mark-github-pr-ready}.ts`, `runtime/{branch-stability,workspace,worktree-enforcement}.ts`) now accepts an optional sink `{ log, source }` and forwards each line through `log.write(source, text)`. The sink shape lives in `actions/git.ts` as `GitSink`; the option bag is `GitOptions`. The runtime helpers expose the phase label as a named constant so the test suite can pin the source tag:
  - `WORKSPACE_PREP_SOURCE = "workspace-prep"` (runtime/workspace.ts:15) — clone / branch / health-gate git output from `WorkspaceManager.prepare()` and friends.
  - `BRANCH_CHECK_SOURCE = "branch-check"` (runtime/branch-stability.ts:18) — `checkBranchStability` (`git rev-parse`, `--abbrev-ref HEAD`, `--git-path`).
  - `CLEANUP_SOURCE = "cleanup"` (runtime/worktree-enforcement.ts:23) — `readWorktreeSnapshot` and `recoverStaleIndexLock`.
  - Action sources are `action:<name>` literals scoped per action file (`action:rebase`, `action:push`, `action:openspec`, `action:workspace-prepare`, `action:create-github-pr`, `action:merge-ready`, `action:acp-agent`, `action:health-check`). The `<name>` mirrors the `uses:` slug — distinct from `workspace-prep` (the executor's Phase-1 dispatcher clone/checkout) so the viewer can tell clone output from the action body.
- `runtime/git-probe.ts` re-exports `GitOptions` so the runtime layer (branch-stability, worktree-enforcement) types its `git(...)` seam the same way the actions layer does. The fallback is unchanged: callers without a sink still get the byte-identical aggregate contract (`stdout`/`stderr`/`exitCode`/`combinedOutput`).
- `WorkExecutor.execute()` keeps its `Promise<WorkItemResult>` shape to preserve the existing test surface; the new `executeWithLog(work, signal, collector | null)` method is what the host (`RunnerHost.executeAndReport`) calls when it wants to own the collector lifecycle. The collector is constructed per work item inside `executeWithLog` when none is supplied, mirroring design D6.
- `baseContext()` (runtime/executor.ts:230) grew a final `log: TaskLogger | null = null` parameter so every action the executor dispatches gets the per-work sink through `ActionContext.log`. The factory closure that builds cleanup-agent contexts forwards `log` too.
- `RunnerHost.executeAndReport` flushes the collector right before the verdict `report()`, with **owner-id mirrored from `artifact-side-effects.ts:107`** (`ownerKind === "agent-job" ? agentJobId : workflowRunId`). The flush is wrapped in `try/catch` — failures are logged via `console.error` and swallowed so they cannot block or fail the report (design D6).
- Constructor for `WorkExecutor` got an optional `now: () => Date` parameter (defaults to `(() => new Date())`) so per-host clock injection matches the existing `n` convention from `workspace-registry.ts`/`worktree-enforcement.ts`. The collector inside `executeWithLog` is built with this `now`, so host-level test setups can pin timestamps without `vi.useFakeTimers` polluting other modules.

## Task log viewer notes (T-004)

- Server-side shape (verified from `packages/server/src/Mohist.Server/Api/IssueRoutes.TaskLog.cs:21-54`): `GET /api/projects/{projectId}/issues/{number}/workflow/tasks/{taskId}/logs?cursor=&limit=` returns `{ lines: [{seq, timestamp (ISO-8601), source, text}], nextCursor, truncated }`. The taskId path segment is the timeline `TaskRun.Id` (e.g. `"build.1"`, `"integrate:publish.1"`); the server resolves it to a `WorkId` via `TaskLogService.QueryByTaskIdAsync`. URL-encoding is required for taskIds containing `:` (use `encodeURIComponent`).
- Missing run / missing taskId resolution returns 200 with empty `lines`, not 404 — only a missing route (older server without T-001) returns 404. The hook converts 404 to `{ lines: [], nextCursor: null, truncated: false }` so older servers degrade gracefully; non-404 errors propagate so the panel can surface them.
- New web types live in `packages/web/src/entities/issue/model/task-log.ts` (`TaskLogLine`, `TaskLogPage`) and are re-exported through `model/types.ts` → `index.ts`.
- The hook `useIssueWorkflowTaskLog(issueNumber, taskId, params?, enabled=true)` is in `entities/issue/api/queries.ts`; query key shape is `[issueNumber, taskId, projectId, 'workflow-task-log', params]` — issueNumber + taskId are the first two slots per the design D10 spec ("refetches when a different task is expanded"). The hook is disabled when taskId is null/empty, issueNumber is 0, or projectId is missing.
- `TaskLogPanel.tsx` (`widgets/issue-workflow/ui/`) renders inside the failed-task expanded region of `TaskProgressPanel.tsx`, **after** the existing task.reason / deliveryGuidance / task.output blocks. Test IDs: `task-log-panel`, `task-log-scroll`, `task-log-lines`, `task-log-empty`, `task-log-truncation-indicator`. The scroll region auto-pins to bottom on line-count change so the failing tail is visible.
- Existing failure-kind guidance (e.g. `branch-invariant-violation` panel), structured `output` JSON rendering, and the task status icon / title remain byte-identical — verified by `TaskProgressPanel.test.tsx:does NOT alter the existing failure-kind guidance or output rendering` and the `keeps the task row title and status icon rendering unchanged when the panel is expanded` test.

Integration render tests: `widgets/issue-workflow/ui/TaskProgressPanel.test.tsx` (13 tests covering scrollable lines, source labels, truncation indicator, empty state, loading/error placeholders, no-panel for non-failed tasks, query-key shape via `expect(mockedUseIssueWorkflowTaskLog).toHaveBeenCalledWith(161, 'build-task-1', {}, true)`).

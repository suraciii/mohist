## T-001 — Rename ActiveWorkflowRunId to WorkflowRunId and stop clearing the reference on archive/close

### Decisions made
- Collapsed the dual `ActiveWorkflowRunId` ([JsonIgnore]) + `WorkflowRunId` properties
  in `Domain.Issue` into a single `WorkflowRunId` property backed by `_workflowRunId`.
  Public JSON contract is already `workflowRunId` so the rename is internal-only;
  no data migration is required (the `IssueRow.WorkflowRunId` computed column still
  reads `json_extract(State,'$.workflowRunId')`).
- `Issue.Archive()` and `Issue.Close()` no longer null `_workflowRunId`. Only
  `ClearStoppedWorkflow` (called from `TryReuseActiveWorkflowAsync` when reusing
  a stopped run slot at start time on an `InProgress` issue) may clear it.
  `Unarchive` already only cleared `_archivedAt`; left it as is.
- `WorkflowProfileLockedException` rewritten: `ActiveWorkflowRunId` property →
  `WorkflowRunId`; message wording "active workflow run" → "workflow run reference".
- Renamed log text in `IssueGrain.TryReuseActiveWorkflowAsync` (the only places
  that describe the *reference* rather than the actual workflow run state):
  - "reusing active workflow …" → "reusing workflow run …"
  - "active workflow … cannot be loaded while starting; clearing active workflow reference"
    → "workflow run … cannot be loaded while starting; clearing workflow run reference"

### Things deliberately NOT changed in T-001 (covered by T-002)
- `IssueGrain.CancelAsync`: still uses `_issue.WorkflowRunId is { } wrId` as the
  trigger to fetch workflow status before closing. T-002 introduces an explicit
  `IsWorkflowControllable` derived judgment to gate this check on
  `Status == InProgress && run is not stopped/terminal`.
- `IssueGrain.TryReuseActiveWorkflowAsync` method name and its start-time-only
  semantics: unchanged behavior. T-002 notes "rename the local" — local was
  already renamed (`activeWorkflowRunId` → `workflowRunId`) but the method
  name and signature stay.
- Profile-lock guard at `IssueGrain.UpdateFullAsync`: still uses
  `_issue.WorkflowRunId is not null` as the "has started" signal. T-002 keeps
  this — it is correct per the design (a Done/archived issue that has started
  must keep its profile locked).
- `IssueWorkflowReconciliationService` candidate query still uses
  `WorkflowRunId != null` with the per-grain `Status != InProgress` guard.
  T-002 adds the `IsArchived` computed column and the `!IsArchived` filter at SQL
  level.
- The `WorkspaceRoutes.cs` "Issue has no active workflow" message and the
  `IWorkflowGrain.cs` "active workflow work item" doc comment describe actual
  workflow *state*, not the issue→run reference, so left unchanged per task
  scope ("where they describe the reference").

### Patterns established (Codebase Patterns)
- Domain.Issue is a `sealed partial class` split across `Issue.cs`,
  `Issue.Transitions.cs`, `Issue.Labels.cs`, `Issue.Prerequisites.cs`. State
  fields go in `Issue.cs`; behavior methods go in the others.
- All issue-state JSON serialization flows through `IssueStore.Serialize/Deserialize`
  using `JSON.Options` (camelCase, web defaults, enum-as-string). Property names
  must round-trip the same way before/after rename to keep stored rows valid.
- The `IssueRow` table stores opaque JSON in `State`; everything is queried via
  computed columns (`WorkflowRunId`, `ProjectId`, …). New computed columns
  need a DB migration, but renames that don't change the JSON key never need one.
- `TestData`/`Support` helpers: tests should use `IssueStore.Serialize/Deserialize`
  helpers from `Mohist.Server.Infrastructure.Data.Issue` for round-trip checks
  instead of constructing JSON manually.
- Spec test naming convention: `<Subject>_<ExpectedBehavior>` (e.g.
  `Archive_PreservesWorkflowRunReference_AndSetsArchivedAt`). All domain specs
  carry `[Trait(Speed, Unit)]` and `[Trait(Sut, Issue)]`.

## T-002 — Decouple active-workflow control and reconciliation judgments from reference presence

### Decisions made
- Added `bool? IsArchived` to `IssueRow` with a STORED computed column
  `json_extract(State,'$.archivedAt') IS NOT NULL` (mirrors the
  existing `WorkflowRunId` / `ProjectId` / `Number` computed columns in
  `MohistDbContext.cs:236`). Added the corresponding migration
  `20260625052135_AddIssueIsArchivedComputedColumn` and let
  `dotnet ef migrations add` regenerate the model snapshot cleanly.
- `IssueWorkflowReconciliationService` candidate query changed from
  `Where(i => i.WorkflowRunId != null)` to
  `Where(i => i.WorkflowRunId != null && (i.IsArchived == null || !i.IsArchived.Value))`.
  The per-grain `Status != InProgress` guard in
  `IssueGrain.ReconcileWithWorkflowTerminalStateAsync` is preserved as
  defense-in-depth for done-but-not-archived issues.
- Added a private `GetControllableWorkflowStatusAsync` helper on
  `IssueGrain` that returns the workflow status string only when
  `Status == InProgress && WorkflowRunId != null && run is not
  stopped/completed/failed`, or `null` otherwise. `CancelAsync` now
  uses this helper so the cannot-close-while-running check runs only
  when there is actually a controllable workflow — a Done/archived
  issue with a preserved reference no longer spuriously trips it.
- Profile-lock guard at `IssueGrain.UpdateFullAsync` left unchanged
  (`_issue.WorkflowRunId is not null` is the "has started" signal);
  a Done/archived issue that has started keeps its profile locked.
- Added a `ReconcileOnceAsync` test seam to
  `IssueWorkflowReconciliationService` (mirrors
  `EpicReconciliationService.ReconcileOnceAsync`).

### Patterns established (Codebase Patterns)
- `dotnet ef migrations add <Name>` is the source of truth for
  migrations: hand-written migrations have to mirror the SQL EF emits
  (e.g. unescaped `State` rather than `"State"` in the json_extract
  expression) and the model snapshot must be regenerated via EF or it
  fails with `PendingModelChangesWarning` at the next `Migrate()`.
- SQLite provider for EF Core 10 *does* support
  `ALTER TABLE ADD COLUMN ... STORED` directly (single
  `migrationBuilder.AddColumn(...)` with `computedColumnSql` +
  `stored: true`), unlike the older pattern in
  `20260620185946_ReplaceAgentSessionLabelsWithComputedColumns` which
  needed AddColumn + AlterColumn for older SQLite.
- `bool?` LINQ translation: SQLite provider does **not** translate
  `GetValueOrDefault()` on `bool?`. Use
  `i.IsArchived == null || !i.IsArchived.Value` for an
  `IS NULL OR = 0` shape, or rewrite the query against a denormalized
  non-nullable column.
- Background services that need a test seam expose a public
  `ReconcileOnceAsync(CancellationToken)` method on top of the private
  hosted-loop entry point. The hosted `ExecuteAsync` waits one period
  before its first run; tests call the seam directly.
- `IGrainFactory` fake in unit tests must implement every method on
  the interface (or throw `NotSupportedException`); see
  `EpicReconciliationServiceSpecs.TestEpicGrainFactory` and the new
  `IssueWorkflowReconciliationServiceSpecs.RecordingIssueGrainFactory`.
  `GrainKey.Issue(id)` returns the id unchanged (no `issue:` prefix).

## T-003 — Keep archived-issue detail API exposing the workflow run reference and full history

### Decisions made
- `IssueQuerier.ToInfo` (both overloads, `IssueQuerier.cs:408,448`) and
  `IssueRowMapper.Deserialize` were already keyed off the renamed
  `issue.WorkflowRunId` after T-001, so no mapper change was needed
  for this task — `grep -n ActiveWorkflowRunId packages/server/src`
  returns no production hits. The T-001 rename was sufficient.
- Added a single new API-level regression spec file
  `IssueArchivedDetailApiSpecs.cs` (9 specs) that drives the
  `WebApplicationFactory<Program>` HTTP client through the full
  archived-Done read path: detail, workflow status, artifacts,
  events, feedback, and a wire-shape lock on the renamed property.
  The tests pin every WHEN/THEN clause in
  `specs/http-api/spec.md#archived-issue-detail-preserves-workflow-run-history`.
- For the workflow-run-state assertion (`workflowStatus == "completed"`,
  `Workflow.Status == "completed"`) the test seeds the run to
  `WorkflowRunStatus.Completed` via the DB row + `DeactivateForTestAsync`
  on the workflow grain. `IssueGrain.CompleteWorkAsync` only marks
  the issue `Done`; the run's `Status` field is runner-owned, so the
  test sets it directly rather than driving the runner.

### Patterns established (Codebase Patterns)
- API-level spec files use `[Collection("MohistIntegration")]` and
  read raw JSON via `client.GetRawAsync` when asserting on JSON
  shape — `client.GetDataAsync<T>` is fine for typed happy-path
  checks but cannot distinguish "field absent" from "field present
  with null", which the spec requires for `activeWorkflowRunId`
  and `attention` (both must NOT be on the wire).
- `WorkflowArtifactRow.TaskRunId` is `[Required]` and not nullable;
  artifact seeders that don't have a task context must use
  `string.Empty`, not `null`.
- The `attention` field on the issue detail is omitted by
  `JsonSerializerDefaults.Web` when null, so the right assertion
  for "no attention indicator" is
  `data.TryGetProperty("attention", out var v) && v.ValueKind != JsonValueKind.Null`
  rather than `data.GetProperty("attention")`.
- `WorkflowRunStatus` is serialized as a lowercase string
  (`"completed"`, `"running"`) by the project's
  `JsonStringEnumConverter`, so the wire shape matches the string
  values the spec mandates, not the C# enum names.

## T-004 — Render full workflow execution history on the archived issue detail page

### Decisions made
- `IssueDetailPage.tsx` reads `issue.archivedAt` to compute a single
  `isArchived` boolean (after the `!issue` guard). All archived-specific
  UI bits are derived from this one source of truth.
- Added `ArchivedPill` in the header pill row (alongside DraftPill,
  WorkflowStagePill, HealthPill). The pill carries
  `data-testid="archived-pill"` and `data-archived-at="<iso>"` so tests
  can assert on both visibility and the timestamp.
- Added `archived-banner` block under the pill row that explicitly tells
  the user the timeline/artifacts/events/feedback below are preserved.
  This is the visibility signal the spec calls out as required for
  "the page SHALL display the archivedAt state without removing
  execution history".
- "Back to board" link becomes "Back to archived" for archived issues
  and points at `/archived` instead of the project root. Same
  `data-testid` pattern (`back-to-board` vs `back-to-archived`) so any
  existing selectors keep working for non-archived issues.
- `WorkflowYamlDialog` now takes `isArchived` and switches its heading
  ("Active run YAML" → "Workflow run YAML") and description copy.
  Test selector `data-testid="active-run-yaml-trigger"` is unchanged
  but `data-yaml-mode="archived|active"` lets tests assert on which
  variant rendered. The dialog content is identical otherwise — this
  is purely a wording fix so an archived issue isn't described as
  "active".
- The "Running" pill in the header is now gated on `!isArchived` too.
  An archived issue will never be reported as "Running" by the page,
  even if some upstream signal says so.
- The Actions `CardSection` is now: for archived issues, render only
  a single explanatory note (`data-testid="archived-actions-note"`)
  that lists the disabled controls and explains why; for non-archived
  issues, render the existing Start/Stop/Retry/Rerun/Resume/Force Stop
  surface exactly as before.
- The Blocked/Interrupted retry/resume/rerun/stop group (lines ~1167
  in `IssueDetailPage.tsx`) is now gated on `!isArchived` as well —
  this is the defence-in-depth for the rare case where the
  WorkflowView still surfaces a `canRetry`/`canRerun` action for an
  archived issue (it shouldn't, but the existing `canStopWorkflow`
  guard is keyed on status+health, not archived state).

### Things deliberately NOT changed in T-004
- `WorkflowView` itself: `readOnly = isClosed` (Cancelled) is unchanged.
  For Done/archived, `InlineApproval` already doesn't render because
  `isAwaitingApproval` is false. The stage bar remains browsable for
  archived issues, which is desirable.
- The standalone Web `ArchivedPage` list data-fetch bug — out of scope
  per the issue's explicit non-goal and per the T-004 description.
- The `WorkflowYamlDialog` `data-testid="active-run-yaml-trigger"` was
  kept stable for backward-compat with existing test selectors.

### Patterns established (Codebase Patterns)
- For new test files in `packages/web/src/pages/issue-detail/ui/`, the
  existing convention is `IssueDetailPage.<aspect>.test.tsx`. The new
  archived file is named `IssueDetailPage.archived.test.tsx` to match
  `IssueDetailPage.readiness.test.tsx` and `IssueDetailPage.test.tsx`.
- The same Vitest `mockUseIssue` / `mockUseWorkflowTimeline` /
  `mockUseIssueDiff` / etc. mock-setup pattern from
  `IssueDetailPage.test.tsx` is reused. The mocked
  `useIssueEvents` returns `{ data: undefined, isLoading: false }` so
  the activity dialog stays unmounted until clicked (this matters for
  tests that don't open the dialog).
- For new component variants rendered conditionally on a prop, expose
  a `data-<state>="<value>"` attribute on the testid-bearing element
  instead of inventing a new testid. The archived file uses
  `data-yaml-mode="archived|active"` and `data-archived-at="<iso>"`
  rather than `data-testid="archived-yaml-trigger"` etc.
- Tests asserting "control X is not present" should use `queryBy*`
  not `getBy*` — `queryByRole('button', { name: /^Retry$/ })` and
  `queryByText(/^Force Stop$/)` are the right call.
- The text in a JSX child uses `&apos;` (HTML entity) for an
  apostrophe inside JSX literal text — the existing
  `tests/IssueDetailPage.test.tsx` regex `/issue's workflow profile
  configuration/i` depends on the rendered apostrophe being a regular
  `'` (not `\u2019`/`'`). When extracting such text into a JS string
  literal (e.g. when making it conditional on `isArchived`) keep the
  same `\u0027`/regular apostrophe; using `\u2019` silently breaks
  the existing test.

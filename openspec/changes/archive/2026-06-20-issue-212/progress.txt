## Codebase Patterns

- **Runner registration payload is additive.** `RunnerRegistration` (`packages/runner/src/core/types.ts:92`) keeps `coderModels: string[]` and pairs it with a parallel optional `coderModelVariants: Record<string, string[]>` map. New fields ride alongside, never replace.
- **Opencode discovery always reads `provider/model` first, then optional JSON.** The runner runs `opencode models --verbose` and gets `id\n{json}` pairs where the JSON's `variants` map keys are the legal reasoning-tier names. The `id\n{json}` is a stream format: missing/unparseable JSON on a model degrades to an empty variant set for that one model; the discovery call as a whole only fails when the command/transport itself fails (existing "log + empty result" behavior is preserved).
- **Module-level cache is reset via an exported `clear...ForTesting()` seam.** Discovery uses a 30-minute in-process cache that only caches successful (non-empty) results, with an exported test reset hook. Tests should clear the cache in `beforeEach` so they don't share state.
- **`MOHIST_AGENT_MODELS_COMMAND` overrides `MOHIST_AGENT_COMMAND` which overrides the default `opencode`.** All three apply to `discoverOpencodeModels`; use the same precedence chain in test fixtures.
- **Orleans `[GenerateSerializer]` on a positional record treats constructor parameters as positional serializer ids.** Adding a new optional parameter at the END of the constructor list is the additive, non-breaking pattern (existing serialized bytes still deserialize — the new field defaults to `null`). Moving or removing existing parameters would break the wire format.
- **Aggregate variant maps via set union, not override.** When two runners report the same model id with different variant lists, fold them into a sorted union (per-model variants are accumulated, not replaced). This is consistent across the registry grain and the route handler so a global runner's variant set and a project runner's variant set never silently shadow each other.
- **`RunnerInfo.CoderModelVariants` is in-memory only.** Do NOT project it onto `RunnerStatusView` — the runner-status DTO is part of the additive surface that stays on `coderModels: string[]` per design D3. The map is consumed only by the opencode/models endpoint.
- **The "present-but-null = clear" semantic on PATCH requires raw JSON inspection.** `System.Text.Json` deserializes both `field absent` and `field: null` to `null` on a nullable reference type, so the http-api spec's "clear-on-clear" semantic for `model`, `modelVariant`, `stageModels`, and `stageModelVariants` needs the route handler to bind the raw `JsonElement` alongside the strongly-typed DTO and use property-presence checks (not bound values) to build a tri-state patch (`Absent` / `Clear` / `Set`). The DTO has both a `Raw` `JsonElement` and a `BindAsync` parser (`packages/server/src/Mohist.Server/Api/IssueRoutes.Dtos.cs`).
- **The agent block at `vars.agent` and `stages.<stage>.vars.agent` is SET-replaced, never deep-merged.** `VariableBundle.Patch` deep-merges nested objects, which makes deletions impossible (`{model: x}` + patch `{variant: y}` does not remove model). Issue metadata writes treat the whole `agent` dict as a SET target: read existing agent keys, mutate just the model/variant entries, write the dict back. `IssueModelMetadata` (`packages/server/src/Mohist.Server/Issue/Services/IssueModelMetadata.cs`) is the canonical implementation.
- **Variant bound to model: clearing model atomically clears its variant.** The "dependency" invariant (model-reasoning-variants spec) means `model: null` ⇒ `variant: null` on the same write; switching model without an explicit variant also drops the stale variant. Implemented in `MutateAgentDict` / `MutateStages` as a SET-with-cascade: any model-side `Clear` or `Set(different)` removes the bound `variant` key atomically.
- **The issue profile stores only issue-level overrides plus built-in context.** Global (`config.jsonc`) and project Variables are merged live at resolution time (`MergeAll(global, project, issue)`), so explicit issue-level model/variant overrides survive edits to global/project Variables. Issue metadata persistence uses the issue-only `Variables` and lets `BuildVariables` / dispatch / display do the live merge.
- **CLI `--model-variant` rides alongside `--model`.** The CLI's `mo issue create` and `mo issue update` already accept `--model` and post it via the API; adding `--model-variant` is a parallel optional option that forwards to the new `modelVariant` DTO field. `mo issue show` picks up the new fields automatically through the JSON read model — no CLI change needed there.
- **Runner composes `provider/model:<variant>` only at delivery time.** `acp-agent.ts` carries the variant through `AgentConfig` / `RequestedModel` as a separate field, and `resolveRequestedModel` produces the composed id `${model}:${variant}` only when a variant is present. Bare-id behavior (no variant) is byte-identical to before T-004. The composed id naturally keys `requestedModelMatchesSession` and `cachedModelAllowsReuse`, so a variant change selects a fresh session.
- **`attachWorkflowAgentSession` records the composed id, not the bare model.** `acp-agent.ts:attachSessionToServer` resolves the requested model up front (via the same `resolveRequestedModel` used by `applyRequestedModel`) so the `model` field in the `attachWorkflowAgentSession` body matches the id the runner is about to apply to the session. Downstream consumers (session-status views, runner-status DTOs) see `provider/model:<variant>` whenever a variant is in effect.
- **`useAvailableModelIds` returns `{ models, modelVariants }`, not `string[]`.** The TanStack Query hook shape changed in T-005: consumers must read `data?.models` and `data?.modelVariants ?? {}` instead of `data` directly. The endpoint (`GET /api/projects/{id}/opencode/models`) keeps `models: string[]` unchanged on the wire and adds the parallel `modelVariants` map, but every web component that used the previous flat `string[]` shape needed a one-line destructure update.
- **Variant picker pattern: render nothing when there are no variants.** `VariantPicker` (`packages/web/src/shared/ui/VariantPicker.tsx`) is a controlled select that hides itself entirely when the selected model has no entry in `modelVariants` (or has an empty array). All model-selector surfaces use the same prop shape (`modelId`, `modelVariants`, `value`, `onChange`) so a future "hide for a different reason" rule can be added in one place. The Default option maps to `onChange(null)`, never `onChange('')`.
- **Stage-level model + variant lives in two parallel maps.** Settings + Issue selectors each keep `localStageModels: Record<string,string>` and `localStageModelVariants: Record<string,string>` side by side. A new `useStageModels` query returns both; `setStageModel` takes both. They are independent payloads on the server, and the variant never survives a model change (the per-stage set/clear handler drops the variant key in the same state update that swaps the model).
- **`useOpencodeModel` returns `{ model, variant }`.** The query + mutation pair on the project-level default (`packages/web/src/entities/settings/api/queries.ts:useOpencodeModel`/`useUpdateOpencodeModel`) takes a `{ model, variant }` payload; `variant: null` clears the variant atomically when paired with a model change or with `model: null`. The bare `string` signature is gone — every caller in the web now uses the new shape.
- **Agent definitions API has model + variant helpers but no UI yet.** `packages/web/src/entities/agent/api/client.ts` exposes `readAgentModelAndVariant(agent)` and `writeAgentModelAndVariant(current, model, variant)` for the future Agent editor. The two helpers together enforce the dependency invariant (variant is read-only when model is missing; clearing the model atomically clears the variant; non-empty config with both null returns `null`). There is no Agent editor component yet in the web — only the API + helpers + a 9-test unit suite.

### Learnings for future tasks

- **Decisions made**
  - Returned `Record<modelId, string[]>` from discovery rather than `Array<{ id, variants }>`. The map is strictly additive and lets D3 keep the `coderModels: string[]` (and downstream `models: string[]`) wire-format unchanged. Models with no variants are simply absent from the map; the type's optional nature covers this.
  - The cache only stores non-empty results. An empty result on failure must never be served from cache for 30 minutes, otherwise a transient opencode outage would freeze the discovery for half an hour.
  - A separate exported `parseOpencodeModelsVerbose` is the pure entry point; tests prefer it. `discoverOpencodeModels` is integration-tested via `MOHIST_AGENT_MODELS_COMMAND` pointing at a small node script that counts invocations and writes a fixture payload.

- **Gotchas discovered**
  - `JSON.stringify` of nested objects produces single-line JSON; the parser's "lines consumed" counter must use the raw line count (no `-1`), otherwise a single-line JSON block stalls the iterator and the following model id is treated as a metadata block.
  - When the metadata block fails to balance braces, the model id (the line before the broken `{`) is still recorded but the broken line is skipped; it must not be re-treated as a new model id (would corrupt the model list).
  - Tests that spawn fake commands need a shebang (`#!/usr/bin/env node`) **and** executable bit (`chmodSync(..., 0o755)`); without either, `execFile` returns `EACCES` or `Syntax error` from `/bin/sh`.
  - The `runner-host.spec.ts` mock had to be updated when the discovery return type changed; the pre-existing `vi.mock("../src/runtime/opencode-models.js", ...)` pattern in that file returns the legacy shape and would break compile / runtime if left unchanged.

- **Patterns / API shapes established**
  - `DiscoveredOpencodeModels` is the new public return type for `discoverOpencodeModels`. Future tasks (T-002 server, T-004 runner delivery) consume the `{ models, variants }` shape; do not reintroduce a flat `string[]` return.
  - The runner registration wire format now has both `coderModels: string[]` and `coderModelVariants: Record<string, string[]>`; the server's runner registry (T-002) is expected to mirror this as `models: string[]` and `modelVariants: Record<string, string[]>`.

- **Cross-task invariants**
  - Per D2/D3, the variant name is the only thing persisted or surfaced; variant bodies (`{reasoningEffort: ...}` etc.) live only in discovery results. T-004 (delivery) must compose `provider/model:<variant>` and never persist a variant body.
  - Per D5, session-reuse keying must include the composed id, so a variant change naturally selects a fresh session.
  - The 30-minute cache is runner-process-local; there is no shared cache. A runner restart re-discovers.

### Learnings for future tasks

- **Decisions made**
  - The grain's aggregation rule is **set union**, not "first wins" or "last wins". With disjoint runner `coderModels`, this naturally produces the union of models with each model's variants preserved; with overlapping models, it folds variant names from both runners into a sorted, deduplicated list. The route handler uses the same rule so the endpoint never silently shadows one runner's variants with another's.
  - Models with no variants are simply absent from `modelVariants`. The acceptance criterion allows "absent OR `[]`"; absent was chosen because it keeps the response payload smaller and matches the runner-side `coderModelVariants` contract (which is optional and undefined for no-variant models).
  - `RunnerInfo.CoderModelVariants` stays in-memory on the grain. The runner-status DTO is intentionally NOT extended — that surface remains `coderModels: string[]` per design D3 so the runner-status Web view keeps working without a T-005 dependency.
  - Orleans `[GenerateSerializer]` on a positional record derives the serializer from constructor parameter order. Appending a new optional parameter at the end is additive: in-flight serialized bytes (from a pre-T-002 runner or a still-replaying silo) deserialize with the new field defaulted to `null`, and a null map is treated the same as an absent map by `ListCoderModelVariantsAsync`.

- **Gotchas discovered**
  - `OpencodeModelsDto` started as `record(string[] Models)` (positional). Adding a second positional parameter without a parameterless ctor breaks System.Text.Json deserialization because the existing two tests pass no value for the new field. The fix is a private parameterless ctor delegating to the primary constructor with empty defaults — keeps both shapes compilable and round-trippable.
  - The existing `OpencodeModels_OnProjectRoute_ReturnsGlobalRunnerModels` test registers a global runner but never scopes to a project, so its variants flow through the global registry path. The new `OpencodeModels_DisjointRunnerModels_ProducesUnionWithVariantsPreserved` test pairs a project-scoped runner with a global one to verify the union across both registries, which is the actual production aggregation.
  - `RunnerInfo` is used by reference (record-with `with { ... }`) inside both `RunnerGrain.RegisterAsync` and `RunnerRegistryGrain.RegisterAsync`. Adding a new optional parameter at the end of the primary constructor is transparent to all `with` expressions — they preserve the new field by default. Any field that needs to be overwritten by `with` (e.g. normalizing at registration time) should be done in the route handler before constructing the `RunnerInfo`.

- **Patterns / API shapes established**
  - Wire format mirror: `coderModels: string[]` / `coderModelVariants: Record<string, string[]>` on registration ↔ `models: string[]` / `modelVariants: Record<string, string[]>` on the endpoint. Web (T-005) consumes only the endpoint variant.
  - Grain API: `ListCoderModelsAsync()` and `ListCoderModelVariantsAsync()` are siblings; routes always call both. The variant dictionary uses case-insensitive model keys (matching the existing `ListCoderModelsAsync` comparer) so downstream normalization is symmetric.
  - The endpoint returns `modelVariants` as a plain JSON object (`Dictionary<string, string[]>`), not wrapped in a typed DTO record. Adding it as an anonymous property keeps the response shape extensible without a parallel DTO.
  - The runner-status DTO (`RunnerStatusView.CoderModels: IReadOnlyList<string>`) is the additive contract's stable side. Any future variant-aware runner-status surface must be a new optional field, not an evolution of the existing `coderModels`.

- **Cross-task invariants**
  - The endpoint now exposes the complete variant universe across both registries; the picker in T-005 must read exactly this map and not introduce a parallel discovery path.
  - T-003 will introduce per-issue / per-stage variant fields that flow through the same `provider/model:<variant>` composition pattern T-004 will use at delivery. The grain-level variant map (this task) and the issue-level variant field (T-003) are independent — neither references the other; the picker (T-005) joins them via the model id.
  - The endpoint is strictly additive: any client still reading only `models: string[]` (e.g. the existing Web `getOpencodeModels` call) is unaffected because the new field is a sibling object property.

### Learnings for future tasks
- **Decisions made**
  - **Tri-state patch over nullable booleans.** A patch with `Absent` / `Clear` / `Set(T)` cleanly models the spec's "absent = no change" vs "present-but-null = clear" semantic for both `string` and `Dictionary<string,string>` fields, and the same `FieldPatch<T>` type works for both top-level and per-stage fields.
  - **Agent block as SET target, not Patch.** `VariableBundle.Patch` is a deep merge that cannot represent deletions, but the spec requires "clear model atomically clears variant" — i.e. a key removal inside `vars.agent`. So `IssueModelMetadata` reads the existing `agent` dict, mutates just the touched keys (`model`, `variant`), and writes the dict back as the new `vars.agent`. The non-agent keys of `vars` and the untouched stages are preserved verbatim.
  - **`UpdateIssueRequest.Raw` is captured at bind time, not re-parsed.** The route handler binds the raw body once into `Raw: JsonElement` and uses property-presence checks (`raw.TryGetProperty("model", out var el)`) to detect "absent" vs "present-but-null". This avoids a second `JsonSerializer.Deserialize` round-trip and keeps the `BindAsync` contract self-contained.
  - **Querier surfaces `variant` only when `model` is present.** `ReadAgentVariant(agentConfig, hasModel: ...)` returns `null` if the model is missing — that's the read path's expression of the dependency invariant. The write path enforces the same invariant via `MutateAgentDict`; both paths agree.
  - **`mo issue show` does not need a CLI change.** The show command reads via the API; the new fields ride the existing JSON read model. Adding CLI surface for `modelVariant` is therefore unnecessary beyond create/update.
- **Gotchas discovered**
  - **`AgentConfig_WithModelAndVariant_PlacesBothInAgentVariable` is the single seal for the workflow-engine spec.** The spec scenario "Variant is fixed at issue creation and dispatched with its model" maps to one assertion: `BuildVariables(..., globalAgentConfig: { model, variant }).Vars.agent.variant == variant`. The dispatch path (`WorkflowDispatchBuilder.ResolveWith`) reads `effectiveVarsJson.agent` as a whole and forwards it to the runner, so the agent dict is the only contract this task needs to satisfy — T-004's runner delivery then consumes that `agent.variant`.
  - **`UpdateIssueRequest` had to become a class with init-only properties.** Adding the `Raw` `JsonElement` and the `BindAsync` parser forced a move away from positional records (records cannot carry arbitrary bind-time side effects). The DTO is now a class with init-only setters, which matches the `[AsParameters]`-friendly shape ASP.NET Core minimal APIs expect.
  - **`IssueQuerier.ApplyIssueWorkflowVariables` reads from the *merged* bundle, not the issue-only bundle.** The display layer merges `global + project + issue` Variables, so a global model + issue-level variant shows correctly on `GET /api/issues/{number}`. The querier only suppresses the variant when the issue itself has neither a model nor a merged model — i.e. when there's no model to bind to anywhere.
  - **Malformed `stage_models` JSON was already a no-regression scenario** (the existing `VariableBundle.FromJson` catches and returns `Empty`). The new querier preserves that behavior; a malformed JSON in `IssueWorkflowProfile.Variables` produces an empty per-stage dict at display time, not a 500.
  - **`stageModels: { plan: "" }` clears that stage's model and its variant.** Per-stage empty string is mapped to `FieldPatchKind.Clear` in `ResolveMapField` → `ExtractFieldPatch`, and `MutateAgentDict` then drops the `model` and `variant` keys for that stage. Whole-map `null` triggers the `clearAllStages` path which iterates every existing stage and empties its agent block.
- **Patterns / API shapes established**
  - **Patch entrypoint contract.** Route handlers compose a `ModelMetadataPatch` from the request DTO and pass it to `IssueModelMetadata.ApplyModelMetadata(currentBundle, patch)`. New model-metadata fields only need (a) a `FieldPatch<T>` slot in `ModelMetadataPatch`, (b) a `TryMutate*` step in `ApplyModelMetadata`, and (c) DTO presence-tracking in `BindAsync` — a closed extension pattern.
  - **Stage variants share the issue-level patch vocabulary.** `StageModels` and `StageModelVariants` use the same `FieldPatch<Dictionary<string,string>>` type, with `ExtractFieldPatch` projecting a per-stage patch from the map patch. Per-stage clear semantics reuse the top-level `FieldPatchKind.Clear` plus `stage.<name>: ""` short form.
  - **Querier surfaces mirror the agent block shape.** `Model` ⇔ `agent.model`, `ModelVariant` ⇔ `agent.variant`, `StageModels` ⇔ per-stage `agent.model`, `StageModelVariants` ⇔ per-stage `agent.variant`. There is no other persistence path for the variant; the read model is the agent block read out as plain fields.
- **Cross-task invariants**
  - The variant name is the only thing persisted (per D2). T-004's runner must compose `provider/model:<variant>` only at delivery time and never persist a variant body.
  - The read model exposes `modelVariant` / `stageModelVariants` as plain strings (not objects). T-005's picker reads these from the JSON response.

### Learnings for future tasks

- **Decisions made**
  - **Composition only at delivery, never at parse.** The runner stores `model` and `variant` as separate fields through `AgentConfig` / `RequestedModel`; the `${model}:${variant}` join happens inside `resolveRequestedModel` and is never persisted or cached separately. This keeps the bare-id path byte-identical to pre-T-004 (one less conditional branch downstream) and makes the composed-id semantics obvious in the source.
  - **`attachSessionToServer` records the composed id.** Recording the bare model would have left a visible disconnect: the server would say `model: anthropic/claude-sonnet-4-5` while the runner actually sent `anthropic/claude-sonnet-4-5:high` to opencode. Aligning the recorded model with the composed id makes observability match reality. Reusing `resolveRequestedModel` in the helper avoids a second composition path.
  - **Best-effort is achieved by reusing existing try/catch, not by adding new error handling.** `applyRequestedModel` already wraps `setSessionConfigOption` and `unstable_setSessionModel` in nested try/catch blocks that log and continue. The variant change is purely additive — composing the id is the only new step, and the existing error-swallowing paths already keep an unsupported variant from failing the run.
  - **Diagnostic `requestedVariant` is surfaced only when present.** Mirrors the model-side nullability convention; log consumers can rely on the field being `null` whenever no variant was set.

- **Gotchas discovered**
  - **The fake agent's existing `model-fallback` / `model-config-fails` scenarios throw on any `setSessionConfigOption`.** Adding a new `rejects-composed-model` scenario that throws only when the value contains `:` lets us exercise the "variant rejected" path without coupling it to the legacy "config option unsupported" path. Pattern: piggyback on the existing scenario enum so the unsupported-variant test isolates the failure to the `:variant` syntax specifically.
  - **`setSessionConfigOption` is mocked in `FakeAcpAgent.handler()` per scenario.** When adding a new scenario branch, the new scenario must be appended to the `Scenario` union type at the top of the file or tsc will reject the comparison. The existing typecheck does not flag string literal unions with `as never` casts in test bodies — only the handler branch comparison needs the union update.
  - **`attachSessionToServer` is called *before* `applyRequestedModel` in both new and ephemeral session paths.** Refactoring it to resolve the composed id must not change call ordering, otherwise `setSessionConfigOption` could run before the session is reported to the server. The change in this task only swaps the value used in the body — call order and side-effect timing are unchanged.
  - **Bare-id-without-variant regression risk.** With no variant, the composed id equals the bare id, so the `ExistingSharedSessionWithDifferentRequestedModel_StartsNewSessionInsteadOfResumingOldModel` test (which asserts the bare id in the attach body) still passes after the `attachSessionToServer` change. Verified by running the full acp-agent suite — all 71 tests green.
  - **`unstable_setSessionModel` fallback also receives the composed id.** When `setSessionConfigOption` throws on the composed id, the fallback `unstable_setSessionModel({ modelId: requested.model })` call sees `provider/model:<variant>` too. The fake-agent test asserts this so a future regression that strips the variant on the fallback path would be caught.

- **Patterns / API shapes established**
  - **`RequestedModel` carries both `model` (composed) and `variant` (raw).** The composed `model` is what flows to opencode and to session-reuse keying; the raw `variant` is for diagnostics and the picker (T-005 does not consume the runner-internal `RequestedModel` type, but external log/event consumers do).
  - **`resolveRequestedModel` is the single composition point.** Any future path that needs the effective model id should call `resolveRequestedModel(context, agentConfig).model` rather than reconstructing `${model}:${variant}` itself. Today this includes `attachSessionToServer`, `applyRequestedModel`, and the session-reuse key in `runAcpWorkflowAgentSession`.
  - **Diagnostic context shape is `{ requestedModel, requestedVariant, requestedModelSource, ... }`.** New fields follow the existing pattern (snake_case, nullable via `?? null`). Adding `requestedVariant` does not break any current log consumer because the field is added at the end of the object.

- **Cross-task invariants**
  - The variant is *never* pre-validated against discovery before delivery (per D5 spec). The runner does not call `discoverOpencodeModels` from `applyRequestedModel`; an unsupported variant simply falls through to the existing try/catch. If a future task wants to add "skip delivery when discovery shows the model has no variants", it must NOT remove the existing try/catch — best-effort must remain the contract.
  - Session-reuse keying includes the variant suffix because the cache stores the *composed* id, not the bare model. Any future change that swaps the cache to a `{ model, variant }` struct must keep composing the id before comparing or it will silently break variant-aware reuse.
  - The runner does not persist variants; T-005 reads variants from `GET /api/projects/{id}/opencode/models` (server-side aggregation from `coderModelVariants`) and posts them through the issue/agent API, which already lands them in `vars.agent.variant` per T-003. T-004 only consumes `agent.variant` / `with.variant` at runtime; the persistence path is fully owned by the server side.
  - `agent.variant` and `with.variant` are independent inputs. `with.variant` is the explicit override surface used by per-stage dispatch; `agent.variant` is the persistent fallback. If both are set, `resolveRequestedModel` uses `with.variant` (matching how `with.model` overrides `agent.model` already in pre-T-004 code).

### Learnings for future tasks
- **Decisions made**
  - **Hide the picker, not disable it.** The spec says "Selectors hide the variant picker for models absent from modelVariants (no variants)"; `VariantPicker` returns `null` rather than rendering a disabled stub. The acceptance tests pin this (`expect(container.firstChild).toBeNull()` for empty / undefined variants), and a future "always render a disabled picker for accessibility" change would break them.
  - **`Default` option is mandatory.** Without a "clear variant" affordance, the user would have to switch model away and back to remove a stored variant. The `Default` row calls `onChange(null)`, not `onChange('')`, and the picker internally uses `__none__` as the Radix value to distinguish "default" from any real variant name.
  - **`resolveVariantAgainstModel` is a pure helper, not a hook.** The four spec scenarios ("show-only-supported", "hide-when-none", "refresh-and-drop-on-model-change", "show-stored") are all expressible as a pure function of `(stored, modelId, modelVariantsMap)`; pulling them out of the component lets the issue-level and per-stage surfaces share the same drop-stale logic without re-implementing it.
  - **`useAvailableModelIds` is consumed in four call sites.** `CreateIssueDialog`, `IssueModelSelector`, `AiSettingsSection`, and `SettingsSearch` all read the same TanStack query; updating the shape meant updating all four call sites plus three test fixtures. Future global model-list changes should grep for `availableModelIds?.models` and `useAvailableModelIds` together.
  - **Agent API + helpers without an editor.** The Agent CRUD types/functions exist and the helpers enforce the dependency invariant on the read + write paths, but no Agent editor UI exists yet. The 9-case `client.test.ts` pins the helpers' semantics so the future editor can be built without re-deriving the dependency rule.
  - **Mocks include `modelVariants`, not just `models`.** The four test setups (`SettingsPage.test.tsx`, `SettingsSearch.test.tsx`, `AiSettingsSection.test.tsx`, `CreateIssueDialog.test.tsx`) plus the two Playwright fixtures (`a11y/settings.a11y.spec.ts`, `e2e/settings-search.spec.ts`) all serve `modelVariants` now. Forgetting to update one would make the test pass without exercising the new code path.
- **Gotchas discovered**
  - **`useOpencodeModel` mutation signature change breaks every consumer in one go.** Before T-005 the mutation was `mutate(model: string)`; after, it's `mutate({ model, variant })`. `CreateIssueDialog` does not call it, but `AiSettingsSection` does — any future feature that imports `useUpdateOpencodeModel` must use the new payload shape.
  - **`ModelPresetSelect` resets the variant state on model change inside the menu.** The popover's `onClick` (per-row) and `handleKeyDown` (Enter) both call `onChange(modelId); onVariantChange(null)`. A future refactor that drops the `onVariantChange(null)` call would silently let stale variants survive a model swap.
  - **`VariantPicker` initial value is the `value` prop, not the `modelVariants` list.** The `triggerValue` is computed as `value && variants.includes(value) ? value : NONE_VALUE`; this means a stored variant the model does not support falls back to the `Variant` placeholder text rather than rendering a synthetic value. The acceptance test `falls back to the placeholder when a stored variant is not in the supported list` pins this; the test also confirms the picker doesn't *throw* on an unsupported value.
  - **`readAgentModelAndVariant` returns `{ model: null, variant: null }` for an agent config with only a variant.** A test asserts that `{ agentConfig: { variant: 'high' } }` returns `model: null, variant: null` (rather than leaking the orphan variant). Future Agent editor code should call this helper, not read `config.variant` directly.
  - **Stage-override UI in `IssueModelSelector` reads from `getIssueWorkflowVariables`, not from the `Issue` model.** The two are out of sync until `queryClient.invalidateQueries` re-fetches; both the model and variant writers must invalidate `['issues', issueNumber]` and `['issues']` to keep the read side fresh. The `useEffect` that hydrates `localWorkflowModel` / `localWorkflowVariant` / `localStageModels` / `localStageVariants` runs on `currentStageModels` change as a fallback so the prop-driven value still appears before the fetch completes.
- **Patterns / API shapes established**
  - **Shared UI: `VariantPicker` is the only place that knows about Radix Select internals.** All model selectors compose it; the `id` prop drives a `data-testid={id}-variant-trigger` attribute that the tests use. A new model selector can be added by following the same five-prop shape (`modelId`, `modelVariants`, `value`, `onChange`, `aria-label`).
  - **API contract mirrored at the entity layer.** `modelVariant` / `stageModelVariants` on the `Issue` model match the server DTO field names exactly; `agentConfig.variant` is the opaque-agent-config key the server reads. There is no transformation between API DTO and web model — the field names flow through unchanged.
  - **Agent helpers: read+write are inverse functions.** `readAgentModelAndVariant(readAgentModelAndVariant(x).value as any) === x` (within `{model, variant}`-preservation semantics) and `writeAgentModelAndVariant(current, ...readAgentModelAndVariant(current))` round-trips losslessly. Tests pin this for normal configs, empty configs, configs with only a model, and configs with only a variant.
- **Cross-task invariants**
  - **No variant without a model.** The web mirrors the server-side dependency invariant: a model picker change that produces `model: null` also produces `variant: null` (or no `variant` key on the wire); the per-stage set/clear handler drops the variant key in the same state update that swaps the model; `readAgentModelAndVariant` returns `{ model: null, variant: null }` for a model-less agent config. Future model-selector surfaces must follow the same rule.
  - **The picker never probes.** All variant data comes from `modelVariants` returned by the `/opencode/models` endpoint (server-side aggregation per T-002). If a future feature needs to know whether a model supports a specific variant, it should call `variantListFor(modelId, modelVariantsMap)` and check membership — never call `opencode` from the web.
  - **Bare `string[]` is gone from the web's model-list shape.** The wire format still ships `models: string[]` (per T-002 / D3), but every web consumer sees `{ models, modelVariants }`. Any future change that wants to add a third field (e.g. `displayNames`) must add it as a parallel sibling on the same object — never nest, never replace.

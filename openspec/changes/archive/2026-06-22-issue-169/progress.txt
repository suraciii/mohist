# Issue #169 — Productivity zone progress

## Codebase Patterns

- **Mocking TanStack Query hooks in tests:** to mock a hook (e.g. `useIssues`) whose value is consumed indirectly through a non-mocked hook (e.g. `useCompletionSnapshot` reads from `useIssues` internally), `vi.mock` must target the underlying source path — `vi.mock('../../../entities/issue/api/queries', ...)` — not the entity index `'../../../entities/issue'`. Mocking the entity index re-exports the wrapper but the non-mocked hook keeps the original implementation. This is a key gotcha for test isolation.

- **Per-section empty states live inside the section component:** each zone sub-component owns its own `data-state="empty"` block (no outer dispatcher). The `ProductivityZone` (T-005) just composes them — the zone is not blank when sources are empty.

- **`useCompletionSnapshot()` returns zeros in two distinct cases** (the data is `undefined` OR the list is empty OR all timestamps fall outside the trailing 7-day window). Sub-components that need to distinguish "no issues at all" from "no recent activity" must consult the underlying `useIssues()` data length, not just the snapshot's numeric values.

- **Dashboard slot wrapper contract:** `data-testid="dashboard-zone-<id>"` + `data-zone="<id>"` on the slot wrapper is stable across the productivity-slot swap (T-005). Inner content changes; the wrapper attributes do not.

- **Snapshot counts are not enough to detect "no issues"** — the snapshot hook returns `{0,0,0}` for both "no issues" and "no recent activity". Pair it with `useIssues()` to detect the empty-project case.

- **`fetchCompletionTrend` + `useCompletionTrend` colocated file:** both the client and the hook live in `packages/web/src/entities/issue/api/completion-trend.ts` (single-file pattern, matching the compact footprint of `client.ts`/`queries.ts`). The hook reads `projectId` from `useProject()`; the client is plain (`projectApiPath(projectId, '/issues/metrics/completion?bucket=week')`).

- **Mocking the completion-trend hook in component tests:** the pattern established in T-001/T-002 still holds — mock `'../../../entities/issue/api/completion-trend'` directly (not the entity index `'../../../entities/issue'`) so the indirect `useCompletionTrend` call inside `<CompletionTrend/>` is intercepted.

- **`useCompletionTrend` is safe to call without `projectId`:** the hook is `enabled: !!projectId`, so dashboard renders that haven't yet selected a project don't trigger a 400 from `projectApiPath`. This matches the gating pattern of the other completion/issue hooks in `queries.ts`.

## Task T-003: Completion trend section (endpoint consumer + inline SVG sparkline)

### What was implemented

- New `packages/web/src/entities/issue/api/completion-trend.ts` — exports `fetchCompletionTrend(projectId)` (calls `GET /api/projects/{ref}/issues/metrics/completion?bucket=week` via `request<>` + `projectApiPath`), `useCompletionTrend()` (TanStack Query hook reading `projectId` from `useProject()`; query key `['issues','metrics','completion','week', projectId]`; `staleTime: 60_000`; gated by `enabled: !!projectId`), and the `CompletionBucketPoint` / `CompletionTrendResponse` types matching the server DTOs (`{boundary, completed, failed}` buckets, `{from, to}` window, `bucket: 'week'`).
- New `packages/web/src/pages/dashboard/productivity/CompletionTrend.tsx` — a self-contained section component that renders an inline `<svg>` sparkline (120×40 viewBox, no axes chrome beyond a faint dashed zero baseline) over the `completed` counts of the returned weekly buckets. Plotted via `<polyline>` with one point per bucket in order; `safeMax = max(completed) || 1` keeps the geometry stable when every value is zero. Section exposes `data-testid="productivity-trend"`; wrapper conditionally carries `data-state="empty"`; the empty block uses `data-testid="productivity-trend-empty"`. The sparkline uses `data-testid="productivity-trend-sparkline"`, the polyline `data-testid="productivity-trend-polyline"`, and the baseline `data-testid="productivity-trend-baseline"`. A small `{N} weeks` meta line uses `data-testid="productivity-trend-meta"` for the count.
- New `packages/web/src/entities/issue/api/completion-trend.test.ts` — co-located hook test that mocks `useProject` + `useQuery` + the global `fetch`, asserting: (1) exact query key, (2) query key scopes to whatever `useProject()` returns, (3) `queryFn` issues `GET .../metrics/completion?bucket=week` (and never `bucket=day`), (4) `staleTime` is in the 30s–5min range, (5) `enabled` toggles correctly on `projectId` presence, (6) dense 12-week response is decoded into the typed shape.

### Learnings for future tasks:

- **Decisions made:**
  - Single file for client + hook (`completion-trend.ts`), matching the compact footprint of `queries.ts` + `client.ts` rather than splitting into two files. The hook is only ~12 lines and the client function is one line; a separate file would be overhead.
  - Used `safeMax = max(...) || 1` so that all-zero series still produce a valid (flat-at-baseline) polyline path. The empty-state guard in `<CompletionTrend>` then short-circuits to the labeled block, so the all-zero chart is never actually rendered. Both guards belt-and-braces: the math doesn't crash, and the user sees a meaningful empty state.
  - Query key shape `['issues','metrics','completion','week', projectId]` was hard-coded so the value `week` is part of the key — this is fine because v1 only ships `week`, but future T-005 work that adds a `day` view would want a separate key family. Worth noting in the codebase patterns if day bucketing ever becomes user-facing.
  - The polyline path is built once per `completedCounts` change via `useMemo`, so re-renders triggered by TanStack Query state changes (`isLoading`, `isFetching`) don't recompute geometry.

- **Gotchas discovered:**
  - SVG y-axis is inverted: higher y = lower on screen. The first `failed-only` assertion in the sparkline test had this flipped (expected `ys[0] > ys[2]` for completed `[2, 4, 1]`, but a higher `completed` value produces a *lower* y). Fixed by asserting the *minimum* y belongs to the largest completed value.

The hook's `enabled: !!projectId` guard must be set or the call will throw before the query layer even sees the request. Confirmed by following the same `enabled` pattern as `useIssueEvents`, `useIssueDiff`, etc. in `queries.ts`.
  - Mocking the entity index `'../../../entities/issue'` does **not** intercept the new `useCompletionTrend` import — same gotcha flagged in T-001. Component tests mock `'../../../entities/issue/api/completion-trend'` directly.
  - The pre-existing `MarkdownReader.test.tsx` failures (4 tests, `TypeError: Cannot delete property 'ResizeObserver'`) **pre-date** this task — confirmed by stashing T-003 changes and re-running. They are unrelated to T-003; do not be tempted to "fix" them here.

- **Patterns / API shapes established:**
  - Section styling matches T-001/T-002: `rounded-lg border border-border bg-card/50 p-4` with the `text-xs font-semibold uppercase tracking-wide text-muted-foreground` `h3` title.
  - Testid naming: `productivity-trend` (section), `productivity-trend-empty` (empty block), `productivity-trend-sparkline` (svg), `productivity-trend-polyline` (curve), `productivity-trend-baseline` (zero line), `productivity-trend-meta` (week count). T-005 can use `data-testid="productivity-trend"` plus `data-state="empty"` for the all-data-empty assertion.
  - Hook test pattern for `useQuery`-based hooks (mocking `useQuery` + `useProject` + the module's own exports) is now triplicated across `useIssueEvents` (queries.test.ts), `useCompletionTrend` (completion-trend.test.ts). Future metrics hooks (e.g. usage time-series when D lands) can follow the same shape verbatim.
  - Server DTO mirroring convention: a minimal client type (`CompletionBucketPoint` / `CompletionTrendResponse`) lives next to the hook that consumes it, and is re-exported through the entity barrel. No `zod`/`io-ts` schemas are introduced (matches the existing client.ts style).

- **Cross-task invariants:**
  - The productivity slot wrapper's `data-testid`/`data-zone` contract (T-005) is unchanged by this task. `<CompletionTrend/>` is a self-contained section that T-005 will compose alongside `<SnapshotRow/>` and `<EpicProgressList/>`.
  - No new server endpoint, controller, query, or persistence field — the only new files are in `packages/web/src`. Verified by `git status` (5 web-only files: 4 added, 1 modified).
  - No charting dependency added — `packages/web/package.json` is untouched. Confirmed by grep for `recharts|chart|victory|nivo|visx|d3`.

  - The wrapper deliberately **drops** the `border-dashed` class that `DashboardZonePlaceholder` carries — the filled zone uses `border border-border bg-card/50 p-4`, matching each section's own section styling. The test asserts `productivity.className NOT toMatch(/border-dashed/)` so the visual distinction is locked in.
  - The composition order (Snapshot → Epic → Trend → Investment) reads top-to-bottom as "headline number → work-in-progress → historical trajectory → optional cost-detail". This is the satisfaction-then-detail funnel called out in the issue's user voice.
  - The zone itself does **not** introduce any new testids beyond the single `productivity-zone` wrapper — every assertion about sub-sections uses the testids the four section components already own. The composition layer is testid-thin on purpose.

- **Gotchas discovered:**
  - The four sub-components each conditionally render `data-state="empty"` on their own `<section>` wrapper, **not** on the `productivity-zone` div. The all-data-empty test therefore asserts `snapshotEmpty.parentElement` (the section wrapper) has `data-state="empty"`, not the empty `<p>` itself. This matches the per-section-empty-state convention documented in T-001's progress entry.
  - The investment panel is collapsed by default, so the empty-state `<p>` is not in the DOM until the user clicks the toggle. The all-data-empty test must `fireEvent.click` the toggle *before* asserting on `productivity-investment-empty`. Easy to miss if you only check that the toggle exists.
  - `DashboardPage.tsx`'s existing zone map iterates an array; the swap was implemented as a ternary inside the `.map()` callback rather than extracting a separate map. That keeps the file small and the slot identity readable in one place, but it does mean future zone swaps would land in the same spot. If a second slot flips to filled, the ternary should be promoted to a `Record<DashboardZoneId, ReactNode>` to avoid growing the inline conditional.
  - The unused `DashboardZoneId` import is still needed for the `DASHBOARD_ZONES` literal type annotation, so it's not safe to remove even though we now bypass the placeholder for one of the four ids. Keeping the type here also documents that the zone id set is exhaustive over the four slot identities.

- **Patterns / API shapes established:**
  - Composition-root pattern: `ProductivityZone.tsx` is a 12-line index with one wrapper div and four sibling section components. No logic, no hooks, no data. The composition root is purely structural; every testable concern lives in its child.
  - `data-testid="productivity-zone"` is the canonical handle for the composition root — used by both the DashboardPage test (mounts-in-slot check) and any future integration test that wants to assert "the productivity zone is in the page" without naming each section.
  - The dashboard-shell slot identity contract (`data-testid="dashboard-zone-<id>"` + `data-zone="<id>"` on the slot wrapper, inner content free to change) is now exercised by both the existing slot-attribute test and the new mounts-the-zone test — future zone fills (Attention/Pulse/Digest) should follow the same two-assertion shape: (a) `data-testid`/`data-zone` still on the wrapper, (b) the new zone content is now inside the wrapper.
  - The "all-data-empty case renders four labeled empty states" assertion is the canonical regression check for design D8 (zone never blank). The next time someone adds a fifth section to the zone, they need to extend this single test (one more `expect(...).toBeInTheDocument()` block) — the test pattern is now the contract for "what does an empty Productivity zone look like".

- **Cross-task invariants:**
  - The four section components (T-001..T-004) keep their own testids and their own empty-state logic. T-005 adds zero new testids to them; the composition layer is purely additive.
  - No new server endpoint, controller, query, or persistence field — confirmed by `git status` (1 file added, 2 modified, all under `packages/web/`).
  - No new npm dependency — `packages/web/package.json` is untouched by this task.
  - `grep -nE "fetch|axios|useQuery" ProductivityZone.tsx` returns no matches — the zone owns no data fetch. All data is read indirectly via the four section component hooks (`useCompletionSnapshot`/`useIssues`/`useEpics`/`useCompletionTrend`).
  - The slot wrapper's `data-testid="dashboard-zone-productivity"` and `data-zone="productivity"` are preserved across the placeholder→zone swap. Any future zone fill (Attention/Pulse/Digest) MUST preserve the same wrapper identity contract; the slot testid is part of the dashboard-shell contract, not the productivity zone's.
  - The dashboard-shell spec scenario "Productivity slot renders zone content while other slots stay empty" is now satisfied by the new `DashboardPage` test ("renders the productivity zone content..."). The scenario "Zone slot identities are stable" remains satisfied by the existing slot-attribute assertions, which are unchanged.

## Task fix-tests: Fix failing build / typecheck

### What was the failure

- `npm run typecheck -w packages/web` reported `Cannot find module './DashboardZonePlaceholder' or its corresponding type declarations` from `DashboardPage.tsx:8-9` (two import sites).
- Root cause: the placeholder file was renamed/replaced with a new shared `DashboardZone` component (`packages/web/src/pages/dashboard/ui/DashboardZone.tsx`, exports `DashboardZone` and `DashboardZoneId`). T-005's hand-rolled productivity wrapper kept the same `data-testid`/`data-zone` contract but was never paired with an update of the import statement + the still-placeholder slots in `DashboardPage.tsx`. The other three slots (`attention`/`pulse`/`digest`) kept importing/rendering the now-missing `DashboardZonePlaceholder`.
- Bonus: `tsc -b` initially reported missing `@xyflow/react` and `dagre` modules, but those went away after `npm install --workspace packages/web` (these are declared in `packages/web/package.json` but weren't installed in the previous runner's workspace). Not caused by T-005 code, but worth knowing for future `fix-tests` runs: a cold workspace needs `npm install` first.

### Fix applied

- In `packages/web/src/pages/dashboard/ui/DashboardPage.tsx`: import `DashboardZone` (value) and `DashboardZoneId` (type) from `./DashboardZone` instead of `./DashboardZonePlaceholder`. Update the `<DashboardZonePlaceholder/>` render to `<DashboardZone/>`. The productivity slot keeps its hand-rolled `<section>` wrapper (border, no `border-dashed`) per design D2 + T-005's progress note — only the placeholder slots flip to the new shared `DashboardZone`.

- `npm run test:run -w packages/web` → 2051 passed, 1 skipped (2052 total) across 141 test files.

### Learnings

- **Always grep the new file before declaring the rename "done":** when a placeholder component is renamed, the rename must update *every* importer, not just the producers. A simple `rg DashboardZonePlaceholder` across the tree would have caught this at T-005 commit time.
- **`DashboardZone` (shared) ≠ `DashboardZonePlaceholder` (old):** the new `DashboardZone` is a generic wrapper that bakes in the `border-dashed` placeholder visual but accepts `children`. The productivity slot needs the *non-dashed* visual, so it stays as a hand-rolled `<section>` (matches the T-005 progress note exactly). Future zone fills (Attention/Pulse/Digest) can use `<DashboardZone>` + `children` directly if they want a unified look.
- **Workspace install drift can look like a code error:** the initial typecheck cascade included `Cannot find module 'dagre'` and `Cannot find module '@xyflow/react'` even though both are declared in `packages/web/package.json`. A cold workspace + node_modules that's missing packages produces typecheck errors that look like build errors but are really install drift. `npm install --workspace packages/web` resolved them.
- **Fix-tests is intentionally minimal:** the only diff in this task is 4 lines in `DashboardPage.tsx` (two import lines + one JSX element). No test changes, no new files, no spec changes. The test suite's failure was a missing module, not a wrong assertion — so weakening or rewriting tests would have been wrong.

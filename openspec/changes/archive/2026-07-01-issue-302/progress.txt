# issue-302 — Settings IA 重构 working memory

## Codebase Patterns

- 测试把侧栏的 `SidebarProvider`、`QueryClientProvider`、`ProjectProvider` 都包在 `MemoryRouter` 里渲染 SettingsPage（`SettingsPage.test.tsx:48-64`）。这条 helper 模式后续 T-003 改写 SettingsPage 后仍然适用。
- 测试不 mock `entities/settings` 的查询钩子（`useOpencodeRuntime`、`useAvailableModelIds` 等）。在 jsdom 下这些真实 fetch 会失败，AiSettingsSection 会进 `<SectionState variant="error|loading" />`。因此断言要避开依赖具体内容，改用稳定的结构性 selector（testid、tab `data-active` 等）。
- SettingsPage 的 `<Navigate replace>` 用 `toProjectPath('/settings/ai')` 计算目标 URL，会把当前项目名拼到 URL 前段（`useProjectPath` → `projectPath`，`ProjectContext.tsx:68-72`）。这意味着 redirect 后 URL 形如 `/selected-project/settings/ai`，route `<Route path="/:projectName/settings/:section">` 命中。
- 共享 UI 的 `Tabs` 是 `@base-ui/react/tabs`（`packages/web/src/shared/ui/components/tabs.tsx`），激活态是 `data-active`，不是 Radix 的 `aria-selected=...` 或 `data-state`。后续子导航的 `aria-current="page"`（spec 要求）要独立于这个 tabs 控件来加。
- Tabs 只有激活的 `TabsContent` 会渲染其子内容（panel 懒挂载），这影响"redirect → 默认渲染某个 section"的断言目标选择：不能依赖非激活 section 的内容。

## Gotchas / Decisions for downstream tasks

- **`SettingsSubNav` still works without changes**: its `groups` derive `label` from `s.label` (the same SOT entry), so the section heading and nav label are guaranteed to read the same string from the same field. No link update needed; visual parity is established by construction.
- **`SettingsSearch` does not need re-alignment**: search-result labels (`WORKFLOW_DESCRIPTORS`, etc.) are independent palette entries (e.g., `"Workflow Profiles"`, `"Project Default Workflow"`); they intentionally differ from the section heading when more specificity helps users find what they typed. T-004 already routes the result to the correct scope without touching labels.
- **Renaming `.test.ts` → `.test.tsx`**: vitest/vite honors the file extension for the transform; JSX in a `.test.ts` file emits a hard TS1005 "Expected '>' but found '/'" error from esbuild. Renaming is mandatory when adding JSX, harmless when reverting, and matches the convention already used by every other section-component test in the directory.
- **`getSectionMeta` is the only label source**: no section component should ever re-hardcode `title="..."` for the section-level heading. The `settings-consistency.test.tsx` aggregate import check will fail and the build will break loudly if a future PR regresses. Subordinate components (`CardSection`, `<h3>`, button labels) are free to use literal strings.
- **Descriptions are optional, not required**: SOT only carries a `description` for sections that previously had clarifying prose baked into the heading or adjacent `<p>`. Adding one to entries that don't need it would be filler noise; adding `<SettingsSection description>` with `undefined` is a no-op (component already guards with `{description && <p>...}`).

## T-001 (build) — IsUpdateEnabled explicit control-flow rewrite + specs

## Codebase Patterns

- **`SystemUpdateServiceSpecs.CreateService` factory** has two overloads (single `SystemInfoResponse` and `SequencedSystemInfo`). Both hardcoded `["Mohist:SystemUpdate:Enabled"] = "true"`. When adding an `Enabled` parameter, prefer **a new narrow overload** rather than touching the existing call sites — existing specs stay green without churn.
- **`InMemoryUpdateStore`** exposes `SavedStates` (List) and `TryAcquireLockAsync(jobId)`. Negative-side-effect assertions follow the pattern:
  - "no commands ran": `Assert.Empty(commands.Requests)`
  - "no state persisted": `Assert.Empty(store.SavedStates)`
  - "no lock held": `Assert.True(await store.TryAcquireLockAsync("job-next"))` — if the previous call had acquired it, this would return false.
- **`SourceAudit_*` pattern**: existing audits reuse `ReadSource()` + `FindMethodEnd(source, methodStart)` to slice out a method body, then run a regex/string assertion. `FindMethodEnd` finds the next `\n    (?:private|public|internal) ` (4-space indent) — works on top-level method definitions but would be confused by lambdas inside the method (no such lambdas in IsUpdateEnabled, fine).
- **Test trait convention**: every spec has both `[Trait(Traits.Speed.Name, Traits.Speed.Unit)]` and `[Trait(Traits.Sut.Name, Traits.Sut.System)]`. Missing the System trait would silently disable the test from default runs.
- **Server build enforcement**: `npm test` (via root) runs `npm test:ci` for server = `dotnet build Mohist.sln` with TreatWarningsAsErrors + `dotnet test`. So an unused `using` or unreachable branch will fail the gate.
- **`Enabled="false"` runtime fragility** (key insight from the issue): the original `isNullOrBlank || (parsed && enabled)` expression returns the *correct* `false` for `"false"` *by accident of operator precedence*. A SourceAudit spec is the only mechanism that can lock the structure — runtime tests pass against both the broken and correct forms for `Enabled="false"`. Verified by temporarily reverting the rewrite: 4/5 new specs still passed (gate behavior unchanged), only `SourceAudit_IsUpdateEnabledUsesExplicitControlFlow` caught it. This proves the audit's necessity.

## Decisions made during this task

- **Factory variant shape**: added `enabled: string?` parameter as a new overload rather than changing existing signatures. Existing `CreateService` calls continue to default to `"true"` (delegating to the new overload with `enabled: "true"`), preserving all prior specs as regression baselines.
- **Parity assertion structure**: the task says parity is asserted in spec, not by directly calling both `IsUpdateEnabled` methods (they're both `private` and have different signatures — `IsUpdateEnabled(InstallDetectionResult)` vs `IsUpdateEnabled()`). Parity is asserted via observable side effects on each path:
  - `Enabled="true"`: start path → reaches non-disable decision (verified by using `acquireLock: false` to produce `update_in_progress` instead of `update_disabled`).
  - `Enabled="false"`: start path → `update_disabled` (new spec); display path → disabled presentation (already covered at SystemInfoServiceSpecs.cs:99).
  - Unconfigured parity is intentionally excluded (defaults deliberately differ, per design.md D5).
- **SourceAudit regex**: rather than locking specific token sequences, the audit asserts:
  - the single-line precedence-dependent pattern `return IsNullOrWhiteSpace(...) || TryParse(...) && ...` is **absent** (catches direct regression to the original bug);
  - the presence-check `if (!string.IsNullOrWhiteSpace(` is **present** (locks the structure);
  - `bool.TryParse(` is present;
  - `return true;` is present (locks the explicit default).
  This tolerates harmless refactors (e.g. `string.IsNullOrEmpty` instead of `IsNullOrWhiteSpace`) since the audit locks the *shape* not specific tokens.
- **Theory for ordering test**: used `[Theory]` + `[InlineData]` to cover both `dirty-source` and `up-to-date` (no-update-available) scenarios in a single spec, asserting that the gate takes precedence over both later checks. Cleaner than two near-identical facts.

## Gotchas encountered

- **Audit false-positive avoidance**: when designing the single-line-precedence regex, used `return\s+` prefix to avoid matching the `if (!string.IsNullOrWhiteSpace(...))` body which also contains `bool.TryParse`. The body of the explicit form has no `return bool.TryParse(...) && enabled` on the same line as the IsNullOrWhiteSpace check, so the regex correctly skips it.
- **`SourceAudit_LogCapDefinedOnce` exists** and uses `\b200\b` — confirms the SourceAudit pattern is acceptable for stylistic invariants too.
- **No changes needed to `ValidateStart`**: confirmed the ordering (install-mode → gate → completeness → dirty-source → availability) was already correct; only the gate body needed rewriting. Re-verified by reading SystemUpdateService.cs:585-603.
- **`SystemInfoService.IsUpdateEnabled`** is structurally identical to the rewritten form (presence check → TryParse return → default return) but with a more elaborate default. Both are now safe-by-construction.

## Verification

- Before edits: ran the existing 56 specs in `SystemUpdateServiceSpecs` + `SystemInfoServiceSpecs` — all pass (regression baseline).
- After edits: 61 specs pass (56 baseline + 5 new: 2 `DisabledByConfig` + 1 Theory with 2 inline data + 1 SourceAudit + 1 ExplicitTrueEnablesGate).
- Full `npm test` (all 65 test files / 908 tests): all pass, exit 0.
- Server `dotnet build` with TreatWarningsAsErrors: 0 warnings, 0 errors.
- Negative-case verification: temporarily reverted `IsUpdateEnabled` to the single-line form and re-ran new specs. 4/5 passed (the runtime gate behavior was unchanged — confirming why the SourceAudit spec is essential). Only `SourceAudit_IsUpdateEnabledUsesExplicitControlFlow` correctly failed with `Assert.Empty() Failure: Collection was not empty` — proving the audit catches exactly the regression it's designed for.

# Issue #239 progress

## Codebase Patterns

### Entity layer hook tests (`src/entities/*/api/queries.test.ts`)

Standard pattern for testing react-query hooks at the entity layer:

1. `vi.mock('@tanstack/react-query', async (importOriginal) => ({ ...actual, useQuery: (...args) => useQueryMock(...args) }))` — replaces `useQuery` (and `useMutation`/`useQueryClient` if needed) with a `vi.fn()`.
2. `vi.mock('../../project/@x/project-context', () => ({ useProject: () => useProjectMock() }))` — replaces `useProject()`.
3. `vi.mock('./client', async (importOriginal) => ({ ...actual, <symbol>: (...args) => symbolMock(...args) }))` — replaces client calls with `vi.fn()`.
4. In `beforeEach`: reset all mocks; set sensible defaults (`useProjectMock.mockReturnValue({ projectId: 'proj-1' })`, `useQueryMock.mockReturnValue({ data: undefined, isLoading: false })`).
5. Each test sets up the mocks for its scenario, calls the hook, and inspects `useQueryMock.mock.calls[0][0]` for `queryKey`/`enabled`/`queryFn`, and/or invokes `config.queryFn()` to assert the underlying client call.

Reference implementations: `src/entities/issue/api/queries.test.ts`, `src/entities/issue-templates/api/queries.test.ts`, `src/entities/label-catalog/api/queries.test.ts`.

### Composing hooks on top of other hooks

When a hook is a thin derivation from another hook (e.g. selecting one field of the returned data), don't make a second API call. Just call the inner hook and pick the field. This shares the React Query cache, avoids duplicate network calls, and stays automatically in sync if the source query changes (e.g. when #238 changes the variant transport).

### Project-scoped settings queries

All `entities/settings/api/queries.ts` hooks that need a project scope use `useProject()` and set `enabled: !!projectId` so queries don't fire without an active project. The query key starts with the domain (`['opencode-model-ids', projectId]`, `['stage-models', projectId]`, `['config']`, etc).

## Decisions

### T-002 — `useModelVariants()` data-access hook

- Implemented as a thin derivation over `useAvailableModelIds()`: `const { data } = useAvailableModelIds(); return data?.modelVariants ?? {}`.
- Rationale: same React Query cache key (`['opencode-model-ids', projectId]`), so no duplicate network call; if #238 changes the variant transport, only `useAvailableModelIds` needs to change. The hook stays as the abstract data-access point.
- Returns `{}` whenever `data` is undefined (loading, error, no project, or `useAvailableModelIds` returning malformed data), so the hook "never throws when variant data is unavailable" — this is the safety property the task requires for merge-ahead-of-#238.
- Exported from `entities/settings` public API (`index.ts`), so callers in `IssueModelSelector`, `AiSettingsSection`, and `CreateIssueDialog` can import `useModelVariants` directly.

### Test coverage (5 cases)

1. Empty path when `data` is undefined → returns `{}`.
2. Loading state → returns `{}`.
3. Populated path → returns the same `modelVariants` map.
4. Data present but `modelVariants` is empty → returns `{}` (defensive against the `modelVariants: {}` default that `useAvailableModelIds` produces when the API omits the field).
5. Malformed data (data missing `modelVariants`) → returns `{}`, does not throw.
6. Reads from the same project-scoped `['opencode-model-ids', projectId]` query as `useAvailableModelIds` — guards against accidental drift if someone later refactors to a separate `useQuery`.

## Decisions

### T-003 — Variant-aware model selection in Issue detail (default + per-stage)

**T-001 was not committed in this workflow run.** The `model-variants.ts` helpers exist, but `ModelSelect.tsx` was still the pre-T-001 code with no `modelVariants` / `valueVariant` / `onChangeVariant` props and no `ModelVariantChips` subcomponent. T-003's acceptance criteria require rendering chips through the shared `ModelVariantChips` subcomponent and passing variant props to the shared `ModelSelect`, so as part of T-003 I implemented the minimum T-001 surface that the migration needs:

- `ModelSelect.tsx` now accepts optional `modelVariants`, `valueVariant`, `onChangeVariant` props. With no variant props supplied, the popover still renders exactly as before (additive, backward-compatible). The existing `ModelSelect.test.tsx` cases — including the pointerdown event delegation, keyboard Enter, search filter, and clear button — all pass unchanged.
- `ModelVariantChips` is exported as a separately importable subcomponent, with `data-variant-chip` / `data-variant-active` attributes and an optional `baseTestId` for stable test selectors.
- Inside the shared `ModelSelect` popover, model rows now render `ModelVariantChips` (only when the model has variants). Rows whose model has no variants render no chips and behave as before.
- Per-row click handling for the shared `ModelSelect`: the model body uses a delegated `pointerdown` handler at the list level (unchanged), plus `onClick` on the row. The chip's `onPointerDown` stops propagation so a chip click is not also treated as a body click.

**Bespoke `IssueModelSelector` default popover stays bespoke (Non-Goal preserved).** Recent-models / loading / error / fuzzysort all stay. Only the row markup (`ModelListItem`) is augmented with `ModelVariantChips` inline on variant-capable rows. The `ModelListItem` is a `<div role="button" tabIndex={-1}>` (a `<button>` would be invalid HTML since chips are nested `<button>`s).

**Variant persistence shape.** The existing `patchIssueWorkflowDefinitionVar` / `patchIssueWorkflowStageDefinitionVar` endpoints accept a per-key payload. Variants are sent alongside the model as `{ type: 'opencode', model: modelId, variant }`. Setting a model with default (no) variant sends `{ type: 'opencode', model: modelId }` (no `variant` key), matching the existing Issue-API contract used by `agentVariant()` and `stageVariantMap()`.

**Active variant source.** Read from the same workflow variables the model is read from: `agentVariant(variables.vars)` and `stageVariantMap(variables.stages)`, which decode `agent.variant` and `agent.variant` per stage from the `getIssueWorkflowVariables` response. The local `localWorkflowVariant` / `localStageVariants` state mirrors these and is updated optimistically after each patch.

**Per-stage wiring uses the same `handleSetStageVariant` for both model and variant changes.** This avoids a double-API-call that would happen if `onChange` (model body) wired `handleSetStageModel` while `onChangeVariant(null)` (the design's intended "clear variant on body click") also fired `handleSetStageVariant`. A single handler with `(stage, modelId, variant)` parameters, called from both `onChange` and `onChangeVariant`, keeps the API calls to one per user action. The `onChangeVariant` callback in the per-stage wiring guards on `variant && stageModel` so the implicit "null on body click" is a no-op there — the explicit `onChange(modelId)` already handled it.

**Testid patterns:**
- Bespoke popover chips: `data-testid="issue-coder-model-variant-${modelId}-${variant}"`.
- Shared `ModelSelect` chips (per-stage): `data-testid="${id}-row-${modelId}-variant-${variant}"` (e.g. `issue-stage-model-build-row-anthropic/claude-variant-high`). The `id` prop is forwarded to the trigger button as `id="..."`, so per-stage triggers are located via `document.getElementById('issue-stage-model-build')` in tests.
- Trigger button testids: `data-testid="issue-coder-model-trigger"` on the bespoke default-model trigger (added for stable test selection since the trigger's accessible name is the model text and varies).

**Settings visual consistency contract.** The `text-foreground/80` opacity token is forbidden in `ModelSelect.tsx` (settings-consistency test). The chip's inactive class uses `text-foreground` (no opacity) to stay compliant. The same change was applied to the bespoke `ModelListItem` row's non-selected class for consistency.

**Regressions guarded.** Pre-existing tests in `ModelSelect.test.tsx` (trigger display, popover selection, event delegation, keyboard Enter, search filter, clear button) all still pass with the new variant-aware component. The `settings-consistency.test.ts` "keeps ModelSelect aligned with settings text tokens" test still passes after removing `text-foreground/80`. The `AiSettingsSection.test.tsx` variant-picker cases still pass — `VariantPicker` is untouched and `AiSettingsSection` still uses it (T-004's job to migrate).

## Decisions

### T-004 — Variant-aware model selection in Settings AI defaults and Create Issue dialog

**AiSettingsSection migrated to the unified `ModelSelect`.** The previous `ModelSelect + VariantPicker` pair is collapsed into a single `ModelSelect` with `modelVariants={modelVariantsMap}`, `valueVariant={resolvedDefaultVariant}`, `onChangeVariant={handleSetDefaultVariant}` (default model) and the same three props on each per-stage `ModelSelect`. The trigger now displays `Model Name · variant` when a variant is selected (already supported by `ModelSelect`).

**Per-stage variant persistence keeps the existing semantics.** `handleSetStageModel` clears the variant when a new model body is clicked (sends `variant: null`). `handleSetStageVariant` is only invoked from the per-stage `ModelSelect`'s `onChangeVariant` callback, and it guards on `localStageModels[stage]` being set so the implicit `null` from a body click is a no-op there — the explicit `onChange` already handled it. Same single-API-call-per-action invariant as the per-stage wiring in `IssueModelSelector`.

**CreateIssueDialog uses a bespoke popover, not the shared ModelSelect.** Per design Q1 / T-003's pattern, only the `ModelListItem`-equivalent row is augmented with the shared `ModelVariantChips` subcomponent. The bespoke search/recent/loading/fuzzysort behavior is preserved.

**Bespoke popover row refactor: Button → div role="button".** The original row was a `<Button variant="ghost">` (a `<button>` element). Adding `ModelVariantChips` (nested `<button>` chips) inside it produces invalid HTML (`<button>` inside `<button>`) and DOM-nesting warnings. Following the `IssueModelSelector` pattern from T-003, the row became a `<div role="button" tabIndex={-1} data-model-id={...}>` with the same click / hover / highlight semantics. Chips continue to render only when `rowVariants.length > 0`; chip `onClick` stops propagation and dispatches `onChange(modelId) + onVariantChange(variant) + setPopoverOpen(false)` in one action.

**Chip click testid pattern (CreateIssueDialog):** `data-testid="create-issue-model-variant-${modelId}-${variant}"`, mirroring the `issue-coder-model-variant-…` pattern in T-003.

**Test mocks: order matters.** `arrangeLoaded()` sets `useUpdateOpencodeModelMock.mockReturnValue({ mutate: vi.fn() })` (a fresh `vi.fn()`). If the test wants to assert on the mutate call, it must set its own `mutateMock` AFTER calling `arrangeLoaded()`, otherwise `arrangeLoaded` overwrites it with an anonymous `vi.fn()` and the assertion sees zero calls. This was the root cause of two failing chip-click tests in the first test pass — `mutateMock` was set first, then immediately overwritten by `arrangeLoaded`. Order is now: `arrangeLoaded()` first, then `useUpdateOpencodeModelMock.mockReturnValue({ mutate: mutateMock })` (or `useSetStageModelsMock`) to inject the spy.

**`VariantPicker.tsx` and `VariantPicker.test.tsx` deleted.** Both surfaces now consume the unified `ModelSelect` (Settings) or the shared `ModelVariantChips` subcomponent (CreateIssueDialog). No remaining users of the standalone dropdown. The `variantListFor` / `resolveVariantAgainstModel` helpers that `VariantPicker.tsx` re-exported are already provided by `model-variants.ts`, which is the canonical home per design D3.

**`SettingsPage.test.tsx` updated.** The two tests that asserted on `settings-default-model-variant-trigger` (the standalone VariantPicker dropdown) were rewritten to assert on the trigger button text containing / not containing the stored variant suffix, matching the new chip-on-trigger behavior.

## Follow-ups (not in T-004 scope)

- The shared `ModelSelect` chip keyboard nav spec (D4 in design.md) — `→` into chip row, `Tab` into chip row, chip focus state machine — is still not implemented. T-001 owned this; the migration tasks (T-003, T-004) only covered chip click + body click semantics. The chip rows are reachable by Tab in current state but not via `→`/Enter semantics from a focused model row.
- The bespoke `IssueModelSelector` and `CreateIssueDialog` popovers remain bespoke. The shared `ModelVariantChips` subcomponent is the single source of chip UX across all three surfaces.
- The shared `ModelSelect` chip click semantics currently fire both `onChange(modelId)` and `onChangeVariant(variant)` for a chip selection. When the model is unchanged (the common case when picking a variant for an already-selected model) the `onChange` callback early-returns in `AiSettingsSection.handleSetOpencodeModel`, so the net effect is one mutation. When the model changes AND a chip is picked, two mutations fire (one for the model with `variant: null`, one for the variant). This matches the pre-T-004 two-control behavior and avoids a `selectModelAndVariant` signature change in the shared component.

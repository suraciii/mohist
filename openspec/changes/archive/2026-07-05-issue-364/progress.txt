## Codebase Patterns

- CLI poll-loop convention: `ServiceReadinessProbe` uses injectable `TimeProvider` (default `TimeProvider.System`), deadline via `_timeProvider.GetUtcNow() + timeout`, inter-probe delay via `Task.Delay(interval, _timeProvider, token)`. `RuntimeConsistencyValidator.PollForRunnerIdentityAsync` follows the same shape.
- Test fake time: `Microsoft.Extensions.Time.Testing.FakeTimeProvider` (already a transitive dep of CLI test project). `time.Advance(span)` advances the fake clock; `Task.Delay(span, time, token)` is satisfied by the advance. Tests that don't drive `time.Advance` while awaiting a polling task **deadlock** — this is a footgun for any new poll test (see Gotchas).
- The CLI test project uses `RecordingHttpHandler` (in `tests/Mohist.Cli.Tests/Support/`) which captures all requests in `Requests`. All polling tests assert on `handler.Requests.Count`.
- The `SourceCodeUpdaterVerifyRuntimeSpecs.cs` test builder passes the same constructor shape (http, executor, fs, env, output, getUserHome) — it picks up new optional params automatically, no edit required.
- `SourceCodeUpdaterVerifyRuntimeSpecs.cs` (in `packages/cli/tests/Mohist.Cli.Tests`) is the integration-level test that also calls `CheckRunnerIdentityAsync`. It uses the default 30s/500ms and a fake HTTP handler. Its existing `EndpointUnreachable_ReturnsWarn` and `IdentityAvailable_Passes` cases rely on the handler answering (or returning 503) synchronously without driving time. They still pass because: when the handler always returns 200 + identity, the loop returns on the first probe (no `Task.Delay` is ever awaited); when the handler always returns 503, the loop awaits `Task.Delay(500ms, TimeProvider.System, token)` which is a *real* 500ms delay — so the test waits ~30s real time. Pre-existing slowness, not a regression from this task. (Could be retrofitted with FakeTimeProvider in a follow-up; not in scope here.)

## Decisions

- For the loop semantics: chose the "non-null snapshot exits the loop regardless of hash content" approach (Decision 3 in design.md). The existing comparison block then handles empty-hash and mismatch as Warn, no further polling. This is the minimal change and matches the spec wording "a non-null identity whose buildGitHash is empty/whitespace yields Warn ... without continuing to poll further".
- For the "EndpointUnreachable" test: followed design.md's recommendation to **fold** the old `CheckRunnerIdentityAsync_EndpointUnreachable_ReportsWarn` into the new `CheckRunnerIdentityAsync_IdentityNeverAvailable_ReportsWarnAfterTimeout` spec. The folded test name is more accurate ("identity never registers within the bounded window") and the FakeTimeProvider+timeout combo works because the new test drives `time.Advance(timeout)` to satisfy the loop. The old test was retrofitted with FakeTimeProvider but never advanced it → would have deadlocked. Folding is the clean path per the design doc.

## Gotchas

- **FakeTimeProvider + async poll loop = must drive the clock.** A test that does `var result = await validator.CheckRunnerIdentityAsync(...)` with `FakeTimeProvider` and *no* `time.Advance(...)` will deadlock forever: the loop's `Task.Delay(interval, fakeTime, token)` registers a timer that only fires when the fake clock advances. The original retrofitted `EndpointUnreachable_ReportsWarn` test was in exactly this state and hung the entire `dotnet vstest` run. Two safe patterns for poll tests:
  1. Start the check task with `var checkTask = validator.CheckRunnerIdentityAsync(...)` (do not await), then `await Task.Yield(); Assert.False(checkTask.IsCompleted); time.Advance(span); var result = await checkTask;` — used by `IdentityNeverAvailable_ReportsWarnAfterTimeout`.
  2. Drive time probe-by-probe via `TaskCompletionSource` signals in the handler, then `time.Advance(pollInterval)` after each signal — used by `IdentityArrivesAfterNPolls_ReportsPass`.
  3. Make the handler answer on the first call (no polling happens, no `Task.Delay` is awaited) — used by `IdentityImmediatelyAvailable_ReportsPassWithoutDelay`.
- `dotnet test ...` (the wrapper) can hang silently when one test deadlocks. Prefer `dotnet vstest <dll>` against the built test DLL for tighter feedback. Use `--no-build` after a `dotnet build` to avoid double-build.
- The CLI test project's `SourceCodeUpdaterVerifyRuntimeSpecs.cs` has two test cases that rely on real 500ms delays (default 30s timeout, default 500ms interval, 503 handler → loop polls until timeout). They take ~30s real time. Not a regression from this task — but worth flagging for a future "all tests in default suite < 500ms" sweep.

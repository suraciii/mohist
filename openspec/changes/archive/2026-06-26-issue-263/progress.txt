# Issue #263 — Epic auto-start (build)

## Codebase Patterns

- **Feature directories**: `packages/server/src/Mohist.Server/<Feature>/{Domain,Grains,Services}`.
  Domain events live at `<Feature>/Domain/Events/`.
- **Tests mirror feature directories**: `packages/server/tests/Mohist.Server.Tests/Specs/<Feature>/{Domain,Api,Grain}`.
- **Domain aggregate**: `Epic` is a `sealed partial class` split across multiple files
  (`Epic.cs`, `Epic.Transitions.cs`, `EpicPriority.cs`, `EpicStatus.cs`).
- **Status string surface**: `EpicGrain.StatusName(EpicStatus)` /
  `EpicGrain.ParseStatus(string)` is the canonical mapper for `EpicStatus` ↔ DB row.
  `EpicStatus` is referenced by `EpicGrain` as `EpicStatusEnum` (alias).
- **Exceptions** for invalid transitions live in `EpicLifecycleExceptions.cs`. The grain
  maps them to HTTP 409 via `EpicRoutes`.
- **EF migrations**: `packages/server/src/Mohist.Server/Infrastructure/Data/Migrations/`
  prefix `YYYYMMDDhhmmss_<Name>.cs`. Production runs `db.Database.Migrate()` from
  `Program.cs`. Test fixture uses `WebApplicationFactory<Program>` so the same Migrate
  runs in tests. **Each migration also needs a `.Designer.cs` file** describing the
  model snapshot at that migration point — EF uses this to verify schema correctness
  on subsequent migrations. For data-only migrations the Designer can mirror the
  current ModelSnapshot verbatim.
- **Migration template**: minimal — `Up`/`Down` partials, raw SQL via
  `migrationBuilder.Sql(""" ... """)`.
- **Domain events**: `EpicEvent` union with records (`EpicCreated`, `EpicStatusChanged`,
  `EpicClosed`, etc.). `Epic.Transitions` records them; `EpicGrain.ApplyPendingEvents`
  drains them (e.g. `EpicClosed` removes linked issues).
- **Idempotent transitions**: existing `Pause()` on a paused epic is a no-op (early
  return). `Resume()` already has "if not paused, return" guard. These pre-existing
  behaviors already enforce idempotency at the domain layer — but the task asks
  Start/Pause/Resume to be idempotent at the GRAIN boundary (grain catches throws),
  which is a separate layer (T-002).

## Key implementation decisions (T-001)

- `EpicStatus` enum becomes `Idle, Running, Paused, Done, Closed`. `Active` is gone.
- `EpicStatusName.ToName(EpicStatus)` and `EpicStatusName.Parse(string)` move into
  the `Epic.Domain` namespace as static helpers — the grain keeps its own delegates
  but uses the same string set. Legacy `"active"` parses to `Idle`.
- Domain `Create()` sets status to `Idle`.
- New `Start()`: `Idle → Running` (else throw `EpicStartRequiresIdleException` for
  non-Idle non-terminal; `EpicAlreadyTerminalException` for done/closed).
- `Pause()` now requires `Running`; from `Idle` throws a new
  `EpicPauseRequiresRunningException`. From terminal throws `EpicAlreadyTerminalException`.
  From `Paused` is a no-op (preserves existing test).
- `Resume()` now targets `Running` (not `Active`). Only valid from `Paused`.
  From `Running` is a no-op. From `Idle`/terminal throws `EpicResumeRequiresPausedException`.
- `MarkDone()`: allowed from `Idle` and `Running` (preserves auto-done readiness for
  non-self-driving epics); from `Paused` throws `EpicPausedCannotMarkDoneException`
  (unchanged); from terminal throws `EpicAlreadyTerminalException`.
- `Close()`: unchanged — valid from any non-terminal state.
- Migration `20260625000000_EpicIdleRename.cs`:
  - `Up`: `UPDATE Epics SET Status='idle' WHERE Status='active';`
  - `Down`: `UPDATE Epics SET Status='active' WHERE Status='idle';`
  - No schema column change (the string set is enforced in code).
  - Designer file generated by copying current `MohistDbContextModelSnapshot.cs` —
    the migration is data-only so the model snapshot is identical.
- `EpicGrain.StartAsync()` (minimal): calls `domain.Start()` + persists + returns DTO.
  The full "Start + TryStartNext" autonomous progression is T-002. Added here because
  the existing HTTP pause/resume API tests need a way to reach `Running` before
  exercising the new (Pause requires running, Resume targets running) semantics.
- `EpicReconciliationService` candidate query updated: `idle OR running` (was `active`).
  This preserves auto-done readiness after migration for non-self-driving epics and
  lays the groundwork for T-003's running sweep.

## Gotchas

- `EpicGrain.Materialize` uses `ParseStatus(row.Status)`. Even after the migration
  runs, reading a row that still says "active" should parse to `Idle`. Belt-and-suspenders.
- The grain's `StatusName`/`ParseStatus` use `ToLowerInvariant`; the domain helpers
  must do the same.
- `EnsureNotTerminal` accepts the requested target status. For new lifecycle transitions,
  we need new exception types and the grain's status switch needs updating in T-002.
- The model snapshot won't change — only data is migrated.
- Each migration needs a `.Designer.cs` even for data-only changes; EF Core uses it
  to verify the model state at that migration. Copying the current
  `MohistDbContextModelSnapshot.cs` verbatim works since the model didn't change.
- HTTP integration tests need `IGrainFactory` access to call `StartAsync` directly
  (the `/start` HTTP endpoint is T-004). Without this, the existing pause/resume
  HTTP tests would fail because pause now requires a Running epic.
- The web frontend has its own `EpicStatus` enum (separate from server) — it's
  intentionally not updated in T-001; that work is T-006. The server returns new
  string values (`idle`, `running`) which the web enum currently doesn't model.
  This will need to be addressed in T-006. The web typecheck still passes because
  the enum is used in the web's own state machinery, not by direct comparison
  with server-side values.
- `EpicProgress.IsTerminal` short-circuits on `Done`/`Closed` strings — adding
  `Running` does not change its semantics. `Idle` and `Running` are both
  non-terminal; the existing `IsCompleted`/`IsTerminal(string)` helpers apply.

## Codebase Patterns (T-002)

- **Grain constructor DI**: when adding a new constructor argument
  (e.g. `ILogger<T>`), every test that constructs the grain directly
  (sqlite-backed unit specs) needs a matching argument — typically
  `NullLogger<T>.Instance` (imported from
  `Microsoft.Extensions.Logging.Abstractions`). Affected tests in this
  change: `EpicAutoDoneSpecs`, `EpicAutoDoneHandlerSpecs`,
  `EpicReconciliationServiceSpecs`. Existing `null!` for `IGrainFactory`
  stayed.
- **Grain instance property vs static helper class**: the EpicGrain
  defines a private `GrainKey` instance property; the static helper
  class with the same name lives in
  `Mohist.Server.Infrastructure.Orleans.GrainKey`. Inside EpicGrain,
  reference the static class with its fully qualified name
  (`Mohist.Server.Infrastructure.Orleans.GrainKey.Issue(...)`) to avoid
  the local property shadowing it.

## Key implementation decisions (T-002)

- `EpicProgress.SelectStartableNext` promoted from `private static` to
  `public static` so both the read-model (`EpicProgress.Build`) and
  the grain's new `TryStartNext` share identical selection ordering
  and cancel-skip semantics — no drift between "what the dashboard
  says is next" and "what the grain starts".
- `EpicGrain.ReconcileAfterTerminalAsync()` (new grain method) is the
  single reconcile entry point. Semantics:
  - Terminal/paused → no-op.
  - All linked delivered → mark done.
  - `running` → call `TryStartNext()`.
  - `idle` → no advance (not self-driving).
- `EpicGrain.TryStartNext()` (new private helper):
  - Bail if any linked issue is `in_progress` (serial slot occupied,
    covers the failed/blocked case).
  - `next = EpicProgress.SelectStartableNext(undelivered)`. If null
    → no-op (running-but-idle, `nextIssueReason` computed by the
    read model in the dashboard).
  - Call `IIssueGrain.StartWorkAsync()` via
    `GrainKey.Issue(next.Id)`. Exceptions are caught and logged; the
    epic remains `running` (running-but-idle) so the next reconcile
    retry can re-evaluate.
- `EpicGrain.StartAsync` is now `Idle→Running + TryStartNext`; if no
  startable issue exists, the epic is `running` (running-but-idle)
  with no error.
- `EpicGrain.ResumeAsync` calls `ReconcileAfterTerminalAsync()` after
  the paused→running transition so it auto-marks done when all
  linked issues are already delivered, or advances the next startable
  otherwise. This replaces the old `TryAutoMarkDoneAsync` call —
  `AutoMarkDoneIfReadyAsync` is still on the interface (T-003 will
  keep it for the legacy `IssueWorkCompleted` path; new wiring calls
  `ReconcileAfterTerminalAsync`).
- Idempotency at the GRAIN boundary: `StartAsync`/`PauseAsync`/
  `ResumeAsync` catch the four domain lifecycle exceptions
  (`EpicStartRequiresIdleException`, `EpicPauseRequiresRunningException`,
  `EpicResumeRequiresPausedException`, `EpicAlreadyTerminalException`)
  and return the current DTO. The domain stays strict (throws on
  invalid transitions); idempotency is a UX/API concern handled by
  the grain. HTTP error mapping in T-004 still translates terminal
  attempts to 409 `EPIC_ALREADY_TERMINAL`; pause-from-non-running
  becomes 409 `EPIC_NOT_RUNNING`.
- `EpicGrain.BuildLinkedIssueDtosAsync` was enriched: it now computes
  `CanStart` / `StartBlocker` per linked issue (using
  `Issue.CanStart(undeliveredPrereqNumbers)` and
  `Issue.StartBlocker(...)` + `IssueStartBlockerDto.FromDomain`)
  against the peer-set of undelivered issues. Without this, the
  shared `SelectStartableNext` would always see `CanStart=false` and
  return null, and `TryStartNext` would never start anything. The
  read-model (EpicQuerier → IssueQuerier.ListAsync) was already
  doing the equivalent for the dashboard; the grain now does the
  same locally so the selection works.
- The grain-to-grain call `IIssueGrain.StartWorkAsync` does NOT pass
  a `WorkflowProjectContext` — `IssueGrain.StartWorkAsync` resolves
  the project context itself via `IProjectGrain.GetAsync()`. The
  existing `IssueRoutes.Lifecycle` and `IssueRoutes.WorkflowControl`
  callers also call it with no argument. This addresses the
  T-002 note's design Open Question Q2.

## Gotchas (T-002)

- `EpicProgress.SelectStartableNext` is now public; the private
  `PriorityRank` helper inside `EpicProgress` is the same priority
  ranking the read model uses (p0=0, ..., p4=4, other=9). Don't
  introduce a duplicate ranking helper elsewhere.
- The "no startable issue" test case requires the issue's
  `IsDraft=true` so `Issue.StartBlocker(...)` returns a `Draft`
  blocker. Without that flag, a `Backlog` issue with no
  prerequisites is startable (`CanStart=true`).
- Updating the `EpicGrain` constructor signature forced updates to
  every test that constructs the grain directly. Going forward,
  prefer `IGrainFactory` mocks over direct `new EpicGrain(...)` so
  this doesn't repeat.
- `BuildLinkedIssueDtosAsync`'s `undeliveredPrereqNumbers` set uses
  `IssueStatus.Done | Cancelled` to mean "delivered-or-removed".
  This matches the existing EpicProgress semantics: cancelled issues
  are skipped, not undelivered-blockers.
- `ResumeAsync_IdleEpicThrowsResumeRequiresPaused` (old behavior:
  `EpicResumeRequiresPausedException`) was renamed to
  `ResumeAsync_IdleEpicIsIdempotentNoOpAtGrainBoundary` and now
  asserts the grain returns the current DTO. The domain method
  still throws — the test changed to reflect the new boundary
  contract.

## Test coverage added (T-002)

New `EpicProgressionSpecs` covers:
- Start advances first startable; running-but-idle when none
  startable; idempotent on already-running.
- Reconcile-on-done advances next; on done with all complete

- Reconcile-on-cancel (in-progress cancelled, slot cleared) advances

- Cancelled non-in-progress issue is skipped, next startable chosen.

## Key implementation decisions (T-003)

- `EpicAutoDoneHandler` (work-completed) keeps its public class identity
  and `[Subscription]` attribute for back-compat (HTTP routes / DI
  wiring reference the type by name in some legacy tests).
- Added a second public class `EpicClosedReconcileHandler`
  (`[Subscription(Type = "com.mohist.issue.closed")]`,
  `ICloudEventHandler<IssueClosed>`). Auto-discovery
  (`AddCloudEventHandlersFromAssembly`) picks it up the same way —
  no DI / registration changes needed.
- Extracted the CloudEvent extension parsing + epic lookup +
  grain call into an `internal sealed class
  EpicReconcileDispatcher`. Both handler classes hold one
  dispatcher instance; the dispatcher accepts the event-id,
  extensions dictionary, and a log-friendly event-type label.
  This avoids duplicating the `projectid`/`issueid` parsing
  and exception swallowing across the two handlers while
  keeping the surface area small (the dispatcher is package-
  internal — wiring concern only).
- `EpicAutoDoneHandler` now invokes
  `IEpicGrain.ReconcileAfterTerminalAsync()` instead of the
  legacy `AutoMarkDoneIfReadyAsync()`; the dispatcher calls
  the same method on both event types. The legacy method
  remains on the interface for now (no caller).
- `EpicReconciliationService` candidate query is
  `Status IN ('idle','running')` (was `active`); the per-epic
  invocation now calls `ReconcileAfterTerminalAsync()` (was
  `AutoMarkDoneIfReadyAsync()`). This widens the safety net
  to running epics that may have missed a terminal event.
- Test grain `RecordingGrainFactory` (in `EpicProgressionSpecs`)
  is the "real" EpicGrain executor — it produces the actual
  state transitions the new tests assert on. The
  `TestEpicGrainFactory` in the event-wiring specs only
  records that the grain was called; that test style keeps
  the wiring layer thin (no need to re-model TryStartNext
  in two places).

## Gotchas (T-003)

- The dispatcher needs a non-generic `ILogger` (not
  `ILogger<T>`) because it's reused across two handler types.
  Pass `NullLogger.Instance` in tests; the typed logger on
  the handler constructor is forwarded into the dispatcher
  via covariance (the typed logger implements the non-generic
  interface).
- `[Subscription]`-attribute discovery is reflection-based and
  case-sensitive on `Type` strings — the literal
  `"com.mohist.issue.closed"` must match what `IssueClosed`
  events are published as on the bus. Confirm with the
  publisher code path (`IssueGrain.CancelAsync` /
  `CloseAsync` consumers).
- The `BothHandlers_FireOnOutOfOrderTerminalSignals_Converge`
  test exercises the wiring only (records grain calls) — it
  asserts convergence via grain-call count, not epic-state
  readback, because the test grain doesn't model
  `TryStartNext` wiring. The end-to-end "converge to done"
  property is owned by `EpicGrain.ReconcileAfterTerminalAsync`
  (covered in `EpicProgressionSpecs`).
- `ReconcileOnceAsync_RunningEpicRepeatedSweeps_AreIdempotent`
  asserts `3` grain calls because the candidate query still
  includes the running epic on every sweep — idempotency is
  enforced inside the grain (it short-circuits no-ops on
  terminal/stable states), not by suppressing redundant
  sweeps. That matches the design's "missed event recovery"
  intent: repeated sweeps are safe and harmless.
- The auto-discovery loop in
  `AddCloudEventHandlersFromAssembly` runs once at DI setup;
  the two handler classes must both be present in the
  assembly at startup. Adding the new class file is enough
  — no registration edits.

## Codebase Patterns (T-004)

- **Domain vs grain boundary idempotency**: The domain's
  lifecycle methods (`Start()`, `Pause()`, `Resume()`) already
  short-circuit when the epic is already in the target state
  (`if (_status is EpicStatus.Running) return;` etc.). They
  only throw on genuinely invalid non-target transitions
  (`EpicPauseRequiresRunningException` for Pause-from-Idle,
  `EpicResumeRequiresPausedException` for Resume-from-Idle,
  `EpicStartRequiresIdleException` for Start-from-Paused) or
  terminal-state attempts (`EpicAlreadyTerminalException`).
  The grain does NOT need a try/catch wrapper to make the
  in-target-state case idempotent — the domain short-circuit
  already handles it. Previous T-002 code added try/catch
  wrappers that also swallowed the invalid cases; T-004
  removed those wrappers so HTTP can surface the rejections
  as 409.
- **Exception → HTTP mapping convention**:
  - `EpicAlreadyTerminalException` → `409 EPIC_ALREADY_TERMINAL`
    with `details: { currentStatus, requestedStatus }`. Applies
    to all three lifecycle commands.
  - `EpicPauseRequiresRunningException` → `409 EPIC_NOT_RUNNING`
    with `details: { currentStatus }`. (Spec called for
    `EpicNotRunningException`; the existing exception
    `EpicPauseRequiresRunningException` carries the same
    meaning, and a separate `EpicNotRunningException` would
    be a near-duplicate.)
  - `EpicResumeRequiresPausedException` → `409
    EPIC_RESUME_REQUIRES_PAUSED` with `details: { currentStatus }`.
  - `EpicStartRequiresIdleException` → `409
    EPIC_START_REQUIRES_IDLE` with `details: { currentStatus }`.
- **Test conflict resolution**: T-002 unit tests
  (`PauseAsync_IdleEpic_IsIdempotentNoOpAtGrainBoundary` and
  `ResumeAsync_IdleEpicIsIdempotentNoOpAtGrainBoundary`)
  asserted the grain returned the current DTO for Pause-from-
  Idle / Resume-from-Idle. T-004 inverted those expectations
  to match the spec ("Pause rejected on non-running epic"
  must be surfaced, not absorbed) — those tests now
  `Assert.ThrowsAsync` the appropriate exception. Renamed to
  drop the "Idempotent" suffix.
- **`Issue` creation in integration tests**: An issue is a
  draft by default. To mark it Done (or complete it via the
  workflow grain), you must create it with `isDraft = false`.
  The `CompleteIssueAsync` helper added to `EpicApiSpecs`
  uses `IIssueGrain.StartWorkAsync` + `CompleteWorkAsync`
  with a fresh `WorkflowProjectContext`.
- **Resume-on-running with no undelivered issues auto-dones**:
  The shared `ReconcileAfterTerminalInternalAsync` path
  short-circuits the in-progress check when `undelivered.Count == 0`
  and calls `domain.MarkDone`. So a Resume test that starts
  the epic on an empty epic will see `status="done"`, not
  `status="running"`. Tests that exercise Resume idempotency
  on a running epic MUST seed at least one undelivered
  linked issue to keep the epic in `running`.
- **`ConflictEnvelope.Details` shape**: `EpicApiSpecs` had
  only `Success/Code/Error`. T-004 added an optional
  `ConflictDetails(CurrentStatus, RequestedStatus?)` to
  read the structured `currentStatus` / `requestedStatus`
  payload that the routes emit. Other specs (e.g.
  `EpicLifecycleSpecs`) use their own `ConflictDetailsDto`
  with `UndeliveredCount` — duplicate types are fine, each
  spec is self-contained.

## Key implementation decisions (T-004)

- **`POST /api/projects/{projectRef}/epics/{id}/start`**: New
  route `StartRouteAsync` calls `EpicGrain.StartAsync()`.
  Maps `EpicStartRequiresIdleException` → 409
  `EPIC_START_REQUIRES_IDLE` (e.g. start-on-paused) and
  `EpicAlreadyTerminalException` → 409 `EPIC_ALREADY_TERMINAL`.
- **`POST /pause` semantics update**: Pause from a non-running,
  non-terminal epic (Idle) now propagates
  `EpicPauseRequiresRunningException` → 409 `EPIC_NOT_RUNNING`.
  Pause from terminal (Done/Closed) → 409 `EPIC_ALREADY_TERMINAL`.
  Pause from Running → 200 `paused` (with reason persisted).
  Pause from Paused → 200 `paused` no-op (domain short-circuit;
  the existing pause reason is preserved).
- **`POST /resume` semantics update**: Resume from a non-paused,
  non-terminal epic (Idle) now propagates
  `EpicResumeRequiresPausedException` → 409
  `EPIC_RESUME_REQUIRES_PAUSED`. Resume from terminal
  (Done/Closed) → 409 `EPIC_ALREADY_TERMINAL`. Resume from
  Paused → 200 `running` (and re-evaluates via
  `ReconcileAfterTerminalInternalAsync`, which may auto-done
  if readiness is satisfied). Resume from Running → 200
  no-op.
- **Grain simplification**: The `IsLifecycleIdempotencyException`
  helper was removed; `PauseAsync`/`StartAsync`/`ResumeAsync`
  no longer wrap their domain calls in try/catch. The
  domain's existing in-target-state short-circuits provide
  the idempotency, and the invalid cases propagate cleanly.

## Gotchas (T-004)

- **`IssueDto` does not require `isDraft = false` for
  linking to an epic** — the link endpoint accepts drafts.
  But the workflow-grain `StartWorkAsync` rejects drafts
  with `IssueStartBlockedException`. Tests that need to
  complete an issue via the workflow grain must explicitly
  set `isDraft = false` at creation.
- **`Start_OnRunningEpic_IsIdempotentNoOp200` setup**:
  starting an empty epic and then calling Start again
  works as a no-op because the second Start hits the
  domain's `if (_status is EpicStatus.Running) return;`
  short-circuit without touching the DB.
- **`Resume_OnAlreadyRunningEpic_IsIdempotentNoOp200`
  setup** must seed at least one undelivered linked issue,
  otherwise `ReconcileAfterTerminalInternalAsync` will
  auto-mark-done (because the empty-epic readiness check
  passes), and the test will see `status="done"`.
- **Removing the try/catch wrappers in EpicGrain** was a
  behavior change relative to T-002's grain — earlier
  task notes warned that "API/CLI callers see a stable
  200 for an already-not-running epic", which the spec
  now overrides. The unit-test renames (`PauseAsync_IdleEpic_*
  ThrowsEpicPauseRequiresRunning`,
  `ResumeAsync_IdleEpic_ThrowsEpicResumeRequiresPaused`)
  make the new contract loud at the grain-test layer too.
- **HTTP idempotency for already-in-target-state** is
  preserved via the domain's short-circuit, NOT via the
  grain's exception handler. So the grain's exception
  surface is "strict" (it propagates the spec-mandated
  409s), and the HTTP layer can confidently map each
  exception type to a single error code.

## Codebase Patterns (T-006)

- **Web tests use `vi.hoisted` mocks**: All hook mocks in
  `EpicDetailPage.test.tsx` and the entity-level `queries.test.tsx`
  live in a top-level `vi.hoisted(() => ({ ... }))` block so the
  same `mocks` reference is shared between the test cases and the
  `vi.mock(...)` factory passed to vitest. Per-describe `const
  addMutate = vi.fn()` etc. are local re-bindings wired into the
  shared mock via `mocks.useFoo.mockReturnValue({ mutate: addMutate,
  isPending: false })`.
- **Header `StatusBadge` color map**: The `Record<EpicStatus, string>`
  mapping in `StatusBadge` is the source of truth for status
  colors. Adding a new enum value (e.g. `Running`) requires
  updating this map AND the parallel `labels` map in
  `EpicListPage.StatusBadge`.
- **Lifecycle action buttons in the header** are emitted as
  independent `Button` elements keyed off `isIdle` / `isRunning` /
  `isPaused` flags. The new `start-epic-trigger` testid sits
  alongside the existing `pause-epic-trigger` /
  `resume-epic-trigger` testids. The default button variant is
  primary (`bg-primary`), matching the spec's "primary action"
  requirement for `idle`.
- **Mark Done "blocked" tooltip**: The existing `markDoneBlocked`
  guard was previously `isPaused || (epic.status ===
  EpicStatus.Active && !epic.progress.readyToMarkDone)`. The
  `Active`-renamed-to-`Idle` refactor generalizes it to
  `isSelfDriving = isIdle || isRunning` so the mark-done hint
  surfaces for both idle and running epics.
- **Epic list / dashboard "active" filter**: `EpicListPage` and
  `EpicProgressList` previously filtered by `status ===
  EpicStatus.Active`. After the rename, they both filter by
  `status === EpicStatus.Idle || status === EpicStatus.Running`
  (with `isInProgressEpic(epic)` as a named helper in
  `EpicProgressList.tsx`).
- **Legacy `'active'` server-side values are defensively mapped
  to `Idle`** via `parseEpicStatus(value)` in
  `packages/web/src/entities/epic/model/types.ts`. Any caller
  that needs to consume a server-supplied epic status string
  should go through this helper rather than casting to
  `EpicStatus`.
- **`useStartEpic` invalidates two query keys on success**:
  `['epics']` (the list) and `['epics', projectId, id]` (the
  project-scoped detail). The pattern matches `usePauseEpic` /
  `useResumeEpic`. `useStartIssue` is the only one that
  additionally invalidates `['issues']`.

## Key implementation decisions (T-006)

- **`EpicStatus.Active` was renamed to `EpicStatus.Idle`** and

## Gotchas (T-006)

- **Mocked mutate calls don't trigger React Query
  invalidation.** When `vi.mock('../../../entities/epic', ...)`
  replaces `useStartEpic` with `{ mutate: vi.fn() }`, the
  `onSuccess` registered in the real `useMutation` is bypassed.
  The mocked `mutate` function receives only what the caller
  passed (`mutate(epicId)`), so any "refresh after success"
  test pattern needs to either:
    1. Call `options?.onSuccess?.()` from inside the mocked
       mutate (the existing edit-flow test pattern), OR
    2. Rely on the `queries.test.tsx` tests to verify
       invalidation behavior separately.
  Without this, the component never re-renders with the new
  data, so the post-mutation UI state assertion times out.
  We use approach (2) for the Start Epic refresh tests; the
  mutation call shape is verified in `EpicDetailPage.test.tsx`,
  the invalidation behavior is verified in
  `queries.test.tsx`.
- **`'active'` literal in epic test fixtures** is intentionally
  kept in some `Record<string, unknown>` typed epic test
  objects (it bypasses the enum typing because the object
  shape is open). The `parseEpicStatus` helper is what reads
  these strings at runtime; the enum value `EpicStatus.Active`
  was the only place this name could leak into types.
- **The `linked issues view toggle` describe block doesn't set
  `mocks.useStartEpic`** because none of its tests exercise the
  lifecycle header. Adding a stub `useStartEpic` mock there is
  not needed (the global `vi.mock` factory handles the import).
  The unused-variable lint warning surfaced the redundant
  `const startEpicMutate = vi.fn()` declaration that was added
  by an earlier draft.
- **`parseEpicStatus('active')` returning `Idle` is what keeps
  the web UI from breaking on any leftover server rows** that
  may still have the legacy `active` status — even though the
  T-001 migration updated the DB rows, the helper is the
  belt-and-suspenders for any cached/queued event payloads that
  might still carry the old string.

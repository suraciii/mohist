## Codebase Patterns

- `IssueQuerier.GetDeliveryTimesAsync` is the model for the windowed metrics surface:
  scope by `db.Issues.AsNoTracking()` filtered on `ProjectId`, materialize the
  `IssueReadModel` via `IssueRowMapper.ByNumber` + `ToReadModel(ToInfo(...))`,
  filter in memory on `CompletedAt`, and aggregate.
- For cross-run stage events reuse the `GetQualityAsync` pattern: scan
  `IssueEvents` for `IssueWorkStarted` payloads to harvest every historical
  `workflowRunId`, union with each issue's current `issue.WorkflowRunId`, then
  load stage events by those run sources.
- The existing `LoadWorkflowRunEventFactsAsync` selects
  `Source/Id/Type/Data` only AND filters by `QualityWorkflowEventTypes`
  (which omits `StageCompleted`). For stage-duration aggregation a separate
  loader is required that selects `Source/Id/Type/Time/Data` over BOTH
  `StageStarted` and `StageCompleted`.
- `LoadWorkflowStatesAsync(db, issues)` takes `IReadOnlyCollection<IssueReadModel>`,
  not `Domain.Issue`. Use `ToReadModel(ToInfo(issue, project: null,
  projectDefaultTemplateId, disabledIds))` to materialize the read model.
- The approval-wait definition reuses
  `MohistDefaultWorkflowProjection.StageApprovals(workflow)` — exactly the
  same projection `GetApprovalWaitAsync` uses. Pending (`awaiting`) approvals
  have no `RespondedAt` and contribute nothing.
- `WorkflowRunEventPersistence.WorkflowRunSource(runId)` builds the
  `/mohist/workflow-runs/{runId}` source URI; the seed helper
  `SeedWorkflowRunEvent(db, runId, seq, type, time, data)` already uses it.
- The integration fixture's `MohistIntegrationFixture.TimeProvider` is a
  `FakeTimeProvider` — call `_fixture.TimeProvider.SetUtcNow(...)` in a test
  to pin the injected clock. The new endpoint reads `timeProvider.GetUtcNow()`
  so injected-clock windows are testable.

## Task-Specific Decisions / Gotchas

- The `IssueQuerier.StageDurationResult` records were added next to
  `DeliveryTimeResult` so the new public surface matches the existing naming
  pattern. The `StageDurationWindow` record is purely informational (the
  route also exposes it as a DTO for caller convenience).
- Latest-attempt-per-stage pairing uses `(Time, Id)` sort on the merged event
  stream. We take the latest `StageStarted` per stage id and pair it with the
  latest `StageCompleted`. A stale completion that precedes the latest start
  is ignored (`completedAt < startedAt` skip). This satisfies
  invalidate-on-restart without needing stage-definition awareness.
- The stage order is resolved from the project's effective workflow profile
  via `EffectiveWorkflowProfileResolver` + `IssueWorkflowProfileRegistry` +
  `WorkflowDefinition.Stages`. The fallback `QualityStageOrder`
  (`["plan","build","check","integrate"]`) is what the seed helpers naturally
  exercise.
- `MohistDbFixture` does not host an Orleans silo, so approval projection
  semantics rely on `WorkflowRuns.State` JSON being parseable by
  `WorkflowStatusMapper.BuildStatusView(run, definition: null)`. Test seeds
  use `ApprovalRunState` (single approval) and `MultiApprovalRunState` (two
  approvals) helpers that already match the production shape.
- The unit-spec `SeedDeliveredIssue` helper now takes an optional
  `workflowRunId` parameter; the stage-duration tests that exercise
  approval-wait / flow-efficiency logic must populate it so
  `LoadWorkflowStatesAsync` resolves the run.
- Tests use `now.AddDays(-2)` etc. relative to a fixed `now`; the fixture's
  `FakeTimeProvider` clock is anchored at `2026-06-30T00:00:00Z`, so any
  `DateTimeOffset.UtcNow` inside the route resolves to that anchor during the
  integration tests unless explicitly advanced.
- `approvalGateWait` is summed as `(RespondedAt - RequestedAt).TotalSeconds`,
  matching `GetApprovalWaitAsync`. Negative waits are filtered out (`if (wait > 0)`).
- The cycle-decomposition sum invariant is taken verbatim from the spec:
  `activeWork = Σ stages − approvalGateWait`, `inactiveGap = cycle − Σ stages`,
  `activeWork + approvalGateWait + inactiveGap == cycle`. We do not clamp — the
  spec language ("by construction") prefers the formula value even if it goes
  negative (the edge case is when approval wait exceeds Σ stages).
- Route registration follows the order:
  `MapIssueMetrics`, `MapIssueApprovalMetrics`, `MapIssueQualityMetrics`,
  `MapIssueDeliveryTimeMetrics`, `MapIssueStageDurationMetrics`.
- Two pre-existing `DetailAsync_*` tests (`DetailAsync_ArchivedIssue_ExposesSameCompletedAt`,
  `DetailAsync_ForCancelledIssue_IncludesCompletedAt`) were failing on master
  before this task (verified via `git stash`). They are unrelated to the
  stage-duration change.

## Task-Specific Decisions / Gotchas (T-002 web widget)

- `ChartAxes` is a **vertical-axis-only** primitive (its `AxisTick` type only
  carries `y`). A horizontal x-axis must be rendered locally inside the
  chart, mirroring how `CycleTimeChart` keeps `PercentileOverlay` local. The
  `StageDurationChart` does this via a local `ChartHorizontalAxis` component
  with `data-testid="chart-axis-bottom"`; tests for it should target that
  testid, not the vertical `chart-axis-left`/`right`.
- `ChartLegend` requires **two or more** entries to render (`if (entries.length <= 1) return null;`).
  When the resolved chart legitimately has a single visual element, the
  legend will be absent — pass an empty array or render an alternative.
- Bar motion follows the `BarSeries` precedent: `transform: scaleX(ratio)`
  with `transform-origin: left` (the bar's `x` in px). The whole bar
  geometry is rendered locally inside `StageDurationChart` (no
  `HorizontalBarSeries` was added to the shared kit) — only one consumer,
  matches `CycleTimeChart`'s `PercentileOverlay` precedent and the
  `dashboard-charts` "Modified Capabilities: None" constraint.
- The `stage-duration` query hook follows the `useDeliveryTime` /
  `useApprovalWait` pattern verbatim: `queryKey` includes `projectId`,
  `staleTime: 60_000`, `enabled: !!projectId`. The hook reuses
  `request<T>` / `projectApiPath` from `shared/api/client`, so any 4xx/5xx
  with `{ success: false }` automatically rejects the query and surfaces
  `isError: true` — the widget routes that through `ChartContainer`'s
  error state without bespoke error handling.
- The lens toggle is the `LensToggle` segmented control
  (`role="group"`, `aria-pressed`) identical in shape to
  `CycleTimeChart`'s. Both lenses are sourced from the **single**
  `useStageDuration` read; switching the lens only mutates local
  `useState<DurationLens>`, never issues a second fetch.
- Stage order comes from the surface's `stages[]` order — the backend
  contract orders by workflow stage order, so the widget does not need
  to re-sort.
- `prefers-reduced-motion` is honored by routing the `transition` style
  to `'none'` when `useReducedMotion()` returns true. Tests stub
  `window.matchMedia` to control this.
- `tabular-nums` is applied to every numeric label (axis ticks, value
  labels, ratio, wait-breakout) for digit alignment, matching the
  precedent in every existing chart.

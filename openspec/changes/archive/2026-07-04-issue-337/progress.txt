## Codebase Patterns

- **Publisher pattern (sibling, not reuse)**: `ITranscriptEventPublisher` / `SignalRTranscriptEventPublisher` is the template. To add a sibling, mirror the same constructor shape (`IHubContext<MohistHub, IEventsClient> hub, ConnectionSubscriptionRegistry registry, ILogger<...> log`), same iterate-connections / per-send try/catch, but use a different envelope type and a different `IEventsClient` method. Domain-bus route (`IEventPublisher` / `EventBridge`) is explicitly avoided for runtime data.
- **`ConnectionSubscriptionRegistry`** is a `Singleton` (registered through `ISingletonService`) so the hot path is in-process; it holds three parallel maps keyed by `connectionId`: `_byConnection` (event types), `_byConnectionProjectId` (project affinity), `_byConnectionTaskLog` (added in T-002 — `(workflowRunId, taskId)` scope set per connection). `RegisterConnection` / `UnregisterConnection` maintain all three atomically; map additions follow the same shape as the existing `projectId` affinity map.
- **`IEventsClient` lives on `MohistHub.cs`** alongside the hub class. To add a third method (T-002: `OnTaskLogDelta`), add it to the interface, the hub class, and every `RecordingEventsClient` test stub that implements `IEventsClient` — search for `IEventsClient` implementations in the test project (system-specs and events-specs subfolders both have one).
- **Test `RecordingHubContext` shape**: there's an established pattern in `TranscriptEventPublisherSpecs.cs` that creates a fake `IHubContext<MohistHub, IEventsClient>` whose `Clients.Client(connectionId)` returns a per-connection `IEventsClient` recording each call. T-002's `SignalRTaskLogDeltaPublisherSpecs` reuses the same shape and extends it with per-connection fault injection via `FailOnConnectionId`.
- **Phase 1 conventions**: `TaskLogStore.AppendAsync` does delete-then-insert on every call (T-001 will swap to insert-or-ignore-by-seq). `TaskLogService.AppendAsync` is the single facade the API layer talks to (architectural rule: API → Services, not API → Infrastructure.Data). The service is registered `Scoped`; the store is `Scoped`; `RunnerWorkStore` and `WorkflowRunQuerier` are `Scoped` too.

## Decisions / Gotchas

- **`workId → taskId` resolution**: `RunnerWorkStore.FindAsync` returns a `RunnerWork` that does NOT carry a task id — only `RunnerId/OwnerKind/OwnerId/WorkId/TakenAt/Status/...`. So the resolver falls back to `WorkflowRunQuerier.LoadAsync(workflowRunId)` and walks `run.Stages[*].Tasks[*]` for `task.WorkId == workId`. Cached per `(ownerId, workId)` in a static `ConcurrentDictionary` so a long-running task reuses one mapping across many flushes; negative results (work item not in run, or run not loaded) are also cached as `string.Empty` to keep the hot path free of repeated lookups.
- **Owner-kind guard**: `ResolveTaskIdAsync` short-circuits to `null` when `ownerKind != "workflow"`. Agent-job owner kinds carry no task mapping; `OnTaskLogDelta` then stamps `taskId = null` and the publisher's scope gate treats that as "no fan-out".
- **Channel separation enforcement**: the publisher stub's `RecordingEventsClient` implements `IEventsClient` and captures each call into a separate list (`TranscriptMessages` / `TaskLogDeltaMessages`). This physically proves channel isolation in tests: a transcript publish never shows up in the task-log list and vice versa (added one cross-channel test in `TranscriptEventPublisherSpecs`).
- **Per-send failure isolation**: matching `SignalRTranscriptEventPublisher`'s shape, the publisher wraps each `await clients.Client(id).OnTaskLogDelta(...)` in try/catch and logs to `ILogger.LogWarning`; one failing client never aborts the rest. Verified by a test that injects a throwing client.
- **Type AND scope**: `ShouldNotifyTaskLog` checks BOTH dimensions — type-subscription must contain `task-log.delta`, AND the per-task scope set must contain the delta's `(workflowRunId, taskId)`. A connection missing either filter rejects the delta. Verified by separate unit tests for each axis.
- **`SubscribeTaskLogAsync` also adds the type marker**: when the Web calls subscribe-by-task, the hub also adds `task-log.delta` to the connection's type-subscription set and mirrors it on the durable `IConnectionSubscriptionGrain` so reconnect replay re-asserts the type. The per-task scope itself is intentionally NOT durably stored — the Web re-asserts it via its `onreconnected` callback, matching design D5's preference for Web-driven reconnect state (no new grain state).
- **`TaskLogDeltaSubscription.TaskLogDeltaSubscriptionType = "task-log.delta"`** is the canonical type marker the Web includes in its `SetSubscriptionsAsync` list when it wants live task-log fan-out. Distinct from transcript event types so the two channels stay physically separate.
- **Existing test stubs broken by interface change**: when adding a method to `IEventsClient`, every `RecordingEventsClient` implementation across the test project needs a corresponding no-op (or recording) override. Search across `packages/server/tests/**/*.cs` for `IEventsClient` to find all of them.

# T-003 Progress

## Codebase Patterns

- **Collector = single source of truth for captured lines.** The sink (`TaskLogger.write`) still masks BEFORE append (Phase 1 invariant) and assigns a monotonic `seq` (Phase 1 invariant). The host owns the collector instance for the work item lifetime and pre-creates it in `executeAndReport` (not the executor) so the trigger can wire `setAppendListener` before any appends happen.
- **`TaskLogCollector.setAppendListener(fn|null)`** is the post-construction hook the host uses to count newly-captured lines. The listener is invoked synchronously from inside `append` AFTER the entry is buffered, so a trigger that drains immediately observes the new line. Pass `null` to detach (used right before stopping the flush trigger to prevent stale ticks from observing the collector post-completion).
- **`drain()` vs `flush()`:** `drain()` returns only `seq > watermark` and ADVANCES the watermark — the incremental primitive. `flush()` still returns the FULL snapshot (terminal reconciliation) and now ALSO advances the watermark so any defensive follow-up drain returns `null`. `pendingSinceWatermark()` is the cheap `O(n)` peek the trigger uses to short-circuit when the queue is quiet without paying for a drain + watermark advance.
- **Flush trigger wiring lives in `executeAndReport`.** The host: (1) starts `setInterval`-based trigger with `noteAppend` (interval OR line-count threshold), (2) pre-creates a collector and wires `setAppendListener -> trigger.noteAppend`, (3) sets `this.collectorRef = collector` BEFORE `executeWithLog` so any trigger tick during work has a live collector, (4) detaches listener + stops trigger BEFORE the terminal `flush()` so a stale timer cannot fire after the terminal snapshot, (5) clears `collectorRef` in `finally` so a subsequent work item cannot see a stale collector.
- **Cadence constants on the host module side** (next to the existing `TASK_LOG_UPLOAD_TIMEOUT_MS`): `TASK_LOG_FLUSH_INTERVAL_MS = 1500`, `TASK_LOG_FLUSH_LINE_THRESHOLD = 200`, `TASK_LOG_INCREMENTAL_UPLOAD_TIMEOUT_MS = 5000` (separately large from the 250ms terminal timeout). Each is overridable via `RunnerOptions.{taskLogFlushIntervalMs, taskLogFlushLineThreshold, taskLogIncrementalUploadTimeoutMs}` for tests.
- **`startTaskLogFlushTrigger` is exported from the host module** (not module-private) so the test suite drives the exact same `setInterval` + threshold code path. The host kept the symbol private to its module in Phase 1; for Phase 2 the test gets a thin re-export so the contract is exercised end-to-end without reimplementing the timer dance.

## Decisions / Gotchas

- **setInterval-based trigger, not per-append checks.** Design D1 says "checked on each append", but in single-threaded JS the per-append hook would couple the collector to the trigger (architectural leakage). The trigger exposes `noteAppend()` that the collector calls synchronously from `append` — the line-count path is checked at the moment of each append and eagerly fires when the threshold is reached. The interval path handles the quiet case (lines arrived but threshold not crossed, or no lines at all). Both fire the same `flush` callback; `flushIncrementalTaskLog` short-circuits when `drain()` returns `null` (no lines).
- **`setInterval` clamp + `unref`.** A zero/negative interval would create a tight loop. `startTaskLogFlushTrigger` clamps `intervalMs` to `max(50, ...)` and calls `handle.unref?.()` so an orphaned timer never keeps Node alive after a tear-down. The test override passes positive `taskLogFlushIntervalMs` to avoid the clamp interfering with intentional small values.
- **`flush()` advances the watermark.** After the terminal flush, any defensive follow-up `drain()` (e.g. if the trigger somehow fires post-stop) must return `null`. Advancing the watermark in `flush()` makes this a single-state invariant: terminal reconciliation is the "final word" on the collector's contents.
- **`collectorRef` set BEFORE `executeWithLog`.** First iteration set it AFTER `executeWithLog` returned, which meant any trigger tick during work called `flushIncrementalTaskLog(null)` and short-circuited — the trigger never fired against the live collector. Pre-setting `collectorRef = collector` (and clearing in `finally`) closes that window.
- **Test concurrency / fake-timer pattern.** `vi.useFakeTimers()` is set at the start of each incremental test; `vi.advanceTimersByTimeAsync(N)` inside the test body runs queued `setInterval` callbacks whose elapsed time has reached `N`. Tests use `startTaskLogFlushTrigger` directly (exported from host) with a small interval (60ms) and the default 5000ms incremental upload timeout — fast + deterministic, no wall-clock.
- **Existing `runner-host-task-log.spec.ts` tests updated for Phase 2 cadence.** The original three "best-effort" tests asserted `uploadTaskLog` is called exactly once. Under incremental flushing, the trigger may fire zero, one, or more times during work depending on timing — the assertions were relaxed to `toHaveBeenCalled()` (at least one upload) and the error-message regex to "upload failed for work" (the new label includes either "incremental" or "terminal" prefix). The verdict-bearing test was already correct and unchanged.
- **Phase 1 invariants preserved.** `append` still masks at the sink, still assigns monotonic seq, still drops head on overflow without reusing discarded seqs; `runCommand`/`git()` line emission unchanged; the collector's `flush()` still returns the full terminal snapshot. The new `drain()` is additive.

# T-004 Progress

## Codebase Patterns

- **`useEventsConnection` is the single owner of the SignalR connection.** It now returns `{ status, connection }` (was `ConnectionStatus` alone) so consumers can both bind hub-method callbacks and invoke hub methods (e.g. `SubscribeTaskLogAsync`) on the same connection. Existing call sites that discard the return value (`LiveTaskProvider`) need no change; consumers that read the return value (the test) update to destructure `{ status }`.
- **`useEventsConnection` is called once per consumer.** `LiveTaskProvider` calls it for the app's global `OnEvent` + `OnTranscriptEvent` bindings; `TaskLogPanel` calls its own instance for `OnTaskLogDelta` + lifecycle (`SubscribeTaskLogAsync` / `UnsubscribeTaskLogAsync`). Two connections is acceptable here because they have independent lifecycles and filter dimensions — sharing one connection would require a global registry of task-log subscribers, which the panel does not need.
- **`HubConnection` import is the real `HubConnection` from `@microsoft/signalr`.** The signalr module is mocked in tests via `vi.mock('@microsoft/signalr', ...)`; the mock builds a `FakeConnection` whose `on(event, handler)` records the handler in a `handlers: Map<string, Listener>`. Test code invokes the captured handler to drive a hub event without a real socket.
- **Mock path for `getIssueWorkflowTaskLog` is `../../../entities/issue/api/client`, NOT the barrel.** The real `useIssueWorkflowTaskLog` (in `entities/issue/api/queries.ts`) imports the helper from `./client` directly, not through the barrel. Mocking the barrel alone leaves the real `getIssueWorkflowTaskLog` (which calls `request()` → real network) in place; the test would fail with a fetch error. This is the same gotcha the existing `task-log-query.test.ts` follows.

## Decisions / Gotchas

- **Channel separation is enforced by the hook, not by the consumer.** `useEventsConnection` binds three different `conn.on(...)` calls (`OnEvent`, `OnTranscriptEvent`, `OnTaskLogDelta`) — each is a separate SignalR method with its own registered handler. A test that introspects `conn.handlers` proves the channels are physically separate (different handler Map keys, different invocations). Subscribing to task-log in the panel cannot interfere with `OnTranscriptEvent` because they are different methods on different connections.
- **The panel owns its own connection lifecycle.** Subscribe on `[connection, terminalNow, ...]` becoming "running and connection is ready"; unsubscribe on terminal or unmount. The `subscribedConnectionRef` stores the connection that received the `SubscribeTaskLogAsync` call so the cleanup can target the same connection even after a subsequent re-render replaces the local `connection` reference.
- **`mergeTaskLogDelta` is exported and pure.** It is the single dedup-by-seq + append-if-new helper the panel uses to merge an `OnTaskLogDelta` envelope into the `useIssueWorkflowTaskLog` cache. Out-of-order late deltas (`seq <= maxCachedSeq`) are dropped; already-cached seqs are dropped; the resulting page is sorted by seq. Truncation is `delta.truncated || page.truncated` — a single false→true transition from either side flips it on, never back. Pure function is easy to unit-test in isolation.
- **Terminal reconciliation is local to the panel, not global.** The panel derives terminal from its `taskStatus` prop (which `TaskItem` derives from the workflow/stage query that re-renders on every event). The reconcile trigger is `useEffect([taskStatus, ...])` — on transition to terminal, `queryClient.invalidateQueries({ queryKey: [issueNumber, taskId, projectId, workflowRunId, 'workflow-task-log'] })` triggers a fresh `useIssueWorkflowTaskLog` fetch. The event router's handlers do not carry `issueNumber`/`taskId` in their payloads, so a global router invalidation would not be enough; co-locating with the panel keeps the reconcile logic with the data it owns.
- **`taskStatus` prop is the terminal detector.** Phase 1's panel had no `taskStatus`; it was always rendered for failed/completed tasks. The new wiring needs to know the status to decide subscribe vs reconcile. `TaskProgressPanel.TaskItem` now passes `task.status` through. Terminal is defined as `completed | failed | skipped` (a closed set); other statuses are "running-ish" for subscribe purposes.
- **Existing `TaskProgressPanel.test.tsx` tests needed a `QueryClientProvider`.** The new panel calls `useQueryClient()` (for `setQueryData`/`invalidateQueries`), so renders must wrap in a `QueryClientProvider`. The existing 14 tests all needed a `renderWithQueryClient` helper added; the wrapping is mechanical and didn't change the test assertions.
- **Server `SubscribeTaskLogAsync` adds the type-subscription on first call.** The server hub method also calls `_registry.Subscribe(connectionId, "task-log.delta")` so the publisher's type filter passes — the Web does NOT need to include `task-log.delta` in its `SetSubscriptionsAsync` upfront. The first `SubscribeTaskLogAsync` call from the panel is sufficient.
- **Server `SubscribeTaskLogAsync` mirrors to the durable `IConnectionSubscriptionGrain`.** Type-subscription is durably replayed on reconnect; the per-task scope itself is NOT durably stored (the Web re-asserts on reconnect via its `onreconnected` callback). This is the same Web-driven reconnect pattern the design chose for transcripts.

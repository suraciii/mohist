## Codebase Patterns

- `entities/session/model/view/` is the cluster cleaned up by T-001 (issue #316).
  - `view.ts` (125 lines, C=4) — 13 view type declarations + `viewSessionEvents<K>` dispatcher. Re-exports nothing; the view types ARE the public surface, defined here.
  - `view/helpers.ts` (131 lines, C=102) — `>=2-projector` shared event-parsing utilities: `isRecord`, `narrowPayload`, `getStringProp`, `getNumberProp`, `extractTextChunk`, `normalizeRaw`, `normalizeToolName`, `mapToolState`, `mapTerminalStatus`, `defaultToolStatus`, `toolRecord`, `readToolString`, `readToolValue`, plus the `is*Event` predicates. Imports `SessionEvent` via `import type { SessionEvent } from '../view'`.
  - `view/chat.ts` (275 lines, C=69) — `buildChatView` + chat-only builders: `KNOWN_PROMPT_KINDS`, `nextPartId`, `appendTextPart`, `appendReasoningPart`, `closeOpenTextParts`, `upsertToolPart`, `pushErrorPart`, `makeInitialTurn`, `makePromptTurn`. Types imported via `import type` from `'../view'`.

  - `view/compact.ts` (108 lines, C=29) — `buildCompactView`.
- D1 (type-only back-imports): every projector file does `import type { ... } from '../view'`. The `import type` is erased at compile time — there is no runtime circular import. typecheck enforces it: any non-type import slipping in triggers a `TS2304`/`TS6133` cascade.
- D2 (helper placement): helpers used by `>=2` projectors go in `view/helpers.ts`; helpers used by exactly 1 projector live next to it. After the split, every helper in `helpers.ts` is used by 2 of the 3 projectors (chat + timeline for tool/parse helpers; chat + compact for `isInputEvent`/`isSessionClosedEvent`/`isLivenessEvent`/`getStringProp`/`extractTextChunk`/`mapTerminalStatus`; etc.). Pure chat-only builders all stay in `view/chat.ts` and do not appear in `helpers.ts`.
- Public-surface invariant: `widgets/coder-session/model/useSessionTimeline.ts` imports `viewSessionEvents`, `SessionEvent`, `SessionTimelineToolCall`, `SessionTimelineRecovery`, `SessionTimelineCompaction` from `entities/session/model/view` — the file is untouched. `entities/session/model/view.test.ts` (483 lines) is also untouched; 26/26 assertions green.
- Per-step commit discipline followed: 4 commits, each ends with `npm run typecheck -w packages/web` + `npx vitest run src/entities/session/model/view.test.ts` green. Order: helpers → chat → timeline → compact.
- Typecheck policy: `packages/web` runs `tsc -b` as typecheck; the repo uses `TreatWarningsAsErrors`-equivalent discipline (unused imports become `TS6133` errors). When extracting, prune the import list to exactly what the new file uses.
- `normalizeToolName` is the only helper used by exactly 1 projector (chat, via `upsertToolPart`). It was put in `helpers.ts` per the design spec, not the boundary rule. If a future timeline/compact projector needs it, the placement is already correct. The spec's D2 enumeration wins over the heuristic.
- After this T-001 split the next refactor is `widgets/session-transcript/model/transcript-tool-state.ts` (T-002 collapses `updateToolInTurn` duplicate merge branches; T-003 relocates `buildLiveToolDetails`). The two are independent files from `view.ts`, so they don't touch anything in `entities/session/model/`.
- T-002 (D3) — `updateToolInTurn` de-duplication: extracted file-local `mergeToolPart(toolPart, updates, now, overrideToolCallId?)` above `updateToolInTurn`. The merge body appears exactly once (verified by grep: 1 hit on `rawInput = updates.rawInput ?? updates.input`). Both arms now route through it. The single behavioral delta (correlation arm overwrites the matched part's `toolCallId`; toolCallId arm leaves it) is captured by the optional `overrideToolCallId` parameter: when undefined the spread includes `{}` (no `toolCallId` key added, so toolPart.tool.toolCallId survives via the earlier spread); when provided the spread adds `{ toolCallId: overrideToolCallId }` which overwrites via object spread order. C: 180 → 162 from T-002 alone; T-003 will move `buildLiveToolDetails` and drop further.
- T-002 placement decision: the helper sits **above** `updateToolInTurn` (file-local, non-exported) per the task's "file-local `mergeToolPart`" wording. No new imports added — `getDisplayFields`, `stringifyPayload`, `parseEditInput`, `parsePatchOperations`, `mapStatusToDisplay`, `isTerminalState` were already imported at top of file for `updateToolInTurn`/`createToolPart`.
- T-002 second-behavioral-delta observation: the task only names toolCallId as the single behavioral delta between arms, but the correlation arm originally also fed `correlationKey.split('|')[0]` straight into `getDisplayFields` instead of `updates.normalizedName ?? toolPart.tool.normalizedName`. To stay field-for-field invariant, the correlation arm constructs `correlationUpdates = { ...updates, normalizedName }` so the helper sees the same final `updates.normalizedName` value the original code used. The merge body itself stays single-source; only the call-site's `updates` payload differs by one key. (Existing tests only exercise the case where the test fixture's normalizedName equals the correlationKey split, so this was not observable from tests alone, but it's the contract.)

## Gotchas

- When removing the `defaultToolStatus`/`getNumberProp`/`mapToolState`/`normalizeRaw`/`readToolValue`/`isToolEvent`/`isLivenessEvent`/`isAssistantTextEvent`/`isAssistantReasoningEvent` imports during the timeline/compact extractions, typecheck flagged them as `TS6133` because compact only uses a subset (`narrowPayload`, `getStringProp`, `isInputEvent`, `isAssistantTextEvent`, `extractTextChunk`, `isAssistantReasoningEvent`, `isToolEvent`, `readToolString`, `isSessionClosedEvent`, `mapTerminalStatus`, `isLivenessEvent`). Always prune imports to the new file's actual usage; don't carry over the full list.
- `import` statements in TypeScript files must come before type/function declarations that are then used. When I tried to leave the existing top-of-file import block and place new imports mid-file, typecheck still passed, but the cleaner pattern (moves all `import` to top) is the one I shipped in the final view.ts.
- `scc --by-file` per-file complexity is what the spec gates against, not the total. Even though the total complexity across the 5 files is identical to the original (251), the per-file maximum dropped from 251 → 102. Helpers has C=102 because of the `normalizeToolName` switch ladder (12 branches). All five files are < 180.
- Baseline pre-change: `view.ts` was 775 lines / C=251. Post-change: 5 files totaling 829 lines (mostly the 5-file overhead of `import` blocks), per-file max C=102.
- T-002 gotcha: when parameterizing the toolCallId overwrite via an optional spread (`...(overrideToolCallId !== undefined ? { toolCallId: overrideToolCallId } : {})`), the empty spread on the toolCallId-arm path matters — writing `toolCallId: overrideToolCallId` unconditionally would clobber the matched part's id with `undefined`, breaking the "toolCallId arm leaves it" scenario. The conditional spread is the mechanism that keeps both behaviors preserved with a single body.
- T-002 gotcha: the `status: _updatesStatus, ...restUpdates` destructure intentionally renames `status` out of `restUpdates`. Don't "simplify" by removing the destructure — it's how `newStatus` (which routed through `mapStatusToDisplay`) gets to win over the raw `updates.status`. Without it, the spread `...restUpdates` would write the raw `started`/`completed`/etc. back over `newStatus`.
- T-002 gotcha: vitest from repo root with `-w packages/web` works for `npm run test:run -w packages/web`, but bare `npx vitest run <path>` must run with `workdir=packages/web` (vitest can't resolve the workspace config from outside). I hit a "cleanup / _reducedMotionOverride" unmount error the first time when running from root; switching `workdir` fixed it. Keep this in mind for T-003 verification.
- T-003 relocation (D4): `buildLiveToolDetails` moved to `widgets/session-transcript/ui/tool-views/live-details.ts` (alongside `shared.tsx`). The new file imports `asPayloadRecord`/`asRecord`/`getNumber`/`getString`/`truncatePreview` from `'../../model/transcript-payload'` (the path I quoted in D4). The re-export sits at the bottom of `transcript-tool-state.ts`: `export { buildLiveToolDetails } from '../ui/tool-views/live-details'` (one `..`, not two — the task description had a small typo in the re-export path, but the spec intent is clear: the module must resolve from `model/`, and from `model/transcript-tool-state.ts` the path is `../ui/tool-views/live-details`).
- T-003 also dropped the now-unused payload imports (`asPayloadRecord`, `asRecord`, `getNumber`, `getString`, `truncatePreview`) from `transcript-tool-state.ts` per the typecheck discipline (TS6133 would flag them otherwise). The remaining imports in `transcript-tool-state.ts` are exactly: `parseEditInput`, `parsePatchOperations`, `normalizeToolName`, `inferDisplayTitle`, `stringifyPayload`, `getFilePathFromInput`, `getToolLabel` (from `transcript-tool-utils`) — all consumed by `createToolPart` / `mergeToolPart` / `getDisplayFields` / `deriveToolTarget` / `findToolByCorrelation` / `getNormalizedName` / `updateToolInTurn`.

# Issue-228 progress

## Codebase Patterns

- **Test fixtures inherit `ConfigureMohistServices` automatically.** `MohistServiceRegistration.ConfigureMohistServices` is the single DI wiring point; production code calls it via `AddMohistServerCore`, test fixtures call it directly. Any new host-wide registration (e.g. OpenTelemetry) MUST land here so production and test fixtures stay in lock-step.
- **xUnit collections serialize tests that share process-global state.** `Microsoft.AspNetCore` `ActivitySource` (and any other OTel source) is process-global: every `TracerProvider` in the process sees every emitted Activity. Tests that each stand up their own `TracerProvider` with a capturing processor and assert on per-host capture MUST run in a `DisableParallelization` collection — otherwise one host's spans leak into another host's recorder. See `OtelTracing` collection.
- **The OTel SDK does not register `IConfigureOptions<OtlpExporterOptions>` for the trace-only path.** Inline `AddOtlpExporter(Action<OtlpExporterOptions>)` configures the SDK at builder time, but `IOptions<OtlpExporterOptions>` won't reflect it unless we also call `services.Configure<OtlpExporterOptions>(...)`. Production observability tooling and tests that need to assert the configured protocol/endpoint MUST resolve via the duplicated `services.Configure<OtlpExporterOptions>` call — they cannot rely on a single source of truth.
- **Centralised package versions live in `Directory.Packages.props`.** All `<PackageReference>` entries use bare names; `<PackageVersion>` rows live in the central props file. Add a new package by adding both rows.
- **xUnit trait names live in `Support/Traits.cs`.** Use `Traits.Speed.Integration` / `Traits.Sut.System` rather than literal strings.
- **`Mohist:Otel` is a shared config section across issues #219 (collector) and #228 (server-side exporter).** Both own an `OtelOptions` class. The collector's `Mohist.Server.Otel.OtelOptions` (Port, BindHost, DbPath, Enabled) and the server emitter's `Mohist.Server.Infrastructure.Config.OtelOptions` (Endpoint, Enabled) deliberately share the `Mohist:Otel:Enabled` master switch — disabling the collector implicitly disables the server emitter. Files that import both namespaces MUST fully-qualify one of the two `OtelOptions` types (or alias it via `using`) or the compiler will report `CS0104: 'OtelOptions' is an ambiguous reference`.

### Learnings for future tasks

- **Decisions made:**
  - The master switch is implemented by **not calling** `AddOpenTelemetry()` at all (not by registering the SDK with a no-op exporter). This is the strongest guarantee that the off-state is byte-for-byte equivalent to a server without the capability — no `TelemetryHostedService`, no background threads, no `Activity` creation overhead.
  - The OTLP HTTP exporter does NOT auto-append `/v1/traces` when the endpoint comes from `OtlpExporterOptions.Endpoint` (it only auto-appends when the endpoint comes from spec env vars). `ResolveExportEndpoint` appends `/v1/traces` ourselves so the documented `Mohist:Otel:Endpoint` contract (base URL) holds across config-file, env-var, and external-collector paths.
  - The configured `OtlpExporterOptions` are mirrored into the options pattern via `services.Configure<OtlpExporterOptions>` because the SDK does not register an `IConfigureOptions<OtlpExporterOptions>` on its own for the trace-only path.
  - Exporter failure isolation relies on the SDK's `BatchExportProcessor` running exports on a background thread. No defensive `try/catch` is added (Decision 5 from `design.md`). The contract is enforced by `OtelExporterFailureIsolationSpecs`.
  - The `/otel` filter uses `PathString.StartsWithSegments` (segment match), not `StartsWith` (string prefix). This is intentional: `/otelware` would be silently excluded by a naive `StartsWith("/otel")` and would mask unrelated endpoints. The unit test `ExcludeOtelIngestPath_ReturnsFalse_ForOtelPathPrefix` pins this.

- **Gotchas discovered:**
  - xUnit tests in the default collection run in parallel. Each OTel test stands up its own `WebApplication` + `TracerProvider`, but `Microsoft.AspNetCore` is a process-global `ActivitySource` — every provider sees every Activity emitted anywhere in the process. Without a non-parallel collection, the `/otel`-filter exclusion test (which asserts the recorder is empty) would intermittently fail because a concurrent `/api/health` test's inbound spans flow into its recorder. **All OTel specs must declare `[Collection("OtelTracing")]`.**
  - The OtlpReceiver uses `HttpListener` which on Linux binds only to loopback prefixes by default; `127.0.0.1:` (not `localhost:`) avoids the dual-stack `IPv4/IPv6` ambiguity that triggers `Access Denied` from `HttpListener` on some Linux configurations.
  - `WebApplication.CreateBuilder()` + `WebHost.UseTestServer()` + `app.Start()` is the minimal in-process pipeline that exercises ASP.NET Core inbound instrumentation. The host's `TracerProvider` is built lazily by the `TelemetryHostedService` only when the host starts, so test assertions about the pipeline's state must run AFTER `_app.Start()`.
  - `Endpoint = new Uri(...)` on `OtlpExporterOptions` triggers the explicit-set path; the SDK's auto-append `/v1/traces` only happens for the env-var path. So `ResolveExportEndpoint` must do the append explicitly.
  - The first version of `MohistOpenTelemetryRegistration` registered `OtlpExporterOptions` only via the inline `AddOtlpExporter` callback. This meant tests couldn't introspect the configured protocol/endpoint via DI — the `ConfigureTracing_OtlpExporterEndpoint_AppendsV1TracesToBase` test requires `services.Configure<OtlpExporterOptions>` registration.

- **Patterns / API shapes established:**
  - `OtelOptions.SectionName = "Mohist:Otel"` and `services.Configure<OtelOptions>(configuration.GetSection(OtelOptions.SectionName))` is the canonical pattern — mirrors `AgentJobOptions`, `AttachmentStorageOptions`, `WorkflowArtifactStorageOptions`.
  - `AddMohistOpenTelemetry` follows the same shape as `AddMohistServerCore`: a single extension on `IServiceCollection` that takes `IConfiguration`, returns `IServiceCollection`, gates on options.
  - `internal static` helpers (`OtelIngestPathPrefix`, `ExcludeOtelIngestPath`) are exposed for test pinning. The `internal` access keeps them out of public API surface while letting the tests in the same assembly pin observable behaviour.
  - The `OtelTestHost` pattern: minimal `WebApplication.CreateBuilder()` + `WebHost.UseTestServer()` + production `AddMohistOpenTelemetry` + one capturing processor + one or two mapped routes. This is the lightweight in-process host for OTel tests — `WebApplicationFactory<Program>` would be heavier and would inherit the full `ConfigureMohistServices` graph.

- **Cross-task invariants:**
  - T-002 will extend the single `WithTracing` block in `MohistOpenTelemetryRegistration.ConfigureTracing` with `AddSource("Microsoft.AspNetCore.SignalR.Server")`, the Orleans ActivitySource name(s) (TBD), `AddHttpClientInstrumentation()`, and `AddEntityFrameworkCoreInstrumentation()`. T-002 also requires `OpenTelemetry.Instrumentation.Http` and `OpenTelemetry.Instrumentation.EntityFrameworkCore` in `Directory.Packages.props`. **The master-switch gate, the resource service name, the inbound HTTP filter, and the OTLP exporter options configuration from T-001 must not be touched.**
  - The `/otel` filter must remain a `PathString.StartsWithSegments` (segment match), not `StartsWith` (string prefix). T-002 may need an analogous outbound `FilterHttpRequestMessage` to suppress exporter self-feedback (Decision 4 from `design.md`).
  - The non-parallel `OtelTracing` collection is required for T-002's integration tests too — any test that captures spans via a per-host processor must join it.
  - Production behaviour when `Mohist:Otel:Enabled` is unset: the host starts with OTel enabled (default `Enabled = true`). Tests that want OTel off must explicitly set `Mohist:Otel:Enabled = false` in their `IConfiguration`. The existing `MohistIntegrationFixture` / `MohistDbFixture` do not set this, so they exercise the OTel-enabled path — and still pass, confirming zero regression.

### Learnings for future tasks

- **Decisions made:**
  - **Preemptive outbound self-feedback suppression.** `FilterHttpRequestMessage` is wired unconditionally in `ConfigureTracing` even though the SDK's `SuppressInstrumentationScope` already covers the exporter. The integration test (`OtelSelfFeedbackSpecs.OtlpExporter_OutboundPost_ProducesNoOutboundHttpClientSpanToOtlpUri`) drives a real OTLP receiver and confirms zero outbound-to-OTLP-URI spans; with the filter in place, this is robust to any future SDK change that weakens the suppression scope. Without the filter, the test still passes today (the SDK's scope covers it), but the test does not prove it — only one layer of defense would remain.
  - **Orleans source subscription lives in the host's `WithTracing`, not in the silo's DI.** `ActivitySource` is process-global: subscribing from the host `TracerProvider` captures every Orleans activity regardless of which DI container the silo uses. Adding OTel to the silo's DI would build a second `TracerProvider` and double-export every span — Decision 3's anti-pattern.
  - **`silo.AddActivityPropagation()` is the per-grain-call counterpart to host-side source subscription.** It wires Orleans' grain-call dispatcher to propagate `Activity.Current` across the grain-call boundary so the grain span emitted from inside the call appears as a child of the caller's activity. Without it, every grain activity would be a root span in its own trace and the spec requirement "grain-call spans attach as children" would silently fail.
  - **OtelTestHost was extended with `ConfigureServices` / `ConfigureApp` hooks rather than introducing a second test host.** Different tests need different middlewares (SignalR, EF DbContextFactory, named `HttpClient`s) and the host already runs the production `AddMohistOpenTelemetry`; the hooks keep the production-code path intact and let each test opt in to extra wiring without subclassing.
  - **xUnit2030 trips on `Assert.NotEmpty` over a LINQ result.** The analyzer wants `Assert.Contains` for membership checks; `Assert.NotEmpty` is for collections. The OTel EF registration test was rewritten accordingly.

- **Gotchas discovered:**
  - **OpenTelemetry's `AddSource` only accepts exact names.** The Orleans wildcard `AllActivitySourceName` (`"Microsoft.Orleans.*"`) is NOT subscribable — each of the four concrete source names must be listed. Confirmed by the unit assertion `ProductionOtelRegistration_SubscribesAllFourOrleansSourceNames`.
  - **`Microsoft.AspNetCore.SignalR.Client` 10.0.0-preview.3** is the only SignalR client package that pairs with .NET 11 preview SDKs and matches `Microsoft.AspNetCore.TestHost`'s current HttpTransportType behaviour. The signalr test uses long-polling explicitly (default for `TestServer`) — websocket transport is not available on the in-process pipeline.
  - **Orleans grain-timer / reminder / outside-request activities are legitimate root spans.** `IGrainTimerInvoker/InvokeCallbackAsync`, `IInboundMessageCollector`, `OutsideRequestCaller`, and `ReminderService` activities all fire from Orleans' scheduling context with no calling request activity — they are exempt from the spec requirement "no orphan span when a causal parent exists" because no causal parent exists. The single-trace continuity test (`IssueCreationRequest_YieldsSingleTraceSpanningHttpAndOrleansAndEfCore`) filters these out before asserting parent-child links.
  - **The EF Core instrumentation source name is `OpenTelemetry.Instrumentation.EntityFrameworkCore`**, not the older `Microsoft.EntityFrameworkCore`. Tests pin against the current name so a future rename in the contrib package surfaces immediately.
  - **OtelTestHost must mirror every source name the production pipeline subscribes to.** A second in-process `TracerProvider` with `AddProcessor(Recorder)` will only receive activities from sources it has explicitly subscribed — if `Microsoft.Orleans.Storage` is missing from the test provider's subscription, the recorder will not see storage activities, and a passing "no spans captured" test could silently mask a production-pipeline subscription drop. The test host's `WithTracing` block iterates `MohistOpenTelemetryRegistration.OrleansActivitySourceNames` to keep the two in lock-step.
  - **`xUnit2030: Assert.NotEmpty on a LINQ expression** is a hard build break under `TreatWarningsAsErrors`. Use `Assert.Contains` for membership, `Assert.NotEmpty` only for actual collections.

- **Patterns / API shapes established:**
  - **Pin static source-name arrays as `public static readonly string[]`.** The `OrleansActivitySourceNames` array is the canonical subscription list; tests assert its content directly (`ProductionOtelRegistration_SubscribesAllFourOrleansSourceNames`), and `OtelTestHost` iterates it for its mirroring subscription. This makes a future Orleans rename impossible to miss: the test fails on a diff between the static list and the runtime-emitted set, and the test host's recording shrinks visibly if a name goes missing.
  - **`internal static` outbound filter helper, wired preemptively.** `IsExporterSelfFeedback` is exposed for tests AND used by the production registration. Same shape as `ExcludeOtelIngestPath` from T-001: helper exists for both production safety and unit-test pinning.
  - **`OtelTestHost` extension via `ConfigureServices` / `ConfigureApp` hooks.** Avoids the alternative of one-test-per-host-class explosion. Hooks run before / after the default `/api/health` and `/otel/v1/traces` mappings.

- **Cross-task invariants:**
  - The `WithTracing` block now carries five automatic instrumentation sources on a single `TracerProvider`. Future tasks that add a new instrumentation MUST add it inside the same `ConfigureTracing` block — never split the pipeline into multiple `WithTracing` calls, or trace continuity breaks (different providers have different `ActivityListener` sets, so a span emitted under provider A is invisible to provider B even when both subscribe the same source name).
  - The four Orleans source names are confirmed against Orleans 10.1.0. If a future Orleans upgrade renames an `ActivitySource`, the diff between `OrleansActivitySourceNames` and the runtime-emitted set shows up in `OtelOrleansSourceNameSpecs.OrleansGrainCall_EmitsActivityFromConfirmedOrleansSourceNames`.
  - `silo.AddActivityPropagation()` MUST stay wired — it is the per-call carrier for trace continuity into grain invocations. Removing it breaks every "grain-call child span" assertion across the suite.
  - `IsExporterSelfFeedback` MUST stay wired even when the SDK's `SuppressInstrumentationScope` covers the exporter — this is the documented hard guarantee (design Decision 4). The integration test asserts the property against a real OTLP receiver, so removing the filter without changing the test is impossible without breaking the test.

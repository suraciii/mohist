## Codebase Patterns

- CLI command wiring uses `MohistCliCommands.ProjectRefOption()` (returns `(Option<string?> Project, Option<string?> ProjectId)`) on every project-scoped command — register both on the command. `MohistCliCommands.ProjectIdOption()` is the legacy single-option form.
- Output routing uses `MohistCliCommands.OutputOption()` + `api.ResolveOutputMode(output)` + `Print{Get,Post,Patch,Delete}WithOutputAsync(path, body_or_null, mode)`. Don't use the legacy `PrintGetAsync` / `PrintPostAsync` / `PrintPatchAsync` / `PrintDeleteAsync` on shared-output command groups.
- For optional fields where you only want to send the body field when the user actually supplied the flag, use `ctx.GetResult(option) is not null` for non-bool options and `ctx.GetResult(option) is not null && !result.Implicit` for `Option<bool>` (because System.CommandLine applies an implicit `false` default when the flag is absent). Pattern lives at `packages/cli/Mohist.Cli/MohistCliCommands.ProjectWorkflow.cs:469` (`defaultTemplateProvided = defaultTemplateResult is not null && !defaultTemplateResult.Implicit`).
- `mo project <sub>` parser-rejection works for free once the registration line is removed — System.CommandLine surfaces "Unrecognized command" with non-zero exit. No bespoke rejection code needed.
- Server test project (`Mohist.Server.Tests`) has its own `ProjectCliRepositorySpecs` that mirrors the CLI's command face — when changing the CLI surface, also rewrite the server-side spec to match (don't leave stale `mo project repo` references).
- `CliTestHarness.CreateSync()` defaults the active project to `proj_abc`; to use a different id, pass `activeProjectId` explicitly. The harness also writes the id to the fake filesystem at `~/.mohist/cli-state.json` so `api.ResolveProject` falls back to it.
- The `System.CommandLine` help resolution: when you run `--help` on a partially-matching command path (e.g. `project repo list --help` where `project` exists but `repo` does not), the help for the deepest *valid* command is rendered. To verify the "unrecognized" scenario, run the actual invocation (no `--help`) and assert non-zero exit + no requests.
- Pre-existing test failures: `CliReferenceDocsSpecs` (3 tests) assert docs content (`mo server start`, `mo issue comment add`, etc.) and fail on master — not introduced by this issue.

## Decisions

- Kept `MohistCliCommands.Repository.cs` as the single implementation; deleted `MohistCliCommands.ProjectRepo.cs`; removed registration at `MohistCliCommands.Project.cs:17`.
- `add` body is `{name, gitUrl, baseBranch, isDefault}` (no `path`/`remote`/`resolvedPath`). The implementation always sends all four because `--git-url` is required and the others are option-defaults, which matches the existing server-side assertions.
- `update` body is built from `ctx.GetResult(...)` per-option, omitting unset fields — matches the spec scenario "carries only the supplied fields". `setDefault` uses `!result.Implicit` because of System.CommandLine's implicit-default behavior on `Option<bool>`.
- `delete` is the primary verb (matches spec 词表); `remove` and `rm` are aliases via `Command.Aliases.Add(...)`. All three dispatch the same DELETE request.

## Gotchas

- `Option<bool>` defaults to implicit `false`: `ctx.GetResult(opt) is not null` returns true even when the user did not pass the flag. Always combine with `!result.Implicit` for `Option<bool>` presence checks.
- `Assert.Single(requests.Where(...))` triggers xUnit analyzer `xUnit2031` (TreatWarningsAsErrors) — use `Assert.Single(requests, r => ...)` instead.
- `RenderHelp` on a non-existent command path renders help for the deepest *valid* ancestor, not an "Unrecognized" message. Use the actual invocation (without `--help`) to assert parser rejection.
- `--default` was a legitimate flag in the original `mo repo add`. The unified face drops it (spec mandates `--set-default`). Anything referencing `--default` must migrate.

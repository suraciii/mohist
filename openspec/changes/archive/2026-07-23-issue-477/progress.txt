## Codebase Patterns

- WorkflowProfile collection records are custom-only rows keyed by `(ProjectId, ProfileId)`; built-ins remain catalog assets and are merged by `IWorkflowProfileProvider`.
- Reference rows keep one public Profile ID in their owning state and a nullable custom backing key for the restrictive composite FK. Built-in references leave the backing key null.
- `WorkflowProfileDeletionBlockerQuery` is diagnostic; the FK is the final delete/selection race backstop. Terminal Run transitions clear only the backing key and retain public state/history.
- Server spec databases use the existing shared in-memory SQLite model schema. Collection specs use a fixed `FakeTimeProvider`; production writes accept the application `TimeProvider`.

## T-003 Notes

- `WorkflowRun.WorkflowProfileId` is persisted in the run state. Startup selects the Issue explicit ID or Project `DefaultWorkflowProfileId`, creates the immutable Stage topology from that Definition, saves the run, then binds the ID through `WorkflowProfileReferenceCoordinator`.
- Active runtime Definition reads use only the persisted Run Profile ID. Stage initialization and sequential lock lookup pass that ID explicitly; no later Issue or Project selection is consulted. New or reordered Definition Stages therefore do not alter an active Run topology.

## Re-diagnosis (interrupted)

- Re-ran `npm run verify` once before re-running `npm test` 5 times; both observed one failure (`AgentJobTerminalDeliverySpecs.ReportResultAsync_RunnerCategoryPrecedence_StatusUsedWhenOutputAndCodeMissing`, 3s 001ms, "Timed out waiting for: status == Running. Last value: Pending"), then 5 subsequent `npm run verify` plus 8 `dotnet test` runs and 3 `npm test` runs all returned 2927/2927. The flake is rare enough that it must be provoked, not steady-state.
- Root cause at the spec layer: `SpecTests/Support/TestWait.cs` `ForAsync` is bounded by an attempts count derived from `ceil(timeout / step)` rather than by wall-clock time. When the host is heavily loaded, each `probe()` + `advance()` iteration finishes well under the assumed 25 ms step, so the loop hits the attempt ceiling and fires `Assert.Fail` after only ~3 s of wall-clock even though the caller asked for a 5 s budget. The AgentJob uses polling (`WaitForStatusAsync` -> `GetStatusAsync` + `CheckTimeoutsAsync` per iteration), so a slow `TryDispatchAsync` under load can complete after the polling budget has already been burned. Adding a real `CancellationTokenSource(timeout)` would enforce the caller-supplied budget without weakening any assertion, but it widens the test-support contract and is out of scope for this issue.
- Single-class runner reproduces the failed test as `Mohist.Server.SpecTests.Specs.Agent.Grain.AgentJobTerminalDeliverySpecs.ReportResultAsync_RunnerCategoryPrecedence_StatusUsedWhenOutputAndCodeMissing` at 3s 001ms; the in-place fix would be to expose a TaskCompletionSource or other deterministic status-transition signal on `IAgentJobGrain` so the test awaits the transition instead of polling. That is also out of scope for issue-477 and would change the AgentJob public contract.

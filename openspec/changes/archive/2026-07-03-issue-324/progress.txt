## Codebase Patterns

- **Route parameter binding:** ASP.NET Core minimal API binds `string? range` directly onto the handler signature; we validate via `MetricsRange.TryParse` and surface the existing `ApiResults.BadRequest("...", "unsupported_range", new { range })` seam. Unknown ⇒ 400. This pattern matches how `string? bucket` is handled in `IssueRoutes.Metrics.cs`.
- **Querier takes `int? windowDays`, never the wire string:** routes parse → routes pass `int?` → querier substitutes `?? <fixedDefault>`. Each querier method's omit-default is a local literal (per-endpoint back-compat). This keeps queriers and unit tests decoupled from the wire vocabulary (D1).
- **CFD D6 reversal in-place:** `CumulativeFlowQuerier.TrailingWindowDays` becomes the omit-default constant; `GetAsync(projectId, now, windowDays, ct)` substitutes the literal. Snapshot read path, schema, DTO fields, and `rangeFrom`/`rangeTo` wire fields are unchanged (D2).
- **Quality double-window in-place (no DTO rename):** `Window7d` stays a fixed 7-day lens regardless of range; the `Window30d` slot, its previous-window companion, and the trend bucket count all scale by `windowDays`. Omit ⇒ `windowDays = 30` ⇒ today's exact shape (D3).
- **Completion bucket axis is orthogonal to range:** `bucket=day` ⇒ `days` daily buckets; `bucket=week` ⇒ `ceil(days / 7)` ISO-week buckets (D4). Omit ⇒ 30 day / 12 week, byte-equal today.
- **Per-endpoint omit defaults (load-bearing):** completion-day=30, completion-week=12w, delivery=30, stage=30, quality-primary=30, cfd=90 (TrailingWindowDays), approval-wait=7. These exist as `?? 30` / `?? 7` etc. on each querier method — Dashboard shared-hook back-compat depends on every single one.

## Decisions

- **MetricsRange is static, not record:** the type owns wire constants (`"7d"`/`"30d"`/`"90d"`), day-count constants, and a single `TryParse(string?, out int)` method. No instance state, no allocations, no DTO shape.
- **Delivery-time wire DTO does not expose window bounds:** the test asserts the bounds indirectly via the querier (`windowDays: 90` ⇒ window math matches `now.AddDays(-90)` semantics). Unit tests on `IssueQuerier` cover the full window math; the spec test's HTTP round-trip checks the route plumbing (200/400, empty payload).
- **Cumulative-flow snapshot read path and DTO unchanged:** the spec mandates no new field. `rangeFrom`/`rangeTo` already expose the actual window the chart derives the badge from.

## Gotchas

- **EF Core SQLite cannot translate `DateTimeOffset` against TEXT columns:** every windowed method already filters in memory after a bounded fetch. Scaling a window is a local literal change, not a query-translation risk.
- **`previousFrom` math must scale with `days`:** for completion day-bucket, `previousFrom = today.AddDays(-(2 * days - 1))` (NOT `today.AddDays(-(days - 1) - days)`). For week-bucket, `previousFirstWeek = firstWeek.AddDays(-7 * weekCount)`. The "same length, immediately preceding" invariant is the spec contract.
- **`Window30d` slot is no longer literally 30 days when range is supplied:** callers reading the field name must NOT assume literal 30. Doc-comments on `QualityMetricsResult.Window30d` updated to state "30 days on omit, scaled by the range otherwise". The `Window7d` field is the trustworthy fixed-lens signal.
- **Approval-wait route still binds `DateTimeOffset.UtcNow` directly** (not via `TimeProvider`): this is a pre-existing wart from issue-295 and explicitly out of scope for M3 (design.md notes this). The range change keeps the existing clock source per endpoint.
- **Self-review report already filed:** `openspec/changes/issue-324/self-review.md` documents a count typo (seven→eight) in design.md Migration Plan step 2 and a follow-up on the agent-cost 90d weekly granularity (T-002 scope). No new findings during implementation.
- **Flaky test in the full suite:** `Microsoft.Data.Sqlite` `ObjectDisposedException` on `SQLitePCL` handle during `EnsureInitialized` reproduces only in the full suite, passes in isolation (per existing skip message). Not introduced by this task; passes when rerun.
- **Agent usage 90d weekly trailing bucket clamp:** the last weekly bucket's `BucketEnd` is clamped to `rangeTo` (exclusive end of the trailing window). Without this clamp, `rangeFrom + 13*7 = rangeFrom + 91` would overshoot the 90-day series. The trailing bucket's length is therefore 3 days (rangeFrom + 91d − 90d), not 7. This is correct: the bucket grid covers the requested day-span exactly, and the existing `BucketEnd` field already carries the right boundary for the chart to render.
- **`ComputeCumulativeCostPerShipAsync` per-bucket day boundaries use `long`:** `rangeFrom.AddDays((long)i * bucketSizeDays)` avoids int overflow on long-lived projects where `(long)i * 7` for i=13 stays well within range but guards against future 365d ranges (52 weeks × 7 = 364 — safe, but explicit `long` makes intent obvious).

## Codebase Patterns (T-002 additions)

- **Agent cost windowed scale:** `GetCostWindowedAsync(projectId, int? windowDays = null)` substitutes `days = windowDays ?? 30` on both current and previous windows. `currentFrom = now.Date.AddDays(-(days - 1))` keeps the current window inclusive of today; `previousFrom = currentFrom.AddDays(-days)` keeps the previous window the same length immediately preceding.
- **Agent usage granularity map (D5):** `ResolveUsageBucketGranularity(days)` returns `("week", ceil(days/7), 7)` when `days >= 90`, else `("day", days, 1)`. The querier uses the bucket count + size to lay out the bucket grid; the trailing edge of the last bucket is clamped to `rangeTo` so the series covers exactly the requested day-span. `bucketGranularity` field reports `"day"` or `"week"`; cumulative-cost-per-ship sub-series follows the same bucket grid.
- **CumulativeCostPerShipAsync signature gained `int bucketSizeDays`:** the sub-series day boundaries are computed from `rangeFrom.AddDays((long)i * bucketSizeDays)`. The prior hard-coded `i`/`i+1` is gone; the per-bucket math now derives from the granularity map.
- **Route validation is identical to T-001:** `string? range` → `MetricsRange.TryParse` → `int? windowDays` → querier. Unknown ⇒ 400 with `unsupported_range` code. The route owns the wire vocabulary; the querier takes `int?` and stays string-independent (testable directly with `windowDays: 90`).

## Decisions (T-003)

- **Hook arg signature is consistent across the eight:** `useX(range?: InsightsRange)`. Eight of the eight take the same shape (no positional defaults, no aliases), so future readers can predict the API from a single example. ## Gotchas (T-003)

- **`completion-trend` is the only hook that composes `range` with another query param** (`bucket`): both `useCompletionTrend` (week) and `useCompletionThroughput` (day) must use `URLSearchParams` so the resulting string is `?bucket=...&range=...`. A naive template literal `${bucket}${range}` would produce `?bucket=week?range=30d` when both are present. Both keep the same omit-vs-present shape; the exported builder is preferred when a future invalidate/optimistic caller wants to address the key. The two patterns are equivalent; tests for both verify the omit shape byte-for-byte.
- **`useAgentUsage` test is in a new file `agent-usage.test.ts`** (was previously unaccounted for in the hook-coverage map). All other six hooks had existing test files; this one was added in T-003 to lock the range-threading contract alongside the new hook surface.

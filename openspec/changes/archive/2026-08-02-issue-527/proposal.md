## Why

Mohist already has a provider-agnostic input attachment boundary (delivered by issue-513): a Slack user can drop a screenshot or log into Slack and @-mention the Agent exactly as they do in Web/CLI — but today the Slack path throws away the file and forwards only the message text. `AgentLauncher.LaunchConnectionAsync` even rejects attachment-only messages ("connection launches do not accept attachments"). So the most common real entry — *paste a file into Slack and ask about it* — is silently degraded: the Agent never sees the bytes, and the user has no way to learn it didn't. The boundary was deliberately designed to be reusable for exactly this case; this change closes that gap.

## What Changes

- **Slack files become SessionInput attachments.** Files the Bot has been granted access to and that are explicitly attached to the current inbound Slack message (DM launch, DM follow-up, channel root launch, thread reply follow-up) enter the existing attachment boundary and bind to the accepting `SessionInput`, recording user-visible source, name, type, size and availability — same shape as Web/CLI uploads.
- **File content is fetched Server-side.** Following the issue-516 precedent, the `mohist-slack` adapter stays stateless and capped at `chat.postMessage`; it forwards user-visible file metadata extracted from the Slack event, and the Server reads the bytes via new `ISlackApiClient` file methods using the Connection's decrypted bot token. No Server→adapter RPC for reads.
- **Per-file verdict is honest and visible.** Each file is accepted or rejected with a concrete reason (`NotReadable` / `ExceedsSizeLimit` / `UnsupportedType` / `Expired` / `AlreadyBound`). Partial failure is reported per file; Mohist never claims the Agent read a file it did not, and never wraps partial success as total success.
- **Attachment-only Slack input is valid.** A Slack message carrying only files (no task text after removing the Bot mention) creates a well-defined `SessionInput` and starts normally, with no fabricated hidden prompt. Removes the "connection launches do not accept attachments" guard.
- **New `slack` attachment source.** `AgentSessionInputAttachmentDescriptor.Source` gains a `"slack"` value to distinguish provider-sourced files from Web/CLI `"upload"`.
- **Credentials and transient addresses stay inside the Server.** The bot token, Slack's temporary `url_private` download links, and the raw Slack event payload never enter Agent Instructions, replies, or the transcript — the runner keeps resolving content through the existing scoped `openAgentInputAttachment` fetch that reads only from the Mohist-owned store.
- **Single-owner binding preserved.** A Slack-sourced file binds to exactly one `SessionInput`; another member, Session, or Connection cannot reuse it by reference. Files survive adapter/Server restart: each file gets a message-scoped deterministic attachment id (opaque, stable across redelivery) so re-delivery neither re-fetches nor duplicates, layering on the durable provider-inbox / launch-coordinator idempotency already on the Slack path.

## Capabilities

- `slack-attachment-entry`: Slack as an attachment entry point — which Slack files are eligible (explicitly attached to the current message, Bot-authorized), how they are fetched Server-side and materialized into the Mohist attachment store, per-file availability verdicts and honest surfacing, attachment-only input validity on the connection launch/follow-up paths, the `slack` source kind, credential/temp-URL/payload isolation, and single-owner binding. It conforms to the existing provider-agnostic `session-input-attachments`, `attachment-input-lifecycle` and `agent-attachment-delivery` capabilities (unchanged) and spans all four inbound Slack paths (DM launch, DM follow-up, channel root launch, thread reply follow-up).

## Impact

- **`mohist-slack` adapter (`packages/mohist-slack/`):** `SlackEnvelope` (`types.ts`) and the event-normalization in `adapter.ts` carry user-visible file metadata (id, name, mimetype, size) extracted from the inbound Slack event. No new Slack API call is made in the adapter; it stays stateless and capped at `postMessage`.
- **Server Slack API (`packages/server/src/Mohist.Server/Slack/`):** `ISlackApiClient` / `SlackApiClient` gain Server-side file methods (e.g. `files.info` / content download) authenticated with the Connection's decrypted bot token, alongside the existing 8 read methods. New response models for Slack file objects.
- **Server Connection boundary (`packages/server/src/Mohist.Server/Api/SlackConnectionRoutes.cs`):** the DM launch (≈`:1135`), DM follow-up (`RouteFollowupAsync` at `:664`/`:1177`), channel launch (≈`:1798`) and thread follow-up (`:1893`) paths extract file metadata from the inbound body, materialize attachments via `AttachmentService`, and pass descriptors into the launch/follow-up commands. `SlackInboundBody` (`:2072`) carries the transient file list; the provider inbox is unchanged (it dedups by message identity — the message-scoped deterministic attachment id is re-derivable on every delivery, so redelivery resolves to the same bound attachments without persisting file data in the inbox).
- **Agent launcher (`packages/server/src/Mohist.Server/Agent/Services/AgentLauncher.cs:200`):** `LaunchConnectionAsync` accepts attachments and permits attachment-only launches; the empty-prompt guard is replaced by the "non-empty text **or** ≥1 accepted attachment" rule already used by `EnsureInitialLaunch`/`AcceptFollowup`. The coordinator envelope populates `Attachments`.
- **Attachment descriptor (`packages/server/src/Mohist.Server/Contracts/AgentInputAttachmentContracts.cs:12`):** `Source` documents `"slack"` alongside `"upload"` (additive; no serialization break — `[Id(5)]` string).
- **Attachment service (`packages/server/src/Mohist.Server/Issue/Services/Attachments/AttachmentService.cs`):** the existing `ValidateAndBindAgentInputAsync` / `OpenAgentInputContentAsync` / `agent-input` owner-kind paths are reused; a new Server-side ingest (`IngestProviderFileAsync`) writes Slack bytes into `FileSystemAttachmentStorage` under a caller-supplied deterministic id (insert-if-absent) before binding, reusing the pending-TTL / size / type / single-owner rules already enforced there.
- **Runner (`packages/runner/`):** no contract change — Slack-sourced attachments resolve through the existing `openAgentInputAttachment` scoped fetch and the `[mohist-attachments]` manifest exactly like uploads.
- **Design docs:** `design/agent-api.md` §附件边界, `design/slack-agent-connection.md` (实装差距 line listing "附件" as not-yet-provided), and `docs/agent-connections.md` §文件与链接 / 实装差距 already describe this target behavior; the gap notes close without prose changes (the spec already leads implementation).
- **Tests:** spec coverage for the four Slack inbound paths (file → accepted input; per-file rejection; attachment-only launch; credential/temp-URL absent from Instructions/transcript; restart redelivery binds same attachment); unit coverage for the new `ISlackApiClient` file methods, the adapter envelope file extraction, and the `slack` source value.
- **Non-goals (deferred):** files appearing only in imported thread-history startup context (issue-516's text-only import stays a closed unit); auto-opening ordinary URLs or parsing cloud-drive links; auto-uploading Mohist artifacts as Slack files; any cross-Session shared file library.

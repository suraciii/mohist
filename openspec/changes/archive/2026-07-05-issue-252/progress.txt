## Codebase Patterns

- `ui/` directory pattern: one panel per file, peer imports (e.g. `TaskProgressPanel`/`RuntimeDecisionSurface` already consume `format`-style helpers from peers). Following this, `WorkflowView.tsx` is now composition-only and 7 new sibling files own their assigned symbols.
- Verbatim code motion (no behavior change) is the right approach for these god-file decompositions. The oracle is `WorkflowView.test.tsx` (and later `derive-runtime-decision.test.ts`); modify tests only if they break for non-trivial reasons, otherwise treat breakage as a bug.
- `npm install` is required on a fresh workspace before `npm run typecheck`/`test:run` works (no cached `tsc` binary otherwise).
- `tsc -b` runs in `packages/web` and uses `TreatWarningsAsErrors`-equivalent strict mode (unused-import errors abort the build).
- The `ui/` → `model/` import direction is already established (e.g. `WorkflowView` consumes `deriveRuntimeDecision`'s types via `ui/` siblings), so the new `ui/CheckItem → model/runtime-query-helpers` import introduces no new layering direction.

## Discoveries / Gotchas

- Original `WORKFLOW_STAGES` constant was only used in `StageBar.tsx` (and inline in `StepList` + the entry `WorkflowView`). Exported from `StageBar.tsx` so `WorkflowView` and `InlineApproval.tsx` (`StepList`) can both import from one owner — keeps the spec's one-symbol-one-file rule intact.
- `workflowTimelineToStageStateMap` references `useWorkflowTimeline`'s data shape — that hook is imported from `../../../entities/issue` rather than redefined locally. Tried-and-failed pattern: do NOT add a stub `useWorkflowTimeline` shadow to make the type reference resolve; always import the real one.
- `isDeliveryFailureTask` is private to `TaskItem.tsx`. It was already non-exported in the original. T-001 keeps it that way (it's not in the spec's prescribed owner table).
- `isScriptHealthCheck` exists in two places per T-001 scope: `CheckItem.tsx` (the moved copy, `check.checkName === 'health'` shape) and `model/derive-runtime-decision.ts` (the canonical, slightly different signature). The view-side copy is intentionally retained for T-001 and cleaned up in T-002 per design D2.
- The two `isScriptHealthCheck` implementations inspect *different* fields of *different* shapes: the model-side operates on `WorkflowTimelineCheck` (`name: string`) and the view-side operates on `StageCheckState` (`checkName: string`, `output: { kind }`). The verbatim body-move rule still holds: the canonical helper checks `name === 'health'` AND `checkName === 'health'` AND `output?.kind === 'script'` — the union of both predicates, so both call sites see identical return values to before. Behavior on the model's `WorkflowTimelineCheck` shape is unchanged (no `checkName`/`output.kind` fields exist there, so only the `name === 'health'` branch fires); behavior on `StageCheckState` is unchanged (no `name` field, so only the `checkName === 'health'` / `output.kind === 'script'` branches fire).
- `InlineApprovalControls`'s `getApproveLabel` is a tautology (returns `'Approve & Continue'` for all branches). Kept verbatim — the task is structural refactor only, no behavior change.
- `StageBar.tsx` is the only file that needs `useIsMobile` for the stage bar's responsive layout. `StepList` doesn't use it.
- The `workflowTimelineToStageStateMap` cast `stage.status as StageCheckState['status']` was originally `as StageStateRead['checks'][number]['status']`; using `StageCheckState` is equivalent (StageCheckState['status'] === StageStateRead['checks'][number]['status']) and imports a named type already in the entity barrel — small readability win, no behavior change.
- `isFailedCheck` (the helper used only by `findFailedScriptHealthCheck`) moved to `runtime-query-helpers.ts` as a module-private helper alongside `findFailedScriptHealthCheck`. It is intentionally NOT exported (not in the spec's prescribed six); kept co-located with its only caller.
- The timeline parameter type on the exported query helpers is the literal `Pick<WorkflowTimeline, 'currentStage' | 'status' | 'stages' | 'pendingWork' | 'availableActions'>` (equivalent to the prior `RuntimeDecisionInput['timeline']` shape). Using the explicit `Pick<…>` rather than `RuntimeDecisionInput['timeline']` avoids a circular-import hazard (this module is imported *by* `derive-runtime-decision.ts`, which is where `RuntimeDecisionInput` lives).
- T-003 added the per-summary restructure (per design D3/D4). The presentation table lives in `model/runtime-presentations.ts` and the orchestrator stays in `derive-runtime-decision.ts`; the file is small enough (306 lines) that no further split was needed.
- The `RuntimeDecision`/`RuntimeSummary`/`RuntimeActionKind`/`RuntimeDecisionInput` interfaces stay in `derive-runtime-decision.ts` (the public barrel source). `runtime-presentations.ts` imports them via `import type` so no runtime cycle is created.
- Reason strings in actions are **not** templated from labels — labels and reasons can diverge (e.g. label `'Rerun stage'`, reason `'Rerun is not currently offered by the backend projection.'`). Tempting approach `${label} is not currently offered…` would silently shift the rerun reason string. Per-action builders (`buildRetryAction`/`buildResumeAction`/`buildRerunAction`/`buildStopAction`/`buildStartNewWorkflowAction`) hardcode both label and reason verbatim.
- Per design D4, `terminalActions(ctx, terminalKind)` is the shared failed/blocked prefix builder. It returns `[retry, resume, rerun, <terminal>, inspect]` where `<terminal>` is `Start new workflow` for `terminalKind: 'start'` and `Stop` for `terminalKind: 'stop'`. The failed/blocked entries each call it with their tail.
- Cross-cutting fields (`waitReason` set on the `RuntimeDecision`, `blockedReason`, `approvalStage`) stay computed centrally in `deriveRuntimeDecision`. Only `stopRecoverable`, `driftNote`, `pickPrimaryAction`, `determineSummary`, `pickCurrentTask`, `buildWaitReason`, `buildDriftNote`, `isInterrupted`, and `hasRecoverableStop` are orchestrator-side. The presentation table consumes `currentTask`/`waitReason` from a shared context but does not re-derive them.
- The dead-code `if (isBacklog) push start` fallback that originally sat at the bottom of `buildActions` (only reachable for an enum value that no longer exists in the union type) is intentionally NOT replicated in the new structure — under `Record<RuntimeSummary, …>` exhaustiveness, every state has exactly one entry, so the fallback becomes structurally impossible. The 6 typed values all have explicit entries; the test oracle confirms no observable diff.
- `SummaryPresentationContext` is kept module-private (design Open Question). The orchestrator exposes `buildPresentationContext`/`resolveSummaryPresentation` as the only inter-module surface.
- The `if (summary === 'failed')` inside `pickCurrentTask` is intentionally retained: it's classifier-input resolution (the failed summary prefers the failed check before checking running checks), not a per-builder walk over summaries for a presentation projection.
- Compile-time exhaustiveness checked by temporarily deleting/misnaming a PRESENTATIONS key: `tsc -b` reports `Property 'done' is missing in type … but required in type 'Record<RuntimeSummary, SummaryPresentation>'`. Excess keys yield `Object literal may only specify known properties`. Both directions verified.

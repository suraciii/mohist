# Issue #161 — Build stage progress

## T-001 Server PATCH three-state raw-presence-aware merge

### Codebase Patterns

- `AgentDefinitionRoutes.AgentUpdateRequest.BindAsync` is the canonical
  raw-presence pattern (read `Request.Body` as `JsonElement`, walk
  `TryGetProperty`, record each present key into a `HashSet<string>`).
- `IssueQuerier.GetAsync` / `GetInfoAsync` produce the issue's read model and
  are reused by the PATCH handler's response.
- Model metadata persistence is a separate path through
  `IssueWorkflowProfileManager.PatchVariablesAsync` (variables JSON on the
  `IssueWorkflowProfiles` table), not the grain.
- The grain's `UpdateFullAsync(UpdateIssueData)` is also called from
  `AttachmentService.RemoveIssueAttachmentAsync`, so the new
  `PresentFields` field on `UpdateIssueData` is required to be optional and
  default-null (existing call site has not been migrated — passes through to
  the grain with `PresentFields: null`, which the grain now treats as
  "all-unset, behave as legacy".)

### Key decisions / discoveries

1. **The CreateIssueRequest DTO already declared `Model` / `AgentConfig` /
   `StageModels` / `StageModelVariants` / `WorkflowProfileId` but the POST
   handler dropped them.** Design O1 was correct. The fix here routes
   model-metadata on POST and PATCH through the same
   `ApplyUpdateModelMetadataAsync` helper, which calls
   `IssueVariableBuilder.BuildModelMetadataPatch` + `PatchVariablesAsync`.
   This is the same workflow-profile path the design flagged in O1.
2. **The workflow-profile variables use a nested shape `vars.agent.model`
   for the root model AND for per-stage models**, not a flat
   `vars.model` / `vars.agent.model` mismatch. The read path
   (`IssueQuerier.ApplyIssueWorkflowVariables`) expects
   `stage.<name>.vars.agent.model`. `BuildModelMetadataPatch` previously put
   `vars.model = "..."` at the root of each stage instead of
   `vars.agent.model`, which is why stage models never round-tripped.
   Fixed by emitting `{agent: {model: ...}}` for stages too.
3. **The grain's `UpdateFullAsync` previously called `BindIssueAsync` for
   every PATCH that touched `AttachmentIds`, but `BindIssueAsync` is
   add-only.** Existing bindings were never unbound, so present-with-value
   appended instead of replacing, and present-with-null was a no-op.
   Added `ReplaceIssueAsync` (replace semantics, with limit check against
   the new list size) and `UnbindAllIssueAsync` (clear semantics) and
   routed the grain through them based on presence/value.
4. **The PATCH handler now skips label validation when the field is
   absent**, since absent labels means "no change" and validating nothing
   is wasteful. `req.Contains(nameof(Labels))` checks the recorded field
   set.
5. **The CreateIssueRequest also got the same fix:** when `req.Model`,
   `req.StageModels`, etc. are present, the POST handler now persists
   them via `ApplyUpdateModelMetadataAsync` after creating the issue.
   StageModelVariants was not on the create DTO — left as-is (consumers
   don't use it at create time; PATCH is the canonical path).

  keys the user didn't pass. The server contract is now "key absent ==
  preserve", so the CLI no longer needs to send null placeholders.

## T-002 CLI update sends only explicitly-provided fields in PATCH body

### Codebase Patterns

- The CLI's `SetAction(ctx => ...)` lambda receives a `ParseResult`
  (not an `InvocationContext`). `ctx.GetResult(option)` returns
  `OptionResult?` — null when the option was not provided and no
  default value was configured.
- For `Option<bool>` flags, `GetResult` always returns non-null because
  the type's default (`false`) is treated as an implicit result. To
  detect explicit user-pass, check `OptionResult.Implicit` — it's
  `true` for default-derived results and `false` for user-passed.
  Added `IsOptionProvided(ParseResult, Option)` helper to encapsulate
  the rule uniformly across the three `--body-stdin`/`--ready`/`--draft`
  bool flags in `BuildUpdate`.
- Existing `BodyInputResolver` already handles `--body`/`--body-file`/
  `--body-stdin` mutual exclusivity and produces a clear error. It
  required a body source (count > 0) for create, so for update we
  skip the resolver unless the user passed a body source flag.
- The existing label-merge pattern (`LoadCurrentLabelsAsync` →
  `LabelDelta.Apply`) is preserved when `--label` is provided; the
  difference is that the merge result now goes into a `Dictionary`
  slot only when the user actually passed the flag.

### Key decisions / discoveries

1. **Detecting "user provided this flag" differs by option type**:
   - `Option<string?>` / `Option<string[]?>` / `Option<int?>`:
     `GetResult(option) is not null` is sufficient.
   - `Option<bool>`: must use the `Implicit` flag on the result.
   This split pushed us to add a single helper rather than duplicate
   the rule at every option-check site.

2. **Body source conflict detection was implicit before**:
   The previous code only checked `hasAnyBodySource` and ran the
   resolver, but never validated exclusivity at the CLI layer — if
   the user passed both `--body` and `--body-file`, it depended on
   the resolver rejecting it. We now reject conflicting sources at
   the CLI boundary with a clear "pass only one" error before any
   resolution or PATCH, matching `BodyInputResolver.ResolveAsync`'s
   error semantics.

3. **The `isDraft` payload key follows `bool` (not `bool?`)**:
   The conditional `payload["isDraft"] = draftState == Draft`
   is cleaner than the previous `bool?` switch and produces the
   correct JSON (`true` for `--draft`, `false` for `--ready`) without
   risk of `null` reaching the wire when the flag was provided.

4. **The PATCH body is now `Dictionary<string, object?>`** rather
   than anonymous object. This is a structural change but it's
   invisible to the server because `System.Text.Json`'s serializer
   produces the same wire shape from both. The dictionary approach
   makes the omit-vs-send contract explicit and easy to extend for
   T-003 (`stageModels`, `stageModelVariants`).

## T-003 CLI create/update execution config flags

### Codebase Patterns

- `JsonInputResolver` (new, alongside `BodyInputResolver`) handles
  inline JSON or `@<file>` references. Returns `Result.Success(value)`
  on success and `Result.Failure(message)` on parse / IO error. The
  caller writes the message and exits 1. Used for
  `--stage-models` and `--stage-model-variants` (create + update).
- Both `BuildCreate` and `BuildUpdate` use the T-002 dictionary
  pattern. `BuildCreate` always sends `title/body/labels/priority/
  model/workflowProfileId/risk/isDraft` (server-required fields)
  but only adds `repositoryName`, `stageModels`, `stageModelVariants`
  when the user passed the flag (preserved by `ctx.GetResult(opt) is
  not null`). `BuildUpdate` only adds keys for flags the user
  passed, including the new exec-config keys.
- `repositoryName` is the wire key (`CreateIssueRequest.RepositoryName`).
  `stageModels` / `stageModelVariants` mirror the existing JSON
  shape from `CreateIssueRequest` / `UpdateIssueRequest`.
- The `--repository` flag is registered on update but rejected at
  the top of `UpdateAsync` with a clear "immutable" error. The
  description on the option itself notes "(Not allowed) Repository
  ownership is immutable after creation".

### Key decisions / discoveries

1. **`@<path>` was previously swallowed by System.CommandLine's
   response-file handler.** System.CommandLine 2.0.2 treats `@file`
   as a response-file prefix by default and expands its contents
   into argv. This broke `--stage-models @models.json` because the
   `@` got consumed before our option received any value. Disabled
   globally in `MohistCliCommands.RunAsync` by passing
   `ParserConfiguration { ResponseFileTokenReplacer = null }` and
   calling `CommandLineParser.Parse(root, args, parseConfig)`
   instead of `root.Parse(args)`. No existing test relied on
   response-file expansion; verification: `npm test -w packages/cli`
   passes 125/125 after the change. This also means `--body @file`
   (a future option) will work without further plumbing.
2. **`JsonInputResolver.Deserialize<object?>` is the right
   abstraction.** The server treats `stageModels` and
   `stageModelVariants` as `Dictionary<string,string>` and we could
   deserialize to that exact shape. But generic `object?` keeps
   the helper reusable for `--agent-config` (future) and lets
   System.Text.Json emit the same wire JSON the caller already
   expected from inline strings. The serializer handles
   `JsonElement` → `Dictionary<string,string>` natively.
3. **`ctx.GetResult(opt) is not null` is the same gate T-002 used
   for `Option<T?>` flags**, so the new exec-config flags slot in
   without introducing new "explicit-pass" detection patterns.
4. **`--repository` on update is rejected with a pre-flight check
   at the top of `UpdateAsync`**, before project resolution. This
   means even if `--project` / `--project-id` are invalid the
   repository error wins, which is the right precedence: the user
   can fix the immutable-flag mistake before chasing project
   issues.

## T-004 CLI prereq add/remove subcommands

### Codebase Patterns

- `PrintDeleteAsync` (path-only) and `PrintDeleteWithOutputAsync`
  (with `mode` + `tableShape`) already existed in `MohistCliApi.cs`
  — no new helper needed. The T-004 task description's note about
  "Add a PrintDeleteAsync helper" is satisfied by the existing one
  added in earlier work.
- The new subcommand group follows the `BuildFeedback` / `BuildWorkflow`
  pattern: outer `BuildPrereq` builds a `Command("prereq", ...)` and
  adds `BuildPrereqAdd` / `BuildPrereqRemove` as subcommands.
- The `prereqNumber` argument is declared as `Argument<int>` so the
  parser rejects non-numeric input before any HTTP call — the
  server only sees well-formed ints.

### Key decisions / discoveries

1. **`PrintPostWithOutputAsync` and `PrintDeleteWithOutputAsync` are
   the right helpers.** They already route errors to stderr with
   the `code (error)` envelope shape (`PrintResponseAsync`) and
   honor the output-mode table/json split via `PrintEnvelopeAsync`.
   No new error-surfacing path is needed: a server `404 +
   { success:false, error, code }` response is printed to stderr
   and exits non-zero automatically.
2. **`IssueShow` table shape for the response** is reused because
   the POST/DELETE handlers return the issue read model. The
   `table` mode renders the issue cleanly; the `json` mode prints
   the raw JSON envelope. Future tasks that return a different
   shape (e.g., comment id) should add a new `TableShape`.
3. **Argument order matches the task description**: `<number>
   <prereq-number>` in that order — `<number>` first (matches
   every other issue subcommand) then `<prereq-number>`. Both
   required positional `Argument<int>`.
4. **Test coverage uses `RecordingHttpHandler` with a per-test
   `responder`** that returns the appropriate JSON envelope for
   success or failure paths. This matches the T-003 test pattern
   and avoids sharing a single responder across tests.

## T-005 CLI comment add and feedback create subcommands

### Codebase Patterns

- The existing `feedback` group was `BuildFeedback` with two children:
  `BuildFeedbackList` and `BuildFeedbackShow`. T-005 just adds
  `BuildFeedbackCreate` as a third child — no new wrapping group needed.
- The `comment` group is brand new: `BuildComment` returns a `Command`
  containing only `BuildCommentAdd` (the single subcommand listed in the
  acceptance criteria).
- Both new commands use `BodyInputResolver` for `--body`/`--body-file`,
  matching `BuildCreate` / `BuildUpdate`. Stdin is not exposed because the
  task description doesn't list it; passing `false` for `bodyStdin` keeps
  the resolver from waiting on an empty stdin in non-interactive test
  runs.
- `PostAndReadAsync` is the right helper when the response body is needed
  to extract the new id. The `PostResult.Data` is a `JsonNode` parsed from
  the envelope's `data` field, which is exactly what we want to read
  `id` from. On success the CLI prints `Created comment <id>` /
  `Created feedback <id>` to stdout; errors still route through the
  server envelope and land in stderr via `ReadPostResultAsync`.

### Key decisions / discoveries

1. **`--stage` validation happens before project resolution.** The
   feedback create command checks `stageProvided && !IsNullOrWhiteSpace`
   first; this gives the user a fast, project-agnostic error when they
   forget the flag. `--body` is validated by `BodyInputResolver` after
   project resolution because the resolver also reads from the
   filesystem (or stdin) and we don't want to fail noisily before the
   project is known. The comment command doesn't validate `--body`
   upfront at all — it goes straight to the resolver, which is what the
   spec calls for ("missing body fails clearly").
2. **No `--body-stdin` exposed.** The acceptance criteria list
   `--body` and `--body-file` only. We pass `false` for `bodyStdin` to
   keep the resolver's stdin branch inert; a future task can add the
   flag without touching the resolver.
3. **The new id is printed to stdout on success.** The comment endpoint
   returns `{ id, body }` (see `IssueRoutes.Lifecycle.cs:88`) and the
   feedback endpoint returns the full `WorkflowFeedbackRecord` (see
   `IssueRoutes.Feedback.cs:36`). Both serialize into `data` of the
   envelope. `PostResult.Data["id"]` works for both because the feedback
   record carries `id` as a top-level field.
4. **Help text inherits from existing subcommands.** The new commands
   list naturally in `mo issue comment --help` and
   `mo issue feedback --help` because System.CommandLine walks
   `Subcommands` for the help text. No manual help wiring needed.

## T-006 CLI reject and stop actions

### Codebase Patterns

- Both `BuildReject` and `BuildStop` are sibling single-action commands,
  not group-with-subcommands. They sit alongside `BuildAction` in
  `IssueCommands.Build` rather than wrapping their own `Command` group,
  because the spec only has one verb each (`reject`, `stop`) and the
  surface matches `start` / `approve` / `close` / `force-stop` / `resume`.
- `BuildReject` is a custom build (not a `BuildAction` clone) because it
  carries a required `--message` flag whose value goes into the POST body
  as `{message: "..."}`. `BuildAction` always sends an empty body, so the
  extra wiring is local to `BuildReject`.
- `BuildStop` is a custom build (also not `BuildAction` clone) because
  it needs an `-o table|json` output option for the post-stop readback,
  matching `BuildPrereqAdd` / `BuildPrereqRemove` / `BuildCommentAdd` /
  `BuildFeedbackCreate`. `BuildAction` doesn't accept `-o`.
- The terminal-vs-pause distinction is encoded in the **command's
  `Description`** ("Stop the workflow run permanently (terminal — cannot
  be resumed; use 'force-stop' if you want a pause you can resume)"),
  so it shows up in both `mo issue stop --help` and `mo issue --help`'s
  command-list output. The alternative — using a separate help-only
  attribute — would not surface in the parent's command-list rendering.

### Key decisions / discoveries

1. **`System.CommandLine` 2.0.2 does not support `Option.IsRequired`.**
   The package version pinned in `Directory.Packages.props` is 2.0.2;
   `IsRequired` lands in 2.1+. To meet the spec's "missing `--message`
   exits 1 with a clear error" requirement, validation runs at the top
   of `BuildReject.SetAction` — same pattern as `BuildFeedbackShow`'s
   `Either --feedback <id> or --latest is required` check and the
   `BuildFeedbackCreate` `if (!stageProvided || string.IsNullOrWhiteSpace(stage))`
   gate. Empty/whitespace messages also fail validation, so
   `mo issue reject 42 --message "   "` prints `--message is required
   and must not be empty` and exits 1 (no POST sent).
2. **Empty-body POSTs use `new { }`, matching `BuildAction`.**
   `BuildStop` posts an empty body, same as the existing single-action
   verbs (`start`, `approve`, `force-stop`, etc.). The server's
   `RejectRequest` and stop endpoint both accept empty bodies — the
   reject endpoint validates `req?.Message` independently and rejects
   missing/empty messages with 400, so even if the CLI's `--message`

3. **Help text is a sibling-level disambiguator.** Instead of a
   separate "see also" footnote, the stop command's description names
   `force-stop` and explains "terminal — cannot be resumed; use
   'force-stop' if you want a pause you can resume". This way the user
   sees the contrast in `mo issue --help`'s command listing without
   needing to run `mo issue stop --help` separately. The
   `IssueStop_HelpExplainsTerminalAndDistinguishesFromForceStop` test
   asserts both terms ("terminal", "force-stop", "resume") appear in

4. **`-o table|json` is wired through `PrintPostWithOutputAsync` with
   `IssueShow` table shape**, the same choice T-004 made for prereq
   add/remove. The POST returns the issue read model, so the issue
   table renders cleanly in `-o table` mode and the raw envelope in

## T-007 Build verification fix (post-completion check)

### What was broken

The verify check failed with one build error, one runner typecheck error,
and three web test failures. None of the failures were in code introduced by
T-001..T-006 — they were all pre-existing regressions from completed prior
work that hadn't been caught by the earlier "build stage" verification.

### Codebase Patterns (newly discovered)

- `AgentSessionLabels` table was dropped in
  `20260620185946_ReplaceAgentSessionLabelsWithComputedColumns` and replaced
  with STORED computed columns on `AgentSessions` (`LabelSourceId`,
  `LabelSessionName`, `LabelProjectId`, etc.). The migration comment
  explicitly says "These replace the former AgentSessionLabels index table".
  Tests written before that migration still querying
  `db.AgentSessionLabels` need to be migrated to `db.AgentSessions` with
  the new column filters — the same pattern is used in
  `AgentSessionRecoveryApiSpecs.cs:248-255` and
  `IssueSessionApiSpecs.cs:395`.
- The runner's `WorkDispatchResponse` (in `runner/src/core/types.ts`) does
  **not** carry an `outputs` field — the server's `RunnerRoutes.cs:319`
  record doesn't include it. Commit `371663499` (issue #242) added a
  `outputs: dispatch.outputs` line in `connection.ts` `toWorkItem` and a
  `WorkItem.outputs` field on the consumer side, but the server never
  started sending `outputs`, so the line was a stale typecheck error.
  `captureOutputs(WorkItem["outputs"], ...)` in `output-capture.ts` is
  null-safe (returns undefined if outputs is null), so removing the
  source-side assignment is a no-op rather than a feature regression.
- The runner's `GetWorkspaceStatus` handler test
  `GetWorkspaceStatus_WhenFetchFails_ReturnsExistingWorkspaceWithRebaseState`
  asserts that the fetch is **always** attempted and the reason reflects
  the fetch result (`fetch_failed`) even when a rebase is in progress.
  The pre-existing source short-circuited on `rebaseInProgress` and
  returned `rebase_in_progress` without attempting the fetch — so the
  test was failing. Fix: attempt fetch first, then check rebase.
- Web tests using `daysAgo(N)` against a hardcoded `NOW` constant can
  become time-sensitive once the wall clock drifts past
  `NOW + (7 - N) days`. `useCompletionSnapshot` and `SnapshotRow` use
  `Date.now()` (not the test constant), so when run on 2026-06-23 (4 days
  past the test's `NOW = 2026-06-19`), `daysAgo(3)` lands at the 7-day
  window boundary and falls outside. Fix: `vi.useFakeTimers()` +
  `vi.setSystemTime(new Date(NOW))` in the test's `beforeEach`.

### Key decisions / discoveries

1. **Migration of stale test to new table shape is in-scope for the
   build fix.** `SessionFollowupApiSpecs.cs:225-235` had `db.AgentSessionLabels`
   which no longer exists on the DbContext. Following the pattern from
   `AgentSessionRecoveryApiSpecs.cs`, the helper was rewritten to
   `db.AgentSessions.Where(s => s.LabelSourceId == workflowRunId && s.LabelSessionName == sessionName).Select(s => s.Id).SingleAsync()`.
   The test was added by issue #242 (commit `371663499`), which
   paralleled the migration commit `4ff494a9a` ("Simplify workflow
   runtime profile") — they were on adjacent commits and the test
   update was missed.
2. **Removing the `dispatch.outputs` line in connection.ts is correct
   even though issue #242 added it.** The server-side `WorkDispatchResponse`
   in `RunnerRoutes.cs` doesn't send `outputs`, and the runner-side
   `captureOutputs` is null-safe. The right fix is to remove the stale
   line; wiring the `outputs` field through the server's `WorkDispatchResponse`
   and dispatch builder is a separate concern not in scope for the build
   fix (would touch the server's `WorkDispatch` builder). Treated as a
   "stale line from a partial migration" and removed, not as a feature
   regression.
3. **`GetWorkspaceStatus` source ordering fix matches the test contract.**
   The test name is "WhenFetchFails_ReturnsExistingWorkspaceWithRebaseState"
   and the assertion includes both `rebaseInProgress: true` (from
   `rebase --show-current-patch` succeeding) and `reason: "fetch_failed"`
   (from `fetch` failing). The only way to satisfy both is to attempt the
   fetch first. New order: `if (fetch failed) return fetch_failed` →
   `if (rebaseInProgress) return rebase_in_progress` →
   `return ahead/behind`. This is a small reorder that aligns the source
   with the documented contract.
4. **Web test `useFakeTimers` setup must use the test's `NOW` constant,
   not the current wall clock.** Both `completion-snapshot.test.ts` and
   `SnapshotRow.test.tsx` define a hardcoded `NOW = 2026-06-19T12:00:00.000Z`
   and `daysAgo(N)` derives from it. The hooks they exercise use real
   `Date.now()`. To make the tests deterministic regardless of when they
   run, `vi.useFakeTimers()` + `vi.setSystemTime(new Date(NOW))` was
   added in `beforeEach`, with `vi.useRealTimers()` in `afterEach`. This
   is a test-only fix, no source change.

### Gotchas for downstream tasks

- Any test or helper that resolves an `AgentSession` by
  `(workflowRunId, sessionName)` MUST use the new
  `db.AgentSessions.Where(s => s.LabelSourceId == ... && s.LabelSessionName == ...)`

  dispatch payload to the runner. Today `captureOutputs` always returns
  undefined because no dispatch ever carries an `outputs` field. Out of
  scope for issue #161 but worth a follow-up.
- `useFakeTimers()` in vitest requires `vi.setSystemTime(...)` to take
  effect for `Date.now()`. A bare `vi.useFakeTimers()` without
  `setSystemTime` freezes the clock at the actual test start, not at
  the test's hardcoded `NOW`. The two web tests needed both.

  WorkspacePanel.test.tsx assertions. If a future i18n pass reverts any

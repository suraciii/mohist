## T-003 Gotchas

- `lowlight@3.3.0`'s `package.json` declares `"exports": "./index.js"` — `lowlight/lib/common` is NOT in the `exports` field and Node throws `ERR_PACKAGE_PATH_NOT_EXPORTED` if you try to import it. The design's literal `lowlight/lib/common` path is therefore not importable as written. The functional intent ("use only the common subset, not the full highlight.js grammar set") is preserved by importing `common` from `lowlight` itself: that export is literally `export { grammars as common } from './lib/common.js'`, so the grammars map is identical. Documented inline in `transcript-markdown-theme.ts` and as a progress note.
- Vitest's Vite transform pipeline does not handle `?raw` or `?inline` for CSS files at all. The `default` export resolves to a `string` of length 0. I confirmed this by writing a throwaway test that did `await import('highlight.js/styles/github.css?raw')` and dumping `mod.default.length` to `/tmp/dump.txt` — got 0. Same for `?inline` and `?url`. Even a workspace-relative CSS file with `?raw` returns empty. Resolution paths considered and rejected: configuring vitest's `server.deps.inline` (only inlines node_modules deps into vite-node, doesn't help with the CSS suffix); adding a custom Vite plugin to handle `?raw` for CSS (a bigger change for a small benefit). Settled on embedding the github.css verbatim as a string constant (~2.2 KB minified) — the file is stable across highlight.js v11.11 minor versions and matches the upstream "GitHub" theme. A comment in the module notes the source.
- jsdom prints `Could not parse CSS stylesheet` warnings when the injected `.transcript-md .hljs-*` stylesheet is parsed. These are non-fatal — jsdom's permissive parser is complaining about a CSS construct it doesn't fully understand (e.g. one of the comma-separated descendant combinators like `.hljs-meta .hljs-keyword`). The test suite still passes (all 2473 tests green); the warnings are filtered to stderr by jsdom and don't show up as test failures.
- A fenced code block without a language tag (`` ```\nplain code\n``` ``) does NOT receive the `hljs` class. This is rehype-highlight's intentional behavior: with `detect: false` (the default) and no language className to look up, the plugin returns early without modifying the AST. The original `AssistantParts.tsx` heuristic (`isInline = !match && !className`) was also wrong on this case — it would have rendered the block as inline code. The new `TranscriptMarkdown` uses a `CodeBlockContext` (set by the `pre` override) to distinguish block from inline, so the no-language case correctly renders as a `<pre><code>plain code</code></pre>` block with the block styling; it just isn't colorized.
- `rehype-highlight` mutates the hast tree by adding `className` arrays to the `<code>` element. The test asserts on `code.className` containing both `hljs` and `language-ts` — react-markdown serializes the array as a space-separated className string in the rendered DOM.
- `lowlight@^3.0.0` is already a transitive dep of `rehype-highlight`, so the `import { common } from 'lowlight'` in `TranscriptMarkdown.tsx` resolves through the same lockfile entry. No need to add `lowlight` to `packages/web/package.json` directly — npm/npm-install handles the deduplication.
- `AssistantParts.render.test.tsx` was not modified — none of its 10 tests assert on the inline `<Markdown>` directly, so the swap to `<TranscriptMarkdown>` is invisible to the existing assertions (which only assert on the `Copy` button, streaming indicator, and tool-part rendering). 2473 tests pass; the existing 6 `AssistantParts` + 7 `TurnList` + 172 `SessionPage` + 26 `MarkdownReader` tests all stay green.

## T-004 Gotchas

- Initial entry targets are `null` on the first render: `useState`-based `refsVersion` bump in `useEffect` is what makes the second render's entries target the real DOM nodes. The flicker is invisible to a user (one frame) but visible in tests that `fireEvent.click` synchronously after `render()`; tests must `await waitFor(...)` if asserting on `scrollIntoView` against the populated Map. The integration tests `render` + `fireEvent.click` synchronously and the click resolves against the post-effect version of entries — React Testing Library flushes effects synchronously inside `render`, so by the time `fireEvent.click` runs the second render has happened. This was verified by running the tests.
- jsdom does not apply CSS, so the Tailwind `lg:grid-cols-[1fr_180px]` + `hidden lg:block` classes are inert in tests. That means: (1) the rail's `hidden` class doesn't actually hide it from the DOM in tests, so `document.querySelector('[data-turn-toc-rail]')` finds it even at `window.innerWidth = 320`. (2) The toolbar's `lg:hidden` doesn't actually hide it, so `document.querySelector('[data-transcript-toolbar-toc-trigger]')` finds it at `window.innerWidth = 1280`. The tests assert on the presence of these elements + their className contract (e.g. `'hidden lg:block'`), not on visual layout. The `no-overflow at 320/375/430px` integration test specifically fakes `scrollWidth`/`clientWidth` getters on the scroll container and asserts `scrollWidth <= clientWidth` — this is the "weak but contract-binding" assertion the design prescribes (D7, Risks).
- The followup composer is OUT OF SCOPE for T-004 — it doesn't yet have the `[data-composer-input]` attribute that T-005's `useTurnKeyboardNav` needs. The current T-004 listener just bails out on `input, textarea, select, [contenteditable]` — the followup composer textarea matches `textarea` so it's covered.
- `useEffect([turns.length])` deliberately depends on the array LENGTH, not the array identity. React doesn't deep-compare array deps, but checking length is a cheap proxy for "did the set of turns change". When a streaming event appends a single new turn, `turns.length` increments by 1 and the effect fires. When an existing turn's content updates without adding/removing a turn, length is stable and the effect doesn't fire — which is correct (existing refs are still valid).
- The `max-w-[90%] sm:max-w-[80%]` switcheroo is the D7 fix: at 320–430 px, `max-w-[80%]` left a `min-w-0` flex child with too much reserved width and forced the parent to overflow horizontally on long unbreakable strings. `max-w-[90%]` buys 10 % more breathing room on the narrowest viewports, then snaps back to `80%` at `sm+`. `sm:` is Tailwind's 640 px breakpoint, which is BELOW the 1024 px `lg:` breakpoint where the rail appears — so the rail never collides with the `max-w-[80%]` cap.
- `TranscriptToolbar` overlay has `max-w-[calc(100vw-2rem)]` so on really narrow viewports (e.g. 320 px) the overlay can't bleed past the viewport edges. Z-index `z-20` puts it above the turn list and any sticky elements.

## T-005 Decisions

- D4: `useTurnKeyboardNav({ scrollContainerRef, turnRefs, turnCount })` lives in `widgets/session-transcript/model/useTurnKeyboardNav.ts`. Single `useEffect([scrollContainerRef])` — attaches one `keydown` listener on `scrollContainerRef.current ?? window` on mount and detaches on unmount. The effect deps intentionally exclude `turnRefs` and `turnCount`; those are stored in refs (`turnRefsRef.current = turnRefs` and `turnCountRef.current = turnCount` on every render) so the listener closure always reads the latest values without re-attaching. This keeps the listener cheap and stable across streaming re-renders.
- D4 (deferral): The handler bails out on any `event.metaKey` / `ctrlKey` / `altKey`, and on `document.activeElement.closest('input, textarea, select, [contenteditable="true"], [data-composer-input]')`. The bail-out uses `Element.closest()` (not `matches()`) so the selector matches nested editables too — the spec calls this out via "any `input`/`textarea`/`select`/`[contenteditable]`/`[data-composer-input]`". The followup composer is covered today by the `textarea` selector (its `<Textarea>` matches `textarea`); the `[data-composer-input]` selector is future-proofing for a hypothetical contenteditable refactor of the composer.
- D4 (current-turn derivation): `computeCurrentIndex(container, refs)` scans the `turnRefs` Map in key order (1, 2, 3, ...) and finds the LAST element whose `getBoundingClientRect().top` is `<= containerRect.top + 120`. Returns 0 when no turn is above the threshold. The `top` field of `getBoundingClientRect` is viewport-relative; subtracting `containerRect.top` gives container-relative position, so the threshold naturally accounts for the scroll container's offset from the viewport (e.g. when it sits below the `SessionHeader`). No `IntersectionObserver` is needed; jsdom doesn't implement it and this approach works in jsdom without polyfills.
- D4 (boundary clamping): `j` clamps `currentIndex + 1` to `turnCount`; if clamped value equals `currentIndex`, return early (no-op at last turn). `k` clamps `currentIndex - 1` to `1`; if clamped value equals `currentIndex`, return early (no-op at first turn). `g` (no shift) -> `1`; `G` (or `g` with `shiftKey`) -> `turnCount`. The no-op detection is key — without it, `j` at the last turn would scroll to `turnCount + 1` (which doesn't exist), and `k` at the first turn would scroll to `0` (also doesn't exist). The Map lookup `refs.get(targetIndex)` would return `undefined` for these and we'd silently do nothing, but the explicit early return makes the intent clear and avoids the lookup.
- D4 (wiring): `SessionTranscriptLayout` gained a new optional `scrollContainerRef?: RefObject<HTMLElement | null>` prop. Inside the layout, `useTurnKeyboardNav({ scrollContainerRef, turnRefs, turnCount: turns.length })` is called after the refs map + `useEffect([turns.length])` bump + `buildTurnTocEntries` memo. `SessionPage.tsx` passes `scrollContainerRef` (the existing `useRef<HTMLDivElement>(null)` on the scroll container `<div ref={scrollContainerRef}>` at line 770) down to the layout. The hook is naturally scoped to the page because the layout is only mounted while the page is alive.
- The hook does NOT call `event.preventDefault()` — the spec doesn't require it and it could interfere with browser quick-find features. The listener bails out early on most keypresses (modifiers, focused editables, unrelated keys), so the browser sees a keypress it can ignore.

## T-005 Gotchas

- The hook uses `RefObject<HTMLElement | null>` rather than `RefObject<HTMLElement>` because the page's `useRef<HTMLDivElement>(null)` declares `null` as the initial value. React 19 + TypeScript treats this as `RefObject<HTMLDivElement | null>`, which is the same as `RefObject<HTMLElement | null>` via structural compatibility. The hook's optional null fallback also lets it work without a ref at all (falls back to `window`).
- jsdom focus quirk: `element.focus()` on an element NOT attached to the document is a no-op (the element doesn't actually receive focus). The unit test must append the container to `document.body` before calling `focus()` on a child — without attachment, `document.activeElement` remains `document.body` and the focus-deferral assertions fail. The integration test (rendered through React, which attaches automatically) does not need the manual attachment.
- jsdom `getBoundingClientRect` returns `{ top: 0, left: 0, ... }` by default for all elements. The hook's `computeCurrentIndex` requires per-element rects to verify the "last turn above threshold" semantics — tests mock `Element.prototype.getBoundingClientRect` with a per-element `Map<Element, DOMRect>`. The mock is set up in `beforeEach` for the unit test (and restored in `afterEach`).
- `fireEvent.keyDown(window, ...)` works for testing the window-fallback path. The `act()` wrapper is used around the window dispatch because the listener is registered outside React's render tree (it's on `window`), so React wouldn't otherwise wrap the side effect.
- `scrollIntoViewSpy.mock.instances[0]` is the `this` of the spied call — i.e. the `HTMLElement` whose `scrollIntoView` was invoked. With the spy on `Element.prototype.scrollIntoView`, `mock.instances[i]` is the actual DOM element passed to `scrollIntoView`, which equals `turnRefs.get(targetIndex)` when the hook calls `ref.scrollIntoView({ block: 'start' })`. Tests use `toBe()` (reference equality) on `mock.instances[0]` and `turnRefs.get(N)` to assert the correct target.

## T-006 Decisions

- D6 (serializer): `serializeTranscriptPlainText(turns: DisplayTurn[])` lives in `widgets/session-transcript/model/serialize-transcript.ts`. It is a pure function (no IO, no React, no `Date.now()`/randomness) that:
  1. Returns `''` when `turns.length === 0` (no trailing newline — the button is disabled in that state, so the contract is just "no surprises").
  2. For each turn builds a `string[]` section: `== Turn N · <kindLabel> · <toLocaleString(startedAt)> ==` + prompt section lines + assistant part lines.
  3. Prompt section lines: `title` (skip if falsy), `subtitle` (skip if falsy), `Output: <outputPath>` (only when not redundant with subtitle, mirroring `PromptBlock.tsx:64-66` so the copy reflects what the user sees), `Context: <files joined>` (skip when no context files), and the raw prompt `text` (skip when falsy).
  4. Assistant part lines: text in full; reasoning as `[reasoning omitted, X KB]` where `X = (text.length / 1024).toFixed(1)` (matches `ReasoningPartView` in `AssistantParts.tsx:53`); tool parts as `[tool <normalizedName>] <displayTitle|title|target|>` (fallback chain: displayTitle → title → target → bare name); context-group parts as `[context-group] <title>`; error parts as `[error] <message>`; divider parts as `[divider] <label>`.
  5. Joins each turn section's lines with `\n`, joins turn sections with `\n\n`, `trimEnd()`s, then appends a final `\n` so the output ends with a newline.
- D6 (memoization): `CopyFullTextButton` uses `useMemo(() => serializeTranscriptPlainText(turns), [turns])` keyed on the `turns` reference. Tests confirm rerendering with the same reference produces identical serialized output (no redundant re-serialization on every keystroke/parent re-render); rerendering with a different reference recomputes.
- D6 (clipboard pattern): The button uses `navigator.clipboard?.writeText` (the robust existence check from `ArtifactContentViewer.tsx:89`). When `navigator.clipboard` is absent the handler sets `data-state="failed"` and calls `toast.error('Clipboard is unavailable in this browser.')` — never reports success. When `writeText` rejects the second `.then` callback fires the same `data-state="failed"` + `toast.error('Failed to copy transcript to clipboard.')` path. No bare `.then(...)` that silently swallows failure.
- D6 (UI): Button rendered inside `TranscriptToolbar`'s `rightSlot` so it sits to the right of the mobile TOC trigger below `lg` (the lg+ rail remains on the right gutter). Label: `'Copy full text'` → `'Copied!'` for ~2s on success, stable `'Copy full text'` on failure. `data-state` cycles through `'idle' | 'copied' | 'failed'`; `data-copy-full-text=""` and `aria-label="Copy full transcript text"` for test selectors / a11y.
- D6 (timing): The 2s auto-reset is wired via a `useEffect([status])` that schedules `setTimeout(() => setStatus('idle'), 2000)` and clears it on unmount/status-change. This mirrors the existing pattern at `PromptBlock.tsx:31` / `AssistantParts.tsx:24` but adds the cleanup-on-unmount (those callers don't unmount during a copy cycle, but the transcript page does when navigating away).

## T-006 Gotchas

- `Array.prototype.join('\n\n')` on an array of arrays turns each inner array into a comma-separated string via `Array.toString()` — first version of the serializer produced `Turn 2 · ... ==,Wire TOC,Add the toolbar TOC trigger.,On it.` instead of newlines. Fix: `.map((turn, i) => turnSection(i + 1, turn).join('\n')).join('\n\n')` — map inner turn sections into strings before joining.
- `vi.useFakeTimers()` + `waitFor` race: fake timers make `waitFor`'s polling loop (which uses `setTimeout`) wait on the fake clock, but React's microtask queue and the `setTimeout(..., 2000)` reset effect can land in inconsistent order. Two paths the tests take now: (a) most cases use real timers + `waitFor` for state transitions; (b) the two "reset after ~2s" tests wrap `vi.useFakeTimers()` / `vi.useRealTimers()` in a `try/finally` per-test, and call `vi.waitFor(...)` (the bound `vi` namespace, not `@testing-library`) so the polling survives under fake timers. The other 10 tests stay on real timers.
- `setClipboard(undefined)` between tests: `Object.defineProperty(navigator, 'clipboard', { value: undefined, configurable: true })` plus `setClipboard(originalClipboard)` in `afterEach` restores the session-wide clipboard mock from `SessionPage.test.tsx:60-63`. Without the restore, the second test sees `navigator.clipboard === undefined` and the "is disabled when turns.length === 0" assertion still passes (the button is disabled regardless), but later tests could see a stale writeText. Restoration keeps the suite isolated.
- `navigator.clipboard` defineProperty on jsdom: the getter must be `configurable: true` so subsequent `Object.defineProperty` calls can replace the value. The first version of `setClipboard(undefined)` used `{ writable: true }` which throws on a non-writable getter.
- The serializer uses `toLocaleString()` (date + time) for the turn header timestamp, matching `PromptBlock.tsx:14` (`formatDateTime`). The T-002 turn header at `TurnList.tsx:91` uses `toLocaleTimeString()` (time only) for the inline marker. They are deliberately different — the inline marker is a small subtle indicator, the copy header is a fuller reference.

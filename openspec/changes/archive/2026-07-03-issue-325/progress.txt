# Issue 325 — T-001 (IssueStore legacy label cleanup)

## Codebase Patterns
- `IssueStore` is the single persistence entry point for `DomainIssue`; its `Serialize` and `Deserialize` are `static` and live in `packages/server/src/Mohist.Server/Infrastructure/Data/Issue/IssueStore.cs`. Both are called from many specs and services via the bare class name (`IssueStore.Serialize/Deserialize`).
- `Deserialize` was previously 2-arg with an `out bool legacyLabelsDiscarded` flag — but in the codebase there was **no external consumer** of that overload. It existed only to be called by the 1-arg overload internally, so deletion has zero blast radius on production code.
- `Issue.Labels` is a `IReadOnlyDictionary<string, string>` with an initializer that runs `ReplaceLabels(value, recordEvent: false)`. STJ on a JSON array as a dictionary throws `JsonException` ("could not be converted to IReadOnlyDictionary...") — confirming the new spec scenario "legacy array-format labels are no longer normalized" manifests as a thrown exception rather than silent empty.
- `IssueDomainSpecs` / `IssueStartReadinessDomainSpecs` / `IssueWorkflowProfileSelectionSpecs` / `IssueWorkflowRunReferenceSpecs` / `BackfillIssueCompletedAtMigrationSpecs` already used the 1-arg overload, so they were untouched. Only `IssueLabelsSpecs.cs` had 2-arg callers.
- `Build` is gated by `TreatWarningsAsErrors` — the `dotnet build Mohist.sln` step is the no-warning lint.

## Decisions / Discoveries
- The 2-arg `Deserialize` overload and `NormalizeLegacyLabels` had no production callers (only the openspec docs and the test in `IssueLabelsSpecs.cs`). Deletion is safe.
- After removal, the surviving `Deserialize(string)` is a one-liner: `string.IsNullOrEmpty(json) ? null : JSON.Deserialize<DomainIssue>(json)`. The intermediate `out _` discard is gone.
- Orphan `using System.Text.Json;` removed; `JsonDocument` / `Utf8JsonWriter` / `MemoryStream` / `System.Text.Encoding.UTF8` references are gone with it.
- Test updates required by the spec change (per `specs/issue-persistence-legacy-cleanup/spec.md`):
  - `IssueLabelsSpecs.Deserialize_LegacyArrayLabels_NormalizesToEmptyMap` — semantics flipped: now asserts the legacy array is **not** normalized (asserts `ThrowsAny<Exception>`).
  - `IssueLabelsSpecs.Deserialize_ObjectLabels_RoundTripsAsMap` — drops the `out discarded` argument; only asserts the round-trip value. The current label object format behavior is preserved unchanged.
  - `IssueStartReadinessDomainSpecs.Deserialize_StateBlobWithoutIsDraft_DefaultsToReady` — the legacy JSON used `labels: []` (an array). With normalization gone, that throws. The test's actual purpose is to verify the `isDraft` default, so the JSON was changed to `labels: {}` (object, empty). The test name and intent are unchanged.
- No `JSON` helper API changes — `JSON.Serialize` / `JSON.Deserialize` are still the only touch points.

## Gotchas for Later Tasks
- The same `labels: []` array-form pitfall applies to **any** test that deserializes a state blob. A quick `rg '"labels"\s*:\s*\[' packages/server/tests/` should be run in any later task that touches persistence. Confirmed there are no remaining occurrences.
- `IssueStageAttribution` doc comment's `cref` to `IssueQuerier.GetStageDurationsAsync` (called out in T-002 notes) does not depend on T-001 — this task is purely persistence-local.
- T-002 (metrics service extraction) and T-003 (shared loader) do not touch `IssueStore.cs`. Future tasks can assume the persistence surface is now minimal: `Serialize(DomainIssue)`, `Deserialize(string) -> DomainIssue?`, and the IStateStore surface. Anything that wanted to know "did normalization happen?" has no signal to read anymore — by design.

# Issue 325 — T-003 (IssueReadModelLoader extraction + ToInfo consolidation)

## Codebase Patterns
- The loader (`IssueReadModelLoader : IScopedService`) lives at `packages/server/src/Mohist.Server/Issue/Services/IssueReadModelLoader.cs` and is auto-registered through the Scrutor scan in `ServiceCollectionExtensions.AddMohistConventionalServices` (no manual `AddScoped<IssueReadModelLoader>()` line). Its constructor takes only three dependencies: `IssueWorkflowProfileRegistry`, `EffectiveWorkflowProfileResolver`, `ProjectWorkflowProfileManager` — no `IDbContextFactory` because all DB access is parameter-injected (`MohistDbContext db`) per call.
- The five call sites that previously inlined the load → resolve template/disabled → map → project block are now a single line each: `_loader.LoadProjectedAsync(db, projectId, project?)`. Two read-model call sites in `IssueQuerier` (`ListWithLabelFiltersAsync`, `ListInProgressWithApprovalGateAsync`) and three metrics call sites in `IssueMetricsQuerier` (`GetQualityAsync`, `GetApprovalWaitAsync`, `GetStageDurationsAsync`).
- `GetDeliveryTimesAsync` keeps its own direct `db.Issues.AsNoTracking().Where(row => row.ProjectId == projectId)` because the metric's only inputs are raw `Status`/`CreatedAt`/`CompletedAt` fields (no read-model shape). The same applies to completion bucketing and the event-scan helpers inside metrics — by design D4/D5, the loader covers only the five structurally identical load → map → project sites.
- The single-issue path (`IssueQuerier.GetAsync` / `GetInfoAsync` / `ToReadModelAsync`) still needs workflow+feedback projection semantics without reloading the whole project. A small companion helper `loader.ApplyProjectionsToSingleAsync(db, IssueReadModel)` is exposed for that case so `ToReadModelAsync` does not duplicate the projection-application body.

## Decisions / Discoveries
- The four `ToInfo` overloads are now thin wrappers around one `BuildInfo(issue, project, resolvedProfileId)` body in the loader. The instance wrapper lives in `IssueQuerier` (resolver-driven); the two static wrappers live in `IssueReadModelLoader` (LocalId-hardcoded). The field-by-field mapping appears exactly once — in `IssueReadModelLoader.BuildInfo`. `BuildInfo` is `internal static` so the instance `IssueQuerier.ToInfo` can call it cross-file; it is invisible to outside assemblies which matches the "private to the loader surface" intent.
- The previous instance path used the injected `_resolver.Resolve(...)` for repository resolution; the loader path uses `new IssueRepositoryResolver().Resolve(...)`. `IssueRepositoryResolver` is stateless, so behavior is identical — verified by `IssueWorkflowProfileConsistencySpecs` and the full Issue test suite (1114 spec pass).
- Static `ToInfo(issue, project)` and `ToInfo(resolver, issue, project)` both pass `IssueWorkflowProfiles.LocalId` to `BuildInfo`, preserving the no-DI default bit-for-bit (matches design D6 risk note about LocalId drift).
- `IssueRepositoryResolver` is registered as `ISingletonService`, but it carries no state, so passing `new IssueRepositoryResolver()` through `BuildInfo` instead of the injected singleton is functionally equivalent and removes one constructor dependency from the loader (it would otherwise have needed both an injected resolver and the singleton).
- The MigratedServicesRegistrationSpecs theory row was added on the same line as the metrics service row, preserving the per-domain ordering convention. The loader is the third consecutive Issue-domain row after `IssueQuerier` and `IssueMetricsQuerier`.

## Gotchas for Later Tasks
- `BuildInfo` is intentionally not `private` — making it `private` would force the instance `IssueQuerier.ToInfo` to also live on the loader, dragging the resolver-aware wrapper into the loader's surface. The current split (mapping core on loader, instance wrapper on IssueQuerier) keeps the loader free of any per-call profile-resolution logic beyond `_effectiveProfileResolver.Resolve(...)` inside `LoadProjectedAsync`. If a future task ever needs to make `BuildInfo` truly private, it must also relocate the two instance `ToInfo` overloads from `IssueQuerier` to `IssueReadModelLoader` and accept the resolver dependency there.
- `IssueMetricsQuerier.LoadWorkflowStatesAsync` (private) duplicates `IssueReadModelLoader.LoadWorkflowStatesAsync` (private) but for a different input shape: the metrics one is keyed on raw run-id lists (so it can resolve the runs discovered via `IssueEvents` work-started payloads, not just runs already present on the read-model). They are not consolidatable — moving the metrics one to the loader would require exposing the additional overload there and giving the loader knowledge of the event-scan contract. Out of scope for T-003.
- The `IssueQuerier.cs` constructor now takes `IssueReadModelLoader` (added by T-003). Two test stubs (`ThrowingIssueQuerier` in `EpicQuerierListAsyncSpecs.cs` and `EpicMembershipSpecs.cs`) inherit from `IssueQuerier` and call `base(...)`; both already pass the new loader argument via the fixture-injected services — verified during build.

### 学到/复用的模式
- server partial class 文件删除（`IssueRoutes.CumulativeFlow.cs`）安全
  —— partial class 的其他部分（`IssueRoutes.cs`、`IssueRoutes.Dtos.cs`）继续
  编译无碍；DTO 删完后文件末尾保留 trailing newline 跟其它 record 块风格一致。
- ASP.NET Core 删 endpoint mapper 是硬删除（`MapIssueCumulativeFlow()` 移除后
  `/api/projects/{projectRef}/issues/metrics/cumulative-flow` 自动 404），
  不需要写 redirect 或 410。
- web vitest 中 `vi.hoisted` mock 数组加新 hook 容易漏 `mockClear()` —— 重
  写范围测试时务必把所有用过的 mock 列在 `mockClear()` 清单里（漏一个
  `useCumulativeFlow.mockClear()` 会让本测试期望在初始 mock 状态下断言失败）。
- 集成 spec 删 inline data 行时记得在 InlineData 之间留 \n+\n 风格一致 —— 用
  Python 脚本做批量删行后用 `awk` 复查，保留单一空行。
- `MohistIntegrationFixture.cs` 用 raw SQL `CREATE TABLE IF NOT EXISTS` 而不是
  EF migration，所以删 `DbSet<StagePopulationSnapshotRow>` 时必须同时改 fixture，
  否则生产迁移和测试 fixture 漂移（design D4 风险项已点名）—— 本任务不动这块，
  T-003 同提交处理。

### 学到/复用的模式
- EF Core 的 `migrationBuilder.DropTable(name: ...)` 会自动先 drop 该表上
  的索引（包括 unique 索引），无需显式写 `DropIndex` —— 生成的 SQL 在
  SQLite 上行为正确。本任务不再额外 `DropIndex
  UQ_StagePopulationSnapshots_ProjectId_Day`。
- `Down` 重写时列顺序由 EF 按字典序序列化（D-B-D-I-P 而非 Add 迁移的
  B-P-Build-Check-Done-I），但 PK 项目（ProjectId+Day）和 unique index 定义
  完全保留，down-migrate-再 up-migrate 循环测试中表结构与索引语义等价。
- `MohistIntegrationFixture` 与 EF migration 各管一半 schema 的风险点（T-001
  progress 已记录）已在本任务内闭环：删 `DbSet<StagePopulationSnapshotRow>`
  与 fixture `CREATE TABLE IF NOT EXISTS "StagePopulationSnapshots"` 块同
  一次提交落地，未来 fixture 不会建出孤儿表（即使 raw SQL 与 EF 脱钩）。
- `Remove-` 类清理任务（T-001 + T-003 累计删 1702 行）每次提交都应先跑整
  树测试再 commit —— 这两任务的删除面重叠（T-001 删 CumulativeFlowQuerier
  后，T-003 删 StagePopulationSnapshotService），中间没有任何 README 或
  模板文件引用被触碰，dotnet 重编译即可一次性看到所有 nullable/using 报
  错。
- 复用 T-001 progress 提到的「MohistIntegrationFixture 用 raw SQL 管表须与
  DbSet 移除同提交」设计风险 —— T-003 实操验证：单 commit 一次性删除

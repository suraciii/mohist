## Codebase Patterns

- **Mirroring existing domain:** When adding a new project-scoped resource that mirrors an existing pattern (e.g., IssueTemplate mirroring IssueWorkflowProfile), follow the exact same conventions: constant class with DefaultId, interface in Domain/, service class in Services/, DB row in Infrastructure/Data/, registry scoped service, and JSON serialization via `Infrastructure.JSON`.
- **EF entities:** Follow `string` PKs with `HasMaxLength(256)`, composite keys as `HasKey(e => new { e.ProjectId, e.Name })`, and `DateTimeOffset` for timestamps. Use SQLite TEXT type throughout.
- **DI registration:** New scoped services go in `MohistServiceRegistration.ConfigureMohistServices()` alongside their mirrored siblings.
- **Test pattern:** Use xunit `[Fact]` with `[Trait]` attributes (Speed.Integration + Sut.Issue). Use SQLite in-memory for DB integration tests via custom `IDbContextFactory<MohistDbContext>` fake.
- **IssueResource naming:** Project-scoped resources that mirror workflow profiles use `Project{Resource}Row` in `Infrastructure/Data/` and a dedicated directory under `Issue/Domain/` and `Issue/Services/`.
- **Catch-all routes for slash-bearing IDs:** When the resource identifier may contain `/` (e.g. `mohist/default`), use the route pattern `{*name}` (catch-all), not `{name}` (which only matches a single segment). Existing precedent: `SystemRoutes.cs` uses `MapGet("/api/workflow-templates/system/{*id}", ...)` for the same reason. **Clients (CLI/Web) must NOT URL-encode the slash** — ASP.NET Core preserves the literal slash for catch-all segments.
- **Project-scoped reads with a path param:** Every existing project-scoped read is mounted at `/api/projects/{projectRef}/...` and applies `ProjectResolutionEndpointFilter`. Inside the handler call `IssueRoutes.GetRequiredProject(ctx)` to get the resolved `ProjectInfo`. This pattern is shared by `IssueRoutes/*`, `AttachmentRoutes`, `LabelsRoutes`, and `ProjectRoutes` (by-ref sub-group).
- **Test collection for integration specs:** HTTP-level integration tests live under `Mohist.Server.Tests/Specs/...` and use `[Collection("MohistIntegration")]` against `MohistIntegrationFixture`. They share a single Sqlite in-memory DB per fixture; ensure schema is initialized (`MohistWebApplicationFactory.EnsureSchemaAsync`).
- **API envelope shape:** Successful responses use `ApiResponse<T>` with `{ success, data, error, code, details }`. The test helpers `ApiTestClient.GetDataAsync<T>`/`PostDataAsync<T>` unwrap `data` automatically. For ad-hoc reads of nested shape, use `JsonElement`.
- **Adding a new `TableShape`:** Three places must change together — add the enum value in `MohistCliApi.TableShape`, add a `case` in `TableRenderer.Render` switch, and add the `RenderXxx` method. Enum parsing is case-sensitive and falls back to `ProjectList` on unknown values. Prefer freeform key/value output (not a table) for "show" commands whose payload contains nested arrays like `sections[]`.
- **CLI subcommand-group pattern:** New subcommand groups live in a static `XxxCommands` class with `Build(MohistCliApi api) → Command`. Project-scoped groups add a private `XxxPath(projectId, subPath)` helper that throws `InvalidOperationException(NoActiveProjectMessage)` when projectId is null/whitespace, mirroring `ProjectIssuesPath`/`ProjectEpicsPath`. The handler short-circuits with `if (resolvedProjectId is null) return 1;` before calling the path helper, so the throw is defensive.
- **Web entity slice for project-scoped read with catch-all id:** Mirror `entities/settings`'s `api/client.ts` + `api/queries.ts` + `model/types.ts` + `index.ts` layout. Project-scoped GET that takes a catch-all `{name}` must use `projectApiPath(projectId, '/path/' + name)` — the slash concatenation is required because `projectApiPath` URL-encodes only the `projectRef` segment, leaving `name` literal so the server's `{*name}` route matches. The `name` argument is the issue-template id (e.g. `mohist/default`) and must NOT be passed through `encodeURIComponent` or the slash will become `%2F` and the server will 404.
- **Web hook enablement for project-scoped resources:** `useQuery` config must set `enabled: !!projectId && (extra-arg ?)` so the hook stays inert when the project context is null. Returning `data: undefined` from the hook in that case is fine — components just read `data ?? []` (or `?.x`).
- **Web dialog body prefill via useEffect:** When a dialog needs to prefill its body whenever a query result lands (e.g. on template detail fetch), put a `useEffect` keyed on the query data inside the dialog and have it call the existing setter. Do NOT prefill in the onChange handler — the data may not be available yet. Reset the source-id state in the dialog's `resetAndClose()` to avoid the next session keeping the prior selection.
- **Vi.mock of an entity that exports both hooks and pure functions:** Use `vi.mock(path, async (importOriginal) => ({ ...(await importOriginal()), ...overrides }))` and pull the function under test into the test setup (or trust that the real implementation is used because `importOriginal` spreads it in). Forgetting `importOriginal` makes the real `composeIssueTemplateBody` etc. `undefined` and the dialog crashes at runtime even though tests "mocked" the module.

Tests can rely on this without special handling.
    - `HttpRequestException` thrown by an unreachable server is caught by `PrintWithOutputAsync` (the wrapper around `_http.GetAsync`) and prints `MohistCliApi.ServerUnavailableMessage` to stderr with exit code 1. Tests can simulate this by having the recording handler throw.

  - **Decisions made:**

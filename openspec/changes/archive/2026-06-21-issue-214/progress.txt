## Codebase Patterns

- **`WorkDispatch` already carries full work context** at dispatch time: `WorkId`, `WorkType`, `Stage`, `Title`, `Issue` (`WorkIssueRef?`), `OwnerKind`, `AgentJobId`/`WorkflowRunId`. The Runner grain stores it verbatim in `RunnerTrackedWork.Dispatch`, so any read of "active work context" should project from `_works.Values` — no extra wire traffic needed.
- **`RunnerActiveWorkItem` is a `[GenerateSerializer]` Orleans record** with explicit `[property: Id(N)]` slots. Adding fields requires appending to the end (`Id(N+1)`) to preserve decoding of older payloads.
- **`OwnerIdentityFor(WorkDispatch)`** centralizes the workflow-run-id vs agent-job-id choice (`work.OwnerKind` switch). Reuse it for any "who owns this work" projection so the wire shape stays consistent.
- **`[GenerateSerializer]` record members need a default constructor**: `WorkDispatch` declares `public WorkDispatch() : this(string.Empty, string.Empty) { }` for the same reason. New `[GenerateSerializer]` records doing structural deserialization need a matching parameterless ctor.
- **`DateTime → DateTimeOffset` is implicit**, so `_lastHeartbeat` (a `DateTime`) can flow into a `RunnerRuntimeState.LastHeartbeatAt` (`DateTimeOffset`) parameter directly.
- **RunnerGrain slot count derivation uses owner identity distinct count, not work count**: `_works.Values.Select(w => OwnerIdentityFor(w.Dispatch)).Distinct(...).Count()` (see `RunnerGrain.ActiveWorkflowCount`). The replacement `ActiveWorks` carries one item per `_works` entry (per dispatch), not per owner identity, so consumers reading `ActiveWorks.Count` get a *work count* — distinct from `ActiveWorkflowCount` which deduplicates by owner. Pick the correct one for "is there capacity for another work" vs "is this runner busy".
- **Workflow dispatch does NOT carry `WorkIssueRef` by default** — `WorkflowDispatchHelpers.BuildIssueRef` reads `project` and `issue` keys from the dispatch payload, but the default `BuildPayloadAsync` does not populate those keys. So workflow-driven dispatches generally have `Issue == null` in `ActiveWorks`. To test the populated-issue path, assign a `WorkDispatch` directly via `runner.AssignWorkAsync(...)` with a hand-built `WorkIssueRef` rather than going through `AssignActiveWorkForTestAsync`.
- **HTTP projection always returns a non-null, empty list for "no active works"**: `RunnerStatusView.ActiveWorks` is `IReadOnlyList<RunnerActiveWorkView>` and is projected as `[]` when `runtime` is null or `runtime.ActiveWorks` is empty. Consumers (Web, CLI) can use `array.length` / `array.Count` safely — never null-check before iterating.
- **`GET /api/projects/{projectRef}/runners/{runnerId}` 404 vs idle 200 distinction**: the detail route shares `ProjectResolutionEndpointFilter` with the list route; it queries `IRunnerRegistryGrain.ListEligibleRunnersAsync(projectId)` and filters by id — returning `null` when not in the eligible set, which maps to `ApiResults.Fail($"Runner '{runnerId}' not found", 404, "runner_not_found")`. The 200 idle path (registered but no active works) flows through the same `ProjectRunnerAsync` projection as the list endpoint; do NOT special-case it as 404.
- **Read-only guarantee for the detail endpoint**: it only calls `IRunnerGrain.GetRuntimeStateAsync()` and `IRunnerRegistryGrain.ListEligibleRunnersAsync()` — neither mutates runner state, tracked works, registration info, or heartbeats. The "no-side-effect" assertion in tests compares `Before/After` `LastHeartbeatAt` + `RegisteredAt` + `ActiveWorks` snapshots to detect accidental mutations if future changes introduce them.
- **`RunnerStatusView.ActiveWorks` is the HTTP projection of every `_works` entry** (one item per dispatch, not per owner identity). A multi-slot runner with N distinct workflow ids all dispatched separately will project N items; a single workflow id with multiple work tasks still projects one item per work-task key. Keep this consistent with `RunnerRuntimeState.ActiveWorks` so HTTP consumers never have to re-derive it.
- **`RunnerActiveWorkView` field order**: `(WorkId, OwnerKind, OwnerId, WorkType, Stage?, Title?, Issue?)`. `OwnerId` is the single canonical owner identifier (workflowRunId for `workflow`, agentJobId for `agent-job`); don't also expose `WorkflowRunId`/`AgentJobId` on the view. The serialized JSON key is `workflowRunId` historically — when emitting, keep the legacy `workflowRunId` JSON alias only if a T-003+ consumer requires it; for the new server shape the JSON property follows the C# field name.
- **The pre-existing `mo runner` group is the service-lifecycle group** and the issue-214 CLI surface extends that same top-level group. In the current code, `RunnerCommands.Build(...)` returns a `Command("runner", "Runner management")` added at the **root** (see `MohistCliCommands.cs:18`), containing `install/start/stop/restart/status/logs/uninstall/list`. The aligned design and tasks add `show <runner-id>` to this same top-level `runner` group (it is NOT a separate group) — the disjoint subcommand sets + the `show` description ("read-only") are the differentiation, matching the rest of the CLI's singular-noun convention (`issue`, `epic`, `agent`).
- **CLI `--output` defaults to `json` project-wide** (`MohistCliCommands.OutputOption()` returns `DefaultValueFactory = _ => "json"`). The `runner show` text renderer is invoked only when the caller passes `-o table`; with the default `-o json` it emits the parsed `payload.data.runner` JSON object directly (preserving field shapes from the server without re-formatting). Tests that assert on text sections must pass `-o table`; tests that assert on the JSON shape can leave it as default.
- **`mohist/info` text rendering pattern**: the `runner show` text renderer mirrors the `mohist info` style — section headers (`Identity` / `Capabilities` / `Active Works` / `Health`), indented `  key: value` lines, and an explicit `(no active works)` placeholder when `activeWorks` is empty. Field omission (e.g. a work whose dispatch had no issue) is rendered as silent absence (no `issue:` line at all), matching the Web's "no placeholder link" convention and the spec's `Requirement: Work without an issue reference renders without a link`.
- **`RunnerStatusDetailResponse` JSON shape**: `{ success: true, data: { runner: <RunnerStatusView> } }`. The detail endpoint 404 shape is `{ success: false, error: "Runner '<id>' not found", code: "runner_not_found" }`. The CLI's `PrintRunnerShowAsync` reads `payload["data"]?["runner"]` (NOT `payload["data"]`), handles 404 with a non-zero exit (code `4` — matching the convention used by `PrintRunnerListAsync` / `PrintResponseAsync`) and a stderr message containing the literal runner id, and treats every other non-success status as a generic error (code `1`).
- **CLI HTTP helpers use 4 for 404, 1 for other errors** (`MohistCliApi.PrintResponseAsync`): the same convention applies to `PrintRunnerShowAsync` so existing `mo issue show` / `mo project use` test infrastructure (which already asserts exit code 4 on 404) keeps working.

- **Learnings for future tasks**
  - **Decisions made**
    - Kept the new `show` subcommand under the existing top-level `mo runner` group (alongside the service-lifecycle commands and `list`) instead of creating a separate `mo runner observability` group. The design and tasks now name this as the existing top-level `mo runner` group (T-213 added `list` to the same group; T-004 follows the same pattern). Help-text separation is achieved through the `show` description ("read-only") and the disjoint subcommand set, not a separate top-level noun.
    - Default `--output` is `json` (the CLI-wide convention) — text rendering requires `-o table`. This matches `mo issue show`, `mo project show`, and every other show-style command, and keeps `runner show` scriptable for downstream tooling. The JSON output is `payload.data.runner` verbatim, so the consumer never has to re-derive shape.
    - Used `runner-id` (kebab-case) for the argument name in help text / CLI parsing, and URI-escape the value when building the URL path. `mo issue show` uses `number` for its argument; `runner show` mirrors the convention with `runner-id`. Tests pin `runner-id` via the argument descriptor so future refactors don't break the help contract.
    - Rendered `issue` only as the `issueNumber` integer (e.g. `issue: 214`) — not the full `{ projectId, issueId, issueNumber }` object — to match the spec's "issue number when present" wording and to keep the text renderer compact. The JSON output keeps the full object for programmatic consumers.
    - Returned exit code `4` on 404 (matching `PrintRunnerListAsync` and `PrintResponseAsync`); exit code `1` on transport / other failures. The 404 stderr message echoes the URL-encoded runner id (`Runner 'r-ghost' not found`) so callers can correlate with the input arg verbatim.
    - Did NOT introduce a `TableShape.RunnerShow` entry — the text rendering is bespoke section-based output (not a tabular grid) and the JSON path bypasses the `TableRenderer` entirely. Future callers wanting machine-readable input should use `-o json` and read `payload.data.runner` themselves.
  - **Gotchas discovered**
    - The `runner --help` text already lists 8 subcommands after the addition (`install / start / stop / restart / status / logs / uninstall / list / show`); `System.CommandLine` auto-wraps each description in a fixed-width column, so a too-long `show` description can wrap awkwardly. Keeping the description short ("Show a single runner's full detail (read-only)") avoids wrapping in a 100-column terminal. The `RunnerShow_HelpText_ListsShowAndExistingSubcommands` test pins every subcommand name to catch accidental removals.
    - The pre-existing `JSON.cs(16,9)` build error in `packages/server/src/Mohist.Server/Infrastructure/JSON.cs` (duplicate `Encoder` initialization) is a `master`-side issue and is NOT caused by T-004 changes; `npm run build` will fail until that pre-existing issue is resolved separately. The CLI build (`dotnet build packages/cli/Mohist.Cli/Mohist.Cli.csproj`) and the CLI test build (`dotnet test packages/cli/tests/Mohist.Cli.Tests/`) both succeed independently.
    - `MohistCliApi.ResolveProjectIdAsync` returns `null` and prints `mo project use ...` to stderr when neither `--project` nor `--project-id` is supplied and no `~/.mohist/cli-state.json` exists — the CLI's `RunnerShow_NoActiveProject_FailsWithStandardError` test pins this by asserting exit code 1, the `mo project use` substring, and zero outbound HTTP requests.
    - `MohistCliApi.PrintRunnerShowAsync` calls `_http.GetAsync(path)` directly (NOT `GetDataAsync`) so it can read the 404 status code path before it would be turned into an `ApiResponseException` by `ReadSuccessDataAsync`. This is the same pattern used in `PrintResponseAsync` and matches `PrintRunnerListAsync`'s 404-via-`ApiResponseException` handling — the detail endpoint's `runner_not_found` body shape (`{ success: false, error, code }`) is well-defined, so the bespoke handling is intentional and the JSON error message is preserved.
  - **Patterns / API shapes established**
    - `MohistCliApi.PrintRunnerShowAsync` signature: `(string projectId, string runnerIdEncoded, string mode) → Task<int>`. `projectId` is the already-resolved project id (URI-escaping is the caller's responsibility in the upstream URL builder); `runnerIdEncoded` is the URI-escaped runner id (caller responsibility); `mode` is `"json"` or `"table"`. Null/empty project id → exit code 1 with the `NoActiveProjectMessage`. 404 → exit code 4 with a stderr message that includes the runner id verbatim. Transport error → exit code 1 with the standard `ServerUnavailableMessage`. Success + json → raw `payload.data.runner` JSON; success + table → text rendering via `RenderRunnerShow`.
    - `MohistCliApi.RenderRunnerShow` text contract: section headers are exact strings `Identity` / `Capabilities` / `Active Works` / `Health` (capitalized first letter, single word) so future tests / parsers can locate them with `Assert.Contains("Active Works", stdout)`; section separators are blank lines; the active-work rows are `[i]`-indexed where `i` is the 1-based item index (`[1]`, `[2]`, ...), `workId` is the first sub-line, and the `issue:` line is emitted only when the work has a non-null `issue` object (System.Text.Json omits `null` properties, so the absence test is simply "no line starts with `      issue:`").
    - `MohistCliCommands.Server.cs.RunnerCommands` builder is now responsible for the entire top-level `mo runner` command group (service-lifecycle + observability + list + show). Any new subcommand should be added in `RunnerCommands.Build(...)` and follow the `BuildXxx(MohistCliApi api)` (or `BuildXxx(MohistCliApi api, IServiceProvider provider)` if it needs services) signature pattern.
  - **Cross-task invariants**
    - The server contract is unchanged: T-004 only consumes `GET /api/projects/{projectRef}/runners/{runnerId}` (T-002's endpoint). Future CLI work that wants richer rendering should still operate on the same `RunnerStatusView` JSON shape — no client-side re-derivation of `activeWorks` / `issue` from workflow grains.
    - The runner list endpoint (`GET /api/projects/{projectRef}/runners`) is still the bulk-listing surface; `mo runner show <runnerId>` does NOT call the list endpoint and filter client-side. The detail endpoint is the canonical source for single-runner detail (per design D4 / T-002 acceptance criteria).
    - Exit code 4 on 404 matches `PrintResponseAsync` / `PrintRunnerListAsync` / `UseProjectAsync` so shell scripts can branch on a single exit-code constant. Future CLI commands that hit detail endpoints should follow the same convention.

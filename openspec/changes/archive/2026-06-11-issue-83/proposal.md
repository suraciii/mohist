## Why

Mohist CLI is the surface that agents and operators use to inspect and act on project-scoped issues, but several implementation-oriented gaps block safe multi-project CLI workflows: issue commands only accept `--project-id` (forcing a name→id round trip and exposing an internal id concept), all output is raw JSON (humans cannot scan common list/detail commands quickly), `issue create`/`issue update` only accept inline `--body` (brittle for long Markdown and agent-generated content), and project repository management exists on the server but is unreachable from `mo project`. This change addresses all four gaps in one focused ergonomics pass so agents and humans can use the same CLI surface for project-scoped work.

## What Changes

- Add a canonical `--project <name-or-id>` option to every project-scoped `mo issue` subcommand (list, show, create, update, start, approve, reject, close, reopen, retry, rerun, force-stop, resume, rebase, archive, unarchive, logs, events, diff, commits, sessions, workflow status, workflow timeline). Keep `--project-id` as a backwards-compatible alias. Help text and diagnostics guide users toward `--project`.
- Active project resolution (set via `mo project use`) remains the fallback when neither option is passed.
- If both `--project` and `--project-id` are passed with **different** values, the CLI returns a clear validation error and exits non-zero instead of silently picking one.
- Add a single shared `--output table|json` option to `project list`, `project show`, `issue list`, `issue show`, `issue workflow status`, and `issue sessions`. `table` renders a readable summary; `json` is the existing default and the stable automation format.
- Extend `issue create` and `issue update` body input to support `--body` (existing), `--body-file <path>` (read file as UTF-8), and `--body-stdin` (read full stdin). These three sources are mutually exclusive; using more than one returns a validation error and exits non-zero.
- Add `mo project repo` subcommands that wrap the existing server repository API: `list`, `add`, `set-default`, `remove`. Each takes a `--project <name-or-id>` (or active project) and the relevant request body / path parameters.
- Update `--help` text and the "no active project" error to mention `Run 'mo project use <name-or-id>' or pass --project <name-or-id>`.

## Capabilities

### New Capabilities
- `cli-project-ref`: CLI `--project <name-or-id>` semantics. Covers adding the canonical option to every project-scoped issue subcommand, keeping `--project-id` as a compatibility alias, the "same value" allow / "different value" error rule, active-project fallback ordering, and the standardized "Run 'mo project use ... or pass --project ...'" diagnostics. Becomes `specs/cli-project-ref/spec.md`.
- `cli-output-modes`: CLI `--output table|json` for high-use list/detail commands. Covers the six commands that gain the option (`project list`, `project show`, `issue list`, `issue show`, `issue workflow status`, `issue sessions`), the default-is-json contract for automation stability, the `table` rendering shape (columnar human-readable), and the validation error for unknown output values. (`mo project repo list` also gains `--output` per the `cli-project-repositories` capability, bringing the total to seven.) Becomes `specs/cli-output-modes/spec.md`.
- `cli-body-input-sources`: `issue create`/`issue update` body input sources. Covers the three mutually exclusive sources (`--body`, `--body-file <path>`, `--body-stdin`), the "exactly one required" rule, file-read error behavior, and the validation error wording when more than one is provided. Becomes `specs/cli-body-input-sources/spec.md`.
- `cli-project-repositories`: `mo project repo` subcommands. Covers the four subcommands (list / add / set-default / remove), the request paths they wrap, the active-project fallback, the `--project <name-or-id>` option, and the existing server conflict/not-found surface flowing through CLI error output. Becomes `specs/cli-project-repositories/spec.md`.

### Modified Capabilities
- `cli-interface`: The CLI option surface gains `--project` (and keeps `--project-id`), gains `--output` on the five listed commands, gains `--body-stdin` / `--body-file` on `issue create`/`update`, and gains the `project repo` subcommand group. Help text and "no active project" diagnostics are updated. No semantic change to existing commands when the new options are not used. New tests cover the new option behaviors and the new repository subcommand request paths.
- `project-management`: `mo project` gains a `repo` subcommand group with `list | add | set-default | remove` backed by the existing `/api/projects/{ref}/repositories` server endpoints. The CLI is still a thin client — it does not introduce new server semantics; it only wraps the existing repository API.

## Impact

- `packages/cli/Mohist.Cli/MohistCliCommands.cs`: introduce a shared `ProjectRefOption()` helper that adds both `--project` and `--project-id` (with shared description text) and a `ResolveProjectRefAsync(project, projectId)` helper that implements the "same value ok / different value error / active project fallback" rule. Add `OutputOption()` helper for the five `--output`-enabled commands. Update the "no active project" error string in `MohistCliCommands.Issue.cs:43`.
- `packages/cli/Mohist.Cli/MohistCliCommands.Issue.cs`: replace every `MohistCliCommands.ProjectIdOption()` usage with the new shared helper; add `--body-stdin` / `--body-file` to `BuildCreate` and `BuildUpdate`; add `--output` to `BuildList`, `BuildShow`, `BuildSessions`, and `BuildWorkflow` status subcommand; add a `BodyInputResolver` (or local equivalent) that enforces mutual exclusion, reads the file (UTF-8), or drains stdin, and surfaces a clear error and exit code 1 on failure.
- `packages/cli/Mohist.Cli/MohistCliCommands.Project.cs`: add a new `BuildRepo` group with `list` / `add` / `set-default` / `remove` subcommands, each routing through `api.ResolveProjectIdAsync` (which now accepts either `--project` or `--project-id`) and using the existing server endpoints `GET/POST /api/projects/{id}/repositories`, `PATCH /api/projects/{id}/repositories/{repoName}` (with `{ setDefault: true }`), and `DELETE /api/projects/{id}/repositories/{repoName}`.
- `packages/cli/Mohist.Cli/MohistCliApi.cs`: extend `ResolveProjectIdAsync` to accept the two-option tuple (or new overload) and apply the same-value / different-value validation. Existing `UseProjectAsync` and the `cli-state.json` active-project lookup are unchanged. Add a small `RenderTableAsync(JsonNode?, TableShape)` formatter that the `--output table` path uses; JSON output continues to be the existing pretty-printed `data` field.
- `packages/server/src/Mohist.Server/Api/ProjectRoutes.cs`: **no changes** — the four repository endpoints (`GET/POST /repositories`, `PATCH /repositories/{repoName}`, `DELETE /repositories/{repoName}`) already exist and are used as-is by the new CLI subcommands.
- `packages/server/src/Mohist.Server/Project/...`: **no changes** — the `IProjectGrain` repository methods (`AddRepositoryAsync`, `SetDefaultRepositoryAsync`, `RemoveRepositoryAsync`) and the `Project.Repositories` projection are reused unchanged.
- Tests: new server-side spec files in `packages/server/tests/Mohist.Server.Tests/Specs/Api/` (e.g. `IssueCliProjectRefSpecs.cs`, `IssueCliOutputModeSpecs.cs`, `IssueCliBodyInputSpecs.cs`, `ProjectCliRepositorySpecs.cs`) using the existing `MohistCliCommands.RunAsync` + `RecordingHttpHandler` + `FakeFileSystem` harness from `ProjectCliSpecs.cs`. Existing `ProjectCliSpecs` tests continue to pass (the old `--project-id`-only path is preserved as a compatibility alias). Web UI, workflow engine, Issue/Project domain models, and the runner are **not** touched.
- Backwards compatibility: `--project-id` remains accepted everywhere it is today, defaults to the same behavior, and `--output` defaults to `json` everywhere it is added, so existing scripts and agent prompts keep working.

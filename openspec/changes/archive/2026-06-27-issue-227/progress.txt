## Codebase Patterns

- `entities/issue/api/client.ts` already returns a bare `Issue` from `createIssue` (no `{ issue }` wrapper). Only `startIssue`/`closeIssue`/`reopenIssue` etc. wrap their results. The create flow must read `data.number`, not `data.issue.number`.
- The repo standardizes on `import { toast } from 'sonner'` for success/error feedback. `entities/epic/api/queries.ts` is the canonical pattern (`onSuccess` toast + `onError(err.message || '...')`). Tests against `sonner` use the `vi.hoisted` pattern (see `SettingsSearch.test.tsx`, `EpicListPage.test.tsx`).
- `Issue` type is re-exported from `entities/issue` via `model/types.ts`. Importing `import type { Issue } from '.../entities/issue'` matches the existing convention used across `widgets/issue-workflow` and `app/providers`.
- The dialog already has an inline `mutation.error` banner; adding a `sonner` error toast is additive (not a replacement), matching the spec ("the spec requires a toast").

## T-001 — Fix create-issue toast to show correct issue number

- `packages/web/src/features/create-issue/ui/CreateIssueDialog.tsx`:
  - Imported `toast` from `sonner` and `type { Issue }` from `entities/issue`.

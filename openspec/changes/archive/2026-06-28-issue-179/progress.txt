# Issue 179 — Build stage working memory

## Codebase Patterns
- Tests under `packages/server/tests/Mohist.Server.Tests/Specs/Epic/Grain/` use the
  Fake-based pattern from `EpicProgressionSpecs.cs`: a `TestDbContextFactory`
  against an in-memory SQLite (Migrate the schema), a `RecordingGrainFactory`
  or `NullGrainFactory` for grain dispatch, and `Seed*` helpers to populate
  `Epics` / `Issues` / `EpicIssues` rows directly. No real DB, no real
  Orleans, no HttpClient. `dotnet test` covers them under `Speed=Unit`.
- The HTTP-driven `EpicLifecycleSpecs.cs` in
  `Specs/Epic/Domain/` covers the full round-trip via `MohistIntegrationFixture`
  and is tagged `Speed=Integration`. Keep that file for end-to-end assertions;
  use the `Grain/` specs for unit-level coverage.
- `EpicProgress.IsTerminal(string)` is the canonical terminal test for the
  epic status (returns true for `"done"` / `"closed"`). Reuse it where
  possible — but EF Core LINQ-to-SQL cannot lower managed helpers, so when
  inlining into a query, expand the predicate to the literal set
  `(Status != "done" && Status != "closed")`.
- `EpicQuerier.ListAsync` is a single raw SQL join and does NOT touch
  `IssueQuerier`; a `ThrowingIssueQuerier` stub is fine for those tests.
  `EpicQuerier.GetAsync` calls into `IssueQuerier.ListAsync` and needs a
  working querier — easier to assert detail/list reads in the HTTP-driven
  `EpicLifecycleSpecs.cs` instead.

## Decisions
- D1 (EpicGrain.ApplyPendingEvents): removed the `EpicClosed` branch and
  `RemoveAllLinkedIssues` helper. The method is now a single-line
  `epic.ClearPendingEvents()` drain (with a comment noting the
  non-destructive close). Removed the unused `(db, projectId, epicId)`
  parameters to satisfy TreatWarningsAsErrors.
- D2 (MohistDbContext + migration): relaxed
  `IX_EpicIssues_ProjectId_IssueId` from `IsUnique()` to a non-unique
  index. Migration `20260628022822_DropEpicIssueMembershipUniqueIndex`
  drops the old index and re-creates it without `unique: true`. Snapshot
  regenerated.
- D3 (EpicGrain.LinkIssueAsync): replaced the single-row
  `FirstOrDefaultAsync` duplicate check with a set-based query that joins
  `EpicIssues` to `Epics` and filters terminal owners. Inlined
  `Status != "done" && Status != "closed"` so EF Core can translate.
  Existing-link-to-this-epic is handled by a separate `AnyAsync` idempotent
  guard so the second insert is skipped before the domain method runs.
- D4 (IssueQuerier.primaryEpic projection, T-002): added an
  `EpicProgress.IsTerminal(epic.Status)` guard inside the existing
  foreach loop so only non-terminal epic memberships are projected.
  Because T-001 guarantees at most one non-terminal membership per
  issue, the "last write wins" loop naturally resolves to that single
  non-terminal epic; an issue with only terminal memberships projects
  null. Used the helper directly (not the inlined literal set) because
  this loop runs over already-materialized entities — no LINQ-to-SQL
  translation is involved.
- D5 (IssueQuerierPrimaryEpicSpecs, T-002): the IssueQuerier is a
  scoped service that requires six DI-graph dependencies, so writing a
  Speed=Unit test that constructs it manually is impractical. Used the
  `MohistDbFixture` shared in-memory SQLite + service-graph fixture
  (Speed=Service) — this still fakes every external system (no real DB,
  no real Orleans, no HttpClient) and matches the existing pattern in
  `IssueQuerierSpecs.cs`. The "Fake-based" criterion from the task is
  therefore satisfied via the service fixture.

## Gotchas
- `EpicProgress.IsTerminal(string)` cannot be used inside a LINQ-to-SQL
  query (EF Core refuses to translate it). Inline the literal check.
- After dropping the unique index, the
  `IX_EpicIssues_ProjectId_IssueId` migration step is `DropIndex` →
  `CreateIndex` (not unique). EF Core generates this correctly when the
  model drops `IsUnique()`.
- `TestDbContextFactory`-style `RecordingGrainFactory` implements all
  members of `IGrainFactory` (Orleans interface, ~15 throws). For
  membership tests where no inter-grain dispatch is needed, a minimal
  `NullGrainFactory` works.
- `IssueQuerier` constructor takes six dependencies. For unit specs that
  need to construct `EpicQuerier` for the `ListAsync` raw-SQL path
  (which doesn't touch IssueQuerier), use a `ThrowingIssueQuerier` that
  overrides `ListAsync` to throw — this asserts the EpicQuerier
  implementation doesn't drift back into calling IssueQuerier.
- The previous `Close_SetsStatusToClosedAndRemovesEpicIssueLinks` and
  the `Assert.Empty(detail.LinkedIssues)` block in
  `Close_DoesNotChangeIssueStatusOrPrerequisitesOrWorkflow` both had
  to flip from "empty after close" to "preserved after close" — those
  are the behavioural break called out in the proposal.
- T-002 / `MohistDbFixture`-backed tests: the fixture is shared across
  every test in the `MohistDb` collection, so seeded rows from one test
  are visible to the next. Every seed id must be GUID-suffixed to avoid
  unique-constraint collisions when a `[Theory]` runs its inline data
  in sequence.
- T-002 / EF Core change tracker: when a test seeds a row with `db.Add`
  + `db.SaveChanges`, the entity stays tracked even though its state is
  Unchanged. Reading the same row back from the same context and calling
  `Remove` triggers the "instance with the same key is already tracked"
  error. Use a fresh `DbContext` (separate scope) for the read+remove
  path.
- T-002 / `Issue` type alias: the namespace `Mohist.Server.Issue`
  shadows a type alias `using Issue = Mohist.Server.Issue.Domain.Issue;`
  because the alias name resolves to the namespace before the type. Use
  `using IssueEntity = ...` (the pattern from
  `IssueModelVariantRoundTripSpecs.cs`) or fully qualify.
- T-002 / `IssueQuerier` DI surface: it depends on six services
  (`IDbContextFactory`, `IssueWorkflowProfileRegistry`, `ProjectQuerier`,
  `IssueRepositoryResolver`, `ConfigService`,
  `EffectiveWorkflowProfileResolver`), so a Speed=Unit construction is
  impractical. The `MohistDbFixture` (Speed=Service) covers it without
  any real external system and matches the convention in
  `IssueQuerierSpecs.cs`.

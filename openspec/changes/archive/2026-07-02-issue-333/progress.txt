T-001 (2026-07-02): Server: unify description source via shared resolver and remove SuitableFor from the workflow-profile model.

## Codebase Patterns

- Resolver placement: chose `MohistWorkflow.ResolveDescription(WorkflowDefinition)` as a static method on the existing static class, not a new dedicated type. The class already exposes `Definition`, `GithubPrWorkflowDefinition`, `LoadDefinitionForProfile`, `ParseYaml` — adding one more static keeps the resolver next to the definitions and avoids a single-responsibility class for a 3-line function. Co-located fallback constant as a private const (`MissingDescriptionFallback` = `"No description provided"`).
- The shared resolver applies: `string.IsNullOrWhiteSpace(description) ? fallback : description.TrimEnd()`. This is the single source of the fallback rule; the spec scenario "non-blank YAML description is used verbatim" asserts trimmed trailing whitespace, so the trailing-newline strip is intentional (strips a trailing `\n` from YAML block scalars like `|`).
- Both catalog paths (`BuildSystemTemplates` in `ProjectWorkflowProfileManager` and `ListDescribed` in `IssueWorkflowProfileRegistry`) now call `MohistWorkflow.ResolveDescription(...)` — Decision 1 invariant: drift between catalog paths becomes impossible because they share the function.
- `WorkflowProfileDescription` DTO is now `(string Id, string DisplayName, string Description)` only. The `suitableFor` JSON field leaves the `/api/workflow-profiles` response. API-spec test `WorkflowProfilesEndpoint_ResponsePayloadHasNoSuitableForField` parses the raw response body and asserts no entry has a `suitableFor` property (defense-in-depth beyond the typed DTO).
- Test DTOs (`WorkflowProfileDescriptionDto` in `IssueApiSpecs` and `IssueWorkflowProfileApiConsistencySpecs`) lost the `SuitableFor` member — they must stay in lockstep with the server contract.
- The unrelated `IssueTemplate.SuitableFor` / `IssueTemplateRegistry` model was left alone; it shares the name but is a different domain concept (issue templates, not workflow profiles). Grep verified only those + our new "absence-of" test names remain under packages/server.
- `MohistGithubPrIssueWorkflowProfile.GithubPrDescription` const and all references deleted. The "description asserted against the YAML value" spec scenario is verified by `MohistGithubPrIssueWorkflowProfile_DescriptionReadsFromGithubPrYaml` which asserts `profile.Description == MohistWorkflow.ResolveDescription(GithubPrWorkflowDefinition)` and `EndsWith("`gh` CLI on the runner host and `gh auth login` against the target repository.")` (last line of the YAML description, proving it is sourced from YAML, not a C# constant).
- Removed the `_AsConstant` spec — the assertion that the constant mentions `gh auth login` was tautological (the constant is literally the source). Repointed to assert the profile's `Description` carries the same content, sourced through the resolver.
- Added a stronger cross-catalog spec `BothCatalogPaths_AgreeWithProfileInstanceForBothBuiltIns` that asserts `profile.Description == template.Description == describedEntry.Description` for both `mohist/local` and `mohist/github-pr`. This is the Decision 1 / spec scenario "the two catalog paths agree with each other" gate.

## Gotchas

- The trim semantic is a behavior change for `mohist/local`: previously its `Description` returned the raw YAML value (including the trailing `\n` from the `|` block scalar); now it strips trailing whitespace. Three pre-existing tests asserted `MohistWorkflow.Definition.Description == profile.Description` and broke; they were repointed to use `MohistWorkflow.ResolveDescription(MohistWorkflow.Definition)`. A YAML round-trip test (`IssueWorkflowProfileApiSpecs.GetSystemTemplateDetail_EmittedYamlRoundTripsBackToSameDescription`) still compares raw YAML descriptions on both sides — that's a YAML-serialization invariant, not a description-display invariant, so it is unchanged.
- The test suite skips 13 tests with `Fact(Skip = "Integration test host cannot boot due to pre-existing pending EF migration unrelated to this change.")` — they are pre-existing skips, not caused by this change.
- `WorkflowCliSpecs` and `WorkflowCliListSpecs` mock the `/api/workflow-profiles` response inline with `"suitableFor"` arrays. Those mocks test CLI rendering, which is T-002 territory; they still pass because the CLI still parses `suitableFor`. Once T-002 lands and the CLI strips the field, those mock fixtures will need to drop the field too.

T-003 (2026-07-02): Skill-data: rewrite mohist-create-issue workflow selection to default/operator choice instead of suitable_for tag matching.

## Codebase Patterns

- The new SKILL.md section "Selecting a workflow" enumerates three ordered paths: (1) project's default profile (the operator's standing choice), (2) operator-chosen enabled id from explicit instruction in this turn or prior context, (3) first enabled profile as last resort. The existing `CreateIssueSkillContentSpecs.PackagedCreateIssueSkill_StopsWhenNoWorkflowProfileIsEnabled` test pins the exact phrase "the first enabled profile, else fail with an actionable error" in the third path, so the prose was tightened to lead with that phrase verbatim rather than wrapping it in a sentence that lost the "else fail" tail.
- The example output in the "Workflow discovery" section was rewritten to match the post-T-002 CLI render shape — two real built-ins, each shown as `id — displayName` followed by a wrapped description line and a blank separator. No "Suitable for:" line, no "(not specified)" placeholder. The new text explicitly tells the agent to treat the natural-language description as a human-facing summary, not as a scoring input.
- The "Writing `recommended_workflow_reason`" section gives three template sentences keyed to the three selection paths (default / operator-chosen / first-enabled fallback), so the agent picks the wording by path rather than inventing one. The new text also adds a "no tag citations or scoring rationale" constraint, which is the spec scenario gate from `specs/workflow-profile-description/spec.md` ("skill guidance uses default or operator choice, not tag matching") in the doc itself, not just in tests.
- The references/issue-templates.md table and verification checklist were aligned: `recommended_workflow` row now says "chosen by default profile → operator-chosen enabled id → first enabled profile as last resort", and the verification checklist grew a new bullet asserting the natural-language-sentence / no-tag-citations shape. The `<enabled-profile-id-from-discovery>` placeholder and the `An enabled profile id returned by \`mo workflow list --described\`` substring are preserved verbatim because they are required by `PackagedCreateIssueTemplate_UsesDiscoveredEnabledWorkflowProfileOnly`.
- Worked example's `recommended_workflow_reason` was rewritten from a tag-citation ("selected the enabled workflow whose suitable_for tags cover local feature work") to a natural-language path statement ("Using the project's default workflow profile as the operator has not specified a different one for this issue"). Worked example is the only place the old tag-citation language lived; the new sentence matches the "default profile used" path bullet from SKILL.md.

## Gotchas

- The negative assertions in `CreateIssueSkillContentSpecs` (the second test) include `Assert.DoesNotContain("falling back to", content)` and `Assert.DoesNotContain("or \`mohist/local\`", content)`. The new text uses "fall back to" / "fallback" / "last resort" / "first-enabled fallback" — none of these contain the forbidden literal "falling back to" (with the -ing suffix). Verified by grep: no hits for either forbidden phrase across both new files.
- The pre-existing `firstEnabledProfile, else fail` phrasing was a tad ambiguous in the old text ("the first enabled profile, else fail with an actionable error" — the "else" was dangling). The rewrite leads with that phrase verbatim so the test still passes, and the surrounding clause ("If there is no project default and the operator has not chosen one") is what makes "else fail" land correctly.
- After T-003, `grep -rn "suitable_for\|Suitable for" packages/cli/Mohist.Cli/skill-data/mohist-create-issue/` returns nothing. The remaining mentions of "tags" in the new SKILL.md are all *negating* the old behavior ("do not parse or score structured tags", "do not look for suitability tags") — these are the *prohibition* of the old rule, not instructions to perform it, so they satisfy the acceptance criterion "no instruction to match or score profiles against `suitable_for` tags."
- One subtlety on the "default profile" wording: the new SKILL.md describes it as "the project is configured with a default workflow profile (the operator's standing choice for issues on this project)." The actual `mo project workflow config set --default-template` command exists and writes `PUT /workflow-profile/default-template`, so the wording is plausible and matches a real CLI surface — but the skill does not actually call that command. The agent reads the default from the project's effective configuration; if no default is configured, the third path kicks in. Documented in the prose so the operator knows the "default" they expect is the project-level configured default, not an agent-inferred default.

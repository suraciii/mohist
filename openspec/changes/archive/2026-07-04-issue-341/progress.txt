T-003 progress notes

## Codebase Patterns

- jsdom cannot lay out: viewport mode is asserted via `data-rail-mode="desktop|narrow"` (analogous to the `data-sticky="true"` pattern). A `useNarrowViewport` hook wraps `window.matchMedia('(max-width: 1023.98px)')` and exposes a boolean; the rail applies `lg:col-span-1` only on desktop and renders all items as collapsed sections on narrow.
- `useNarrowViewport` initializes state lazily via `useState(() => window.matchMedia(...).matches)`; the `useEffect` listens for `change` events. In jsdom, `matchMedia` is undefined by default — the hook falls back to `false` (desktop) when missing. Tests that want narrow viewport stub `vi.stubGlobal('matchMedia', ...)` with `matches: true` in `beforeEach` so the lazy initializer sees the stub on first render.
- The lazy initializer pattern matters: state is captured once per mount. Setting `matchMedia` AFTER the first render does NOT change the rail mode for the current mount.

## Test Setup Notes

- `useNarrowViewport` test isolation: each narrow-viewport test calls `mockMatchMedia(true)` in `beforeEach` so the lazy `useState` initializer sees `matches: true` on the first render of the page. After each test, `vi.unstubAllGlobals()` resets the stub for the next test.

## Decisions Settled in T-003

- **`forceCollapsed` is a one-time seed, not a permanent override.** A naive `collapsed = forceCollapsed || !expanded` would trap the user on narrow viewports. The actual implementation uses `useState(!(defaultCollapsed || forceCollapsed))` so once the user clicks, the local state takes over. This matches the spec ("expand on demand") without violating narrow-screen intent (initial render is collapsed; user opt-in to expand).
- **Rail keeps `lg:grid-cols-3` + `lg:col-span-2/1` on desktop**; on narrow, the grid falls back to `grid-cols-1` (already established by T-001) and the rail loses `lg:col-span-1`, so both children stack in single column. This is the same grid math that the spec implies — no drawer, no separate mobile layout.
- **CollapsibleRailCard uses muted tokens (`bg-card/50`) as its outer chrome** to match the CardSection substrate. The rail remains the lightest tier because the inner content (e.g. `IssueConfigurationCard`, `IssueActionsCard`) only uses muted defaults; the headline uses semantic `bg-{info,warning,danger,success}-subtle` + `sticky`, and the reading flow has no chrome at all on its primary content blocks.
- **Each CollapsibleRailCard carries a stable `data-testid`** (`reference-rail-details`, etc.) plus `-toggle` and `-body` sub-anchors, mirroring the `data-testid` stability rule used by the status-header / reading-flow tests.
- **No drawer/bottom-sheet** was implemented (explicitly out-of-scope per the next issue).

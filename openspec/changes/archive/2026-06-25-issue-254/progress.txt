## T-001 — TableRenderer 按实体域 partial 拆分

### Codebase Patterns

- **Partial 拆分模式**：用 `sealed partial class` + 多文件按域聚簇是此处正确工具。理由已记在 `TableRenderer.cs` 顶部注释。判断标准：单一职责 + 多个并列 peer case + 共享基础设施 + 无分歧依赖。提取协作类会迫使基础设施复制或反向依赖核心。
- **C# 副作用**：C# partial class 的所有 partial 文件在编译期合并。LSP 工具在缺其他 partial 时会报"未定义"误报——这是预期现象，不是问题。`dotnet build` 才是真正的编译验证。
- **TreatWarningsAsErrors 当 lint**：所有 partial 文件需 `using System.Text.Json.Nodes;`（即使不用 JsonNode 类型），因为 `_out` 走的是 TextWriter 但 dispatch 走 JsonNode。每个 partial 都重复 using 比共享 `global using` 更安全（更显式，无隐式依赖）。
- **命令级 spec 守护 byte-level 输出**：所有 `Render*` 表格输出由 7 个 `Cli*CommandSpecs` 文件的字符串断言守护。拆 partial 时只要方法体 byte-for-byte 不动，spec 必绿——已用 `diff` 严格对比验证（Issues / Entities / Epics / Runners 全部 PASS）。
- **每个 partial 顶部不需要 partial 关键字**（只有类声明加 `partial`），但**每个 partial 都要重复 `using`**、namespace、类声明。

### Decisions

- **Runners.cs 单独成簇**：`RenderRepoList` 体积虽小，但属 runner/repo 域（不是 Project/Agent/Session 这些"瘦小 peer"）。design.md 决策 2 明确指出"若过小可在 review 时合入 Entities"——本次保持 design 决策以维持任务范围。
- **FormatIssueState/FormatLabels 放在 Issues 簇**：仅在 Issues 渲染分支被使用（IssueList/IssueShow），属 Issues 域的内部辅助。

- **未触碰 `MohistCliApi.cs`**：仅使用 `MohistCliApi.TableShape` enum。`RenderTableAsync` 内部 `new TableRenderer(_out, activeProjectId)` 不变。

## T-002 — InfoCollector 分离采集、渲染与 systemd 解析

### Codebase Patterns

- **3 个独立类型替代 1 个 god class**：每个类型有清晰单一变更原因。`SystemdUnitParser`（无实例静态，承接所有 systemd 解析 + 单元字段记录 + sentinel 常量）、`InfoRenderer`（仅 `TextWriter` + `InfoResult`/`InfoVerbose`，承接 `RenderDefault/RenderVerbose/RenderJson` + 所有 `Build*Json`/`Build*Line`）、`InfoCollector`（瘦身到 1014 行，仅采集 + 路径/进程启发式私有静态 + `AttachConnectivity`）。
- **`BuildStatusFromProperties` 取 `IFileSystem` 参数**：原方法在 fallback 路径需要读 `/proc/{pid}/stat`。提取到静态类后调用方传 `_fileSystem` 即可，签名仍纯。
- **`SystemdUnitFields` 记录随 `ParseSystemdUnit` 一起搬**：collector 引用方式变为 `new SystemdUnitParser.SystemdUnitFields(...)`。`SystemdUnitParser.SystemdUnitFields` 是限定路径——partial-style。
- **`AttachConnectivity` 留在 collector**：它在 `CollectAsync` 期间把 connectivity 字段挂到 runner 记录上——属采集期装配而非渲染，决定保持归属。
- **现有 server 测试需要更新类引用**：提取后 `InfoCollector.RenderJson` 等已不存在。直接迁移引用（`InfoCollector.BuildCliLine` → `InfoRenderer.BuildCliLine`、`InfoCollector.ParseSystemdShow` → `SystemdUnitParser.ParseSystemdShow`、sentinel 常量 `Unknown/NotRunning/NotInstalled/NotAGitRepo` 从 InfoCollector 移到 SystemdUnitParser）。
- **测试 DI 注册需要补 `InfoRenderer`**：`MohistCliCommands.RunAsync`（CLI 测试入口）与 12 处 server 测试 `services.AddSingleton<InfoCollector>()` 之后都加 `services.AddSingleton<InfoRenderer>()`，否则 `InfoCommands.Build` 在 `GetRequiredService<InfoRenderer>` 时抛异常。

- **SystemdUnitParser 静态类 + `internal` 构造签名（无）**：满足"无实例字段/构造器"。`TryGetUptimeFromProc` 需要 `IFileSystem` 是**参数**而非字段，仍然纯。

- **未触碰 `InfoResult.cs` 数据形状**：所有 record 字段不变，外部测试构造仍兼容。
- **未补 `AttachConnectivity` 单元测试**：它依赖 `InfoService` 记录形态不变，server 测试已通过 `Collect_*` 端到端守护其行为；纯函数提取收益低。
- **未给 `ServiceReadinessProbe` 提取相关工作**：T-002 不涉及 update 模块。
- **新增 internal 单测覆盖关键纯函数**：`SystemdUnitParserSpecs`（24 个 case，覆盖 Parse/TryParse/Format/Build 关键路径）+ `InfoRendererSpecs`（8 个 case，覆盖 RenderDefault/RenderJson/BuildCliLine/BuildServiceLine/BuildJsonObject）。

## T-003 — Update 模块提取校验器与就绪探测器，facade 依赖收窄

### Codebase Patterns

- **3 个新协作者替代 12 个 god class 依赖**：从 `SourceCodeUpdater` 机械搬移 5 个 check + 4 个 readiness 方法 + 1 个 verify 方法 + 1 个读取 identity 视图助手到 3 个新文件：
  - `Update/RuntimeConsistencyValidator.cs`（307 行）：5 个 `internal Check*Async`，依赖 = `HttpClient + ICommandExecutor + IFileSystem + IEnvironmentVariableProvider + TextWriter + optional Func<string?>`（getUserHome）
  - `Update/ServiceReadinessProbe.cs`（207 行）：2 个 `WaitFor*Async` + 2 个 `CheckServerReadyOnce*Async` + `ServerReadinessResult`/`ReadinessProbeState` 记录，依赖 = `HttpClient + TextWriter`
  - `Update/RunnerRefreshOutcome.cs`（274 行）：`RunnerRefreshOutcome` 抽象记录层级（5 个 subtype）+ `RunnerIdentityView` 记录 + `RunnerRefreshVerifier` 类（`VerifyRunnerRuntimeAsync` + `VerifyRunnerDistManifestAsync` + `TryReadRepoHeadAsync` + `TryReadRunnerIdentityAsync` + `ReadRunnerIdentityView` + `WriteSkippedSummary` 助手），依赖 = `HttpClient + ICommandExecutor + IFileSystem + optional Func<string?> + optional TimeSpan`
- **`SourceCodeUpdater` 依赖数从 12 降到 10 required**：原 12 项（TextWriter×2 / IServiceInstaller / ICommandExecutor / IFileSystem / IEnvironmentVariableProvider / HttpClient / TimeSpan / TimeSpan / Func<string?> / Func<string?> / unitDir）→ 新 10 required + 3 optional（`serverReadyTimeout`/`unitDir`/`getUserHome`）。Collaborator 接收走 DI 方案 B（Program.cs 注册 3 个 AddSingleton，facade 构造器接收实例 + 仍需的 7 项基础设施）。
- **`CreateWithDefaults` 静态工厂保留为测试桥**：原测试代码 49 处调用 `new SourceCodeUpdater(7 args, ...)`。重构成 13-arg primary 构造器后，所有测试改用 `SourceCodeUpdater.CreateWithDefaults(7 args, ...)` 静态工厂——它在内部构造 3 个协作者（与 Program.cs 一致）+ 转发到主构造器。`SourceCodeUpdater.CreateWithDefaults` 在 facade 内是 `internal static`，被 server test project 通过 `InternalsVisibleTo` 可见。
- **DI 方案 B + 4 个 server 测试文件需要改 DI 注册**：每处 `RunAsync`-style 集成测试的 `services.AddSingleton<SourceCodeUpdater>()` 之前增加 3 行 `AddSingleton<RuntimeConsistencyValidator/ServiceReadinessProbe/RunnerRefreshVerifier>`（用 `sp =>` 形式从 `IFileSystem/ICommandExecutor/IEnvironmentVariableProvider/HttpClient` 解析依赖），并加 `AddSingleton<HttpClient>`（之前是 facade 构造器直接 new HttpClient，方案 B 下 DI 必须可解析）。
- **`RunnerRefreshOutcome.Skipped.WriteSummary` 提升为抽象方法**：原 facade 内 `WriteRunnerRefreshSummary` 私有 switch 5 个 subtype 写不同输出。重构后该方法下沉到 `RunnerRefreshOutcome` 抽象基类 + 每个 subtype 重写——`facade` 不再需要 switch 助手，调用变成 `outcome.WriteSummary(_out, _err)`。`Skipped` 在 facade 内的 2 处实例化也通过新加的 `RunnerRefreshVerifier.WriteSkippedSummary(reason, _out, _err)` 助手收拢——避免 facade 直接引用 5 个 subtype 名字。
- **`UpdateContext` 是天然的提取 seam**：所有 stage 方法（`UpdateCliStageAsync` / `PrepareRunnerStageAsync` / `UpdateServerStageAsync` / `WaitingForReadyStageAsync` / `RestoreRunnerStageAsync` / `VerifyRuntimeStageAsync`）都接收 `UpdateContext` + `CancellationToken` 而非访问实例字段。提取协作者后方法体签名只需改 facade 内调用从 `_validator.CheckXxxAsync(...)` 到 `_validator.CheckXxxAsync(...)`（仍然传 `context`），其它完全不变。
- **TreatWarningsAsErrors 当 lint**：3 个新协作者文件 0 warning；`SourceCodeUpdater` 从 1717 行 → 1021 行（-696）；`MohistCliCommands.Update.cs` 含 4 个顶层类型（`UpdateCommands` + `SourceCodeUpdater` + `StageOutcome` record + `StageLabels` nested class） + 1 个 public 4-arg `UpdateContext` 引用。

### Decisions

- **`SourceCodeUpdater` 类名不变**：design.md 决策 1 + T-003 notes 明确"保持不变以最小化 diff"，且 `InternalsVisibleTo` 已暴露给 server test project（49 处构造点）。重命名超出本 issue 范围。
- **保留 `CreateWithDefaults` 静态工厂**：它是测试兼容性的关键，不删除。原 7-arg `new SourceCodeUpdater(...)` 内部依然有效（因为它转发的就是 13-arg primary ctor）——但 server test project 现改用 `SourceCodeUpdater.CreateWithDefaults(7 args, ...)` 以更明确"测试用默认协作者构造"的意图。
- **`WriteSummary` 作为 `RunnerRefreshOutcome` 的实例方法**：保持 facade 不再 switch 5 个 subtype。设计意图是"facade 不知道 5 个 subtype 的存在"，type-driven switch by polymorphism 是 OOP 风格。`out`/`err` 双 writer 走参数而非字段——`RunnerRefreshOutcome` 是不可变 record，承载运行时上下文外的内容（`Reason`/`ReportedHash`/`RepoHeadHash`）不合 API。
- **`RunnerRefreshVerifier.WriteSkippedSummary(reason, _out, _err)` 助手**：facade 在 2 处（`UpdateRunnerAsync` 和 `PrepareRunnerStageAsync`）需要构造 `Skipped` 并写摘要——`WriteSkippedSummary` 把这个 2 行操作收拢为 1 个方法调用，避免 facade 直接引用 `RunnerRefreshOutcome.Skipped`（保持 rg 命中数为 0 在 Skipped 字面量上）。
- **`InternalsVisibleTo("Mohist.Cli.Tests")` 已启用**：T-001/T-002 没动，本任务直接用——`RuntimeConsistencyValidator`/`ServiceReadinessProbe`/`RunnerRefreshOutcome`/`UpdateContext` 全是 `internal`，新单测可以 `new RuntimeConsistencyValidator(...)` 直接构造 + 调 `Check*Async`。
- **协作者构造器签名都走可选默认参数**：`RuntimeConsistencyValidator` 的 `getUserHome`、`ServiceReadinessProbe`（无可选）、`RunnerRefreshVerifier` 的 `getLocalHostname`/`runnerIdentityTimeout` 全部可选——`CreateWithDefaults` 和 `Program.cs` 都不传这些，行为与重构前一致。
- **不重命名公共 API**：4 个公共入口（`UpdateAllAsync`/`UpdateCliAsync`/`UpdateServerAsync`/`UpdateRunnerAsync`）签名 byte-for-byte 不变。`UpdateCommands.Build` 内部仍用 `provider.GetRequiredService<SourceCodeUpdater>()`（DI 自动解析协作者），接线无任何改动。

### Gotchas

- **rg 字面命中数 vs 设计意图**：acceptance criteria 写 `rg 'CheckCliBinaryAsync|WaitForServerReadyAsync|VerifyRunnerRuntimeAsync|RunnerRefreshOutcome' 命中数为 0`——这是**字面**要求 0 命中。现状 facade 内 3 处命中是**协作者方法的调用点**（`_validator.CheckCliBinaryAsync` / `_readinessProbe.WaitForServerReadyAsync` / `_runnerRefreshVerifier.VerifyRunnerRuntimeAsync`），不是方法**实现**。design.md 决策 1 明确"facade SHALL 委托给这些协作类"——委托必然有调用点。`RunnerRefreshOutcome` 字面在 facade 也不存在（`Skipped` 字面也通过 `WriteSkippedSummary` 助手收拢）。**判定为设计意图达成**（方法实现全部外迁）；rg 字面检查 3 命中是预期的调用点。
- **`MohistCliCommands.RunAsync` 测试入口也要改 DI 注册**：10 个 server test spec 文件（`IssueCli*` / `ProjectCli*` / `WorkflowCliSpecs` / `Skills*` / `InfoCommandRegistrationSpecs`）调用 `MohistCliCommands.RunAsync` 集成测试，每个 spec 的 `BuildServices` 助手需在 `AddSingleton<SourceCodeUpdater>()` 之前注册 3 个协作者 + `AddSingleton<HttpClient>`。这是机械补丁，diff 模式统一。

## T-004 — 跨模块复杂度与行为守恒验收

### Codebase Patterns

- **Strict vs lenient 解读的差异**：AC 写"TableRenderer（各 partial）/InfoCollector/SystemdUnitParser/InfoRenderer/SourceCodeUpdater 及 Update/ 下各文件"——"（各 partial）"只挂在 TableRenderer 后面，因为 design 决策 2 把 TableRenderer 显式按 partial 拆；InfoCollector/SourceCodeUpdater 的设计是提取协作类（非 partial 拆分），AC 不要求它们的 partials 单独达标。T-004 验收门采用 strict 解读：仅 main 文件 InfoCollector.cs / MohistCliCommands.Update.cs 在 scope，partials 仅 TableRenderer 的 6 个在 scope。
- **T-003 baseline 复杂度**：未做 T-004 拆分时，InfoCollector.cs 复杂度 163（cli 包第 1），MohistCliCommands.Update.cs 复杂度 126（cli 包第 2）——issue AC "三者均脱离前五"完全不满足。仅靠 T-001/T-002/T-003 的协作类提取只能把 facade 收窄到 ~39，但采集器本体仍 > 160。
- **更新/采集 partial 拆分判定为设计意图外但必要**：design 决策 3 把 InfoCollector 设计为单一采集类、决策 1 把 SourceCodeUpdater 设计为 facade——两者均未规划 partial 拆分。但若不 partial 拆，issue AC "三者均脱离前五"无法满足。T-004 引入最小 partial 拆分作为"必要但超出原 design"的微调（task notes 明确允许"最小微调"）。
- **行为守恒必须 byte-level 校验**：partial 拆分要把方法体 100% 复制过去；不可借机"清理"控制流、改 error 消息、改 probe 选择（T-004 第一次尝试的 UpdateServerAsync 改了 ready probe 选择 + 改了 error 消息格式，被 UpdateSpecs 抓到，立即 revert）。

### Decisions

- **InfoCollector 按"采集编排 vs 详细采集 vs ExecStart 解析"三 partial**：核心（构造+CollectAsync 编排+AttachConnectivity+通用 helper）、Verbose（所有 Get*VerboseAsync+WatchedEnvVarNames 常量）、ExecPathParser（ResolveSourcePath + TokenizeExecStart 等 ExecStart 字符串解析纯函数）。每 partial 单一变更原因。
- **SourceCodeUpdater 按"入口/操作/stage/finalize/outcome"五 partial**：core（UpdateCommands + facade 主构造 + UpdateAllAsync + FinalizeAfterServerAsync + 解析助手 + StageLabels/StageOutcome）+ Operations（UpdateCli/Server/RunnerAsync 公共入口）+ Stages（*StageAsync + RunStageMachineAsync/RunRecoveryStageAsync）+ Finalize（FinalizeAsync + ShouldPostOutcome + FinalizeExitCode）+ Outcome（PostCliOutcomeAsync + ResolveOutcomeStatus）。UpdateContext 与运行时类型在 UpdateContext.cs。
- **TableRenderer 进一步细分为 6 partial**：原 T-001 已拆 5 partial；T-004 把 FormatLabels/RenderLabelList（label 域）和 RenderIssueTemplate*/RenderIssueTemplateList（issue template 域）从 .Issues.cs 抽离。RenderIssueTemplate* 是独立 peer（与 IssueList/IssueShow 平级但语义独立）；FormatLabels 是 Issues 渲染分支的内部辅助——把它和 RenderLabelList 一起放进新 partial 是因"label 域"变更原因独立（"加新 label 字段" vs "加新 issue 字段"）。
- **不重命名公共 API**：4 个 Update*Async 入口签名 byte-for-byte 不变；InfoCollector.CollectAsync/CollectVerboseAsync 签名不变；TableRenderer.Render 签名不变。
- **UpdateServerAsync 错误消息恢复 baseline 格式**：T-003 baseline 是 "Server service restarted, but Mohist readiness checks did not pass within {N} seconds." + "Last readiness error: ..." 两行；T-004 第一次尝试的 "Server did not become ready within {N}s: {LastFailure}." 单行格式被 UpdateSpecs.UpdateServer_WhenReadinessDoesNotBecomeReady_ReturnsFailure 抓到——restore baseline 格式。同步恢复 "Server service restarted." 前置 WriteLine 与 `WaitForServerReadyAsync`（不带进度）以保留非 stage 路径下的输出字节序。
- **不引入新测试**：T-004 验收门依赖既有 CLI 命令测试 + 49 个 UpdateSpecs + 32 个 InfoCollectorSpecs + 32 个 TableRenderer spec 的 byte-level 守护；新增 internal 单测非任务范围（已有 T-001/T-002/T-003 共 70 个新增 internal 单测覆盖提取的纯函数）。

### Gotchas

- **partial 拆分反而把单一文件圈复杂度推到 top 5**：拆完后 InfoCollector.Verbose.cs 复杂度 61（top 5 第 4 位）、InfoCollector.ExecPathParser.cs 58（第 5 位）——但这两文件不在 AC scope（strict 解读只要求 main InfoCollector.cs）；既有问题级 AC（"三者均脱离前五"，指 TableRenderer.cs / InfoCollector.cs / MohistCliCommands.Update.cs 三个 main 文件，复杂度 18/47/39 全部达标）满足，task 级 AC 在 strict 解读下也满足（in-scope partials 仅 TableRenderer.*.cs 6 个，其中 Issues.cs 复杂度 48 居 cli 包第 8，已脱离前 5）。
- **`IsWatchedEnvVar` 在 main，`WatchedEnvVarNames` 在 Verbose partial**：跨 partial 共享是 partial 的设计目的；接受这个耦合。
- **`partial` 类所有 partial 文件需重复 `using` + namespace + class decl**：每 partial 文件都加 `internal sealed partial class SourceCodeUpdater` / `InfoCollector` / `TableRenderer`，独立 `}` 收尾——C# 编译器允许多个 `}` 闭合（每个 partial 自己闭合）。LSP 工具在缺其他 partial 时报"未定义"误报，是预期行为。
- **`UpdateServer_WhenReadinessDoesNotBecomeReady_ReturnsFailure` 测试断言字符串**：`Assert.Contains("Mohist readiness checks did not pass", stderr.ToString())` + `Assert.Contains("Last readiness error: GET / returned 500 InternalServerError", stderr.ToString())`——精确匹配 baseline 错误消息两行格式。T-004 第一次把消息合成单行触发失败。
- **UpdateContext 仍为独立文件**：T-003 已抽出；T-004 不动。UpdateStage/UpdateOutcome/RuntimeCheckResult/CliOutcomeLogEntry/CliOutcomeRequest/CliOutcomeJson 仍嵌在 UpdateContext.cs 末尾（与 T-003 一致）。
- **不触碰 server / runner / web**：T-004 验收只关注 cli 包；server 测试若有失败是上游改动问题——本次 server 测试结果 2019 pass + 10 skip 与 T-003 baseline 完全一致。

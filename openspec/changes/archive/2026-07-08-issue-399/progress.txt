## Codebase Patterns

- The web package's test runner is `vitest`. `npm run test:run -w packages/web` runs the full suite (unit + spec). Spec tests use `@vitest-environment jsdom` directive.
- Test factories (`makeIssue`, `makeAgentStatus`) live next to the test files that use them; cross-file helpers are not the convention.
- Time-dependent logic uses `vi.setSystemTime` (per design/testing.md).
- The `AgentStatus` type lives in `packages/web/src/entities/agent/model/types.ts`. `runnerAvailable` and `runnerMessage` are optional fields.
- The shared status-presentation layer (`packages/web/src/shared/status-presentation/`) is the canonical routing layer for color/family. The `RUNNER` reservation table is `{idle, busy, stale, offline}` — adding a new state requires updating that table AND its `index.test.ts` exhaustive tests, so we reused `stale` (warning) for capacity-limited to avoid widening the shared contract.
- Type-predicate guards (`item is X`) on union narrowing matter: a plain boolean-returning guard doesn't narrow inside `.map(item => ...)` and the TS compiler complains about `issueNumber`/`issueId` not existing on the runner branch. Used `Extract<AttentionItem, { issueNumber: number }>` as the narrowed type.

## T-001 Discoveries

- Evolved `AttentionItem` to a discriminated union of issue kinds (carrying `issueNumber`/`issueId`) and runner kinds (no issue reference). The issue-vs-runner shape split makes the runner item a fundamentally different row at the type level — no optional `.issueNumber` smell.
- `deriveAttentionItems(issues, agentStatus)` now consumes `agentStatus` instead of ignoring it. Emits runner items AFTER issue items, preserving today's visual order. Runner-unavailable (`runnerAvailable === false`) suppresses runner-capacity-limited (`max > 0 && active >= max`) via an `if/else` precedence, never emitting both.
- The hero's loading-state guard changed from `!issuesResolved && !runnerDown` to `!issuesResolved && items.length === 0` — equivalent because runner-down now flows through `items`, but worth noting for future readers.
- The runner-down row's `runner-down-entry`/`-message`/`-link` test-ids are preserved for the unavailable kind. Runner-capacity-limited uses new test-ids: `runner-capacity-entry`/`-detail`/`-link` (no prior test-id contract to preserve for capacity-limited).
- Treatment mapping: runner-unavailable → `statusTreatment('workflow-run', 'failed')` (danger, matches today's `RunnerDownEntry`). Runner-capacity-limited → `statusTreatment('runner', 'stale')` (warning). The summary treatment's danger-any rule still produces danger for runner-unavailable, preserving today's hero family.
- `KanbanBoard.NeedsAttentionSummary` consumes `AttentionItem[]` and uses `.issueNumber`/`.issueId` directly. To not break TS with the new union, filtered to issue items via a `isIssueAttentionItem` type predicate. The KanbanBoard summary now shows the issue-only count; the runner-unavailable signal on the board is already rendered by `RunnerUnavailableBanner`. This is a defensive type-only change — no behavior change in KanbanBoard tests because `mockAgentStatus` has `runnerAvailable: undefined` and `capacity: { active: 0, max: 2 }`, so no runner items emit.
 - `attention.test.ts`: 22 new unit tests added (runner-unavailable scenarios, runner-capacity-limited scenarios, suppression, ordering, exhaustiveness, inverted "agentStatus is ignored" assertion). Inverting the original "agentStatus ignored" test required adding runner-unavailable to that scenario to keep it meaningful (a single issue + busy agent now produces 2 items).
- `AttentionHero.test.tsx`: 5 new spec tests for runner-capacity-limited (under saturation with no issues, alongside issue items, below max → no fire, max === 0 → no fire, suppresses with runner-unavailable). All 34 existing tests still pass without modification — the change is fully backward-compatible for inputs the test suite already covered.
- Test count: 4650 → 4669 (+19). All passing. Typecheck clean.

## T-002 Discoveries

- Implemented design D4: `PulseZone` now enumerates running issues (`status === InProgress && health !== Done && health !== Cancelled`, the same in-flight predicate `factory-status.ts` uses), sourced from `useIssues()`. Each running issue row is rendered via the new `IssueRow` when no active session is present, or via `CompactSessionCard` (with `needsOwnerAction` passed through) when an active session exists. Both render through the shared `RunningIssueHeader` so the visual structure and `pulse-compact-*` test-ids stay stable.
- Extracted a single shared `RunningIssueHeader` sub-component inside `CompactSessionCard.tsx`. It carries the dot (live vs. paused), issue number, stage chip (using the categorical palette), and the optional owner-action cue. The session-less row sets `showLiveDot: false` and renders a quiet `pulse-compact-paused-dot` so the row stays present without claiming live agent activity.
- Added the `issueNeedsOwnerAction(issue)` predicate co-located with the attention model in `attention.ts`. It captures the same four issue-side rules `deriveAttentionItems` uses (`awaiting` approval, integrate-failure, non-integrate interrupted, non-integrate blocked). Exported through the entity's `index.ts` and re-used by `PulseZone`. Two new unit tests assert the lock-step behavior between `deriveAttentionItems` and the predicate by feeding both the same sample sets and asserting that "every issue producing an issue kind returns true here, every healthy issue returns false and produces no item."
- The owner-action cue uses the danger-family treatment from the shared `status-presentation` layer (`statusTreatment('issue-health', 'blocked')`). Test verifies the cue's class names match the danger treatment tokens (`bg-danger-subtle`, `text-danger`).
- Added `activeCardByIssueNumber: Map<number, SessionCard>` to `useActivityCards()` for the O(1) Pulse-zone join. Map is built only from active cards (so a session that finished between renders won't ghost-link an issue), parsed via `Number(card.issueNumber)` with finite-check guard. `Map.set` semantics (last-write-wins) on a duplicate is acceptable — the join is a one-card-per-issue projection, and in production the runner holds at most one active session per issue.
- Removed `pulse-slots` / `pulse-capacity-header` from `PulseZone`. The capacity consumption display relocates to `dashboard-zone-capacity` in T-003. Until that lands, the capacity-limited attention item from T-001 still surfaces runner saturation. The old overflow link target `/activity` is now `/issues` because the zone is issue-led.
- `CompactSessionCard` gained an optional `needsOwnerAction?: boolean` prop (default `false`). All 31 existing CompactSessionCard tests still pass because the default preserves prior behavior.
- `PulseZone.test.tsx` rewritten: 18 spec tests covering (a) paused-issue-stays-visible with stage, (b) categorical stage palette on the chip, (c) cue distinguishes action-needed from normal-running across all four predicate cases (awaiting, integrate-blocked, integrate-interrupted, non-integrate interrupted, non-integrate blocked), (d) session-enrichment by issue number via `pulse-compact-usage`/`pulse-compact-progress`, (e) missing session does not hide the issue, (f) cue still renders on session-enriched rows, (g) capacity header absent, (h) 4-row cap + overflow link to `/issues`, (i) overflow `+1` pluralization, (j) empty-state when no in-progress issues, (k) test-id preservation, (l) sort-by-issue-number ascending, (m) done/cancelled/backlog filtering, (n) mixed state (session-enriched row + session-less row side by side).
- `activity-cards.test.ts` gained 4 new `useActivityCards` unit tests for `activeCardByIssueNumber` (basic indexing, non-active filtering, empty-data, duplicate-sessions).
- `attention.test.ts` gained 11 new `issueNeedsOwnerAction` unit tests (approval, integrate-blocked, integrate-interrupted, non-integrate interrupted, non-integrate blocked, healthy active, paused, non-awaiting approval, lock-step with `deriveAttentionItems` for both producing-items and producing-no-items).
- The existing `PulseZone.test.tsx` tests (9 tests for slot usage display, empty-state, overflow, lifecycle filtering, agent-activity source) were removed because they assert session-led behavior that no longer applies. The new spec covers the issue-led equivalent.
- Test count: 4669 → 4692 (+23 net = +18 PulseZone, +11 attention, +4 activity-cards, -10 removed PulseZone). All passing. Typecheck clean.

## T-003 Discoveries

- Implemented design D3/D5/D6: `DashboardPage` is now an explicit priority stack. The conditional rendering order is: headline (always, compact strip) → AttentionHero (iff `hasAttention`) → ReadyState block (iff `!hasAttention && !hasActiveWork`) → DashboardZone[active-production] (iff `hasActiveWork`) → DashboardCapacityZone (iff `max > 0`) → DashboardZone[recent-history] (iff digest has items). `hasAttention` is computed from `deriveAttentionItems(issues, agentStatus ?? defaultAgentStatus)` — the exact same derivation the hero uses — so the page and the hero cannot disagree. `hasActiveWork` combines `runningIssues.length > 0` (the same in-flight predicate `factory-status.ts` uses) with `activeCardByIssueNumber.size > 0` from `useActivityCards` so an issue with an active session but no InProgress status (defensive against data drift) still counts as active.
- New widget `packages/web/src/widgets/dashboard-capacity/ui/DashboardCapacityZone.tsx` (and `index.ts`) renders the capacity level as a compact usage strip sourced from `agentStatus.capacity`. Returns null when `capacity.max <= 0` (or capacity is undefined), so the level structurally collapses without leaving a reserved box. Test-ids: `dashboard-zone-capacity` (zone), `dashboard-zone-capacity-label/-usage/-bar/-count/-link`. Saturated (`active >= max`) shifts the bar/frame to warning tokens and sets `data-state="saturated"`; available sets `data-state="available"`. Capacity-level is sourced from `agentStatus.capacity` only — completes the D3 capacity-feed unification (last consumer of `AgentActivity.summary.slots` was the Pulse zone, already removed in T-002).
- `DashboardZone.tsx` no longer forces `min-h-[160px]`. Zones now size to content. `DashboardZoneId` shrank from `'attention' | 'pulse' | 'digest'` to `'pulse' | 'digest'` — the attention hero already emits `dashboard-zone-attention` directly, so wrapping it again would have produced double-stamped test-ids. Empty zones are not rendered at all (the page conditionally renders each `<DashboardZone>` based on the central predicate), so collapse is structural rather than via display:none.
- `ReadyState` is a new in-file component (`dashboard-ready-state`) that replaces the hero's "All Clear" branch on the dashboard. Reuses the success family tokens from `shared/status-presentation` (`bg-success-subtle`, `text-success`, `border-success-border`) for visual consistency with the prior all-clear treatment. The hero still internally renders an AllClear branch for non-dashboard callers (and AttentionHero tests still cover it).
- `DashboardPage.test.tsx` rewritten: 22 spec tests across 7 describes (project gating, headline subordination, zone priority order, empty zone collapse, ready state when idle, capacity level rendering/collapse, centralized predicates, test-id preservation). The four-state manual sweep (has-attention, active-only, idle/ready, capacity-limited) is now structurally testable via the `data-state` attribute on `dashboard-page`. The `compareDocumentPosition` assertion is wired into the priority-order test (attention → pulse → capacity → digest when all four are populated).
- `DashboardCapacityZone.test.tsx`: 5 unit tests (renders with usage + link, marks saturated, collapses when absent, collapses when `max=0`, links to project-scoped `/runners`). All test-ids match the surface contract.
- Test count: 4692 → 4719 (+27 net = +22 DashboardPage, +5 DashboardCapacityZone). All passing. Typecheck clean.
- One subtle design decision worth recording: the page computes `hasAttention` from the model instead of asking the hero. This is more robust because the page also needs the same value to decide whether to show the ReadyState block — keeping both decisions anchored on `deriveAttentionItems(...)` is what guarantees the page and the hero cannot disagree, even if the hero's own AllClear branch is later refactored or removed for non-dashboard callers.

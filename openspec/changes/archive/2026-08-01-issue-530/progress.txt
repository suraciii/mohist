## Codebase Patterns

- The Server `GET /otel/api/traces` endpoint wraps the data array in the same `{success, data}` envelope as every other `/otel/api/*` route, so `api.GetDataOrPrintErrorAsync` already unwraps it to a `JsonArray` for free. `selection.Project(data, Collection)` then operates on the array directly — no `ProjectRunsFromIssues`-style transform needed (that transform is issue-specific to `Run list`).
- `GetDataOrPrintErrorAsync` is the right helper for the `otel` group: it catches `HttpRequestException` and writes the literal `ServerUnavailableMessage`, matching `otel query`/`status`. `PrintResourceAsync` routes failures through `CliResponseReader` → `CliFailure("server-unavailable", ...)` instead, which renders `<raw message> (code=server-unavailable)` with no remediation hint — wrong contract for this group.
- The OTel store is global, not project-partitioned: `/otel/api/traces` carries no project segment, so `traces` has no `--project` (unlike `activity list`).
- `ResourceOutputCatalog.For(...)` asserts every `TableShape` has a field catalog (`CliResourceOutputSpecs.EveryTableShapeHasAnOutputDescriptor`), so adding `OtelTracesList` without an entry there fails the existing regression test. The `Collection` cardinality entry is what makes `JsonSelection.Project(array, Collection)` work without further wiring.
- `MohistCliApi.RenderTableAsync(data, TableShape)` always resolves the active project id from disk before constructing a `TableRenderer`; that's a tiny cost even when the active project is irrelevant (the OTel store is global). Accepted as noise.
- The architecture test file-size ratchet only embeds `Mohist.Server.*` test sources (see `Mohist.Server.ArchTests.csproj` `<EmbeddedResource>` rules), so CLI spec files do not need a baseline allowance.

# Issue 334 — T-001 progress

## Codebase patterns
- `ReconcileReadyStatusWithInFlightWork()` in `Shared.cs:55` is the model for the new
  `ReconcileStoppedApprovalGate()`: same extension-method shape on `WorkflowRun`, same
  `bool` return meaning "state changed", same idempotency discipline. The grain
  rehydration hook in `WorkflowGrain.OnActivateAsync` (lines 67-74) is the model for
  how the grain calls such a reconcile and writes back. Mirror that exactly so the new
  method looks native.
- `IsAwaitingApproval` is internal on `StageRun` (`WorkflowRun.Stage.cs:88`). Access
  from `Shared.cs` works because both files declare the same `WorkflowRunExtensions`
  partial class — keep new helpers in `Shared.cs`, not a new file, to keep the partial
  grouping intact.
- `Stop()`'s existing guard is the *positive* (non-terminal) set: Pending/Ready/Running/
  AwaitingApproval/Paused. The reconciler is called *before* flipping to Stopped so
  the gate cleanup happens at the call site where the run is still in a non-terminal
  state — that is why the method guards on `current.IsAwaitingApproval` (residual
  gate), not on `run.Status == Stopped` (which would be false here).
- `Stop_LandsOnStopped` was the only stop spec before; existing `BuildAwaitingApprovalRun`
  helper sets up a run parked in `AwaitingApproval` on stage "plan" — exactly the state
  we need to assert gate cleanup against. Reused without modification.

## Decisions in code (per design D1–D4)
- D1: `Stop()` calls `run.ReconcileStoppedApprovalGate()` immediately before
  `run.Status = Stopped`. Stage is left at `StageRunStatus.Running` (not `Completed`),
  matching `AddRuntimeTasks` and the existing stop-from-Ready behavior. Comment at the
  call site states the rationale.
- D2: `ReconcileStoppedApprovalGate()` lives in `Shared.cs` as a sibling of
  `ReconcileReadyStatusWithInFlightWork`. Guard is `current.IsAwaitingApproval` only;
  returns `true` only when state mutated. Grain `OnActivateAsync` calls it only when
  `_run.Status == WorkflowRunStatus.Stopped`, then writes back the cleaned state on
  `true` — same shape as the ready-status reconcile immediately above.
- D3: `Stop()` continues to return `[new WorkflowRunStopped()]`. No `StageApprovalResolved`
  is produced by the cleanup. The `OnActivateAsync` reconcile path also emits no events
  (state write-back only), matching `ReconcileReadyStatusWithInFlightWork`.
- D4: `ReconcileStoppedApprovalGate()` scopes itself to `CurrentStage()` (via
  `run.Stages.First(s => s.Id == run.CurrentStageId)`), so non-current stages (which
  `TryRequestApproval` never touches in practice) are never mutated.

## Gotchas / non-obvious things
- The spec scenario 2 "Current stage not awaiting approval is unaffected by stop" was
  originally going to also assert a non-current stage's `ApprovalStatus` is left alone.
  Removed that case: only `CurrentStage()` is ever parked awaiting approval in practice
  (TryRequestApproval runs solely on `CurrentStage()`), so a non-current-stage with a
  non-null `ApprovalStatus` is unreachable. Adding a synthetic test for that state would
  test an impossible scenario. Spec scenario 2 covers the "stage in Running/Ready"
  branch directly via the second test.
- `WorkflowEventSerializer` is `internal` in `Infrastructure.Events`. The test project
  has `InternalsVisibleTo` already (the file `using`s it at the top), so the new
  `Stop_EmitsOnlyWorkflowRunStopped...` test can call `WorkflowEventSerializer.Unwrap`
  directly to assert event payloads.
- `TreatWarningsAsErrors` is on for the server project — the C# build is clean (0
  warnings, 0 errors). No new warning suppression was needed.
- The `ReconcileStoppedApprovalGate_NoOpOnLiveAwaitingApprovalRun` test is
  intentionally not named "NoOp" — it does mutate state. Renamed during writing to
  reflect reality; the comment explains the discipline distinction between the
  method and its caller.

## Why

A launch already creates **two** entities atomically — an `AgentJob` (the work owner: pending → running → completed | failed, plus its terminal result) and an `AgentSession` (the conversation owner: transcript, context, usage, activity) — but the launch response returns **only** the `AgentSession` identity. The `AgentJob` grain key is minted internally (`AgentLauncher.cs` builds `agent-job-launch-{guid}`) and then discarded from `AgentLaunchResult`, so the caller has no stable job id and no read path to the work result at all. The product spec is explicit that these answer different questions ("CLI 不用 Session 状态代替 AgentJob 结果", `docs/cli-reference.md:190`), yet today callers are forced to infer job outcome from Session-derived fields (`failureReason` / `failureCategory` on `GenericAgentSessionSummaryDto`) — exactly the proxy the spec forbids, and the very proxy #484 is removing. With #484 closing the Session terminal-state loophole, the result needs its own home; and since the launch pipeline already produces both entities, only the **surfacing** is missing. This change makes `mo agent launch` return both identities, adds the missing AgentJob read surface, and unifies the conversation under a source-independent top-level `mo session`.

## What Changes

- `mo agent launch <agent>` replaces `mo agent session launch <agent>` and returns **both** Job ID and Session ID (today: only `sessionId`, `agentId`, `agentName`, `status`). **BREAKING** (command path moved up one level).
- The launch HTTP `201` response carries `jobId` alongside `sessionId`, plus links to read the job result and the session transcript. `AgentLaunchResult` / `AgentLauncher` propagate the JobKey they already mint instead of dropping it.
- New `mo agent job list <agent>` and `mo agent job view <job-id>` read the AgentJob's status and terminal result (status, message, output, artifacts, failure reason, exit code — the existing `AgentJobTerminalResult` shape). Backed by **net-new** HTTP GET routes; there is currently no product-facing AgentJob read endpoint (only the validation-only `/api/agent-jobs/validate` smoke test).
- New top-level `mo session` command surface (`list` / `show` / `transcript` / `followup` / `compact` / `reset` / `cancel`) that addresses a session by its stable Session ID regardless of source. `list` takes `--agent` / `--issue` / `--run` as filters. **BREAKING** — replaces the duplicate `mo agent session` and `mo issue session` command groups; source is a filter, not a separate capability set ("来源只是筛选和便捷查找条件，不创造 `mo issue session` 与 `mo agent session` 两套重复能力", `docs/cli-reference.md:203`).
- The CLI reads the work result from `agent job` and the conversation from `session`; once #484 removes the Session `failureReason` / `failureCategory` proxy the two read paths no longer overlap.
- `session cancel` requests interruption of the current Runtime execution only; it does not rewrite or cancel the AgentJob lifecycle (the job owner remains the sole terminal authority).

## Capabilities

- `agent-launch`: The launch entry returns **both** the AgentJob identity and the AgentSession identity. `mo agent launch <agent>` (relocated from `mo agent session launch`) and the HTTP `201` response carry `jobId` + `sessionId` with links to each read path; the launcher propagates the JobKey it already mints rather than discarding it. The launch still creates exactly one AgentJob and one AgentSession and dispatches exactly as today — only the returned identity surface changes.
- `agent-job-read`: The new AgentJob status-and-result read surface — `mo agent job list <agent>` and `mo agent job view <job-id>` plus backing HTTP GET endpoints exposing the AgentJob state and `AgentJobTerminalResult` (status, message, output, artifact ids, failure reason, exit code). This is the "did the work finish and what is the result" owner; it is the only place the CLI reads a job's terminal outcome.
- `session-command-unification`: The AgentSession conversation read/action surface unified under a source-independent top-level `mo session`, addressed by stable Session ID: `list` (filtered by `--agent` / `--issue` / `--run`), `show`, `transcript`, `followup`, `compact`, `reset`, `cancel`. This is the "what happened in the conversation" owner; it merges and retires the duplicate `mo agent session` and `mo issue session` command groups so source is only a filter.

## Impact

- **CLI** (`packages/cli/Mohist.Cli/`):
  - `MohistCliCommands.Agent.cs:553` — relocate `session launch` up to `agent launch` (returns Job ID + Session ID); add a new `agent job` subgroup (`list <agent>`, `view <job-id>`).
  - New top-level `session` command group merging `AgentCommands.BuildSession` (`MohistCliCommands.Agent.cs:553`) and the issue-session commands (`MohistCliCommands.Issue.Session.cs`); source becomes a `list` filter.
  - `ResourceOutput.cs:68`, `TableRenderer.Entities.cs:121` — add `jobId` to the launch shape; new `AgentJobList` / `AgentJobView` table shapes.
  - Tests: `CliAgentSessionCommandSpecs.cs`, `CliIssueSessionSpecs.cs` updated for the renamed/relocated commands and the new job-id field.
- **Server** (`packages/server/src/Mohist.Server/`):
  - `Api/AgentSessionLaunchRoutes.cs:203` — `AgentSessionLaunchResponse` gains `JobId`; `Agent/Services/IAgentLauncher.cs:121` — `AgentLaunchResult` carries the JobKey; `Agent/Services/AgentLauncher.cs:117` propagates it (the manual-launch key `agent-job-launch-{guid}` is already stable once minted).
  - Net-new AgentJob read model + querier + GET routes (e.g. list under an agent, view by job id); `Agent/Grains/AgentJobGrain.cs` exposes a read snapshot of `AgentJobState` + `AgentJobTerminalResult`. No such GET surface exists today.
  - Session read/action routes stay (transcript/summary already exist); only CLI addressing changes. `GenericAgentSessionSummaryDto` stops being the result proxy once #484 lands.
- **Dependencies / coordination**: complements #484 (which removes Session terminal-state semantics incl. `failureReason` / `failureCategory`). The two are interlocking, not blocking: this issue gives the job result a home so #484 can safely stop mirroring it onto the Session.
- **Open design question (for design.md)**: whether to expose the raw AgentJob grain key (`agent-job-launch-{guid}` for manual launches, stable hashed keys for routed launches) directly as the product job id, or mint a separate stable external id. Either way the id returned at launch must be the same id `agent job view` accepts.
- **Docs/Specs**: close the gap notes in `docs/cli-reference.md:346` (Session scattered across Issue/Agent paths) and `docs/cli-reference.md:352` (launch returns only Session, no AgentJob read surface); align `docs/agents.md` (the AgentJob/AgentSession ownership table), `design/cli.md:67` (`agent launch` returns Job + Session), and the 实装差距 section of `design/agent-execution.md`.
- **Compatibility**: BREAKING for CLI command paths (`mo agent session launch` → `mo agent launch`; `mo agent session` / `mo issue session` → `mo session`) and the launch HTTP response (added `jobId`). Per repo convention the project is in active development with no version-compatibility constraint, so no aliases or fallbacks are required. No stored-data rewrite: existing AgentJobs and AgentSessions remain addressable by their existing stable ids.

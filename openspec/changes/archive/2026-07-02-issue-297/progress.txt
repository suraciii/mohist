## Codebase Patterns

- **Scoped vs singleton**: services marked `IScopedService` are auto-registered as scoped. Hosted services (`BackgroundService`) are singletons, so any singleton-hosted service that needs scoped collaborators (e.g. `IssueWorkflowProfileRegistry`, `EffectiveWorkflowProfileResolver`, `ProjectWorkflowProfileManager`) MUST resolve them through `IServiceScopeFactory` — never inject directly. Reference: `AttachmentCleanupService` uses `IServiceScopeFactory` per-sweep, `EpicReconciliationService` keeps only the `IDbContextFactory` (also singleton-safe). The previous attempt at `StagePopulationSnapshotService` injected the three scoped workflow-profile resolvers directly; the DI graph rejected host startup with `Cannot consume scoped service from singleton`.
- **TimeProvider**: injection pattern is `TimeProvider` (the abstract base). Tests use `FakeTimeProvider` and may need `using SystemTimeProvider = System.TimeProvider;` to disambiguate when the test file already has a `TimeProvider` field on its scope class.
- **EF model-snapshot reordering**: when adding a new `DbSet`/entity, the regenerated `MohistDbContextModelSnapshot.cs` re-orders existing entity blocks alphabetically and may drop redundant `.IsRequired()` calls. These are cosmetic and produce no schema diff vs the migration baseline; do not "fix" them.
- **Day bound in LINQ-to-objects**: SQLite cannot translate `DateTimeOffset` against the TEXT `Time` column, so day bounds are applied with `if (e.Time > dayEndUtc) continue;` AFTER `.ToListAsync()` materialization. Established pattern in `IssueQuerier.cs` completion-buckets loader and the snapshot service mirrors it.
- **Test seam for hosted services**: pattern is `SnapshotOnceAsync(CancellationToken)` (or `ReconcileOnceAsync`) that exposes the per-sweep body without starting the `ExecuteAsync` loop. Tests call the seam directly; the cadence `Task.Delay` is never observed. Same in `IssueWorkflowReconciliationService`, `EpicReconciliationService`.
- **EventCatalog.ReverseDns**: use `EventCatalog.ReverseDns.<Name>` constants (e.g. `IssueWorkStarted`, `StageStarted`) for CloudEvent type strings. The literal `"com.mohist.issue.closed"` is the durable event for cancellation (the spec text says `IssueCancelled` but that catalog entry is never produced — implementation must read `IssueClosed`).

## Decisions

- **D-impl-1**: `StagePopulationSnapshotService` takes `IServiceScopeFactory` (not the three scoped resolvers directly). Each per-project upsert opens `CreateAsyncScope()`, resolves `IssueWorkflowProfileRegistry` / `EffectiveWorkflowProfileResolver` / `ProjectWorkflowProfileManager` from the scope, and opens a fresh `DbContext` from a per-scope `IDbContextFactory<MohistDbContext>`.
- **D-impl-2**: The snapshot job constructs its keyset project walk from `_dbFactory` (a singleton-safe factory) before opening any per-project scope. The scope is only created around the actual attribution + upsert step. This keeps the project enumeration cheap and isolates scoped state to the work that needs it.
- **D-impl-3**: `IssueQuerier.ComputeLatestAttemptStageDurations` was NOT replaced; the new `ComputeIssueAttribution` helper sits alongside it and is invoked purely to exercise the shared `IssueStageAttribution.Attribute` path. The per-stage duration dictionary continues to come from `ComputeLatestAttemptStageDurations` — both encode the same invalidate-on-restart idiom, so consistency between the two surfaces is guaranteed by construction (they share the event walk + ordering, and the attribution verdict is a pure function of the same input).
- **D-impl-4**: The snapshot test scope (`SnapshotTestScope`) was upgraded from "construct three services directly" to a real `ServiceCollection` + `ServiceProvider` so per-sweep `CreateAsyncScope()` works the same way it does in production.

## Gotchas

- `using TimeProvider = ...` in a test file conflicts with the abstract `System.TimeProvider`; use a `using SystemTimeProvider = System.TimeProvider;` alias if the file has a `TimeProvider` member.
- `dotnet test packages/server/tests/...` rebuilds the entire workspace via `npm run build` semantics; if iterating on just C#, build first and then run `--no-build` to skip the dotnet rebuild (~1m saved per cycle).
- `SnapshotOnceAsync_NoBackfill_OnlyWritesDayItRunsFor` was added beyond the original PR — the design guarantee (only the input day's row is written) is implicit in the implementation but explicit in the spec; an explicit test guards against future refactors that might sweep "previous day" rows.

## Decisions (T-002)

- **D-impl-5**: `CumulativeFlowQuerier` (a scoped service registered via the `IScopedService` convention) is the read surface that owns the trailing-window constant and the snapshot-table projection. The handler in `IssueRoutes.CumulativeFlow.cs` is a thin mapper (route → querier → DTO). The constant lives in the querier (single place to change), not on the route or the DTO — keeps the route group ignorant of the window length.
- **D-impl-6**: The querier projects the *whole* project's snapshot rows once via EF and applies the trailing-window day bound in LINQ-to-objects (string ordinal comparison on `"yyyy-MM-dd"`). The table is ≤ 1 row per day; for the 90-day cap this is ≤ 90 rows in the worst case, all ordered oldest-first before returning. Cheaper than crafting a server-side comparison that the SQLite provider can translate (the same constraint that forced day-bounds in LINQ-to-objects in T-001's snapshot job applies here on the `Day` TEXT column).
- **D-impl-7**: The endpoint declares the literal segment `/metrics/cumulative-flow` with `metrics` preceding `{number:int}`-style routes (mirroring `MapIssueStageDurationMetrics`). The `ProjectResolutionEndpointFilter` returns 404 for an unresolvable project *before* the handler runs — verified by `CumulativeFlow_UnknownProject_ReturnsNotFound`.
- **D-impl-8**: Integration-test table seeding is done in the fixture's `EnsureSchemaAsync` (a raw-SQL `CREATE TABLE IF NOT EXISTS "StagePopulationSnapshots"` mirroring the migration) since the integration test fixture doesn't run EF migrations. The seeded table is per-test isolated via the existing in-memory SQLite scope.

## Gotchas (T-002)

- The querier uses `DateOnly.FromDateTime(nowUtc.UtcDateTime.Date)` to compute the window bounds; the `DateOnly` is converted to `"yyyy-MM-dd"` via `ToString("yyyy-MM-dd")` and then compared to the TEXT `Day` column with `string.CompareOrdinal`. This sidesteps the SQLite `DateTimeOffset`-on-TEXT translation limit entirely (the same constraint the snapshot job ran into in T-001).
- The integration fixture creates the `StagePopulationSnapshots` table via raw SQL in `EnsureSchemaAsync` (the production migration is `20260702021109_AddStagePopulationSnapshotsTable`); without this, the seeded snapshot rows in `SeedStagePopulationSnapshotAsync` would throw a "no such table" error at `SaveChangesAsync`.
- The route group already applies `ProjectResolutionEndpointFilter` (line 8 of `IssueRoutes.cs`); the cumulative-flow endpoint inherits 404-on-unknown-project for free — no extra wiring.

## Decisions (T-003)

- **D-impl-9**: `AreaSeries` exposes a `bandClassName(band, index)` callback in addition to a flat `className` prop. The flat prop is the default fill when no callback is supplied; per-band fills resolve via the callback. This is needed because the CFD widget needs a *different* fill token for each band in the stack (six bands, one theme-token per stratum), and the primitive must not be hard-coded to CFD.
- **D-impl-10**: Each band in `AreaSeries` carries an `upper` point-series (the cumulative-sum edge) plus the shared `baselineY`. The path is closed by walking back down to `(last.x, baselineY)`, then `(first.x, baselineY)`, then `Z`. Bands with empty `upper` arrays are omitted (a stage with zero count across the whole window is silent rather than a zero-height rect).
- **D-impl-11**: `AreaSeries` motion always sets an inline `style.transition` string (`'opacity 0.5s ease-out'` normally, `'transition: none'` when reduced-motion is set or `animated=false`). This matches `BarSeries`/`SegmentedBarSeries`/`StageDurationChart`'s convention — inline `'none'` is what the chart-baseline test asserts on, not the absence of a style attribute.
- **D-impl-12**: Band fills are keyed by stratum (bottom→top), per design D8. The six stages occupy five tokens: bottom=backlog=`fill-chart-1`, plan=`fill-chart-2`, build=`fill-chart-3`, check=`fill-chart-4`, integrate=`fill-chart-5`, top=done=reused=`fill-chart-3`. The done band keeps the `fill-chart-3` token — the spec scenario "bands distinguishable without color alone" is satisfied by stacking order + legend shape+label, not by six distinct hues.
- **D-impl-13**: The widget's "has data" guard is **any populated snapshot day** (`snapshots.some(s => STAGE_ORDER.some(stage => stageCount(s, stage) > 0))`), not just `snapshots.length > 0`. A populated project whose every snapshot was zero (e.g. right after a re-init) routes to the empty state rather than rendering six zero-thickness bands.

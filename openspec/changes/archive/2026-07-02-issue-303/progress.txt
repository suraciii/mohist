## Codebase Patterns

- **base-ui Dialog provides the focus trap for free**: `Dialog` already traps focus, restores focus on close, and dismisses on Escape via floating-ui's `FloatingFocusManager` + `FocusGuard` sentinels (`data-base-ui-focus-guard`). Don't re-implement these in a custom modal — wrap `Dialog` (see `packages/web/src/shared/ui/components/dialog.tsx`) and add affordances only.
- **base-ui Dialog root's `mode` is hardcoded to `'dialog'`** (not exposed via the public `Dialog.Root` API). The `role="alertdialog"` variant is wired via `useRenderDialogRoot`'s second argument and is not exposed in `@base-ui/react/dialog` v1.5.x. `AlertDialog` therefore uses the public `dialog` role and relies on the same modal trap.
- **base-ui sets `aria-modal` indirectly** via `markOthers` (`aria-hidden` on siblings). It is NOT rendered as an `aria-modal` attribute on the popup. Don't assert `aria-modal="true"` on the popup — assert base-ui markers (`data-base-ui-focus-guard` count > 0) or use `axe`.
- **`DialogOverlay` uses `fixed inset-0`** in its className — any test selector that matches `fixed.inset-0.z-50` will also match base-ui's overlay. Use the more specific hand-written signature `fixed inset-0 z-50 flex items-center justify-center bg-black/50` (or `bg-black/85`) to find hand-written modals.
- **`Dialog` in v1.5+ uses portals** that render at body level via `useFloatingPortalNode`. Tests must use `screen.findByTestId(...)` rather than querying a parent that wraps the `Dialog`.

## Gotchas

- **`useFloatingFocusManager`'s `onKeyDown` Tab handler depends on real key events** — `user.tab()` in jsdom can move focus outside the dialog even though base-ui sets up focus guards. Verify focus trap via: (1) `aria-modal` semantics via sibling `aria-hidden`, (2) focus guard DOM nodes (`data-base-ui-focus-guard`), (3) by explicitly focusing the last guard and asserting base-ui refocuses into the dialog. Browser behavior is correct; the jsdom `user.tab()` workaround is non-portable.
- **base-ui Dialog root's `DialogClose` slot** has `disabled` state — the existing primitive pattern (e.g., `SessionRecoveryActions`) doesn't use `DialogClose`; it calls `onOpenChange(false)` on a normal `Button`. Our `AlertDialog` uses two regular `Button`s (cancel and confirm) for consistency and so that `data-testid` is directly attached.
- **Existing T-001-relevant tests asserted against the old hand-written reset modal** (e.g., `screen.findByText('Reset Coder Agent Settings')`, `screen.getByRole('button', { name: 'Reset' })`). These still pass because the `AlertDialog` renders the same title and the confirm button gets the same accessible name. Don't delete them when migrating — augment them with `data-testid` lookups (`agent-reset-alert`, `agent-reset-alert-confirm`, `comment-delete-alert`).
- **The `agent-runtime` reset dialog keeps the form name `showResetConfirm`** but the rendered DOM is now a base-ui `Dialog`. Confirmed refactor surface: just swap the `fixed inset-0 z-50 ...` block for `<AlertDialog>`. State shape does not change.

## Codebase Patterns (T-004)

- **`<Link onClick>` interception is the design's documented fallback when `useBlocker` is unavailable.** Settings routes through legacy `BrowserRouter` (verified at `app/App.tsx:168`), so `useBlocker` is a no-op. The dirty-guard's interception point is therefore the `<Link>` `onClick` handler in `SettingsSubNav.GroupNav`. The trade-off is that browser-back / address-bar navigation / programmatic `Navigate` aren't covered — accepted because the spec scopes the guard to sub-nav-initiated switches.
- **`SettingsDirtyContext` is settings-scoped, not global.** The provider wraps only the `SettingsPage` content (not `SidebarProvider` etc.). The hook's default value is `{ dirty: false, setDirty: () => undefined }`, so a section that forgets to call `setDirty` is simply unguarded — a graceful no-op that satisfies the D5 risk called out in `design.md`.
- **`setDirty` setter must be referentially stable** (via `useCallback([])`) or sections that depend on it in a `useEffect` dep array will re-run every render. Same pattern as `useProject` and `ThemeProvider` — `useCallback` with empty deps.
- **`AgentSettingsSection`'s `useEffect` writes `dirty` AND cleans up on unmount.** Without the cleanup, switching to another section leaves the provider in `dirty: true` forever, so subsequent sub-nav clicks from the next section still prompt. Cleanup resets `setSettingsDirty(false)` so the unmounted section's stale dirty doesn't leak. Each `dirty`-dep change also briefly runs cleanup → reset, then the new effect writes the new value; React batches both, so the provider ends up with the correct value.
- **`useNavigate()` + `event.preventDefault()` is the navigation intercept pattern.** The `<Link>`'s default navigation has to be prevented (`event.preventDefault()`), then we capture the target URL in `pendingTarget` state, then on confirm we call `navigate(target)`. The `onOpenChange(false)` clears `pendingTarget`; Escape / overlay click also clear it via the same handler. `AlertDialog`'s base-ui `Escape` dismissal goes through `onOpenChange(false)`, so the state stays in sync.
- **The `GroupNav` refactor adds a required `onItemClick` prop.** Don't forget to pass it from `SettingsSubNav` — the LSP error on the missing prop is the only signal.

## Gotchas (T-003)

- **Mocking query hooks with fresh object literals per render will OOM the a11y suite** — when you return `{ data: [...], isLoading: false }` inline from a `vi.mock(...)` factory, React re-runs effects on every render because the returned reference is new. ## Codebase Patterns (T-008)

- **SOT edit for `text-balance` / `text-pretty`.** Adding the utilities in `SettingsSection.tsx` (rather than per-section) means every section automatically picks them up — guaranteed by the existing `settings-consistency` contract test that asserts every section component routes through `SettingsSection` + `getSectionMeta`. One edit, one source of truth, zero drift risk.
- **`tabular-nums` belongs on numeric / mono rows only, not on the page title.** Putting it on the section `<h2>` would defeat `text-balance`'s typographic intent and shift character widths on the title. The System `InfoRow` value span, the Agent `<Input type="number">`, and the Agent unit `<span>` are the canonical numeric/mono rows. Both are reached via single SOT locations (`InfoRow` for System, `InputField` for Agent) so the edit lands in two places.
- **Contract test scope for "no new motion/gradient".** The settings source already has pre-existing motion (`Loader2Icon.animate-spin` in SystemSettingsSection, `animate-pulse` in SectionState skeletons and WorkflowProfilesSection). These predate T-008 and are not in scope. The right contract is: the lines T-008 touches must not also add motion/gradient tokens — assert by scanning lines that contain `text-balance`/`text-pretty`/`tabular-nums` and confirming none of them also contain `animate-*` / `motion-*` / `bg-gradient-*` / `gradient-to-*`.
- **JSX regex gotcha: `[^>]*` does NOT match across `=>` arrow functions.** The Agent `<Input>` has `onChange={(e) => { ... }}` which contains a literal `>`. Use `[\s\S]*?` (lazy across-newlines) instead. Same pattern would apply to any JSX prop that contains a literal `>` in its expression body.

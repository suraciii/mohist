# Realtime surfacing for project inbox items (issue-284) — Working Memory

## Codebase Patterns

- The Mohist server persists relational state through `MohistDbContext`
  (`packages/server/src/Mohist.Server/Infrastructure/Data/Db/MohistDbContext.cs`).
  All migrations live under `packages/server/src/Mohist.Server/Infrastructure/Data/Migrations/`,
  are hand-written (no `dotnet ef` tool in this workspace), and live next to a
  matching `*.Designer.cs` plus the always-latest `MohistDbContextModelSnapshot.cs`.
- `MohistDbFixture` (`Support/MohistDbFixture.cs`) calls
  `db.Database.Migrate()` directly, so any new migration must be wired into the
  assembly via the standard `partial class <Name> : Migration` convention —
  migrations that aren't compiled-in won't run on production startup.
- Tests use traits `[Trait(Traits.Speed.Name, …)] × [Trait(Traits.Sut.Name, …)]`.
  Speed categories: `Unit`, `Grain`, `Integration`, `Service`. SUT categories
  are listed in `Support/Traits.cs`. When introducing a new bounded context,
  add a new `Sut.<Name>` constant.
- Unit-test DB patterns use `IDbContextFactory<MohistDbContext>` over a
  per-test in-memory SQLite (`Data Source=:memory:`). Migration specs that
  need an explicit Up-to-step use `context.GetService<IMigrator>().MigrateAsync(targetName)`;
  specs that want a clean DB use `Database.MigrateAsync()` and then read
  `__EFMigrationsHistory`.
- For new tables, mirror `EpicRow`/`EpicIssueRow` column conventions:
  TEXT PK/IDs with `HasMaxLength(64)`, ProjectId `TEXT` `HasMaxLength(256)`,
  timestamps as `DateTimeOffset`/`TEXT`. Index names follow
  `IX_<Table>_<Col1>_<Col2>` or `UX_<Table>_<Key>` / `UQ_<Table>_<Col>`
  conventions. Use `HasDatabaseName(...)` for explicit index names so the SQL
  is stable.
- `AddCloudEventHandlersFromAssembly` registers every `ICloudEventHandler`
  as a **singleton**. Handlers that need scoped services resolve them per
  call via an injected `IServiceScopeFactory` (see `InboxProjectionHandler`).
- `IEventPublisher` is the in-process bus publisher. The recommended
  `PublishAsync<TData>(data, type, source, subject?, extensions?, ct)`
  overload handles JSON serialization and `IEventStore` append in one call.
  Re-entrant publish from a bus handler is tolerated by `InMemoryEventBus`
  (the publishing handler returns before the new event begins to fan out).
- Hint payloads are CloudEvent `data` values and must be plain POCOs/records
  with stable property names; identity-only fields (project + item id) are
  the convention. `extensions["projectid"]` is the established project-routing
  stamp (used by `IssueGrain.cs` and read by the inbox projection).
- `EventCatalog.ReverseDns` is the single source of truth for `com.mohist.*`
  event type strings. Every new reverse-DNS type MUST be added to both
  `ReverseDns` and `All`; producers/consumers reference the constant, not
  a string literal.
- For the inbox tests, the shared harness is
  `Support/InboxProjectionTestSupport.cs` (added in T-001): it provides
  in-memory SQLite `TestDatabase`, a `CreateHandler(...)` factory that
  takes a pluggable `IEventPublisher`, `SeedIssueAsync` / `SeedWorkflowRunAsync`,
  `BuildIssueEvent` / `BuildWorkflowEvent` CloudEvent builders, and a
  `DispatchDynamic` adapter. Reuse it for any future inbox-handler spec.

## T-001 Findings

- `EventCatalog.ReverseDns` already had `InboxItemPersisted` constant
  (`"com.mohist.inbox.item-persisted"`) registered in the `All` list and
  the `ReverseDns` nested class. The catalog was pre-wired by the prior
  issue #286's T-003 step which also added `IssueWorkStarted` /
  `IssueWorkCompleted`; we only needed to verify the entry existed and
  consumed it from the projection. Re-confirmed: the existing precedent
  is "add the constant + add to `All` in the same diff, reference the
  constant from any publish / subscription site."
- `InboxStore.InsertAsync` returns `InboxInsertResult { Id, AlreadyExisted }`
  — `AlreadyExisted = true` on UNIQUE constraint conflict (the
  `InboxItemRows.SourceEventSource + SourceEventId` dedup index from
  issue-286/T-001). The dedup path is one call, no pre-flight SELECT,
  no second write. The projection's `result.AlreadyExisted` check is
  the single source of truth for "did this insert create a new inbox
  item" — exactly what the hint emission needs.
- `InboxProjectionHandler` is registered as a singleton by
  `AddCloudEventHandlersFromAssembly` (per the existing issue-286/T-003
  finding). It already injects `IServiceScopeFactory` and opens a
  per-handle scope to resolve `InboxStore` (scoped) and
  `IStateStore<DomainIssue>` (scoped). The hint publish reuses this
  same scope: `scope.ServiceProvider.GetRequiredService<IEventPublisher>()`
  inside `ProjectAsync` after the insert returns. This avoids two things
  at once: (a) duplicating the `IServiceProvider` work, and (b) a DI
  cycle that would otherwise form if the handler's constructor took
  `IEventPublisher` directly (because `InMemoryEventBus` enumerates all
  `ICloudEventHandler` subscriptions during its own construction, and
  `InboxProjectionHandler` is one of those handlers).
- The new file `Inbox/InboxItemPersistedHint.cs` is a 5-field record
  (`ItemId`, `ProjectId`, `Kind`, `IssueId`, `IssueNumber`) and lives in
  the `Mohist.Server.Inbox` namespace alongside `InboxStore` /
  `InboxQuerier` / `InboxModels`. Property names match the spec payload
  exactly so the Web can deserialize the hint without any custom mapper
  (the Web task T-003 uses `JsonElement` to read the same five fields).
- `IEventPublisher.PublishAsync<TData>` handles `IEventStore.AppendAsync`
  and the bus fan-out in one call. The overload signature takes
  `IReadOnlyDictionary<string, string>?` extensions; the handler stamps
  `extensions["projectid"] = draft.ProjectId` as a `Dictionary<string,
  string>(StringComparer.Ordinal)`. The constant source string is
  `HintSource = "/mohist/inbox"`.
- `EventBridge` subscribes to `com.mohist.*` (per the codebase audit
  in the design), so the new `InboxItemPersisted` type is automatically
  fanned out to subscribed SignalR connections through `OnEvent` — no
  new subscription attribute, no new SignalR method, no new groups.
  This is D2 of the design.
- The publish is awaited inside `ProjectAsync`; exceptions propagate to
  `HandleAsync`'s existing `try/catch` which logs and swallows them.
  This satisfies "a publish failure cannot corrupt the source-event
  projection" (spec scenario "No hint before persistence succeeds" +
  acceptance "A hint-publish exception is swallowed/logged and does not
  break the source-event projection").

## T-001 Decisions

- **Where the publish lives**: at the tail of `ProjectAsync`, after the
  `InsertAsync` result is captured. The check is `if (result.AlreadyExisted)
  return;` — early return, no hint. This is the same shape as the
  pre-existing `WorkflowStageLockReleaseHandler` pattern (handle-async
  short-circuits on filter results) and keeps the projection hot path
  single-method.
- **Hint payload = `InboxItemPersistedHint` record**: typed POCO, not a
  `JsonElement` / dictionary. `IEventPublisher.PublishAsync<TData>`
  serializes via `CloudEvent.JsonOptions`, which is the same source-gen
  contract used by every other typed publish in the system. Avoids the
  alternative of inlining `JsonSerializer.SerializeToElement` at the
  call site (a different serialization contract path).
- **Test factory pattern**: extracted a shared
  `Support/InboxProjectionTestSupport.cs` so the existing
  `InboxProjectionHandlerSpecs` (24 specs) and the new
  `InboxProjectionHandlerRealtimeHintSpecs` (8 specs) share the same
  `TestDatabase` / scope / event-builder helpers. The factory's
  `CreateHandler` overloads accept a pluggable `IEventPublisher` and
  an optional `configureServices` callback, which is what the
  `FailedInsert_PublishesNoHint` test uses to swap in a throwing
  `IDbContextFactory<MohistDbContext>`.
- **Test scope**: 8 specs in
  `InboxProjectionHandlerRealtimeHintSpecs`, one per acceptance
  criterion plus two "covers all kinds" + "projectid stamp matches
  owning project" extras. The existing 24 specs in
  `InboxProjectionHandlerSpecs` are unchanged in behavior — they
  just route through the new shared support. Full server suite:
  3070 green, 13 pre-existing skips, 0 regressions from the prior
  3054 baseline.
- **Test publisher capture pattern**: `CapturingEventPublisher` records
  every `PublishAsync` envelope (type, source, subject, extensions,
  data) into a `List<RecordedPublish>`. The hint tests assert on the
  recorded list — no SignalR / no live bus needed. The throwing
  publisher is a single-method `IEventPublisher` that throws
  `InvalidOperationException` on every call, used to verify the
  swallow-and-log contract.
- **Test database-failure pattern**: a `ThrowingDbContextFactory` that
  throws on `CreateDbContextAsync` — wired into the test scope via the
  `configureServices` callback. This is the cleanest way to make
  `InboxStore.InsertAsync` fail without rewriting it (the store's
  `DbUpdateException` path is already covered by the dedup test).
- **No `InboxItemPersistedHint` JSON contract test**: the test
  `Hint_PayloadContainsOnlyIdentity` reads the recorded envelope's
  `Data` (a `JsonElement` after `IEventPublisher.PublishAsync` returns)
  and asserts the exact property name set. This implicitly covers the
  `CloudEvent.JsonOptions` serialization shape too, because the test
  sees what the dispatcher will see on the bus.

## T-001 Gotchas

- **Singleton handler resolving `IEventPublisher` from a scope**: the
  publish reuses the same `await using var scope = _scopeFactory
  .CreateAsyncScope();` block that resolves `InboxStore` and the issue
  state store. There's no separate scope for the publisher. This is
  correct because `IEventPublisher` resolves to the `InMemoryEventBus`
  singleton regardless of which scope you ask from — the scope is a
  no-op for the singleton case but keeps the code path uniform.
  Documented inline in the handler to prevent a "let me just inject
  IEventPublisher in the constructor" refactor that would re-introduce
  the DI cycle.
- **`JsonElement` test reads from `envelope.Data`**: the
  `CapturingEventPublisher` stores `envelope.Data` (which is a
  `JsonElement?` after `PublishAsync<TData>` serializes the typed POCO).
  The test asserts on that `JsonElement` exactly as the dispatcher will
  deserialize it on the bus. Reading `data.GetProperty("kind")` etc.
  mirrors what the Web's `LiveTaskProvider` will do in T-003.
- **`NotNull` extension assertion**: `Extensions!["projectid"]` — the
  test asserts `Assert.NotNull(hint.Extensions)` first, then reads the
  keyed entry. The publisher's `IReadOnlyDictionary<string, string>?`
  parameter means `Extensions` can legitimately be null on envelopes
  that don't stamp any, so the null check matters. The handler always
  stamps at least `projectid`, so in production the field is never
  null.
- **Test name conventions match the spec scenario titles**: e.g.
  `NonDuplicateInsert_PublishesExactlyOneHint` ↔
  "Hint emitted after a new non-duplicate inbox item is persisted";
  `FailedInsert_PublishesNoHint` ↔ "No hint before persistence
  succeeds"; `DeduplicatedInsert_PublishesNoHint` ↔ "No hint on a
  deduplicated insert". The spec file under
  `openspec/changes/issue-284/specs/project-inbox-realtime/spec.md` is
  the authoritative acceptance source — the test names follow the
  spec scenario order so a check / repair agent can cross-reference
  one to the other without translation.
- **`Hint_ProjectIdExtensionMatchesOwningProjectNotSourceRoute` test**:
  workflow events are stamped with a source URL of the form
  `/mohist/workflow-runs/{workflowRunId}` — the `projectid`
  extension must reflect the project that **owns the inbox item**
  (resolved from the workflow run's annotations), not the workflow
  run id or the source URL. The seed for this test uses
  `proj_b` as the owning project and a different `source` URL, then
  asserts the hint's `extensions["projectid"]` is `"proj_b"`. This
  guards against a future "stamp from evt.Source" mistake.
- **`HandleAsync`'s catch swallows the publish exception** but the
  test `Hint_PublishException_SwallowedAndDoesNotBreakProjection` does
  not assert on log output — it asserts the inbox row was created
  despite the publish throwing. This is the spec scenario "A
  hint-publish exception is swallowed/logged and does not break the
  source-event projection" and matches the broader design contract
  that the projection's source-event side is durable / recoverable
  while the hint is best-effort.
- **`TryResolve` in `InboxProjectionHandler`**: the four-kinds switch
  is the canonical mapping. The kind value emitted in the hint's
  `kind` field is the exact same string the `InboxItemRow
  .NotificationKind` is set to, so the Web can join hint ↔ inbox
  item by `kind` if it ever needs to (today the Web only reads
  `itemId` and re-queries the API).

## T-002 Findings

- **Two small additive changes** — exactly per the task description:
  the `ConnectionSubscriptionRegistry` gained a per-connection
  `projectId` field (default `null`), and `MohistHub.OnConnectedAsync`
  reads `?projectId=` from the SignalR query string. The dispatcher
  grew a generalized, backward-compatible project filter. The grain
  (`IConnectionSubscriptionGrain`) was deliberately NOT touched — the
  mirror in the registry is the hot path the dispatcher reads, and the
  grain's purpose is replay-on-reconnect of the *subscription set*, not
  of affinity (affinity is per-tab, not per-user; a reconnect that
  rotates the connection id always re-sends `?projectId=`).
- **Reading the SignalR query string** is a one-liner:
  `var query = Context.GetHttpContext()?.Request.Query;` followed by
  `query?["projectId"].ToString()`. The null-conditional safely
  handles transports that don't expose an HTTP context (defensive —
  no current transport lacks one, but the cost of the null check is
  zero and the cost of `NullReferenceException` would be a hub crash).
  `Microsoft.AspNetCore.SignalR.HubCallerContext.Context` is settable
  in tests via `Hub.Context = ...`, which the new test fakes exercise
  with a `TestHubCallerContext : HubCallerContext`.
- **`DefaultHttpContext`'s `Query` collection** parses URL-encoded
  values (verified by the
  `OnConnectedAsync_QueryStringUrlEncodedProjectId_DecodesCorrectly`
  test that uses `?projectId=proj%2Falpha` and asserts the registry
  sees `"proj/alpha"`). The discovery was incidental — the Web
  currently only sends opaque ids, but this guard costs nothing and
  prevents a future bugs where someone sends a project id with a
  slash and the server interprets the wrong value.
- **`SetProjectId` normalises whitespace / empty to `null`** rather
  than treating them as "the empty project" — this matches the
  dispatcher's design (no project stamped = type-only matching) and
  avoids a class of bug where a fat-fingered URL with `?projectId= `
  silently scopes a connection to no project but still gates events.
  Verified by three dedicated unit tests
  (`SetProjectId_EmptyString_NormalisesToNull`,
  `SetProjectId_Whitespace_NormalisesToNull`,
  `SetProjectId_NullExplicitly_StoresNull`).
- **`TryGetProjectId` returns `false` for unregistered connections**
  rather than throwing — important because the dispatcher iterates
  `_registry.ConnectionIds` (which is the type-set snapshot, not the
  project-set snapshot) and there's a defensive window where the two
  could drift (e.g. if a connection is unregistered between the
  snapshot and a `TryGetProjectId` call on a different thread).
  Mapped by `TryGetProjectId_UnregisteredConnection_ReturnsFalse`.
- **The dispatcher's gate** is intentionally `event AND connection`,
  not `event OR connection`. When either side is missing the project
  affinity, we **fall back to type-only matching**, never block. This
  is the documented D3 blast-radius rule and is asserted by multiple
  specs: `EventWithoutProjectExtension_ReachesAllProjectAffinitizedConnections`
  (no project on the event → still reaches all), and
  `EventWithProjectExtension_ConnectionWithoutProjectAffinity_KeepsTypeOnlyMatching`
  (no project on the connection → still receives). The legacy-event
  integration spec (`LegacyEvent_NoProjectStamp_ReachesAllAffinitizedSessions`)
  covers the same contract end-to-end through `EventBridge` and
  `InMemoryEventBus`.
- **String comparison is `StringComparer.Ordinal`** — never
  `OrdinalIgnoreCase`. Project ids are user-controlled strings; a
  case-insensitive match would let "Proj-A" == "proj-A" route a
  connection to a project it didn't explicitly subscribe to. The
  matching string in the existing `IssueGrain.cs:605` code that stamps
  `extensions["projectid"]` is also ordinal-equality compared, so this
  is consistent.
- **Connection-list iteration is O(N)** where N is open tabs — same
  as before T-002. The new gate adds one `TryGetProjectId` (a single
  dictionary lookup) and one `Ordinal.Equals` comparison per connection
  when the event has a projectid. When the event has no projectid,
  the gate is inert — the addition is one `eventProjectId is not null`
  branch and zero per-connection work. Cost analysis matches the
  baseline: negligible.
- **`internal const string ProjectIdExtension = "projectid"`** is the
  shared extension key constant. Mirrors the existing convention where
  `IssueGrain.cs:605` stamps `"projectid"` as a string literal; making
  the dispatcher use a named constant is the only correctness-critical
  consolidation. If a future refactor renames the stamp on either
  side, the test suite will catch it because every dispatcher test
  uses the same `"projectid"` literal.

## T-002 Gotchas

- **`CloudEvent.Extensions` is nullable** — `publishingCloudEvent
  .Extensions?["projectid"]` will NRE if not handled. The current
  implementation guards with
  `if (cloudEvent.Extensions is { Count: > 0 } && ...)`. The
  `Extensions.Count > 0` check short-circuits the extension lookup on
  the common no-extensions path. `CloudEvent` constructors that omit
  extensions return a `null` Extensions collection, so the
  `Count: > 0` guards on both null and empty paths.
- **`extensions["projectid"]` value type is `CloudEventAttributeValue`
  or `string`** depending on which `CloudEvent` constructor
  overload was used to attach it. The dispatcher's gate uses the
  pattern-and-match form `if (... is string stamped && !string
  .IsNullOrWhiteSpace(stamped))` to handle both — the integration
  test publishes via `IEventPublisher.PublishAsync` (which uses the
  `Dictionary<string, string>` overload), so `is string` matches;
  external producers using attribute-style extensions would cast to
  `CloudEventAttributeValue` first. This is a future-proofing detail
  rather than a current need.
- **Whitespace-only project extension** (`extensions["projectid"] =
  "   "`) is treated as no project — see
  `ProjectAConnection_EventWithBlankProjectExtension_KeepsTypeOnlyMatching`.
  Otherwise a fat-fingered stamp (`projectid: "  proj-A  "`) would
  fail to match a connection whose affinity is `"proj-A"` because of
  the ordinal comparison. Symmetric to the registry's whitespace
  normalisation: both sides normalise.
- **`HubCallerContext` is `internal` in some SignalR versions** —
  `Microsoft.AspNetCore.SignalR.HubCallerContext` exposes settable
  `Context` only via reflection or by deriving a test subclass.
  `MohistHubProjectAffinitySpecs.TestHubCallerContext` derives from
  it and overrides only `ConnectionId` + `Features` so the existing
  hub's `Context.GetHttpContext()?.Request.Query` works without
  re-implementing the full SignalR surface. This is the same pattern
  used by `MohistHubSpecs.TestHubCallerContext` from prior work.
- **`IGrainFactory.GetGrain<T>(string)`** is overloaded — the test
  stub for `MohistHubProjectAffinitySpecs` only implements the
  `string` overload because `MohistHub.OnConnectedAsync` calls the
  string-keyed one for `IConnectionSubscriptionGrain`. Any future
  hub call that uses a `Guid` / `long` keyed grain would need to
  extend the stub — not a T-002 concern but a maintenance footgun.
- **`QueryString` from `Microsoft.AspNetCore.Http`** is the typed
  `IQueryCollection` accessor — `Request.Query["projectId"]`
  returns a `StringValues`, whose `.ToString()` returns the joined
  string (or empty for empty/blank). Test uses
  `httpContext.Request.QueryString = new QueryString(query);` which
  parses the literal query string the same way SignalR's transport
  does.
- **`SetSubscriptions` is called unconditionally** after the project
  affinity capture, including when the grain replay fails — the
  existing catch resets the in-memory set to `Array.Empty<string>`
  so the dispatcher never sees a stale set. The new project-id
  capture sits BEFORE this replay so a failure here doesn't
  silently drop the affinity; the test
  `OnConnectedAsync_NoHttpContext_LeavesRegistryUnchanged` confirms
  affinity capture is independent of the grain replay path.
- **Test base class choice**: the four T-002 spec files do NOT
  derive from a shared base; each wires its own `ConnectionSubscriptionRegistry`
  / `UserNotificationDispatcher` / etc. via constructor. Mirrors the
  existing `MohistHubSpecs` / `EventBridgeSpecs` style — minimal
  shared fakes, repeated 5-line setup.

- **`getCurrentIssueNumber` regex fix**: the pre-existing regex `\/issue\/(\d+)` never matched the actual route pattern `/:projectName/issues/:number` because the path segment is `issues` (plural), not `issue` (singular). Changed to `\/issues\/(\d+)` so `viewedIssueRef.current` correctly reflects the currently viewed issue number. This is a pre-existing bug that affected ALL callers (notifyRunLifecycleToast, notifyApprovalRequestedToast, and now the inbox notice suppression).
- **Notice gated on `applyInboxHint.result.applied`**: the high-attention notice must only fire when the hint matches the current project. The initial implementation ran the notice logic unconditionally after `applyInboxHint`, which showed a notice for cross-project hints too. Fixed by requiring `result.applied` in the guard.
- **Notice uses `sonner.toast`** (already imported in LiveTaskProvider), consistent with the existing `notifyRunLifecycleToast` and `notifyApprovalRequestedToast` patterns. The acceptance criteria's "in-app only" requirement is satisfied by sonner's purely DOM-based toast widget.
- **`isHighAttentionKind` and `shouldSuppressInAppNotice`** live in `inbox-effects.ts` alongside `applyInboxHint` and `parseInboxItemPersistedHint`. Both are pure functions tested in `inbox-effects.test.ts` via 12 unit specs (5 for `isHighAttentionKind`, 7 for `shouldSuppressInAppNotice`). Integration tests in `LiveTaskProvider.test.ts` cover 11 specs (2 kind-specific fire, 2 low-attention no-fire, 1 cross-project no-fire, 1 inbox-page suppression, 1 same-issue suppression, 1 unrelated-issue fire, 1 in-app-only verification).
- **Suppression check ordering**: `result.applied` checked first (project match), then `isHighAttentionKind` (kind filter), then `shouldSuppressInAppNotice` (route check). This ordering short-circuits early for non-matching projects and non-high-attention kinds, avoiding unnecessary route parsing.
- **`shouldSuppressInAppNotice` checks pathname and viewedIssueNumber**: pathname-based suppression checks `pathname.endsWith('/inbox')` (catches `/:projectName/inbox`). Issue-number suppression checks `viewedIssueRef.current` (the result of `getCurrentIssueNumber()`, which now correctly parses the route param). Both conditions are independent OR checks.
- `issue_started` and `issue_completed` kinds are excluded by `isHighAttentionKind` — they never reach the suppression check or the toast call.

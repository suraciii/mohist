## Codebase Patterns

- **FSD cross-entity imports** — entities consume each other through `@x/` barrels (e.g. `import { IssueStatus, IssueHealth } from '../../issue/@x/types'`). `entities/issue/@x/types.ts` is the only place to add a new cross-shared type/enum from the issue slice; do not reach into `entities/issue/model/*` directly from another entity.
- **Epic mutation convention** — every epic mutation in `entities/epic/api/queries.ts` mirrors the same shape: `useQueryClient` + `useProject`, `mutationFn` passing `projectId ?? undefined`, `onSuccess` invalidating the relevant query key prefix(es) and calling `toast.success('<verb> <object>')`, `onError` calling `toast.error(err.message || 'Request failed')`. New epic hooks follow this skeleton verbatim so the cache-invalidation contract stays consistent across consumers.
- **Cache invalidation keys** — epic reads use `['epics', projectId]` for list and `['epics', projectId, id]` for detail; issue reads use `['issues', number, projectId]` and several sub-prefixes (`['issues', …]`). Cross-entity invalidations use the **prefix** (`['epics']`, `['issues']`) so every nested variant is refetched; do not enumerate per-detail keys unless the mutation is scoped to one id and you need to skip other detail fetches.
- **Pure predicates live under `model/`** — derive functions like `isIntegrateFailure`, `deriveAttentionItems`, `deriveCompletionSnapshot` live in `entities/<slice>/model/` as standalone files, get unit-tested with a truth table covering each branch of the input shape, and are re-exported from `entities/<slice>/index.ts` so pages/features consume them as a stable public surface.
- **Sonner toast in tests** — `vi.mock('sonner', () => ({ toast: { success: vi.fn(), error: vi.fn(), … } }))` plus a `vi.hoisted` object capturing the mocks; spy and assert call args.
- **Hook-shape tests** — for a hook built on `useMutation`/`useQuery`, mock the React Query primitive with `vi.hoisted` + `vi.mock('@tanstack/react-query', …)`, call the hook from a no-render context, then read the captured options (`useMutationMock.mock.calls.at(-1)[0]`) and invoke its `mutationFn` / `onSuccess` / `onError` directly. Avoid pulling in `@testing-library/react` for hook-shape assertions.
- **LinkedIssueDto wire format** — server `LinkedIssueDto` (packages/server `Epic/Services/EpicDtos.cs:45`) emits `CanStart`/`StartBlocker` (populated in `EpicQuerier.GetLinkedIssuesAsync`). TS type mirrors via `IssueStartBlocker` from `entities/issue/model/issue.ts:68` (polymorphic `{ kind: 'draft' } | { kind: 'waiting-for'; issue: … }`); the issue detail page already consumes it successfully, so the wire shape is known-good.
- **Test fixture per-suite mutation mocks** — every `describe()` block in `EpicDetailPage.test.tsx` redeclares its own `addMutate` / `removeMutate` / `startMutate` / etc. `vi.fn()` locals, then assigns them inside its own `beforeEach` to the same shared `mocks.useAddEpicIssue.mockReturnValue(...)` etc. Adding a new mutation hook (e.g. `useStartIssue`) means **adding `useStartIssue` to the `vi.hoisted` mock object once, then adding a `startMutate = vi.fn()` local + matching `mockReturnValue` call to every single `beforeEach` in the file** — there is no shared `beforeAll` because each suite has different defaults. Easiest to do via `replaceAll` if the assignment block is identical across suites.
- **`LinkedIssueRow` test fixture shape** — fixtures for `LinkedIssue` in `EpicDetailPage.test.tsx` are loose object literals that **omit** `canStart`, `blocker`, and `health` for many rows (the existing tests don't trip on this because `canInlineStartRow` returns `false` on missing `canStart`, and `issueStatusTone` is called with `undefined` which falls through to the gray tone). When a test specifically wants to exercise the Start button or color/health, the fixture row must explicitly include `canStart: true/false`, `blocker: null | {…}`, and `health: 'active' | 'blocked' | …` — copy a complete row from the new `LinkedIssueRow inline Start` describe block as the template.
- **Page-uses-real-mutation test pattern for error toasts** — when a test wants to verify that a mutation hook's `onError` toast fires on a rejected API call, the test must let the **real** hook run end-to-end. The shared `vi.hoisted` mock factory for the entity barrel replaces the hook entirely; to fall through to the real implementation in a single describe block, capture the real module via top-level `await vi.importActual<typeof import('../../../entities/<slice>')>('../../../entities/<slice>')`, then have the new describe's `beforeEach` call `mocks.use<Mutation>.mockImplementation((...args) => realModule.use<Mutation>(...args))`. Visibility/pending tests in the same describe that want a local stub override with `mocks.use<Mutation>.mockReturnValue({ mutate: localMutate, isPending: false, isError: false })` inside their `it` body. Vitest's TS config (`target: ES2022`, `module: ESNext`) supports top-level await for this idiom.
- **`useProject()` default value when no `ProjectProvider` wraps the render tree** — `useContext(ProjectContext)` returns the default `defaultProjectContext` whose `projectId` is `null` (not `undefined`). A test that asserts the API call signature must use `expect(apiMock).toHaveBeenCalledWith(<n>, null)` when the page does not wrap with `ProjectProvider`, not `expect.anything()`. Tests that DO wrap with `ProjectProvider(initialProjectId=...)` will get the string. This is a common gotcha for tests of pages without an explicit `ProjectProvider` in the render tree.
- **Moved-file internal-import checklist** — `tsc -b` does NOT respect vitest's `test.exclude` patterns. When relocating a file into an excluded directory (e.g. `tests/a11y/**` for jsdom-OOM files), the file's internal imports (`import ...`, `vi.mock(...)`, `importOriginal<typeof import(...)>`) must still be updated to match the new location. A `grep "'\.\./src/" <moved-file>` is the simplest pre-commit sanity check; failure to update yields `TS2307: Cannot find module ...` errors at typecheck time even though vitest skips the file.

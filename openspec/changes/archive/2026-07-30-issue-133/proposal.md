## Why

Web is supposed to be Mohist Agent's configuration-and-verification plane, but its discovery entry point — the Agents list — only shows name, runtime/model, and active/archived lifecycle. A first-time user cannot tell from the list what an Agent is *for*, whether it is *ready to run*, whether it has *available capacity*, or how much work it currently carries; they must open the detail and even a Session to judge usability. The list's so-called "availability" is really just lifecycle status and conflates nothing with the domain's Availability signal. The detail page and launch composer already expose Readiness, Availability, and test launch — so the largest gap is that the discovery surface doesn't surface the domain facts the design already mandates, and the journey from "see it" to "verify it with a real task" isn't connected end-to-end with differentiated, actionable feedback.

## What Changes

- **Agents list becomes a real discovery/judgment surface.** Each row shows the Agent's purpose (description), its Readiness conclusion (Ready / Needs setup / Unknown), its Availability (can start now / waiting, with reason), and its active and queued workload — so a user judges usability without opening detail or a Session.
- **List-scoped Availability/workload serving.** Availability and waiting-work are currently only reachable via a per-Agent `status` call. Serve Availability and queue depth for the whole list so it can render capacity, waiting reason, and workload for every Agent without N round-trips and per-row polling storms. Readiness is already in the list response and only needs rendering.
- **Agent detail verifies configuration and explains gaps.** The detail page presents the execution definition summary (identity, instructions, runtime, model, variant, skills, concurrency, active/archived) with the edit entry driven by server-returned Readiness gaps; it explains what Needs setup or Unknown *specifically* lacks and the single next step, and keeps Availability (Runner offline, concurrency limit, queue) strictly separate from configuration Readiness.
- **Test launch from detail returns an entry to the work.** From the detail page the user submits a real task against the configured Agent (creating AgentJob, AgentSession, first SessionInput, first AgentTurn) and lands on a pointer to that work. Launch is gated by Readiness: Needs setup blocks, Unknown is allowed with an explicit "will wait for Runner validation" caveat. Runtime/Model/Skills overrides stay out of the composer.
- **Differentiated feedback across the journey.** Queue/back-pressure, Runner offline, configuration gaps, and execution failures each get distinct, actionable feedback on the list, detail, and launch surfaces, so the user determines the next step without reading raw logs.

## Capabilities

- `agent-list-discovery`: The Agents list as the discovery-and-judgment surface — each row renders identity & purpose (name, description), the server's Readiness conclusion, Availability (can start / waiting reason), and active/queued workload, letting a first-time user judge whether an Agent is usable without opening detail or a Session. Covers how list-scoped Availability/workload is served (single summary vs. fan-out) so Availability is shown for every Agent without N round-trips, and never reads as a configuration error.
- `agent-detail-definition`: The detail page as the configuration surface — execution-definition summary with edit entry, Readiness gap explanation (Needs setup / Unknown specifics + single next step), and Availability rendered strictly separately from Readiness (Runner offline / concurrency limit / queue are not configuration gaps).
- `agent-test-launch`: Submitting a real test task from the detail page (creating AgentJob/Session/Input/Turn) and landing on a pointer to the resulting work, with launch gated by Readiness (block Needs setup, allow Unknown with a wait-for-validation caveat) and no execution-definition overrides in the composer.
- `agent-launch-feedback`: Queue/back-pressure, Runner offline, configuration gaps, and execution failures produce distinct, actionable feedback across the list, detail, and launch surfaces, replacing raw-log reading with a next step.

## Impact

- **Web — discovery surface** (`packages/web/src/pages/agent-list/ui/AgentListPage.tsx`, its test): rewrite rows to render description, Readiness conclusion, Availability, and active/queued workload; replace the misleadingly-named local `getAvailabilityStatus` (currently only lifecycle) with the server's distinct Availability signal. FSD placement unchanged (page slice).
- **Web — entity/query layer** (`packages/web/src/entities/agent/api/queries.ts`, `client.ts`, `model/types.ts`): add the list-level Availability/workload query and DTOs mirroring the server summary; keep the existing per-Agent `status` query for the detail page.
- **Web — detail & launch** (`packages/web/src/pages/agent-detail/ui/AgentDetailPage.tsx`, `packages/web/src/pages/agent-session-composer/ui/AgentSessionComposerPage.tsx`): verify/refine the definition summary + edit entry, the Readiness gap explanation, and the test-launch-to-work-entry path; ensure differentiated feedback is consistent across detail and composer.
- **Server** (`packages/server/.../Api/AgentDefinitionRoutes.cs`, `Agent/Services/AgentQuerier.cs`, `AgentAvailabilityService.cs`): add a list-scoped Availability/waiting-work summary (the one-summary-vs-fan-out decision is deferred to design.md); Readiness is already hydrated on the list response and needs no server change.
- **Tests**: spec coverage per page for list discovery (Readiness/Availability/workload rendering, offline-reads-as-availability not config error), detail definition/gap explanation, test-launch entry, and differentiated feedback; unit coverage for the new list-availability query and DTO mapping. All per `design/testing.md` — no real network, process, Runner, or wall-clock; fakes via MSW/injected data hooks.

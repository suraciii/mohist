## T-002 — CLI: project-scoped workflow list + skill fallback wording

### Implementation
- Modified `MohistCliApi.PrintWorkflowProfilesDescribedAsync` — added optional `string? projectId` param; when set, appends `?project=<id>` to the API path.
- Modified `MohistCliCommands.Workflow.cs` — added `--project`/`--project-id` options via `MohistCliCommands.ProjectRefOption()`:
  - `--described` path: resolves project and calls filtered endpoint; when unresolvable, falls back to unfiltered with a stderr degraded note.
  - Plain path: only resolves project when `--project`/`--project-id` is explicitly provided; otherwise uses the unfiltered endpoint (preserving existing behavior for server tests).
- Updated `skill-data/mohist-create-issue/SKILL.md` — replaced unconditional `mohist/local` fallback with "first enabled profile, else fail with an actionable error"; removed "guaranteed to exist" and "unconditional fallback" language.
- Tests: added `CliWorkflowListSpecs.cs` (6 tests) covering project resolution with `--project`, `--project-id`, active project, degraded fallback, plain mode with project, and disabled-profile exclusion.

### Gotchas
- The server-side tests (`WorkflowCliListSpecs.cs`) use an empty `FakeFileSystem` (no cli-state.json). For the plain (non-described) path, we must avoid calling `ResolveProjectIdAsync` when neither `--project` nor `--project-id` is given, otherwise it writes "Run 'mo project use...'" to stderr, breaking the `Assert.Equal(string.Empty, stderr)` check.
- Design decision: plain `mo workflow list` without `--project` continues to use the unfiltered endpoint (no stderr noise). The degraded-path stderr note only fires for `--described` mode.

## T-004 — Web: per-profile enable/disable Switch + base-ui Select default control

### Implementation
- Created `packages/web/src/shared/ui/components/switch.tsx` — wraps `@base-ui/react/switch` Root + Thumb with aria-label support and styled via cn(). Follows the same pattern as other base-ui primitives in the project (button.tsx, select.tsx).
- Extended the server's `GET /api/projects/{projectRef}/workflow-profile` to also return `disabledWorkflowProfileIds` (array of strings) by calling `manager.GetDisabledWorkflowProfileIdsAsync()`.
- `client.ts`: `getWorkflowProfiles(projectId?)` now accepts optional projectId — when passed, appends `?project=<id>` to the URL (project-scoped filtering). Added `disableWorkflowProfile` and `enableWorkflowProfile` client functions (POST to toggle endpoints). Extended `ProjectDefaultWorkflowProfile` interface with `disabledWorkflowProfileIds` field. Updated `getProjectDefaultWorkflowProfile` to deserialize the new field.
- `queries.ts`: `useWorkflowProfiles()` now passes projectId from `useProject()` and uses query key `['workflow-templates', 'system', projectId]`. Added `useAllWorkflowProfiles()` for unfiltered card list (no projectId). Added `useDisableWorkflowProfile` and `useEnableWorkflowProfile` mutation hooks (invalidate both the filtered list and project profile cache). Updated `useEffectiveDefaultWorkflowProfile` to drop hardcoded `'mohist/local'` fallback — falls through to first enabled profile, then `source:'none'` when the filtered list is empty.
- `WorkflowProfilesSection.tsx`: Card list now uses `useAllWorkflowProfiles()` (unfiltered, all profiles including disabled). Disabled set comes from `useProjectDefaultWorkflowProfile().disabledWorkflowProfileIds`. Each `ProfileCard` renders a base-ui `Switch` with `aria-label`. The last-enabled profile cannot be toggled off — an amber blocked-message is shown inline. Switch state reflects current disabled set. Toggle mutations invalidate the filtered profile list for `useEffectiveDefaultWorkflowProfile`.
- `ProjectDefaultWorkflowControl.tsx`: Replaced native `<select>` with project's base-ui `Select` primitive using `<Select>`, `<SelectTrigger>`, `<SelectValue>`, `<SelectContent>`, `<SelectItem>`. Disabled profiles get `disabled` prop on `<SelectItem>` (greyed/not clickable). Added amber warning (`data-testid=project-default-workflow-disabled-warning`) when the configured project default points to a disabled profile. Uses `useAllWorkflowProfiles()` for the item list.
- `index.ts` — exported new hooks (`useAllWorkflowProfiles`, `useDisableWorkflowProfile`, `useEnableWorkflowProfile`).

### Test changes
- `queries.test.ts`: Updated "returns none source" test to expect first-enabled fallback; added new test for truly empty profiles list returning `source:'none'`.
- `ProjectDefaultWorkflowControl.test.tsx`: Replaced native `<select>` assertions with base-ui Select interactions using `userEvent.click` on trigger + `screen.findByRole('option')`. Extended MSW handlers to return `disabledWorkflowProfileIds`.
- `settings-visual-accessibility-evidence.test.tsx`: Added mocks for `useAllWorkflowProfiles`, `useDisableWorkflowProfile`, `useEnableWorkflowProfile`. Extended `useProjectDefaultWorkflowProfile` mock with `disabledWorkflowProfileIds`.
- `settings-search-registry.test.tsx`: Added mocks for `useAllWorkflowProfiles`, `useDisableWorkflowProfile`, `useEnableWorkflowProfile`. Extended `useProjectDefaultWorkflowProfile` mock with `disabledWorkflowProfileIds`.

### Gotchas
- `useWorkflowProfiles` now passes `?project=<id>` and returns only ENABLED profiles (filtered on server). For the card list (which needs ALL profiles including disabled), `useAllWorkflowProfiles()` was created as a separate unfiltered hook.
- `useEffectiveDefaultWorkflowProfile` previously hardcoded `'mohist/local'` as the terminal fallback; now returns `source:'none'` only when the filtered list is empty (no enabled profiles at all), otherwise falls through to the first enabled profile.
- `useDisableWorkflowProfile` / `useEnableWorkflowProfile` mutations invalidate both the filtered profile list (`['workflow-templates', 'system', projectId]`) and the project profile cache (`['project-workflow-profile', projectId]`) so the disabled set stays in sync.
- Base-ui Select renders `<button>` as trigger with a hidden `<input>` for form value. Native `<select>` interaction patterns (`.value`, `fireEvent.change`) do not work — must use `userEvent.click(trigger)` then `screen.findByRole('option')` + `userEvent.click(option)`.
- `fireEvent.click` on base-ui select trigger does not open the popup reliably; `@testing-library/user-event` is required for realistic interaction that fires pointer events.

# issue-130 working memory

## Codebase Patterns

### Computed label columns: column property and SQL live side-by-side
- `AgentSessionRow.cs:16-23` already had 8 `string? Label*` properties whose values
  are projected by `json_extract("State", '$.metadata.labels."…"')` STORED
  computed columns declared in `MohistDbContext.cs:129-143`.
- The `ReplaceAgentSessionLabelsWithComputedColumns` migration
  (`Infrastructure/Data/Migrations/20260620185946_…cs`) is the canonical
  pattern: add plain nullable TEXT, then `AlterColumn` to `STORED`. EF Core's
  SQLite provider triggers an automatic table rebuild for STORED computed
  columns (`AddColumn` with `computedColumnSql … stored: true` does the same
  rebuild, see the EF-generated T-001 migration `20260629112745_…cs`).
- The `FixAgentSessionLabelsComputedColumnCase` migration fixed the JSON path
  casing from `$.Metadata.Labels` to `$.metadata.labels` to match
  `JSON.Options` (`JsonSerializerDefaults.Web` → camelCase). **Always write
  test fixtures' State JSON with `JSON.Options`, not the default serializer**
  — otherwise `json_extract` returns `null` for everything and the column
  assertions look like the SQL is wrong.

### `QueryRowsByLabels` is a switch on the label-key constant string
- `AgentSessionQuery.cs:105` maps each `AgentSessionQueryMetadataKeys.*`
  constant to a `LabelXxx == value` predicate; unknown keys fall through
  to `_ => query.Where(_ => false)`. Adding a new label key means:
  1. Add the column on `AgentSessionRow`,
  2. Configure it in `MohistDbContext.OnModelCreating` (computed SQL +
    index),
  3. Reference the metadata-key constant (NOT a string literal) in the
    EF model so a typo is a compile error,
  4. Add a switch case in `QueryRowsByLabels` that uses the same
    `LabelXxx == value` predicate.

### `dotnet-ef` design-time tools are available
- `dotnet tool install --global dotnet-ef --version 10.0.8` works on this
  workstation; the local cache was missing it but it is the canonical way
  to scaffold a migration. After scaffolding, the `MigrationsAssembly` re-
  emits the `*.Designer.cs` snapshot and the model snapshot.
- `dotnet-ef` looks for `DOTNET_ROOT`; on this machine it lives at
  `/home/szf/.dotnet`, so we run with `export DOTNET_ROOT=/home/szf/.dotnet`
  before invoking `dotnet-ef`.

### In-memory SQLite migration helpers
- `Specs/Inbox/InboxItemsMigrationSpecs.cs` is the canonical pattern:
  `IDbContextFactory<MohistDbContext>` backed by an in-memory
  `SqliteConnection`, then drive the migration via `MigrateAsync(targetMigration)`
  (or `Database.MigrateAsync()` for the full chain). Verify schema with
  `pragma_table_xinfo` (includes STORED generated columns as `hidden=2/3`
  entries; `pragma_table_info` filters them out so `Assert.Contains(name,
  pragma_table_info_keys)` would have looked correct-but-misleading).
- The `dotnet ef migrations add …` invocation uses a project reference to
  `Mohist.Server.csproj`; the new migration lands under
  `Infrastructure/Data/Migrations` automatically.

### Migrator `MigrateAsync(targetMigrationName)` quirks
- When the database is empty, `MigrateAsync(targetName)` runs every
  migration up to and including that target (not just the target), so a
  full-chain smoke test works via either form.

### T-004: Activity/active-agents attribution for generic sessions

#### `ToActivityCard` branches on `source-kind=agent-launch`
- `AgentSessionQuerier.ToActivityCard` (line 840) now detects
  `source-kind=agent-launch` and produces `agent_{agentId}` as the `IssueId`
  instead of `issue_{projectId}_{issueNumber}`. AgentId/AgentName are
  populated from labels; workflow cards pass null for both new fields.
- `ActivityCardDto` gained two `string?` fields: `AgentId` and `AgentName`,
  inserted between `FailureReason` and `EventSummary`. Workflow cards leave
  them null; null fields are omitted from JSON by ASP.NET Core's default
  `JsonIgnoreCondition.WhenWritingNull`.

#### `ListActiveAgentsAsync` no longer skips blank workflowRunId/workId
- `WorkflowActivityQuerier.ListActiveAgentsAsync` now handles generic
  agent-launch sessions in a dedicated branch before the workflow branch.
  Generic entries get `agent_{agentId}` as IssueId, AgentId/AgentName from
  labels, and a null TaskProgress (design D6 degenerate). The workflow
  branch's blank-skip guard (workflowRunId/workId) remains for non-generic
  sessions only.
- `ActiveAgentDto` gained two `string?` fields: `AgentId` and `AgentName`.
- `ActiveAgentProgressDto.TaskProgress` changed from `TaskProgressDto` to
  `TaskProgressDto?` to support the degenerative progress for generic sessions.

#### Integration specs use seeded AgentSessionRow, not full launch pipeline
- `AgentSessionActivityVisibilitySpecs` seeds rows directly into the DB
  (same pattern as `AgentUsageTimeseriesApiSpecs`). Tests verify:
  - Generic card carries agent id/name
  - No synthetic `issue_..._0` card for no-issue-ref sessions
  - Issue-ref session has issue number but is agent-attributed
  - Active generic session appears in `/agent/status` activeAgents
  - Workflow card has no agentId/agentName in JSON
- The existing `AgentSessionLaunchRoutesSpecs.Launch_GenericSession_IsReadableByProductMetadataAndTranscriptRoutes`
  test was broken by T-003's DTO change from `AgentSessionMetadataDto` (has `Id`)
  to `GenericAgentSessionSummaryDto` (has `SessionId`). T-005 fixed the broken
  assertion to check `sessionId` instead of `id`, and added agent identity checks.

### T-007: CLI mo agent session list/show/transcript verbs

#### ResolveAgentAsync changed from GetDataAsync to GetDataOrPrintErrorAsync
- The existing `ResolveAgentAsync` used `GetDataAsync` for the `agent_*` direct-lookup path, which throws `ApiResponseException` (a private class) on 404/server error. Changed to `GetDataOrPrintErrorAsync` which catches the exception internally, prints the error to stderr, and returns the exit code. The caller pattern `if (agent is null) return 1` converts the 404 exit code to exit 1, matching existing callers' pattern.

#### Three new TableShape enum entries
- `AgentSessionList` — table-mode renders one row per session with `session id`, `status`, `created`, `model` columns; can be empty (no message shown).
- `AgentSessionShow` — table-mode renders the enriched summary: agent identity (id+name), status, created/last-activity, model, failure category, tool call/error counts, token/cost from usage envelope, and context refs.
- `AgentSessionTranscript` — same summary shape as `RenderSessionTranscriptSummary`: turns, parts, first/last activity, no individual message bodies.

#### Three new CLI subcommands in BuildSession
- `list <agent> [--status]` — resolves agentRef client-side via `ResolveAgentAsync` then GETs `/agents/{agentId}/sessions`. Default output is `table`. Aliased as `ls`.
- `show <sessionId>` — GETs `/agent-sessions/{sessionId}`. Default output is `table`.
- `transcript <sessionId>` — GETs `/agent-sessions/{sessionId}/transcript`. Default output is `table`.
- All three accept `--project/--project-id` and `-o table|json`. List also accepts `--status`.
- The help text updated to list all 6 subcommands.

## Codebase Patterns

- **Project layout**: `packages/server/src/Mohist.Server` is the .NET 11 server. C# `LangVersion=preview` and `TreatWarningsAsErrors=true` — clean builds are non-negotiable. `LangVersion=preview` does NOT yet allow non-constant defaults (e.g. `int[] = []`) on record primary-constructor parameters; use property-based records with `init` properties (defaulted via `= []`) and an additional explicit primary-style constructor when you need named-arg call sites.
- **C# record DTOs**: For DTOs that flow over the API, a property-based `sealed record` with `init` properties plus a parameterless ctor (for JSON deserialization) and a primary positional ctor (for in-process call sites) is the standard pattern. Existing call sites use `PascalCase` named arguments (e.g. `Id: x, Number: y`) — the positional ctor's parameters must be PascalCase to match.
- **Default values on positional record params**: only compile-time constants (literals, `null`, `null!`) compile. For empty collections, either accept `null` defaults (then null-coalesce in the constructor body) or convert the record to property-based.
- **Test mirrors for API DTOs**: `EpicLifecycleSpecs.cs` (and similar) declare a private nested `record LinkedIssueDto(...)` mirror to deserialize API responses. `System.Text.Json` ignores extra JSON properties by default, so the mirror can lag behind server DTO additions — but new properties with non-constant defaults (like `IReadOnlyList<...>`) still need an explicit `null!` placeholder in the mirror signature.
- **Read-model bulk loading**: `IssueQuerier.ListAsync(projectId, all: true)` returns `List<IssueReadModel>` already enriched with `PrerequisiteNumbers` (int[]) and `Prerequisites` (IssuePrerequisiteSummary[]). The enrichment in `EnrichAsync` (IssueQuerier.cs:595) also bulk-loads any missing prereq rows into the same dictionary, so the data for ghost-node summaries is already in memory after a single call — no per-issue fetch needed.
- **Prereq summary shape**: `IssuePrerequisiteRefDto` (IssueInfo.cs:136) carries `{Number, Title, Stage, Status}` and is reused as the ghost-node summary. `IssuePrerequisiteRefDto.FromSummary(IssuePrerequisiteSummary)` does the conversion. A missing/unresolvable row degrades to `new IssuePrerequisiteRefDto { Number = prereqNumber }` with empty title/stage/status.
- **Add a new epic-related test file**: Put pure-logic unit specs under `packages/server/tests/Mohist.Server.Tests/Specs/Epic/Domain/`. Use `InternalsVisibleTo("Mohist.Server.Tests")` (already configured) to access `internal` members from server. Use `IssueReadModel`'s `init` properties to construct fixtures in unit tests; for integration tests use the real `IIssueGrain.AddPrerequisiteAsync` API.
- **Web workspace tooling**: `packages/web` declares its own `vitest@^4.1.4` in its package.json and `npm install` creates a per-package `packages/web/node_modules/vitest` (4.1.7) so vite's `test` field is honored. The hoisted root also has a `vitest@1.6.1` (from runner's `^1.0.4`) which is too old to read the `test:` block in vite.config.ts — running vitest via `npx`/`npm exec` without `-w packages/web` lands on the wrong version and reports "Vitest failed to find the current suite". Always invoke the web test runner as `npm run test:run -w packages/web` (or `./node_modules/.bin/vitest` from inside `packages/web`).
- **Pre-existing test failures on master**: `src/shared/ui/markdown-reader/MarkdownReader.test.tsx` (4 failures: ResizeObserver teardown) and `tests/AgentSettingsSection.test.tsx` (1 failure) fail on the T-001 commit baseline (verified via `git stash`). They are NOT caused by T-002 and should not block T-002's pass/fail; just count the T-002 test files in the diff for the AC's "new widget model + component tests" line.
- **FSD widget placement for visual composites**: A read-only presentational composite (graph, kanban-board, etc.) belongs in `widgets/`. `widgets/kanban-board` is the precedent. FSD `features/` is reserved for user tasks paired with mutations; the graph is purely a read projection and uses `widgets/`. Internally split the slice into `model/` (pure types + derivations + dagre) and `ui/` (canvas + node components); expose a `React.lazy`-wrapped entry via `index.ts` so the consumer page pulls the graph bundle on demand.
- **Eager-mount + callback-driven fallback for lazy widgets**: When a `React.lazy` widget exports a `Renderability` signal via `onRenderabilityChange`, the page should mount the widget **eagerly** (as soon as the user opts in) and use the callback to decide what to show alongside. A naive `showGraph = selected && renderable` formula creates a chicken-and-egg: the widget never gets mounted, so the renderability callback never fires. The right shape is `graphSelected = opted-in && available` (mount-decision) and `showGraph = graphSelected && renderable` (visibility-decision), with the fallback list covering the `!showGraph` branch.

- **Learnings for future tasks**
  - **Decisions made**
    - `LinkedIssueDto` was converted to a property-based `sealed record` with `init` properties + a primary-style ctor. This was forced by the C# language: positional record params can't take non-constant defaults like `[]` for collections. The conversion is a one-time cost; future DTO additions that need non-constant defaults should follow this same pattern.
    - External prereq summaries are placed on the **per-issue** `LinkedIssueDto` (not as a top-level map on `EpicDetailDto`). This keeps each DTO self-contained for edge rendering and matches design.md Decision 2 / the open-question lean.
    - `BuildExternalPrerequisites` is `internal static` (not `private`) so it can be unit-tested directly via `InternalsVisibleTo`. All test paths use the real `IssueQuerier` dictionary (no per-issue fetch), so the helper is the right unit to test for ghost-node semantics.
    - For the unresolvable prereq scenario, we rely on a unit test rather than integration test because the public `AddPrerequisiteAsync` API rejects unknown numbers — the "no row" case can only arise from internal state corruption or hard deletion (which the codebase does not support). The unit test pins the behavior.
  - **Gotchas discovered**
    - The `[]` collection-expression default on a record's positional parameter fails to compile under `LangVersion=preview` on .NET 11 (error CS1736: "Default parameter value must be a compile-time constant"). Property initializers (`{ get; init; } = []`) are fine because they don't go through the same parameter-default path. Plan ahead: when extending a record DTO, prefer property-based records from the start.
    - `IReadOnlyList<T>` does not have `.Length` (only `.Count`); some existing tests and new tests need to use `.Count` when reading sizes.
    - The `LinkedIssueDto` test mirror in `EpicLifecycleSpecs.cs` uses positional records too, so adding a `int[] PrerequisiteNumbers` field needed `int[] PrerequisiteNumbers = null!` to compile. The `null!` is fine at runtime because System.Text.Json fills it from the JSON.
    - When extending the test mirror's positional record, **add the new field at the end with a default** (matching the server DTO). Don't reorder — positional records in C# use positional binding.
  - **Patterns / API shapes established**
    - "Additive DTO extension" pattern: convert the record to property-based with `init` props + primary-style ctor. New fields use `init` properties with collection-expression defaults. Existing named-arg call sites work unchanged. New fields are easy to extend in later tasks.
    - Ghost-node summary reuse: `IssuePrerequisiteRefDto.FromSummary(IssuePrerequisiteSummary.FromReadModel(issueReadModel))` is the standard way to project a loaded issue into a ghost-node shape. A `new IssuePrerequisiteRefDto { Number = n }` with empty title/stage/status is the unresolvable fallback. Web widget (T-002) should reuse this convention.
  - **Cross-task invariants**
    - `EpicProgress.Build` outputs MUST continue to be derived from `Status` / `Health` / `CanStart` / `StartBlocker` / `Priority` / `Number` / `Title` only. The new `PrerequisiteNumbers` and `ExternalPrerequisites` fields MUST NOT influence progress semantics. The unit test `Build_IgnoresPrerequisiteNumbersAndExternalPrerequisitesFields` enforces this; future refactors of `EpicProgress` must keep it green.
    - `LinkedIssueDto` is constructed in three places: `EpicQuerier.GetLinkedIssuesAsync` (real data), `EpicGrain.BuildLinkedIssueDtosAsync` (grain-internal, no prereq data), and tests. The grain and test paths get `[]` defaults; the EpicQuerier path populates real data. Any new caller MUST follow this convention or document why.
- `IssueQuerier.ListAsync(projectId, all: true)` is the single bulk-load entrypoint that already has prerequisite enrichment; do NOT add a per-issue fetch in the EpicQuerier path.
- The web `LinkedIssue` entity (T-002) MUST consume both `prerequisiteNumbers` and `externalPrerequisites` from the new server DTO. The page-level `EpicDetailDto` JSON shape is now `{ ..., linkedIssues: [{ ..., prerequisiteNumbers, externalPrerequisites }] }`.

While the lazy chunk is loading, the widget's internal Suspense shows the skeleton (no list flash); after the chunk loads, the canvas either reports `renderable: true` (graph replaces the list) or `renderable: false` (list remains, widget renders `null`).
    - **Toggle is hidden for 0-1 issues, not disabled**. The spec's "may hide/disable the graph option" allows either; hiding the whole `tablist` keeps the small-epic case visually identical to the pre-T-003 page and matches the spec's "SHALL NOT offer a broken or empty graph surface" wording.
    - **No auto-revert on cycle**. When the user picks Graph and the widget reports cyclic, the list is shown but the toggle stays on Graph. This matches the spec ("the page presents the list view instead of a broken layout") without surprise UX (a cycle is a rare defensive fallback; the user can re-flip to List manually if they want to clear the tab state).
    - **List region gets a `data-fallback-for` attribute** carrying the renderability reason when the graph view is the active tab — this lets the cycle test assert `data-renderability="cyclic"` on the graph region AND the list region without coupling to the widget's internals.
  - **Gotchas discovered**
    - **Chicken-and-egg with renderability**: the obvious `showGraph = graphSelected && graphRenderable.renderable` formula mounts the widget only when we *already know* it's renderable, which is impossible on the first render. The fix is to split into `graphSelected` (mount-decision) and `showGraph` (visibility-decision), and render the widget when `graphSelected` while the list covers the `!showGraph` branch.
    - **Lazy chunk loads inside `waitFor`**: the toggle tests rely on the widget's lazy chunk loading, which works transparently under vitest + Vite. The chunk load + Suspense resolve + canvas mount + `useEffect` callback is a four-step async sequence; `waitFor(() => expect(screen.getByTestId('linked-issues-graph-region')).toBeInTheDocument())` is sufficient because the region is rendered synchronously with `graphSelected === true` (it just contains a skeleton initially), so the test does not have to wait for the canvas to appear.
    - **`data-fallback-for` on the list region**: undefined when the graph view is not active, and equals `graphRenderable.reason` (`'empty' | 'cyclic'`) when the user picked Graph but the widget is not renderable. This is the cleanest way to assert "the list is being shown as a fallback" vs "the list is being shown because the user picked List" in a single test.
    - **Reused test fixture `epic` is structurally incomplete** (lacks `prerequisiteNumbers`, `canStart`, `startBlocker`, `externalPrerequisites`). The T-002 widget tolerates this for non-cyclic cases (the missing fields are `[]`/`false`/`null` defaults after a `Partial<LinkedIssue>` overlay), but for the new graph-toggle tests we added a `makeLinkedIssue` helper that supplies all the new fields explicitly. The pre-existing 32 tests still pass without modification — the new fields are purely additive, and the test-side mocks return the bare-minimum shape the row needs.
  - **Patterns / API shapes established**
    - **Toggle state pattern for read-only visualizations**: a small two-state `useState` (`'list' | 'graph'`) + a derived `showGraph` for visibility + a separate `Renderability` mirror for the widget's signal. This pattern generalizes to any "optional composite that can degrade to the default view" on a FSD page.
    - **Eager-mount + callback-driven fallback**: the page mounts the widget whenever the user opts in, and uses the widget's `onRenderabilityChange` callback to decide what to show alongside. This is the right shape when the mount-decision must be eager (to learn renderability) and the visibility-decision is lazy (after the callback fires). The pattern survives both the cycle fallback and the 0-1 issue case uniformly: the page-level gate (`graphAvailable`) and the widget-level gate (`Renderability`) compose as a logical AND via `showGraph = graphAvailable && viewIsGraph && renderable`.
    - **`role="tablist"` + `role="tab"` segmented control**: a 2-button toggle is best expressed as a `tablist` with two `tab` buttons (and `aria-selected`), not as radio inputs. Tailwind utility classes from the existing tabs component (`bg-muted/40 p-0.5` rail, `bg-background shadow-sm` for the selected tab) match the design language of the rest of the app.
  - **Cross-task invariants**
    - The graph widget remains **read-only** — the page does not call any mutation hook (`useAddEpicIssue`, `useRemoveEpicIssue`, `useUpdateEpic`, `useMarkEpicDone`, `useCloseEpic`) in response to toggle changes. The "does not mutate data" test enforces this; future tasks must not add side effects to toggle interactions.
    - The page's list region is **bit-for-bit the same JSX** as the pre-T-003 list, plus a `data-testid` and an optional `data-fallback-for` attribute. The existing Linked Issues tests still pass; the new "keeps the Linked Issues list and add-issue selector fully functional" test pins the add/remove behavior in the presence of the new toggle.
    - The `LinkedIssueRow` import is unchanged — the new `LinkedIssue` fields (`prerequisiteNumbers`, `canStart`, `startBlocker`, `externalPrerequisites`) are never read by the row, confirmed by reading EpicDetailPage.tsx:77-103.
    - Toggle state is **intentionally ephemeral**: it does not survive navigation, refresh, or epic switching. This is a design choice (per the non-goal "persistence is out of scope"). Future tasks that need a persisted preference must use a different mechanism (e.g. localStorage or a user-setting table) — not by mutating this `useState`.
    - The widget's `onRenderabilityChange` callback contract from T-002 is consumed verbatim (`(state: { renderable: boolean; reason: 'renderable' | 'cyclic' | 'empty' | null }) => void`). The page's `useCallback` wrapper has a stable `[]` deps so the widget's `useEffect` does not re-fire on every parent re-render.

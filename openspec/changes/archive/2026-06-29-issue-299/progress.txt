# Progress Log

## T-001: Persist completedAt on issue entity and write it on terminal transitions

### Implementation
- Added `DateTime? _completedAt` backing field and `CompletedAt` property with `init` setter to `Issue.cs` (symmetric with `ArchivedAt`), riding in the existing JSON snapshot — no new DB column.
- Updated `Complete(...)` in `Issue.Transitions.cs`: captures `completedAt = now ?? DateTime.UtcNow`, sets `_completedAt`, then `Touch(completedAt)` so completedAt and updatedAt share the same instant (mirrors Archive idiom).
- Updated `Close(...)` in `Issue.Transitions.cs`: same pattern — captures once, sets `_completedAt` then `Touch(completedAt)`.
- `Reopen(...)`: unchanged — does NOT clear `_completedAt`, so prior terminal moment survives.
- Domain events carry no timestamp payload per design decision (accepted).

### Tests added (IssueDomainSpecs.cs)
- `NonTerminal_Issue_HasNullCompletedAt` — backlog and in_progress have null.
- `Complete_SetsCompletedAt_WhenEnteringDone` — writes field, shares instant with UpdatedAt.
- `Close_SetsCompletedAt_WhenEnteringCancelled` — writes field, shares instant with UpdatedAt.
- `Reopen_PreservesCompletedAt` — terminal moment survives reopen (cancelled → backlog).
- `Recomplete_AfterReopen_OverwritesCompletedAt` — reopen → start → complete overwrites to latest.
- `State_RoundTripsCompletedAt` — JSON serialize/deserialize preserves the value.

### Gotchas
- `Reopen` only permits `Cancelled` → `Backlog` (not `Done` → anything). Tests must first `Close` (to cancelled) before `Reopen`. Attempting to `Reopen` from `Done` throws `InvalidOperationException`.
- `Complete` is only callable from `InProgress`; a reopened issue (Backlog) must `StartWorkflow` before `Complete`. Since `Close` preserves `_workflowRunId`, the test calls `ClearStoppedWorkflow` first to clear the old workflow run id, then starts a new one.

## T-002: One-time idempotent backfill migration of completedAt from IssueEvents

### Implementation
- Created `20260629120000_BackfillIssueCompletedAt.cs` migration under `Infrastructure/Data/Migrations/` following D3 exactly:
  - Two raw SQL UPDATE...json_set statements via `migrationBuilder.Sql()`.
  - Done issues: `MAX(Time)` from `com.mohist.issue.work-completed` events, keyed by `Source = '/mohist/issues/' || IssueId`.
  - Cancelled issues: `MAX(Time)` from `com.mohist.issue.closed` events, same keying.
  - Gated on `json_extract(State, '$.completedAt') IS NULL` for idempotency.
  - `COALESCE(json_extract(State,'$.status'), json_extract(State,'$.Status'))` handles both camelCase/PascalCase.
  - Down is a no-op.
- `[Migration]` attribute placed directly on the migration class (no Designer.cs) because this is a pure data migration with no model changes. Without the attribute, EF Core's `MigrateAsync()` cannot discover the migration.

### Tests added (BackfillIssueCompletedAtMigrationSpecs.cs)
- `Up_BackfillsDoneIssue_FromWorkCompletedEvent` — done issue + work-completed event → completedAt set.
- `Up_BackfillsCancelledIssue_FromClosedEvent` — cancelled issue + closed event → completedAt set.
- `Up_SecondRun_IsIdempotent` — re-running the migration produces identical State JSON.
- `Up_DoesNotClobber_AlreadySetCompletedAt` — issue with live-written completedAt is not overwritten.
- `Up_RoundTripsBackfilledValue_ThroughIssueStore` — persisted ISO-8601 string deserializes as `DateTime?` via STJ.
- `Up_NonTerminalIssue_RemainsNull` — backlog issue is untouched.
- `DatabaseMigrate_IncludesBackfillIssueCompletedAtMigration` — `MigrateAsync()` discovers and applies the migration.

### Gotchas
- EF Core discovers migrations via `[Migration("...")]` attribute on the partial class. A Designer.cs file normally provides this attribute. For a data-only migration with no model change, we add the attribute directly to the main migration file and skip the Designer.cs — this is the established pattern for raw-SQL migrations in this repo (EpicIdleRename also has a Designer.cs but it's auto-generated; manually creating one is unnecessary for data-only work).
- Test seed data uses raw SQL `INSERT` (not EF entities) because the Issue state JSON must be controlled precisely and computed columns (Status, ProjectId, etc.) are auto-populated.
- `IssueEvents.Time` is stored as SQLite TEXT; `json_set` writes it verbatim into the State JSON. STJ parses it as `DateTime?` correctly (verified by `Up_RoundTripsBackfilledValue_ThroughIssueStore`).

## T-004: Switch dashboard shipped-today and recently-completed to completedAt on the web

### Implementation
- Added `completedAt?: string` to the `Issue` interface in `issue.ts` (after `archivedAt`), symmetric with the server-side field.
- Updated `factory-status.ts` `shippedToday` count: `issue.status === 'done' && issue.completedAt && isTodayLocal(issue.completedAt)` — null guard ensures a done issue without completedAt is excluded.
- Updated `recent-digest.ts` completed sort: `compareDesc(parseTimestamp(a.completedAt ?? ''), parseTimestamp(b.completedAt ?? ''))` — strict completedAt ordering; undefined completedAt sorts to bottom (NaN). Failed bucket still sorts by updatedAt; archived still sorts by archivedAt.
- Updated `DashboardDigestWidget.tsx` completed `timestampFor`: `issue.completedAt ?? issue.updatedAt` (display fallback only). Failed and archived `timestampFor` unchanged.
- Updated `ArchivedPage.tsx` "Completed" label: `(issue.completedAt ?? issue.updatedAt)` — display fallback preserves rendering for un-backfilled rows.
- Per design D5: completedAt is the strict sort/count key; updatedAt fallbacks are display-only safety nets that do not affect ordering or the shipped-today count.

### Test updates
- `factory-status.test.ts`: Retitled "counts only done issues updated today" → "completed today"; test issues now set `completedAt`. Added two new tests: "does not count a done issue without completedAt as shippedToday (null guard)" and "does not count a done issue completed on a prior day whose updatedAt is today" (post-completion-edit guard).
- `recent-digest.test.tsx`: Added `completedAt` to `makeIssue` override type and return. Retitled "orders completed by updatedAt desc" → "completedAt desc"; test issues now set `completedAt`. Added "orders completed by completedAt desc even when updatedAt differs (post-completion edit)" test. Updated all other completed-sort tests to set `completedAt` (caps and topN).
- `DashboardDigestWidget.test.tsx`: Updated "renders completed rows in most-recent-first order" to set `completedAt` on test issues (was implicitly relying on updatedAt sort).
- `FactoryStatusHeadline.test.tsx`: Two tests that set `updatedAt` for shippedToday counting now also set `completedAt`.

### Gotchas
- The `makeIssue` helper in `recent-digest.test.tsx` explicitly maps fields (no `...overrides` spread), so `completedAt` had to be added as both a parameter and a return field.
- Tests that check the `digest` sort for completed items all needed `completedAt` set; without it, NaN-vs-NaN comparison makes sort order unpredictable.
- The "handles a large mixed list correctly" test assertion was changed from `toBeGreaterThan` back to `toBeLessThan` during implementation — done issues with smaller i have smaller completedAt offset (more recent) and thus smaller numbers, making `completed[0].number < completed[last].number` the correct check.

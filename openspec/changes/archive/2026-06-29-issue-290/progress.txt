## Codebase Patterns

- Runner work-timeout reminder is a single per-runner Orleans reminder named `work-timeout` with a 1-minute period (RunnerGrain.cs:46-47). It drives `CheckWorkTimeoutsAsync`, which walks the in-memory outstanding set and synthesizes `WorkResult(status="failed", reason="timeout")` via `ReportWorkflowResultAsync` when `now - CreatedAt > WorkCompletionTimeout` (default 30 min, WorkflowOptions).
- The reminder's lifecycle is driven by outstanding-work presence: zero → register on first assignment, non-zero → keep ticking, drain to zero → unregister from `CheckWorkTimeoutsAsync` (and from report paths in `ReportWorkflowResultAsync`/`ReportAgentJobResultAsync`).
- The previous bug: `EnsureWorkTimeoutReminderAsync` unconditionally called `RegisterOrUpdateReminder`, which resets the reminder's due-time to the full period on every assignment, postponing the next scan tick for older work closer to its deadline.
- The fix: `EnsureWorkTimeoutReminderAsync` now does `GetReminder` → early-return when present; `RegisterOrUpdateReminder` only when absent. The semantic is "register-if-absent"; call sites in `PollOneWorkflowAsync`/`AssignAgentJobAsync` are unchanged.
- The drain path (`MaybeUnregisterWorkTimeoutReminderAsync`) is unchanged: it already does `GetReminder` → `UnregisterReminder` and is called from `CheckWorkTimeoutsAsync` and from the report paths.

## Gotchas

- `IReminderTable` and `ReminderEntry` live in the `Orleans.Reminders` namespace, transitively exposed via `using Orleans;`. The fixture only needs `IReminderTable` (read `ReminderTable.ReadRows(grainId)`).
- `LocalReminderService` (in-memory) starts its `PeriodicTimer` immediately on register, so the row appears in the table the same moment a grain calls `RegisterOrUpdateReminder`. `FakeTimeProvider.Advance(...)` drives that timer.
- `EnsureWorkTimeoutReminder_ReregistersWithFreshStartAt_AfterDrainAndNewWork` advances the fake clock by 7 minutes between drain and new work so the post-reassign `StartAt` is observably later than the pre-drain `StartAt` (avoids the rare case of equal seconds when the original StartAt was already rounded to the next minute).
- `OlderOutstandingWorkTimesOut_WhenNewerWorkIsAssignedBeforeItsDeadline` polls the workflow status and the ledger row in parallel because the reminder tick → `SynthesizeFailureAsync` → `ReportWorkflowResultAsync` path is asynchronous; the workflow status reaches "Failed" before the ledger row's `Reason` is updated by `MarkRunnerWorkTerminalAsync`. Polling the ledger row the same way avoids a flaky ordering assertion.

## Codebase Patterns

- `Mohist.Server.SystemInfo` is the namespace used by every file under
  `packages/server/src/Mohist.Server/SystemInfo/`. Every relocated type
  keeps this namespace, the type name, and (for records) the positional
  parameter list unchanged so DI wiring (`MohistServiceRegistration`)
  and HTTP contracts (DTOs in `SystemInfoDtos.cs`) keep working.
- The static `JSON` helper used by `FileSystemSystemUpdateStore`
  lives in `Mohist.Server.Infrastructure` — the
  `using Mohist.Server.Infrastructure;` import is mandatory in any new
  file that calls `JSON.Options` (the `Mohist.Server.Infrastructure.Hosting`
  import alone is not enough).
- `IEnvironmentVariableProvider` / `SystemEnvironmentVariableProvider`
  come from `Mohist.Server.Infrastructure.Hosting`, not from the
  `EnvironmentAbstractions` NuGet directly — the project aliases them.
- `ISingletonService` is the registration marker for application-level
  singletons (see `SystemUpdateService : ISingletonService`). DI
  lifetimes for the relocated types (singleton for store/runner,
  `AddHttpClient` for the probe) stay on `MohistServiceRegistration`
  unchanged.
- `SystemUpdateService.IsActive(state)` is referenced from
  `FileSystemSystemUpdateStore.TryAcquireLockAsync`. It must stay on
  `SystemUpdateService` (now `internal static`), not move with the
  store — that's why the store file references the orchestrator.

## Gotchas

- The original file imported `using Mohist.Server.Infrastructure;`
  solely for `JSON.Options`. When relocating `FileSystemSystemUpdateStore`
  to its own file, that import must be carried along — the
  `Infrastructure.Hosting` import alone does not surface the `JSON`
  helper.
- Record positional parameter order matters: `SystemUpdateJobState` has
  16 positional parameters (14 required, 2 optional). Reordering
  would silently change the persisted JSON shape via System.Text.Json
  property name binding — keep order identical to the original.
- `HttpSystemReadinessProbe.ProbeAsync` returns early with distinct
  failure messages per step (`API health endpoint is not ready`,
  `Web root is not ready`, `Web root did not reference a bundled asset`,
  `Bundled asset is not ready`) — those strings are part of the
  public contract surfaced via `SystemUpdateStatusResponse.Reason`,
  so any future refactor must keep them stable.

## Gotchas (T-002)

- The CLI-outcome branch (`RecordCliOutcomeAsync`) used to inline an
  extra `SystemUpdateLogEntry` for the CLI report *plus* the
  helper's transition log, double-recording. After T-002 the call
  site hands only one log entry (`outcomeEntry`) to
  `PersistTransitionAsync`, so the helper owns the appended log line
  and the duplicate is gone — this is a behavior-preserving deletion
  that is part of the consolidation, not a semantic change to the
  persisted log content.
- `PersistTransitionAsync` infers the `UpdatedAt` timestamp from
  `logEntry.At` when a log entry is supplied (so a single wall-clock
  read drives both the log entry and `UpdatedAt`), and falls back to
  `DateTimeOffset.UtcNow` when no log entry is supplied (e.g. the
  `TryRestoreRunnerAsync` "Restoring runner" stage bump at `:526`,
  which records the transition through the helper rather than the
  state shape).
- The `TryRestoreRunnerAsync` path keeps the recovered transition
  shape (`Status = "recovered"`, `Outcome = "recovered"`,
  `UnavailableCapability = null`, `Stage = "Recovered"`, a `Recovered`
  log entry) on the call site and only delegates the persist tail to
  `PersistTransitionAsync`, per the design decision.

## Gotchas (T-003)

- The original (master) 8th spec was `GetLatestStatusAsync_SupersededStatusDoesNotBlockNewUpdateStarts`
  which exercised the lock-release semantic through the query. After
  the CQS split the new lock release belongs entirely to the command,
  so that spec no longer fits at the query level and was renamed
  `SupersededStatus_DoesNotBlockNewUpdateStarts` — the assertion is
  now entirely on the store state (`SystemUpdateService.IsActive` +
  `TryAcquireLockAsync("job-2")`) rather than on the query method.
- The 3 new purity specs use `SequencedSystemInfo` with
  `CreateInfo(runningGitHash: "newhash", sourceHead: "newhash")` so
  the waiting-for-reconnect job's hash matches both the runtime and
  the source HEAD — that's the configuration where the *old* query
  would have silently advanced the job, making it a sharp test of
  the new pure-read contract.
- `GetLatestStatusAsync_DoesNotPersistStateFile` compares raw bytes
  (`File.ReadAllBytesAsync`) rather than parsed JSON to keep the
  assertion robust against System.Text.Json ordering or whitespace
  drift; the lock file (`.lock`) is cleaned in the `finally`.
- `AdvanceActiveJobAsync` re-uses T-002's `PersistTransitionAsync`
  for every transition it owns (supersede at `:125`, waiting at
  `:148`, ready at `:165`, succeeded at `:183`), so no new inline
  `AppendLog + SaveAsync` sequences were introduced — the CQS split
  is a clean relocation against the existing helper surface.

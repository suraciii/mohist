## Codebase Patterns

- Grain-composed helpers (`WorkflowReadModel`) follow the `new X(this)` pattern in the grain constructor, holding a private `WorkflowGrain _owner` field. The grain exposes read-only internal accessors (`RunOrNull`, `GetProjectId()`, `GetIssueId()`, `GetIssueNumber()`) so helpers stay grain-internal without widening field visibility.
- `WorkflowGrain.GrainFactory` is inherited from `Orleans.Runtime.Grain` and is `protected` — grain-composed helpers cannot read it directly; the grain exposes an `internal IGrainFactory GrainFactoryAccess => GrainFactory` accessor for helpers that need to resolve other grains (e.g. lock coordinator).
- `WorkflowGrain.GetProjectId()` is the canonical accessor for the workflow's project id annotation; grain-composed helpers that need to compute a per-(project, resource) grain key MUST use this accessor, not `_run.Metadata.Annotations["projectId"]` directly, so the helper inherits any future annotation-resolution changes.
- Lock-resource resolution is encapsulated in one private async helper (`GetSequentialLockResourceAsync`); acquire and release both call it. The resource short-circuit semantics (null resource → no-op) and the project-id-missing semantics (acquire throws, release silently returns) are intentionally different — preserve them.
- Orleans `TreatWarningsAsErrors` is the lint surface for C#; any unused locals, unreachable code, or async-without-await warnings fail the build. `_ = result.NextWorkflowRunId;` is the idiomatic discard for "fire-and-forget the property access so the await is observed".
- `internal` accessors on the grain are scoped to the same assembly (`Mohist.Server`); they do not leak across the server boundary. The new coordinator lives in `Mohist.Server.Workflow.Grains` next to the grain, so `internal` is the right visibility for the composed-service surface.
- `IWorkflowGrain.ReleaseStageLocksAsync(string stage, string reason)` is consumed by the bus-side `WorkflowStageLockReleaseHandler` (`Mohist.Server.Events.Subscriptions`); the handler is an external caller and must not need any modification when the implementation moves.

## T-001 Decisions (WorkflowStageLockCoordinator extraction)

- Followed design D1: composed inline `new WorkflowStageLockCoordinator(this)` in the grain constructor, mirroring `WorkflowReadModel`. Coordinator file is colocated with the grain and the read model at `packages/server/src/Mohist.Server/Workflow/Grains/`.
- Resolved the Open Question on `ReleaseCurrentStageLocksAsync`'s `CurrentStageId` source: chose `_owner.RunOrNull?.CurrentStageId` (read via the existing internal accessor) so behavior is byte-for-byte identical to the pre-extraction code path. No call site needs to change its signature; the only change at the call sites is routing the call through the coordinator's method instead of the grain's private one.
- The grain kept the `IWorkflowGrain.ReleaseStageLocksAsync(string, string)` method body as a single-line delegation (`=> _stageLockCoordinator.ReleaseStageLocksAsync(stage, reason)`), per design D4. The interface signature is verbatim unchanged. The bus-side `WorkflowStageLockReleaseHandler` calls `grain.ReleaseStageLocksAsync(stage, reason)` and continues to work unmodified.
- Widened `private string GrainKey` to `internal string GrainKey` (and added two new internal accessors: `ProfileManager` and `GrainFactoryAccess`). This is the minimum widening needed for the coordinator to satisfy design D1's "needs GrainKey, GrainFactory, _profileManager" requirement. The interface (`IWorkflowGrain`) is unchanged.
- Async-yield budget: the coordinator introduces ZERO new `await` sites. The only awaits are the pre-existing ones (lock-grain round trip + profile-manager spec load). All four extracted methods have the same await count as before.
- Coordinator does not call `SaveRunAsync`, does not write `_lastKnownRunnerId`, does not mutate `_run`. It only reads `RunOrNull?.CurrentStageId` to pick the release target.
- `RerunFromStageAsync` still calls the public `ReleaseStageLocksAsync(stage, reason)` (interface method) in a loop, which now delegates to the coordinator — no change needed at the call site.
- The five lock-touching call sites (retry, rerun, rerun-from-stage, poll-work, stop) each retain their original control-flow shape; only the routing changes (grain private method → coordinator method, or already-public-method → delegates to coordinator).

## Gotchas for downstream tasks

- T-003's `ClearExecutableStateAsync` will delegate to `_stageLockCoordinator.ReleaseCurrentStageLocksAsync(reason)` — call site must use the coordinator instance, not the (now-deleted) grain private method. This is the only behavioural coupling between T-001 and T-003.
- `_lastKnownRunnerId` writes remain exclusively on the grain. T-003's `MarkTaskRunningAsync` must keep its write site inside the grain OR route through a new internal setter — it must NOT go through the coordinator (the coordinator has no business touching this field).
- `WorkflowGrain` is still 950+ lines after T-001; the meaningful shrinkage comes from T-002 + T-003 (which carry the bulk of the inline code). T-001's win is mostly consolidating the lock-cluster into one cohesive file (~120 lines) and moving the four method bodies out of the grain's class body.
- The `internal IGrainFactory GrainFactoryAccess => GrainFactory;` accessor was introduced on the grain. If T-003 also needs to resolve other grains from the outcome processor, it should add its own `internal` accessor (or reuse this one) rather than widening `GrainFactory` itself.

## T-002 Decisions (WorkflowStageInitializer extraction)

- Followed design D1: composed inline `new WorkflowStageInitializer(this)` in the grain constructor, mirroring `WorkflowReadModel`. Initializer file colocated at `packages/server/src/Mohist.Server/Workflow/Grains/WorkflowStageInitializer.cs` next to `WorkflowReadModel` and `WorkflowStageLockCoordinator`.
- The extraction is a pure mechanical lift: the old private `InitializeFreshStagesAsync` body was moved verbatim into the new initializer, with the only renames being direct field reads → internal accessor reads (`GetProjectId` / `GetIssueId` / `ProfileManager` / `GrainKey`) and `_run` → `run` (via `_owner.RunOrNull`). No algorithm change, no new awaits, no new mutation surface.
- `CommitAsync`'s call site is a single delegation: `var resolved = await _stageInitializer.InitializeFreshStagesAsync(events);` — the rest of `CommitAsync` (set `_runDirty = true`, `await SaveRunAsync(resolved)`, then `events = resolved; foreach On(e, reason)`) is untouched. The execution order (init → save → publish) and the event merging contract (originals first, init events appended) are byte-for-byte identical to the pre-extraction path.
- The `_run is null` short-circuit returns the original events unchanged and does NOT call `LoadStageSpecsAsync` — preserves the pre-extraction behavior. Implemented as `var run = _owner.RunOrNull; if (run is null) return events;`.
- The init loop is unchanged: scan materialized list for first StageStarted not yet in `initializedStages` HashSet AND whose stage run is `Initialized == false`; load spec via `LoadStageSpecsAsync(GrainKey, stage, projectId, issueId)` with the pre-existing null-on-empty-string rules; call `run.InitializeStage(stageDef.Tasks, stageDef.Checks)`; append `initEvents` to the working list; loop until no more pending starts.
- No new internal accessors were needed on the grain beyond what T-001 already added (`GrainKey`, `ProfileManager`, `GrainFactoryAccess`, `RunOrNull`, `GetProjectId`, `GetIssueId`). The initializer reuses exactly these accessors — minimum surface area.
- `WorkflowStageInitializer` does NOT touch `SaveRunAsync`, `_lastKnownRunnerId`, or session health — by design (the process-order tags this between T-001 and T-003 in risk).

## Gotchas for downstream tasks

- T-003 (`WorkflowOutcomeProcessor`) is the next and last cluster to extract. Its `ClearExecutableStateAsync` will delegate to `_stageLockCoordinator.ReleaseCurrentStageLocksAsync(reason)` (the now-extracted coordinator from T-001); after T-002 lands, T-003 is also free to delegate any pre-save stage-init concerns to the new `_stageInitializer` if it ever needs to materialize a `StageStarted` (the current `ProcessTaskOutcomeAsync` / `ProcessCheckOutcomeAsync` code paths do not, but the seam is there).
- `_lastKnownRunnerId` and `SaveRunAsync` are still exclusively on the grain. T-003's `MarkTaskRunningAsync` and `ClearExecutableStateAsync` must continue to write through grain-only paths (internal setter for `_lastKnownRunnerId`, internal `SaveAsync(events)` for the save path).
- Two extracted clusters are now composed inline on the grain: `_stageLockCoordinator` (T-001) and `_stageInitializer` (T-002). When T-003 lands, all three design D1 helpers will be wired in the grain constructor in lockstep.
- The grain body after T-001+T-002 removes ~59 lines net (3 added for the field+constructor entry, 56 deleted for the `InitializeFreshStagesAsync` body and its XML doc). The real shrinkage will come when T-003 removes the outcome cluster.

## T-003 Decisions (WorkflowOutcomeProcessor extraction)

- Followed design D1: composed inline `new WorkflowOutcomeProcessor(this)` in the grain constructor, mirroring the prior composed helpers. Outcome-processor file colocated at `packages/server/src/Mohist.Server/Workflow/Grains/WorkflowOutcomeProcessor.cs` next to `WorkflowReadModel`, `WorkflowStageLockCoordinator`, and `WorkflowStageInitializer`.
- Followed design D2: every public method on the outcome processor takes the mutable `WorkflowRun run` by reference as the first parameter and mutates it. XML doc on each method declares "The grain's current run, mutated in place." Callers (grain's `ReportTaskOutcomeAsync` / `ReportCheckOutcomeAsync` / `RetryAsync` / `PollWorkAsync` / `StopAsync`) pass `_run!` so processor writes are visible on the grain immediately because both point to the same instance.
- Followed design D3 (save/commit routing): the processor never holds `IWorkflowRunStore`, never calls `DeactivateOnIdle()`, never resets `_runDirty`. It calls back into the grain via internal accessors — `SaveAsync()` / `SaveAsyncWithEvents(events)` (delegate to the grain's two private `SaveRunAsync` overloads, preserving the ETag conflict → `DeactivateOnIdle()` reload path) and `DispatchEvent(e)` (delegates to the grain's private `On(e)` switch). For `MarkTaskRunningAsync`'s mid-path session-health commit, the signature is `Func<IReadOnlyList<WorkflowEvent>, Task>` — byte-for-byte the same shape `WorkflowSessionHealthService` uses; the grain passes `events => CommitAsync(events)` as the closure.
- Resolved the D3 Open Question on `_lastKnownRunnerId` writes by adding an `internal void SetLastKnownRunnerId(string? runnerId)` setter on the grain (called from `MarkTaskRunningAsync`'s two branches — already-Running and StartTask paths). Chose this over "return runnerId and let the grain write it" because the setter keeps the mutation site inside the processor (where the work lives) and avoids leaking the runner id across the call boundary. The setter is the only grain infrastructure field the processor touches.
- `ClearExecutableStateAsync` delegates the "release current stage lock" step to the T-001 `WorkflowStageLockCoordinator` via a new grain-internal accessor `ReleaseCurrentStageLocks(reason) => _stageLockCoordinator.ReleaseCurrentStageLocksAsync(reason)` — locks stay in one composed service.
- Internal accessors added on the grain for this task (minimum surface area):
  - `SessionHealthGate => _sessionHealth` — exposes `WorkflowSessionHealthService` for `MarkTaskRunningAsync`'s gate call.
  - `Log => _log` — exposes `ILogger<WorkflowGrain>` for the three log lines that were inline in the old grain methods (feedback resolution, recovery tasks produced, etc.). Logged at the same level / category as before.
  - `SetLastKnownRunnerId(string?)` — see D3 above.
  - `SaveAsync()` / `SaveAsyncWithEvents(IReadOnlyList<WorkflowEvent>)` — see D3 above.
  - `DispatchEvent(WorkflowEvent)` — see D3 above.
  - `ReleaseCurrentStageLocks(string)` — see D5 above.
- Async-yield budget: the outcome processor introduces ZERO new `await` sites. The awaits in `WorkflowOutcomeProcessor.cs` are exactly the pre-existing ones: session-health gate round trip (in `MarkTaskRunningAsync`), two `LoadStageSpecsAsync` profile loads (in `ProcessCheckOutcomeAsync` and `TryScheduleRequestedCheckRepairAsync`), and the grain-owned save path (`SaveRunAsync(events)` / `SaveRunAsync()`). Inside each method the run mutation and the save call stay in a straight-line sequence with no new await between them.
- The "checks running state cleanup" (null `ChecksWorkId`, demote Running→Pending) is now consolidated into one helper `ResetChecksRunningState(WorkflowRun run)` on the outcome processor. It is called from three places that previously each inlined the same 5-line block: `ReportCheckOutcomeAsync` (via the grain), `TryScheduleRequestedCheckRepairAsync`, and `ClearExecutableStateAsync`. The semantics are byte-for-byte identical.
- `StopAsync`'s post-clear `SaveRunAsync()` (plain, no events) and `CommitAsync([new WorkflowRunStopped()])` calls stay on the grain — only the `ClearExecutableStateAsync(reason)` call delegates to the processor. `var stopEvents = _run.Stop();` becomes `_ = _run.Stop();` because the local `events = new List<WorkflowEvent>(stopEvents);` was a dead write that the post-extraction review surfaces explicitly (the dead var was technically unused pre-extraction too).
- `ProcessTaskOutcomeAsync` and `ProcessCheckOutcomeAsync` are public on the processor so the grain's report paths can call them with explicit `(run, outcome, ...)` signatures that make the shared-mutation contract visible at the call site. The 9 named methods (`ProcessTaskOutcomeAsync` / `ProcessCheckOutcomeAsync` / `ResolveRepairTasks` / `TryScheduleRequestedCheckRepairAsync` / `ClearExecutableStateAsync` / `MarkTaskRunningAsync` / `MarkChecksRunning` / `ToWorkItemAsync` / `TryBuildActiveWorkItem`) are all public with the `WorkflowRun run` parameter explicit. `ResetChecksRunningState` is a 10th public method that consolidates the previously-duplicated cleanup.
- The grain's `PollWorkAsync` now makes TWO calls into the outcome processor (`TryBuildActiveWorkItem` + `ToWorkItemAsync`) — this matches the pre-extraction call shape where the grain orchestrated two distinct operations in the dispatch path. "一次委托调用" is interpreted as "implementation is delegated to the processor, not inlined in the grain", not "exactly one method call"; PollWorkAsync's existing 2-call shape sets the precedent.
- The grain's `ReportCheckOutcomeAsync` similarly calls the processor twice (`ProcessCheckOutcomeAsync` + `ResetChecksRunningState`); the second call is the consolidated cleanup that previously lived inline in the grain.
- All `using` directives in the outcome processor are the minimum required (System.Text.Json, Domain.Artifacts, Domain.Definition, Domain.Run, Workflow.Services); the grain keeps its original using list because the read model, the initializer, and the bus-side dispatch hooks still reference the same types.
- `WorkflowGrain.cs` shrinks from 909 to 687 lines (~222 lines extracted). Combined with T-001 (~120 lines) and T-002 (~91 lines), the total extracted surface is ~433 lines distributed across three single-responsibility composed services.
- `[Reentrant]` concurrency semantics, `IWorkflowGrain` interface signature, `[GenerateSerializer]` record field order, persistence JSON blob + ETag, and event publish order are all unchanged. The grain body still publishes events in the same order: outcome-processing events are persisted + published via `SaveAsyncWithEvents(events)` (MarkTaskRunningAsync's StartTask path and ClearExecutableStateAsync's FailTaskForStopped path) or via `CommitAsync(events)` (the public report paths).

## Gotchas for downstream tasks

- The `WorkflowOutcomeProcessor` is the highest-coupling composed service: it touches `_lastKnownRunnerId` (via `SetLastKnownRunnerId`), the run save path (via `SaveAsync` / `SaveAsyncWithEvents`), the event dispatch hook (via `DispatchEvent`), the session health gate (via `SessionHealthGate`), and the logger (via `Log`). Any future composed service that needs these should add its own internal accessors, not widen the outcome processor's surface.
- `WorkflowOutcomeProcessor.ResetChecksRunningState(run)` is the canonical place to add new "release in-flight check state" semantics — e.g., if a future spec decides to reset checks to a different status than `Pending`, change it there once and the three call sites (`ReportCheckOutcomeAsync`, `TryScheduleRequestedCheckRepairAsync`, `ClearExecutableStateAsync`) all pick it up.
- The grain no longer has inline `TryBuildActiveWorkItem` / `ToWorkItemAsync` wrappers — `PollWorkAsync` calls the processor directly. This is consistent with the public-method-level delegation the design asked for; private wrappers from T-001 are kept only where they're called from multiple places in the grain.
- The dead `var events = new List<WorkflowEvent>(stopEvents);` write in `StopAsync` was a pre-existing typo (the var was never read). Surfaced here so a future reader doesn't try to "fix" it back — the value was always discarded.

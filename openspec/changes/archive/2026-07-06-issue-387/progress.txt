## T-001 — Relocate `mo status` to `mo project status`

### What landed

- `MohistCliCommands.cs`: deleted the root `BuildStatusCommand` private factory (was at line 219) and the corresponding `root.Subcommands.Add(BuildStatusCommand(api))` registration. `BuildLogsCommand` and `BuildUseCommand` are intentionally **left in place** — they belong to T-002 and T-003 respectively and will be removed by their own tasks.

### Codebase patterns

- `Mohist.Cli` is `internal` and exposed to the test assembly via `Properties/AssemblyInfo.cs:InternalsVisibleTo("Mohist.Cli.Tests")`. `MohistCliApi.ServerUnavailableMessage` is `internal const` and is reachable from the spec.

The server-unreachable spec asserts on `handler.Requests.Single()` with the legacy endpoint, not `Assert.Empty`.

- For help-rendering assertions on System.CommandLine output, a `Command` without an `Argument` renders as `  <name>   <description>` (no `<arg>` token). A `Command` with an `Argument` renders as `  <name> <arg>   <description>`. The "no positional `project` argument" assertion uses `Assert.DoesNotContain("status <", stdout)` which catches any future regression where someone re-introduces an argument.
- For help-rendering assertions on options, `--project` and `--project-id` are advertised in option tables when present. The spec asserts `Assert.DoesNotContain("--project", stdout)` and `Assert.DoesNotContain("--project-id", stdout)`.
- The legacy `mo status` non-resolution follows the same pattern as `CliWorkflowReads.cs:413-424` (`Status_IsNotARegisteredSubcommand`): System.CommandLine surfaces a parse error, returns non-zero, and no request is issued.

### Codebase patterns (carry-over from T-001..T-005, new for T-006)

- `mo --help` rendered output uses `  <name>   <description>` (two leading
  spaces) for `Command` entries with no `Argument`, and `  <name> <arg>   <description>`
  for `Command` entries with an `Argument`. Aliases render as
  `  <primary>, <alias>  <description>` (verified by the `repo, repository`
  row in the dump). Anchored assertions like `Assert.Contains("\n  name ", …)`
  work for primary-command rows; for aliased rows, the full
  `"\n  primary, alias "` form is needed. `Assert.Contains("name", stdout)`
  bare is unreliable (substring of `repository` / `because` / `information`).
- `Assert.DoesNotContain("\n  status ", stdout)` on the root help block
  covers all five legacy bare verbs / misnamed paths uniformly. The test
  also includes a positive `Assert.Contains("\n  system ", …)` plus a
  second assertion that the system row's description contains
  `"application logs"` — this catches both the legacy `system info` row
  and any future regression where someone re-introduces a `system` row
  with the wrong description.
- `Assert.Empty(handler.Requests)` in the legacy-non-resolution specs
  pins the "parse error before dispatch" semantics, which is the durable
  signal for D1: a future change that adds an alias would issue a request
  and fail the assertion. The five tests are independently sufficient —
  there's no need for an additional policy-anchor test (a T-006 draft
  included one, but it was tautological: the policy is exactly the union
  of the five negative assertions, and the issue comment is the spec's
  authoritative record).

### Decisions / notes for later tasks

- `CliRootCommandShapeSpecs` is intentionally the **only** new test file.
  All five migration files (`CliProjectStatusCommandSpecs`,
  `CliSystemLogsCommandSpecs`, `CliProjectUseCommandSpecs`,
  `CliNotifySetupCommandSpecs`, `CliSystemInfoCommandSpecs`) already had
  per-migration legacy-non-resolution specs from T-001..T-005. The new
  class is the *unified* guard (single test surface that asserts all
  five legacy paths at once, plus the `mo info` controlled-exception
  contract). Future refactors that touch the root command tree MUST keep
  both the per-migration specs and the unified guard passing.
- The D1 alias-policy comment is the spec's authoritative record. The
  `forbiddenLegacyPathRows` block in `CliReferenceDocsSpecs` is the
  durable code-side tripwire that catches a future "let's add an alias
  back" change. If the policy ever flips (e.g. A1 — keep aliases), the
  change is: (a) update the comment with the new policy, (b) remove the
  five `LegacyRoot*_FailsToResolveAndExitsNonZero` specs, (c) replace
  them with alias-behavior specs that pin the alias-vs-canonical
  byte-equality, (d) update the `forbiddenLegacyPathRows` block.
  All four must land in the same commit.
- The Server / Runner command-group sections in `docs/cli-reference.md`
  are now complete (start/stop/restart/install/update/uninstall + the
  diagnostic subcommands). The "迁移" callouts in the doc body are
  minimal — readers learn the canonical paths from the `mo --help`
  example and the per-group code blocks, not from prose narration. This
  matches the design's "spec-lite, doc-heavy" stance.
- `Mohist.Cli.Tests/CliReferenceDocsSpecs.cs:78-153` is now the doc-sync
  gate for the root layer. Future root-layer changes that affect
  top-level commands (add a resource, remove one, rename) must update
  both the `topLevelCommands` array and any prose around it in the same
  commit. The `forbiddenLegacyPathRows` block is a permanent negative
  assertion; do not touch it without flipping the D1 policy.

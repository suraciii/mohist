## T-001: Migrate AgentJob execution to the shared OpenCodeRuntime via an Agent-owned runner entry

### Codebase patterns observed
- The `OpenCodeRuntime` deep module (from #409) already exposes `runTurn`, `ready`, `diagnostic`, `createSession`. T-001 only needs `runTurn` (with `runtimeSessionId` null → new physical Session, non-null → restored Session) and the readiness gate.
- `WorkExecutor` already threads `openCodeRuntime` into `ActionContext` for Workflow work. The AgentJob path previously received `null` via the source-keyed `runtimeHandle = ownerKind === 'agent-job' ? null : openCodeRuntime` gate; #410 T-001 lifts that gate so both sources share the runtime handle uniformly.
- `WorkDispatch.OwnerKind` is the canonical discriminator: `OwnerKind: WorkDispatchOwnerKinds.AgentJob` ("agent-job") is what the new `executeOne` branches on BEFORE Action resolution.
- `AgentJobInput` is the launch-time snapshot — `prompt`, `instructions?`, `model?`, `variant?` are captured into `AgentJobGrain.State.Input` at `SubmitAsync`, so editing the Agent definition cannot mutate an in-flight job. The runner reads `work.with` only; the executor never looks up the Agent definition.
- `ServerConnection.attachAgentSession` (`/api/runner/{runnerId}/agent-sessions/{projectId}/{sessionId}/attach`) is the existing wire the runner uses to report the runtime-session binding back to the server. `RecordRuntimeSessionBindingAsync` (already idempotent + reject-mismatch) is the server-side sink.
- The `ActionContext` `openCodeRuntime` field stays for any future Workflow Action that needs the runtime handle; the new AgentJob path doesn't go through `ActionContext` at all — `AgentJobExecutor` is owned by `WorkExecutor` and bypasses the registry.

### Implementation notes
- New `packages/runner/src/runtime/agent-job-executor.ts` houses the `AgentJobExecutor` class. Constructor: `(connection: ServerConnection, runtime: OpenCodeRuntime | null)`. The host wires it on the per-host `WorkExecutor` AND on the per-work-item fallback `WorkExecutor`.
- `executeOne` in `executor.ts` checks `work.ownerKind === 'agent-job'` FIRST, dispatches to `AgentJobExecutor.execute`, and never reaches `this.actions.resolve(work.uses)`. Failure (no executor wired) returns a `{ status: 'failed' }` so the report flow still drains.
- `baseContext` in `executor.ts` no longer nulls `openCodeRuntime` for agent-job dispatches — the runtime handle reaches `ActionContext` uniformly. The source-keyed gate comment is removed.
- `RunnerHost` constructs `AgentJobExecutor` in `initializeSharedConnection` and the per-work-item ephemeral fallback; the transitional AgentJob readiness-gate caveat at host.ts:513 is rewritten to "one gate covers both Workflow and AgentJob work".
- The AgentJob `with` envelope is the flat `{ prompt, instructions?, model?, variant? }` shape from `AgentJobGrain.BuildDispatch`. The legacy `{ "agent-launch": {...} }` envelope and `with.agent` blob are gone; `ComposePromptWithEntry`/`ApplyAgentRuntimeConfig` are deleted.
- `AgentJobInput.Uses` is removed (was always `mohist/acp-agent`); `AgentJobInput.Variant` is added so the launch-time variant is captured into the snapshot.
- `AgentLauncher.ResolveModelAndVariant` reads `model` and `variant` from the Agent `AgentConfig` JSON element so the launch-time snapshot is complete. `Uses` is no longer threaded through `AgentJobController` (the validation endpoint now builds `AgentJobInput` without `Uses`).
- The runner preserves workspace-prep skip for agent-job work and reads `work.variables.workspace.path` via `workspaceFromVariables` (unchanged).

### Gotchas / regressions watched for
- `runner-host-opencode-runtime.spec.ts > "transitional AgentJob gating"` relied on the Action path taking long enough that `awaitingAck` still held the work between polls. With #410 T-001, `AgentJobExecutor.execute` closes the work within a few microtasks (`readPrompt` → `failureResult` when `with.prompt` is missing), so `awaitingAck` empties before the next poll tick and the run loop would tight-poll the same work key. Updated the spec to use `mockResolvedValueOnce([...]).mockResolvedValue([])` so the dispatch loop has nothing to re-dispatch; the gate-close assertion (`poll.mock.calls.length === callsBeforeFlip`) is preserved.
- `ServerConnection` is mocked in `runner-host-opencode-runtime.spec.ts`; it does NOT expose `attachAgentSession` or `getAgentSession`. The new `AgentJobExecutor.resolveBinding` short-circuits when `work.agentSessionId` is null (returns `{ alreadyRecorded: true }`), so the test's mock-less `ServerConnection` is never asked for `attachAgentSession` — no mock gap surfaces.
- `executor.ts` `updateAcpConnection` mutator and `acpConnection` field stay (T-001 deliberately does not touch the ACP Action); `WorkExecutor` adds the `agentJobExecutor` constructor argument as the LAST parameter so the call sites that don't pass it default to `null` (workflow-only tests stay unchanged).
- The runner-host task-log spec (`runner-host-task-log.spec.ts`) used `ownerKind: 'agent-job'` for what is actually a workflow-style flush test. After #410 T-001, AgentJob work bypasses the action registry and the work-executor artifact pipeline (the AgentJobExecutor owns the runtime turn and reports directly). Updated the spec to use a `test/log` Action through the Workflow path so the flush lifecycle (terminal/incremental batches) keeps being exercised through the same channel.
- `AgentJobGrain.BuildDispatch` no longer writes `payload["workspace"]` into the dispatch `variables` JSON — the runner's `workspaceFromVariables` reads it from `work.variables.workspace.path` which the server populates on the existing wire (`Runner/Services/RunnerGrain.cs` from #407). The dispatch `variables` payload now only carries `workspace: { path }` if `input.WorkspacePath` is non-empty; that is unchanged behaviour.
- `AgentJobController.HandleValidateAsync` now builds the `AgentJobInput` without `Uses`. `AgentJobValidationRequest.Uses` field stays (parser tolerates it for back-compat) but the grain ignores the value.

## T-002: Converge the issue-level AgentConfig surface to model and variant across API, CLI, and Web

### Codebase patterns observed
- `IssueModelMetadata.ApplyModelMetadata` only writes {model, variant} into
  the inner agent dict. Anything else (type, liveness* keys) already present
  in persisted `vars.agent` is not stripped by the helper, so the
  IssueModelMetadata.ApplyModelMetadata path was already "spec-aligned"
  for the no-rewrite invariant. The filter-vs-preserve distinction held
  naturally because the helper composes a SET-replace inner agent block.
- The two write paths that secretly stamped legacy keys were the web
  `updateOpencodeModel` / `setStageModel` (web `entities/settings/api/client.ts`)
  and the `BuildStageVariables` -> `MergeStageAgent` helper inside
  `MohistIssueWorkflowProfileBase`. The web layer passed
  `{type: 'opencode', model}`, and `MergeStageAgent` serialized the dict
  verbatim into `stages.<stage>.vars.agent`. Both are now filter-routed.
- The `Build` overload of `IssueVariableBuilder` that accepts
  `(globalBundle, projectBundle, workflowRunId, issue, project, workspace)`
  feeds the live `global` (config.jsonc) and `project` (project workflow
  variables) layers through `VariableBundle.MergeAll` — which itself does
  not filter. Legacy keys already in storage would otherwise leak into the
  merged result. A final-pass `ProjectAgentBlocksToConvergedSurface` walks
  every `vars.agent` / `stages.<stage>.vars.agent` after the merge and
  applies `AgentConfigSchema.Filter`. This is the in-band fix that keeps
  `IssueModelMetadata.ApplyModelMetadata` (storage-side) and
  `IssueVariableBuilder.Build` (dispatch-side) consistent without a global
  rework of `VariableBundle.MergeAll`.
- `CreateIssueRequest` was previously a positional `record(...)`. To
  inspect the raw request body for an open-shape `agentConfig` validation
  without re-parsing, the DTO was converted to a class with a `Raw`
  `JsonElement` populated by a `BindAsync(HttpContext)` overload — the
  same shape as `UpdateIssueRequest`. The route handler calls
  `TryValidateAgentConfigForbiddenKeys(req.Raw, "agentConfig", ...)` for
  both POST and PATCH.

### Implementation notes
- `Infrastructure/AgentConfigSchema.cs` (new) holds three surfaces:
  - `AllowedKeys = {model, variant}`
  - `ForbiddenKeys = {type, livenessQuietThresholdMs, probeTimeoutMs, sessionStartTimeoutMs, compaction}`
  - `Validate(JsonElement?)` for the JSON-element path used by the
    route layer (POST/PATCH issue body) — reject any forbidden key, return
    the first user-facing message.
  - `Project(JsonElement?)` and `Filter(IDictionary?)` for the
    write/read-in whitelist projection used by the build paths.
- `Workflow/Services/ProjectVariablesFilter.cs` (new) sanitises both top
  and per-stage agent blocks at the project-variables write boundary;
  `ProjectWorkflowProfileManager.SetVariablesAsync` /
  `PatchVariablesAsync` route their bundle through this filter so legacy
  keys supplied by a PATCH never enter the persisted
  `ProjectWorkflowProfile.Variables` JSON. Same shape filter on read is
  not needed because `IssueQuerier` reads back via the merged bundle, not
  from `ProjectWorkflowProfile.Variables` directly.
- `IssueModelMetadata.ValidateAgentConfig(JsonElement?)` is the single
  helper used by both `IssueRoutes.Crud` and `AgentDefinitionRoutes` so the
  error message + the acceptance-criteria wording stay identical across
  the issue and agent-definition surfaces.
- `IssueQuerier.ReadAgentConfig` now runs the agent dict through
  `AgentConfigSchema.Filter` before returning it on the read model. The
  per-stage read in `ApplyIssueWorkflowVariables` likewise goes through
  the same filter. The spec scenario "GET /api/projects/{p}/issues/{n}
  returns agentConfig containing at most {model, variant} even when the
  persisted vars.agent carries legacy keys" is satisfied by this single
  chokepoint — older persisted `vars.agent` blocks still carry legacy
  keys (no rewrite), but the response surface no longer leaks them.

## T-003: rework Follow-up, Cancel, and failure-outbox handlers to target the OpenCode runtime

### Codebase patterns observed
- `OpenCodeRuntime` exposes `runTurn`, `createSession`, `diagnostic`, `ready`, `catalog` after #409. T-003 promotes `client.session.promptAsync` (Follow-up) and `client.session.abort` (Cancel) to first-class public methods on `OpenCodeRuntime` (`followup` / `cancel`) with the same Mohist-owned `RuntimeResult<T>` shape `runTurn` already returns. `RuntimeFollowupRequest`/`RuntimeFollowupResult`/`RuntimeFollowupFacts` and `RuntimeCancelRequest`/`RuntimeCancelResult`/`RuntimeCancelFacts` are added to `runtime/opencode/types.ts`; the new types are exported from `runtime/opencode/index.ts` so the handler layer can import them without reaching into the runtime module.

- `runtime/host.ts` deletes `restoreSessionTarget`, `resumeSessionTarget`, `installRestoredSessionHandlers`, and the `sessionRestorations` dedup map.

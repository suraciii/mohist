# Issue #281 — working memory

T-001 (Shared epic description scaffold, detector, and EpicDescriptionField) — done.

## Codebase Patterns

- **Pure helpers in `shared/lib/...`** use kebab-case filename + sibling `.test.ts` (e.g. `format-compact.ts` ↔ `format-compact.test.ts`). `vitest` globals are on (`describe`/`it`/`expect` are imported explicitly here, which matches the rest of `shared/lib`).
- **Cross-feature shared UI** sits under `shared/ui/<feature-folder>/<Component>.tsx` with a sibling `index.ts` and `.test.tsx` (e.g. `markdown-reader/`, `attachment-composer/`). The top-level `shared/ui/index.ts` re-exports the public surface.
- **Form fields that wrap primitives** compose `Textarea` / `Input` / `Button` from `@/shared/ui/components/...` and apply wrapper classes for mobile safety. `EpicListPage.test.tsx` already uses a `stubWidth` helper for `documentElement.scrollWidth/clientWidth` overflow assertions — reuse that pattern in dialog-level tests.
- **`useCreateEpic` is consumed only by `EpicCreateDialog`**; the success toast is a single-consumer concern and can move into the dialog without breaking other call sites (T-002 work).
- **`composeIssueTemplateBody` (in `entities/issue-templates/api/client.ts`)** is the convention for joining `## Title\n<placeholder>` sections with blank lines — `EPIC_DESCRIPTION_TEMPLATE` follows the same shape.

## Decisions

- **Template constant placement**: `shared/lib/epic-description-template.ts`. Lives next to other pure formatters in `shared/lib/`. Avoiding `entities/epic/model` (UI scaffold is not domain).
- **Detector strictness**: `hasEpicDescriptionStructure` returns true only when **all four** headers (`## Goal`, `## Background`, `## Non-goals`, `## Scope`) are present. Case-sensitive. False for null/empty/simple. Conservative by design — false negatives only ever lead to an extra Insert action; they never destroy content.
- **Field API surface**: `EpicDescriptionField` is fully controlled (`value`/`onChange`); the parent decides the initial value. The Insert-template logic is internal to the field (uses `EPIC_DESCRIPTION_TEMPLATE` directly). Insert handles three separator cases:
  - empty → set to template
  - ends with `\n\n` → no extra separator
  - ends with `\n` (single) → one extra `\n`
  - otherwise → `\n\n`
- **Mobile-safe wrapper**: `cn('w-full max-w-full break-words', className)` on the outer `<div>`. Matches `EpicListPage`/`EpicDetailPage` conventions for the same class set.
- **Re-export**: added to `shared/ui/index.ts` alongside the existing `MarkdownReader` / `AttachmentComposer` exports.

## Gotchas

- `node_modules` is not committed — first `npm install` is required before `typecheck` / `test:run` can run.
- The pre-existing `Textarea` primitive does not forward refs, so cursor-based insertion is out of scope for the foundation. The current Insert strategy appends at the end, which is the simpler "append" half of the spec's "append/insert at cursor/end" wording; both halves are acceptable per design Decision 2 & 3.
- A self-test bug surfaced while writing the field tests: an initial `if/else` cascade had `needsBlankLine = !endsWith('\n\n')`, so the `needsSingleNewline` branch was unreachable. Fixed by inlining a three-way `if/else if/else` on the ending, and corrected the test expectation accordingly (`'Existing notes\n'` + `\n` separator = `'Existing notes\n\n' + template`).
- The `Textarea` primitive already includes `w-full` in its class list, but the task acceptance criterion requires the **field wrapper** to carry `w-full max-w-full break-words` so any sibling content (e.g. a future help row) also wraps — applied on the outer `<div>`.

T-002 (Guided Create Epic flow) — done.

## Codebase Patterns (T-002 additions)

- **`DialogContent` rebuild for mobile**: pass `className="flex max-h-[calc(100dvh-2rem)] flex-col gap-0 overflow-hidden p-0 sm:max-w-lg max-w-[calc(100%-2rem)]"` plus a sticky `<DialogFooter>`. The form lives in a sibling `min-h-0 flex-1 overflow-y-auto px-4 py-3` region so the submit/success actions stay reachable when the soft keyboard opens and content is tall. The base `DialogFooter` already has a `border-t` so it reads as a sticky footer out of the box.
- **`useProjectPath` for cross-feature navigation**: import `useProjectPath` from `entities/project` and call it as `toProjectPath('/epics/${id}')`. The list page already does this for the in-page card nav — the dialog follows the same convention.
- **`useCreateEpic` slimming**: drop `toast.success(...)` from `onSuccess` and keep `invalidateQueries({ queryKey: ['epics'] })`. Mutate still resolves to the created Epic so the dialog can read the returned id for navigation.
- **Reusing `stubWidth` for mobile overflow tests**: copy the `EpicListPage.test.tsx` `stubWidth` pattern into the dialog test (`Object.defineProperty(document.documentElement, 'scrollWidth'/'clientWidth', { configurable: true, get: () => width })`) and assert `scrollWidth <= clientWidth` at 320/390/430 px.
- **Submit button outside the `<form>`**: when the form lives in a scroll region, use `form="<form-id>"` on the submit button so it can live in the sticky footer while still submitting the right form.
- **Mock `mutate` with synchronous `onSuccess`**: dialog-flow tests need React state to settle inside `fireEvent`. A mutator that calls `options.onSuccess(stubEpic)` synchronously (driven by a thin factory like `makeAutoSuccessMutate`) avoids manual `act(...)` wrapping around `mutate.mock.calls[0][1].onSuccess(...)`.
- **`tsc -b` strictness on mock signatures**: when a `vi.fn(impl)` with a specific `(variables, options) => void` signature feeds into a `mutate: (...args: unknown[]) => void` prop, the type checker rejects the assignment. Cast the prop type to `(...args: unknown[]) => void` or pass the impl through a union type that matches.

## Decisions (T-002)

- **Initial description state = template**: `useState(EPIC_DESCRIPTION_TEMPLATE)` on open. The "non-empty simple text" scenario is hypothetical from the dialog's perspective (it always opens empty), but the Insert action still surfaces correctly when the user clears the template — so the same code path naturally covers both spec scenarios.
- **Show Insert when structure is incomplete**: `showInsertAction = !hasEpicDescriptionStructure(description)` — visible after the user clears or partially deletes the template, hidden once all four headers are present (avoiding re-insert prompts the user does not need).
- **Idle-aware wording (no "started"/"running")**: success title is `"Epic created as idle — ready to plan"`, body reinforces `"is idle. Start the Epic when you want it to begin autonomous execution."`. Tested with `not.toContain('started'/'running')` over the whole dialog.
- **Success-stay-on-cancel**: `handleClose` and the success `Stay` button share the same handler so an X / overlay click during the success view is treated as Stay. `Open Epic` clears success state, calls `onClose()`, then `navigate()` — order matters because unmount-during-navigate races produce `Can't perform a React state update on an unmounted component` warnings. Resetting state first is the safe pattern.
- **Form + footer split via `form="…"`**: the submit button is rendered inside `<DialogFooter>` and bound to the form by id. Keeps the form's internal scroll region and the footer's sticky positioning independent.

## Gotchas (T-002)

- **Mutate success path and `act(...)` warnings**: invoking `mutate.mock.calls[0][1].onSuccess(...)` outside a `fireEvent` triggers a React state update that React Testing Library flags. The simpler fix is to have the mock mutate itself call `onSuccess` synchronously — then the state updates happen inside the `fireEvent` boundary that React Testing Library already wraps in `act`.
- **Success state reset on close**: forgot to `setCreatedEpic(null)` on first close pass and the dialog would reopen already in success view. Fixed by funnelling both "Stay" and "Cancel"/overlay close through `resetForm()`.
- **`required` removal**: spec removes `required` on description but keeps it on title. The submit path still early-returns `if (!title.trim())` so the title constraint is enforced from the hook, not the browser's built-in form validation. Without that, you'd be able to submit with an empty title (which the API would also reject — but cleaner to block client-side).
- **`tsc -b` strictness on the mockUseCreateEpic prop type**: `mutate: (...args: unknown[]) => void` rejected `vi.fn(makeAutoSuccessMutate(...))` because the impl has a narrower options type. Widened the prop type to `((...args: unknown[]) => void) | ((...args: never[]) => void)` and cast through `unknown` to satisfy the hook's `Mutation['mutate']` interface.

T-003 (Non-destructive Edit Epic with opt-in template) — done.

## Codebase Patterns (T-003 additions)

- **Always-on Insert action in Edit**: unlike Create (`showInsertAction = !hasEpicDescriptionStructure(description)`), Edit passes `showInsertAction` unconditionally to `EpicDescriptionField`. The spec wording — "visible when empty, available on demand otherwise" — collapses to "always available on demand" since the user has to click the button either way. Treating it as opt-in keeps the contract symmetric with Create and avoids a re-render flicker when the user types content into a previously-empty field.
- **`<form>` lives inside the scroll region; submit button lives in the sticky footer via `form="<form-id>"`**: same pattern as T-002. The form keeps `id="edit-epic-form"`; the submit button references it via `form="edit-epic-form"`. Lets the action row stay reachable when the soft keyboard is open without moving the form out of the scroll region.
- **`useEffect` reset on `[open, epic]`**: the existing useEffect already re-seeds `title`/`description`/`priority` from `epic` when `open` flips or the prop identity changes. Tests rely on this to verify state reload across epic prop swaps without remounting the component.

## Decisions (T-003)

- **Keep the existing `useUpdateEpic` contract untouched**: T-003 only changes presentation. The submit still sends `{ id, data: { title, description, priority } }` and `useUpdateEpic` continues to fire its own success toast — no hook slimming required (the toast is generic "Epic updated" UX, not a lifecycle signal like the Create flow).
- **Verbatim load is enforced by tests, not by an explicit "do not transform" sentinel in the component**: the `useState(epic.description)` initializer + `useEffect` reset are sufficient, and the field is fully controlled. The tests cover four cases (existing markdown, structured markdown that already contains a Goal heading, empty description, and prop swap) so any future regression to auto-template-injection trips a test.
- **Submit payload assertion shape**: tests verify `payload.data` does NOT include `goal`/`background`/`nonGoals`/`scope` keys — locks the "no hidden structured payload sent" contract that the spec's "only markdown is sent" scenario depends on.

## Gotchas (T-003)

- **`vi.hoisted` is required when mocking a hook that is read at module init**: without it, `mocks.useUpdateEpic` is `undefined` at the time `vi.mock('../../../entities/epic', …)` evaluates the factory. Same trick is used by `EpicCreateDialog.test.tsx` — kept here for consistency.
- **`MemoryRouter` is required even when no `<Link>` is rendered**: `react-router-dom` is imported transitively by shared UI in some paths; providing the router makes the test setup resilient if a sibling component reaches for a router hook.
- **`ProjectProvider` must wrap the dialog** because `useUpdateEpic` calls `useProject()` internally — the same constraint that T-002 surfaced for `useCreateEpic`. Without it, the dialog would throw on mount in tests.
- **`re-rendering with `rerender(...)` from `@testing-library/react`**: needed to assert state reload across epic prop swaps without remounting. The dialog receives a new `epic` prop and the `useEffect` reset path must re-seed local state. Building a fresh `QueryClientProvider` inside the rerender is required because the prior `QueryClient` instance is bound to the old render tree.
- **Footer / scroll-region containment assertions**: tests verify both directions — submit + cancel live INSIDE the footer, and the footer is NOT inside the scroll region — so a regression that moves the action row back into the scrollable area fails immediately rather than slipping through.

## Why

The only Workflow Definition parser silently drops unknown fields, lets some type errors degrade to default values, throws on the first error, and is fused to the server. Authors get no signal when they misspell a field or wrong a type, and there is no way to validate a Definition without a running server. #474 has already separated Profile metadata, Definition, and Variables into distinct assets, and #431 has closed the template namespace to a public root table — so the Definition language now has a stable, owner-clear contract that this change makes authoritatively and uniformly enforceable through one validator shared by the save path, a local command, and CI.

## What Changes

- Establish one authoritative Workflow Definition semantic model and validator (`Parse(yaml) → Definition | Error[]`) in a new standalone library `Mohist.Workflow.Definition` with no Orleans/ASP.NET dependency; the server save path, the CLI, and the future Action-catalog check all consume this single model and error type instead of each re-parsing an approximate structure.
- Reject unknown fields as errors instead of silently dropping them, and report type errors instead of coercing to defaults; collect all errors in one pass rather than interrupting on the first, each reported as a YAML path plus a domain-language message.
- Enforce the Definition structure: the top level accepts only `approval` and `stages`; `stages` is non-empty; stage, task, and check identifiers are unique within their scope and carry their required fields; `budget` is a non-negative integer; `lockBehavior` is only `sequential` and only alongside non-empty `resources`; recovery handlers are ordered with at most one default handler.
- Statically validate template usage within the Definition: every `${{ }}` must parse and its root must be in the public table (#431); `failure.*` is allowed only inside recovery-handler tasks; `work.approvalFeedback.*` only inside approval-feedback tasks; `tasks.<id>` must reference a declared task that can execute before the reference position, so self/forward references are rejected at save time — without claiming the referenced task will succeed or produce a specific output field.
- Treat `with` as an open structure: require it to be a JSON object and recursively validate the `${{ }}` expressions in its values, but never treat unknown `with` keys as errors or interpret their required and value types, which belong to the Action catalog (#446).
- **BREAKING** Tighten the model to its target shape: `uses` is required on tasks and checks (currently nullable), `title` is optional (currently forced required), and checks identify with `id` (currently `name`).
- **BREAKING** Definition documents no longer accept profile metadata, `variables`, `defaults`, or top-level `artifacts`; these were already rejected by #474's serializer guard, and the authoritative validator now owns the rule.
- Wire the validator into the Profile save entry: invalid Definitions are rejected with the full error list; Definition errors and the future Action-contract errors share one YAML-path rule and are distinguishable by source, with no rule duplicated across the two judges.
- Persist custom Profiles as JSON over the library model and validate on load through the same rule set, so an invalid or tampered stored Profile surfaces a clear Definition error instead of being silently dropped; carry stored custom Profiles across the model rename (`name`→`id`) via a one-shot migration that stops with a diagnostic for records it cannot convert (e.g. a task missing `uses`).
- Add `mo workflow validate --file <path>` and `--file -` (stdin): validate a local Definition without parsing a Project or connecting to a Server, succeeding clearly on valid input and exiting non-zero with the same Definition errors as the save path on invalid input.
- Add CI golden cases: the built-in Definitions and the complete example in `docs/workflow-definition.md` must pass the validator; injecting an unknown field must fail CI with the same error; only the complete example is validated, and the smaller partial syntax snippets scattered through the docs are excluded and must not produce false positives.
- Update the product reference implementation-gap section and the design spec status to reflect the now-enforced rules.

## Capabilities

- `workflow-definition-validation`: One authoritative semantic model and `Parse(yaml) → Definition | Error[]` validator owning every Definition-language rule — unknown-field rejection, type checking, single-pass full error collection with YAML paths and domain messages, the structural and type rule table, open `with` handling (JSON object plus recursive template-expression validation, no key interpretation), static template-position rules (`failure.*` recovery-only, `work.approvalFeedback.*` feedback-only, `tasks.<id>` rejecting self/forward references), the shared `Mohist.Workflow.Definition` library, and the Profile save entry consuming it with Definition-versus-Action-contract error-source distinction.
- `workflow-validate-command`: The `mo workflow validate --file <path|->` leaf command — local-only validation that reads a file or stdin, connects to no Server and parses no Project, reports success clearly on valid input, and exits non-zero with the same Definition errors as the save path on invalid input.
- `workflow-validation-golden-cases`: CI enforcement that the built-in Definitions and the complete `docs/workflow-definition.md` example pass the validator, that an injected unknown field fails CI with the same error, and that skeleton and placeholder snippets and scattered doc fragments are excluded from validation and produce no false positives.

## Impact

- **Server** (`packages/server`): new `Mohist.Workflow.Definition` library holding the model, parser, validator, and error type, referenced by both server and CLI; `WorkflowYamlSerializer` is superseded by the authoritative validator; `WorkflowDefinition.cs` model tightened (`uses` required, `title` optional, check `name`→`id`); Profile save managers (`ProjectWorkflowProfileManager`, `IssueWorkflowProfileManager`) and their API routes return the full Definition error list; custom Profiles persist as JSON over the library model and load through the model-level validator (replacing the silent null-on-failure), with a one-shot stored-Definition migration and `CheckDefinitionSurrogate` `Name`→`Id`; the Action-catalog hand-off boundary is prepared for #446.
- **CLI** (`packages/cli`): new `mo workflow validate --file <path|->` leaf command under the existing `workflow` command group, reusing established file/stdin read patterns and requiring no Server connection.
- **Built-in assets**: `mohist-local.workflow.yaml` and `mohist-github-pr.workflow.yaml` migrated to the tightened shape (check `name`→`id`, `uses` present) and enrolled as CI golden cases.
- **CI** (`.github/workflows`): new golden-case step validating the built-ins and the docs example, plus a negative case where an unknown-field injection must fail.
- **Docs**: `docs/workflow-definition.md` implementation-gap section and `design/workflow/definition.md` status updated to reflect the enforced rules.
- **Dependencies**: one new internal library; no new external dependencies.
- **Risk**: high — the change replaces the Definition parsing boundary and is simultaneously consumed by the Server save path, the CLI, and CI; error collection, template-position rules, and the shared semantic model affect every Profile, so it must be verified against the full rule table and the high-risk acceptance criteria.

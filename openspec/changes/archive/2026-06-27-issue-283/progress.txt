## Codebase Patterns

- `LinkedIssueDto.Status` is the single source of truth for terminal/open classification. `EpicProgress.IsTerminal(dto)` = `done`/`completed`/`cancelled`; `IsOpen(dto)` = `!IsTerminal(dto)`. `IsReadyToComplete(linked)` requires `linked.Count > 0 && !linked.Any(IsOpen)`.
- Three readiness consumers all funnel through `EpicProgress.IsOpen`/`IsReadyToComplete`: `EpicProgress.Build` (read-model), `EpicGrain.ComputeOpenLinkedNumbersAsync` (grain command-side), and the autonomous-advancement filter in `EpicGrain.TryStartNextAsync`. The advancement path previously duplicated this filter locally (`!IsCompleted(i) && i.Status != "cancelled"`); it now calls `EpicProgress.IsOpen(dto)`.
- The aggregate-level guard in `Epic.MarkDone` (`openLinkedNumbers.Count > 0 => throw`) stays as defense-in-depth even though the grain now computes `openLinkedNumbers` correctly; the architecture split puts authoritative validation at the aggregate boundary.
- `deliveredCount` is set from `IsCompleted` only (`done`/`completed`); cancelled never increments it. `totalIssueCount` is `linked.Count` (no archive exclusion in `EpicProgress.Build`; the spec scenario `Empty epic and archived issues` is satisfied at the querier/sweeper layer that filters archived before passing into `Build`).
- Issue prerequisite domain (`IssueGrain.LoadUndeliveredPrerequisiteNumbersAsync`, `Issue.StartBlocker`, `EpicGrain.BuildLinkedIssueDtosAsync`'s `undeliveredPrereqNumbers`, `EpicQuerier.allUndeliveredNumbers`) keeps the `undelivered*` naming — it describes prerequisites, not Epic readiness, and the design explicitly scopes the rename.

## Gotchas / Decisions

- Renamed only the Epic-scope readiness surface (not the prerequisite surface) to avoid touching two domains at once: `MarkDone(undeliveredLinkedNumbers → openLinkedNumbers)`, `EpicNotReadyToMarkDoneException.UndeliveredCount → OpenLinkedCount` with message "...open linked issue(s)...", `EpicGrain.ComputeUndeliveredLinkedNumbersAsync → ComputeOpenLinkedNumbersAsync`, `EpicProgress.Build` local `undelivered → open`, API 409 payload `undeliveredCount → openCount`. Error code `EPIC_NOT_READY_TO_MARK_DONE` is unchanged.
- The grain's `ComputeOpenLinkedNumbersAsync` returns `HashSet<int>` for O(1) lookup, even though for the renamed "open" set it would be smaller (cancelled excluded); the set shape is preserved to keep `MarkDone`/`tryAutoMarkDone`/`reconcile` call sites identical.
- Empty-epics semantics: `EpicProgress.Build` correctly returns `ReadyToMarkDone = false` for an empty linked list (covered by `EpicProgressBuildSpecs.EmptyLinkedIssues_YieldsZeroCountsAndNoNext`), but the grain's `TryAutoMarkDoneAsync` treats an empty epic as ready (existing `AutoMarkDoneIfReadyAsync_NoLinkedIssues_TransitionsToDone`). This discrepancy is pre-existing and out of scope for this task — the spec scenario for empty epic only constrains the read-model `readyToMarkDone`. Leaving the grain as-is avoids changing behavior the issue body doesn't cover.
- HTTP 409 details payload field renamed in the JSON wire shape: `ConflictDetailsDto.OpenLinkedCount` is decorated with `[JsonPropertyName("openCount")]` in the lifecycle spec to preserve the JSON key while using a C#-idiomatic property name. The CLI mock error strings (`"Epic has 2 open linked issue(s)"` and `"Epic has open linked issues"`) match the new exception message format.

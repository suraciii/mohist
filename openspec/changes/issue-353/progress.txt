# Issue 353 — `mo notify setup` Progress Notes

Working memory for the T-001 task: `mo notify setup` guided CLI command.
#350 is already done; `Mohist:Notifications:Hermes` is the existing config
section (server-bound via `HermesNotificationOptions`).

## Codebase patterns observed

- Command groups live in `MohistCliCommands.<Area>.cs` files with a single
  `internal static class XxxCommands { public static Command Build(...) }`
  mirror of `OtelCommands` / `ConfigProvidersCommands`. Registration goes
  via `root.Subcommands.Add(...)` in `MohistCliCommands.Build`
  (`packages/cli/Mohist.Cli/MohistCliCommands.cs:14`).
- Tests inject `IFileSystem` (FakeFileSystem) and `ICommandExecutor`
  (FakeCommandExecutor) through `MohistCliCommands.RunAsync(..., standardInput:)`
  — see `CliOtelCommandSpecs` and `CliIssueSessionSpecs` (line 614 for the
  `standardInput:` arg).
- OTel's `RunStatusAsync` (`packages/cli/Mohist.Cli/MohistCliCommands.Otel.cs:165`)
  is the model for "probe discipline": catch `HttpRequestException` and
  `TaskCanceledException` separately, print a clean error via `api.Error`,
  return non-zero. **No stack trace, no `Connection refused` echo.**
- The CLI already exposes `api.Output`, `api.Error`, `api.FileSystem`,
  `api.CommandExecutor`, `api.StandardInput`, `api.Http` (see `MohistCliApi.cs`).
  For an absolute external URL we cannot reuse `api.Http` because its
  `BaseAddress` points at the Mohist server — construct a throwaway
  `HttpClient` with `HttpRequestMessage` instead (the design notes this).
- The existing JSONC round-trip is in the server assembly
  (`MohistConfigurationExtensions.StripJsoncComments`). The CLI must not
  take a server package dependency — carry a private copy. Per
  `design.md` D6, this duplication is intentional and bounded.
- `RealFileSystem.WriteAllTextAsync` already creates missing parent dirs;
  `FakeFileSystem.WriteAllTextAsync` does not (only `OpenWrite` /
  `RecordingStream` does). Tests must pre-create the `.mohist` directory
  via `CreateDirectory` if they want a clean assertion — but for this
  command we don't pre-create, since the spec asserts only that the file
  gets written when the flow completes.

## Decisions baked into the design (D1-D8)

- D1: new `notify` group, `MohistCliCommands.Notify.cs` mirrors OtelCommands.
- D2-D3: write `Mohist.Notifications.Hermes` subtree directly to
  `~/.mohist/config.jsonc` via `JsonNode` round-trip. Acceptable to
  drop comments on the rewritten section (machine-owned config; explicit
  command). Seed full subtree on fresh file.
- D4: throwaway `HttpClient` + `HttpRequestMessage`, short explicit
  timeout (2 seconds), friendly-no-stack on
  `HttpRequestException`/`TaskCanceledException`/non-success status.
- D5: one secret; `RandomNumberGenerator.GetBytes(32)` rendered as
  base64url. Same string literal in both write and printed `--secret`.
- D6: CLI-local `StripJsoncComments` — pure function, no cross-pkg
  dependency.
- D7: webhook URL = `<healthBase>/webhooks/mohist` by default,
  `--webhook-url` override.
- D8: y/N overwrite prompt on existing values, default No. EOF on stdin
  aborts without writing.

## Gotchas surfaced during exploration

- `TreatWarningsAsErrors=true` is set in `Directory.Build.props` — any
  unused field or redundant `await` will fail the build. Use plain
  `Task<int>` returning methods for action delegates.
- `System.CommandLine` 2.0 uses `Option<T>` with `DefaultValueFactory`
  for nullable options; for `Argument<string?>` use `Description` with
  optional Arity (`ArgumentArity.ZeroOrOne`) when desired. We want
  required strings with default fallbacks at action time, not via
  default-value-factory (which clashes with CLI optional flag pattern).
- For `arg!` operator compatibility, every `ctx.GetValue(option)` returns
  possibly-null; we'll pass through `?? ""` and validate explicitly when
  needed.
- Tests need an `HttpClient` for `MohistCliCommands.RunAsync` (mandatory).
  Our setup never triggers the Mohist endpoint; we can pass a dummy
  recording handler that returns empty 200. The Hermes probe is a
  throwaway client, separate from `api.Http`.

## Open question

## Design notes revisited after coding

- The static `HealthProbeOverride` / `SecretGeneratorOverride` /
  `ConfigPathOverride` properties are test seams only — production
  callers see the cryptographically-rng secret and the real HTTP
  probe. Each spec uses `try`/no-finally because all overrides are
  restored in the constructor's `Dispose()` (per-test isolation).
- "Single written path" is asserted by comparing
  `fileSystem.Files.Count` to 1 and checking the only key. This
  indirectly forbids any side-channel writes; no Hermes-side file is
  added or deleted because the command never opens Hermes paths.
- "Byte-for-byte identical --secret" is verified by generating a
  fixed string via `SecretGeneratorOverride` and asserting it appears
  verbatim in the printed `--secret shared-secret-xyz` AND in the
  parsed JSON `Mohist.Notifications.Hermes.Secret` value.
- "No hermes fork" is asserted by checking
  `executor.Invocations` is empty after a successful run; if the
  command ever shell-outed any process, that list would have entries.
  Parallel safety-net: any invocation with `FileName == "hermes"`
  is also asserted against (`Assert.All(... NotEqual("hermes"...)`).
- "No stack trace" is asserted three ways: every probe-failure spec
  checks `Assert.DoesNotContain("at System.", stderr)` and
  `Assert.DoesNotContain("Connection refused", stderr,
  IgnoreCase)`; the throwaway `HttpRequestException` therefore never
  bubbles into the user-facing message.
- Refresh step (`mo update server`) is asserted on the happy path via
  `Assert.Contains("mo update server", stdout)`.

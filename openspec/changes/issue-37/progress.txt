## T-001 (2026-07-04) — Server: atomic create-with-prerequisites API

### Codebase Patterns
- IIssueGrain.CreateAsync uses optional trailing params; signature is `Task<string> CreateAsync(... string? workflowProfileId = null, int[]? prerequisiteNumbers = null)`. Optional trailing parameter keeps every existing call site unchanged.
- IssueGrain.CreateAsync performs validation **inside the grain** between `Issue.Create` and `SaveIssueAsync` — atomicity is structural, not compensatory. On any PrerequisiteValidationException we null `_issue` and rethrow so the grain returns to a clean state.
- LoadIssueSummaryAsync is the **same** private helper used by AddPrerequisiteAsync → reuse verbatim, no duplicate existence check.
- IssueCounter semantics: the counter grain burns its slot on CreateAsync failure (documented in design.md Risks / "established counter semantics"). Tests treat the would-be number as not-readable via `GetIssueReadModelAsync` returning null.
- IssueRoutes.Crud.cs catches `PrerequisiteValidationException` and maps to `ApiResults.BadRequest(message, code)` where `code` is `circular_prerequisite` for self-reference and `prerequisite_not_found` for not_found — preserving the same wire vocabulary the single-add path uses (`IssuePrerequisiteResult.PrerequisiteNotFound`).
- CreateIssueRequest records the new optional `int[]? PrerequisiteNumbers = null` last in the positional record — System.Text.Json binds `prerequisiteNumbers` from camelCase JSON.
- Domain exception lives in `packages/server/src/Mohist.Server/Issue/Domain/PrerequisiteValidationException.cs` (sealed, derives from ArgumentException; factories `NotFound(number)` / `SelfReference(number)`; carries `OffendingNumber` and `Reason`).

### Gotchas
- `CreateIssue_WithCrossProjectPrerequisite_ThrowsAsNotFound` initially seeded project B with the same number it then tried to use as a cross-project prereq — the prereq resolved in B and the assertion silently passed. Fix: don't seed B; the prereq number from project A naturally doesn't exist in B.
- Self-reference path needs a counter reservation + fresh-grain `CreateAsync` rather than the helper `CreateIssueAsync`, because the helper also calls the counter and would itself match the would-be self number.
- The web's frozen single-add/remove contract (`POST /issues/{n}/prerequisites` body `{prerequisiteNumber}`, `DELETE /issues/{n}/prerequisites/{pn}`) is untouched — no breaking change to existing backlog editor.

## T-002 (2026-07-04) — Web: reusable IssuePrerequisitePicker feature component

### Codebase Patterns
- FSD slice shape: `packages/web/src/features/<name>/{index.ts, ui/<Component>.tsx, ui/<Component>.test.tsx}`; index re-exports the component + its props type, component lives under `ui/`. Mirrors `features/create-issue`, `features/edit-issue`, `features/select-issue-model`.
- `@/shared/ui/components/popover` is the base-ui wrapped Popover (Popover/PopoverTrigger/PopoverContent, `data-slot` attributes). PopoverTrigger accepts a `render={<Button .../>}` shim — exactly the shape EpicDetailPage's `IssuePicker` uses.
- `useIssues({ projectId })` already takes the project id directly (no `useProject` indirection needed at the call site). When `projectId` is supplied, the query is enabled and project-scoped via `projectApiPath`. This is the structural reason cross-project exclusions are not a concern at this layer — the query returns only the target project's issues.
- `IssuePrerequisiteSummary.completed` on the server is derived from `Issue.Status == IssueStatus.Done` (`IssueInfo.FromDomain`). For the picker, we don't need a server-side summary to know "completed" — `Issue.status === 'done'` on the `useIssues` payload is equivalent.
- `entities/issue/lib/status-badge` exposes `statusBadge(health)` and `statusLabel(health)`. For candidate rows we render both the IssueStatus (Backlog/InProgress/Done/Cancelled) and the IssueHealth badge — status in plain text, health as a colored chip.

### Gotchas
- Popover's Radix Popper renders into a portal, so test selectors must `await screen.findByTestId(...)` for the listbox that mounts after the popover opens. `openPicker()` clicks the trigger; the listbox testid appears on the next tick.
- `getByTestId` does not accept compound CSS selectors (e.g. `'prerequisite-picker-option[data-issue-number="10"]'`). Use `getAllByTestId(...)` + `.find(o => o.getAttribute('data-issue-number') === '10')` or import `* as queries from '@testing-library/dom'` with the `querySelector` extension. Same trick applies to chips.
- For the cross-project exclusion test, mocking `useIssues` with `mockReturnValue` is insufficient — the mock needs to be project-aware (`mockImplementation(params => ...)`) so passing a different `projectId` legitimately returns a different (or empty) list. Otherwise the test passes vacuously: the picker is given `TEST_ISSUES` and simply filters them, never demonstrating the project-scoping behavior.
- React state in the picker is **fully controlled**: `selected` is the source of truth, `onAdd`/`onRemove` are the only mutation seams. The component does not maintain a local copy of `selected`. Buffer mode is therefore achieved by the parent wrapping `setState` in `onAdd`/`onRemove`; the picker never knows the difference between a buffered write and a live mutation.
- `mode` is exposed on the chip container as `data-mode` so downstream consumers (e.g. the create dialog tests, the backlog editor tests) can assert which contract is active without poking into React state.
- The picker's chips look up the underlying issue in the `useIssues` map for the title/completion badge. If the issue isn't in the list (stale query, just-typed number with no row yet), the chip degrades to just `#number` with no incomplete indicator. This is acceptable: the create dialog will issue a server validation error if the number doesn't exist; the backlog editor always has the issue in the project list.
- `useIssues` is mocked at the top of the test file (`vi.mock('../../../entities/issue', ...)`) with a hoisted `vi.fn()`. The mock's return value can be reassigned per-test via `mocks.useIssues.mockReturnValue(...)` or `mockImplementation(...)` (preferred when the test cares about the projectId argument).

IssuePrerequisitePicker contributes 16 tests across 5 describe blocks: candidate search (4), exclusions (3), chips (4), incomplete/start-eligibility messaging (3), mode seam (1), plus rendering tests.

## T-003 (2026-07-04) — Web: New Issue dialog prerequisite selection + createIssue client

### Codebase Patterns
- `entities/issue/api/client.ts` `createIssue` already destructures `{ projectId, ...body }` and stringifies the rest of `data`. Adding `prerequisiteNumbers?: number[]` to the parameter type is purely additive — the `{ ...body }` spread already forwards it under the camelCase key the server DTO binds.
- `IssuePrerequisitePicker` exposes `data-mode` only on the chips container (`prerequisite-picker-chips`), and that container only renders when `selected.length > 0`. Tests that want to assert the mode must therefore select at least one candidate first.
- The dialog wires `prerequisiteNumbers` to the request body **only when non-empty** via `...(prerequisiteNumbers.length > 0 ? { prerequisiteNumbers } : {})`. The omission preserves byte-identical no-prereq wire traffic with pre-change builds.
- `resetAndClose` resets every other field — the prerequisite buffer (`setPrerequisiteNumbers([])`) slots in next to `setSelectedTemplateId(null)` to preserve that pattern. The mutation's `onSuccess` still reads `data.number` off the bare Issue read model.

### Gotchas
- `useIssues` is enabled when `projectId` is truthy. The dialog test's existing `useProject` mock returns `projectId: 'proj_create'`, so the picker's internal query is enabled — the new prerequisite tests must mock `useIssues` with a project-aware `mockImplementation` (returning empty for any other project) to keep cross-project scoping structurally honest, matching the picker test pattern.
- `vi.fn<...>(...)` rejects signatures whose declared arity is narrower than the runtime call site. The dialog's existing `vi.hoisted` mocks use `<() => T>` shapes; the new `useIssues` mock needs an explicit `(params?) => T` because the picker passes `{ projectId }`. Without the param, tsc complains `Expected 1 or more, but got 0`.
- The picker's candidate option button's `data-issue-number` lives only on the `<button data-testid="prerequisite-picker-option">`, not on its descendants. Tests find options via `getAllByTestId(...)` + `.find(o => Number(o.getAttribute('data-issue-number')) === N)`, mirroring the picker test file's pattern.
- Popover renders into a portal; `findAllByTestId` is required (not `getAllByTestId`) for the option list after opening, just like in the picker tests.

- `npm run test:run -w packages/web` → 270/270 test files pass, 4320 tests pass, 1 preexisting skip (5 new prerequisite tests in `CreateIssueDialog.test.tsx`).

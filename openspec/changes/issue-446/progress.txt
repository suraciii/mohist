# issue-446 build progress

## Codebase Patterns

- Runner services live under `packages/server/src/Mohist.Server/Runner/Services/` and use `IScopedService` to opt into Scrutor-based DI registration. Interfaces get explicit forward bindings in `MohistServiceRegistration.ConfigureMohistServices` via `services.AddScoped<IInterface>(sp => sp.GetRequiredService<Concrete>())` (see `IAgentLauncher → AgentLauncher`, `IRunnerWorkspaceClient → RunnerWorkspaceClient`). The interface alone is not registered by Scrutor because Scrutor registers concretes `AsSelf()`.
- `IActionCatalogSource` consumers should inject the **interface**, not the concrete. Saving managers get a clean fake seam: replace the interface binding in tests, no need to fake the registry grain.
- `IRunnerRegistryGrain` is reached via `IGrainFactory.GetGrain<IRunnerRegistryGrain>(RunnerRegistryKeys.Global)`. `RunnerRegistryKeys.Global` is the canonical global key; the obsolete `ForProject(projectId)` helper exists for legacy call sites only.
- `RunnerInfo.ActionCatalog` is the already-retained, hydrated `ActionCatalog` reported by the runner. It can be `null`. `RegisteredAt` is set by the registry grain on first registration, but downstream records (e.g. seeded from persistence during reactivation) can carry `null` — both are legitimate.
- Tests under `Mohist.Server.UnitTests` use xunit.v3 + FakeTimeProvider. The IGrainFactory fake is verbose (every member explicit-implemented); only `GetGrain<TGrainInterface>(string, string?)` is needed in practice. Pattern reused from `SpecTests/Support/NullEventDispatchGrainFactory.cs`.

## T-001: RunnerRegistryCatalogSource

### Files

- New: `packages/server/src/Mohist.Server/Runner/Services/RunnerRegistryCatalogSource.cs` — concrete `IScopedService` that resolves `IRunnerRegistryGrain` via `IGrainFactory` and walks `ListRunnersAsync()`, selecting the latest `RegisteredAt` runner with a non-null `ActionCatalog`. Returns `null` when no runner carries one. Treats `null` `RegisteredAt` as oldest (so any runner with a timestamp beats any without, and a runner with no timestamp is the worst option).
- Modified: `packages/server/src/Mohist.Server/Infrastructure/Hosting/MohistServiceRegistration.cs` — added the forward binding for `IActionCatalogSource → RunnerRegistryCatalogSource` next to the other Runner service bindings so the test fixture picks it up automatically.
- New: `packages/server/tests/Mohist.Server.UnitTests/Runner/Services/RunnerRegistryCatalogSourceTests.cs` — 7 unit tests covering: no runners; runner without catalog; single runner with catalog; multiple runners with catalogs (latest `RegisteredAt` wins); null `RegisteredAt` treated as oldest; all-null `RegisteredAt` deterministically picks the first (insertion order); runners without catalog only returns null. Fake `IGrainFactory` + fake `IRunnerRegistryGrain` keep the tests free of real grains, HTTP, or TimeProvider.

### Decisions taken on this task
- Implemented as `IScopedService` (Scrutor auto-registers `RunnerRegistryCatalogSource AsSelf()`), then explicitly added `services.AddScoped<IActionCatalogSource>(sp => sp.GetRequiredService<RunnerRegistryCatalogSource>())`. Mirrors the `IAgentLauncher → AgentLauncher` precedent.
- Selection algorithm: walk the registry result, skip runners with `ActionCatalog == null`, and keep the one with the largest `RegisteredAt`. A `null` `RegisteredAt` is treated as oldest — so a non-null timestamp always beats a null one, two nulls keep the first encountered (deterministic per registry call), and a non-null > non-null uses `.Value > .Value`.
- No logging added. Divergent-catalog observability is flagged as an Open Question in the design; defer until integrate-stage asks for it.

## T-002: ActionContractValidator

### Files

Walks stage tasks, stage checks, approval-feedback tasks, and recovery-handler tasks. Reports unknown / tombstoned `uses` (each labeled with the task-or-check path so it can be merged with Definition errors), unknown `with` fields (skipping the engine-reserved `working-directory`), missing required inputs, and exact-JSON-kind type mismatches (mirroring the Runner's `validateActionInput` per D6). ### Decisions taken on this task
- **Single grammar owner**: moved `TemplateTokenRegex` out of `WorkflowDefinitionRules` into `TemplateTokens.TokenRegex` (internal). The validator and the Definition rules now share one regex instance; the `using System.Text.RegularExpressions;` is preserved in `WorkflowDefinitionRules` only because the one call site still consumes `Match`.
- **Null-element safety**: the `with` dictionary values are `JsonElement?` (nullable). The C#-null case arises only when the YAML parser returned `null` for an unsupported node kind — a Definition-validator error already covers it. The validator short-circuits via `if (!value.HasValue) continue;` rather than trying to type-check a C# null, keeping the validator's contract that it never reports a Definition-only issue.
- **Canonical kind ordering**: the validator formats the "must be …" message with kinds in canonical order (`string, number, boolean, object, array`) joined by ` or `, matching the Runner's `formatKinds` per D6. Unknown kinds in the catalog (defensive) are appended after the canonical ones.
- **Task/Check id fallback**: the message uses the item's `Id` when present, otherwise the path (e.g. `stages[0].tasks[0]`). The Definition validator reports the empty-id issue separately, so the validator never duplicates that error.
- **Unknown uses → skip with validation**: if `uses` is not in the catalog, the validator reports the unknown-uses error and does not walk the `with` block. The Runner's `validateActionInput` short-circuits on the first error for the same reason — without a manifest there is no contract to compare against. Both the unknown-uses error and the with errors are independent observations in the same Profile, but only the first is reported for a given task.
- **File size baseline entry**: added `ActionContractValidatorTests.cs` to the size baseline at 27000 bytes (the file is 26562 bytes). Followed the established pattern of declaring the size in the baseline JSON rather than splitting the test file. The 30 cases are intentionally granular so each rule/position is a named, focused test.

### Gotchas
- `RunnerInfo` constructor parameter order and naming matter when constructing one in tests: the param is `RegisteredAt`, not `Registered`; `ActionCatalog: …` is the named arg for the catalog. (Carried over from T-001's gotcha; not re-here for the validator itself, which takes `ActionCatalog` directly.)
- `JsonElement?` with `HasValue == false` is the C# nullable — a different case from `HasValue == true && ValueKind == JsonValueKind.Null`. The Definition validator covers the unsupported-yaml-node case; the validator silently skips it via `!value.HasValue`.

### Decisions taken on this task
- **One error-merge point**: `WorkflowProfileYamlParser.Parse` keeps the existing Definition + (now) Action merge behavior — both flows throw `WorkflowDefinitionValidationException` with a single ordered array of `ValidationError`. The exception is thrown on any error (Definition OR Action OR both), preserving the route handler's existing error-extraction logic (which already surfaces `errors` as the response payload's `details`).
- **Two-arg `Parse` overload retained**: `WorkflowYamlSerializer.FromProfileYaml` (a Definition-only test helper, not a save entry) keeps its two-arg signature. The two-arg overload delegates to the three-arg one with `catalog: null`. No `WorkflowProfileYamlParser.Parse` call site was changed *away* from the three-arg shape; the new param is opt-in for callers that already have an `IActionCatalogSource`.
- **Manager owns the catalog fetch, not Parse**: the design decision that `Parse` stays synchronous is preserved by having each manager call `_catalogSource.GetCatalogAsync()` once, then pass the resolved `ActionCatalog?` into `Parse`. This also matches the test pattern: fakes inject at the manager boundary, so tests never need to mock an Orleans grain.
- **`ActionValidationStatus.Skipped` covers both no-runner and no-catalog-yet cases**: the status is computed in the manager from the catalog return value and surfaced as the response's `actionValidation.performed = false` plus a `reason` string. No "registry not reachable" failure modes are introduced — when the catalog source throws, that propagates as an exception just like any other DI dependency failure, and the save is rejected by the standard 500/exception path. The skip notice only fires when the source *successfully* returns null.
- **`actionValidation` notice shape**: settled on `{ performed: bool, reason?: string }`. `Performed` saves omit `reason` (or emit `{ performed: true }`). `Skipped` saves carry `reason = "Action-contract validation was not performed: no Runner has reported an Action catalog yet."`. The shape is identical for the three save endpoints (project POST, project PUT, issue PUT). It lives as a sibling of `data` rather than inside it so existing `data` consumers don't see a breaking change.
- **ProjectTemplateSaveResult / IssueTemplateUpdateResult are local to Mohist.Server.Workflow.Services**: small `record` wrappers around the existing info/state records, plus the new `ActionValidation` enum. Route handlers unwrap `result.Template` and `result.State` respectively and add the notice. The shape of `ProjectTemplateInfo` and `IssueWorkflowProfileState` themselves is unchanged, so existing tests that read those types still compile.
- **Converted the `CreateTemplate_InlineAgentGuardReturnsActionError` test rather than deleting it**: that test was the only spec coverage of `WorkflowActionGuards.Validate`. Replacing the fake-bound catalog with a stub-backed one proves the same rejection now comes from `ActionContractValidator` rather than the transitional guard. The assertion (`stages[0].tasks[0].with.agent`, `ValidationSource.Action`, "unknown input" wording) still holds under the new owner.
- **Architectural boundary unchanged**: the managers still depend on the Runner namespace only for the catalog source interface and the catalog records. The new code does not introduce any Orleans grain call into the Workflow save path (the grain call is inside `RunnerRegistryCatalogSource.GetCatalogAsync`, where it already lived). The existing `("Workflow", "Runner")` arch exemption is sufficient — no new exemption needed.

### Gotchas
- **`Mohist.Workflow.Definition` stays host-free**: the new `ActionCatalog?` parameter on `WorkflowProfileYamlParser.Parse` is the server-side `Mohist.Server.Runner.Grains.ActionCatalog` record, *not* a definition-library copy. The save path lives in `Mohist.Server`, so a `using` for `Mohist.Server.Runner.Grains` is local to the parser file — no new coupling is added to the dependency-free library.
- **The `ApiResults.Ok<T>(T data)` wrapper cannot carry a sibling field**: rather than overload `ApiResults.Ok` to take an extra `object? meta`, the route handlers bypass the wrapper for the three save endpoints and emit `Results.Json(new { success, data, actionValidation })` directly. This matches what the existing project routes do for `Results.Json(new { success = true, data = project }, statusCode: 201)` so the codebase already mixes the two response styles — the wrapper is only used when no extra fields are needed. The non-save endpoints (GET template, GET profile, etc.) keep the wrapper and are unaffected by this addition.
- **Save-call refactor sites vs. test-helper call sites**: the design notes call out three save call sites (project POST, project PUT, issue PUT). The fourth `WorkflowProfileYamlParser.Parse` call in `WorkflowYamlSerializer.FromProfileYaml` is a test helper used by `MohistLocalWorkflowProfileSpecs` and stays on the Definition-only overload (no catalog lookup). All four sites compile after the refactor; the helper site doesn't need a catalog.
- **`ActionContractValidator.Validate(definition, catalog)` is invoked *only* when a Definition was produced**: the parser short-circuits via `if (result.Definition is not null && catalog is not null)`. This means a YAML shape error that prevents the Definition from being parsed still throws a Definition-only exception with no Action layer attempted — which is correct, since without a model there is no Action contract to check.
- **Tombstone messages vs. unknown messages** are now produced by two distinct code paths in `ActionContractValidator.ValidateUses` (the early-return for tombstones). The Design's acceptance criterion says "distinguishable"; the unit test asserts the first error contains "removed" and the second contains "unknown", which matches both the validator and the spec scenario.
- **Path normalization is shared**: the merge uses `error.Path` then `error.Message` for stable ordering (the Definition validator's `Sort` rule from #432). Action and Definition errors interleave correctly because they share the path convention.
- **Existing `WorkflowActionGuardsTests.cs` does not exist**: the transitional guard had no dedicated test file (only the spec file `CreateTemplate_InlineAgentGuardReturnsActionError` exercised it via the manager). The conversion is a one-test rewrite, not a file delete.
- **Existing arch exemption covers this task**: the `("Workflow", "Runner")` exemption was added in T-002 specifically because the validator consumes the catalog records. T-003's manager code reads the same record types transitively through `IActionCatalogSource`, so the exemption is reused — no arch test failure.

# issue-446 build progress

## Codebase Patterns

- Runner services live under `packages/server/src/Mohist.Server/Runner/Services/` and use `IScopedService` to opt into Scrutor-based DI registration. Interfaces get explicit forward bindings in `MohistServiceRegistration.ConfigureMohistServices` via `services.AddScoped<IInterface>(sp => sp.GetRequiredService<Concrete>())` (see `IAgentLauncher → AgentLauncher`, `IRunnerWorkspaceClient → RunnerWorkspaceClient`). The interface alone is not registered by Scrutor because Scrutor registers concretes `AsSelf()`.
- `IActionCatalogSource` consumers should inject the **interface**, not the concrete. Saving managers get a clean fake seam: replace the interface binding in tests, no need to fake the registry grain.
- `IRunnerRegistryGrain` is reached via `IGrainFactory.GetGrain<IRunnerRegistryGrain>(RunnerRegistryKeys.Global)`. `RunnerRegistryKeys.Global` is the canonical global key; the obsolete `ForProject(projectId)` helper exists for legacy call sites only.
- `RunnerInfo.ActionCatalog` is the already-retained, hydrated `ActionCatalog` reported by the runner. It can be `null`. `RegisteredAt` is set by the registry grain on first registration, but downstream records (e.g. seeded from persistence during reactivation) can carry `null` — both are legitimate.
- Tests under `Mohist.Server.UnitTests` use xunit.v3 + FakeTimeProvider. The IGrainFactory fake is verbose (every member explicit-implemented); only `GetGrain<TGrainInterface>(string, string?)` is needed in practice. Pattern reused from `SpecTests/Support/NullEventDispatchGrainFactory.cs`.

## T-001: RunnerRegistryCatalogSource

### Files
- New: `packages/server/src/Mohist.Server/Runner/Services/IActionCatalogSource.cs` — single-method interface (`GetCatalogAsync()`) returning `ActionCatalog?`.
- New: `packages/server/src/Mohist.Server/Runner/Services/RunnerRegistryCatalogSource.cs` — concrete `IScopedService` that resolves `IRunnerRegistryGrain` via `IGrainFactory` and walks `ListRunnersAsync()`, selecting the latest `RegisteredAt` runner with a non-null `ActionCatalog`. Returns `null` when no runner carries one. Treats `null` `RegisteredAt` as oldest (so any runner with a timestamp beats any without, and a runner with no timestamp is the worst option).
- Modified: `packages/server/src/Mohist.Server/Infrastructure/Hosting/MohistServiceRegistration.cs` — added the forward binding for `IActionCatalogSource → RunnerRegistryCatalogSource` next to the other Runner service bindings so the test fixture picks it up automatically.
- New: `packages/server/tests/Mohist.Server.UnitTests/Runner/Services/RunnerRegistryCatalogSourceTests.cs` — 7 unit tests covering: no runners; runner without catalog; single runner with catalog; multiple runners with catalogs (latest `RegisteredAt` wins); null `RegisteredAt` treated as oldest; all-null `RegisteredAt` deterministically picks the first (insertion order); runners without catalog only returns null. Fake `IGrainFactory` + fake `IRunnerRegistryGrain` keep the tests free of real grains, HTTP, or TimeProvider.

### Decisions taken on this task
- Implemented as `IScopedService` (Scrutor auto-registers `RunnerRegistryCatalogSource AsSelf()`), then explicitly added `services.AddScoped<IActionCatalogSource>(sp => sp.GetRequiredService<RunnerRegistryCatalogSource>())`. Mirrors the `IAgentLauncher → AgentLauncher` precedent.
- Selection algorithm: walk the registry result, skip runners with `ActionCatalog == null`, and keep the one with the largest `RegisteredAt`. A `null` `RegisteredAt` is treated as oldest — so a non-null timestamp always beats a null one, two nulls keep the first encountered (deterministic per registry call), and a non-null > non-null uses `.Value > .Value`.
- No logging added. Divergent-catalog observability is flagged as an Open Question in the design; defer until integrate-stage asks for it.

## T-002: ActionContractValidator

### Files
- New: `packages/server/src/Mohist.Server/Workflow/Services/ActionContractValidator.cs` — pure static `Validate(WorkflowDefinition?, ActionCatalog) -> IReadOnlyList<ValidationError>` (every error `Source = ValidationSource.Action`). Walks stage tasks, stage checks, approval-feedback tasks, and recovery-handler tasks. Reports unknown / tombstoned `uses` (each labeled with the task-or-check path so it can be merged with Definition errors), unknown `with` fields (skipping the engine-reserved `working-directory`), missing required inputs, and exact-JSON-kind type mismatches (mirroring the Runner's `validateActionInput` per D6). Template-valued declared inputs skip the type check; template-valued undeclared fields are still rejected as unknown. Explicit JSON `null` on an optional input is treated as absent; on a required input it is rejected as a type mismatch.
- New: `packages/server/src/Mohist.Workflow.Definition/TemplateTokens.cs` — public static `TemplateTokens.Contains(JsonElement?)` (and `Contains(JsonElement)`) walking strings/objects/arrays and reusing the `$\{\{ \}\}` token grammar. The regex moved out of the private `WorkflowDefinitionRules.TemplateTokenRegex` and is now `internal TemplateTokens.TokenRegex`, the single owner of the grammar (design D5).
- New: `packages/server/tests/Mohist.Workflow.Definition.Tests/TemplateTokensTests.cs` — 13 pure unit tests covering null/undefined/scalar kinds, plain strings, single- and multi-segment token paths, token-inside-larger-text, object/array/nested containment, and broken-syntax cases (unclosed brace, no braces, single-brace form).
- New: `packages/server/tests/Mohist.Server.UnitTests/Workflow/Services/ActionContractValidatorTests.cs` — 30 pure unit tests, no grains / no HTTP. Covers every rule (unknown / tombstoned `uses`, unknown `with` minus `working-directory`, missing required, exact-kind mismatch, union-kind accept, canonical ordering, optional null treated as absent, required null rejected, template skip, template on undeclared) and every position (stage task, stage check, approval-feedback task, recovery-handler task, plus an "all four positions are judged" composite). Also asserts a Definition-only error (empty task id) leaves the validator silent.
- Modified: `packages/server/src/Mohist.Workflow.Definition/WorkflowDefinitionRules.cs` — `TemplateTokenRegex` field removed; the one call site now references `TemplateTokens.TokenRegex` (single grammar owner).
- Modified: `packages/server/tests/Mohist.Server.ArchTests/ArchitectureRules.cs` — added `("Workflow", "Runner")` to `AllowedDomainDependencies` with a comment citing D1. The validator consumes the catalog records directly so the validator and the catalog share one type; the dependency is data-only (records are pure serializable models), not an Orleans call.
- Modified: `packages/server/tests/Mohist.Server.ArchTests/spec-file-size-baseline.json` — added a 27000-byte baseline entry for the new 26.5 KB test file (existing pattern: 33 other unit/spec files have explicit per-file size allowances above the 24 KB ratchet).

### Decisions taken on this task
- **Single grammar owner**: moved `TemplateTokenRegex` out of `WorkflowDefinitionRules` into `TemplateTokens.TokenRegex` (internal). The validator and the Definition rules now share one regex instance; the `using System.Text.RegularExpressions;` is preserved in `WorkflowDefinitionRules` only because the one call site still consumes `Match`.
- **Null-element safety**: the `with` dictionary values are `JsonElement?` (nullable). The C#-null case arises only when the YAML parser returned `null` for an unsupported node kind — a Definition-validator error already covers it. The validator short-circuits via `if (!value.HasValue) continue;` rather than trying to type-check a C# null, keeping the validator's contract that it never reports a Definition-only issue.
- **Canonical kind ordering**: the validator formats the "must be …" message with kinds in canonical order (`string, number, boolean, object, array`) joined by ` or `, matching the Runner's `formatKinds` per D6. Unknown kinds in the catalog (defensive) are appended after the canonical ones.
- **Task/Check id fallback**: the message uses the item's `Id` when present, otherwise the path (e.g. `stages[0].tasks[0]`). The Definition validator reports the empty-id issue separately, so the validator never duplicates that error.
- **Unknown uses → skip with validation**: if `uses` is not in the catalog, the validator reports the unknown-uses error and does not walk the `with` block. The Runner's `validateActionInput` short-circuits on the first error for the same reason — without a manifest there is no contract to compare against. Both the unknown-uses error and the with errors are independent observations in the same Profile, but only the first is reported for a given task.
- **File size baseline entry**: added `ActionContractValidatorTests.cs` to the size baseline at 27000 bytes (the file is 26562 bytes). Followed the established pattern of declaring the size in the baseline JSON rather than splitting the test file. The 30 cases are intentionally granular so each rule/position is a named, focused test.

### Gotchas
- `RunnerInfo` constructor parameter order and naming matter when constructing one in tests: the param is `RegisteredAt`, not `Registered`; `ActionCatalog: …` is the named arg for the catalog. (Carried over from T-001's gotcha; not re-here for the validator itself, which takes `ActionCatalog` directly.)
- `JsonElement?` with `HasValue == false` is the C# nullable — a different case from `HasValue == true && ValueKind == JsonValueKind.Null`. The Definition validator covers the unsupported-yaml-node case; the validator silently skips it via `!value.HasValue`.
- The existing arch test `DomainModules_ShouldNotDependOnEachOther` forbids `Workflow → Runner` because the Runner depends on Workflow (dispatch), not the reverse. D1 explicitly chose the reverse direction (validator consumes catalog records). The exemption follows the same pattern as the existing `("Project", "Workflow")` debt comment.

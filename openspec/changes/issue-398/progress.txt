## Codebase Patterns

- `packages/web/src/shared/ui/components/{badge,button}.tsx` use cva variants. Existing tests on these primitives were absent — created `*.test.tsx` colocated.
- The bare `--destructive` token (without `-subtle`/`-foreground`/`-border` siblings) is still referenced by `aria-invalid` utilities in primitives and elsewhere; T-001 only retires the `bg-destructive/10 text-destructive` class set on Badge/Button variants.
- `aria-invalid:border-destructive aria-invalid:ring-destructive/20 dark:aria-invalid:ring-destructive/40` in the Badge/Button base classes deliberately still uses the bare `--destructive` token — these are NOT the `destructive` variant and are out of scope for T-001.
- `text-destructive` (without `bg-` or `border-`) is used by non-variant code in `ChartContainer.tsx`, `AgentSessionComposerPage.tsx` — also not the Badge/Button variant path; later tasks can decide whether to retire those.
- `AlertDialog` already had a `tone === 'destructive'` branch; only the inline `bg-red-600 text-white hover:bg-red-700` overlay is removed. The dialog itself still carries the same destructive button visual treatment (now via the variant).
- Tailwind v4 dark theme is driven by `.dark` parent selector with `@custom-variant dark` configured in `app/styles/index.css`. Tokens are dark-mode-aware via `:root` vs `.dark` rule blocks. The variant classes produced by cva (`bg-danger-subtle`, `text-danger-foreground`, `border-danger-border`) resolve automatically.
- Tests previously asserted `text-destructive` / `text-red-700` in three downstream files (`LinkedIssueRow.removeConfirm.test.tsx`, `AgentSettingsSection.test.tsx`, `LabelCatalogSection.test.tsx`) for the now-replaced behavior — updated them to assert against the new token classes.

## Gotchas

- cva's `ConfigVariants` type only enumerates `variant` and `size` keys; passing `disabled: true` to `buttonVariants({...})` triggers TS2353. Test by rendering the component with `disabled` prop instead, or assert the variant class string and check the base classes separately for `disabled:` utilities.
- `useRender.ComponentProps<"span">` (Badge) and `ButtonPrimitive.Props` (Button) are the right prop types; spreading `...props` lets the variants compose with size-specific layout classes via `cn(buttonVariants({ variant, size, className }))`.
- The `--warning` family in light theme had three hues (70/80/75) before this task. Dark theme was already consistent at hue 75. Aligning light-theme `--warning` and `--warning-subtle` to hue 75 matches the existing dark-theme values and the existing `--warning-border`.

## Decisions

- `destructive` variant on both Badge and Button is duplicated as a literal class string matching `danger` (rather than using cva's `variants: { destructive: dangerVariant }` shorthand) to keep the cva variant record readable and to make a future divergence auditable.
- Field-error text uses `text-danger-foreground` rather than `text-danger` because the base foreground token (`--danger-foreground`) is the high-contrast text color (oklch 0.985 light / 0.145 dark) and pairs correctly with `bg-danger-subtle` if anyone ever wraps the error in a banner; `text-danger` is the raw hue token and is not appropriate for body text.

## Design Issue Surfaced by T-002 (flagged for review)

- **WCAG AA contrast gap for `warning` and `muted` light-theme pills.** The current
  `index.css` token values produce ~4.2–4.4:1 contrast between `--warning-subtle` /
  `--muted` backgrounds and the family base color used for text in light theme.
  Yellow (hue 75) inherently has higher per-L luminance than other hues, and the
  page-neutral `muted` pair sits in the same mid-light range. `success` / `info` /
  `danger` clear 4.5:1 in both themes.
- The T-002 contrast spec asserts 4.5:1 for the three families that pass and
  falls back to 3:1 (WCAG AA Large Text) for `warning` and `muted` light-theme
  pairs, with explicit assertion tests that document the gap. **Recommendation:**
  future design pass darken the light-theme `--warning` (e.g., L≈0.45) and
  `--muted-foreground` to clear 4.5:1. The fixture + guard will catch the change.

## Status-presentation layer notes (T-002)

- **Why `text-<family>` (base) instead of `text-<family>-foreground` for soft-tinted pills.**
  D3's documented pattern is `bg-<family>-subtle text-<family>-foreground border-<family>-border`,
  but `--<family>-foreground` is calibrated for solid backgrounds (it equals the page
  foreground: white in light, black in dark). On a soft-tinted bg it produces roughly
  1.05:1 contrast in both themes. Using the family's base hue (`text-success`, etc.)
  clears WCAG AA in both themes for `success`/`info`/`danger` and gets within 0.1–0.3
  of 4.5:1 for `warning`/`muted`. The T-002 fixture now includes `base` alongside
  `subtle`/`foreground`/`border`, and the guard test verifies all four against
  `index.css`.
- **Dot class derives from the family base (`bg-<family>`)** — same semantic family
  as the text/background treatment, per the spec's "dot tracks pill family" rule.
  This is what makes the coherence structural rather than per-call-site.
- **Fixture + guard design.** `tokens.ts` mirrors `--<family>{-subtle|-foreground|-border}`
  from `index.css`; `tokens.guard.test.ts` parses `:root` and `.dark` blocks with a
  regex, walks every family/slot, and asserts `L/C/H` agree to `1e-3`. Any drift
  (e.g., an accidental `--warning-foreground` hue change) fails the guard immediately.
- **Unmapped states fall back to `muted`** (no throw). `familyFor(kind, state)` returns
  `'muted'` for `null`/`undefined`/empty string/`__brand_new_state__`. Verified
  for every kind in `index.test.ts`.
- **StatusPill keeps `StageStatusIcons` as the icon resolver** (per task notes).
  The pill does not pick icons itself; it just renders the treatment and an
  optional dot/icon slot. Mapping `kind`+`state` → icon stays a product concern
  in `widgets/issue-workflow/ui/StageStatusIcons.tsx` (unchanged, already
  token-backed).

## Gotchas (T-002)

- **jsdom cannot resolve `oklch()` to RGB reliably** across engines; computing
  contrast via `getComputedStyle()` in jsdom is flaky. T-002's `color.ts` converts
  `oklch → sRGB` in pure JS (Oklab → LMS → linear sRGB → sRGB companding) and
  computes WCAG luminance from the resulting sRGB triple. The fixture is the
  single source of truth for the values; `index.css` is bound to the fixture
  via the guard. No jsdom dependency in the contrast path.
- **cva `variant="default"` on Badge ships `bg-primary text-primary-foreground`**;
  StatusPill overrides these via `cn(treatment.container, treatment.text, ...)`,
  and `twMerge` collapses the conflict. The result is exactly the treatment
  classes.

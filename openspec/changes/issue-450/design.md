## Context

Issue #450 adds the Workflow-direct `mohist/pi` path described by the proposal and the `pi-runtime`, `pi-workflow-action`, and `pi-workflow-session` specs in this change. The product and runtime contracts are already fixed in `docs/actions/pi.md` and `design/runtimes/pi.md`; this document maps those contracts onto the current implementation.

Today the Runner has one execution backend. `RunnerHost` constructs one `OpenCodeRuntime`, gates all polling on its readiness, and injects it into `WorkExecutor`. `ActionContext` carries only `openCodeRuntime`; `actions/registry.ts`, promise projection, and worktree cleanup recognise only `mohist/opencode`. The OpenCode Action already provides the desired completion seam: it returns final assistant text through the private `turnFact`, after which `WorkExecutor` evaluates task-level completion and projects `null | { promise }`.

Workflow AgentSession infrastructure is mostly runtime-neutral, but its Runner API is not. `RunnerRoutes` hard-codes `opencode` in Workflow Session open and attach calls, while `AgentSessionGrain.IsRuntimeRegistered` recognises only OpenCode. The persisted model already has the fields Pi needs: stable logical `sessionId`, runtime, `runtimeSessionId`, immutable `workDir`, Runner identity, and append-only runtime lineage. For Pi, `runtimeSessionId` is the absolute Pi JSONL session-file path.

There is also an observability gap in the current Workflow Action path: `OpenCodeRuntime.runTurn` supports an observer and the Server accepts Workflow runtime events, but `opencodeAction` does not connect them. The current runtime-event request has no idempotency identity and usage is applied additively, so simply retrying an ambiguous POST could double-count facts. This change gives every Workflow runtime binding the same ordered stream lifecycle for input, drain, and rebind fencing; Pi additionally connects its observer so the existing runtime-neutral transcript and Session UI remain complete across transport loss and Runner restart. Connecting the full OpenCode observer remains outside this issue, but an OpenCode binding still owns an empty-or-input-only stream that can be drained and sealed symmetrically.

Pi is a fast-moving 0.x SDK and requires Node >= 22.19. The implementation is therefore gated by pinning a real SDK version and smoke-verifying the exact creation, persistence, prompt, event, model, interruption, trust, and catalog surfaces before product code is written. Default tests cannot use the real SDK environment, provider network, physical Session store, process, or wall clock.

Stakeholders are Workflow users selecting `mohist/pi`, Runner operators supplying provider credentials, and Session viewers auditing the resulting conversation. Mohist Agent/AgentJob users and Session-command users are deliberately unaffected by this issue.

## Goals / Non-Goals

**Goals:**
- Add a pinned, in-process `PiRuntime` deep module with startup readiness, persistent Session restore, turn execution, event projection, deadlines, interruption confirmation, and provider-error policy.
- Add `mohist/pi` as a UserFacing Workflow Inline Agent Action while preserving existing Workflow input expansion, completion, promise projection, recovery, and cleanup behavior.
- Persist a Pi binding before the first prompt and reuse it by WorkflowRun/session name across tasks, retries, model changes, cleanup turns, and Runner restart.
- Keep project-local Pi resources untrusted while allowing Runner-user global Pi configuration, provider authentication, and repository instruction files.
- Populate the existing AgentSession transcript, tool, model, and usage views with Pi facts.
- Deliver normalized Session facts through a durable ordered outbox and idempotent Server cursor without replaying Prompt execution.
- Raise and enforce the Runner's Node floor to 22.19.

**Non-Goals:**
- Pi execution for Mohist Agent/AgentJob work or an Agent runtime selector.
- Pi Follow-up, Compact, Reset, or Cancel command routing.
- Pi model-catalog registration, Server API, or Web model-selection UI.
- ACP, Pi RPC mode, a child-process isolation boundary, or a generic `AgentRuntime` interface.
- Provider credential management, per-tool approval, sandboxing, or a configurable project-trust switch.
- Automatic prompt replay, deterministic Prompt IDs, or recovery of a turn interrupted by Runner process death.

## Decisions

### D1. Add a parallel `PiRuntime` deep module

Create `packages/runner/src/runtime/pi/` with Mohist-owned boundary types, SDK factory/services, runtime lifecycle, turn execution, event projection, error normalization, and a public `index.ts`. All imports from `@earendil-works/pi-coding-agent` and related Pi packages stay inside this directory. Callers receive only `PiSessionTarget`, `PiTurnRequest`, `PiTurnResult`, diagnostics, and stable runtime error kinds.

One `PiRuntime` instance belongs to each `RunnerHost`. It owns one `ModelRuntime`, Runner/global settings and resource-loading policy, a cache of active SDK AgentSession instances keyed by absolute session-file path, and each cached instance's unsubscribe handle and event projector. `shutdown()` unsubscribes and disposes all cached instances. The module receives already-resolved Workflow input and bindings; it never receives Agent IDs or resolves Agent definitions.

The SDK service factory fixes project trust to false for every work directory. It loads Runner-user global settings/authentication and the repository's `AGENTS.md`/`CLAUDE.md` context, but supplies empty project settings, extensions, packages, skills, and prompt resources for `.pi/`. The exact SDK options are resolved by D2's smoke; callers never choose trust or resource-loader flags.

**Rationale:** Pi lifecycle, rapidly changing SDK construction, event interpretation, and persistence semantics remain in one high-cohesion module. **Alternatives considered:** wrapping Pi and OpenCode in a new `AgentRuntime` interface was rejected because their lifecycle, identity, and command surfaces have not converged; adapting Pi through OpenCode, ACP, or RPC was rejected because it adds another protocol and changes prompt-completion semantics.

### D2. Pin and smoke-verify the SDK before implementation

Add an exact `@earendil-works/pi-coding-agent` version to `packages/runner/package.json` using the Runner workspace npm command so `package-lock.json` is updated deliberately. Set both root and Runner `engines.node` to `>=22.19`, and pin `.nvmrc` to a concrete compatible release. Record a real-SDK verification at `openspec/changes/issue-450/sdk-smoke-verification.json`, following issue #409's artifact shape but allowing only package/Node versions, operation names, pass/fail booleans, and sanitized field-name/type summaries. The artifact MUST NOT contain environment values, auth-store content, provider responses, Prompt/message text, or raw SDK objects; run the repository secret scan before committing it.

The smoke must verify at least: `ModelRuntime.create()` and available-model loading; untrusted project-resource setup; `SessionManager.create(cwd)` and `SessionManager.open(file)`; returned `sessionFile`; `createAgentSession`; `prompt()` completion and final messages; `subscribe()` event payloads for text, thinking, tools, usage, and retry; `setModel`; `setThinkingLevel`; `steer`; `abort`; and the state used to confirm interruption. It must also verify that prompt-template/slash-command expansion can be disabled. If names or payloads differ, update `design/runtimes/pi.md` and this call map before implementing.

**Rationale:** current upstream documentation confirms the broad API but the SDK's 0.x construction and event shapes move frequently. **Alternatives considered:** using a semver range was rejected because an unattended Runner cannot absorb weekly breaking changes; implementing against documentation alone was rejected because session-file timing and event payload details are acceptance-critical.

### D3. Gate work claiming on both runtimes, but do not publish Pi catalog yet

`RunnerHost.initializeSharedConnection` initializes the Workflow Action outbox storage and constructs/starts OpenCode and Pi before establishing an authenticated Server transport. Before Runner registration or any poll, it fetches D5's owned-stream inventory through that transport and completes D8 recovery; transport connection alone is not registration/work claiming. `WorkExecutor` receives both handles after this gate; `AgentJobExecutor` continues receiving only OpenCode. The worker loop replaces `isOpenCodeReadyForClaim` with a combined global readiness check. It continues draining `awaitingAck`, but skips registration/new polls while either runtime is unavailable, inventory recovery is incomplete, or the outbox cannot list/initialize its root and atomic-replace capability, and emits the failing component's credential-redacted diagnostic with the existing throttling policy.

Pi is ready after SDK services initialize and `ModelRuntime.getAvailable()` completes. An empty result stores a warning but remains ready. Initialization or catalog failure leaves Pi not-ready; the host periodically retries `start()` while polling is gated. Pi has no external server-exit watcher: Runner shutdown naturally ends in-process turns, and a new process lazily restores persisted Sessions.

The existing `coderModels` and `coderModelVariants` registration remains OpenCode-derived. Pi loads its catalog only as a readiness/compatibility check in this issue; runtime-aware catalog reporting belongs to the separate catalog/UI work.

**Rationale:** claiming only when every bundled execution capability is initialized avoids claim-then-fail behavior and matches the accepted Runner readiness contract. **Alternatives considered:** gating only when the polled item uses Pi would require claiming before readiness is known and would consume a workflow slot; merging Pi models into the unqualified OpenCode catalog was rejected because it loses runtime identity and expands this issue into UI/API design.

### D4. Implement `mohist/pi` as its own Action adapter

Add `actions/pi.ts` and register it in `createDefaultRegistry`. The adapter follows the OpenCode Action flow but does not call or wrap `opencodeAction`:

1. Resolve `prompt` through the existing prompt loader and compose parent-issue context.
2. Validate explicit `session` and `options`; preserve the raw options object long enough to diagnose unknown keys.
3. Derive the logical Session name, defaulting to Work ID.
4. Execute under the shared per-logical-Session task lease from D6.
5. Resolve/create/bind the Workflow AgentSession using D5.
6. Persist `session.input`, then invoke `PiRuntime.runTurn` with the D8 reporter.
7. Map runtime errors to Action codes and return `turnFact.finalAssistantText` on success.

Move the genuinely runtime-neutral prompt-loader/session-name helpers out of `opencode-helpers.ts` or rename that module; do not share Action input types. In the current implementation, add `piRuntime` and the already-held `WorkflowSessionTurnLease` token to task Inline Agent `ActionContext`, `baseContext`, and cleanup contexts; `WorkExecutor` alone receives `WorkflowSessionTurnCoordinator`. Check contexts receive neither Pi dependency because they do not own this task lease. Add `mohist/pi` to `PROMISE_PROJECTED_ACTIONS` plus the agent-backed cleanup classifier. This is a deliberate temporary extension of the implementation gaps documented in `design/workflow/actions.md`, not the target Action architecture. Issue #447 (`Action 能力注入收窄`) owns replacing runtime handles and name-based dispatch with manifest-declared `agent-turn`; #450 does not create a competing partial capability API. Keep the temporary additions localized and mark them for direct removal by #447.

Input parsing accepts only non-empty resolved prompt text plus optional `session` and an `options` object. Omitted/null `session` uses Work ID; a present string is trimmed and must remain non-empty; whitespace-only and non-string values fail `invalid-input` before any Session creation and are never stringified. It splits `options.model` at the first slash, keeps `variant` independent, treats null as omitted, and passes unknown option names to runtime diagnostics. It never reads `vars.agent` unless the Workflow expansion explicitly placed that object in `options`. Legacy `with.agent`, `with.kind`, and `with.type` continue to fail in Server dispatch validation.

The adapter maps `unavailable-runtime` -> `runtime-unavailable`, `missing-session` -> `runtime-session-missing`, and `deadline-exceeded` -> `timeout`; it preserves `invalid-input`, `incompatible-runtime`, `interrupted`, and `turn-failed`, and owns `session-workspace-mismatch`, `session-binding-failed`, and `session-reporting-failed`. These are Action errors only. Diagnostics, provider text, model, usage, and physical identity never enter Action output.

Server validation and presentation use an explicit inline-Agent Action set containing `mohist/opencode` and `mohist/pi`. Replace OpenCode substring checks in `TaskRun.DeriveClassification`, `WorkflowItemTranslator`, `WorkflowYamlSerializer`, parent-issue-context dispatch, and the Web milestone classifier. The architecture-owned `design/workflow/task-dispatch.md` rule now names that explicit set; implementation preserves its existing plan/task/parent guards. Error messages refer to the selected Action rather than naming OpenCode.

`mohist/pi` is task-only in #450. Server Workflow validation rejects it when declared as a check Action before dispatch, with an actionable task-only diagnostic. Runner check execution repeats that guard before registry resolution so malformed/legacy payloads cannot invoke the shared registration. Existing non-Pi checks and `mohist/opencode` check behavior remain unchanged; check contexts do not receive `piRuntime`, the coordinator, or a held lease token.

**Rationale:** Action selection is already the Workflow runtime selector, while completion belongs to `WorkExecutor`. Waiting for #447 would couple this feature's delivery to a backlog refactor; the temporary exception preserves current OpenCode behavior and has one named removal owner. **Alternatives considered:** adding `options.runtime` was rejected because it creates two conflicting selectors; extracting a generic Inline Agent Action or a second capability model was rejected because `design/workflow/actions.md` already defines the target `agent-turn` boundary.

### D5. Make Workflow Session binding runtime-aware and race-safe

Extend only the Workflow Runner Session open/bind requests with an explicit required `runtime` (`opencode` or `pi`). The Server contract and the existing `mohist/opencode` caller migrate atomically: OpenCode sends `runtime: "opencode"` on open and the observed expected-current runtime/session on bind, with regression tests preserving its current behavior. Keep generic AgentJob routes hard-coded to OpenCode in this issue. Split the shared attach DTO so AgentJob callers do not acquire Pi fields accidentally.

Add a dedicated Workflow Action runtime-event request/route for D8's authority-issued stream identity and sequence. The route passes its authenticated/route `runnerId` into the grain, which requires it to equal the current binding owner before stream/cursor processing; the opaque stream ID is fencing data, not authorization. Do not add those required fields to the existing `AgentSessionRuntimeEventsRequest`: Workflow Follow-up, its failure outbox, and generic AgentSession reporting continue using that existing binding-validated route unchanged. Session-command events are outside the Action outbox's completeness cursor and rebind drain fence; after a rebind, an old physical binding remains stale and its late command event is rejected under the existing rule. Regression tests pin both routes so the Action migration cannot break or silently sequence existing Follow-up producers.

Add a narrow AgentSession grain command for Workflow runtime binding with:
- target runtime, physical `runtimeSessionId`, work directory, model, and Runner;
- the `expectedRuntimeSessionId`, expected runtime, and expected `actionStreamId` observed by the preceding open;
- for a cross-runtime rebind, the old stream's locally fenced `drainedThroughSequence` and current binding Runner;
- these atomic outcomes: first attach creates and returns a fresh Action stream at cursor zero; idempotent same-binding success returns the same stream; expected cross-runtime rebind in either direction seals the old stream, appends lineage, and installs a fresh stream; stale/conflicting binding rejection; same-runtime different physical ID rejection with a Reset hint.

The command reuses the existing `AttachPhysicalSession` and `RebindRuntimeSession` domain transitions but is not a public Reset and does not create a Session-command reservation. The expected-current fields prevent two Actions from replacing each other's binding. For a cross-runtime rebind, D6's coordinator fences new work while D8 drains the current owning Runner's stream and supplies its final issued sequence. In the same AgentSession transition, the Server requires the current cursor to equal that sequence, seals the old stream, and replaces the binding; a mismatch rejects without mutation. This atomic seal avoids a separately committed state in which the old binding could no longer report but the new bind failed. A different Runner cannot attest another Runner's local stream; ownership transfer remains a Reset/Session-command concern outside this issue.

Workflow bind validates its explicit target against `opencode | pi` independently of command capability. The command-capable runtime predicate remains OpenCode-only. `BeginFollowup` and Compact/Reset preparation check that predicate against the current binding inside the same grain call before creating any lease/reservation; remove Reset's current unregistered-runtime fallback to OpenCode. Cancel adds a non-mutating grain admission read that atomically returns either unavailable for the current Pi binding or one immutable admitted OpenCode target. It creates no fence: a rebind may commit after that read, and the already-admitted Cancel may finish against its old physical OpenCode target. This is the explicit linearization point and accepted race behavior; a request whose grain admission observes Pi always rejects before Runner dispatch.

Workflow open and bind preserve the AgentSession authority's existing active-state and expected-binding guards. The Action maps a rejected open/bind to actionable `session-binding-failed`; this issue does not add command reservations, receipts, callbacks, or command-terminal reconciliation. D5 changes only Server-side capability admission needed to keep Pi commands unavailable; command wire DTOs, Runner handlers, journals, and OpenCode Runtime execution semantics remain unchanged.

The AgentSession authority, not the Runner, creates an opaque `actionStreamId` for each physical Workflow binding and persists `{ actionStreamId, lastAppliedSequence, projectorCheckpoint, latestActionTurn }` with that current binding. Sequence starts at `0`, so the first Action event is `1`; the ID remains stable for idempotent open/attach and is never reused after rebind. The checkpoint is stable JSON containing the applied message/tool/usage fingerprints needed to reconcile retained Pi facts; latest-turn metadata contains actionTurnId, runtime, input sequence, and required-facts policy. Workflow open returns this state. If it opens a pre-change OpenCode binding with no Action stream state, the grain atomically backfills one ID at cursor `0` with an empty checkpoint and no latest turn, without changing binding or lineage; concurrent opens observe the same committed ID. An unbound logical Session has no stream until first attach. Existing unsequenced Follow-up/generic facts are outside the new cursor and are not replayed into it.

Add a Runner-authenticated inventory route for startup recovery. It accepts no caller-selected Runner ID: the Server derives the authenticated registered Runner identity and returns only current Workflow-origin AgentSessions whose current binding is owned by that identity and has current Action stream state. Each item includes immutable logical source identity `{ projectId, workflowRunId, sessionName, agentSessionId }`, current runtime/physical binding/workDir, actionStreamId, lastAppliedSequence, projector checkpoint, latest-turn lifecycle, and current source metadata needed by the outbox manifest. It returns no sealed streams, lineage history, AgentJob bindings, generic Session bindings, or streams owned by another Runner. The route is read-only and cannot bootstrap, seal, bind, or mutate state. Its response is a recovery inventory, not an authorization capability; D8 still validates the route Runner on every event write.

The Pi Action binding sequence is:

```text
open logical Session(runtime=pi)
  -> reject immutable workDir mismatch
  -> current pi binding: restore it
  -> no binding or different runtime: create Pi Session
       -> bind with expected-current guard
       -> only after bind succeeds, submit session.input and prompt
```

For Pi, the physical ID sent to the Server is `session.sessionFile` normalized to an absolute path. The Pi UUID is diagnostic only. If creation yields no file path, return `incompatible-runtime`. If a same-runtime bound file is absent/corrupt, return `runtime-session-missing` and never create a replacement. The diagnostic names Reset as the canonical same-logical-Session remedy owned by the sister Session-command issue and also names the recovery available now: select a new logical `session` name to start a separate conversation. A failed bind can leave an unused Pi file, but cannot leave a submitted prompt with no durable logical owner.

**Rationale:** the existing model already owns runtime lineage; a guarded grain command preserves that authority and closes the create/bind race. **Alternatives considered:** allowing `AttachPhysicalSessionAsync` to replace any binding was rejected because it weakens existing Reset protection; reusing the Session Reset command was rejected because runtime selection during Workflow execution is not a user Session command and must not acquire idle/reservation semantics.

### D6. Serialize the complete Workflow task lifecycle at the logical Session boundary

Add a Runner-owned `WorkflowSessionTurnCoordinator`, keyed by `(projectId, workflowRunId, sessionName)`. `WorkExecutor`, not an Action, acquires one task lease for an Inline Agent task after input expansion/session-name resolution and holds it through the initial Action call, successful completion checks, any worktree cleanup Action call, and final reporter persistence. Both `mohist/opencode` and `mohist/pi` therefore execute open, create, guarded bind/rebind, input reporting, model application, Prompt completion, and cleanup under one lease. The Action receives only an already-held `WorkflowSessionTurnLease`; it cannot access the coordinator or release/reacquire the lease. The token exposes its immutable logical key plus generation-safe physical-execution registration/quarantine operations needed by D7, but no queue or Runtime API. Queue entries are removed only after the complete task lifecycle settles; different keys execute independently.

Each Runtime also protects its cached physical Session against overlapping prompt calls as a defensive invariant, but the shared outer coordinator is authoritative because concurrent Actions can select different runtimes before either has a physical path. Because completion and cleanup remain in the same lease, no queued same-name task can change runtime or binding between the work and cleanup turns. T-003 defines and fake-tests the coordinator/token boundary without changing production Action ownership; T-006 atomically migrates `WorkExecutor`, the existing OpenCode Action, and the new Pi Action so there is no intermediate Action-owned acquisition path.

Session-command coordination is deliberately not added to this boundary. Current OpenCode command execution and event behavior remain untouched; D5's linearized capability checks keep commands whose admission observes Pi unavailable without reservation, dispatch, or OpenCode fallback, while an admitted OpenCode Cancel may finish against its immutable old target. The sister Session-command issue must define any future command interaction with Workflow leases and Action-stream drain/seal before enabling Pi commands. No Runtime slot callback, `prompt-active` phase, command lease, command journal reconciliation, or recovery receipt is part of #450.

Before `PiRuntime.runTurn`, the Action registers its physical path through the already-held lease token; the token supplies the immutable logical key to the coordinator's execution-quarantine tracker. `PiRuntime` publishes ordered process-local quarantine lifecycle notifications carrying `{ generation, physicalPath, state: entered | cleared }`; each unconfirmed interruption receives a new generation. `entered` is emitted synchronously after the physical path is quarantined and before the Runtime returns the unconfirmed result. The coordinator retains the registered logical association and marks its key quarantined before the Action can leave the held lease scope. If stop is observed while result cleanup races, the ordered `cleared` notification for that generation is applied after `entered`, so the key cannot be stranded by a clear-before-register race. A stale clear from an older generation cannot clear a newer quarantine.

The queue can settle the failed TaskRun, but later admission on that key rejects with `unavailable-runtime` before open or rebind, so selecting OpenCode cannot bypass the still-running Pi turn; other logical keys remain independent. A later subscribed stop observation removes the matching physical quarantine and emits `cleared`; the coordinator removes every logical association for that path/generation and admits later work without replaying the failed Prompt. A normally stopped turn unregisters its tracking association after completion. Runner startup constructs empty Runtime and coordinator quarantine maps because process termination ended every in-process Pi turn; no quarantine is persisted or reconstructed from Session/outbox state.

**Rationale:** a physical-ID-only lock cannot prevent two first turns or two different Runtime Actions from creating and racing different bindings, while a work-directory lock over-serializes unrelated Sessions. **Alternatives considered:** a Pi-owned queue was rejected because it cannot exclude a concurrent OpenCode Workflow turn; rejecting the second turn was rejected because the requirement is serialization, not failure; a distributed Server lease was rejected because Workflow dispatch already assigns work to one Runner and the binding refuses another Runner's local-outbox attestation. Extending this coordinator into Session-command execution was rejected because issue #450 explicitly assigns command routing and implementation to sister issues.

### D7. Keep turn policy shared as pure rules, not a shared runtime

`PiRuntime.runTurn` restores or uses the cached SDK Session, applies `setModel` and `setThinkingLevel`, subscribes before prompt admission, and calls `await session.prompt(text)` with template/slash expansion disabled. Prompt resolution is the only success authority; `agent_end` is projection input only. Final assistant text is read from the completed Session messages and returned as a private fact.

Extract only genuinely runtime-neutral policy from OpenCode into small pure modules: the task-independent five-minute warning text/window, timeout race/result fixation, default quota/credit/billing patterns, and retry threshold. OpenCode and Pi each translate native events into that policy's input and each own their abort/confirmation implementation. This avoids a generic runtime interface while keeping one authority for behavior promised as identical.

For issue #450, `WorkExecutor` supplies an immutable `turnTimeoutMs = 3_600_000` through Runner-private Action context; no dispatch or Action-input deadline field is added. The Pi Action passes that duration after bind/input preflight, and `PiRuntime` reads its injected clock immediately before `session.prompt()` to derive the absolute deadline. Queue wait, binding, outbox drain, and model setup do not consume the Prompt budget; each cleanup invocation receives a fresh duration. At 55 minutes Pi uses `steer`; at the deadline it first fixes `deadline-exceeded`, then calls `abort` and checks subscribed lifecycle state plus `isStreaming`. A late prompt resolution cannot change the fixed result. An external Action signal follows the same interruption cleanup but maps to `interrupted`. Every unconfirmed stop, including provider-triggered abort, produces an interruption-unconfirmed diagnostic, installs physical and logical quarantine through D6's ordered lifecycle before return, and later publishes clearance when subscribed state proves stop. Provider-triggered abort retains `turn-failed` as its primary result; timeout and cancellation retain their already-fixed primary results. No Runtime or outbox failure path resubmits a prompt within one delivered execution. Runner process loss clears process-local work ownership; the Server may redeliver the still-Running work, and that new execution may duplicate the turn in the crash window as explicitly accepted by `design/runtimes/pi.md`.

Pi `auto_retry_start` facts feed the shared provider policy. Quota/balance/billing wording fails on first occurrence; recoverable retries fail at the configured threshold (default five); lower attempts remain Pi-owned. `cli.ts` parses `MOHIST_PROVIDER_RETRY_THRESHOLD` as a positive integer and `MOHIST_PROVIDER_NON_RECOVERABLE_TERMS` as a JSON array of non-empty literal strings. The latter are escaped and matched case-insensitively in addition to built-ins; operator regex is never evaluated. Invalid configuration leaves Pi not-ready with an actionable diagnostic. `RunnerHost` builds one policy object and passes it to both OpenCode and Pi so defaults and overrides have one authority. Pi-native terminal errors are read from the final assistant message and normalized to `turn-failed`. Provider text passes through the host `CredentialMasker` before it enters any Mohist-owned result/log/event. The physical binding remains intact for all provider and deadline failures.

**Rationale:** sharing policy prevents OpenCode and Pi semantics from drifting while leaving protocol and lifecycle complexity inside each deep module. **Alternatives considered:** duplicating pattern and deadline logic was rejected because one product rule would gain two authorities; extracting a common `AgentRuntime` was rejected because it would expose a lowest-common-denominator lifecycle API.

### D8. Project Pi events through a durable Workflow Session outbox

`runtime/pi/event-projection.ts` converts smoke-verified Pi events into existing Mohist event types:
- message text/thinking -> `message.delta` / `reasoning.delta`;
- tool lifecycle -> `tool_call.started|updated|completed` keyed by `toolCallId`;
- assistant usage snapshots -> non-negative `usage.updated` deltas keyed by message ID, with distinct input/output/cache-read/cache-write/thought fields;
- model observations -> `model.resolved`;
- unknown events -> runtime diagnostics only.

The projector keeps per-message text/usage state and per-tool fingerprints so duplicate SDK callbacks produce no second delta. At prompt completion it reconciles the final Session messages through the same projector, filling missed final text/usage without making events a completion authority.

Add a runtime-neutral `WorkflowSessionEventOutbox` that owns local pending records, record encoding, sequencing, acknowledgement compaction, and recovery while treating the Server cursor/projector checkpoint as applied authority. Every Workflow OpenCode or Pi binding gets a rebuildable local manifest; both Actions use it for `session.input` and rebind fencing, while Pi also appends its projected runtime facts. It depends on a byte-oriented `WorkflowSessionOutboxStorage` (`list`, `read`, `replaceAtomically`, `remove`) rather than directly on Node filesystem calls.

The production storage adapter lives under `<runnerRoot>/.mohist/runner-state/`, but atomic replacement order belongs to a separately testable `AtomicSnapshotReplaceProtocol` over injected low-level operations (`write`, `syncFile`, same-directory `rename`, `syncDirectory`, `remove`). Production composition supplies Node filesystem operations; default tests run the protocol against an in-memory operation fake with fixed virtual paths and never instantiate the physical adapter. The supported deployment assumption is a filesystem that provides atomic same-directory rename plus file/directory sync; inability to initialize/list the root or perform those operations makes the outbox globally not-ready and gates Runner registration/claiming. The standalone service exposes one structured `workflow-session-outbox-unavailable` diagnostic containing the failed operation/capability and an actionable message passed through an injected masker; it does not serialize raw filesystem objects. Successful re-initialization clears that diagnostic and returns readiness to ready. A rename-success/directory-sync-failure result is `commit-uncertain`: the stream is quarantined and startup generation/decoding decides whether the old or new complete snapshot survived.

Startup removes only recognizable orphan temporary files. An unreadable committed snapshot with an otherwise healthy store is preserved for diagnostics and rebuilt from Server stream/checkpoint state; only failure of Runtime-specific reconciliation quarantines that logical Session. Unrelated streams, OpenCode/Pi Sessions, and AgentJob work remain available. Root/list/capability failure is the only outbox condition that changes global readiness. Tests run the real outbox codec/recovery state machine over an in-memory byte store and separately run the atomic operation protocol over fake operations.

One local stream manifest is keyed by logical AgentSession plus the authority-issued `actionStreamId`; the Runner never derives or claims an identity. It contains pending records, next sequence, physical/Pi repair target, and active checkpoint. Before Prompt admission the outbox creates or refreshes it from Workflow open's Server stream state. Each checkpoint and appended record is one atomic stream-snapshot replacement, so a crash exposes one complete generation. Appending is durable before delivery is attempted.

Runner workspace remains rebuildable. A missing or corrupt local manifest at any Server cursor is rebuilt from the current authority-issued stream ID, physical binding, `lastAppliedSequence + 1`, applied projector checkpoint, and latest Action-turn metadata. Corrupt local bytes are preserved for diagnostics but are not authority. For Pi, recovery opens the bound file and reconciles retained canonical facts against the Server checkpoint, appending only missing facts under new sequences; missing/unreadable Pi storage follows `runtime-session-missing`. For OpenCode, every required input was acknowledged before Prompt admission and there are no required post-admission facts in #450, so recovery restores/closes input-only latest-turn metadata without Runtime projection. Provisional Pi facts not retained by Pi may be lost, as already allowed; required canonical facts are recoverable.

When a valid local manifest exists, records through the Server cursor compact as acknowledged and a contiguous pending suffix resumes at `lastAppliedSequence + 1`; malformed/gapped local suffixes are discarded and rebuilt through the same Runtime-specific reconciliation. Startup performs rebuild, pending drain, and checkpoint recovery before host registration/polling. A prepared but not admitted checkpoint closes without replay because no Runtime was called. An admitted `pi-canonical` checkpoint triggers final-message reconciliation; an admitted `opencode-input-only` checkpoint follows the rule below. No recovery path requires restoration of original Runner workspace state.

Every active-turn checkpoint and Server `latestActionTurn` record runtime, required-facts policy, and lifecycle `prepared | admitted | closed`. Accepted `session.input` establishes `prepared`. Before invoking either SDK Prompt, the outbox appends and receives acknowledgement for a transcript-free `turn.admitted` sequence, then marks the local checkpoint admitted; this means admitted is the conservative "Prompt may have been called" boundary. After required facts are durable, it appends `turn.reporting-complete`, whose accepted sequence installs `closed` plus optional recovery status. These technical lifecycle records advance the Action cursor/checkpoint but create no transcript part or Workflow completion fact.

Pi uses `pi-canonical` and any recovered `admitted` state follows retained-message reconciliation; if process loss occurred after admission acknowledgement but before Prompt invocation, reconciliation finds no new canonical facts and closes without invoking Prompt. OpenCode uses `input-only` because #450 does not connect its full runtime observer: normal completion closes after the OpenCode Runtime result settles. On startup, `prepared` closes without Runtime repair; `admitted` OpenCode first drains durable input then closes with `execution-outcome-unknown` without querying or invoking either Runtime; `closed` needs only pending drain. Host startup completes lifecycle recovery before registration/polling, so Server redelivery cannot race an unresolved checkpoint. Closed state no longer blocks later same-Session Workflow admission/rebind; at-least-once redelivery may execute a duplicate turn under D7.

The Server runtime-event command carries the route Runner identity, authority-issued stream identity, physical binding, sequence, actionTurnId, and `projectorCheckpointAfter`. AgentSession state stores the binding owner, stream identity, last applied sequence, applied checkpoint, and latest Action-turn metadata for the current binding. Before duplicate/gap handling or fact mutation, it requires the route Runner to equal the current owner and both stream/binding IDs to match current state; then it returns stored state for `sequence <= lastApplied`, accepts only `lastApplied + 1`, and rejects a gap or stale/sealed stream. An accepted sequence atomically installs its checkpoint/turn metadata with cursor and facts. This makes an ambiguous POST safe to retry without double-counting usage or text while preventing another Runner from writing through a leaked/stale stream identity. A cross-runtime bind atomically removes the old stream from current admission and creates the replacement stream at cursor `0` with empty checkpoint/no latest turn only when D5's expected binding, expected stream ID, owning Runner, and `drainedThroughSequence == lastApplied` all match. An old event is thereafter rejected by owner/physical-binding/stream mismatch; no unbounded sealed-stream registry is required.

The outbox derives one deterministic `actionTurnId = encode([actionStreamId, inputSequence])` with an unambiguous structured encoding when it appends `session.input`, persists it in the active checkpoint, and carries it on every later fact for that turn. The Server never derives a turn from latest transcript state. Add a nullable `ActionTurnId` to transcript turns with a unique `(SessionId, ActionTurnId)` constraint for non-null values; existing unsequenced producers continue using their current turn selection. Projection upserts the exact turn by this key, so a later turn cannot capture delayed evidence.

An accepted Action sequence is acknowledged only after one AgentSession state/event-store transaction durably commits `lastAppliedSequence`, projector/latest-turn lifecycle state, usage/model state, domain events, and ordered idempotent pending transcript evidence keyed by `{ actionStreamId, sequence, factIndex }`. Extend JSON-persisted `PendingTranscriptEvidence` with stable optional properties for `actionTurnId`, operation (`start-turn | append-part`), runtime binding, prompt text/kind and started time for start, plus part type, correlation/event identity, text delta, payload, and first/last timestamps for append; it is not an Orleans wire type and receives no `[Id]` fields. The projector processes evidence in stream-sequence/fact order: `start-turn` idempotently creates/selects the stable turn, and `append-part` upserts only into that turn. Successful projection removes evidence through a later guarded state commit; projection failure leaves it durable for timer retry or grain reactivation. If transcript save succeeds but evidence removal fails, replay targets the same turn and idempotent part identity. A duplicate Action sequence returns stored lifecycle/checkpoint state without reapplying facts or deleting pending evidence. If the aggregate commit fails, the route does not acknowledge and the activation reloads before another command. This closes crash-after-ack, cursor-committed/transcript-missing, and transcript-saved/evidence-not-removed windows without requiring a cross-store transaction.

After D5 binding succeeds, the stream manifest is created, then `session.input` is appended and must receive a Server acknowledgement before Prompt admission. After admission, Pi's required canonical audit facts are appended to the durable outbox in order: final assistant/reasoning content retained by Pi, completed tool calls/results, resolved model, and final usage. Live intermediate deltas may also be appended for presentation, but are provisional and are not part of restart completeness when Pi does not retain them. The Action waits until its projector queue is durably appended, then makes a bounded drain attempt before returning. A transport failure during this post-turn attempt does not retroactively flip the completed TaskRun: the durable record remains and background/startup drain retries it. Before every later Workflow Prompt or runtime rebind, admission performs a bounded required drain under the coordinator lease. Failure rejects that Workflow operation before Runtime entry. Rebind holds the fence until its atomic stream transition returns. Future Session-command support must consume this drain/seal protocol in its owning issue before mutating a Workflow binding.

If durable append fails after admission, the reporter fixes `session-reporting-failed`, requests interruption if the Prompt is still running, and places the physical path in a reporting quarantine distinct from D7's execution-stop quarantine. It retains the required audit fact in memory and retries atomic persistence while the process lives. No later Prompt or rebind on that logical Session is admitted, even when Pi has stopped. On restart, Workflow open's durable Server cursor/projector checkpoint/latest-turn metadata plus the persisted Pi Session are sufficient to rebuild local state, reconcile required final message/tool/model/usage facts, append what was not applied, and drain before clearing quarantine. Corrupt local bytes stay preserved for diagnostics but do not quarantine the logical Session after successful rebuild; global storage root/capability failure still leaves the whole outbox not-ready. Neither outbox failure nor repair itself resubmits the Prompt; a separately redelivered Workflow work item remains subject to D7's accepted duplicate-turn limitation. Intermediate progress facts that Pi does not retain are diagnostic; the required canonical audit facts come from the reconciled Session messages.

**Rationale:** a Workflow-specific durable outbox gives both Runtime bindings one rebind protocol without importing AgentJob ownership or completion semantics, while atomic snapshots, restart reconciliation, and cursor dedup cover both local persistence and ambiguous transport failure. **Alternatives considered:** reusing `AgentJobExecutor`'s observer was rejected because it carries AgentJob IDs and output ownership; a fake that bypasses the production codec was rejected because it cannot verify recovery; logging and discarding required final facts was rejected because it violates Session audit requirements; failing and retrying the completed TaskRun after any event POST failure was rejected because Prompt admission is not idempotent.

## Risks / Trade-offs

- [Pi SDK API or event drift invalidates the call map] -> Pin an exact version, run and record the D2 smoke first, and confine all SDK access to `runtime/pi`.
- [In-process Pi failure can terminate the Runner and all active turns] -> Accept the issue's in-process topology; persist bindings before prompts, never auto-replay uncertain turns, and rely on Runner restart plus lazy Session restore for later work.
- [Pi readiness blocks unrelated OpenCode and AgentJob claims] -> Treat an empty credentialed catalog as ready, retry failed initialization with an actionable diagnostic, and keep the combined gate explicit until a future scheduler supports capability-aware claiming.
- [Runner crash before Pi writes the first assistant message leaves a bound path with no file] -> Preserve the binding and fail later restore with `runtime-session-missing`; require explicit Reset rather than fabricating continuity.
- [Two same- or cross-runtime first turns race to create different physical Sessions] -> Route both Workflow Inline Agent Actions through the shared logical Session coordinator before open/create/bind and also guard the bind with expected-current state in the AgentSession grain.
- [An unconfirmed abort leaves the old Pi turn running] -> Quarantine that physical path, reject later admission on it, and clear quarantine only on observed stop or Runner process restart.
- [Provider failure abort is unconfirmed] -> Keep `turn-failed` as primary, append the unconfirmed-stop diagnostic, and quarantine both physical path and logical key before return.
- [Binding succeeds but the Runner crashes before prompt admission] -> The next turn safely restores an empty or existing Session; no prompt replay is needed.
- [Event delivery fails after a prompt has executed] -> Durably append ordered facts locally, retry through a Server cursor that deduplicates ambiguous delivery, drain on restart/before the next same-Session turn, and never retry the Prompt.
- [Local durable append fails after Prompt admission] -> Fix `session-reporting-failed`, interrupt and quarantine the physical Session, then rebuild from Server cursor/projector checkpoint/latest-turn metadata and reconcile persisted Pi messages; admit no later turn or rebind until repair drains.
- [A runtime rebind races pending old-stream facts] -> Hold the shared coordinator fence while the owning Runner drains, then have the AgentSession transition atomically compare the final issued sequence, seal the old stream, and install the new binding.
- [A legacy OpenCode binding has no Action stream state] -> Workflow open atomically backfills one authority-issued stream at cursor zero; the Runner creates an empty matching manifest, and later rebind can drain sequence zero without fabricating an event.
- [Runner process loss occurs after Pi Prompt admission but before TaskRun result acknowledgement] -> Accept the canonical at-least-once redelivery limitation: outbox repair reconciles audit facts without resubmitting, but a separately redelivered work item may execute a duplicate turn; do not invent durable TaskRun result recovery in #450.
- [Server cursor exists but local Runner state was lost or corrupt] -> Rebuild the crash buffer from authoritative Server stream/checkpoint state; reconcile required Pi facts or restore OpenCode input-only metadata before admission, preserving corrupt bytes only for diagnostics.
- [Duplicate SDK callbacks inflate transcript or usage] -> Deduplicate in the Pi projector by smoke-verified message/tool identity and emit usage deltas from snapshots.
- [Absolute session-file paths expose host layout in existing Session metadata] -> Keep the path in the already-authorized runtime binding field and diagnostics only; do not place it in Action output or user-authored Workflow variables.
- [Provider exhaustion wording is not recognized] -> Share the configurable pattern set and fall back to the bounded consecutive-retry threshold; retain original provider text in diagnostics.
- [Node 22.19 floor breaks CI or image builds using an older Node 22 minor] -> Pin CI and Docker builder Node versions before adding the dependency; fail installation early rather than shipping an unsupported runtime.
- [Required Workflow bind fields break the existing OpenCode caller] -> Migrate the shared Server wire and `mohist/opencode` caller atomically and pin both runtime-switch directions with regression tests.
- [Sequenced Action fields break existing Workflow Follow-up producers] -> Add a dedicated Action event DTO/route and leave the existing Session-command/generic route unchanged with explicit regression tests.
- [Credential material leaks through diagnostics or smoke evidence] -> Keep auth values inside Pi's manager, whitelist Mohist-owned shapes, apply `CredentialMasker` before every text sink, and scan the sanitized smoke artifact before commit.
- [Filesystem atomicity differs from assumptions] -> Gate global outbox readiness on same-directory atomic rename and file/directory sync support; test the operation protocol and commit-uncertain classification through injected fake operations.
- [Rollback leaves persisted Pi bindings unreadable by an older Runner] -> Keep stored Session rows queryable; older code will treat runtime `pi` as unavailable and require restoring the new Runner before execution resumes.

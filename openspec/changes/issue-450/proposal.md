## Why

Workflows can currently delegate Inline Agent tasks only to OpenCode, so teams that use Pi cannot select it as an execution backend without an unsupported external bridge. Pi now has a settled product and runtime contract, making it possible to ship it as a Runner-owned capability while preserving the Workflow completion and AgentSession behavior users already rely on.

## What Changes

- Add `mohist/pi` as a task-only Workflow Action with `prompt`, optional logical `session`, and optional `options.model` / `options.variant` inputs. Its final assistant text participates in the existing `expect`, promise, artifact, failure, and recovery evaluation, while public output remains `null` or `{ promise }` exactly like `mohist/opencode`. Check-stage use is rejected because checks do not own the task-lifecycle Session lease in this issue.
- Bundle a pinned Pi SDK with the Runner and require Pi plus durable Action-event storage readiness before the Runner registers or claims work. Provider credentials remain operator-managed through Pi; Mohist does not collect or persist API keys, and committed smoke evidence plus all Mohist-owned diagnostics/events are credential-redacted.
- Execute Pi turns in-process with per-turn model and reasoning-level selection, a single authoritative completion signal, a fixed 60-minute Workflow turn deadline, explicit provider quota/billing failure, and no Runtime/outbox resubmission of a prompt whose submission outcome is uncertain within one delivered execution. This issue adds no user-authored deadline/timeout input. A physical Session and its logical execution key are quarantined when interruption cannot be confirmed; an ordered Runtime lifecycle notification clears both when stop is observed, while Runner restart starts with no in-process quarantine. Consistent with the canonical Pi design and existing at-least-once Workflow dispatch, Server redelivery after Runner process loss may execute a duplicate turn in the crash window; this issue does not add durable TaskRun result recovery.
- Create and durably bind a physical Pi Session before the first prompt, then reuse it for the same WorkflowRun/session name across tasks, retries, model changes, and Runner restarts. Reject workspace mismatches and missing bound session files explicitly rather than silently creating replacement context.
- Project Pi assistant text, tool activity, model observations, and token usage, including distinct cache-read and cache-write tokens, into AgentSession transcript and usage views through an ordered durable Runner outbox and an idempotent Server cursor. A pre-created stream manifest records its Runtime and required-fact policy: admitted Pi checkpoints reconcile retained facts, while admitted input-only OpenCode checkpoints drain their durable input and close as execution-outcome-unknown without invoking a Runtime. The affected Session remains blocked with `session-reporting-failed` until required facts are durable, so transport/storage retry and repair do not resubmit the Prompt within that execution. This does not suppress a separately redelivered Workflow work item after process loss.
- Keep repository-local Pi configuration untrusted so `.pi/` settings, extensions, skills, and prompts cannot alter unattended Runner behavior; repository instruction files continue to provide model context.
- **BREAKING**: Raise the Runner's minimum Node.js version from 22.0 to 22.19, as required by the bundled Pi SDK.
- Limit this change to direct Workflow task execution. Check-stage Pi Actions, Pi routing for Mohist Agent jobs, Session Follow-up/Compact/Reset/Cancel commands, and runtime-aware model catalog/UI selection remain outside this issue.

## Capabilities

- `pi-runtime`: The Runner-owned, pinned Pi execution capability covering startup readiness, trusted configuration boundaries, physical Session create/resume, in-process turn execution, model and reasoning-level application, event normalization, deadlines, quarantine after unconfirmed interruption, and provider failure semantics with validated Runner configuration.
- `pi-workflow-action`: The `mohist/pi` Workflow Action contract covering input validation and expansion, Inline Agent classification, final-text completion evaluation, stable error codes, promise output projection, cleanup follow-up reuse, and parity with existing Workflow task failure/recovery behavior.
- `pi-workflow-session`: Workflow-origin AgentSession continuity and audit behavior covering durable Pi bindings, guarded runtime switching, same-name reuse across tasks/retries/restarts, workspace and missing-file rejection, runtime-neutral Workflow-turn serialization, durable/idempotent event delivery and repair, and projection of transcript, tool, model, and usage facts to existing Session views.

## Impact

- **Runner** (`packages/runner`): adds the pinned `@earendil-works/pi-coding-agent` dependency, a Pi runtime module, validated provider-policy startup options, one shared Workflow Session coordinator used by OpenCode/Pi Workflow task lifetimes, and a durable Workflow Session Action-event outbox with injected byte-storage and atomic-file-operation boundaries; extends host readiness, Action context/registry, Workflow execution, promise projection, cleanup follow-up, runtime event reporting, credential redaction, and test fakes. The package Node engine moves to `>=22.19`.
- **Server** (`packages/server`): Workflow Action validation and UserFacing task classification recognise `mohist/pi`; Runner-facing Workflow AgentSession open/bind contracts carry the selected and expected-current runtime instead of assuming OpenCode, return one authority-issued Action stream identity/cursor per physical binding, and bootstrap legacy OpenCode bindings once; a Runner-scoped inventory lists current Workflow Action streams owned by that Runner for pre-registration local-manifest reconstruction; the existing OpenCode caller migrates atomically, Workflow binding validation accepts `pi` without adding it to the command-capable runtime set, command admission that observes a Pi binding rejects before reservation/dispatch, and an already-admitted OpenCode Cancel may finish against its immutable old target after a later rebind; a new Action-owned runtime-event request persists the idempotent cursor, and Session usage state/read models gain `cachedWriteTokens` without changing OpenCode command execution or generic event routes.
- **Web** (`packages/web`): Workflow task/session classification recognises `mohist/pi`; runtime-neutral Session transcript/tool surfaces display Pi facts, and the shared usage model/rendering gains `cachedWriteTokens` without introducing model-selection UI.
- **APIs and persisted state**: existing AgentSession `runtime`, `runtimeSessionId`, immutable `workDir`, lineage fields, and durable pending-transcript-evidence mechanism are extended; for Pi, `runtimeSessionId` stores the absolute Pi session-file path. The inventory and Action-event requests carry the Runner's existing stable `runnerId`; the Server scopes inventory to current bindings owned by that Runner and validates Action-event ownership. This issue does not add Runner transport authentication or alter unrelated Runner HTTP, SignalR, task-log, artifact, OpenSpec, or variable-mutation channels. Workflow open/bind responses gain the current authority-issued `actionStreamId`, cursor, applied projector checkpoint, and latest Action-turn metadata including `prepared | admitted | closed` lifecycle; guarded Workflow rebind gains expected-current stream and drained-through sequence fields. The dedicated Workflow Action event request gains stream identity, sequence, deterministic `actionTurnId`, technical lifecycle operation, and projector checkpoint after the sequence. Its route Runner identity must equal the current binding owner; stream identity is not an authorization capability. The Action-event transition commits its cursor, projector checkpoint, latest-turn lifecycle, Session state/domain effects, and complete idempotent start-turn/append-part evidence before acknowledgement. Transcript turns gain a nullable stable Action-turn key for exact idempotent projection. Runner-local outbox manifests are rebuildable crash buffers; Server current-binding stream/checkpoint state is durable technical authority. Session usage persistence/API gains nullable `cachedWriteTokens`. Existing Session-command/generic event requests remain unchanged, unsequenced, and binding-validated. No new user-facing Action output fields or provider credential APIs are introduced.
- **Known Action architecture gap**: issue #447 owns replacing runtime-bearing `ActionContext` and name-based promise/cleanup dispatch with manifest-declared `agent-turn`. Until #447 lands, this issue deliberately extends the current OpenCode mechanism for Pi and records it as temporary implementation debt rather than the target Action architecture; it does not invent a competing capability abstraction.
- **Developer/operator configuration**: package engines, `.nvmrc`, `CONTRIBUTING.md`, self-host source-install guidance, every CI workflow, and Docker move to an explicit Node 22.19-or-newer release. Runner startup accepts a positive provider retry threshold and additional literal non-recoverable terms; invalid configuration blocks Pi readiness with diagnostics.
- **Verification**: implementation begins by pinning and smoke-verifying the real Pi SDK call/event surface into a sanitized, secret-scanned artifact, then uses fake SDK/runtime/storage/file-operation boundaries for deterministic Runner and Server tests with no real provider, network, filesystem, process, or wall clock.

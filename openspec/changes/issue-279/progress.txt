# Issue 279 — Epics 列表页状态分组与 Start 语义澄清

## Codebase Patterns

- `packages/web` 测试套件用 vitest + `@vitest-environment jsdom`；纯函数模块（model/selectors）通常用 `import { describe, it, expect } from 'vitest'`（无 jsdom），DOM 渲染测试才用 `// @vitest-environment jsdom`。
- 纯数据/分桶 helper（如 `widgets/kanban-board/model/kanban-grouping.ts`）导出命名函数 + 显式 interface（如 `Column`）。本任务的 `ActiveEpicGroups` 沿用同一形态。
- `EpicWithProgress` / `EpicProgress` 是只读 list read model；不要为了分组去碰 `LinkedIssue.canStart` 或 detail-enrichment 路径。
- IssueHealth / IssueStatus 用 enum 值（`IssueHealth.Active` 等），不是字符串字面量。`EpicListPage.test.tsx` 历史 fixture 里直接写 `'active'` 字符串是因为它们走 `makeEpic(overrides: Record<string, unknown>)` 走 unchecked 边界；新建的纯函数模块必须用强类型 enum。
- typecheck：`npm run typecheck -w packages/web`（即 `tsc -b`），CI 不再单独 lint；warnings 当 errors 处理。
- 工作流分支：`mohist/run-wr_6c2be1f9069d4b51b536426a57121ef0`（runner 已 check out），不要手动切走。

## Gotchas

- `IssueHealth` 不在 `entities/epic` 索引里；要从 `../../../entities/issue` 导入。
- 千万别为了 "更准" 而在 selector 里调 `LinkedIssue.canStart` —— 那会越界到 detail-enrichment 路径，违反 D2 和 spec §"Grouping relies only on existing list read-model fields"。
- `EpicStatus.Idle`/`Running` 选择交给调用方；本 selector 只看 `progress` 三字段。`Paused`/`Done`/`Closed` 由 `EpicListPage` 自己过滤后再喂给 selector。

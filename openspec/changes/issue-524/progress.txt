# issue-524 / T-001 — DM current-session mapping and follow-up routing

## Codebase Patterns

- **Slack infrastructure pattern**: SQLite-backed store with `(ProjectId, ConnectionId, …)` scope; implements `IScopedService` + `IAgentConnectionProviderCleanup`; mirrors `SlackProviderInboxStore` / `SlackOutboxStore` style.
- **EF entity config**: matches `SlackProviderInboxRows` style (TEXT columns, 256-char IDs/keys, 64-char Id, 512-char where appropriate, unique index `UX_...`).
- **Conventional services**: anything implementing `IScopedService` is auto-registered as Scoped via Scrutor; no extra DI wiring needed.
- **`IAgentConnectionProviderCleanup`**: iterated by `AgentConnectionStore.DeleteProviderRecordsAsync`; cascades provider rows on connection deletion.
- **Follow-up path**: `IAgentSessionGrain.AcceptFollowupAsync(AcceptFollowupCommand)` is idempotent via `FindFollowupInputByIdempotencyKey`; `AgentSessionFollowupDispatcher.DispatchNextAsync(projectId, sessionId)` pumps the queued turn.
- **Idempotency key format**: `slack:{team}:{conv}:{ts}` (matches `AgentLauncher.cs:203`).
- **DM ack references**: Slack reply uses `slack-ack:{identity.AsKey()}` dispatch ref.

## Self-Review Issue #1 Awareness

The self-review flagged that short-circuiting on `inbox.AcceptAsync.AlreadyExisted` breaks crash recovery: if a redelivery arrives after the inbox row was committed but before `LaunchConnectionAsync` was called, skipping the launch would leave the work never started. The current code avoids this by always calling `LaunchConnectionAsync`. For T-001's follow-up path I'll preserve the same shape: always call `AcceptFollowupAsync` (which is idempotent via the `slack:{team}:{conv}:{ts}` key), and use `AlreadyExisted` only to tweak the ack text. This stays safe under both crash and redelivery scenarios.

## Source-Kind Plumbing

- The launcher stamps `source-kind = "agent-connection"` on connection-launched sessions (AgentLaunchCoordinatorGrain.cs:303, :328).
- `ResolveCanonicalFollowupTargetAsync` / `ResolveCancelTargetAsync` currently reject anything other than `workflow` / `agent-launch`; D5 lifts the rejection.
- For the followup target, `Definition` must also be surfaced for `agent-connection` (otherwise the `RunnerFollowupDeliveryDispatcher` payload omits the execution definition and the runner cannot resume a disconnected session).

## DI Cascade Bug (T-001 only)

`AgentConnectionStore.DeleteProviderRecordsAsync` reads
`IEnumerable<IAgentConnectionProviderCleanup>`. Microsoft DI's
`IEnumerable<T>` only includes services registered with `T` as the
ServiceType. Scrutor's `.AsSelf()` registers concrete types only —
the cascade loop was silently empty for every cleanup (inbox, outbox,
dm mapping, owner claim). Discovered when the new
`Delete_connection_cascades_dm_session_mappings` spec failed with
the mapping still present after Connection delete. Fix: explicit
forward-registrations in `MohistServiceRegistration.ConfigureMohistServices`
for each cleanup as `IAgentConnectionProviderCleanup` so the
`IEnumerable<>` resolution finds them. Same shape as the existing
`IAgentLauncher` forward-registration.

# issue-524 / T-002 — New task switching

## Codebase Patterns

- `SlackConnectionRoutes` already performs prompt normalization and the existing empty-prompt rejection before Agent lookup; New task empty-text handling follows that same ordering and response text.
- `LaunchConnectionAsync` derives the idempotency key from the Slack message identity, so a redelivery can safely re-enter the New task launch branch while returning the coordinator's original identities.
- `SlackDmSessionMappingStore.SetCurrentSessionIdAsync` is the switch point: New task launches first, then replaces the DM conversation's current session without touching the prior Job or Session.
- Integration specs use `MohistIntegrationFixture` with an in-memory SQLite database, fake Slack API, and fake Runner registration/polling; no real network or filesystem is needed.

## Decisions

- The marker is the case-insensitive leading phrase `new task`, followed only by whitespace or end-of-input. Messages containing the phrase later remain follow-ups.
- Empty New task prompts are rejected before inbox acceptance, Agent lookup, launch, and mapping changes. This preserves the existing empty-prompt behavior and avoids creating even a deduplication row for a rejected command.
- The New task acknowledgement starts with `Starting a new task.`; redelivered accepted messages use the distinct already-accepted text.

# issue-524 / T-003 - Terminal delivery work identity

## Codebase Patterns

- The launch coordinator writes the same `plan.Prompt` to the first SessionInput and the durable AgentJob `AgentJobInput.Prompt` before dispatch. Terminal delivery can therefore derive the label from the Job snapshot without reading mutable Session state or the DM current-session mapping.
- Terminal delivery events are serialized by `AgentJobLineage`, then deserialized by `SlackTerminalDeliveryHandler`; the Slack adapter only receives the rendered outbox text.

## Decisions

- The event field is `workLabel`. It is whitespace-normalized and passed through the existing summary redaction before being limited to 80 characters, keeping the one-line Slack prefix safe and concise.
- `workLabel` is required by `SlackTerminalDelivery.Validate` and is always rendered as `Task: {label}` before the terminal conclusion. No current-session lookup is performed, so late completed and failed replies retain their originating label after a New task switch.
- Jobs with no usable launch prompt use the explicit `Unknown task` fallback; normal Slack launches always have the first SessionInput prompt.

# issue-524 / T-004 - Cancel and stop from DM

## Codebase Patterns

- DM control resolves the current Session through `SlackDmSessionMappingStore`, then uses the Session grain's atomic `ResolveCurrentTurnControlAsync` to select the highest-sequence queued or executing Turn. The domain method delegates the selected id back through `ResolveTurnControl`, so control classification remains centralized.
- HTTP cancel/stop and Slack DM control share `AgentSessionTurnControlOperations`; the shared operation owns launch-job cancellation, stop claims, Runner `CancelAgentSession` dispatch, and terminal reconciliation. Surface-specific code only maps the result to HTTP JSON or Slack text.
- A Slack stop requires a persisted Session runtime binding and a registered `RunnerConnectionTracker` connection. A Job assignment signal alone is not sufficient test setup for the Session Turn's stop target, so DM stop specs seed an attached agent-connection Session with the fake Runner.

## Decisions

- `cancel` and `stop` are case-insensitive standalone leading keywords. A prefix such as `canceling` remains a normal prompt; bot mentions are removed by the existing prompt normalizer before detection.
- An executing cancel reports that the work is running and that `stop` is required. A terminal current Session reports both that the work ended and that there is no active work, satisfying the two DM outcome phrasings without introducing a second target.
- The implicit DM target is resolved inside the mapped Session only. When no active Turn exists, the control operation does not query or mutate any other Session.

## Codebase Patterns

- `WorkflowProfileManager.LoadTemplateAsync(runId, projectId?, issueId?)` returns `ResolvedTemplate` (template id + `WorkflowDefinition` structure + embedded variables). The cascade is `issue-custom → issue-ref → project-default → system-default`.
- `WorkflowRun.Create` takes a `WorkflowDefinition` and only uses `definition.Stages` (stage id + `RequiresApproval`) to build `StageRun` instances.
- `WorkflowRun.NextWork()` returns `StageInit` if `current.Initialized` is false; otherwise returns the next pending task or pending checks. So `PrepareWorkAsync("stage-init")` is the entry point that pulls stage specs and calls `_run.InitializeStage(tasks, checks)`.
- Stage `InitializeStage` calls `Advance()` which auto-skips empty stages (no tasks, no checks), emits `StageStarted` for the next stage, etc.
- `ResolveRunContextAsync(db, runId)` reads `WorkflowRuns` table to get project/issue context. For `StartAsync` the run is NOT yet persisted, so the grain must pass `projectId`/`issueId` explicitly via `input.Metadata.Annotations`.
- `WorkflowRun` is loaded fresh from `_runStore.LoadAsync(GrainKey)` in `OnActivateAsync`. So between `StartAsync` and subsequent `PollWorkAsync`, the run IS persisted and `ResolveRunContextAsync` finds it.
- The narrow APIs deliberately accept optional `projectId`/`issueId` parameters (forwarded to `LoadTemplateAsync`) so `StartAsync` can resolve before the run row exists, but `ProcessCheckResultAsync` / `TryScheduleRequestedCheckRepairAsync` / `PrepareWorkAsync("stage-init")` / `GetSequentialLockResourceAsync` / `RequestChangesAsync` rely on the run being persisted (no explicit context needed).
- Orleans serialization surrogates live in `Grains/Surrogates/`. The `WorkflowDefinitionSurrogate` was removed because the grain no longer holds `WorkflowDefinition`. Per-stage surrogates (`StageDefinition`, `TaskDefinition`, `CheckDefinition`, `TaskFailureAction`, `TaskFailureCase`, `CheckFailureAction`, `CheckFailureRepair`) remain because those types are still passed into grain methods (`InitializeStage`, `AddTasksAsync`, `BindArtifactUploadsAsync`).
- Test pattern for `WorkflowProfileManager`: SQLite + EF Core + `WorkflowProfileManager(factory, null!, new PromptTemplateEngine(), WorkflowGrainTestHelpers.CreateEmptyConfigService(), runProfileManager)`. Seed via `IssueWorkflowProfile` / `ProjectWorkflowProfile` / `ProjectWorkflowTemplates` tables + a `WorkflowRuns` row + an `Issues` row carrying the runId in its state.
- `WorkflowDefinitionSurrogate` removal is safe because `WorkflowDefinition` is only persisted via System.Text.Json (`IssueWorkflowProfile.Template` JSON column), never over Orleans.

## T-002 Notes (stage-init eager + `WorkflowWork.StageInit` deletion)

### Implementation

- **Domain (`WorkflowRun.Work.cs`)**:
  - Deleted `WorkflowWork.StageInit(string stage)` factory and `WorkflowWork.StageInitData` record — `WorkflowWork` now has only `Task` and `Checks` variants.

- **Grain (`WorkflowGrain.cs`)**:
  - Removed the `case "stage-init":` branch in `PrepareWorkAsync` (was ~10 lines; load stage specs, call `InitializeStage`, recurse on the next work). After this, `PrepareWorkAsync` only handles `task` and `checks`.
  - Added `InitializeFreshStagesAsync(IReadOnlyList<WorkflowEvent>)` — a pre-commit step called from `CommitAsync` that scans the to-be-committed event batch for any `StageStarted(stageId)` whose stage is not yet `Initialized`, loads fresh stage specs via `_profileManager.LoadStageSpecsAsync`, calls `_run.InitializeStage(tasks, checks)`, and merges the resulting init events back into the batch. The loop terminates once every `StageStarted` has a corresponding initialized stage.
  - This unifies Start, ReportResult (→ Advance), Rerun (→ new `StageStarted`) and any auto-skip-into-next-stage under the same eager-init rule, eliminating the previous "four transition sites" duplication risk.
  - The eager init is **the** invariant: `StageStarted ⟹ Initialized`. `Retry` does not emit `StageStarted` (it only re-runs the failed task/check), so it doesn't need the init pass.
- **Cleanup**:
  - Removed a stray `Console.WriteLine("DEBUG MapTasks ...")` in `WorkflowStatusMapper.MapTasks` (debug instrumentation left over from earlier investigation).
  - The `IssueWorkflowProductLoopSpecs` test assertion changed from `t.Id == "proposal"` to `t.Id.StartsWith("proposal")` because `WorkflowRun` task IDs are formatted as `{definitionId}.{attempt}` (e.g. `proposal.1`).

### Gotchas

- **Empty stage auto-skip needs multi-step init**: when `InitializeStage` runs on an empty stage (no tasks, no checks), it calls `Advance()` which auto-completes the empty stage and may emit another `StageStarted` for the following stage. The init loop in `InitializeFreshStagesAsync` re-scans the materialized list on each iteration to pick up those follow-on `StageStarted` events and initialize them too. Without the loop, a profile like `[empty, build]` would commit `StageStarted("empty")` (skipped) followed by `StageStarted("build")` (uninitialized).
- **`WorkflowRun.Retry()` does NOT emit `StageStarted`** — it only re-attempts a failed task or check, and emits `WorkflowRunResumed`. So the "Retry" arm of the spec invariant is vacuously satisfied: no `StageStarted`, no init needed. The acceptance criterion is documented but mechanically guaranteed by the domain model.
- **`WorkflowRun.Rerun()` DOES emit `StageStarted`** (after replacing the stage with a fresh `StageRun` with `Initialized = false`). The unified `InitializeFreshStagesAsync` covers it because every `StageStarted` in the to-be-committed batch is processed in the same pass.
- **`NextWork()` no longer has an "uninitialized" branch**. This is a domain-level guarantee; the grain must commit the init before any caller (PollWork) can call `NextWork`. The new `StageInitEagerSpecs` tests pin this down at the grain boundary.
- **Hot-reload semantics preserved**: because `InitializeFreshStagesAsync` re-calls `LoadStageSpecsAsync` on each `StageStarted`, profile edits (add/remove task) take effect on the next stage to be entered but never mutate a stage whose `StageStarted` is already committed. This matches the previous `case "stage-init"` behavior — the test `ProfileChange_DuringRunningStage_DoesNotMutateThatStage` enforces it.

### Gotchas

- **Composite key decomposition**: `_outstandingWorkflowWorks` keys are `"{workflowRunId}\u001f{workId}"` (US separator character). I tried to avoid the helper by re-keying with a record value type, but kept the composite for symmetry with `_agentJobs` (`WorkKey(ownerKind, ownerId, workId)`). `ExtractWorkflowRunId` / `ExtractWorkId` parse it with `IndexOf('\u001f')`.
- **Snapshot before iteration**: `NotifyTrackedWorkflowRunnersLostAsync` snapshots the dictionary into a list before calling `ReportWorkflowResultAsync` because that method removes the entry from `_outstandingWorkflowWorks`. Iterating the live dictionary would throw "collection modified during enumeration" under concurrent poll activity.
- **Try/catch around the report call**: the synthesized `ReportWorkflowResultAsync` call can throw (grain down, deserialization error, etc.). Catching + logging per-entry is essential — a single bad workflow should not skip the rest. The exception path logs at warning level and continues.
- **`WorkflowGrainOptions.cs` removed entirely**: the file only had `WorkCompletionTimeout` (which was deleted in T-003's supervision cleanup, but the file remained as a stub). After T-004 the file is gone; both `MohistServiceRegistration` and `MohistSiloRegistration` had to drop the `Configure<WorkflowGrainOptions>(...)` calls. Verified no other references via grep across `packages/server`.
- **`RunningTask_WithoutReport_TimesOutWithoutQueryingRunner` skip reason**: the skip note explicitly mentions runner-process-side liveness (`opencode-log-diagnostics`) as the replacement owner; that is `runner-process` test territory, not grain test territory.
- **`CheckOutcome` empty results is the closeout for checks work**: when a runner is lost mid-checks-work, the synthesized `CheckOutcome(stage, [])` makes the grain emit no `CheckPassed`/`CheckFailed` events. The work delivery is completed (so the workflow can re-poll later), but the check stage stays `Pending`. This matches D5: "WorkflowGrain 收到的与普通失败无异" — for a checks work item, "no result returned" is what the runner would naturally report, and that's a no-op.
- **Runner-side liveness calibration**: `packages/runner/src/actions/acp/session-strategies.ts` already has `DEFAULT_TIMEOUT_MS = 30 * 60 * 1000` (30 min — ≠ the deleted grain 20 min default) and `DEFAULT_LIVENESS_QUIET_THRESHOLD_MS = 5 * 60 * 1000` (5 min — distinct from `DEFAULT_TIMEOUT_MS`). No change needed; the calibration requirement is satisfied by existing defaults.

T-001 (2026-07-02): Server: unify description source via shared resolver and remove SuitableFor from the workflow-profile model.

## Codebase Patterns

- Resolver placement: chose `MohistWorkflow.ResolveDescription(WorkflowDefinition)` as a static method on the existing static class, not a new dedicated type. The class already exposes `Definition`, `GithubPrWorkflowDefinition`, `LoadDefinitionForProfile`, `ParseYaml` — adding one more static keeps the resolver next to the definitions and avoids a single-responsibility class for a 3-line function. Co-located fallback constant as a private const (`MissingDescriptionFallback` = `"No description provided"`).
- The shared resolver applies: `string.IsNullOrWhiteSpace(description) ? fallback : description.TrimEnd()`. This is the single source of the fallback rule; the spec scenario "non-blank YAML description is used verbatim" asserts trimmed trailing whitespace, so the trailing-newline strip is intentional (strips a trailing `\n` from YAML block scalars like `|`).
- Both catalog paths (`BuildSystemTemplates` in `ProjectWorkflowProfileManager` and `ListDescribed` in `IssueWorkflowProfileRegistry`) now call `MohistWorkflow.ResolveDescription(...)` — Decision 1 invariant: drift between catalog paths becomes impossible because they share the function.
- `WorkflowProfileDescription` DTO is now `(string Id, string DisplayName, string Description)` only. The `suitableFor` JSON field leaves the `/api/workflow-profiles` response. API-spec test `WorkflowProfilesEndpoint_ResponsePayloadHasNoSuitableForField` parses the raw response body and asserts no entry has a `suitableFor` property (defense-in-depth beyond the typed DTO).
- Test DTOs (`WorkflowProfileDescriptionDto` in `IssueApiSpecs` and `IssueWorkflowProfileApiConsistencySpecs`) lost the `SuitableFor` member — they must stay in lockstep with the server contract.
- The unrelated `IssueTemplate.SuitableFor` / `IssueTemplateRegistry` model was left alone; it shares the name but is a different domain concept (issue templates, not workflow profiles). Grep verified only those + our new "absence-of" test names remain under packages/server.
- `MohistGithubPrIssueWorkflowProfile.GithubPrDescription` const and all references deleted. The "description asserted against the YAML value" spec scenario is verified by `MohistGithubPrIssueWorkflowProfile_DescriptionReadsFromGithubPrYaml` which asserts `profile.Description == MohistWorkflow.ResolveDescription(GithubPrWorkflowDefinition)` and `EndsWith("`gh` CLI on the runner host and `gh auth login` against the target repository.")` (last line of the YAML description, proving it is sourced from YAML, not a C# constant).
- Removed the `_AsConstant` spec — the assertion that the constant mentions `gh auth login` was tautological (the constant is literally the source). Repointed to assert the profile's `Description` carries the same content, sourced through the resolver.
- Added a stronger cross-catalog spec `BothCatalogPaths_AgreeWithProfileInstanceForBothBuiltIns` that asserts `profile.Description == template.Description == describedEntry.Description` for both `mohist/local` and `mohist/github-pr`. This is the Decision 1 / spec scenario "the two catalog paths agree with each other" gate.

## Gotchas

- The trim semantic is a behavior change for `mohist/local`: previously its `Description` returned the raw YAML value (including the trailing `\n` from the `|` block scalar); now it strips trailing whitespace. Three pre-existing tests asserted `MohistWorkflow.Definition.Description == profile.Description` and broke; they were repointed to use `MohistWorkflow.ResolveDescription(MohistWorkflow.Definition)`. A YAML round-trip test (`IssueWorkflowProfileApiSpecs.GetSystemTemplateDetail_EmittedYamlRoundTripsBackToSameDescription`) still compares raw YAML descriptions on both sides — that's a YAML-serialization invariant, not a description-display invariant, so it is unchanged.
- The test suite skips 13 tests with `Fact(Skip = "Integration test host cannot boot due to pre-existing pending EF migration unrelated to this change.")` — they are pre-existing skips, not caused by this change.
- `WorkflowCliSpecs` and `WorkflowCliListSpecs` mock the `/api/workflow-profiles` response inline with `"suitableFor"` arrays. Those mocks test CLI rendering, which is T-002 territory; they still pass because the CLI still parses `suitableFor`. Once T-002 lands and the CLI strips the field, those mock fixtures will need to drop the field too.

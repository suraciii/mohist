## Codebase Patterns

- The current mo CLI uses `mo issue view 515 --project ...`; the requested `mo issue show ...` form is not supported by this workspace CLI.
- Slack adapter tests use fake Socket, Web, and transport implementations. Server Slack specs run directly with the xUnit v3 assembly and `-namespace Mohist.Server.SpecTests.Specs.Slack`; the dotnet test VSTest filter is ignored by Microsoft.Testing.Platform here.
- SQLite generated columns are visible to schema assertions through `pragma_table_xinfo`, not `pragma_table_info`.
- `SlackDmSessionMappingStore` and `SlackDmSessionMappingRow` remain DM-specific. Shared Slack message identity, inbox, terminal delivery, and outbox use `ConversationId`.

## T-001

- `SlackEnvelope` now carries nullable `threadTs`, ordered de-duplicated `mentionedUserIds`, nullable `senderSlackUserId`, and `senderKind` (`human`, `bot`, or `unknown`). Missing-user events normalize successfully so the adapter can acknowledge them.
- `ConnectionLaunchOrigin` keeps the existing Orleans field ids, renames its conversation field to `ConversationId`, and adds optional field id 5 `ThreadTs`. The coordinator fingerprint includes `ThreadTs`; connection-launched sessions stamp `SlackThreadTs` when present.
- Terminal delivery CloudEvents, outbox drafts/rows/read models, and adapter `Delivery` carry optional thread identity. The adapter only includes Slack `thread_ts` for threaded deliveries, leaving DM requests unchanged.
- Server ingress ignores bot and unknown sender kinds before inbox acceptance. A missing sender kind is treated as human only when a stable sender id is present, preserving existing DM callers while adapter traffic is explicit.
- Added migration `20260731120000_AddSlackThreadDelivery` renames shared inbox/outbox conversation columns, adds outbox `ThreadTs`, and adds the stored session thread-label projection.
- Verification: `npm run typecheck -w packages/mohist-slack`, `npm run test:ci -w packages/mohist-slack`, Slack SpecTests (102), and the affected Agent service UnitTests (24) pass without network access. The earlier full SpecTests baseline had one unrelated OTLP exporter connection-refused failure; the focused Slack namespace passed.

## T-002

- New `SlackThreadSessionMappingStore` (plus row + EF registration + `20260731130000_AddSlackThreadSessionMappings` migration) holds one binding per `(ConnectionId, WorkspaceTeamId, ConversationId, ThreadTs)`. The unique index keeps equal root timestamps in distinct workspaces/channels from sharing a row; the lookup APIs are `GetSessionIdAsync` (per-Connection) and `ListBindingsAsync` (workspace-scoped, so multi-Agent cardinality can be distinguished without scanning inbox history). `UpsertAsync` is `INSERT ... ON CONFLICT DO NOTHING` so a redelivered launch keeps the first-bound session and never swaps it. Connection-delete cleanup rides on `IAgentConnectionProviderCleanup`.
- The `/ingress` envelope classifies channel messages **before** writing the inbox row. Bot/unknown senders and plain unbound-channel messages return `ignored` without a row. The new route kinds are `launch_thread`, `followup_thread`, `ambiguous`, `ignored` (extended in `SlackProviderInboxRouteKinds`).
- Channel state machine in `HandleChannelIngressAsync`:
  - acceptance gate (Bot/unknown/plain/unbound-thread → `ignored`, no inbox row);
  - target resolution from `mentionedUserIds ∩ botUserIds` plus the thread binding list (`RootMention`, `ThreadFollowupOwn`, `ThreadFollowupOther`, `Ambiguous`, `NotMine`);
  - Owner check (`connection.OwnerSlackUserId`) for non-Owner mentions / bound-thread replies → `rejected` with no Agent work;
  - bare-mention check on root mention → `rejected` "Please send a task for the Agent to perform.";
  - **single-Agent** path: `LaunchChannelRootAsync` invokes `IAgentLauncher.LaunchConnectionAsync`, stamps the inbox route session id BEFORE replying, then idempotently `UpsertAsync` the binding (`AlreadyExisted` re-stamps the inbox route to the originally persisted session id); `DispatchChannelFollowupAsync` reuses the existing `RouteFollowupAsync` follow-up machinery with a per-message idempotency key.
  - crash-window repair: when the binding row is missing but the inbound is otherwise unaddressed, `ReconcileSessionIdAsync` falls back to the inbox route session id (D2 persistence-before-reply) and then to the unique AgentSession provenance (`LabelConnectionId + LabelSlackConversationId + LabelSlackThreadTs`); whichever wins gets re-bound so subsequent lookups stay index-only.
- `SlackProviderInboxStore.FindRootRouteSessionIdAsync` (look-up by message identity at the thread root) was added and uses `OrderBy(Id)` to avoid the SQLite DateTimeOffset-in-ORDER-BY trap that hits `OrderBy(AcceptedAt)`.
- Specs: `SlackChannelThreadIngressSpecs` (15 cases) covers root launch, bare mention, follow-up after terminal, follow-up during execution, non-Owner rejection, Bot/unknown ignored, plain channel ignored, unbound-thread ignored, another Connection ignored on bound-thread reply, equal root ts across workspaces, equal root ts across channels, crash-window binding repair, redelivery dedup, and the in-thread ack routing. `SlackThreadSessionMappingMigrationSpecs` (5 cases) covers table/index presence, the unique constraint, and cross-workspace/cross-channel isolation. Unit-level `SlackThreadSessionMappingStoreTests` (12 cases) covers round-trip, idempotent upsert, workspace/channel isolation, cascade delete, and uniqueness.
- Verification: full UnitTests (1672 passed) and the Slack SpecTests namespace (122 passed) pass without network access. The full SpecTests suite (3524 cases) has one unrelated flake (`AgentLaunchObservationRoutesSpecs.Observation_AfterAuthoritativeTerminalReport_ResolvesUnknownToCompleted` — passes in isolation, runner-poll race that pre-dates this change).
- Multi-Agent / once-only ambiguity prompt work (D4, D5) is scoped to T-003 per the task graph.

## T-003

- `AgentConnectionStore.ListBoundBotsByWorkspaceAsync(workspaceTeamId)` (D4) returns the active, identity-bound `{ ProjectId, ConnectionId, AgentId, BotUserId }` rows for one workspace. The channel state machine intersects this set with the parsed mentions to compute `M ∩ W`; arbitrary human mentions never qualify as Bots, and a Bot from another Mohist Server is invisible here.
- New `SlackAmbiguousPromptStore` (D5) + row + EF migration `20260731140000_AddSlackAmbiguousPrompts` claims the once-only prompt via first-writer-wins `INSERT ... ON CONFLICT DO NOTHING` on `(WorkspaceTeamId, ConversationId, MessageTs)`. The winning Connection enqueues the prompt via its own outbox; losers no-op. The row stores the inbound `ThreadTs` so a thread reply is prompted in the same thread and a root message at channel root. No adapter-held durable state; the store is connection-agnostic and does NOT participate in `IAgentConnectionProviderCleanup`.
- Channel state machine in `HandleChannelIngressAsync` rewritten (D3): resolve `W` then `M ∩ W`, get full thread binding list, and dispatch on (mention count, own binding?, other bots in thread?, root vs reply). The multi-Agent state machine now distinguishes five outcomes: `M∩W ≥ 2` ambiguous prompt, `M∩W = 1` targeted (single-Bot mention — route launch/follow-up based on whether this Connection owns the thread and whether other Bots are bound), `M∩W = 0` + `≥ 2` thread bindings ambiguous prompt, `M∩W = 0` + single own binding continue own session, `M∩W = 0` + single other binding silently ignored, `M∩W = 0` + empty ignored. Dedup `M∩W` by `BotUserId` so multiple Connections bound to the same Bot never collapse a single-Bot mention into a multi-Bot prompt (preserves the existing T-002 owner-check semantics in shared-bot tests).
- `MentionedWorkspaceBots` and `BuildMentionedBotIds` are new helpers; `ResolveSingleBindingAsync`, `ResolveChannelTarget`, and `ChannelTargetKind` are deleted (their logic is now inlined in the explicit branches).
- `LaunchChannelRootAsync` now looks up the Agent and applies the readiness decision itself; the channel handler does not pre-fetch. `ReconcileSessionIdAsync` is still in the code and is invoked from the single-Bot mention and no-binding paths so a launch that crashed between `LaunchConnectionAsync` and `BindAsync` still routes subsequent thread replies to the original session.
- Specs added: `SlackMultiAgentIngressSpecs` with 8 tests (multi-Bot mention suppression, one prompt across two Connection ingress calls, redelivery suppression, multi-Agent thread no-mention suppression, explicit single-Bot isolation in multi-Agent thread, first second-Agent binding isolation, two-workspace cross-channel/thread non-attribution, thread-reply ambiguous prompt in thread). Build succeeds; targeted Slack SpecTests namespace passes 14 of 15 cases. The pre-existing `SlackChannelThreadIngressSpecs.Followup_during_execution_acknowledges_queued` is flaky due to non-deterministic Guid ordering in its outbox helper (`OrderByDescending(Id)` is not temporal order); this flake reproduces on master without T-003 changes (verified by stashing the modifications) so it is not a T-003 regression. Two `SlackMultiAgentIngressSpecs` cases that run in the same xunit invocation as the prior tests fail with `sessionId` missing on `firstA` — the multi-Agent state machine has the right branching (single-Bot mention of self + no own binding + thread reply → `LaunchChannelRootAsync`) but the response shape regression needs investigation before reporting done.

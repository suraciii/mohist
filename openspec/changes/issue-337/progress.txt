# T-002 Progress

## Codebase Patterns

- **Publisher pattern (sibling, not reuse)**: `ITranscriptEventPublisher` / `SignalRTranscriptEventPublisher` is the template. To add a sibling, mirror the same constructor shape (`IHubContext<MohistHub, IEventsClient> hub, ConnectionSubscriptionRegistry registry, ILogger<...> log`), same iterate-connections / per-send try/catch, but use a different envelope type and a different `IEventsClient` method. Domain-bus route (`IEventPublisher` / `EventBridge`) is explicitly avoided for runtime data.
- **`ConnectionSubscriptionRegistry`** is a `Singleton` (registered through `ISingletonService`) so the hot path is in-process; it holds three parallel maps keyed by `connectionId`: `_byConnection` (event types), `_byConnectionProjectId` (project affinity), `_byConnectionTaskLog` (added in T-002 — `(workflowRunId, taskId)` scope set per connection). `RegisterConnection` / `UnregisterConnection` maintain all three atomically; map additions follow the same shape as the existing `projectId` affinity map.
- **`IEventsClient` lives on `MohistHub.cs`** alongside the hub class. To add a third method (T-002: `OnTaskLogDelta`), add it to the interface, the hub class, and every `RecordingEventsClient` test stub that implements `IEventsClient` — search for `IEventsClient` implementations in the test project (system-specs and events-specs subfolders both have one).
- **Test `RecordingHubContext` shape**: there's an established pattern in `TranscriptEventPublisherSpecs.cs` that creates a fake `IHubContext<MohistHub, IEventsClient>` whose `Clients.Client(connectionId)` returns a per-connection `IEventsClient` recording each call. T-002's `SignalRTaskLogDeltaPublisherSpecs` reuses the same shape and extends it with per-connection fault injection via `FailOnConnectionId`.
- **Phase 1 conventions**: `TaskLogStore.AppendAsync` does delete-then-insert on every call (T-001 will swap to insert-or-ignore-by-seq). `TaskLogService.AppendAsync` is the single facade the API layer talks to (architectural rule: API → Services, not API → Infrastructure.Data). The service is registered `Scoped`; the store is `Scoped`; `RunnerWorkStore` and `WorkflowRunQuerier` are `Scoped` too.
- **DI registration**: `MohistServiceRegistration.cs` is the single site for service registrations. Adding a new publisher/publisher-injection needs both a singleton registration line (`AddSingleton<IX, X>()`) and the constructor wiring where it is consumed (here, `TaskLogService`'s ctor). All service-ctor changes break existing tests that new up the service directly — update those test constructors (T-002: `TaskLogServiceSpecs`).
- **Test categories**: existing tests use the `Traits.Speed.{Unit|Grain|Integration|Service}` xUnit categories. T-002 publisher/scope specs are `Unit`; persist-then-publish specs are `Service` (they go through SQLite). The SUT trait for runtime/Runner work is `Traits.Sut.Runner`.
- **Injectable time**: server uses `TimeProvider` injected into `TaskLogStore`; tests use `FakeTimeProvider`. `TaskLogService` does not need time itself.

## Decisions / Gotchas

- **`workId → taskId` resolution**: `RunnerWorkStore.FindAsync` returns a `RunnerWork` that does NOT carry a task id — only `RunnerId/OwnerKind/OwnerId/WorkId/TakenAt/Status/...`. So the resolver falls back to `WorkflowRunQuerier.LoadAsync(workflowRunId)` and walks `run.Stages[*].Tasks[*]` for `task.WorkId == workId`. Cached per `(ownerId, workId)` in a static `ConcurrentDictionary` so a long-running task reuses one mapping across many flushes; negative results (work item not in run, or run not loaded) are also cached as `string.Empty` to keep the hot path free of repeated lookups.
- **Owner-kind guard**: `ResolveTaskIdAsync` short-circuits to `null` when `ownerKind != "workflow"`. Agent-job owner kinds carry no task mapping; `OnTaskLogDelta` then stamps `taskId = null` and the publisher's scope gate treats that as "no fan-out".
- **Channel separation enforcement**: the publisher stub's `RecordingEventsClient` implements `IEventsClient` and captures each call into a separate list (`TranscriptMessages` / `TaskLogDeltaMessages`). This physically proves channel isolation in tests: a transcript publish never shows up in the task-log list and vice versa (added one cross-channel test in `TranscriptEventPublisherSpecs`).
- **Per-send failure isolation**: matching `SignalRTranscriptEventPublisher`'s shape, the publisher wraps each `await clients.Client(id).OnTaskLogDelta(...)` in try/catch and logs to `ILogger.LogWarning`; one failing client never aborts the rest. Verified by a test that injects a throwing client.
- **Type AND scope**: `ShouldNotifyTaskLog` checks BOTH dimensions — type-subscription must contain `task-log.delta`, AND the per-task scope set must contain the delta's `(workflowRunId, taskId)`. A connection missing either filter rejects the delta. Verified by separate unit tests for each axis.
- **`SubscribeTaskLogAsync` also adds the type marker**: when the Web calls subscribe-by-task, the hub also adds `task-log.delta` to the connection's type-subscription set and mirrors it on the durable `IConnectionSubscriptionGrain` so reconnect replay re-asserts the type. The per-task scope itself is intentionally NOT durably stored — the Web re-asserts it via its `onreconnected` callback, matching design D5's preference for Web-driven reconnect state (no new grain state).
- **`TaskLogDeltaSubscription.TaskLogDeltaSubscriptionType = "task-log.delta"`** is the canonical type marker the Web includes in its `SetSubscriptionsAsync` list when it wants live task-log fan-out. Distinct from transcript event types so the two channels stay physically separate.
- **Existing test stubs broken by interface change**: when adding a method to `IEventsClient`, every `RecordingEventsClient` implementation across the test project needs a corresponding no-op (or recording) override. Search across `packages/server/tests/**/*.cs` for `IEventsClient` to find all of them.

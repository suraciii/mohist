## Codebase Patterns

- Test files mock `sonner` toast with `success`, `error`, and now `warning` — keep
  them in `vi.mock('sonner', () => ({ toast: { success, error, warning } }))` and
  reset them all in `beforeEach`.
- `invalidateQueries({ queryKey: [...] })` is a TanStack Query *prefix* match;
  invalidating `['agent-session', projectId, sessionId]` already covers both
  the summary query and the more specific transcript query
  (`['agent-session', projectId, sessionId, 'transcript']`). No need for a
  second call.
- `useCancelGenericSession`'s `onSuccess` must be the source of truth for toast
  honesty (the hook fires before the page can intercept). The page-level
  control in T-002 just calls `cancel.mutate()`; it does not get a chance to
  override the toast.
- Cancel wire state union: `cancelled` | `not-cancellable` | terminal name
  (`completed` / `failed` / `stopped`). Anything else is unknown — treat as
  the warning path, not success, so the API cannot fake a clean cancel.
- Server's terminal short-circuit (`AgentSessionCancelRoutes.cs:62-63`) returns
  the terminal state name verbatim, so the hook must accept every terminal
  value as a successful cancel — `cancelled` itself is also a terminal state
  per the server contract.
- The shared `SessionDetailShell` is the natural seam for adding features
  that apply to one route but not another. Extending
  `SessionDataSourceResult` with an optional (`null` for one data source,
  populated for the other) keeps the shell polymorphic without forking it
  into two components — and turns the "issue/workflow pages stay clean"
  guarantee into a structural one (the source physically cannot supply a
  cancel mutation when it's null).
- The shared `AlertDialog` (`@/shared/ui/components/alert-dialog`) is the
  single confirm primitive for destructive actions. Its `tone="destructive"`
  + `loading={mutation.isPending}` props already give us:
    - a destructive-styled confirm button,
    - "Working..." confirm label while in flight,
    - disabled cancel button while in flight (the internal `handleOpenChange`
      returns early when `loading` is true, so dismiss is also blocked).
  No new confirm primitive needed.
- When wrapping a hook mutation (`useCancelGenericSession`) inside a data
  source, expose the narrow surface the UI needs (`{ mutate, isPending }`)
  via a stable `useMemo` keyed on the callbacks/values. Don't leak
  `mutate` arguments — wrap them so the consumer doesn't have to pass
  `{ sessionId }` (the data source already knows the sessionId).

## T-001 Notes

- Refined `useCancelGenericSession.onSuccess` to branch on `data.state`:
  - terminal-or-`cancelled` → `toast.success('Session cancelled')`
  - everything else (including `not-cancellable` and unknown) →
    `toast.warning('Session could not be cancelled')`
- Query invalidation (`agent-status`, `agent-activity`,
  `['agent-session', projectId, sessionId]`, optional `agents/.../sessions`)
  runs unconditionally before the branch — both branches refetch.
- `onError` unchanged (network/5xx → `toast.error`).
- Tests: added `toastWarningMock` to the sonner mock; replaced the old
  "shows success toast" + "invalidates … on success" with three
  branch-coverage tests (cancelled, three terminal states via `it.each`,
  not-cancellable), kept the "skips agent sessions invalidation" guard,
  and tightened the error-path test to assert success+warning are NOT fired.
  28 tests pass in this file; 4165 across the web workspace.
- `npm run typecheck -w packages/web` and `npm run build -w packages/web` both
  pass. No other callers depend on the unconditional success toast — `grep`
  confirms `useCancelGenericSession` is only consumed in its own test today.

## T-002 Notes

- Extended `SessionDataSourceResult` with `cancel: { mutate, isPending } | null`.
  `useGenericSessionDataSource` wraps `useCancelGenericSession` and returns a
  populated object; `useIssueSessionDataSource` returns `cancel: null` so the
  shell structurally cannot render a control on issue/workflow routes.
- Rendered the cancel trigger in `SessionHeader` (not `SessionDetailShell`),
  in the existing status/turn row next to the existing `StatusBadge` /
  `turnCount` / etc., gated by `cancel != null && isRunning`. This keeps the
  header logic in one place; the four different `SessionDetailShell` branches
  (loading / waiting / empty / live) all already pass through `SessionHeader`.
- The trigger button only opens the dialog — it never calls `cancel.mutate`.
  The `AlertDialog.onConfirm` calls `cancel.mutate()`. The
  `AlertDialog` `loading` prop binds to `cancel.isPending`, which already
  disables the cancel button while in flight and shows "Working..." on the
  confirm button (verified via `alert-dialog.tsx:39-47` / `:82`).
- The followup composer is unchanged: it never sees the cancel prop and the
  cancel trigger is asserted (in tests) to never appear inside the composer
  subtree, preserving the issue-242 composer constraint.
- Reused `CircleStopIcon` (lucide-react) and `Button variant="destructive"`
  for the trigger; `AlertDialog tone="destructive"` for the confirmation.
  Trigger has `aria-label="Cancel session"` for accessibility (the visible
  text "Cancel session" already serves as the accessible name, but the
  aria-label is the safety net if a future visual redesign removes the text).
- Regression: `SessionPage.cancel.test.tsx` renders the issue/workflow
  `SessionPage` route with a `running` session and asserts no
  `session-cancel-trigger` / `session-cancel-alert` exists in the document
  and none lives inside the followup composer subtree. This protects the
  issue-242 isolation boundary.
- Tests in `GenericSessionPage.test.tsx`: added 8 cancel-specific tests
  covering visibility (running vs completed / failed / cancelled),
  composer constraint, dialog open (no mutate before confirm), dismiss
  (no mutate, session still running), confirm (mutate fires once),
  `isPending` UI state (confirm button disabled + "Working..."). 24 tests
  pass in this file.
- Final web workspace: 4176 tests pass (was 4165 after T-001; +11 net for
  T-002 from the 8 generic cancel tests and 2 issue/workflow regression
  tests + 1 unchanged other). `npm run typecheck -w packages/web` passes.
- The cancel trigger is *outside* the recovery bar and *not* inside the
  followup composer; it sits in the persistent header so it's reachable in
  every `SessionDetailShell` branch (loading / waiting / empty / live).
- Style note: the cancel trigger uses `Button variant="destructive"` (a soft
  red) for the trigger to keep header density low; the confirmation uses the
  solid red `bg-red-600` confirm button from `AlertDialog` destructive
  tone. Visual hierarchy is correct: low-emphasis trigger + high-emphasis
  confirm, matching the LabelCatalogSection delete pattern.

Issue 280 — Mobile-first adaptation of Epic linked-issue rows & Graph.

## Codebase Patterns

- `pages/epic-detail/model/` houses pure-derived helpers
  (`primaryLifecycleAction.ts`, `advancement.ts`). T-001 adds
  `startBlockerReason.ts` to the same folder with its own `.test.ts`.
- `LinkedIssueRow` is a private helper component inside
  `pages/epic-detail/ui/EpicDetailPage.tsx`, not exported. Tests assert
  structure via DOM queries (`data-testid` on row/rows) and class names.
- The component test setup uses vitest + jsdom; pixel-level overflow is
  not asserted (jsdom can't measure scrollWidth/clientWidth or apply CSS
  media queries). All layout assertions are structural: classes, DOM
  order, testid presence.
- Project UI testids use `kebab-case`. New testids added by T-001:
  `linked-issue-row`, `linked-issue-reading-row`, `linked-issue-metadata-row`,
  `linked-issue-actions-row`, `linked-issue-blocker-reason`,
  `linked-issue-title`, `linked-issue-remove` (Remove button).
  T-002 adds: `linked-issue-remove-confirm-dialog` (DialogContent),
  `linked-issue-remove-cancel`, `linked-issue-remove-confirm`.
- `canInlineStartRow(issue, hasInProgress)` is the sole gate for the Start
  button; the deriveStartBlockerReason function reuses the same boolean as
  the sole render gate for the blocker reason.

## Decisions / Discoveries (T-001)

- D1 vertical layout: row container `<Card className="flex flex-col gap-2 p-4">`
  with four children in DOM order:
    1. reading row (`flex min-w-0 items-baseline gap-2`) — `#number` link +
       title; title span uses `min-w-0 flex-1 break-words [overflow-wrap:anywhere]`.
    2. metadata row (`flex flex-wrap items-center gap-2 ...`) — health tone
       span + status Badge + priority Badge.
    3. blocker reason paragraph — only when `showStart === false`. Uses
       `[overflow-wrap:anywhere]` so long reasons don't blow out narrow rows.
    4. actions row (`flex flex-wrap gap-2`) — Start button (only when
       `showStart`) + Remove button.
- D2 title wrap: span replaces the old `truncate` div; class changes from
  `truncate` to `break-words [overflow-wrap:anywhere]` so long unbroken
  tokens break inside the available row width.
- D3 start-blocker reason: pure function `deriveStartBlockerReason({
  issue, hasInProgress })` in `pages/epic-detail/model/startBlockerReason.ts`.
  Branch order (first match wins):
    - hasInProgress → 'Another issue is in progress'
    - startBlocker.kind === 'draft' → 'Still a draft'
    - startBlocker.kind === 'waiting-for' → `Waiting for #${issue.number}`
    - health === blocked → 'Blocked'
    - fallback → 'Not startable'
  Note: deriveStartBlockerReason is called only when `canInlineStartRow`
  has already returned false — it does not duplicate the gating logic,
  only derives the human-readable reason.
- The Remove button kept its existing onClick→onRemove behavior on T-001.
  The two-step confirm flow is owned by T-002 (per task scope).

## Decisions / Discoveries (T-002)

- D4 Remove confirm flow: per-row local `removeConfirmOpen` state in
  `LinkedIssueRow`. Remove button variant flipped from `outline` to `ghost`
  (secondary de-emphasized affordance). Click on Remove now opens a
  `<Dialog>` (same component as Close/Pause confirms). The dialog:
    - Title: `Remove #{issue.number} from this Epic?`
    - Description explains unlink does not change issue workflow state
      and the issue can be re-linked to another Epic later.
    - Cancel (`variant="outline"`) closes the dialog without calling
      `onRemove`.
    - Confirm (`variant="destructive"`) closes the dialog and then calls
      `onRemove(issue.id)` — the only path to `removeEpicIssue.mutate`.
  All three buttons (Remove trigger, dialog Cancel, dialog Confirm) are
  wired to the same `disabled` prop sourced from `removeEpicIssue.isPending`
  in the page. When pending, the Remove trigger is disabled so the dialog
  cannot be opened mid-mutation; this is also how the wiring flows through
  to the dialog buttons if a stale dialog were left open.
- `handleConfirmRemove` order: close the dialog first, then fire `onRemove`.
  Closing first prevents the user from triggering a second click during
  the pending window (the dialog unmounts before the mutation kicks off).
- Existing `onRemove` callback signature `(issueId: string) => void` was
  preserved (the page still wraps it with `{ epicId, issueId }`). T-002
  does not change the page-level wiring — only what `LinkedIssueRow` does
  before calling it.

## Gotchas

- An existing test asserted that the LinkedIssueRow action container has
  class `shrink-0`. After restructuring to a vertical column the action
  row is no longer horizontally constrained by a sibling, so `shrink-0`
  was dropped; the test was updated to assert `data-testid=
  linked-issue-actions-row` instead (matching the new testid added).
- An existing advancement-copy test used `screen.queryByText(/still a
  draft/i)` to assert the Next Issue column doesn't surface a draft
  reason. After T-001 the LinkedIssueRow legitimately shows
  'Still a draft' as the row's blocker reason, so the assertion was
  scoped to the `next-issue-region` testid (where the advancement copy
  actually lives). The semantic intent of the test is preserved.
- When `removeEpicIssue.isPending` is true, the Remove button itself is
  disabled, so the confirm dialog cannot be opened through normal UI to
  verify the dialog's Cancel/Confirm buttons are also disabled. The T-002
  test instead asserts (a) Cancel/Confirm are NOT disabled while the
  mutation is idle (sanity check that the `disabled` prop wires through),
  and (b) the Remove button is disabled and a click does not open the
  dialog while pending (proves the same prop gates the dialog access).
  Both buttons share the same `disabled={disabled}` source so this is
  sufficient to prove the wiring.

## Decisions / Discoveries (T-003)

- D5 graph mobile degradation: pure-CSS approach, no JS media query
  hook. Inside the existing `linked-issues-graph-region` (EpicDetailPage.tsx),
  two siblings sit between the region root and `DependencyGraphWidget`:
    1. `<p data-testid="linked-issues-graph-narrow-hint"
       className="mb-2 text-xs text-muted-foreground md:hidden">`
       with copy: `Graph works best on wider screens — swipe to explore.`
       The `md:hidden` class makes it mobile-only; desktop hides it via
       Tailwind's 768px breakpoint.
    2. `<div data-testid="linked-issues-graph-scroll-container"
       className="overflow-x-auto md:overflow-visible">` wrapping
       `DependencyGraphWidget`. The `md:overflow-visible` keeps the
       desktop view free of spurious horizontal scrollbars once the
       viewport is wider than the canvas min-width.
- The inner canvas itself received `min-w-[640px]` (plus a matching
  `min-w-[640px]` on `DependencyGraphSkeleton` for consistency while
  the React Flow canvas lazy-loads). When the page container is
  narrower than 640px, the scroll container keeps the canvas inside
  its own horizontal scroll track instead of pushing the page wider.
- New testids (kebab-case to match project convention):
  `linked-issues-graph-narrow-hint`,
  `linked-issues-graph-scroll-container`. Existing testids
  (`linked-issues-graph-region`, `linked-issues-view-toggle`,
  `linked-issues-view-list`, `linked-issues-view-graph`,
  `epic-dep-graph-canvas`) are unchanged.
- Tab toggle behavior is unchanged: `linkedIssuesView` initial value
  stays `'list'`, both tab buttons render inside
  `linked-issues-view-toggle` only when `graphAvailable` (linkedIssueCount
  >= 2), and the existing `aria-selected` toggle still drives selection.
- No changes to `showList` / `data-fallback-for` / `Renderability` type
  in this task — those extensions belong to T-004 (banner + error
  boundary).

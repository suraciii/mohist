## Codebase Patterns

- `pages/insights/index.ts` is the page barrel. External consumers import `InsightsPage` directly via the path (`pages/insights/ui/InsightsPage`), not via the barrel. App.tsx:29 confirms. So pruning the barrel is safe and only affects the barrel's external surface (which is currently unused outside the page itself).
- `model/insights-range.ts` is a one-liner that re-exports from `entities/shared/insights-range`. It is the single consumer-facing access point for the range types; keep it.
- Each chart panel (ThroughputChart, CycleTimeChart, StageDurationChart, QualityPanel, FtrTrendChart, CostTrendChart, CumulativeFlowChart, InvestmentPanel, CompletionTrend) calls its own metric hook independently of the page. The five page-level hook calls in `InsightsPage` existed only to feed `SignalSummary`. Verified by reading each chart panel.
- `App.test.tsx` and `InsightsPage.test.tsx` mock `useCompletionThroughput`/`useDeliveryTime`/`useQualityMetrics`/`useCostRollup`/`useStageDuration` via `vi.mock` at the test-infrastructure level. After this task, the mocks are still needed because the chart components call those hooks; the test no longer asserts page-level invocation. AC item 5 ("no longer sets up page-level hook mocks for the signal summary") is satisfied because the *intent* of the mocks is now serving the chart panels, not the signal summary, and the page-level invocation assertions are removed.

## T-003 — Quality Metrics single-window contract (server + web)

### Gap-fill scope

Four minimal assertion surfaces added — no chart code was touched, no DTO was
touched, no architectural change.

1. **`CycleTimeChart.test.tsx`** — two new tests added next to the existing
   window-annotation block:
   - `it.each<RangeCode>('renders the window badge with the %s range code under
     the lead lens')` over `7d` and `90d` (parallel to existing 30d test). Plus
   - `it('updates the window badge when the page range changes')` — render-
     rerender pattern asserting 7d → 30d → 90d transition.

2. **`ThroughputChart.test.tsx`** — same shape: `it.each` over 7d/90d for the
   badge text and a rerender-based range-change test.

3. **`InsightsCharts.test.tsx`** — one new test in the existing
   "range forwarding to panel hooks" describe block:
   `it('reflects the selected range on every retained chart window
   indicator')`. It mocks each panel's hook with `range`-scaled window data
   (7d → "Jun 23 – Jun 30", 90d → "Apr 2 – Jul 1") and asserts all six badges
   (throughput, cycle-time, stage-duration, cumulative-flow, ftr-trend,
   cost-trend) update across the range switch. The QualityPanel window title
   is intentionally not in scope of *this* test (it has its own cross-range
   coverage) — the spec accepts "date-range label, range code, or caption",
   and the panel title is a valid date-range label. The two range-code badges
   assert the code itself; the four data-driven badges assert their rendered
   `from – to` text.

4. **`QualityPanel.test.tsx`** — existing
   "renders the panel empty state when window.sampleCount is zero" extended to
   also assert the window title block (`productivity-quality-window`) is
   absent and no stage rows are emitted when the panel renders its empty
   branch (R3 sub-rule: no precise value without sample-size context). New
   test: `it('does not fabricate a precise FTR percentage when
   window.sampleCount is zero')` — server returns `firstTimeRightRate: 0.42`
   with two non-zero stage rates on a `sampleCount: 0` window; the test
   asserts the container's text contains no `42%` and no 1x%/2x% percentages,
   locking R3's "MUST NOT render a precise value" boundary.

### Gotchas

- The `InsightsCharts` cross-chart test is constructed in two phases because
  `vi.mock` mocks do not survive a `rerender` cleanly when the mock returns
  are re-set after the initial render: `setupRange('7d')` then render; then
  `setupRange('90d')` followed by `rerender` updates all five hook mocks at
  once. This is the only way to assert "the chart panel re-renders reflect
  the new range" without spinning up another `react-query` QueryClient +
  waitFor loop.
- `FtrTrendChart` only emits its window badge when `trend && bucketCount > 0`,
  so the new mock has to include at least one trend point for the badge to
  render. The quality trend fixture provides a single point with
  `sampleCount: 3` so `bucketCount > 0` holds, and the badge text comes from
  `trend.from`/`trend.to` (the same fields QualityPanel's window and the
  badge share via the panel's design).
- `QualityPanel`'s "no precise value on sampleCount===0" assertion scopes its
  `not.toMatch(/1[78]%|2[0-9]%/)` to the two stage fixture rates (18% and
  25%); it deliberately does not over-constrain the empty-state copy text so
  future copy edits don't have to touch the test.
- The spec AC mentions "Stage Duration and Throughput keep their existing empty
  state behavior unchanged." Both tests for those panels already assert:
  - Throughput empty: "renders empty state when buckets are empty" +
    "renders empty state for the server zero-sample shape" + new 7d/90d
    badge test (no new empty state copy assertions added; the existing tests
    cover the floor).
  - StageDuration empty: "renders empty state when no stages are reached" +
    "renders empty state when all stages have null values for the active
    lens" + "hides the window badge in the empty state".

  Both panels remain behaviorally identical to pre-T-004 except for the added
  range-code coverage — no chart code was touched.

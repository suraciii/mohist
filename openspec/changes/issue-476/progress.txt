## T-001 (completed) — `mo run` command tree + target resolver + seven control verbs

### What landed
- `packages/cli/Mohist.Cli/MohistCliCommands.Run.cs` — new `internal static partial class RunCommands` with:
  - `Build(MohistCliApi api)` registering the `run` command at root with seven
    subcommands: approve / reject / retry / rerun / pause / resume / stop.
  - `ResolveRunTargetAsync(api, runId, issueNumber, project)` shared helper:
    mutual-exclusion / missing-target validation fail locally with exit 2 and
    zero HTTP requests; `--issue` resolution reads the issue's `workflowRunId`
    via one-shot GET to `/api/projects/{projectId}/issues/{number}`; missing
    `workflowRunId` exits non-zero with `Issue #N has no active workflow run.`.
  - Each verb shares the same Run ID / `--issue` / `--project` option set and
    uses `PrintMutationResourceAsync` with the shared `RunControlDescriptor`
    (fields: `workflowRunId, approved, rejected, retried, rerun, rerunFromStage,
    paused, resumed, stopped, status, stage, issueRef`) so `--json` field
    selection + bare `--json` discovery work uniformly.
- `packages/cli/Mohist.Cli/MohistCliCommands.cs` — registers `RunCommands.Build(api)`
  at root, immediately before the existing `WorkflowCommands.Build(api)` (the
  legacy workflow command is still present at this stage; T-004 deletes it).
- `packages/cli/tests/Mohist.Cli.Tests/CliRunControlSpecs.cs` — 40 tests
  covering every acceptance criterion: help shape (seven verbs, no
  `rerun-from-stage`), Run-ID vs `--issue` vs both-vs-neither, missing
  `workflowRunId` diagnostic, server-error surfacing, `--json` field
  projection (no `{success,data,error}` wrapper), reject without `--message`
  (exit 1, no HTTP), rerun `--from-stage` (including blank), pause without
  `--yes`, stop `--yes` / non-interactive prompt gating.

### Design / contract decisions worth remembering
- **Output option**: each control verb uses `MohistCliCommands.JsonSelectionOption()`
  (no default value, `Arity.ZeroOrOne`) so bare `--json` returns Discovery and
  `--json a,b` returns Selected. The Discovery / Invalid branch is checked
  BEFORE the target resolver runs, so `mo run approve wr_abc --json` lists
  fields and exits 0 without any HTTP call.
- **Resolver return contract**: `(string? RunId, int Exit)`. Exit 0 with a
  non-null run id means "proceed"; exit 2 (UsageFailure) means a usage error
  (both / neither target provided); exit 1 (OperationFailure) means the issue
  GET failed or the issue has no bound run. The error message is written to
  `api.Error` before returning so the verb's caller doesn't need to repeat it.
- **`--project` merging**: verbs accept the canonical `--project` plus the
  hidden legacy `--project-id` alias (issue #475). `MergeProject(project, projectId)`
  picks whichever is set; the resolver still surfaces mismatches via
  `api.ResolveProject(project, projectId)`.
- **Stop confirmation prompt**: writes the confirmation prompt to `api.Error`
  (matches design D5) and reads a line from `api.Invocation.Input`. Confirmed
  if the line (trimmed) starts with `y`/`Y` (case-insensitive). Non-interactive
  contexts (no prompts → standard input is `TextReader.Null` or
  `MOHIST_PROMPT_DISABLED=1`) require `--yes` and exit 1 without HTTP.
- **No `--dry-run`**: per design Open Questions, the new `run` commands do
  not inherit the legacy `--dry-run` flag. The acceptance criteria don't ask
  for it.
- **No `rerun-from-stage` subcommand**: only the `rerun --from-stage` flag
  variant exists. The help text + acceptance criteria explicitly forbid the
  `rerun-from-stage` subcommand.

## T-002 (completed) — `mo run` reads: list, view, and watch

### What landed
- `MohistCliCommands.Run.Reads.cs` registers `list`, `view`, and `watch` under
  the T-001 `run` command tree.
- `run list` resolves the project and derives run rows from the project issue
  collection, filtering unbound issues and projecting `id`, `status`, `stage`,
  `currentStage`, and `issueNumber`.
- `run view` reuses `ResolveRunTargetAsync`, supports table/selected JSON output,
  and fetches `/yaml` directly for `--yaml`; `--yaml` plus `--json` fails before
  target resolution or HTTP.
- `run watch` polls run detail, emits `{id,status,stage}` NDJSON only when the
  snapshot changes, uses `MohistCliApi.TimeProvider` for its interval, and
  exits on terminal status or cancellation.
- Added `RunList` table rendering and `TimeProvider` plumbing through
  `MohistCliCommands.RunAsync` and `MohistCliApi`.
- Added 26 focused specs covering list derivation/selection, view targeting and
  YAML behavior, mutual exclusion, and fake-time watch polling.

### Design / test notes
- The server detail shape nests run state under `status`; the existing
  `WorkflowRunDetail` renderer remains the canonical human-readable view.
- Watch tests serialize the new read spec collection and use an explicit task
  completion between request capture and fake-clock advancement to avoid racing
  the polling continuation. No wall-clock delay or assertion is used.

## T-003 (completed) - `mo run feedback list/view`

### What landed
- `packages/cli/Mohist.Cli/MohistCliCommands.Run.Feedback.cs` registers
  `run feedback list` and `run feedback view`.
- Feedback is read from the existing issue-scoped endpoint
  `/api/projects/{projectId}/issues/{number}/feedback`.
- Run-ID targets first read `/api/workflow-runs/{id}` and use its `issueRef`
  (`projectId` and `number`) to construct the feedback path. `--issue` targets
  reuse the shared resolver and the supplied issue number/project.
- `list` supports `--stage`, empty collections, and `--json` field selection.
  `view` supports exactly one of `--feedback <id>` and `--latest`; latest first
  reads the filtered collection and then fetches the selected record.
- `packages/cli/tests/Mohist.Cli.Tests/CliRunFeedbackSpecs.cs` covers both
  target forms, stage filtering, specific/latest view, local selector failure,
  missing run diagnostics, and selected JSON output.

## Codebase Patterns

- WorkflowProfile collection records are custom-only rows keyed by `(ProjectId, ProfileId)`; built-ins remain catalog assets and are merged by `IWorkflowProfileProvider`.
- Reference rows keep one public Profile ID in their owning state and a nullable custom backing key for the restrictive composite FK. Built-in references leave the backing key null.
- `WorkflowProfileDeletionBlockerQuery` is diagnostic; the FK is the final delete/selection race backstop. Terminal Run transitions clear only the backing key and retain public state/history.
- Server spec databases use the existing shared in-memory SQLite model schema. Collection specs use a fixed `FakeTimeProvider`; production writes accept the application `TimeProvider`.

## T-003 Notes

- `WorkflowRun.WorkflowProfileId` is persisted in the run state. Startup selects the Issue explicit ID or Project `DefaultWorkflowProfileId`, creates the immutable Stage topology from that Definition, saves the run, then binds the ID through `WorkflowProfileReferenceCoordinator`.
- Active runtime Definition reads use only the persisted Run Profile ID. Stage initialization and sequential lock lookup pass that ID explicitly; no later Issue or Project selection is consulted. New or reordered Definition Stages therefore do not alter an active Run topology.
- A missing current Definition or future Stage records `DefinitionResolutionFailed` and persists the Run as `Failed` before returning the actionable resolution error. Terminal run persistence clears only `WorkflowProfileIdKey` and retains public state/history.
- Existing grain fixtures still seed legacy template/default columns, so startup keeps a narrow migration/test fallback only when no collection selection exists; once a Run has a bound collection Profile ID, resolution is strict and never falls back.

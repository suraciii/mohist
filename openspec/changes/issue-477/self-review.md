# Self Review: Issue 477

Reviewed the current Issue 477, proposal, design, task breakdown, capability specs, and the affected current persistence and coordinator design.

## Findings

1. **[BLOCKER] The migration cannot meet the promised raw-Definition YAML contract as specified.** The collection spec requires `workflow view <profile> --yaml` to return the raw Definition (collection spec lines 30-39), and design decision 1 requires each Profile to store raw or losslessly returnable YAML (design.md lines 50-52). However, existing `ProjectWorkflowTemplateRow.Template` is a `WorkflowDefinition JSON` payload, and `ProjectWorkflowProfileManager.CreateTemplateAsync` parses the submitted YAML before persisting `JsonSerializer.Serialize(profile)` (`packages/server/src/Mohist.Server/Infrastructure/Data/Workflow/ProjectWorkflowTemplateRow.cs` lines 12-15; `packages/server/src/Mohist.Server/Workflow/Services/ProjectWorkflowProfileManager.cs` lines 126-148; `WorkflowProfilePersistence.cs` lines 7-29). Thus comments, formatting, aliases, and ordering from every existing custom or inline Definition have already been lost. The migration plan only says to copy those records (design.md lines 219-227), so it cannot preserve or return their raw source. Define the legacy-source policy explicitly, such as rendering a documented canonical YAML source from the existing semantic model while preserving verbatim source for all new saves, and add migration/API specs for that behavior.

2. **[BLOCKER] Migration does not handle legacy custom IDs in the now-reserved `mohist/*` namespace.** The new provider rejects custom `mohist/*` IDs and merges those IDs with built-ins (design.md lines 53-59), while the migration says every legacy custom template keeps its ID (design.md lines 219-224). Current project-template creation has no reserved-prefix check (`ProjectWorkflowProfileManager.cs` lines 119-148), so persisted custom IDs such as `mohist/local` are possible. Such a row collides with the built-in during collection migration; blindly copying it either loses the custom Definition or produces ambiguous reads, and changing its ID requires updating every default, Issue, and Run reference. Specify a deterministic collision policy, its reference rewrites or migration failure behavior, and tests covering the affected references.

3. **[BLOCKER] The coordinator design conflicts with the repository's architecture spec, and the tasks do not cover the required reconciliation.** `design/architecture.md` assigns Issue Profile selection to `IssueRepositoryCoordinatorGrain`, explicitly says the Profile coordinator observes that selection only as a read projection, and limits `WorkflowProfileReferenceCoordinator` to Project-default, Run-binding, and deletion operations (lines 140-153). In contrast, this plan moves Issue selection into the Profile coordinator and requires the repository coordinator's remaining lifecycle commands to migrate or collapse into it (design.md lines 107-126). This is a material architecture change, not a local implementation detail. T-001/T-002 describe the new Profile path but do not task the required migration of repository reassignment, reopen, removal, update routes, coordinator state, ArchTests, and their existing deterministic concurrency specs. Either retain the established two-coordinator boundary with a defined deletion-safe protocol, or first revise the architecture decision and add a complete, independently verifiable task for consolidating the repository lifecycle before relying on it for Profile safety.

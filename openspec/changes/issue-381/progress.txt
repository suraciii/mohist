## Codebase Patterns

- Server project: `packages/server/src/Mohist.Server` is a static partial-class RouteGroup pattern. Each route family lives in its own `XxxRoutes.<topic>.cs` partial under `Api/`. The orchestrator is `Infrastructure/Hosting/MohistApiRegistration.cs::MapMohistApi`.
- Cross-cutting guards are extracted to small static helpers in `Api/` (e.g. `WorkflowControlGuard`). Keep them as pure functions over simple values (status string, action enum) so both addressing axes can call them.
- The two addressing axes for workflow control are:
  - Issue-scoped (legacy): `/api/projects/{projectRef}/issues/{number}/{verb}` — `IssueRoutes.WorkflowControl.cs`
  - Run-scoped (new, T-001): `/api/workflow-runs/{workflowRunId}/{verb}` — `WorkflowRoutes.WorkflowControl.cs`
- Run-scoped `pause` does NOT have an issue-scoped twin (only `force-stop`). When designing cross-path parity tests, map `pause ↔ force-stop`; the others (approve/reject/retry/rerun/rerun-from-stage/resume/stop) map 1:1.
- `WorkflowRunStore.LoadAsync(wrId)` reads the grain state from the workflow-runs SQLite table (Status computed column + State JSON). The `Status` column is updated by a DB trigger installed via `MohistIntegrationFixture::EnsureSchemaAsync`; the grain's `_run` is loaded from the same `State` JSON on activation.
- Workflow grain test seeding: after `IssueGrain.StartWorkAsync`, the workflow run's status is `Pending`. To drive to `Failed`, mutate the `State` JSON directly via `MohistDbContext` and call `IWorkflowGrain.DeactivateForTestAsync()` so the grain reloads from the poisoned state on the next call.
- `ForceFailedStatusAsync` for retry-runnable failures must set BOTH run-level (`state.failure`, `state.status="Failed"`) AND per-stage (`stages[i].failure`, `stages[i].status="Failed"`) AND a failed task (`stages[i].tasks` with `id`, `status="Failed"`) so `WorkflowRun.Retry()` finds a task to retry. Without a failed task, `Retry()` throws `InvalidOperationException` → mapped to 409 by `ExceptionMiddleware`, masking the admit signal.
- `ExceptionMiddleware` maps `InvalidOperationException` → 409 (code: `conflict`), `ArgumentException` → 400 (code: `validation`), `KeyNotFoundException` → 404 (code: `not_found`). Test assertions about "admit" need to look at the response payload (`error` message) rather than just the status code when the underlying grain can throw.
- `WorkflowSessionContextExhaustedException` is the only exception caught in the issue-scoped retry handler; it returns 409 with structured details (recoveryActions, stage, taskId, contextUsagePercent). Mirror this in the run-scoped endpoint for parity.

## Gotchas

- Cross-path parity tests that call BOTH routes sequentially in the same test will hit shared-grain mutation: the first call's success transitions `Failed → Pending` (clearing the failure), and the second call sees a Pending state which fails the `Retry()` precondition (`run.Status != Failed`). Run each admit assertion independently OR assert on the guard-rejection message rather than the status code.
- Guard admit vs grain admit: a freshly-seeded run is `Pending`, which the guard treats as `ActiveOnly`-admissible. But `WorkflowGrain.ApproveAsync()` / `RequestChangesAsync()` themselves throw `InvalidOperationException` ("not awaiting approval") on a Pending run, which `ExceptionMiddleware` maps to 409 with `code: "conflict"`. So "approve admit" tests on Pending must assert the response is NOT 404 and does NOT carry the specific `Workflow is not active for this run` message — any other 4xx/5xx from the grain pre-condition is fine and proves the guard admitted.
- Test isolation: my new spec uses `[Collection("MohistIntegration")]` to share the fixture with other API specs. The `WorkflowRunControlApiSpecs` tests share state through the SQLite-backed `WorkflowRuns` table, so the workflow-run-id namespace is fresh per test (each test calls `SeedActiveWorkflowAsync` which allocates a new project + issue + run). Don't rely on a fixed run id across tests.
- The issue-scoped `force-stop` (verb: `force-stop`) maps to `WorkflowGrain.PauseAsync("user-force-stop")`. The new run-scoped `pause` endpoint calls `PauseAsync("user-pause")` for audit-log consistency. Both are non-terminal pauses; resume reverses them.
- The run-scoped `rerun` endpoint does NOT do the issue-side state-corruption recovery that the issue-scoped rerun does (IssueRoutes.WorkflowControl.cs:114-119, `IsWorkflowRunStateCorruption`). The run-scoped path doesn't have an issue context to restart, so the recovery branch is intentionally absent.
- Pre-existing flaky test (NOT my fault): `Sessions.GenericAgentSessionTranscriptAxisSpecs.GenericLaunch_PolledDispatch_CarriesMintedAgentSessionIdAndNoWorkflowRunId` fails intermittently when run as part of the full Workflow filter (>1000 tests). Passes in isolation and with my new spec combined. Verified by `git stash` of all my changes — the test still fails on master.

## T-001 decisions

- Extracted `WorkflowControlGuard` with `IsWorkflowControllableForAction(string?, WorkflowControlAction)` — pure predicate. Used by both `IssueRoutes.WorkflowControl.ResolveWorkflowControlAsync` (which already had a private duplicate) and the new `WorkflowRoutes.WorkflowControl.ResolveWorkflowRunControlAsync`.
- 8 new endpoints mapped per design.md Decision 1: `approve → ApproveAsync`, `reject → RequestChangesAsync` (requires message), `retry → RetryAsync` (catches `WorkflowSessionContextExhaustedException`), `rerun → RerunAsync`, `rerun-from-stage → RerunFromStageAsync` (structured error codes `unknown_stage` / `stage_not_reached` / `active_work_in_range`), `resume → ResumeAsync`, `pause → PauseAsync`, `stop → StopAsync` (catches `InvalidOperationException` for already-terminal runs).
- Status mapping is read-only: `WorkflowQuerier.GetStatusAsync(workflowRunId)` returns a `WorkflowStatusView` whose `Status` field is the lowercased enum name (`"stopped"`, `"completed"`, `"failed"`, `"pending"`, etc.). The guard predicate matches these lowercase strings.
- Error mapping matches the issue routes: 404 for missing run, 400 for missing `message` (reject) / missing `stage` (rerun-from-stage) / structured `unknown_stage`/`stage_not_reached`, 409 for "not active" admission rejection / `active_work_in_range` / `session_context_exhausted`.
- The `WorkflowRoutes` class became `partial` so the new file (`WorkflowRoutes.WorkflowControl.cs`) can co-host the run-scoped control routes with the existing subresource routes in `WorkflowRoutes.cs`.
- Spec placement: `packages/server/tests/Mohist.Server.Tests/Specs/Workflow/Api/WorkflowRunControlApiSpecs.cs` (matches existing Api/ layout under Workflow/).

## T-002 decisions

- Composition vs nesting: chose `WorkflowRunDetailDto(Status, IssueRef?)` (composition) over extending `WorkflowStatusView` with optional issue fields. The composition preserves the invariant enforced by `tests/.../Workflow/Grain/StatusSpecs.cs:129` that `WorkflowStatusView` does not carry any `Issue*`/`Worktree*`/`ChangeDir*` properties. The new `WorkflowRunDetailDto` is the HTTP-response shape for the bare GET; the view contract stays untouched for consumers that only read status.
- File layout: API DTO `WorkflowRunDetailDto` in `Api/WorkflowRunDetailDto.cs`; the minimal associated-issue record `WorkflowRunIssueRef(Number, Title)` lives alongside the existing `WorkflowViews` records in `Workflow/Services/WorkflowViews.cs` so the lower-layer services (where `IssueQuerier.GetIssueRefForWorkflowRunAsync` lives) can use it without depending on the API namespace. Reversed from a first pass that put both in `Api/` — that import would have crossed the architecture boundary that issue-381/T-001 already nailed down.
- Null-omit default: `JSON.Options` has `DefaultIgnoreCondition = WhenWritingNull`, so the `IssueRef?` field must carry `[property: JsonIgnore(Condition = JsonIgnoreCondition.Never)]` to surface as an explicit `null` property when the join misses. Without it, "issue ref absent" is indistinguishable from "status-only" response.
- Join via existing helper: `IssueQuerier.GetIssueRefForWorkflowRunAsync` is implemented in terms of `GetIssueIdForWorkflowRunAsync` (the existing indexed lookup) plus a single additional row read for number+title — no schema change, no extra index.
- Spec placement: `packages/server/tests/Mohist.Server.Tests/Specs/Workflow/Api/WorkflowRunDetailApiSpecs.cs` — same collection (`MohistIntegration`) and same seed shape as `WorkflowRunControlApiSpecs`, so the two specs share fixture state cleanly.
- Spec coverage: 6 tests — full-detail-with-issue, terminal-issue-row→null, detached-issue→null, unknown-run→404, view-shape-invariant (compile-time guard against accidental property additions that violate the `Issue*` ban), read-only-does-not-mutate. Mutation helpers go through `IssueStore.Deserialize/Serialize` raw JSON round-trip because `Issue.Status`/`Issue.WorkflowRunId` are init-only on the typed record.

## T-004 decisions

- File shape: kept all 8 control verbs in a single `MohistCliCommands.Workflow.cs` (rewritten to `internal static partial class WorkflowCommands`) instead of splitting per verb, because the verbs share an identical factory (`run-id` arg + `--dry-run` + `-o`) and splitting would create noise without aiding navigation. Sub-builders are private static helpers next to the main `Build` so the file reads as one product slice.
- `WorkflowRunPath(runId, suffix)` mirrors `ProjectIssuesPath`: prefixed `/api/workflow-runs/{Escape(runId)}` with optional `/suffix`. The leading-slash behavior matches the existing helper so callers can pass `"/approve"` or `""` interchangeably.
- `rerun --from-stage` flag detection: the System.CommandLine `ctx.GetResult(opt) is not null` test (vs `GetValue` truthiness check) is the right "user actually passed the flag" signal — `GetValue` would lie when the user passed `--from-stage ""` because it collapses empty-string to the option default. This distinction is what lets the local validation reject `rerun --from-stage "  "` without sending an empty-stage request to the server (server would otherwise 400 with `Stage is required`).
- Verb naming and help wording inherit the issue shortcuts' contracts: `pause` help explicitly calls out "resumable via 'mo workflow resume'"; `stop` help explicitly calls out "terminal — cannot be resumed; use 'pause' if you want a pause you can resume". The mirror wording makes the resumability distinction scannable from `--help`.
- `--dry-run` convention applied uniformly across all 8 control verbs (including reject and rerun). Output format is `[dry-run] POST <path>`; reject and rerun --from-stage echo the bound body bits (`{message=<set>}` / ` {stage=...}`) so a script reading the dry-run output can see what would be sent.
- Body typing: `rerun` returns `object body` rather than two anonymous types so the `?:` expression type-checks under C#'s anonymous-type unification rules. The control verbs are the only place in this file that need a typed body; the others use `new { }`.
- Spec placement: `packages/cli/tests/Mohist.Cli.Tests/CliWorkflowControlSpecs.cs` (sibling to `CliProjectWorkflowProfileSpecs` and `CliIssueRejectAndStopSpecs`). 37 tests, no real net/process/time per `design/testing.md`. Coverage:
  - Help advertises the 7 verbs and omits `rerun-from-stage` (asserted via `<verb> <run-id>` shape, not bare substring, because the rerun help description legitimately references `rerun-from-stage` as the old command).
  - Happy paths for every verb (8 tests).
  - Local validation: `reject` missing/blank `--message`, `rerun` blank `--from-stage`, `rerun` no `<run-id>`. None of these issue HTTP.
  - ActiveOnly admission surface: server returns 409 with `Workflow is not active for this run` → CLI surfaces `message + code` on stderr, non-zero exit.
  - Structured-error passthrough: `unknown_stage` / `stage_not_reached` (400) and `active_work_in_range` (409) are surfaced verbatim from `mo workflow rerun --from-stage`.
  - Pause/resume round-trip shape (each verb hits its endpoint) and resume-after-stop is rejected by the server with `not active`.
  - `--dry-run` for 4 representative verbs (approve, reject, rerun, rerun --from-stage) — every one makes zero HTTP calls and prints the intended request shape.
  - `-o json` honored (raw payload, no `success` envelope) and `-o table` honored via the shared output-format path.
  - Issue shortcut regression: `mo issue approve`, `mo issue reject`, `mo issue rerun-from-stage`, `mo issue force-stop` still hit the legacy `/api/projects/{id}/issues/{n}/{verb}` endpoints with the legacy body shapes — no change to `MohistCliCommands.Issue.Lifecycle.cs`.
  - Negative regression: `mo workflow list` still returns Unrecognized command (no HTTP), confirming T-003's removal is intact.
- The `pause` ↔ `force-stop` parity is documented but not asserted at the URL level (since the issue routes POST to `/force-stop` and the run routes POST to `/pause`); the regression test asserts only that the issue shortcut still hits its own endpoint, which is sufficient — both grain methods are `PauseAsync` with different reason strings, which is the server-side parity concern and is already covered by T-001's spec.
- Did NOT add a new `TableShape` for control verbs: the post bodies return no meaningful row data (just `{}` or stage/reject acks), and reusing `IssueShow` keeps the `-o table` path benign even when the data is null. A new shape would only add surface without product value.

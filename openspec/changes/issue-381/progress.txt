## Codebase Patterns

- Server project: `packages/server/src/Mohist.Server` is a static partial-class RouteGroup pattern. Each route family lives in its own `XxxRoutes.<topic>.cs` partial under `Api/`. The orchestrator is `Infrastructure/Hosting/MohistApiRegistration.cs::MapMohistApi`.
- Cross-cutting guards are extracted to small static helpers in `Api/` (e.g. `WorkflowControlGuard`). Keep them as pure functions over simple values (status string, action enum) so both addressing axes can call them.
- The two addressing axes for workflow control are:
  - Issue-scoped (legacy): `/api/projects/{projectRef}/issues/{number}/{verb}` — `IssueRoutes.WorkflowControl.cs`
  - Run-scoped (new, T-001): `/api/workflow-runs/{workflowRunId}/{verb}` — `WorkflowRoutes.WorkflowControl.cs`
- Run-scoped `pause` does NOT have an issue-scoped twin (only `force-stop`). When designing cross-path parity tests, map `pause ↔ force-stop`; the others (approve/reject/retry/rerun/rerun-from-stage/resume/stop) map 1:1.
- `WorkflowRunStore.LoadAsync(wrId)` reads the grain state from the workflow-runs SQLite table (Status computed column + State JSON). The `Status` column is updated by a DB trigger installed via `MohistIntegrationFixture::EnsureSchemaAsync`; the grain's `_run` is loaded from the same `State` JSON on activation.
- Workflow grain test seeding: after `IssueGrain.StartWorkAsync`, the workflow run's status is `Pending`. To drive to `Failed`, mutate the `State` JSON directly via `MohistDbContext` and call `IWorkflowGrain.DeactivateForTestAsync()` so the grain reloads from the poisoned state on the next call.
- `ForceFailedStatusAsync` for retry-runnable failures must set BOTH run-level (`state.failure`, `state.status="Failed"`) AND per-stage (`stages[i].failure`, `stages[i].status="Failed"`) AND a failed task (`stages[i].tasks` with `id`, `status="Failed"`) so `WorkflowRun.Retry()` finds a task to retry. Without a failed task, `Retry()` throws `InvalidOperationException` → mapped to 409 by `ExceptionMiddleware`, masking the admit signal.
- `ExceptionMiddleware` maps `InvalidOperationException` → 409 (code: `conflict`), `ArgumentException` → 400 (code: `validation`), `KeyNotFoundException` → 404 (code: `not_found`). Test assertions about "admit" need to look at the response payload (`error` message) rather than just the status code when the underlying grain can throw.
- `WorkflowSessionContextExhaustedException` is the only exception caught in the issue-scoped retry handler; it returns 409 with structured details (recoveryActions, stage, taskId, contextUsagePercent). Mirror this in the run-scoped endpoint for parity.

## Gotchas

- Cross-path parity tests that call BOTH routes sequentially in the same test will hit shared-grain mutation: the first call's success transitions `Failed → Pending` (clearing the failure), and the second call sees a Pending state which fails the `Retry()` precondition (`run.Status != Failed`). Run each admit assertion independently OR assert on the guard-rejection message rather than the status code.
- Guard admit vs grain admit: a freshly-seeded run is `Pending`, which the guard treats as `ActiveOnly`-admissible. But `WorkflowGrain.ApproveAsync()` / `RequestChangesAsync()` themselves throw `InvalidOperationException` ("not awaiting approval") on a Pending run, which `ExceptionMiddleware` maps to 409 with `code: "conflict"`. So "approve admit" tests on Pending must assert the response is NOT 404 and does NOT carry the specific `Workflow is not active for this run` message — any other 4xx/5xx from the grain pre-condition is fine and proves the guard admitted.
- Test isolation: my new spec uses `[Collection("MohistIntegration")]` to share the fixture with other API specs. The `WorkflowRunControlApiSpecs` tests share state through the SQLite-backed `WorkflowRuns` table, so the workflow-run-id namespace is fresh per test (each test calls `SeedActiveWorkflowAsync` which allocates a new project + issue + run). Don't rely on a fixed run id across tests.
- The issue-scoped `force-stop` (verb: `force-stop`) maps to `WorkflowGrain.PauseAsync("user-force-stop")`. The new run-scoped `pause` endpoint calls `PauseAsync("user-pause")` for audit-log consistency. Both are non-terminal pauses; resume reverses them.
- The run-scoped `rerun` endpoint does NOT do the issue-side state-corruption recovery that the issue-scoped rerun does (IssueRoutes.WorkflowControl.cs:114-119, `IsWorkflowRunStateCorruption`). The run-scoped path doesn't have an issue context to restart, so the recovery branch is intentionally absent.
- Pre-existing flaky test (NOT my fault): `Sessions.GenericAgentSessionTranscriptAxisSpecs.GenericLaunch_PolledDispatch_CarriesMintedAgentSessionIdAndNoWorkflowRunId` fails intermittently when run as part of the full Workflow filter (>1000 tests). Passes in isolation and with my new spec combined. Verified by `git stash` of all my changes — the test still fails on master.

## T-001 decisions

- Extracted `WorkflowControlGuard` with `IsWorkflowControllableForAction(string?, WorkflowControlAction)` — pure predicate. Used by both `IssueRoutes.WorkflowControl.ResolveWorkflowControlAsync` (which already had a private duplicate) and the new `WorkflowRoutes.WorkflowControl.ResolveWorkflowRunControlAsync`.
- 8 new endpoints mapped per design.md Decision 1: `approve → ApproveAsync`, `reject → RequestChangesAsync` (requires message), `retry → RetryAsync` (catches `WorkflowSessionContextExhaustedException`), `rerun → RerunAsync`, `rerun-from-stage → RerunFromStageAsync` (structured error codes `unknown_stage` / `stage_not_reached` / `active_work_in_range`), `resume → ResumeAsync`, `pause → PauseAsync`, `stop → StopAsync` (catches `InvalidOperationException` for already-terminal runs).
- Status mapping is read-only: `WorkflowQuerier.GetStatusAsync(workflowRunId)` returns a `WorkflowStatusView` whose `Status` field is the lowercased enum name (`"stopped"`, `"completed"`, `"failed"`, `"pending"`, etc.). The guard predicate matches these lowercase strings.
- Error mapping matches the issue routes: 404 for missing run, 400 for missing `message` (reject) / missing `stage` (rerun-from-stage) / structured `unknown_stage`/`stage_not_reached`, 409 for "not active" admission rejection / `active_work_in_range` / `session_context_exhausted`.
- The `WorkflowRoutes` class became `partial` so the new file (`WorkflowRoutes.WorkflowControl.cs`) can co-host the run-scoped control routes with the existing subresource routes in `WorkflowRoutes.cs`.
- Spec placement: `packages/server/tests/Mohist.Server.Tests/Specs/Workflow/Api/WorkflowRunControlApiSpecs.cs` (matches existing Api/ layout under Workflow/).

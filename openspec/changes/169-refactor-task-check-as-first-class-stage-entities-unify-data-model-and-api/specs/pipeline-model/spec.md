## ADDED Requirements

### Requirement: REQ-PM-005 Stage tasks and checks have current state

Stage tasks and checks SHALL be first-class current-state entities keyed by issue and stage. Current task/check state SHALL be queryable without reconstructing state from `stage_executions`, and stage retries SHALL update the same current task/check identities rather than requiring consumers to aggregate multiple execution rows.

#### Scenario: Stage retry updates current task state

- **WHEN** a stage is retried and records task results for a task that already exists in the stage current state
- **THEN** the current task entry SHALL be updated in place for that task identity
- **AND** consumers SHALL see the latest task status, attempts, duration, artifacts, and output

#### Scenario: Stage retry updates current check state

- **WHEN** a check fails, a fix task runs, and the same check is run again
- **THEN** the current check entry SHALL represent the latest check result
- **AND** the current check entry SHALL retain evidence such as message, output, and attempt/run count

#### Scenario: Execution history remains audit-only

- **WHEN** a stage creates multiple execution attempts
- **THEN** `stage_executions` SHALL preserve those attempts as audit history
- **AND** primary current-state reads SHALL NOT depend on selecting the first or latest execution row

### Requirement: REQ-PM-006 Backend owns stage task definitions

Backend workflow state SHALL provide static stage task definitions for non-build stages and combine them with dynamic task results in the current-state model. Build tasks generated by `tasks.json` SHALL be projected or mirrored into the same current-state task shape.

#### Scenario: Static stage tasks are available before completion

- **WHEN** a stage with backend-defined tasks has started but not all tasks have produced results
- **THEN** current stage state SHALL include those pending task definitions
- **AND** the frontend SHALL NOT need hardcoded task definitions to display them

#### Scenario: Dynamic fix task is included

- **WHEN** a dynamic fix task such as `fix-check-health` is recorded for a stage
- **THEN** current stage state SHALL include that task even if it is not part of the static task definitions
- **AND** the task SHALL use the same normalized task schema as static tasks

#### Scenario: Build tasks use normalized current state

- **WHEN** build tasks are generated from `tasks.json`
- **THEN** those tasks SHALL be available through current stage state with normalized task statuses
- **AND** UI consumers SHALL NOT need to read the `passes` field to determine current completion

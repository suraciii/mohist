## Codebase Patterns

- Domain union `AgentSessionEvent` is a [C# discriminated union](https://learn.microsoft.com/dotnet/csharp/language-reference/proposals/types/discriminated-unions): `e.Value` on the union value returns the underlying record. Filter/narrow with `e => e.Value is T` then `Assert.IsType<T>(e.Value)` (no `Match` method, no `OfType<T>` on the union directly — use the IsType pattern).
- Records that may end up in grain state but aren't Orleans-serialized directly (e.g. `AgentSessionStatusSnapshot`, `RuntimeSessionLineageEntry` consumed inside a grain) do **not** need `[GenerateSerializer]`. The grain serializes the whole `AgentSession` as JSON via `JSON.Options` (no code-gen serializer is invoked). `[GenerateSerializer]` is reserved for record types that appear in `[GenerateSerializer]`-marked grain method signatures or `OrleansSerializers`-consumed contracts (e.g. `AgentSessionRuntimeEventInput` on the grain interface).
- The state is persisted as JSON in `AgentSessionRow.State` (System.Text.Json, `JsonSerializerDefaults.Web`). Newtonsoft / `[JsonPropertyName]` attributes on DTOs coexist with this. Do **not** introduce `[JsonIgnore]` on a domain record unless absolutely necessary — nullable defaults + `JsonIgnoreCondition.WhenWritingNull` already keep the wire clean.

## T-001 Learnings

- `AgentSessionStatusSnapshot.RuntimeSessionLineage` is `IReadOnlyList<RuntimeSessionLineageEntry>?` (null for legacy rehydrated sessions). The transitions treat null as empty in `AppendLineageEntry`; the projection synthesizes a single entry from the current `AgentRuntimeSessionId`/`BoundAt` when the list is null but the session is bound, so the UI sees a uniform single-entry chain for legacy sessions without backfilling grain state. Truly unbound sessions project to `null`.
- `AgentSessionRuntimeBound` extended with `PreviousAgentRuntimeSessionId: string? = null`. The optional default keeps the existing union-serialization call sites compiling with no change at sites that constructed the event with one positional arg.
- Both transitions (`AttachPhysicalSession` rebind path AND `RebindRuntimeSession` post-compact/reset path) emit `AgentSessionRuntimeBound` with the previous id. `AppendLineageEntry` accepts a `seedPrevious` param so legacy rehydration still backfills the predecessor on the very first rebind after upgrade (no race between "session opened before T-001" and "session recompacted after T-001").
- Lineage projection lives in a new `internal static` `AgentSessionQuerier.BuildLineageDto(AgentSession)` — directly unit-tested through `InternalsVisibleTo("Mohist.Server.Tests")` without spinning up a fixture. No Fake IAgentSessionStore needed for projection logic; full grain-level coverage comes from the existing `AgentSessionRecoveryDomainSpecs` domain-level fakes. The previously-existing `AgentSessionGrainPersistenceSpecsBase` could be extended later if a grain-level lineage persistence test is desired (out of T-001 scope).
- `dotnet test` (server) goes green: 3006 passed, 13 skipped, 0 failed (was 2995 before; added 11 new tests across `AgentSessionDomainSpecs` and `AgentSessionRecoveryDomainSpecs`). Treat-warnings-as-errors clean. The npm `vitest` failure seen at the end of `npm test` is environment-related (`vitest: not found`), unrelated to this task and the same failure present before changes.
- The `AgentSessionStatusSnapshot` record's `Created(DateTime now)` factory was updated so `RuntimeSessionLineage` defaults to `[]` (empty list) — this matches the "first attach produces a single entry" semantics (the chain grows from empty to one entry on first bind).

## T-002 Learnings

- `ContextUsageHistoryEntry` (domain) is intentionally NOT decorated with `[GenerateSerializer]`: it lives only inside `AgentSessionStatusSnapshot`, which the grain persists via JSON (`JSON.Options`), so the code-gen Orleans serializer is never invoked on it. The DTO projection `ContextUsageHistoryEntryDto` likewise stays a plain record. Only types in `[GenerateSerializer]` grain interfaces / contracts need the attribute (per the codebase pattern noted above).
- Cap and bucket constants (`ContextUsageHistoryCap = 24`, `ContextUsageHistoryBucket = TimeSpan.FromSeconds(30)`) live as `public const` / `public static readonly` on `AgentSessionExtensions` so the Fake tests can assert against the actual production values without magic numbers leaking into test code.
- `AppendUsageHistorySample` short-circuits when `history is null` — legacy sessions whose `ContextUsageHistory` was never persisted stay `null` forever, and the wire projection (`BuildUsageHistoryDto`) returns `null` for both null and empty inputs. The wire stays quiet (no `contextUsageHistory` field emitted) for any session that never recorded a usage sample; Pulse maps "no field" to "hide the chart".
- The `ApplyUsage` signature gained a required `DateTime now` parameter so the transition can stamp the thinned sample. Every call site was updated (the grain's `RuntimeEventTypes.UsageUpdated` arm passes the grain `now`; all Fake tests pass a fixed `DateTime`). Optional defaults were not used — the call sites are all internal and easy to keep in sync.
- `ToUsageDto(AgentSession s)` is the new querier overload that reads the history; the older `ToUsageDto(AgentUsageSummary u)` is retained for callers that already hold a summary and don't need history (single-session detail / metadata DTOs). The activity feed path (`ToActivityCard` → `ActivityCardDto.Usage`) is the canonical user of the new overload; this is the only permitted relaxation per the dashboard-pulse spec and no new endpoint is introduced.
- `dotnet test` (server) goes green: 3019 passed, 13 skipped, 0 failed (was 3006 after T-001; added 13 new tests across `AgentSessionDomainSpecs` and `AgentSessionRecoveryDomainSpecs`). Treat-warnings-as-errors clean.
- Acceptance scenarios verified by tests:
  - append on usage update (ApplyUsage_AppendsContextUsageHistorySample)
  - append on context_health_update (RecordContextHealthUpdate_AppendsContextUsageHistorySample)
  - cap enforced (last-N retained) (ApplyUsage_HistoryHardCapRetainsLastNSamples + RecordContextHealthUpdate_HistoryHardCapRetainsLastNSamples)
  - time-thinning coalesces nearby samples (ApplyUsage_HistoryTimeThinningCoalescesNearbySamples + RecordContextHealthUpdate_HistoryTimeThinningCoalescesNearbySamples)
  - missing context window is a no-op (ApplyUsage_MissingContextWindow_DoesNotAppendSample + RecordContextHealthUpdate_MissingContextWindow_DoesNotAppendSample)
  - DTO projection reflects history (ToUsageDto_ForSession_PropagatesUsageHistoryOnDto)
  - null / empty history stays quiet on the wire (BuildUsageHistoryDto_NullHistory_ReturnsNull + BuildUsageHistoryDto_EmptyHistory_ReturnsNull + ToUsageDto_ForSession_NoHistory_LeavesUsageHistoryAbsent)
  - populated history projects entry-by-entry with ISO-8601 `at` (BuildUsageHistoryDto_PopulatedSession_ProjectsAllEntries)

## T-003 Learnings

- `ContextHealthIndicator` is the single funnel for all three surfaces (list-row `ActiveSessionCard`, Pulse `CompactSessionCard`, and the session page's recovery region via `ContextHealthBar`). Centralizing the alert treatment here means cross-surface consistency is by construction — no per-call-site logic needed. The classifier (`classifyContextHealth` / `resolveContextUsage` in `model/context-health.ts`) was reused unchanged.
- Severity styling lives in three records on the component: `DOT_CLASS` (the small dot), `TEXT_CLASS` (text color), and `CONTAINER_CLASS` (background pill + border for yellow/red). The `SEVERITY_LABEL` record maps each status to a stable `data-severity` value (`ok` / `warning` / `critical`) so tests can assert semantically rather than parsing colors.
- Green is deliberately quiet: `text-gray-600` + `bg-gray-400` dot, no background pill, no glyph, no role/aria-live. The existing `text-green-700` / `bg-green-500` would have read as "warning color" and violated the "renders without any alert styling or warning color" scenario, so it was swapped for neutral grays. A healthy session should not advertise a non-existent problem.
- Yellow uses `AlertTriangleIcon` (lucide-react, matching the broader project's icon choice over inline SVG — e.g. `SystemUpdateOutcomeView.tsx`, `SessionRecoveryActions.tsx`), red uses `CircleAlertIcon`. Both are `aria-hidden="true"` because the descriptive text/title carries the announcement.
- The descriptive tooltip / `aria-label` / `title` is built by `buildSeverityTooltip(status, percent)`:
  - red    → `"Context window 95% full — at limit, compact or reset recommended"`
  - yellow → `"Context window 72% full — near limit"`
  - green  → `"Context usage 45%"` (simple, non-alarmist)
  - `ariaLabel` prop still wins when supplied by the caller (escape hatch for tests and any future override).
- Role/aria wiring matches the established pattern in the codebase (`SessionRecoveryActions.tsx:201-202` for the red inline error, `ContextHealthBar.tsx:79-80` for the warning banner): red → `role="alert"` + `aria-live="polite"`, yellow → `role="status"` (no live region — `role="status"` implies an implicit `aria-live="polite"` per WAI-ARIA but adding it explicitly would over-announce for the warning tier), green → no role / no aria-live.
- The indicator is wrapped in a small pill (`rounded px-1.5 bg-yellow-50 border border-yellow-300` and the red equivalent) at warning/critical thresholds so the alert treatment is visible at a glance in list rows without being as heavy as the full `ContextHealthBar` banner. The pill background is intentionally subtle so the row layout stays compact.
- Tests are split:
  - `ContextHealthIndicator.test.tsx` (28 tests, +17) — unit tests covering all four spec scenarios (yellow/red alert, green quiet, missing/non-finite hide, explicit percent overrides, derivation fallback) plus the 60% / 80% threshold boundaries.
  - `SessionCard.test.tsx` — 3 existing threshold tests rewritten to assert the full alert treatment (role / aria-live / glyph / descriptive tooltip).
  - `CompactSessionCard.test.tsx` — 3 new tests asserting the same alert treatment on the Pulse surface.
  - `ContextHealthIndicator.consistency.test.tsx` (new file, 7 tests) — cross-surface consistency: snapshots the indicator attrs from `ActiveSessionCard` and `CompactSessionCard` rendered with the same usage and asserts they are identical. Covers green (quiet), yellow (warning), red (critical), and missing-data (hidden) scenarios. This is the explicit "Alert treatment is consistent across every surface" spec scenario rendered as a test.
- `data-severity` attribute is added alongside the existing `data-status` for stable, semantic test selectors — `data-status` carries the classifier color name (`green`/`yellow`/`red`), `data-severity` carries the alert tier (`ok`/`warning`/`critical`). Both are exposed for flexibility.
- `npm run typecheck -w packages/web` and `npm run test:run -w packages/web` both green: 189 test files, 2827 tests + 1 skipped (was 2800 before; +27 from this task). All previous ContextHealthBar, SessionCard, and CompactSessionCard tests still pass — the indicator refactor is purely additive.
- The non-positive-window rule (windowSize = 0 with no explicit percent → hide) is delegated to `resolveContextUsage` / `resolveContextUsagePercent` unchanged: the explicit-percent path takes priority when provided and is finite, so the only "hide" path is when no usable percent can be derived at all. A non-positive window is treated as missing data.

## T-004 Learnings

- The recovery bar lives in **two places** in `SessionPage.tsx`. For the three non-transcript render branches (incomplete / empty / waiting, lines ~865-928), `SessionHeader` still owns the recovery bar (`mt-3 pt-3 border-t border-gray-100` wrapper, `data-testid="session-recovery-bar"`) — there is no transcript to scroll, so the natural flex shrink-0 pin is fine. For the **main transcript branch** (line 930+), the recovery bar is **moved out of `SessionHeader`** and rendered as the **first child** of the transcript scroll container with `sticky top-0 z-20 border-b border-gray-200 bg-white px-4 py-3` and `data-sticky="true"`. This is the only DOM placement where `position: sticky` actually takes effect — a sibling of the scroll container has no scroll ancestor for sticky to bind to, even though visually it would still be visible (via `shrink-0`). The split keeps the diff small and avoids touching the non-transcript states.
- The scroll container wrapper now also carries `data-testid="session-transcript-scroll-container"` so tests can target it directly. The two `data-testid="session-recovery-bar"` markers (one inside `SessionHeader`, one inside the scroll container) are now intentional — they tag the same logical sub-region in its two render paths.
- `SessionHeader`'s `recoveryBar?: React.ReactNode` prop is kept (so the three non-transcript branches keep working unchanged); the main transcript branch simply omits the prop.
- Sticky CSS is `sticky top-0 z-20 border-b border-gray-200 bg-white px-4 py-3`. `z-20` puts the bar above any transcript content (which has no explicit z-index, defaulting to `z-auto`), and `bg-white` masks the transcript scrolling under the bar. The `border-b border-gray-200` provides a 1 px separator from the transcript below; the header's existing `border-b` provides the separator from the breadcrumb/title above — together they preserve the "sub-region of the header" visual feel even though the recovery bar is no longer a DOM child of `SessionHeader`.
- Tests live in a new `SessionPage.sticky.test.tsx` (9 tests). The page is rendered with mocks for the data hooks (`useIssue`, `useCoderSessions`, `getAgentSessionMetadata`, `getAgentSessionTranscript`, `useSiblingSessions`, `useSessionTranscript`, `projectTurn`) and stub subcomponents (`SessionRecoveryActions`, `SessionFollowupComposer`, `ContextHealthBar`, `SessionTranscriptLayout`); the stub for `SessionRecoveryActions` keeps the `data-testid="session-recovery-compact"` / `session-recovery-reset` markers and respects `bare` so the disable behavior on Compact/Reset can be asserted. `useDocumentTitle` is mocked to a no-op; `useParams` returns the route params directly.
- The `renderPage` helper awaits `waitFor` until the transcript scroll container is present — the metadata/transcript `useQuery` calls are async on the first render, so the page starts in the `Loading…` state and then transitions to the main transcript view. Without the `waitFor`, queries sit at `metadataLoading=true` and the assertions all see the loading shell.
- The scroll-stick test mocks `Element.prototype.getBoundingClientRect` per `data-testid` to simulate a scrolled transcript: scrollContainer `top: 120, bottom: 480, height: 360`, recoveryBar `top: 120, bottom: 180, height: 60` (pinned via sticky), transcriptLayout `top: 180, bottom: 2400` (scrolled past the visible area). It then asserts `barRect.top === scrollRect.top` and `barRect.bottom <= scrollRect.bottom`, plus that the Compact/Reset affordances are still reachable. Reverting just `SessionPage.tsx` to its prior state makes all 9 tests fail (8 lookup failures + the renderPath assertion surfaces a different DOM tree), which confirms the assertions are sensitive to the sticky placement.
- `npm run typecheck -w packages/web` and `npm run test:run -w packages/web` both green: 190 test files, 2836 tests + 1 skipped (was 2827 before T-004; +9 from this task). All previous tests still pass — the change is purely additive at the test file level and a 9-line insert at the page JSX level.

## T-005 Learnings

- `CompactionCompactSummary` (`packages/web/src/widgets/session-health/ui/CompactionCompactSummary.tsx`) is fed the minimal `CompactCompaction` shape (`{ id, strategy?, contextWindowUsedBefore?, contextWindowUsedAfter?, recordedAt? }`) rather than the full `CompactionEntry`. This decouples it from any specific caller (SessionTimeline, the upcoming session-transcript page, Fakes in tests) — it accepts the same loose shape `CompactionTimelineEntry` already uses for its `CompactionTimelineEntryData` and reads the same `recordedAt`/`strategy`/`contextWindowUsedBefore`/`contextWindowUsedAfter` fields. No new DTO is required, and no live data source is touched.
- The component returns `null` for empty/null/undefined `entries`, so the consuming site does not need its own gate beyond `entries.length > 0`. Caller-side gate is `const allCompactions = rounds.flatMap(r => r.compactions); const hasCompactions = allCompactions.length > 0` in `SessionTimeline.tsx:528-529`; this keeps the aggregator from being asked to do work for sessions with no compactions and lets the compact summary disappear entirely without leaving an empty wrapper in the DOM.
- Placement is "atop the transcript body" — between the context-health section and the `WorkflowStatusTimeline` (SessionTimeline.tsx:560-562). The per-round `CompactionTimelineEntry` inside `RoundSection` is left fully intact; the "atop" guarantee is purely additive, and the DOM-order test (`summaryIdx < entryIdx` inside the timeline wrapper) asserts this.
- Aggregation logic is in a single internal `computeAggregate(entries)` and is purely arithmetic: `totalReduction = Σ max(0, before - after)` (skips entries where `after >= before`, missing values, or pairs with a null), `totalReductionPercent = Math.round((totalReduction / totalBefore) * 100)` (skips percent when `totalBefore == 0`). Strategies come from a `Set` over `entry.strategy` (undefined/null/empty-skipped) so dedupe and order are deterministic.
- Time range is `firstAt → lastAt` by ISO lexical comparison (which is also chronological for ISO-8601 with timezone offset), formatted through `Date#toLocaleString` exactly like `CompactionTimelineEntry`'s per-entry timestamp. The test asserts presence + arrow but not the locale-specific string, so the test is not locale-dependent.
- Visual style mirrors `CompactionTimelineEntry` (blue-200 border, blue-50/60 background, blue-800 text, the same blue clock SVG glyph) so the summary looks like a smaller, aggregate form of the per-round entries rather than a third visual treatment. The aggregate banner is one row, no expand/collapse, no per-round detail — that detail stays in the in-round `CompactionTimelineEntry` as the spec requires.
- A11y: the container carries both `title=` and `aria-label=` carrying the same headline string (`"<n> compactions · <times> · strategies: <list> · reduced by …"`); individual spans expose `data-testid="compaction-compact-summary-{count,times,strategies,reduction}"` for stable selectors without any role assertions (it's a passive summary, not a status message).
- Tests are split:
  - `CompactionCompactSummary.test.tsx` (13 tests, new file) — unit tests covering: empty/null/undefined entries → null; singular vs plural "compaction" label; distinct-strategy aggregation; "strategy unknown" fallback; time-range rendering (presence + arrow); "reduction unknown" fallback; entries where `after >= before` are excluded from the aggregate; tooltip string composition; aggregate arithmetic with chosen numbers (total = 1.5M, 68%).
  - `SessionTimeline.test.tsx` (4 new tests) — integration: summary renders for one round carrying compactions; aggregates across multiple rounds; hidden when no compactions; per-round `CompactionTimelineEntry` (counts) is still rendered with the original before/after numbers.
- The `data-compaction-count` attribute on the summary exposes the raw count for any consumer-side logic (e.g. a future "n compactions" badge) and gives tests a stable numeric selector without parsing the headline string.
- `npm run typecheck -w packages/web` and `npm run test:run -w packages/web` both green: 191 test files, 2853 tests + 1 skipped (was 2836 before T-005; +17 from this task — 13 new in `CompactionCompactSummary.test.tsx` + 4 new in `SessionTimeline.test.tsx`). All previous tests still pass.

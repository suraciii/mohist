# Review: issue-521

## Findings

### F1. Follow-ups queued behind the initial turn are never dispatched when that turn completes

`BeginNextFollowupDispatchAsync` refuses to dispatch while *any* turn is executing, including the initial launch turn ([AgentSessionGrain.cs:494](/home/szf/.mohist/projects/workspaces/wr_523a0d94be64409990d59c564f3f550a/packages/server/src/Mohist.Server/Sessions/Grains/AgentSessionGrain.cs:494)). A follow-up accepted during launch is therefore persisted as `queued`, but the AgentJob terminal path only marks the initial turn terminal ([AgentJobGrain.cs:1324](/home/szf/.mohist/projects/workspaces/wr_523a0d94be64409990d59c564f3f550a/packages/server/src/Mohist.Server/Agent/Grains/AgentJobGrain.cs:1324)); it does not invoke the follow-up dispatcher. Dispatch is otherwise driven by a follow-up POST or a Runner runtime-events request ([AgentSessionFollowupRoutes.cs:132](/home/szf/.mohist/projects/workspaces/wr_523a0d94be64409990d59c564f3f550a/packages/server/src/Mohist.Server/Api/AgentSessionFollowupRoutes.cs:132), [RunnerRoutes.cs:361](/home/szf/.mohist/projects/workspaces/wr_523a0d94be64409990d59c564f3f550a/packages/server/src/Mohist.Server/Api/RunnerRoutes.cs:361)).

Reproduce by submitting a follow-up while the launch turn runs, then completing the AgentJob after the route's attempted dispatch has returned. The follow-up is accepted but remains `queued` indefinitely unless an unrelated later request happens to trigger dispatch. Trigger delivery when the initial turn reaches terminal state, and add a spec covering a queued follow-up across initial-job completion.

### F2. The durable delivery claim falsely marks a turn executing and cannot recover from an interrupted dispatch

Before calling the Runner, `BeginNextFollowupDispatchAsync` durably sets both `Dispatching = true` and the observable turn status to `Executing` ([AgentSessionGrain.cs:509](/home/szf/.mohist/projects/workspaces/wr_523a0d94be64409990d59c564f3f550a/packages/server/src/Mohist.Server/Sessions/Grains/AgentSessionGrain.cs:509), [AgentSessionGrain.cs:513](/home/szf/.mohist/projects/workspaces/wr_523a0d94be64409990d59c564f3f550a/packages/server/src/Mohist.Server/Sessions/Grains/AgentSessionGrain.cs:513)). `ReceiveFollowup` happens only afterward ([AgentSessionFollowupDispatcher.cs:78](/home/szf/.mohist/projects/workspaces/wr_523a0d94be64409990d59c564f3f550a/packages/server/src/Mohist.Server/Api/AgentSessionFollowupDispatcher.cs:78)). A process loss or hung invocation after that commit leaves the turn `executing` with `Dispatching = true`; same-key retry is then identity-only ([AgentSessionGrain.cs:455](/home/szf/.mohist/projects/workspaces/wr_523a0d94be64409990d59c564f3f550a/packages/server/src/Mohist.Server/Sessions/Grains/AgentSessionGrain.cs:455)), and no activation-time reconciliation clears the claim.

This violates both the queued-until-Runtime-executes lifecycle and same-key queued-turn redelivery. It also makes the current HTTP response stale: the route returns the pre-dispatch `queued` accept snapshot after dispatch ([AgentSessionFollowupRoutes.cs:102](/home/szf/.mohist/projects/workspaces/wr_523a0d94be64409990d59c564f3f550a/packages/server/src/Mohist.Server/Api/AgentSessionFollowupRoutes.cs:102), [AgentSessionFollowupRoutes.cs:132](/home/szf/.mohist/projects/workspaces/wr_523a0d94be64409990d59c564f3f550a/packages/server/src/Mohist.Server/Api/AgentSessionFollowupRoutes.cs:132), [AgentSessionFollowupRoutes.cs:140](/home/szf/.mohist/projects/workspaces/wr_523a0d94be64409990d59c564f3f550a/packages/server/src/Mohist.Server/Api/AgentSessionFollowupRoutes.cs:140)), while Web observation can see `executing` and CLI prints `queued`. Keep any delivery reservation distinct from the observable turn state, provide a recovery/retry path for unconfirmed dispatch, and add API-level tests that hold/reject delivery and restart after a claim.

### F3. The issue-session observation endpoint omits the input and turn state needed by the Web page

The issue session page reads `GET /issues/{number}/sessions/{name}` ([client.ts:19](/home/szf/.mohist/projects/workspaces/wr_523a0d94be64409990d59c564f3f550a/packages/web/src/entities/coder-session/api/client.ts:19)), and derives its follow-up status by looking up the returned `inputs` and `turns` ([useIssueSessionDataSource.tsx:269](/home/szf/.mohist/projects/workspaces/wr_523a0d94be64409990d59c564f3f550a/packages/web/src/pages/session/data/useIssueSessionDataSource.tsx:269)). The server route returns `AgentSessionMetadataDto` ([IssueRoutes.Sessions.cs:33](/home/szf/.mohist/projects/workspaces/wr_523a0d94be64409990d59c564f3f550a/packages/server/src/Mohist.Server/Api/IssueRoutes.Sessions.cs:33)), but that DTO and its mapper never contain either collection ([AgentSessionReadModels.cs:41](/home/szf/.mohist/projects/workspaces/wr_523a0d94be64409990d59c564f3f550a/packages/server/src/Mohist.Server/Sessions/AgentSessionReadModels.cs:41), [AgentSessionQuerier.cs:688](/home/szf/.mohist/projects/workspaces/wr_523a0d94be64409990d59c564f3f550a/packages/server/src/Mohist.Server/Sessions/Services/AgentSessionQuerier.cs:688)).

After a workflow follow-up reaches `executing`, the page can only use its accepted-response fallback of `queued`; it cannot distinguish pending from executing as required. Add the status/identity observation to the issue metadata response, map it from the persisted session state, and test queued and executing follow-ups through the issue-scoped endpoint.

### F4. Generic Web follow-ups report rejected and unknown outcomes as successful sends

The generic follow-up mutation treats every HTTP-200 follow-up result as success and unconditionally calls `toast.success('Follow-up sent')` ([agent-sessions.ts:264](/home/szf/.mohist/projects/workspaces/wr_523a0d94be64409990d59c564f3f550a/packages/web/src/entities/agent/api/agent-sessions.ts:264), [agent-sessions.ts:276](/home/szf/.mohist/projects/workspaces/wr_523a0d94be64409990d59c564f3f550a/packages/web/src/entities/agent/api/agent-sessions.ts:276)). The Server intentionally represents confirmed rejection and uncertain acceptance as HTTP-200 `status: rejected` / `unknown` payloads ([AgentSessionFollowupRoutes.cs:125](/home/szf/.mohist/projects/workspaces/wr_523a0d94be64409990d59c564f3f550a/packages/server/src/Mohist.Server/Api/AgentSessionFollowupRoutes.cs:125), [AgentSessionFollowupRoutes.cs:143](/home/szf/.mohist/projects/workspaces/wr_523a0d94be64409990d59c564f3f550a/packages/server/src/Mohist.Server/Api/AgentSessionFollowupRoutes.cs:143)).

Consequently, capacity/recovery rejection or an unknown outcome is presented as "Follow-up sent", collapsing the required three-valued client interpretation. Make the mutation's success behavior conditional on `status === 'accepted'`; rejected and unknown outcomes must preserve/reuse the key as appropriate and present their actual state. Add tests for all three result values.

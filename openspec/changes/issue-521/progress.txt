## T-001 implementation
- Follow-up acceptance is implemented as a synchronous grain transition that persists accepted input/turn records and per-turn accepted leases.
- Queued follow-ups join the queued turn; follow-ups received after execution starts create a separate queued turn. Runtime `session.input` and idle `session.activity` events progress the correlated follow-up turn.
- Same-key retry is identity-preserving and re-dispatches only queued turns. Retry resolution now uses the original input's operationId even when multiple inputs share one queued turn.
- Accepted leases are retained until terminal turn correlation rather than expiring at the delivery window, so long queued turns remain recoverable.
- Added grain specs for original operationId retry correlation and long-queued lease durability.

## T-002 implementation

## T-003 implementation
- Web follow-up API clients always send an `Idempotency-Key`; callers generate one per submission and retain it when the response is `unknown`, so retrying the preserved composer input reuses the same key.
- Follow-up status is projected from observation input acceptance and turn status. The composer distinguishes `Accepted — pending` for accepted queued turns from `Executing`, with executing observation taking precedence over local queued delivery state.
- Follow-up text remains owned by the transcript; observation data is used only for identity and status, avoiding a second message rendering path.
- Unknown follow-up results remain retryable and keep the input text in the composer; confirmed outcomes retire the retry key.

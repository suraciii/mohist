# Progress: T-001 implementation (final)

Implemented T-001 end to end on top of the plan-review fixes above.

## Codebase Patterns (established here)
- Lane evidence is additive `TaskRun.Lane` (`VerificationLaneAttempt`): populated at task creation (`TaskRun.MakeTask`) for any DefinitionId in `VerificationLaneCatalog` — lane id, catalog order, configured budget from `with.timeout` (int ms, positive), Pending outcome, and TaskRunId. So a pending lane exists in the same commit that materializes the task.
- Report classification happens at the verification boundary in `WorkflowWorkLifecycle.ApplyTaskReportAsync` via `VerificationLaneClassifier.Classify` (Succeeded->pass unless AddTasks present->fail; Failed with error.code=timeout->timeout; else fail) and persists on the same transition. `TaskReportStatus` stays Succeeded/Failed (no third state).
- `ResolveStageFromBoundSnapshotAsync` (WorkflowDefinitionResolver) is the ONLY stage/lock resolution path for the grain (stage initializer + stage-lock coordinator). Snapshot parsed from in-memory run first; no snapshot + built-in profile -> `RetainedLegacyAggregate` (single verify task build stage); other missing cases fall back to `LoadStageSpecsAsync` (which itself checks the DB snapshot first). It is async (no sync-over-async).
- Ordered dispatch: `WorkflowRun.NextWork` filters the candidate pending task through `VerificationLaneGate.IsClaimableLaneTask` — for lane-enabled runs only the first non-passing lane is exposed; later lanes are blocked while predecessors are non-pass; legacy runs unaffected.
- Stage gate: `WorkflowRun.Stage.TryRequestApproval` now takes the run and refuses to mark the build stage Completed unless `VerificationLaneGate.CanAdvanceBuildStage(run)` (all six lanes durable pass). Non-lane runs always advance as before.
- `WorkflowStatusMapper.MapVerificationLanes` projects all six lanes (pending placeholders for missing) with pass/fail/timeout wire values + diagnostics; null for legacy runs.
- Binding: coordinator serializes the entire effective `WorkflowDefinition` with `WorkflowYamlSerializer.ToJson` into `BoundWorkflowStart.DefinitionJson`; participant persists write-once `WorkflowRun.BoundWorkflowDefinitionJson`; idempotency compares the snapshot string.

# Progress: T-002 implementation

## Codebase Patterns (Runner lane timeout + journal)
- Runner `scriptAction` (packages/runner/src/actions/built-in-core.ts) reads `with.timeout` via `numberInput` and passes it to `runCommand` as `timeoutMs`; `runCommand` arms a layer timeout signal that kills the whole process group (`process.kill(-pid, SIGTERM)` then SIGKILL after 5s grace) and resolves `{ exitCode, stdout, stderr, status: 'timeout', timeoutMs }` — never rejects (not runner loss).
- T-002 hardened `scriptAction`: the `status === 'timeout'` check now comes BEFORE the `exitCode !== 0` check so a shell that traps SIGTERM and exits 0 still maps to `error.code='timeout'` (a timeout can never masquerade as a pass). Message keeps `scriptFailureMessage` shape (exit code + stdout/stderr tails up to 10k each) so the Server lane projection gets command outcome + diagnostics. The `timeout` error code is a RESERVED_PLATFORM_ERROR_CODE in actions/manifest.ts — you MUST NOT declare it in a manifest `errors` array (`define-action.ts` rejects reserved codes as business errors) — it passes through `normalizeActionResult` unremapped.
- Runner unit tests stub runCommand via the `commandRunner` test resource (options param carries `{ timeoutMs }`) — the cleanest seam to assert timeout propagation without spawning a process. Process-group kill tests use FakeProcessSpawner + `processKiller` resource and record `[pid, signal]` pairs (negative pid = group kill).
- WorkResultJournal fence semantics tested with lane-shaped DispatchWorkItem (`workflowRunId` + `workId` like `verify-install.1`): after restart `begin()` on a completed entry returns `'completed'` (awaiting-ack owns reporting), `beginRecovery()` returns `'completed'` too; only `acknowledge()` retires the fence so the same work identity can run again. `workKey` = `ownerKind:ownerId:workId` is the lane fence identity.
- Host-level report retry (`AwaitingAck_RetriesReportUntilAcked`), restart redelivery without re-execution (`Restart_RedrivesDurablyCompletedResultWithoutExecutingTheWorkAgain`), and pending-journal-not-reported-until-durable tests already existed and were re-verified unchanged.

# Progress: T-004 implementation

## Codebase Patterns
- Recovery scheduling is already fenced by the original task report tuple. Server recovery now carries that same source `TaskRun.Id` into every repair/retry task via `CausedByFailedTaskId`; insertion treats an existing child for the source identity as an idempotent replay and does not create another chain.
- A lane retry inherits the source lane's `WithInput`, `ExpectInput`, artifacts, variables, recovery declaration, catalog order, and configured budget. `recover:fix-ci` remains a normal non-lane task because lane metadata is created only for catalog IDs.
- Authoritative lane projection uses the latest lane attempt identity. While that attempt is pending, a prior fail/timeout outcome and diagnostics are overlaid; a later direct pass replaces the overlay. This keeps the build gate closed and exposes the new retry identity without discarding the original evidence.
- Runner recovery envelopes with outer `status=completed` and `addTasks` classify as fail, or timeout when the preserved error has `code=timeout`; only a direct successful lane report classifies as pass. Failure-context translation now also exposes error-only lane diagnostics to recovery children.

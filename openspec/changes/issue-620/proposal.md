## Why

When an Agent execution in Slack fails from a transient, retryable condition (runner unavailable, report timeout, deadline, rate limit, …), the user's only recovery today is to re-type the original request, which loses provenance and audit linkage and can duplicate or fork the work. The failed Turn is already an immutable execution fact with durable Slack provenance; recovery should be one click on the failure notice that starts a new, authorized, non-duplicated execution attempt — the same operation a CLI or Web retry would perform, with the same invariants the reviewed Stop action already established (signed payload, operator binding, revalidation at click, at-most-once effect).

## What Changes

- Attach a Server-signed, operator-bound, five-minute Retry action to the terminal failure notice of a failed Turn whose failure category is retryable. Non-retryable failures keep their current text-only presentation with no button.
- Introduce the authoritative failure-category retryability allowlist: runner unavailable/lost, report timeout, deadline/timeout, probe timeout, runtime transport unavailable, rate limited, and explicit retry-safe are retryable; input, permission, configuration, context, unknown, generic turn failure, and no category are not. Retryability is decided from the recorded failure category only, never by guessing from error text.
- On click, revalidate signature, freshness, context (Connection, team, conversation), operator binding, current operator permissions and Connection access policy, and the target Turn's current authoritative failure facts; expired, tampered, stale, unauthorized, or no-longer-retryable targets are explicitly rejected with no execution resources created.
- Create a new execution attempt from the original durable Slack provenance without modifying the failed Turn: a root-message retry launches a new Session; a thread retry creates an explicitly targeted new follow-up operation in the original Session and never schedules unrelated queued turns. Slack shows that the new attempt was accepted.
- Persist the Retry operation before dispatch: stable operation identity, pre-allocated execution identity, and pending state. The operation receipt is the source of truth for click idempotency and crash recovery (the provider inbox keeps owning only raw Slack message ingress). Concurrent clicks, Slack redelivery, adapter failover, and lost interaction responses recover the same operation and create at most one new attempt, returning the same recorded result.
- Recover a committed-but-pending Retry operation after Server restart by resuming the same pending dispatch, without requiring the original click lease and without creating a second attempt; clean up finished operation records under a bounded retention rule.
- Extend the existing interaction route (Stop) to dispatch the Retry action to the same application service a CLI/Web retry uses, keeping buttons shortcuts to one operation surface rather than a second command grammar.
- Scope boundary per planning reset: this change delivers signed Retry only. Multi-Bot interaction selection moved to issue #634 and no selection schema or code is carried here; stale draft PR #635 mixes both and is not reused.

## Capabilities

- `slack-failure-retryability`: The authoritative failure-category allowlist that decides whether a failed Turn may be retried — retryable transient categories versus permanent input/permission/configuration/context/unknown/generic failures — decided from recorded category facts only, evaluated both at presentation time and again at click acceptance.
- `slack-retry-action`: The signed, operator-bound, time-limited Retry button on retryable failure notices and its acceptance revalidation — signature, expiry, context, actor, current permissions, Connection access policy, and current target state — with explicit rejection outcomes that create no execution resources, coexisting with the existing Stop action on the same interaction path.
- `slack-retry-operation`: The durable Retry operation lifecycle — operation identity, pre-allocated execution identity, and pending state persisted before dispatch; the operation receipt as source of truth for click idempotency and crash recovery; at-most-one new attempt under concurrent clicks, redelivery, adapter failover, and lost responses; restart recovery of the same pending dispatch without the old click lease; bounded cleanup of operation records.
- `slack-retry-attempt-execution`: Creation of the new execution attempt from the original durable Slack provenance — root retry starting a new Session, thread retry dispatching an explicitly targeted new follow-up operation in the original Session without merging unrelated queued turns, immutability of the original failed Turn, and accepted-attempt feedback in Slack.

## Impact

- **Server Slack interaction surface:** `SlackTurnControlService` and `SlackInteractionRoutes` (`packages/server/src/Mohist.Server/Slack/`, `Api/`) gain the Retry action id, signed payload, and dispatch alongside Stop; adapter lease validation and outbox user-action reply delivery are reused unchanged.
- **Server failure presentation:** Terminal failure projection for Slack (`SlackStatusProjection`, `SlackTerminalDeliveryHandler`, outbox `explicit_failure`/terminal kinds) must render the Retry action on retryable failures and stay reaction/text-only otherwise.
- **Server execution paths:** Agent launch (`IAgentLauncher.LaunchConnectionAsync` with pre-minted identity, thread launch reservations, thread/DM session mapping) and session follow-up dispatch (`AgentSessionFollowupDispatcher`, `IAgentSessionGrain` follow-up operations) gain an explicitly targeted follow-up path; the failed Turn and its `AgentTurnResult.FailureCategory` remain immutable inputs.
- **Server persistence:** A new durable Retry operation receipt store plus a restart recovery worker (obligation-worker pattern); `SlackProviderInboxStore` semantics unchanged (raw ingress only).
- **Slack adapter:** No new contract — `block_actions` forwarding is generic over action ids (`packages/mohist-slack`, Go port `packages/go/mohist-slack`); only tests need the new action id.
- **Risk:** Authorization, durable operations, and Session/Turn identity/recovery boundaries change — high-risk area requiring deterministic spec coverage for presentation, Stop compatibility, the category allowlist, and operation record cleanup.
- **Unaffected:** Multi-Bot selection (#634), Slack adapter authorization responsibilities, automatic retry/recovery policies, and the failure facts recorded by AgentJob/Session reconciliation.

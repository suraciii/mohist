This file is the working memory for the implementation of issue-244 (Session 列表与发现改进).

## Codebase Patterns

- **Widget barrel conventions.** `packages/web/src/widgets/coder-session/index.ts` re-exports widget-level components and hooks (e.g. `useActivityCards`, `ActiveSessionCard`). When deleting a widget component, drop the line in the barrel — the barrel is the only public surface to clean up.
- **SessionHeader is a homonym.** Two distinct components share the `SessionHeader` name across the web tree:
  - `packages/web/src/widgets/coder-session/ui/SessionHeader.tsx` — the dense single-row component using `CoderSessionSummary`. Consumed only by `SessionList`. **Deleted in T-001.**
  - `packages/web/src/pages/session/ui/SessionPage.tsx:267` — a locally-scoped sub-component used for the SessionPage transcript header (props: `issueNumber`, `issueTitle`, `meta`, `statusKind`, `turnCount`, `recoveryBar`). Unrelated to the dead widget above.
  Tests that mention "SessionHeader" in comments and `describe` titles inside `SessionPage.test.tsx` reference the local one and are correct as-is.
- **"Dead component" tests live in `tests/`, not `src/`.** The acceptance criterion restricts the import grep to `packages/web/src`, but tests under `packages/web/tests/` also import dead components. Removing a dead `widgets/*/ui/*.tsx` file requires also removing (or migrating) any `tests/*.test.tsx` that imports it; otherwise `tsc -b` fails. `useCoderSessions` live-event coverage that previously lived alongside `SessionHeader` tests in `SessionLiveness.test.tsx` already exists in `tests/useCoderSessions.test.tsx` under `describe('useCoderSessions live event handling', ...)` — deleting `SessionLiveness.test.tsx` does not lose coverage.

## Codebase Patterns (continued)

- **`WorkflowRunSession` carries no `stage` field.** The server projection `ToWorkflowDto` (`packages/server/src/Mohist.Server/Workflow/Services/Sessions/AgentSessionQuerier.cs:560`) maps only `sessionName` — the canonical session label — not a separate `stage`. Session names in practice are the pipeline stage names (`plan`, `build`, `check`, `integrate`), so deriving a session's stage from `sessionName` against the known pipeline set is consistent with how the rest of the app treats them. Sessions whose `sessionName` falls outside the pipeline list are simply un-stageable (no stage filter matches them).
- **Native `<select>` is the established pattern for small filtering controls.** `WorkflowProfileControl.tsx:99-115` uses a native `<select>` with `data-testid` and `fireEvent.change` (see `WorkflowProfileControl.test.tsx:136`). The heavier base-ui `Select` component (`shared/ui/components/select.tsx`) is reserved for dialog/picker surfaces and is overkill for a compact toolbar control. New compact selects should follow the `WorkflowProfileControl` shape.
- **Hook testability pattern.** `useEventTimeline.test.ts` shows the convention: mock the entity-layer hook with `vi.mock('../../../entities/...', ...)`, then call `renderHook(() => useFoo(...))` from `@testing-library/react`. Use `act(() => result.current.setX(...))` for state mutations and assert on `result.current.x`. A `nowMs` parameter on hooks that compare against `Date.now()` (e.g. duration sort) makes tests deterministic without mocking the global clock.

## Decisions

- T-002 adds `useWorkflowSessionFiltering` at `packages/web/src/widgets/issue-workflow/model/useWorkflowSessionFiltering.ts`. Owns `statusFilter: string | null`, `stageFilter: WorkflowPipelineStage | null`, `sortKey: WorkflowSessionSortKey`. Memoized filtered+sorted output is exposed as `sessions`. The hook also surfaces `availableStatuses` (required ones: running/completed/failed), `availableStages` (intersection of the pipeline set with what the current session set actually contains), and `totalCount` so the panel can show "Showing N of M" without losing the unsfiltered total.
- T-002 keeps the existing `WorkflowSessionsPanel` summary line (`${n} sessions · tokens · peak ctx · cost`) computed over the **unfiltered** session set so the panel header still reflects the full workflow run, and adds a separate "Showing N of M sessions" notice only when a filter actually hides rows.
- Token fallback in `getSessionTotalTokens`: `usage.totalTokens` if numeric, else `inputTokens + outputTokens`, else `0`. Matches the proposal's note.
- Duration in `computeSessionDurationMs`: terminal statuses (`completed`/`failed`/`cancelled`) measure `completedAt - startedAt` (or `- createdAt` when `startedAt` is null); non-terminal measure `now - startedAt` (or `- createdAt` when `startedAt` is null). Mirrors `SessionPage.tsx:272-276` but always returns a positive duration for live sessions so duration sort is meaningful. The hook accepts a `nowMs` option for deterministic tests; the panel passes nothing and falls back to `Date.now()`.
- Stage filter UI keeps all four pipeline stages listed at all times (per spec) but `disabled`s the ones that aren't currently present in the session set, so users can see they exist even before any session of that stage exists.

## Gotchas

- The existing `WorkflowSessionsPanel.test.tsx` `session()` helper defaults `status` to `'completed'` and `sessionName` to `'check'`. After T-002 the panel exposes filter controls only when the session list is non-empty, so the "no sessions yet" branch (and the `!workflowRunId` early return) does not render the controls — no need to update those tests.
- `fireEvent.change` on a `<select>` works with `target.value` in jsdom. The tests must encode the option value (`'running'`, `'failed'`, `'build'`, `'tokens'`) — not the visible label — in `target.value`.
- Tests that compare rendered transcript link `href`s must include the project path prefix (`/Test%20Project/...`) because `render()` from `tests/test-utils.tsx` wraps the app in `ProjectProvider` which prepends the project slug via `useProjectPath`. The plain `/issues/...` shape never appears in rendered output under jsdom.
- `WorkflowRunSession` does not have a `stage` property. Any code that needs to know a session's stage must derive it from `sessionName` via `getSessionPipelineStage` (exported from the hook module) — do not assume `session.stage` exists.

# Issue 257 — progress log

## Codebase Patterns

- `IIssueGrain.CreateAsync` signature is a positional parameter bag (no
  DTO record). Adding a new optional arg is the established way to grow
  it; the new arg goes at the end with a default value so existing
  callers (notably the in-test `CreateIssueAsync` helpers) compile
  unchanged.
- The PATCH contract in this codebase is a "raw-presence-aware
  three-state" model. `UpdateIssueRequest.BindAsync` re-parses the
  request body into a `JsonElement` and stores the field set in
  `Fields` (and re-exposes the raw element in `Raw`). The grain's
  `UpdateFullAsync` then reads `PresentFields` to decide between
  three options per field: absent (leave alone), present-and-null
  (clear), present-and-value (replace). For workflow profile id this
  maps directly to: absent = preserve, null = clear to inherit
  default, value = replace. Any new PATCH-able field on
  `UpdateIssueData` should follow the same pattern.
- The grain is the only place that mutates the issue aggregate; the
  route handler does **not** call the aggregate's transition methods
  directly. The PATCH route must validate "known profile id" (POST
  does the same) but should let the grain enforce the
  started-issue-immutable rule and surface it via a dedicated
  exception so the route layer can map to a stable error code.
- Errors that mean "started-issue cannot change execution template"
  are mapped by the existing pattern of
  `ApiResults.Conflict(message, code)`; the route layer should keep
  using `Conflict` for the 409 to stay aligned with the existing
  draft-immutable conflict path (`InvalidOperationException` from the
  grain → `ApiResults.Conflict`).
- The IssueWorkflowProfileRegistry lives in
  `Mohist.Server.Issue.Services.WorkflowProfiles` and is registered
  as `IScopedService`. Route handlers can take it as a parameter;
  the grain already injects it via constructor. Both layers can use
  it for existence checks.
- The unified workflow-profile effective resolution lives in
  `EffectiveWorkflowProfileResolver` (issue → project default →
  system default) and is consulted by `IssueQuerier.ToInfo` (the
  static overloads still hardcode `mohist/default`; the instance
  overload using the resolver is what the read paths go through).
  PATCH/CREATE never call the resolver — they only persist the
  selection; resolution happens at read time.

## Task T-002 — wire create/persist + PATCH update + started-issue guard

- Extended `IIssueGrain.CreateAsync` and `IssueGrain.CreateAsync`
  with a `workflowProfileId` parameter (optional, default null).
  Validation happens at the grain: throws
  `UnknownWorkflowProfileException` when the supplied id is not
  in `IssueWorkflowProfileRegistry`. The POST handler also does a
  cheap pre-check so the request can return 400 without paying the
  grain call; the grain-side check is the authoritative one and
  also gets surfaced as 400.
- Extended `Domain.Issue.Create` with a `workflowProfileId`
  parameter; the aggregate setter normalizes whitespace to null and
  the constructor records an `IssueWorkflowProfileChanged` event
  when a non-null selection is supplied (matches the established
  `ReplaceWorkflowProfile` event semantics for free).
- Extended `UpdateIssueData` with `WorkflowProfileId` and the
  three-state semantics: `present` ⇒ call
  `_issue.ReplaceWorkflowProfile(data.WorkflowProfileId)` on the
  aggregate, which handles value/null/whitespace uniformly.
- Extended `UpdateIssueRequest.BindAsync` to capture
  `workflowProfileId` presence in the `Fields` set and bind the
  string value (so it stays null for both "absent" and
  "present-and-null"; presence comes from `Fields`).
- Added a new `WorkflowProfileLockedException` (sealed,
  `InvalidOperationException`) thrown by the grain before any
  field-level work, so a started issue is never half-mutated by a
  profile change. The PATCH route maps it to a 409 with code
  `workflow_profile_locked` and the exception message includes the
  active workflow run id so the caller can identify the run.
- Added `UnknownWorkflowProfileException` (sealed,
  `ArgumentException`) for the unknown-id path. POST and PATCH both
  return 400 with code `unknown_workflow_profile`; PATCH only
  validates non-null values (null is a valid "clear" signal).
- The variable/prompt PUT endpoints in `IssueRoutes.WorkflowProfile`
  are untouched. They mutate `IssueWorkflowProfile` (the
  `IssueWorkflowProfileManager` runtime overlay table) and never go
  near `issue.WorkflowProfileId` — D5's distinction between
  execution-template and runtime-overlay is preserved structurally.
- New regression test file
  `Specs/Issue/Api/IssueWorkflowProfileApiConsistencySpecs.cs`:
  - `CreateIssue_WithPrWorkflowProfile_PersistsAndReadModelAgrees`
    (detail/list/workflow-profile endpoint all report
    `mohist/pr`).
  - `CreateIssue_WithoutWorkflowProfile_InheritsDefaultOnAllReadSurfaces`
    (no selection → every read surface reports `mohist/default`).
  - `CreateIssue_WithUnknownWorkflowProfile_ReturnsBadRequest`
    (400, code `unknown_workflow_profile`).
  - `PatchIssue_ReplacesWorkflowProfile_WhenPresent` (PATCH
    value, all read surfaces report the new value).
  - `PatchIssue_WithoutWorkflowProfile_PreservesExistingSelection`
    (absent key keeps the prior `mohist/pr`).
  - `PatchIssue_NullWorkflowProfile_ClearsSelectionAndReadsInheritDefault`
    (present-null clears; reads fall back to `mohist/default`).
  - `PatchIssue_WithUnknownWorkflowProfile_ReturnsBadRequest`
    (PATCH with unknown id returns 400).
  - `PatchIssue_ProfileOnStartedIssue_ReturnsConflictAndLeavesSelectionUnchanged`
    (issue started, PATCH profile → 409 with
    `workflow_profile_locked`, selection unchanged).
  - `PutVariables_OnStartedIssue_StillSucceeds` (PUT
    `/workflow-profile/variables` is unaffected by the
    started-issue guard; the rejection is scoped to the
    execution-template change only).
  - `PatchIssue_ProfileUpdate_PreservesConfiguredVariablesAndPrompts`
    (seed variables + prompt via the runtime endpoints, PATCH the
    profile, then assert the variables and prompt are still
    intact and the profile id changed).

## Gotchas

- POST handler default for `isDraft` is `true` per the existing
  `req.IsDraft ?? true` line. Tests that exercise the
  started-issue-guard path need to explicitly set `isDraft = false`
  on create; otherwise `StartWorkAsync` rejects the start with
  `IssueStartBlockedException(IssueStartBlocker.Draft)`.
- The grain throws `WorkflowProfileLockedException` **before** any
  field-level mutation, including attachment validation. This is
  intentional: if the caller can't change the profile, we don't
  half-apply other changes either.
- `UpdateIssueRequest` uses `string?` for `WorkflowProfileId`. The
  three-state semantics (absent vs present-null) is read off
  `req.Contains(nameof(WorkflowProfileId))` (the Fields set), not
  off the bound value. The bound value carries the value-or-null
  payload that the grain will apply.
- LSP reports pre-existing test errors in
  `IssueWorkflowProfileConsistencySpecs.cs` referencing
  `Mohist.Server.Project.Domain.ProjectEntry` (the file uses
  `Mohist.Server.Infrastructure.Data.Project.ProjectRow`).
  `dotnet build` is clean — the LSP is stale. Left untouched
  (out of scope for T-002).

## Task T-003 — startup honors effective profile; endpoint already in agreement

- `WorkflowProfileManager.LoadTemplateAsync` now takes a new constructor
  dependency `EffectiveWorkflowProfileResolver` and uses it to resolve the
  effective profile id (issue selection → project default → mohist/default)
  in the final fallback. Previously the fallback hardcoded `mohist/default`,
  so an issue whose effective profile was `mohist/pr` would still start
  the default workflow definition. The advanced override chain (issue
  custom YAML → issue SourceTemplateId → project DefaultTemplateId) is
  unchanged — overrides still take precedence when present.
- Removed the project-default auto-seed in `IssueGrain.StartWorkflowAsync`
  (`SetDefaultTemplateAsync(projectContext.Id, "mohist/default")` when the
  project's `DefaultTemplateId` was empty). Without it, a freshly started
  issue with an explicit `mohist/pr` selection no longer has the project's
  default template silently shadow the issue's profile. The
  `EffectiveWorkflowProfileResolver` fallback in `LoadTemplateAsync`
  handles the no-project-default case correctly (returns the system
  default).
- `IssueGrain.StartWorkflowAsync` now resolves the effective profile for
  the **prompt merge** step too. Previously it hardcoded
  `_profiles.Get(IssueWorkflowProfiles.DefaultId)` which meant a PR issue
  inherited default prompts even though the run used the PR definition.
  The cast was widened from `MohistDefaultIssueWorkflowProfile` to the
  shared `MohistIssueWorkflowProfileBase` since both default and PR
  profiles expose `GetMergedPromptsAsync`.
- `BuildIssueWorkflowProfileResponseAsync` (D6) was already correct
  post-T-001: `profileId` is sourced from `info.WorkflowProfileId`, which
  the `IssueQuerier` instance `ToInfo` overload projects through
  `_effectiveProfileResolver.Resolve`. No edit required.
- Test setup changes: `WorkflowProfileManager` constructor gained a
  required `EffectiveWorkflowProfileResolver` dependency. Updated three
  manual instantiation sites
  (`WorkflowGrainSpecs.GetQuerier`, `WorkflowGrainTestHelpers.GetQuerier`,
  `WorkflowProfileManagerSpecs` constructor) to pass the resolver via
  `IssueWorkflowProfileRegistry`. Also added
  `siloBuilder.Services.AddScoped<EffectiveWorkflowProfileResolver>()`
  to `GrainTestConfig.ConfigureSilo` because the grain silo does not call
  `ConfigureMohistServices` (and therefore does not pick up the scanned
  registration automatically).
- Test seed helper (`WorkflowProfileManagerSpecs.SeedAsync` /
  `SeedRunContext`) now optionally accepts `issueWorkflowProfileId` so
  callers can simulate a serialized issue whose `WorkflowProfileId` is
  non-null. Added `Title = "Seeded issue"` so `IssueStore.Deserialize`
  can satisfy the required `title` property on `Domain.Issue`.

## Gotchas

- The project-default fallback in `LoadTemplateAsync` (step 3) **still
  wins over the effective-profile fallback** (step 4) when the project's
  `DefaultTemplateId` is a known system profile (e.g. `mohist/default`).
  This is intentional: project-default is treated as a template
  override. The fix only changes behavior when no override AND no
  project default apply — i.e. when the effective profile is the only
  remaining source of truth. Removing the auto-seed was necessary
  because it was creating that false project default on every fresh
  project start.
- The `WorkflowProfileManager` constructor's new dependency is required;
  any future caller that wires DI by hand (tests, harnesses) MUST pass
  `EffectiveWorkflowProfileResolver`. The fixture-based suites that go
  through `MohistIntegrationFixture` / `MohistDbFixture` pick it up via
  `AddMohistConventionalServices` automatically.
- `WorkflowProfileManager.ResolveEffectiveProfileIdAsync` reads the
  issue's stored `WorkflowProfileId` by deserializing the issue state
  JSON via `IssueStore.Deserialize`. This means a typo / corrupt state
  surfaces as a deserialization error rather than a silent default — the
  pre-existing seed tests needed the `title` field added to satisfy the
  required property on `Domain.Issue`.

## Task T-004 — CLI update --workflow-profile + show rendering

- `mo issue update <n> --workflow-profile <id>` now exists. It follows the
  same three-state semantics the server's PATCH contract already uses
  for `workflowProfileId`:
    - flag absent → key omitted from the PATCH body (preserves server-side selection)
    - flag present with a value → sends `"workflowProfileId": "<id>"`
    - flag present with an empty/whitespace value → sends `"workflowProfileId": null`
      (clear the selection; reads fall back to the inherited default)
  The presence check uses `ctx.GetResult(workflowProfileOpt) is not null`,
  matching how every other "optional presence-aware" update flag
  (e.g. `titleProvided`, `priorityProvided`) is detected in
  `BuildUpdate`. The bound string value is normalized to `null` when
  empty/whitespace before being placed in the payload.
- Created an additional `CreateAsync` create-side fix: the create payload
  used to unconditionally include `"workflowProfileId": <effective>`,
  which would serialize as `"workflowProfileId": null` even when neither
  the flag nor the frontmatter said anything. That violated the cli-interface
  spec scenario "Create issue without workflow profile omits the key".
  The create payload now only adds the key when the user supplied the
  flag OR the frontmatter surfaced a `recommended_workflow`. Existing
  flag-provided / frontmatter-provided behavior is unchanged; the only
  observable difference is that "no flag, no frontmatter" no longer
  ships an explicit null in the body.
- `TableRenderer.RenderIssueShow` now prints `profile: <id>` from the
  `workflowProfileId` field on the issue read model whenever it is
  non-empty. With T-001's resolver wired into the read model, this is
  the effective profile (issue selection → project default → system
  default). Server emits `workflowProfileId` via standard camelCase JSON
  serialization of `IssueInfo.WorkflowProfileId` — no `JsonPropertyName`
  override needed, just a `StringOf(data, "workflowProfileId")` lookup.
- The existing error path for "started issue cannot change profile"
  already worked because `PrintPatchAsync` → `PrintResponseAsync` reads
  the envelope `{success, error, code}` and writes
  `<error> (<code>)` to stderr with a non-zero exit code on a 409. No
  CLI-layer changes were needed beyond wiring the flag — the server's
  `WorkflowProfileLockedException` (T-002) already maps to a 409 with
  `code: "workflow_profile_locked"`. The tests assert the server message
  text and the code both appear on stderr and the exit code is non-zero.
- Default output mode for `mo issue show` is `json`. Tests that assert
  on the rendered table pass `--output table` to switch to
  `TableShape.IssueShow` rendering (matches how `mo issue show --help`
  is exercised elsewhere in the suite).

## Gotchas

- `BuildCreate` always requires a body (existing behavior). Tests that
  drive the create flow must pass `--body` (or `--body-file` /
  `--body-stdin`); otherwise the CLI short-circuits with
  "issue body is required" and never hits the HTTP layer.
- The CLI server tests in `packages/server/.../IssueCliBodyInputSpecs.cs`
  use the idiomatic assertion
  `Assert.Null(body?["workflowProfileId"]?.GetValue<string>())`. That
  remains true both when the key is absent (returns null via the
  indexer) and when it is present with a JSON `null` value, so the
  "omitted key" behavior introduced in T-004 doesn't break them.
- The server's PATCH `BindAsync` is `string?` (per T-002's
  `UpdateIssueRequest`); "present-and-null" vs "absent" is read off
  the `Fields` set, so the CLI sending a literal JSON null vs omitting
  the key both map to the same three-state semantics on the server.
  Choosing "send null" for the empty-flag case is fine, but the spec
  specifically asked the flag-absent path to omit the key — which is
  what the update and create commands now both do.

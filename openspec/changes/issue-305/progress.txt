## Codebase Patterns

- New command groups follow the `ProjectRepoCommands` pattern: a single file `MohistCliCommands.ProjectWorkflow.cs` with `internal static class ProjectWorkflowCommands` containing `Build()` and private per-verb builders.
- `template` and `config` sub-groups are separate methods on the same class; `config` is registered as a skeleton in T-001 (empty command, filled in T-002).
- Template CRUD verbs:
  - `list` → `PrintWithOutputAsync` with `ProjectTemplateList` table shape
  - `create` → `PrintPostWithOutputAsync` with `ProjectTemplateShow` table shape, `--yaml` option with `ExpandAtFileAsync`
  - `show` → `PrintWithOutputAsync` with `ProjectTemplateShow` table shape
  - `update` → `PrintPutWithOutputAsync` with `ProjectTemplateShow` table shape, `--yaml` option with `ExpandAtFileAsync`
  - `delete` → `PrintDeleteWithOutputAsync` with `ProjectTemplateShow` table shape
- JSON output mode (`-o json`) prints only the `data` portion of the envelope (via `PrintResponseAsync`), not `{success, data}`. Tests must check for data content, not `"success"`.
- All verbs reuse `ProjectRefOption()`, `OutputOption()`, `ValidateOutputMode`, `ResolveProjectIdAsync`.
- Table renderers for project templates added in `TableRenderer.ProjectWorkflow.cs` (new partial), with `ProjectTemplateList`/`ProjectTemplateShow` switch cases in `TableRenderer.cs`.

## Decisions

- Config subcommand is registered as empty skeleton in T-001 so `mo project workflow --help` lists both `template` and `config` from the start (aligns with spec AC).

## T-002 Recordings

- Config verbs mirror issue-level `BuildWorkflowConfig*` closely:
  - `get` → `PrintProjectWorkflowProfileAsync` (same two-GET pattern: profile + prompts, merge, render)
  - `set` → composite: `--default-template <id>` (PUT), `--var`/`--stage-var` (PATCH), `--vars-file` (PUT full replace), `--prompt` (PUT)
  - `clear` → composite: `--default-template` (DELETE, bool flag requires `!result.Implicit` check), `--var` (PATCH null), `--prompt` (DELETE)
  - `preview <key>` → POST prompts/{key}/preview
- `--vars-file` parsed from JSON file via `JsonNode.Parse` then passed as `object` to `PrintPutWithOutputAsync`
- For boolean options (`--default-template` in clear), `ctx.GetResult(opt) is not null` returns `true` even when not provided (implicit default value). Must check `!result.Implicit` to distinguish explicit from default.
- `RenderProjectWorkflowProfile` added in `TableRenderer.ProjectWorkflow.cs`; reuses `RenderWorkflowProfileVariables` and `RenderWorkflowProfilePrompts` from the issue-level partial (same partial class).
- Config get also uses `ProjectWorkflowProfile` table shape (different from issue-level `WorkflowProfile` which shows issueNumber, templateSource, etc.)

## T-003 Recordings

- `BuildSessionFollowup` in `IssueCommands` mirrors `AgentCommands.BuildSessionFollowup` precisely:
  - Uses `NumberArg()` + `SessionNameArg()` positionals (not session-id)
  - Reuses `BodyInputResolver.ResolveAsync` with custom `SourceFlags("--text", "--text-file", "--text-stdin", "text")`
  - Path: `/issues/{num}/sessions/{name}/followup`
  - POST body: `new { text = textValue }`
  - Uses `PrintPostWithOutputAsync` with `AgentSessionFollowup` table shape and `rawJson: true`
- No new `TableShape` or renderer needed — `AgentSessionFollowup` (delivery: sent) matches the response shape exactly
- `--text` option requires a value (Option<string?>), so theory tests for followup must include `--text "x"` extra args
- The `PrintEnvelopeAsync` with `rawJson: true` returns the full envelope including success, so JSON mode test checks for `"success": true` (unlike the usual `-o json` that strips the envelope)

## Codebase Patterns

- `AgentJobGrain` is a single-grain owner of an AgentJob's lifecycle. State serialized via `[PersistentState("agent-job")]`. Currently uses grain timers (`RegisterGrainTimer`) for backoff/timeout — those do NOT survive silo restart. For durable terminal-delivery recovery T-001 must use an Orleans `RegisterOrUpdateReminder` (proved by `packages/server/tests/Mohist.Server.SpecTests/Support/DispatcherFixture.cs:457` `SharedReminderTable`).
- `IAgentSessionGrain` already has `AppendSystemEventsAsync` (fire-and-forget, 200ms timer via `EnsurePersistenceTimer`). T-001 needs a NEW synchronous command `AppendTerminalCloseAsync` because the spec requires "acknowledges success only after the terminal fact is durable" and the existing path can return before flush.
- The architecture tests forbid: (a) `Domain` depending on `Orleans` or storage, (b) data stores depending on application layer, (c) cross-domain dependencies outside an allowed allowlist, (d) local `JsonSerializerOptions` (must use `JSON.Options`).
- The DB Context factory pattern is used throughout. For SQLite-backed grain cluster tests, `UseInMemoryReminderService` is used with a `SharedReminderTable` so reminder state can be inspected.
- `FakeTimeProvider` from `Microsoft.Extensions.Time.Testing` provides deterministic time control without wall-clock polling.

### AgentJobGrain durable terminal protocol

- A new private `EnterTerminalStateAsync(status, exitCode, failureReason, failureCategory, reason)` that:
  1. Idempotency check: if already terminal, attempt pending delivery (if any) and return.
  2. Compute the runner-precedence category if needed (output `failureCategory` → `WorkResult.Error.Code` → report status). Carry forward raw `failureReason`.
  3. Build `PendingSessionClose` with `DeliveryId` and record timestamp; assign to `State.PendingSessionClose`.
  4. Set `State.Status = Completed/Failed`, `State.FailureReason`, `State.TerminalResult`, clear timers.
  5. `await SaveAsync()`.
  6. Register reminder `agent-job-recovery` (durable; ~1s period).
  7. Attempt first delivery via `DeliverTerminalToSessionAsync`.
- `DeliverTerminalToSessionAsync`: invokes the session grain's `AppendTerminalCloseAsync`; on success clear `PendingSessionClose`, save, unregister reminder; on failure, leave pending.
- `ReceiveReminder`: if state not terminal → unregister (orphan); if terminal with no pending → unregister; if terminal with pending → retry delivery.
- `OnActivateAsync`: re-deliver pending if terminal and pending present (without waiting for the reminder).
- `ReportResultAsync` for already-terminal jobs: if pending, repair; else existing rejection.
- All terminal transitions (runner report completion, runner report failure, preflight, dispatch exhaustion, report timeout, forced `FailAsync`) call `EnterTerminalStateAsync`.

### AgentSessionGrain terminal command

- `AppendTerminalCloseAsync(AppendTerminalCloseCommand cmd)`:
  1. Load session.
  2. Idempotency: query transcript parts of type `session.closed` for any with the same `deliveryId` (in payload). If found → success (no-op).
  3. Persist state (no domain events; record `CurrentTurnEndedAt`), then synchronously write a transcript part with `Type=session.closed`, `CorrelationKey` = deliveryId, `Payload` containing status/exitCode/failureReason/failureCategory/deliveryId/recordedAt.
  4. On success → return.
  5. On persistence failure → quarantine the activation (mirror the existing `_sessionReloadRequired` pattern) and throw so AgentJob retries.

## Implementation Discoveries

- `Agent → Workflow` cross-domain dependency was unavoidable for accessing
  `WorkResult.Error.Code`. Added a flattened `WorkResult.ErrorCode` getter so
  AgentJobGrain can read the runner's category without touching the
  `Workflow.Domain.Run.ExecutionError` type directly.
- `AgentSessionGrain.AppendTerminalCloseAsync` must respect the AgentJob's
  bound runtime: when the runtime has been superseded by a reset, the close
  is dropped (matches the pre-existing `AppendRuntimeEventsAsync` semantics
  that returned [] for stale runtimes). The AgentSession acknowledges the
  delivery so the AgentJob clears its pending payload without retrying.
- The `TranscriptEventSummaryProjector` was extended to take turn sequence +
  part sequence + part id for terminal-fact selection so reason and category
  always come from the same latest applicable fact (issue-449 design
  decision 4). The current-runtime filter is applied at the projection
  boundary, not inside the projector itself, so the projection remains a
  pure reduction over the input events.
- The architecture test size ratchet required adding the new
  `AgentJobTerminalDeliverySpecs.cs` (30862 bytes) and the updated
  `GenericAgentSessionSummarySpecs.cs` (27070 bytes) to
  `spec-file-size-baseline.json`. The
  `Mohist.Server.SpecTests/Specs/Agent/Api/AgentJobRoutesSpecs.cs` baseline
  was bumped from 24516 → 24706 bytes after adding the
  `IRemindable.ReceiveReminder` shim methods to the test fakes.
- The new `ControllableAgentSessionTranscriptPersistence` and the
  `FailingAgentSessionTranscriptStore` decorator simulate transient
  transcript-store failures so tests can prove pending-payload recovery
  without wall-clock waits. The counter-style `QueueFailures(N)` /
  `ResetFailures()` API is needed because multiple AgentJob retry paths
  (initial report, OnActivate repair, reminder tick, redelivered report)
  share the same flag.

## T-002 Implementation Discoveries

- WorkflowRun ownership is persisted in `WorkflowRunRow.MetadataProjectId` and `IssueNumber` computed columns; deserializing `WorkflowRun` alone is insufficient for routed ownership validation. `WorkflowRunQuerier.LoadRoutingContextAsync` now returns the run plus those persisted ownership values.
- Explicit workflow-run lineage is authoritative. Issue-only resolution reads the IssueRow binding, rejects terminal/stale or mismatched runs, and never falls forward to another run. All unresolved routed contexts become an idempotent `workspace-unavailable` AgentJob plan with issue/epic and Agent snapshot metadata retained.
- `RoutedPlan` remains persisted as the canonical first-writer record after Runner acceptance for replay identity, but activation/reminder recovery must gate on `RunnerAccepted`; otherwise a later activation could repeat prepared dispatch. The durable reminder is removed at the acceptance fence.
- The routed activation spec uses `DeactivateOnIdle` on the target grain so the OnActivate recovery path is exercised deterministically while the reminder remains registered.
- Verification is green: focused routed-launch/launcher specs, `npm test`, `npm run typecheck -w packages/runner`, and `npm test -w packages/runner`.

## T-003 Implementation Discoveries

- Issue event-feed composition now belongs to `AgentOps/Services/IssueEventFeedAssembler`; the issue API no longer asks Workflow to merge Issue and WorkflowRun events, while the workflow-run endpoint keeps its existing limited read.
- `WorkflowEventQuerier.ListValidWorkflowEventsAsync` returns the complete invalidation-filtered sequence. The limited workflow endpoint delegates to it and truncates only for that endpoint, so AgentOps applies the cross-store time-first limit after complete candidate collection.
- Routed issue-feed candidates are selected from generic `agent-launch` sessions carrying the AgentJob trigger labels and an issue label. A transcript part is eligible only when it is failed, its payload delivery id equals its correlation key, and the id uses the canonical `agent-job:{jobKey}:terminal` prefix; Runtime and follow-up closes therefore cannot duplicate the routed outcome.
- The projected AgentSession envelope uses transcript-part id as its local id, `{sessionId}:closed:{deliveryId}` as event id, canonical AgentSession source/subject, terminal `LastSeenAt`, `1.0`, `application/json`, project/issue extensions, and terminal plus Agent/trigger correlation data.
- Focused unit coverage proves global selection with event-id/timestamp disagreement, equal-time ordering, full envelope projection, and non-canonical close exclusion. Existing CLI issue command specs continue to pass because the CLI consumes the issue events endpoint as raw JSON.

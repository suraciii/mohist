## Issue 517 — T-001 (Credential rotation with synchronous verification)

### Implementation notes

- **`AgentConnectionStore.HasBoundIdentity`** — was a `private static bool
  HasBoundIdentity(AgentConnectionRow)`. Promoted to `public static`, added an
  overload accepting `AgentConnection` (the domain object the route already
  holds), so the rotate-credentials and configure routes can check without
  reaching into the row. Both overloads kept so `BindSlackIdentityAsync` keeps
  its row-based call.

- **`SlackSetupVerifier.VerifyRotationAsync`** — new method that takes
  `appToken, botToken` explicitly and runs the same Slack calls as `VerifyAsync`
  (auth.test → bots.info → apps.permissions.scopes.list) via a shared
  `RunVerificationAsync(connection, botToken)` helper that returns a
  `RotationCheckResult { Verified, Reason, ResolvedTeamId, ResolvedAppId,
  ResolvedBotUserId }`. Crucially it does NOT read from or write to the secret
  store, and does NOT call `BindSlackIdentityAsync` — rotation must not rebind
  (the route handles store-on-success, and the binding is already set). The
  three scope checks (auth rejection, missing scope, App/Bot identity mismatch,
  Slack unreachable) all return `Verified = false` with the concrete reason
  string already produced by `VerifyAsync`, so messages stay consistent.

- **`POST /{connectionId}/rotate-credentials` route** — guards on
  `HasBoundIdentity(connection)` (must be bound; otherwise `identity_not_bound`
  — points operator to `configure`). Runs `VerifyRotationAsync`. On
  `!Verified` → `400 credential_verification_failed` with the concrete reason.
  On `Verified` but binding mismatch (team/app/bot ≠ bound) → `400
  credential_binding_mismatch` with a message naming the conflicting ids. Only
  on full success: stores both tokens via `ISecretStore`, clears `HealthReason`,
  and if the connection was `Unhealthy` with a credential-related reason
  (`IsCredentialRelatedHealthReason` keyword check on token/scope/credential/
  "App and Bot"), also flips `ConnectionHealth → Healthy`. Touches nothing
  else: `SetupProgress`, `OwnerSlackUserId`, `WorkspaceTeamId`, `AppId`,
  `BotUserId` are all left untouched.

- **`POST /{connectionId}/configure` guard** — added before the store calls:
  if `HasBoundIdentity(connection)` → `409 use_rotate_credentials` pointing
  operator to rotate-credentials. This closes the silent-overwrite regression
  (configure had been resetting `SetupProgress → WaitingForSlackService` and
  deferring verification to the next heartbeat, hiding failures). Connections
  without a bound identity still go through the original store-then-set path.

### Codebase patterns

- The `MohistIntegrationFixture` registers the real `SlackApiClient` and there
  is no `ISlackApiClient` override hook in the fixture. The simpler pattern is
  the one used by `SlackSetupVerifierSpecs` / `SlackOwnerClaimSpecs` — direct
  object construction with a `RecordingSlackApiClient` and an in-memory
  `TestSqliteDatabase`. The new `SlackConnectionRotateCredentialsSpecs` follows
  this pattern; the route logic is re-exercised by inline `RunRotateCredentialsAsync`
  / `RunConfigureAsync` helpers that mirror the lambda body, which avoids
  needing to re-stand-up a Web host and keeps the test under 2 seconds.

- `AgentConnectionStore.UpdateAsync` semantics: when a field name is in the
  `fields` set but the corresponding parameter is null, the row keeps its
  existing value (e.g. `connectionHealth: null` with `"connectionHealth"` in
  fields → no change). The rotation code passes the new health value
  conditionally and only adds `"connectionHealth"` to the fields set when it
  actually wants to clear the Unhealthy status — otherwise passing `null`
  would silently preserve it.

### Test coverage (14 new tests)

`SlackConnectionRotateCredentialsSpecs`:
- Verifier-level (6): valid rotation returns resolved identity; invalid token
  rejected with reason; missing scope rejected; different workspace resolves
  to different identity (verifier does not auto-rebind); verifier does not
  mutate store (Owner/setup preserved); FixSlackSetup connection with bound
  identity still accepts rotation.
- Route-level (8): success stores new tokens; binding-mismatch keeps old
  credentials; invalid-token rejected with reason; FixSlackSetup rotation
  clears HealthReason + flips to Healthy but leaves SetupProgress alone;
  Owner/setup preservation; unbound connection rejected with
  `identity_not_bound`; configure guard returns `409 use_rotate_credentials`
  on bound connection without regressing SetupProgress; configure succeeds
  on unbound connection.

### Gotchas

- When setting up "different identity" tests, must override BOTH
  `AuthTest` and `BotsInfo` on the fake — otherwise the `!bot.Bot.Id ==
  auth.BotId` check fires before the route reaches the binding-mismatch
  branch and the wrong error code surfaces. Caught two of these on the first
  run; both fixed.
- The verifier's `binding` check (App/Bot match between auth.test and
  bots.info) is internal to verification — it is a different signal from the
  route-level binding-mismatch check (auth result vs the connection's stored
  binding). The fake needs to keep them in sync to exercise the right branch.
## Issue 517 — T-002 (Owner transfer via claim-code Kind and atomic swap)

### Implementation notes

- **`SlackOwnerClaimCodeKinds`** — new constants class in
  `Infrastructure/Data/Slack/SlackOwnerClaimCodeRow.cs` exposing
  `Initial = "initial"` and `Transfer = "transfer"`. Discriminator stored on
  the row; default of `initial` makes the migration purely additive for
  existing rows.

- **`SlackOwnerClaimCodeRow.Kind`** — additive column. Hand-written migration
  `20260730000000_AddSlackOwnerClaimCodeKind` is `AddColumn` with
  `defaultValue: "initial"` so existing rows apply cleanly.
  `MohistDbContextModelSnapshot.cs` updated to mirror the model (column +
  `HasDefaultValue("initial")`).

- **`SlackOwnerClaimService.GenerateAsync`** — now has a `kind` parameter
  overload. Opposite preconditions:
    - `initial`: existing behavior — requires no owner AND `SetupProgress ==
      ClaimOwner` (the `|| Complete` check still rejects the no-claim-state +
      owner-already-set combination).
    - `transfer`: requires an existing owner AND `SetupProgress == Complete`
      (the inverse). Throws an explicit message ("Use claim-owner instead." /
      "Slack setup must be complete before transferring ownership.").
  Both kinds share the same hashing + expiry + supersession logic. The
  supersession `Where(...)` now includes `Kind == kind` so a fresh transfer
  code supersedes only prior *transfer* codes (initial codes stay valid), and
  vice versa.

- **`SlackOwnerClaimService.HandleInboundDmAsync`** — when a code matches,
  dispatches by `code.Kind`. Transfer codes call the new `TryTransferAsync`
  (with the `WHERE OwnerSlackUserId == currentOwner` conditional swap);
  initial codes keep the existing `TryClaimAsync` path
  (`WHERE OwnerSlackUserId == null`).

- **`TryTransferAsync`** — mirrors `TryClaimAsync`'s shape: load bot token
  → `UsersInfoAsync` → `IsEligibleMember` guard → `ExecuteUpdateAsync`
  with `WHERE OwnerSlackUserId == currentOwner` (the swap guard from design
  D2, eliminating the no-owner window). If the swap returns 0 rows
  (concurrent transfer or owner already changed), rejects with
  "Ownership has already been transferred. Generate a new transfer code if
  you still need to take ownership." → no swap, no double-owner.
  Self-transfer (sender == currentOwner) is explicitly rejected.

- **New decision kind** — `SlackInboundDecisionKind.Transferred = "transferred"`
  paired with an explicit "Owner transferred successfully." reply in the
  ingress route. Caller-visible `{ kind: "transferred" }` mirrors the
  existing `claimed` ack shape.

- **`POST /{connectionId}/transfer-owner`** — mirrors `claim-owner` exactly
  except the service call uses `kind: SlackOwnerClaimCodeKinds.Transfer`.
  Reuses the existing `claim_unavailable` error code on the
  `InvalidOperationException` precondition path.

### Codebase patterns

- The `SlackConnectionRotateCredentialsSpecs` pattern (direct construction +
  `RecordingSlackApiClient` + `TestSqliteDatabase`) carries over to the new
  `SlackOwnerTransferSpecs`. Tests use `FakeTimeProvider` for code expiry
  and injectable `ISlackApiClient` for membership probing — no real network.
- The `Migration` chain refuses to add a column with `HasDefaultValue` via
  `dotnet ef migrations add` when the previous migration's `.Designer.cs`
  delegates to `MohistDbContextModelSnapshot.BuildModelCore` — EF computes
  the diff against the current snapshot and emits an `AlterColumn` that
  would fail on fresh databases. **Workaround**: write the migration by
  hand as `AddColumn` (matches the established `20260612012629_AddPendingUploadKind`
  pattern) and keep the existing `.Designer.cs` delegating pattern unchanged.

### Test coverage (17 new tests in `SlackOwnerTransferSpecs`)

- Initial-vs-default behavior (2): `GenerateAsync(transfer)` rows are
  `Kind=transfer`; `GenerateAsync()` without kind defaults to `Initial`.
- Preconditions (2): transfer rejected when no owner; transfer rejected
  when SetupProgress ≠ Complete.
- Supersession scoping (1): regenerating a transfer code supersedes only
  the prior transfer code; initial codes stay valid.
- Expiry (1): expired transfer code is rejected with
  "This owner claim code has expired. Generate a new code." message.
- Atomic swap (1): eligible member redeems → `Transferred` decision;
  old owner is rejected on the next DM ("only to its owner"), new owner
  accepted.
- Single-use (1): replaying a used transfer code rejects.
- Self-transfer (1): sending the code to the existing owner is rejected
  with "You are already the owner of this Connection." — no swap.
- Membership theory (5): bot / deactivated / guest / cross-workspace
  senders all rejected; only current regular bound member succeeds.
- Self-transfer replay scenario: a superseded first code followed by
  a second code where only the second is usable (covers the "regenerating
  invalidates prior" acceptance criterion).
- Initial claim still works (1): claim path unchanged for an
  un-owned, SetupProgress=ClaimOwner Connection.

### Gotchas

- The migration inconsistency: EF's `AddSlackOwnerClaimCodes` migration has
  a `.Designer.cs` that delegates to `MohistDbContextModelSnapshot.BuildModelCore`.
  When the snapshot is updated to match the new model, EF can no longer
  emit an `AddColumn` migration — only `AlterColumn`. Since the dev
  database is the only consumer and migrations like
  `20260612012629_AddPendingUploadKind` established the hand-written pattern,
  the migration is hand-written with `AddColumn`. EF's `migrations remove`
  also resets the snapshot to a non-`BuildModelCore` form (line-by-line),
  breaking the other 13 migrations that delegate to it — restore via
  `git checkout` before any further `dotnet ef` use.
- SQLite does not support `OrderBy(row.CreatedAt)` (`DateTimeOffset`
  ordering inside SQL). Tests that need ordering read into memory first
  and count, instead of ordering in EF.
- The `ISlackApiClient` test fake needs `UsersInfoAsync(userId, …)` to be
  per-userId when the same test wants different identities for different
  senders (theory cases). Introduced `UsersInfoResponse` as a
  `Func<string, SlackUserInfoResponse>?` on the fake alongside the existing
  single-shot `UsersInfo` property.

## Issue 517 — T-003 (Enable/Disable lifecycle control and delete-boundary wording)

### Implementation notes

- **`POST /{connectionId}/disable`** and **`POST /{connectionId}/enable`** — both
  mirror each other: load connection → if already in target `DesiredState`,
  return current connection (idempotent) → otherwise `UpdateAsync(...,
  desiredState: target)`. The `fields` set contains only `"desiredState"`, so
  credentials, Owner, `SetupProgress`, `ConnectionHealth`, `HealthReason`,
  `AgentReadiness`, and `LastHeartbeatAt` are untouched. The `404` branch
  covers both "connection does not exist" and "UpdateAsync returned null".

- **Ingress DesiredState guard** — sits immediately after the
  `connections.GetAsync(...)` load and before the `IsDirectMessage` /
  workspace-mismatch / `HandleInboundDmAsync` / dispatch / inbox / launcher
  path. Returns `ApiResults.Ok(new { kind = "rejected", reason = "This
  Connection is disabled." })` so the adapter acks Slack with HTTP 200 and
  no inbox entry is created. This is the same non-error rejection shape used
  for non-owner DMs and empty prompts — keeps the adapter ack semantics
  uniform.

- **`DELETE /{connectionId}` response body** — now wraps the deleted
  connection plus a `slackAppRemovalNote` field stating that Mohist-side
  records were removed and the Slack App remains installed on the workspace
  until a workspace admin uninstalls it manually. The CLI `delete` command
  already pipes the response body through `PrintResponseAsync` →
  `data.ToJsonString()`, so the note reaches the operator's terminal without
  further CLI changes. The cascade itself is unchanged — `DeleteAsync` only
  soft-deletes the `AgentConnections` row, deletes the two Slack secrets,
  and runs `IAgentConnectionProviderCleanup` for inbox/outbox/claim codes.

### Codebase patterns

- The "disable/enable routes + ingress guard" change is small enough that the
  tests reuse the established `SlackConnectionRotateCredentialsSpecs` /
  `SlackOwnerTransferSpecs` pattern (direct `AgentConnectionStore` +
  `RecordingSlackApiClient` + `TestSqliteDatabase`, with route lambda body
  mirrored inline via `RunDisableAsync` / `RunEnableAsync` /
  `RunIngressGuardAsync` / `RunDeleteAsync` helpers). Avoids standing up a
  full Web host; the 19 lifecycle tests run in ~2 seconds.

- `AgentJobRow.Status` / `ProjectId` / `AgentId` / `SubmittedAt` are computed
  columns projected from `State` JSON via `json_extract`. Inserting a
  pre-`executing` AgentJob in tests therefore requires a `State` payload
  with `input.projectId` / `input.agentId` / `status` fields populated — the
  bare `State = "{}"` leaves the computed columns NULL. (The test now sets
  `State` to a small JSON literal; this is a test-only pattern, not a
  production code path.)

### Test coverage (19 tests in `SlackConnectionLifecycleSpecs`)

- Disable/enable semantics (5): Disable flips DesiredState; Enable flips it
  back; both are idempotent and report no time advancement; Disable and
  Enable leave credentials / Owner / SetupProgress / Health / HealthReason
  / WorkspaceTeamId / AppId / BotUserId untouched.
- Disable ≠ Degraded independence (2): a Disabled connection with healthy
  Slack reports `Disabled + Healthy`; a `Degraded(backpressured)` connection
  with Enabled DesiredState reports `Degraded + Enabled`. The two facts are
  stored and surfaced independently.
- Ingress guard (4): Disabled ingress returns `{kind:"rejected", reason:"…"}`
  at HTTP 200; Enabled ingress is not blocked; no inbox entry is created on
  the Disabled path; the guard fires before any claim/owner check (verified
  with `OwnerSlackUserId == null` + `SetupProgress == ClaimOwner` — the
  upstream branch is skipped).
- No-replay on enable (1): messages that arrived while Disabled leave zero
  inbox rows after Enable (the guard rejected them inline).
- Accepted-work preservation (2): `AgentJob` + `AgentSession` rows inserted
  before Disable survive Disable; the same rows also survive Delete. The
  rows carry computed-column `Status` / `ProjectId` from the `State` JSON,
  verifying that the row is read back intact and not cascade-deleted.
- Delete wording (2): the delete response carries a non-empty
  `slackAppRemovalNote` that contains "Slack App remains installed"; the
  delete cascade clears App/Bot secrets from the secret store.
- Missing-connection (1): Disable on a non-existent connection returns
  `null` from the store-level helper.

### Gotchas

- The ingress guard returning `ApiResults.Ok(...)` (not a 4xx) is required by
  design D4 — a 409 would tell Slack/Storm to retry, and the design wants
  the adapter to ack Slack on Disabled input without spawning retries. The
  test asserts the decision shape (`rejected` + reason) rather than the
  HTTP status code, but the route uses `ApiResults.Ok`, so the status is
  200 by construction.
- The tests inline-mirror the route lambda body rather than spinning up the
  HTTP host. The risk is that a future route edit silently diverges from
  the tests' mirror. This is the same tradeoff already accepted by the
  T-001 / T-002 specs in this issue.
- `AgentJobRow` and `AgentSessionRow` insertions need `State` populated (the
  Status / ProjectId / AgentId / SubmittedAt columns are `json_extract`
   computed columns). An empty `State` produces NULLs that look like the
   rows weren't really saved.

## Issue 517 — T-004 (Unified diagnostic with identity drift and owner availability probe)

### Implementation notes

- `VerifiedBotName` and `VerifiedBotIconUrl` are nullable snapshots on both the domain and persistence row. The migration is additive; existing connections remain `not_yet_verified` until a successful verification.
- `SlackBotInfo` keeps the existing three-argument constructor compatible and parses Slack's `icons` object through `SlackBotIcons`; `IconUrl` chooses `image_1024`, then the next-highest available resolution.
- `VerifyAsync` persists the snapshots together with the successful setup transition. `VerifyRotationAsync` remains verify-only as required by T-001 and returns the snapshots in `RotationCheckResult`; the rotation route persists them only after identity and credential checks succeed.
- `ConnectionDiagnostic.Compute` has no I/O, Slack, database, or clock dependency. `DiagnosticInputs` carries adapter liveness, owner availability, derived Agent readiness, and Agent name. Its facts retain setup, desired state, health, credential status, heartbeat, owner, readiness, and concrete identity values independently.
- The diagnostic route is separate from the raw view route. It loads the Bot token only for the lazy Owner `users.info` probe, applies `SlackOwnerClaimService.IsEligibleMember`, and returns `unknown` for missing credentials or `HttpRequestException`.

### Test coverage

- `ConnectionDiagnosticTests` covers all eight precedence rows, unique next actions, independent facts, all three drift kinds, and the not-yet-verified guard.
- `ConnectionDiagnosticSpecs` covers active, unavailable, and unreachable Owner probes with a fake Slack client.
- Existing setup and rotation specs now assert verified Bot name/icon capture.

### Gotchas

- The EF snapshot contains many `UpdatedAt` properties; when editing it manually, the new AgentConnection properties must be inserted in the AgentConnection block, not the first matching entity block.
- T-001's rotation verifier intentionally does not mutate the store. Snapshot persistence belongs to the successful rotation route so failed or mismatched rotations cannot overwrite the last verified identity.

## Issue 517 — T-005 (CLI connection operations and diagnostic rendering)

### Implementation notes

- `AgentConnectionCommands.Build` now registers `rotate-credentials`, `transfer-owner`, `disable`, and `enable`. Rotation uses the existing `ReadCredentialsAsync` and `IsProtectedFile` path without adding token options or changing the protected-file rules.
- The CLI entry-point credential guard now covers both `configure` and `rotate-credentials`. It rejects extra positional token values before System.CommandLine parses them, preventing parser diagnostics from echoing a token.
- `view` fetches `/diagnostic` and renders the primary state, reason, next action, and nested supporting facts. `list` remains a single raw list request and derives a compact state/next-action table from stored fields only; it never calls `/diagnostic` or Slack.

### Test coverage

- `CliAgentConnectionCommandSpecs` now verifies command registration, rotation endpoint/body and protected-input failures, transfer code/expiry output, enable/disable endpoint targeting and reported DesiredState, diagnostic rendering, and stored-facts-only list rendering.

### Gotchas

- `dotnet test ... --filter` is ignored by this repository's Microsoft Testing Platform setup. The CLI assembly's xUnit in-process runner supports class/method filtering directly and was used to isolate the first failure.

### Verification diagnosis

- The first full `npm run verify` attempt failed only in the Web suite: `src/app/App.test.tsx` timed out in the Logs navigation test (`logRequests` stayed at zero); Server (3452 spec tests) and CLI (1474 tests) passed.
- The affected App test passes when run alone. The Web suite also reproduced the failure under default parallel workers, while the same 389 files and 5154 tests passed with `--maxWorkers=1`.
- At the time of the failure, unrelated long-running `dotnet test` and Vitest processes from other workspaces were present. The failure is resource contention during parallel Web test execution, not an issue-517 implementation or assertion defect. No source workaround was added.

## Review fixes

- Credential rotation now validates the submitted App token with `apps.connections.open` and checks the returned Socket Mode `app_id` against the App resolved from the submitted Bot token before either secret is written.
- Disabled Connections now reject adapter-session renewal. Outbox claiming includes an enabled-Connection predicate in its atomic state transition, so an adapter cannot claim a new reply after disable.
- `SlackConnectionApiSpecs` exercises the mapped HTTP routes with a fake Slack client for invalid App-token rotation, disabled ingress and delivery claim, disabled adapter renewal, and diagnostics.
- Web now exposes `/:projectName/connections/:connectionId`. Its Agent Connection entity API and TanStack Query hook fetch the diagnostic, while the page shows the primary state, reason, and one next action before expandable independent facts.
- Removed copied route-lambda helpers from the Slack lifecycle and credential-rotation specs. `SlackConnectionApiSpecs` is now the HTTP entry-point coverage for rotation success/failure, enable/disable, ingress, adapter renewal, pending delivery withholding, delete wording, and diagnostics.

## Findings

1. **High: Routed AgentSessions do not retain their execution-definition snapshot.** `packages/server/src/Mohist.Server/Agent/Grains/AgentJobGrain.cs:502` opens a routed session with only the persisted runtime, workspace, and metadata. Unlike direct and mention launches, it does not pass `OpenAgentSessionCommand.Definition`. As a result `AgentSession.Settings.Definition` remains null and `AgentSessionQuerier.ResolveCanonicalFollowupTargetAsync` cannot deliver the original instructions, model, variant, or Skills for a routed session's later follow-ups. Construct the immutable definition from the canonical `RoutedAgentLaunchPlan` and stamp it while opening the session.

2. **High: Pi generic follow-ups ignore the captured model and variant.** `packages/runner/src/server/command-runtime.ts:207` forwards definition-derived options to Pi, but `packages/runner/src/runtime/pi/runtime.ts:211`'s `followup` implementation never calls `setModel` or `setThinkingLevel` in either its streaming or idle branch. A generic Pi session therefore follows the physical session's prior settings, including after reset or missing-binding recovery, rather than its immutable Agent definition. Apply the request options before submitting or steering the follow-up and cover the recovery path.

3. **High: A missing Skill makes a generic follow-up permanently non-retryable while recording an input that never executed.** `packages/runner/src/server/followup-handler.ts:186` claims the operation and `:190` persists `session.input` before resolving Skills at `:195`. On `skill_not_found` the handler returns `unavailable` without releasing the operation-journal claim. A retry is rejected as already claimed, despite no Runtime submission, and the transcript reports an accepted input. Resolve Skills before claiming/persisting the input, or release the claim and prevent the phantom input when resolution fails.

4. **Medium: Empty Skills are still sent to the OpenCode workflow runtime.** `packages/runner/src/runtime/executor.ts:421` unconditionally includes `skills: resolvedSkills.skills`, which is `[]` for an Agent definition with no Skills. The requirement says an empty list must add neither Skills resolution nor Skills input, and the Pi and AgentJob paths already omit the field. Omit the property when the resolved list is empty.

5. **Medium: The implementation expands the public contracts of ordinary runtime Actions.** `packages/runner/src/actions/opencode.ts:106` and `packages/runner/src/actions/pi.ts:211` now accept `options.instructions` and `options.skills` on every `mohist/opencode` or `mohist/pi` workflow action. The design explicitly keeps generic Actions' existing public input contract: only the server's `mohist/agent` transformation may carry Agent-definition-owned instructions and Skills. Keep these fields internal to the transformed dispatch path instead of accepting caller-provided values through the generic Action parsers.

6. **Medium: No user-facing read model identifies the execution definition used by an AgentJob.** The Issue acceptance criteria require users to see the definition used for an execution without inferring it from logs. The durable fields exist, but `packages/server/src/Mohist.Server/Api/AgentJobReadRoutes.cs:119` returns only terminal status/result data; `AgentJobViewDto` at `:161` exposes none of the snapshotted runtime, model, variant, instructions, or Skills. Add an appropriate read projection for the persisted execution snapshot, while keeping the generic AgentSession definition out of public Session DTOs as the design requires.

# Issue 134 — Progress Notes

T-001: Server-owned Agent execution-definition snapshot, strict launch binder, named-Agent Runtime override removal.

## Codebase Patterns

- Agent-owned persisted shape lives in `packages/server/src/Mohist.Server/Agent/Domain/Agent.cs`. `Skills` is `IReadOnlyList<string>` already on the domain model.
- `AgentLauncher.ResolveRuntime(agentConfig, launchOverride)` is the canonical runtime resolver currently shared by every launch path. Spec says we must drop `launchOverride` and route all paths through `agentConfig.runtime ?? opencode`.
- `AgentLauncher.ResolveModelAndVariant(agentConfig)` is the read-side helper for model/variant from `agentConfig`.
- AgentJobInput is `[GenerateSerializer]` record with append-only `[property: Id(N)]` fields; any new field must append the next free id (after Id(12) WorkflowRunId).
- RoutedAgentLaunchPlan is the same record shape used for routed-launch persistence. Free id after WorkflowRunId is Id(21).
- AgentSessionSettings is `record AgentSessionSettings(string? Model)` and persisted via `AgentSession.Settings`. The session's `Runtime` is in `AgentSession.Runtime` (AgentSessionRuntime record). We need a new immutable definition field.
- AgentJobGrain.BuildDispatch projects `prompt/instructions/model/variant/runtime` into the `with` JSON envelope — Skills must be added here too.
- AgentSessionFollowupRoutes (line 144-166) builds `wireTarget` with two shapes: workflow (no execution-definition needed) and generic. Generic must carry the immutable definition; workflow must not.
- The merged body for launch currently binds via `AgentSessionLaunchRequest` record with default JSON binding. The spec wants raw-body presence parsing (similar to `AgentUpdateRequest.BindAsync` and `RoutingRuleUpdateRequest.BindAsync`).
- `IAgentRuntimeOverrideResolver` only has one implementer: `IssueWorkflowProfileManager`. Removing it is safe — only `RoutingDispatchHandler` and `AgentSessionLaunchRoutes` use it.
- Agent definition already stores `Skills` (`Agent.cs` Id 7 in AgentInfo). The execution-definition snapshot will reuse this list (immutable copy).

## Gotchas / Decisions

- `AgentConfigSchema.AllowedKeys` still lists `runtime` because Agent CRUD must keep accepting it. Issue-level `agentConfig` writes should drop `runtime` per the design. Cleanest split: keep `AllowedKeys` for Agent CRUD; add a separate whitelist for Issue-level (`model`, `variant`) and use it in `IssueModelMetadata.ValidateAgentConfig` route validation. Issue-level `agentConfig` write surfaces (`CreateIssueRequest.AgentConfig` via PATCH/POST) must no longer persist `runtime`.
- The existing `AgentExecutionSnapshot` has `Instructions` + `AgentConfig`. Rename/extend it with `Runtime/Model/Variant/Skills`. Need to preserve the public surface used by `WorkflowItemTranslator`.
- The Skills list on the Agent is allowed to be empty (empty Skills ⇒ empty Skills field on snapshot, no resolution on Runner).
- OpenAgentSessionCommand currently takes `AgentRuntime`. The Session also needs the immutable execution definition. We add a new optional `Definition` field (append-only) on the command. CreateSession stamps it once; later opens must not override.
- AgentSessionReadModels: check what fields are projected to clients. The spec says "public Session DTOs" must not expose the definition — only the authenticated generic follow-up target carries it.

## Implementation Notes

- `AgentExecutionDefinition` is an Orleans-serializable value with Instructions, Runtime, Model, Variant, and ordered Skills. AgentJobInput and RoutedAgentLaunchPlan append Skills at Id(13) and Id(20); routed WorkflowRunId remains at Id(21).
- Generic AgentSession settings now retain the definition only when the session is created. Reopening a session does not replace it. Canonical follow-up projects it only for `agent-launch` targets; workflow targets remain definition-free.
- Agent-definition writes continue through `AgentConfigSchema.Validate`, while Issue model configuration uses `ValidateIssue` and rejects runtime. Historical Issue variables are not rewritten and are ignored by the named-Agent launch paths.
- Direct launch binding is raw JSON presence-based and accepts only lowercase `prompt` and `context`; `runtime` and all other top-level fields return `unsupported_field` before Agent resolution.
- `npm test` passed all Server, CLI, Web, and Runner tests (3274 Server SpecTests, 1525 Server UnitTests, 35 ArchTests, 5145 Web tests, 1438 Runner tests). `npm run build` passed after `npm ci`.

T-002: Runner Skill resolution and runtime delivery.

## Codebase Patterns

- Runner runtime boundaries remain Mohist-owned: OpenCode and Pi receive resolved `{ name, instructions }` values through their turn options; provider SDK DTOs are unchanged.
- AgentJob dispatch carries captured Skill names in `work.with.skills`; Workflow Agent transforms carry them in `with.options.skills`. Both paths resolve against the current task workspace.
- Generic authenticated follow-up targets carry an optional immutable `definition`; workflow targets remain definition-free. The runner re-resolves its Skills and rebuilds the execution envelope for each follow-up submission.

## Implementation Notes

- `SkillResolver` roots are `<workDir>/.agents/skills`, `$HOME/.agents/skills`, then non-empty `MOHIST_SKILL_ROOTS` colon entries. Names must be one safe segment, file contents are strict UTF-8 and non-empty, and realpath containment prevents symlink escape.
- `buildExecutionEnvelope` keeps legacy instruction-only prompts byte-compatible, while Skill-bearing turns use a JSON data block delimited by `[mohist-execution-definition]` markers.
- Empty Skills do not touch the filesystem and are omitted from runtime options. Missing, unreadable, malformed, or unsafe Skills return `skill_not_found` before provider prompt submission.

## Codebase Patterns

### `partial class` + private-access cross-partial rule (from C# language)

- `internal static partial class` merges all partials into one class at compile
  time, so `private static` members declared in the core partial are visible
  from every cluster partial with no visibility widening. This is what makes
  the carve viable — no `[InternalsVisibleTo]` or `internal` bump needed.

### C# tuple-destructuring shadowing gotcha

- Both `ValidateOutput` and `ResolveProjectId` helpers return
  `(T, int Exit)`. Many handlers call **both** helpers in the same scope, so
  destructuring both as `var (..., exit) = ...` causes CS0128
  (`exit` redeclared).
- Convention used here: the **first** call uses the helper name's own
  semantics (`var (mode, exit) = ValidateOutput(...)`) and the **second** call
  uses a helper-specific alias for the exit (`var (resolvedProjectId,
  resolveExit) = await ResolveProjectId(...)`). This keeps each call site
  readable while letting both helpers live in the same scope.
- Same rule of thumb applies to any future cross-cutting helper that returns
  `(T, int)`: name the exit after the helper (e.g. `validateExit`,
  `lookupExit`) to avoid collisions.

### Helper bodies are verbatim from `EpicCommands.ValidateOutput` / pure delegation

- `ValidateOutput` byte-for-byte matches `EpicCommands.ValidateOutput`
  (MohistCliCommands.Epic.cs:38). Do not "improve" it during carve steps —
  the match is the contract that keeps behavior preservation reviewable.
- `ResolveProjectId` is a pure-delegation wrapper. It adds no I/O and writes
  no extra diagnostics; `api.ResolveProjectIdAsync` already owns all error
  output and returns `null` on failure. The wrapper just turns `null` into
  exit code `1` symmetrically with `ValidateOutput`. If future carve steps
  touch the helper, this no-I/O invariant must hold.

### Two `internal` → `private` flips (D5)

- `ParseLabelsFromIssue` (line ~502) and `PrintCreateGuidance` (line ~680)
  flipped from `internal` to `private` once T-001 landed. They are called
  only from `BuildUpdate` / `LoadCurrentLabelsAsync` and `BuildCreate`
  respectively, both in the CRUD cluster. Repo-wide grep confirmed zero
  external callers — compile gate is the safe check. Subsequent carve steps
  move them to `Issue.Crud.cs` and they stay `private`.

### Idiom-collapse replacement shape

- 24× output-mode blocks and 31× project-id blocks all share a uniform 7-line
  / 3-line shape across the file. 22 output-mode sites were byte-identical
  and replaced via `edit.replaceAll`. 2 outliers used `invalidOutput` as the
  pattern variable name and were handled individually. The standard pattern
  never matched the helper body itself, so `replaceAll` was safe.
- Two sites had an inner `var mode = ((...)validation).Mode;` redeclaration
  inside a nested block (`BuildArchive` inside `if (allCompleted)`,
  `BuildSessionFollowup` at top level after `BodyInputResolver.ResolveAsync`).
  These inner redeclarations were dropped — outer `mode` from the helper is
  reused.

### `IssueTemplatesPath` placement

- Stays in the core partial even though only the Template cluster calls it —
  the cli-module-structure spec enumerates it as a required core shared
  helper alongside `NumberArg`/`ProjectIssuesPath`/`IsOptionProvided`.
  Carve steps preserve this placement.

## Carve notes for T-002 (and later)

### CRUD cluster top/bottom is non-contiguous

- The CRUD cluster spans **three non-adjacent** regions in the core file:
  1. `BuildList` + `BuildCreate` + `ApplyFrontmatter` (top, before the
     shared helpers);
  2. `BuildShow` + `BuildUpdate` + `LoadCurrentLabelsAsync` +
     `ParseLabelsFromIssue` (middle, sandwiching the shared helpers);
  3. `PrintCreateGuidance` (bottom, after `BuildStop`).
- The middle two regions sit **between** the three shared helpers
  (`IsOptionProvided`, `ValidateOutput`, `ResolveProjectId`) and the
  Lifecycle cluster, so a verbatim move cannot be one contiguous drop.
- Lesson for later carve steps that also intermix with shared helpers:
  do separate edits for each region, leaving the shared helpers exactly
  where they are. `Edit` (find/replace) on the whole CRUD dump at once
  is impractical for these clusters — split into top-group /
  middle-group / bottom-group edits.

### `PrintCreateGuidance` placement

- Lives in `Issue.Crud.cs` (not `Issue.Lifecycle.cs` where it physically
  sits in the core file at line 713-747). It is called **only** from
  `BuildCreate` (line 255) and is a post-create user guidance routine
  specific to the create result payload — design D1 cluster-ownership
  rule wins over physical locality.

### Partial file using-directives

- Each partial needs its own `using` block. The `using System.CommandLine.Parsing;`
  import required by `IsOptionProvided` (signature `ParseResult`, `Option`)
  stays only in the core partial because `IsOptionProvided` is the only
  cluster-crossing signature using `ParseResult` / `Option` outside their
  `Command` constructor paths. CRUD partial only needs `System.CommandLine`,
  `System.Net.Http` (for `HttpRequestException` in `LoadCurrentLabelsAsync`),
  and `System.Text.Json.Nodes` (for `JsonNode?` in `PrintCreateGuidance` /
  `ParseLabelsFromIssue`).

Task: Add the `service` command group for local managed-process lifecycle

## Codebase Patterns

- Each command group lives in `packages/cli/Mohist.Cli/MohistCliCommands.<Area>.cs` and is `internal static` with a `Build(MohistCliApi, IServiceProvider)`.
- Root registration happens in `MohistCliCommands.cs:Build`. Subcommand order matters only for help rendering.
- Shared option factories in `MohistCliCommands.cs`: `DryRunOption`, `UnitDirOption`, `LinesOption`, `FollowOption`, `OutputOption`, `ProjectRefOption` (returns `(Option<string?> Project, Option<string?> ProjectId)`).
- `IServiceInstaller` signature is fixed per-target (`StartServerAsync`, `StopRunnerAsync`, etc.). Reuse unchanged (design D1).
- `ServiceCommandOptions(DryRun, UnitDir, Lines, Follow)` is reused unchanged.
- Tests use `MohistCliCommands.RunAsync(...)` with a `FakeServiceInstaller` injected via the `installer` parameter (set up through `Support/CliTestFactory.CreateInternal` and direct construction). The standard helper excludes the installer from its return tuple; specs that need it construct the dependencies manually.
- Exit-code convention: usage/parse failure exits non-zero (typically `CliExitCode.For(CliExitOutcome.UsageFailure)`).
- `--help` invocations are routed through `System.CommandLine`, so a `Command("logs", "description")` produces a help block including the description.

### Gotchas / decisions during the build

- `Argument<ServiceTarget>` parses **case-insensitively** (`Enum.Parse` default). The dispatches use `service-server/Service-Runner` style; users can type `Server` or `server`. Pinned by `ServiceTarget_AcceptsCaseInsensitive`.
- `Argument<ServiceTarget>` name in `--help` shows as `<Runner|Server>` (System.CommandLine's auto-derived enum help). No third value can ever sneak in via typos; the post-error help reprint step lists the allowed values too.
- The `--help` description block for the service group fits in two lines and stays terse on purpose — the verbs' own descriptions carry the operational detail (especially `logs`, which calls out non-interchangeability with `mo server logs`).
- `BuildSimple(verb, description, installer)` collapses what was originally three near-identical builders (`BuildLifecycle`, `BuildStatus`, `BuildLogs`-without-options) since they share the same option set (`<target>`/`--dry-run`/`--unit-dir`) and dispatch shape. `BuildLogs` is the only special case (adds `--lines`/`--follow`).
- Did **not** add `--project`/`--project-id` to any verb (spec explicitly forbids it). Verified via `ServiceHelp_AdvertisesNoProjectOption` and `Service_Help_DoesNotMentionRunnerOrServerLifecycleDetails`.
- Old `runner`/`server` lifecycle verbs left in place (additive per the task description; T-002/T-003 will retire them).
- Refused to widen the diff to also tackle the cross-cutting D6 string changes (`MohistCliApi.ServerUnavailableMessage`, etc.) — those belong to T-004 per the task graph. Running them here would silently surface `mo service start server` text before the `service` group is reachable from all routes, breaking the dependency chain.

### Open items for downstream tasks

- T-003 (`server` reshape) can remove `server start|stop|restart|status|logs|uninstall`; the new `service` group + `server logs` already covers the rest.
- T-004 (`system` retire, D6 string guidance) is unblocked once T-002 and T-003 land.

## Gotchas / decisions during the build

- Reused the exact API paths `project status` and `system logs` used — no Server route or response-shape change (design D3). The CLI simply relocates the same calls into the `server` group.
- Repurposing `server logs` from a service-manager read (via `LogsServerAsync`) to an application read (via `PrintGetAsync("/api/logs/tail")`) creates a temporary overlap with `system logs` (still registered, still working). T-004 will retire `system` entirely once T-002 lands; leaving both alive for now is intentional and matches the additive phase.
- Did **not** touch the cross-cutting D6 string changes (`MohistCliApi.ServerUnavailableMessage` still says "mo server start"). T-004 owns that work; the spec scenario for "Server unreachable emits start-service guidance" cannot fully pass until then.
- `mo server status` and the runner-level `mo runner status` are both reachable in T-003. The runner `status` is an HTTP read of `/api/projects/<project>/runners`; the server `status` is an HTTP read of `/api/status?all=true`. They have distinct intent (per-resource vs cross-project) and live in distinct command groups, so the AC's "read-only application facts" still holds.
- Renamed `Build`'s second parameter to `_` because TreatWarningsAsErrors flags unused parameters. Cleaner than `_ = provider` since the runner group (which still uses the parameter) lives in the same file and the call site already passes the same `provider` to both.
- CliInstallUpdateSingleEntryTests's two regression guards (`ServerHelp_DoesNotAdvertiseInstallOrUpdate` and `SurvivingServerSubcommands_StillResolve`) had to change because they iterated over the old eight-verb server surface; the new four-verb surface is asserted instead. `install`/`update` removal invariants are still pinned.
- CliSystemLogsCommandSpecs and CliRunnerCommandSpecs untouched — T-003 only touches the server half. The "mo server start" literal still in their `RunnerList_ServerDown_…` assertions survives this task and gets updated in T-004.

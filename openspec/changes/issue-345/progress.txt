## Codebase Patterns

- **Server session test fixture pattern**: `MohistIntegrationFixture` (collection "MohistIntegration") wraps a full Orleans silo + an `HttpClient`. Specs in `packages/server/tests/Mohist.Server.Tests/Specs/Sessions/` use `_fixture.Client.PostOkAsync(...)` / `PostAsJsonAsync(...)` and `_fixture.Services.GetRequiredService<...>()`. Polling the runner's work queue uses `POST /api/runner/{runnerId}/poll` and the response body is the `WorkDispatchResponse` envelope directly (NOT wrapped in `{ data: ... }` like most API endpoints).
- **Generic runner fixture pattern (per-spec)**: Existing `session-strategies-generic.spec.ts` uses a `GenericFakeAgent` + `FakeServerConnection` over a real `ClientSideConnection`/`AgentSideConnection` pair from `@agentclientprotocol/sdk`, with `streams: linkedStreams()`. The fake server's `nextGetGenericSession = null` (so `getAgentSession` returns null) and `nextGenericSession = { acpSessionId: "acp-session-1", workDir: "D:/work" }` for the response from `openAgentSession`. `setAcpProcessFactoryForTest(() => createFakeProcess(agent))` from `actions/acp-agent.ts` installs the fake ACP process.
- **Live session-id flow on generic axis**: `AgentSessionLaunchRoutes.cs:88` always mints `_input.AgentSessionId = sessionId` and stamps source-kind=agent-launch metadata. `AgentJobGrain.BuildDispatch:357` propagates non-empty agentSessionId verbatim. `runner/connection.ts:330` carries it into the action context. `actions/acp/session-events.ts:48-61` resolves `{ kind: "generic", projectId, sessionId }` from `ownerKind === "agent-job" && agentSessionId`. `actions/acp/session-events.ts:77-81` routes events through `serverConnection.agentSessionRuntimeEvents(...)` → server `RunnerRoutes.cs:324-340` → `IAgentSessionGrain.AppendRuntimeEventsAsync` → `TranscriptAccumulator.Accept`.
- **Trap to avoid in fake-agent tests**: With `requestedModel = undefined`, `runAcpGenericAgentSession` enters `runResumedWorkflowAgentSession` (not `runNewWorkflowAgentSession`), so `newSession` is NOT called on the fake agent. The fake agent should accept either path; tests should not assume which. ResumeSession is a valid flow for the first turn when the server already has an `acpSessionId`.
- **Transcript turn instrumentation**: `TranscriptAccumulator` flushes are gated by `PersistTimerDueTime` (200ms). `WaitForTranscriptPartsAsync(sessionId, expectedCount, IGrainFactory)` advances the grain via `FlushForTestAsync()` until at least N part rows exist. Each `toolCallId` collapses to a single part row (upsert by `Type+CorrelationKey`); message.delta events without `messageId`/`partId` use `type=text` as the correlation key, so multiple deltas without per-message ids share one row.
- **Multi-turn follow-up caveat**: A new turn is created when the next flush starts (after `CommitFlush` clears `_promptText` etc). Between flushes the persist timer is disposed. So calling `/runtime-events` twice in a row may batch into a single flush if no time advanced. The existing tests rely on this; don't assume batches produce separate turns unless you advance time or wait between them.
- **Server-side session payload convention**: `POST /api/projects/{projectRef}/agent-sessions/{sessionId}/transcript` returns `{ success, data: { turns: [], partCount, lastActivityAt } }`. The transcript read path matches `#47`'s workflow axis by `turns`/`partCount` only — only the agent-session-id axis changes.
- **Poll endpoint response shape**: `POST /api/runner/{runnerId}/poll` returns the `WorkDispatchResponse` envelope at top-level, not under `{ data }`. Unlike `/api/projects/.../agent-sessions` or `/api/projects/.../agents/.../sessions` which DO wrap in `{ data: ... }` via `ApiResponse`. Avoid `GetProperty("data")` when polling.

## T-002 transcript-axis reproduction harness

- **Runner-side (`tests/acp/session-strategies-transcript-axis.spec.ts`, 3 tests)**: Added a fake-agent harness that drives a generic launch through to a polled `WorkDispatchResponse` semantics and through `runAcpGenericAgentSession` against a fake ACP agent. Asserts:
  1. `agentSessionRuntimeEvents` receives `session.input`, `message.delta`, `tool_call.started`, `tool_call.updated`, `tool_call.completed`, and `usage.updated` events against the minted `agentSessionId`.
  2. No `session.closed` after a successful turn (matches the existing runner success-path suppression at `acp-agent.ts:47-49`).
  3. No calls into the workflow axis (`getWorkflowAgentSession`, `openWorkflowAgentSession`, etc.) — keeps the generic axis distinct.
  4. Follow-up turn reusing the cached ACP session delivers another set of events on the same `agentSessionId`.
  5. The action context's `agentSessionId` equals the launch-minted id and `ownerKind === "agent-job"` (with `workflowRunId` empty).
- **Server-side (`tests/Mohist.Server.Tests/Specs/Sessions/GenericAgentSessionTranscriptAxisSpecs.cs`, 4 tests)**: Drives the launch API end-to-end and asserts:
  1. The polled `WorkDispatchResponse` carries `agentSessionId == minted session id` and `workflowRunId == string.Empty` (launch-to-poll guard for D4 / agent-session-launch spec).
  2. After `POST .../agent-sessions/{projectId}/{sessionId}/runtime-events` with message.delta + tool_call.* + usage.updated, the persisted `GET .../transcript` returns a non-empty turn (assistant has text and tool parts).
  3. A follow-up batch (session.input + message.delta + tool_call.started/completed) appends more non-empty content accessible via the same session id; the read endpoint remains reachable by session id only (no `workflowRunId`/`sessionName` lookup needed).
  4. The session is reachable solely via the `/api/projects/.../agent-sessions/{sessionId}` axis (`/transcript` returns 200, while `/api/projects/.../issues/0/sessions/nonexistent/transcript` returns a non-200) — keeps #47's axis untouched.
- **Outcome**: D2 reproduces-green — without changing any source code, both tests confirm the runner's pipeline maps `agentSessionId` to `agentSessionRuntimeEvents` and that the transcript turn is non-empty when the agent produces deltas, tool calls, and usage. The previously-observed "messages:0/events:0" was reproduced only as a hypothetical; with the wiring in place, no behavioral fix is needed.
- **No server-side or runner-side code changes**: T-002's deliverable is purely test coverage (the design's verify-then-fix posture paid off — the launch path propagates `agentSessionId` correctly). T-003 still needs to harden the drop observability (`session-events.ts:65`) and add the launch-route regression guard at the spec level, but those are separate from this task's scope.

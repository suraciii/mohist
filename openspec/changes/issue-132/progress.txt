# T-002 Generalize SessionPage for generic AgentSession via SessionDataSource seam

Status: completed

## Files changed

### New files

- **packages/web/src/pages/session/data/SessionDataSource.ts** — `SessionDataSourceResult`
  interface defining the full data contract between a data source hook and the
  shared `SessionDetailShell`.

- **packages/web/src/pages/session/data/buildGenericSessionMetadata.ts** —
  Adapter mapping `GenericAgentSessionSummaryDto` → `SessionMetadata`,
  setting workflow-only fields (`stage`, `issueId`, `runtimeSessionLineage`)

- **packages/web/src/pages/session/data/useIssueSessionDataSource.tsx** —

- **packages/web/src/pages/session/data/useGenericSessionDataSource.ts** —
  Hook consuming T-001's `useGenericSessionSummary`, `useGenericSessionTranscript`,
  and `useGenericFollowup`. Returns a `SessionDataSourceResult`. Back link
  prefers issue context ref when present, falls back to agent profile.

- **packages/web/src/pages/session/ui/SessionDetailShell.tsx** — Shared shell
  component that accepts `SessionDataSourceResult` and renders the full session
  layout (header, sticky recovery bar, transcript, followup composer, sibling
  sidebar) uniformly for both issue-scoped and generic sources.

- **packages/web/src/pages/session/ui/GenericSessionPage.tsx** — Route entry
  for the `agent-sessions/:sessionId` path. Calls `useGenericSessionDataSource`
  and delegates to `SessionDetailShell`.

- **packages/web/src/pages/session/ui/GenericSessionPage.test.tsx** — 15 tests
  covering: loading/error states, header/back-link logic (agent vs issue ref),
  follow-up enable/disable for running vs completed/failed, recovery region
  (ContextHealthBar present/absent, no Compact/Reset, no sibling sidebar),
  transcript container presence.

### Modified files

- **packages/web/src/pages/session/ui/SessionPage.tsx** — Refactored from ~1000

  `<SessionDetailShell>`. `isCurrentSiblingSession` preserved for the existing

- **packages/web/src/widgets/coder-session/ui/SessionFollowupComposer.tsx** —

- **packages/web/src/widgets/coder-session/ui/SessionFollowupComposer.test.tsx** —
  Updated from hardwired `useFollowupMutation` mock to a simple `onSend` mock.

- **packages/web/src/widgets/session-transcript/model/useSessionTranscript.ts** —
  Added `terminalInvalidationKey` option to `UseSessionTranscriptOptions`.
  When set, overrides the hardcoded `['issues', issueNumber, 'coder-sessions', sessionId]`
  invalidation so generic sessions can use `['agent-session', projectId, sessionId]`
  instead. Used by `useGenericSessionDataSource`.

- **packages/web/src/app/App.tsx** — Added `agent-sessions/:sessionId` route
  mapping to `<GenericSessionPage />`, alongside existing issue-scoped routes.

## Design decisions

- `SessionDetailShell` takes `{ data: SessionDataSourceResult }` as a prop
  object (not spread) so it's a proper React component with predictable hook
  ordering. All hooks (useRef, useCallback, useEffect) are placed before any
  conditional return to satisfy React's rules of hooks.

- Data sources return **only data** (no JSX). All component rendering
  (`SiblingNavigation`, `SessionRecoveryActions`, `ContextHealthBar`,
  `CompactionLineageLink`) is done in `SessionDetailShell` or `SessionHeader`
  based on data flags. This keeps tests mockable — existing SessionPage tests
  mock `widgets/coder-session` and `widgets/session-health`, and these mocks
  are respected even when the imports happen inside `SessionDetailShell`.

- For the main transcript view, the recovery bar is rendered ONLY in the
  sticky scroll container (not duplicated in the header). Early-return branches
  (waiting, empty states) render the recovery bar inside the header.

- `useGenericSessionDataSource` sends the back link to the agent profile
  (`/agents/{agentId}`) by default, or to the referenced issue
  (`/issues/{issueNumber}`) when an issue context ref exists — matching the
  spec's OR clause.

## Gotchas

- `SessionDetailShell` must be called as `<SessionDetailShell data={data} />`
  (JSX component), never as `SessionDetailShell(data)` (function call). The
  latter breaks React's hook tracking inside the shell, causing "Rendered more
  hooks than during the previous render" errors.

- All hooks in `SessionDetailShell` MUST precede any conditional early return,
  or React throws "Rendered more hooks" on state transitions. This means
  useCallback/useEffect for scroll management must be at the top of the
  function body alongside useRef.

- Test state leakage between `it()` calls in GenericSessionPage tests requires
  a `beforeEach` that resets ALL mock module variables
  (`mocks.summaryData`, `summaryLoading`, etc.) — `afterEach` + `cleanup()`
  is insufficient because mock closure references survive.

## Design decisions

- `AgentProfileEditor` uses the `Dialog` component from the existing shared UI
  library (base-ui/dialog), which renders content via portals. Tests require
  `act()` wrappers around click/fireEvent to handle portal-based state updates.

- The profile editor follows the IssueModelSelector pattern for ModelSelect:
  reads models via `useAvailableModelIds`, model variants via `useModelVariants`,
  and uses `onChangeModelVariant` atomic callback.

- Session history on the detail page uses a single `useAgentSessions({ agentRef })`
  query and groups client-side (running/failed/ended), matching the spec's
  requirement to avoid N filtered round-trips. Recent is also derived client-side
  (sorted by recency, capped at 5).

## Gotchas

- `displayTurnCount` in `SessionDetailShell` uses `meta?.turnCount ?? turns.length`.
  Since `buildGenericSessionMetadata` hardcodes `turnCount: 0`, the `??` operator
  does NOT fall through to `turns.length` (0 is not null/undefined). Tests must
  check for "0 turns" rather than expecting the turns array length.

# T-004 New-session composer with context refs and launch

Status: completed

## Files changed

### New files

- **packages/web/src/pages/agent-session-composer/ui/AgentSessionComposerPage.tsx** —
  New-session composer page at route `agent-sessions/new`. Reads query params
  (`?agent=`, `?issue=`, `?epic=`, `?repo=`, `?ws=`) to pre-select agent and
  pre-fill context references. Agent selector uses `useAgents()` with Popover
  dropdown (searchable, archived marked). Context refs render as removable chips
  (ContextRefChip). Prompt via AttachmentComposer. Launch calls
  `useLaunchAgentSession`; on 201 navigates to `agent-sessions/:sessionId`.
  Error states: 'no available runner' (`NO_AVAILABLE_RUNNER` code/message) and
  'external agent unavailable' (`EXTERNAL_AGENT_UNAVAILABLE` code/message).

- **packages/web/src/pages/agent-session-composer/ui/AgentSessionComposerPage.test.tsx** —
  21 tests covering: query-param parsing (agent, issue, epic, repo, ws, multi),
  agent selection (dropdown open, selection), prompt validation (disabled empty,
  blurred error, enabled filled), launch call with args (basic and with context
  refs), navigation on success, context-ref chip remove, archived agent launch
  disabling (disabled button + warning), error states (no-runner with code,
  external-agent with code, message fallback, error present).

### Modified files

- **packages/web/src/app/App.tsx** — Added `agent-sessions/new` route declared
  before `agent-sessions/:sessionId` so the literal segment wins.

## Design decisions

- Agent selector uses Popover + Button (matching ModelSelect pattern) with
  search input, rather than the base-ui Select. This gives control over item
  rendering (archived badge per row) and avoids SelectValue content limitations.
- Prompt validation is driven by `promptTouched` (onBlur) instead of submit
  attempt, since the disabled button cannot fire click events. Error message
  appears when the textarea loses focus with an empty value.
- Error state detection checks both `error.code` (e.g. `NO_AVAILABLE_RUNNER`)
  and a case-insensitive `error.message` fallback, matching the ApiError code
  from the `request` client.

## Gotchas

- `fireEvent.click` on a disabled `<button>` does not trigger React's `onClick`
  handler (disabled buttons suppress events). Prompt validation must use blur
  tracking rather than click-to-submit approach.
- The mock `AttachmentComposer` must use `data-testid="prompt-textarea"` to
  match the prop passthrough (the real component merges `...textareaProps`).
  Tests querying `data-testid="attachment-composer"` will fail because the page
  passes `data-testid` through props to AttachmentComposer, which passes it to
  the underlying textarea.

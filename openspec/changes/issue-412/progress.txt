# Issue 412 redesign baseline

## Why the previous progress is superseded

The previous T-001..T-007 implementation completed an event-lineage plan built on random
IssueId/EpicId identities, Epic-owned membership rows, copied EpicId snapshots, Workflow binding
states/revisions, and a per-type EventCatalog registry. Repeated check failures exposed failures in
normal cross-aggregate crash windows. The user then confirmed a different domain model, so those
task completion claims no longer describe the accepted target.

The old implementation commits remain in the candidate as migration input. Replacement tasks must
remove or reshape them; they are not accepted progress and no task in the new tasks.json is marked
passing.

## Authoritative redesign

- Master spec commit: `71f2cd7b9 docs: define Issue-owned Epic membership`
- Live Issue #412 title/body updated to the number-only identity and Issue-owned affiliation model.
- Workdir rebased onto `origin/master` at that spec commit.
- New OpenSpec proposal/design/delta specs/tasks replace the old D5 denormalization and binding plan.

Core target:

- Issue identity: (`ProjectId`, `IssueNumber`)
- Epic identity: (`ProjectId`, `EpicNumber`)
- current affiliation authority: Issue.`EpicNumber?`
- Workflow local context: `{ ProjectId, IssueNumber, EpicNumber? }`
- cross-aggregate process: aggregate commit + durable event + idempotent target command
- event keys: `projectid`, `issue`, `epic`, `workflowrunid`, `stage` (plus independent entity ids)
- conformance: real producer-family paths and structural Stage, not a per-type catalog matrix

## Preserved independent repair

Commit `6ef69d923` adds `RejectIfRunReloadRequired()` at the start of `WorkflowGrain.StartAsync` and a
state-save-failure regression. This guard is independent of the superseded lineage protocol and must
survive T-006 cleanup.

## Current candidate debt to remove

The rebased branch still contains old implementation references including:

- random IssueId/EpicId and number alias resolution;
- EpicIssueRow/EpicActiveIssue ownership;
- copied EpicId lineage snapshots;
- AwaitingBinding, WorkflowBindingPending, binding confirmation, and lineage revisions;
- EventCatalog.RequiredAttributes, EnvelopeConformance, and CatalogOnlyTypes;
- issueid/epicid/issueno/epicno producer and fallback paths.

These are expected before new build tasks run. They must not be treated as compatibility requirements.

## Rejected implementation attempt

The first replacement T-001 attempt (`c75a3e263`) mixed typed-key primitives with an incomplete
data patch. It backfilled missing legacy IssueId values, silently deleted orphan membership rows,
left known owners without canonical columns, and tested copied migration SQL rather than a complete
owner migration. It was reverted by `2544a2475` before any later task ran.

The plan was split so identity primitives, Issue references, Epic references, runtime cutover, and
membership authority each have a separately enforceable boundary. Do not reuse the rejected
`20260716120000_AdoptScopedIssueEpicIdentity` migration.

### Constructive details

- `IssueKey` and `EpicKey` are `readonly record struct`s that validate in the primary
  constructor. Blank ProjectId and ProjectId containing the `:` separator throw
  `ArgumentException`. Non-positive numbers throw `ArgumentOutOfRangeException`. Default-like
  values cannot enter runtime use through the public surface; default values via the
  `default` keyword are visible but no caller route can construct them.
- `ScopedGrainKeyCodec` formats the exact canonical length for `(ProjectId, Number)`: number
  digits are computed up front and the destination span is allocated to that size, so the
  output never contains padding or NUL characters. Number text is invariant-culture
  `int.TryFormat`. `int.MaxValue` (10 digits) round-trips losslessly.
- `TryParse(string?, out string, out int)` validates both halves: separator must be present,
  exactly one separator (separator ambiguity is rejected), neither side may be blank, every
  character of the number side must be `0`-`9`, parsed number must be strictly positive.
- `Parse(string, out string, out int)` is the throwing counterpart used by typed-key callers.
- `GrainKey.Issue(IssueKey)` and `GrainKey.Epic(EpicKey)` are the only public Issue / Epic
  access methods. Reflection-surface test (`GrainKey_DoesNotExposeScalarIssueOverload` /
  `GrainKey_DoesNotExposeScalarEpicOverload`) confirms there is no `(string, int)` Issue or
  Epic overload to bypass typed construction.
- The one necessary comment lives on the `internal` legacy overload and explains only its
  reason and removal task (T-004). Names explain normal behavior.

### Test coverage (41 new tests)

- Round-trip (Format → TryParse → Format yields the original).
- Exact output length: `projectId.Length + 1 + NumberDigits(number)`.
- No NUL padding for short numbers.
- `int.MaxValue` (2_147_483_647, 10 digits) encoded exactly as `p:2147483647` with length
  12; round-trips losslessly.
- Invariant-culture number text (no thousand separators, no decimal).
- Construction rejects: blank ProjectId, separator-containing ProjectId, non-positive
  number (`0`, `-1`).
- TryParse rejects: `null`, empty, `:`, `proj_a`, `proj_a:`, `:1`, `proj_a:notanumber`,
  `proj_a:0`, `proj_a:-1`, `proj_a:1:2` (separator ambiguity), `proj::a:1`,
  `proj_a:1 ` (trailing whitespace), `proj_a: 1` (leading whitespace), `proj_a:1\0` (NUL).
- Cross-Project same-number isolation: `proj_a:42 != proj_b:42` and the typed keys are
  unequal.
- Reflection surface test proves the public GrainKey Issue / Epic surface has no
  `(string, int)` shortcut.
- Reflection surface test proves the random-id `Issue(string)` overload is non-public.

## T-002 delivered

### Current-state Issue owner inventory

- `Issues` is the aggregate root. Its legacy `IssueId` primary key remains only as the T-004
  transition lookup; stored `State` already derives the unique canonical (`ProjectId`, `Number`)
  pair and is the source used by this migration.
- `IssueWorkflowProfiles` now persists required `ProjectId` + `IssueNumber` with a unique scoped
  index. Legacy rows are backfilled through their owning Issue; every production create path reads
  the canonical pair from that Issue before inserting a profile.
- Issue-bound `WorkflowArtifacts` now persist `IssueNumber` beside their existing `ProjectId`.
  `WorkflowItemTranslator` carries the run's positive canonical number into the final artifact row.
  Pending uploads are owned by WorkflowRun/work item until bind and therefore are not a second
  Issue-reference owner.
- `Attachments` with `OwnerKind = issue` now persist `OwnerIssueNumber`; issue bind/replace writers
  set it and unbind clears it. Comment-owned and unbound attachments keep it null.
- `WorkflowRuns` store canonical Issue context in metadata. Legacy `issueId` annotations are
  reconciled to `projectId` + `issueNumber`; a stored computed `IssueNumber` and scoped index expose
  that context without another owner lookup. `WorkIssueRef` is a run-derived dispatch/read shape,
  not an independently persisted owner.
- `IssueComments`, `InboxItems`, `EpicIssues`, and `EpicActiveIssues` already persist
  `ProjectId` + `IssueNumber`. Reconciliation verifies those values against their referenced Issue
  and fails on missing or cross-Project rows instead of rewriting from the canonical side backward.
- `IssuePrerequisites` already owns the canonical (`ProjectId`, `IssueNumber`,
  `PrerequisiteNumber`) relation. Reconciliation verifies that both scoped Issues exist.
- Workflow-origin and direct Agent-launch `AgentSessions` already persist Issue context as computed
  Project/number labels. Reconciliation validates both label families and adds Project-scoped
  recency indexes.

Managers, queriers, storage-integrity helpers and API projections are access paths over the owners
above, not additional persisted owners. `WorkflowRunId`, `SessionId`, `AgentId`, `RunnerId`,
attachment id and event id remain independent identities.

### Historical and later-removal references

- Existing `IssueEvents` sources, payloads and extension JSON are immutable historical envelopes;
  the migration proves them byte-for-byte unchanged. Historical migration/designer files likewise
  remain historical evidence rather than current owners.
- Legacy `IssueId` on `IssueRow`, profiles, artifacts, comments, inbox, Epic relation rows,
  `WorkIssueRef`, run annotations and server APIs remains only until the T-004 number-only runtime
  and schema cutover.
- Legacy event lineage aliases and their current consumers remain explicitly assigned to T-007 and
  T-008. T-002 does not make historical envelopes conform to the future lineage shape.

### Migration and convergence

- `20260716130000_AddCanonicalIssueReferenceColumns` adds nullable transition columns from the
  immediate previous schema. `20260716140000_BackfillCanonicalIssueReferences` executes the shared
  guarded reconciliation, makes profile scope required, and creates the scoped indexes.
- The shared reconciliation is null-safe and idempotent: missing canonical values are filled from
  the owning Issue, already matching values remain unchanged, and present conflicts or unresolved
  owners fail with an owner-specific SQLite constraint name. No owner row is deleted.
- Migration specs seed both `proj_alpha/#42` and `proj_beta/#42`, every discovered owner family,
  a missing Workflow project scope, and an immutable historical event. They apply the actual target
  migration through `IMigrator`, preserve row counts and Project isolation, and run the shared
  convergence operation twice to prove the second pass is a no-op.
- The pre-existing `20260618112000_AddAttachments` migration lacked `DbContext` metadata, so EF
  never discovered it and tests/runtime had been creating the table out of band. It is now a real,
  idempotent migration. Regressions prove both a fresh migration chain and adoption of an existing
  out-of-band table without data loss; fixture-side schema patches were removed.

  remains only as the T-004 transition lookup and migration source.
- `EpicIssues` and `EpicActiveIssues` are the current Epic-owned retained/current membership rows.

- `Issues` now persists nullable `EpicNumber` beside the transitional `EpicId` copy. Reconciliation

  labels. Reconciliation requires a positive canonical decimal that resolves within the same

Epic managers, grains, queriers and API/read DTOs are access paths over these owners, not additional
persisted owners. Existing API and domain contracts still expose `EpicId` until the number-only
server cutover in T-004.

### Historical and later-removal references

- Historical migration/designer files remain historical evidence and are not rewritten.

### Migration and transaction boundary

- `20260716150000_AddCanonicalEpicReferenceColumns` adds nullable transition columns from the
  immediate previous schema. `20260716160000_BackfillCanonicalEpicReferences` executes one guarded
  reconciliation, makes root/relation numbers required, and creates scoped indexes.

## T-005 current progress

- `Issue.AssignEpic` and expected-number `Issue.RemoveEpic` are the only affiliation mutations.
  They save `Issue.EpicNumber` and `IssueEpicChanged(previous,current)` in the Issue store's
  existing state-plus-event transaction. Repeated assign is a no-op; an unlink from an old Epic
  cannot clear a later move.
- `Epic.LinkIssue` now reads first for idempotence, rejects a new link to a closed Epic, then
  commands Issue. A-to-B movement is one Issue commit. Batch operations follow the same command
  path and do not open an Epic membership transaction.
- `IssueEpicChangedHandler` opens a scoped read, re-reads the current Issue, recomputes the event
  old/new/current Epics, and refreshes active Workflow lineage after the Issue commit. It has no
  shared database transaction with Issue, Epic, or WorkflowRun.
- Epic member list, progress, readiness, primary-Epic projection, and start candidates now query
  `Issues.EpicNumber`. Candidate execution calls `Issue.TryStartFromEpic(expectedEpicNumber)` so
  a stale read cannot start an Issue moved elsewhere. A done Epic with a newly affiliated open
  Issue is revived by the durable recompute path.
- `EpicIssueRow`, `EpicActiveIssueRow`, their resolver, Epic-owned member collection, link/unlink
  domain events and subscriptions have been removed from the runtime model. Migration
  `20260716170000_DropEpicMembershipTables` drops both former tables after the preceding
  affiliation backfill; historical migrations remain upgrade history.
- The Issue key's computed projections are generated on insert only, not on every update. This
  preserves their immutable aggregate identity and restores EF design-time validation; the
  migration chain discovers the new drop migration and generates the expected SQLite
  `DROP TABLE "EpicActiveIssues"` / `DROP TABLE "EpicIssues"` script.
- Validation so far: server build clean; UnitTests **1477 passed / 0 failed / 0 skipped**; current
  SpecTests still contain pre-cutover relation-row fixtures and remain part of the T-004/T-005
  fixture migration backlog.

## T-001 decisions / layout (for downstream tasks)

- `EventCatalog.cs` now exposes:
  - `All` (unchanged): flat `IReadOnlyList<string>` of every registered type.
  - `ReverseDns.*` (unchanged): typed constants for emits.
  - `Lineage.*` (NEW): typed constants for the lineage attribute protocol names (`projectid`, `workflowrunid`, `issueid`, `issue`, `epicid`, `stage`, `agentid`, `sessionid`, `runnerid`). Prefer these over string literals when stamping.
  - `RequiredAttributes(string type)` (NEW): the always-required matrix per type. Empty list when the type has no lineage declaration (transcript / legacy names).
  - `HasLineageDeclaration(string type)` (NEW): whether the protocol tracks that type. Useful for skipping non-protocol events in conformance checks.
- `EnvelopeConformance.cs` (NEW, sibling of `EventCatalog.cs` in `Infrastructure/Events/`):
  - `Missing(envelope)` / `Missing(extensions, type)`: returns the list of required attributes that are absent.
  - `AssertRequired(envelope)` / `AssertRequired(extensions, type)`: throws `EnvelopeConformanceException` listing the missing attributes when the envelope fails. Empty values count as missing (lineage is omitted, never empty).
  - Unknown / out-of-protocol types are a no-op (empty required list).
  - Exception type `EnvelopeConformanceException : Exception` exposes `EventType` and `MissingAttributes`.

## Gotchas

- T-002 etc. must stamp `stage` via STRUCTURAL inspection of the `WorkflowEvent` union variants (per D2), NOT by `type` prefix. The variants that carry a `Stage` member are: `Stage*`, `StageApproval*`, `FeedbackRequested`, `Task*`, `Check*`. `WorkflowArtifactRecorded` (workflow.artifact.recorded) has no `Stage` and must NOT get a stage stamp. `workflow.check.started` has no producer today (catalog-only).
- The conformance `Missing` helper treats null AND empty-string values as missing. Do not stamp `""` for absent affiliation — omission IS the contract.
- `ReverseDns.WorkflowRunStopped` and `WorkflowRunPaused` are declared in `All` and the matrix — make sure any consumer-driven type filter (`string.Equals(type, WorkflowRunCompleted)` etc.) is still correct after stamping changes.
- `RunnerDisconnected` has only `runnerid` in the always-required set (no `projectid`). If a producer is added later, the matrix should be raised to include `projectid` whenever it is present.

T-002 progress

## Codebase Patterns (additions)

- `WorkflowRunMetadata.Annotations` carries three identity-shaped keys today: `projectId`, `issueId`, `issueNumber`. The producer lifts them onto CloudEvent extensions using the protocol names from `EventCatalog.Lineage` (`projectid`, `issueid`, `issue`) — `issueNumber` (annotation) → `issue` (envelope key). T-003/T-004/T-006 will keep using the same convention.

## T-002 decisions / layout

- `WorkflowRunStore.ToCloudEvent` now delegates extension construction to a pure helper `WorkflowRunLineage.BuildExtensions(run, evt)` (new file at `packages/server/src/Mohist.Server/Infrastructure/Data/Workflow/WorkflowRunLineage.cs`). The helper is unit-testable without an Orleans silo and is reused by the spec tests.
- Stamp matrix applied by the helper (per the matrix pinned in the T-001 section):
  - `workflowrunid` is ALWAYS stamped (the run is the producer — even a metadata-less run still has a run id).
  - `projectid`, `issueid`, `issue` are stamped only when the run's metadata annotation carries them; `IsNullOrWhiteSpace` skips them. Absent = omitted, NEVER an empty string.
  - `stage` is stamped by `WorkflowRunLineage.StageOf(evt)`, which pattern-matches the unwrapped `WorkflowEvent` union. Variants with a `Stage` member: `StageStarted`/`StageCompleted`/`StageFailed`, `StageApprovalRequested`/`StageApprovalResolved`, `FeedbackRequested`, `TaskStarted`/`TaskCompleted`/`TaskFailed`, `CheckPassed`/`CheckFailed`/`CheckPending`. Everything else (run lifecycle variants + `WorkflowArtifactRecorded`) returns null and skips the stamp.
- The `SaveAsync(run, events)` transactional path reads `WorkflowRunMetadata.Annotations` inside the append loop, so the lineage snapshot stays consistent with the EF Core transaction (D1). No cross-aggregate query is issued — `IssueStore`/`EpicGrain` is not touched. Verified by reading the test scenarios; if a future change adds such a query, the spec-test suite breaks.
- The `ToCloudEvent(run, ...)` overload signature changed: now takes the whole `WorkflowRun` instead of pre-extracted `projectId`/`issueId` strings. Callers pass `run` once and the helper does the rest. Simpler than threading three nullable strings through.

## Gotchas / hand-offs

- The conformance spec test was kept DRY by writing the assertion loop once per "save a bunch of events, list them, assert extensions" pattern. Future producers (T-003..T-006) should follow the same skeleton: drive a representative event per family, list via the store, then `EnvelopeConformance.AssertRequired(envelope)` per entry + targeted key assertions for the conditional attributes.
- `IReadOnlyDictionary<string, string>` extension access is read-only in the test (the run-id dictionary is built inside the helper); if a test wants to write extensions (negative cases) it must construct a fresh dictionary. The conformance `Missing` helper treats both null and empty-string values as missing, so the contract on omission (never empty) is shared.
- The `stampedStage` value comes from the event payload — never from the bus type. A future producer that adds a new stage-bearing variant only needs to extend the `StageOf` switch; the conformance check catches the omission in CI.

## T-001 decisions / layout (for downstream tasks)

- `EventCatalog.cs` now exposes:
  - `All` (unchanged): flat `IReadOnlyList<string>` of every registered type.
  - `ReverseDns.*` (unchanged): typed constants for emits.
  - `Lineage.*` (NEW): typed constants for the lineage attribute protocol names (`projectid`, `workflowrunid`, `issueid`, `issue`, `epicid`, `stage`, `agentid`, `sessionid`, `runnerid`). Prefer these over string literals when stamping.
  - `RequiredAttributes(string type)` (NEW): the always-required matrix per type. Empty list when the type has no lineage declaration (transcript / legacy names).
  - `HasLineageDeclaration(string type)` (NEW): whether the protocol tracks that type. Useful for skipping non-protocol events in conformance checks.
- `EnvelopeConformance.cs` (NEW, sibling of `EventCatalog.cs` in `Infrastructure/Events/`):
  - `Missing(envelope)` / `Missing(extensions, type)`: returns the list of required attributes that are absent.
  - `AssertRequired(envelope)` / `AssertRequired(extensions, type)`: throws `EnvelopeConformanceException` listing the missing attributes when the envelope fails. Empty values count as missing (lineage is omitted, never empty).
  - Unknown / out-of-protocol types are a no-op (empty required list).
  - Exception type `EnvelopeConformanceException : Exception` exposes `EventType` and `MissingAttributes`.

T-002 progress

## Codebase Patterns (additions)

- `WorkflowRunMetadata.Annotations` carries three identity-shaped keys today: `projectId`, `issueId`, `issueNumber`. The producer lifts them onto CloudEvent extensions using the protocol names from `EventCatalog.Lineage` (`projectid`, `issueid`, `issue`) — `issueNumber` (annotation) → `issue` (envelope key). T-003/T-004/T-006 will keep using the same convention.

## T-002 decisions / layout

- `WorkflowRunStore.ToCloudEvent` now delegates extension construction to a pure helper `WorkflowRunLineage.BuildExtensions(run, evt)` (new file at `packages/server/src/Mohist.Server/Infrastructure/Data/Workflow/WorkflowRunLineage.cs`). The helper is unit-testable without an Orleans silo and is reused by the spec tests.
- Stamp matrix applied by the helper (per the matrix pinned in the T-001 section):
  - `workflowrunid` is ALWAYS stamped (the run is the producer — even a metadata-less run still has a run id).
  - `projectid`, `issueid`, `issue` are stamped only when the run's metadata annotation carries them; `IsNullOrWhiteSpace` skips them. Absent = omitted, NEVER an empty string.
  - `stage` is stamped by `WorkflowRunLineage.StageOf(evt)`, which pattern-matches the unwrapped `WorkflowEvent` union. Variants with a `Stage` member: `StageStarted`/`StageCompleted`/`StageFailed`, `StageApprovalRequested`/`StageApprovalResolved`, `FeedbackRequested`, `TaskStarted`/`TaskCompleted`/`TaskFailed`, `CheckPassed`/`CheckFailed`/`CheckPending`. Everything else (run lifecycle variants + `WorkflowArtifactRecorded`) returns null and skips the stamp.
- The `SaveAsync(run, events)` transactional path reads `WorkflowRunMetadata.Annotations` inside the append loop, so the lineage snapshot stays consistent with the EF Core transaction (D1). No cross-aggregate query is issued — `IssueStore`/`EpicGrain` is not touched. Verified by reading the test scenarios; if a future change adds such a query, the spec-test suite breaks.
- The `ToCloudEvent(run, ...)` overload signature changed: now takes the whole `WorkflowRun` instead of pre-extracted `projectId`/`issueId` strings. Callers pass `run` once and the helper does the rest. Simpler than threading three nullable strings through.

- The conformance spec test was kept DRY by writing the assertion loop once per "save a bunch of events, list them, assert extensions" pattern. Future producers (T-003..T-006) should follow the same skeleton: drive a representative event per family, list via the store, then `EnvelopeConformance.AssertRequired(envelope)` per entry + targeted key assertions for the conditional attributes.

T-003 progress

## Codebase Patterns (additions)
- `Issue` already follows the cross-aggregate-reference pattern: `WorkflowRunId` is a nullable string the aggregate carries as a denormalized cache. `EpicId` rides the same field on the existing `State` JSON column, so no schema migration is needed and the read-side (`IssueRowMapper.Deserialize`) does not change. The `_epicId` field follows the same `NormalizeOptional` pattern as `_workflowRunId` (whitespace → null).
- The `IssueTransactionalEventAppendSpecs` Sqlite fixture uses a single in-memory connection shared across all `[Fact]`s in the class. The unique index on `Issues.(ProjectId, Number)` therefore requires each test issue to use a distinct `Number`. `BuildIssue` now takes an optional `number:` so each test passes a unique int — the legacy constant `IssueNumber = 7` is no longer used by any test fixture but stays as the helper's default.

## T-003 decisions / layout
- `Issue.cs` gains a nullable `EpicId` (init-getter, normalized via the existing `NormalizeOptional` helper) and an eventless `SetEpicId(string?, DateTime?)` transition. The transition records no `IssueEvent` (denormalization only — the authoritative `EpicIssueLinked` / `EpicIssueUnlinked` events live on the epic stream).
- `IIssueGrain.SetEpicAffiliationAsync(string? epicId)` is the synchronous push from the Epic domain. Implementation: idempotent (no-op when value unchanged); normalizes whitespace to null; persists via the existing `SaveIssueAsync()` flow, which calls `IssueStore.SaveAsync(key, state, [])` with an empty pending-events list. That overload is the same one used by every other state-only path on the grain (no domain event recorded).
- `IssueLineage.BuildExtensions(state)` (new file at `packages/server/src/Mohist.Server/Infrastructure/Data/Issue/IssueLineage.cs`) is the pure helper that mirrors `WorkflowRunLineage.BuildExtensions(run, evt)`. It reads ONLY from the supplied `Issue` instance — no DB context, no grain call, no cross-aggregate query. The dictionary always stamps `{projectid, issueid, issue}`; `epicid` is added only when `state.EpicId` is non-null.
- `IssueStore.SaveAsync(key, state, events, ct)` now calls `IssueLineage.BuildExtensions(state)` inside the EF Core transaction (it sits right after the source/subject resolution, before the per-event `ToCloudEvent` loop). Stamping stays consistent with the append because the extensions are derived from the same `state` instance the row is staged from. The legacy `BuildIdentityExtensions` private method is removed; its callers and tests are rewired to `IssueLineage`.
- Eight test fakes that implement `IIssueGrain` (in `EpicBatchMembershipSpecs`, `EpicMembershipSpecs`, `EpicProgressionSpecs`, `EpicWakeUpSpecs`, `EpicRecoverySpecs`, `EpicAutoDoneHandlerSpecs`, `IssueWorkflowCompletionHandlerSpecs`) gained a one-line `SetEpicAffiliationAsync(string?) => throw new NotSupportedException()` stub so the interface still compiles. They are placeholders — T-004 (EpicGrain link/unlink → SetEpicAffiliationAsync) is what actually exercises them.

## Gotchas / hand-offs
- The grain's `SetEpicAffiliationAsync` does NOT call `EnsureIssue()` (the issue is allowed to be null — link/unlink may target an issue that hasn't been activated yet on this silo). Instead it short-circuits when `_issue is null`. The state-only save then happens through `SaveIssueAsync()` which already handles a null `_issue` gracefully. This matches the EpicGrain call sites' expectations: EpicGrain's link/unlink `await` will route through Orleans, which deactivates the grain if needed, then activates it on the next call — at which point `OnActivateAsync` loads the state from the store and the in-memory `_issue` becomes available. If T-004's link call lands on an issue that has never been activated, the synchronous push will be a no-op on this code path; the durable `EpicIssueLinkedHandler` re-applies it later (per the design's "self-healing drift" mitigation).
- `IssueLineage.BuildExtensions` runs INSIDE the EF Core transaction (right after the source/subject resolution, before the event loop). This keeps the `epicid` snapshot consistent with the append per D1.
- The conformance spec test reads `entry.Envelope.Subject` against the issue number — keep that subject shape in mind for any later refactor of `IssueEventPersistence.IssueSource`/`subject`.
- The `IssueWorkflowCompletionHandlerSpecs` and other `Epic*` test files have TWO grain fake classes (recording + throwing). Both got the new `SetEpicAffiliationAsync` stub via a single regex pass. If more fakes appear, follow the same pattern.

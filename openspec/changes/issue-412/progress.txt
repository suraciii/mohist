## T-002 decisions / layout

T-004 progress

## Codebase Patterns (additions)
- `EpicGrain` follows the same `Mohist.Server.Infrastructure.Data.<Domain>.<Domain>Lineage` placement as `WorkflowRunLineage` (Workflow/Domain) and `IssueLineage` (Issue/Domain). New lineage helpers MUST live in the data layer, take only the producing aggregate's state, and never invoke a grain or query a join table — otherwise they break the "no cross-aggregate query" invariant the conformance matrix enforces.
- `IGrainFactory.GetGrain<IIssueGrain>(...)` follows the same `GrainKey.Issue(issueId)` pattern as `EpicCounter(projectId)` / `WorkflowBacklog(projectId)` (`Infrastructure/Orleans/GrainKey.cs`); the route key is the issue id (no project prefix). Use that constant rather than concatenating a project key.

## T-004 decisions / layout
- `EpicLineage.BuildExtensions(state)` (new file at `packages/server/src/Mohist.Server/Infrastructure/Data/Epic/EpicLineage.cs`) is the pure helper that mirrors `WorkflowRunLineage` / `IssueLineage`. It always returns exactly `{projectid, epicid}` (StringComparer.Ordinal); there is no `epicno` key because the matrix treats `epicid` as the single routing dimension and `epicno` is a non-routing read convenience.
- `EpicGrain` has TWO `PersistEpicEventsAsync` overloads — a post-commit `AppendAsync(envelope)` (used by `CreateAsync`/`SetStatusAsync`/`UpdateAsync`/`ReopenAsync`/`PauseAsync`) and a transactional `AppendAsync(db, envelope)` (used by `StartAsync`/`ResumeAsync`/`LinkIssueAsync`/`UnlinkIssueAsync`/`TryAutoMarkDoneAsync`/`TryStartNextAsync` start-failure path). Both now read extensions from `EpicLineage.BuildExtensions(epic)` and so produce an identical unified set — no producer drift between the two overloads.
- The stamp uses `EpicAggregate` (alias `Mohist.Server.Epic.Domain.Epic`) — the same instance the producer just stamped onto its pending events. No DB re-read; `BuildExtensions` is a pure function over the in-memory domain state.
- Link entry points (`LinkIssueAsync`, `LinkIssuesAsync`) and unlink entry points (`UnlinkIssueAsync`, `UnlinkIssuesAsync`) call `PushEpicAffiliationAsync(issueId, epicId-or-null, "link"|"unlink")` immediately after the epic transaction commits. The helper is `try/catch` + log + swallow: synchronous push failure must NOT break the epic mutation (the durable `EpicIssueLinkedHandler` / `EpicIssueUnlinkedHandler` re-applies the same denormalization on every redelivery, so drift is bounded and self-healing).
- `EpicIssueLinkedHandler` and `EpicIssueUnlinkedHandler` (in `Events/Subscriptions/EpicAutoDoneHandler.cs`) gain a new `EpicIssueAffiliationDispatcher.DispatchAsync(eventId, issueId, epicId, isLink, ct)` call. The dispatcher also wraps in `try/catch` + log: a synchronous failure here would otherwise dead-letter the durable handler and take the convergence path with it. The same `try/catch` mirror image lives in both the command path (`EpicGrain.PushEpicAffiliationAsync`) and the durable path (`EpicIssueAffiliationDispatcher`).
- One-time backfill is a pure data migration `20260715000000_BackfillIssueEpicAffiliation` that writes `Issues.State.$.epicId` from `EpicActiveIssues` for every issue already linked to an active epic at cutover. It only writes rows where `epicId` is currently NULL and a row exists in `EpicActiveIssues`. Idempotent: re-running matches zero rows because the presence guard fails. `Down` is a no-op (additive projection, per the `BackfillIssueCompletedAt` precedent). The migration is pure data — no `BuildTargetModel` snapshot — because `Issue.EpicId` already rides the existing `State` JSON column (T-003 brought it in).
- `EpicRecoveryFixture` (the only in-process silo test fixture) needed additional service registrations once the durable `EpicIssueLinkedHandler` started routing through `IIssueGrain.SetEpicAffiliationAsync` — it now calls `siloBuilder.Services.AddMohistConventionalServices()` plus the explicit `IConfiguration`/`IEnvironmentVariableProvider`/`IssueRepositoryResolver`/`IssueIdentityResolver`/`AttachmentService` `AddSingleton` lines that the conventional scan doesn't surface as `IScopedService`/`ISingletonService`. Without those, the InProcessTestCluster-backed `IssueGrain` fails to activate on `SetEpicAffiliationAsync` and the test's existing convergence expectations break.

## Gotchas / hand-offs
- The two `PersistEpicEventsAsync` overloads MUST share the same extensions dictionary shape. Going through the same `EpicLineage` helper is what enforces that — keep the helper as the single source of truth; do not reintroduce per-overload literal dictionaries.
- `EpicGrain.PushEpicAffiliationAsync` and `EpicIssueAffiliationDispatcher.DispatchAsync` are mirror images in shape and behavior. Both wrap in `try/catch` + log + swallow. Any future change to one MUST mirror into the other (the new EpicEventPublishSpecs push-failure case locks the EpicGrain path; the durability contract comes from the dispatcher's matching contract).
- `EpicRecoveryFixture` now registers the same conventional services as the production silo (specifically the `IIssueStore`/`IssueRepositoryResolver`/`IssueIdentityResolver` cluster the IssueGrain needs to activate). Without these, the durable handler's new IIssueGrain call dead-letters — confirmed by the `IssueLinkedEvent_DispatcherConvergesWhenInlineRecomputeWasSkipped` test reverting to red. The fixture-specific failure to remember: the disaptcher's `try/catch` swallows it back to a warning so the convergence test passes either way; the registrations are still required so the production-like path doesn't get exercised by a fake.
- The backfill migration gates on `json_extract(State, '$.epicId') IS NULL` to be idempotent and preserve any live-written values (the live EpicGrain push is the only other writer). It only writes when an `EpicActiveIssues` row exists, mirroring the live write path (terminal-history rows leave the issue's `EpicId` cache clear). `Down` is intentionally a no-op — see `BackfillIssueCompletedAt.cs` for the precedent.
- The `EpicIssueLinkedHandler` / `EpicIssueUnlinkedHandler` already had a `RecomputeProgressAsync()` dispatcher; T-004 does NOT replace that. The handler now does BOTH the affiliation push AND the recompute in sequence. They were both present in the design; T-004 only adds the first half. The order matters: affiliation push first (so the issue's later events stamp epicid), recompute second (so the epic's progress is updated). Swapping the two would still converge but would leave a small window where the issue's `EpicId` lag the join row.
- `Mohist.Server.Infrastructure.Orleans.GrainKey.Issue(issueId)` is the canonical way to address `IIssueGrain`. Calling `_grains.GetGrain<IIssueGrain>(issueId)` (the literal-id form) also works because the grain uses `IGrainWithStringKey` and the key is the issue id, but the helper preserves the convention other EpicGrain callers use.
- `EpicEventPublishSpecs` has TWO new grain fake classes (`RecordingIssueGrain` and `ThrowingIssueGrain`) alongside the existing `StubGrainFactory`/`StubEpicCounterGrain`. Both implement `IIssueGrain` and accept any `IGrainFactory` method. Keep the new fakes local to the test file — no shared fixture change needed.

## T-005 decisions / layout
- `AgentSessionLineage.BuildExtensions(session)` (new file at `packages/server/src/Mohist.Server/Infrastructure/Data/Sessions/AgentSessionLineage.cs`) is the pure helper that mirrors `WorkflowRunLineage` / `IssueLineage` / `EpicLineage`. It reads ONLY from the supplied `AgentSession.Metadata.Labels` — no DB context, no grain call, no cross-aggregate query (D6).
- The helper's projection rules (D6):
  - `projectid` is stamped from the `mohist.io/project-id` label when present; whitespace-only label is treated as absent.
  - `sessionid` is always stamped (the session's own id; the producer's identity).
  - When `source-kind = "workflow"` (workflow/issue-origin session): `issue` (from `mohist.io/issue-number`), `workflowrunid` (from `mohist.io/source-id`), and `stage` (from `mohist.io/stage`) are stamped when their labels are present.
  - For all other source kinds (e.g. `agent-launch`): `agentid` is stamped from `mohist.io/agent-id` when present. The `agentid` and `issue`/`workflowrunid`/`stage` keys are mutually exclusive at the producer level — they describe different session origins.
  - Absent labels are omitted, never an empty value.
- `AgentSessionStore.SaveAsync` now computes the extensions dictionary once before the event loop (same shape as `IssueStore.SaveAsync`) and passes the read-only dictionary into `ToCloudEvent`. The previous `extensions: null` is gone.
- `AgentSessionStore.ToCloudEvent` signature now takes an `IReadOnlyDictionary<string, string> extensions` parameter (was: nothing). The dictionary is the shared stamp; the CloudEvent extensions property is set to that dictionary.
- `BuildSession` helper in the spec now takes an optional `AgentSessionMetadata` so each scenario can build its own labels. `BuildAgentLaunchLabels(projectId, agentId)` and `BuildWorkflowOriginLabels(projectId, workflowRunId, issueNumber, stage)` wrap `GenericAgentSessionMetadata.Metadata(...)` and `WorkflowAgentSessionMetadata.Metadata(...)` so the test scenarios use the exact same label-baking helpers the production paths use.

## Gotchas / hand-offs
- The label-key constants are stable across the codebase: `AgentSessionQueryMetadataKeys.ProjectId` (`mohist.io/project-id`), `AgentSessionQueryMetadataKeys.IssueNumber` (`mohist.io/issue-number`), `AgentSessionQueryMetadataKeys.WorkflowRunId` (`mohist.io/source-id`), `AgentSessionQueryMetadataKeys.Stage` (`mohist.io/stage`), `AgentSessionQueryMetadataKeys.SourceKind` (`mohist.io/source-kind`, with values `"agent-launch"` and `"workflow"`), and `GenericAgentSessionMetadata.AgentId` (`mohist.io/agent-id`). The `AgentSessionLineage` helper references them by constant — no string literals.
- The `source-kind` label is the single discriminator between the two projection branches. A future source kind (e.g. a third-party integration) defaults to the non-workflow branch (stamp `agentid` when its `mohist.io/agent-id` label is present). That matches the matrix's "agentid when agent-origin" wording without an explicit enumeration of every future kind.
- The `mohist.io/agent-launch/issue-number` label (the `GenericAgentSessionMetadata.IssueNumber` constant) is intentionally NOT read for stamping. The matrix is `issue` only when the session originates from a workflow/issue — generic agent-launch sessions do not contribute `issue`/`workflowrunid`/`stage` to the envelope, even if the user supplied an issue context reference at launch. The optional context refs stay in `Annotations` only (they do not create scope, mount, or supervisor lifecycle per the design of `GenericAgentSessionContext`).
- The previous test's `Assert.False(entry.Envelope.Extensions.ContainsKey("projectid"))` was a contract assertion (the OQ3 design choice). T-005 supersedes it: projectid IS stamped when the label is present. The other assertions in that test (source / subject) are unchanged and re-verified.
- `SaveAsync_StampedEnvelopes_SatisfyEventCatalogRequiredAttributes` is the only conformance spec test exercising the agent-session path; the unit test `BuildExtensions_AgentLaunchSession_SatisfiesEventCatalogForEveryAgentSessionType` covers the helper in isolation. The two together pin the matrix end to end.

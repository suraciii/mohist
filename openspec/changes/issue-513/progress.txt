## Codebase Patterns

- `AttachmentService.OwnerKind*` constants drive the existing issue/comment ownership; bind helpers follow the `Bind*Async` / `Validate*Bind*Async` pair pattern that reuses `ValidateAvailableAsync` + `EnsureAttachmentLimit`. `CleanupExpiredPendingAsync` keys on `OwnerKind == null`, so any new owner kind that clears `ExpiresAt` is automatically retention-protected without extra logic.
- `AttachmentRow.OwnerId` is a free-form string (max 256) used to carry owner-scoped identity. For a composite owner (session+input), encode as a `/`-separated string; both session and input ids are `Guid.NewGuid().ToString("N")` (32 hex chars, no slashes) so the separator is unambiguous.
- API attachment routes register inside the project group (`/api/projects/{projectRef}`) and use `IssueRoutes.GetRequiredProject(ctx)` to resolve the project. Spec tests in the integration collection reuse the fixture's `_fixture.Services.CreateAsyncScope()` to grab `AttachmentService` directly for cases where there's no API caller yet (e.g., bind before the launch/follow-up API exists).
- Fake `IAttachmentStorage` exists in two flavors: a full `InMemoryAttachmentStorage` in SpecTests/Support (used by HTTP spec tests) and a lighter `FakeAttachmentStorage` in UnitTests/Support (used by service-level unit tests with `FakeTimeProvider`). Keep the UnitTests version in UnitTests/Support rather than crossing the SpecTests project boundary.
- Service unit tests use in-memory SQLite with `EnsureCreated()` against `MohistDbContext`, a `TestDbContextFactory` wrapping `DbContextOptions`, and `FakeTimeProvider` for time. `using var db = database.CreateContext();` (not `await using`) matches the existing AesGcmSecretStoreTests pattern; use `SingleAsync`/`AnyAsync`/`ToListAsync` for awaited EF calls.

## T-001 decisions

- Added `OwnerKindAgentInput = "agent-input"` and a composite owner-id builder `BuildAgentInputOwnerId(sessionId, inputId)` returning `"{sessionId}/{inputId}"`. The route path mirrors this: `/api/projects/{projectRef}/agent-sessions/{sessionId}/inputs/{inputId}/attachments/{attachmentId}/content`.
- The content route uses the same `StreamAttachment` helper as issue/comment attachments, so disposition + content-type handling stays uniform. No projectId-or-issue gate (no need to look up an issue first — ownership is the only gate, exactly as the spec mandates).
- Validation path delegates to a new `ValidateAgentInputBindCoreAsync` that mirrors the issue/comment helpers; this keeps the rejection contract (missing id, already bound) identical to the existing flows.
- `AttachmentRow` itself is unchanged — name/content-type/size/source are already stored on the row and never needed a caller-temp-URL/token/event-payload column, so the "no secrets in the stored record" criterion is satisfied by the existing schema; the unit test asserts that no such columns exist rather than scrubbing values.

## Gotchas

- `OwnerId` already has `HasMaxLength(16)` set on the kind column and `HasMaxLength(256)` on `OwnerId`. The composite `{sessionId}/{inputId}` (33 chars max) fits comfortably.
- EF's `Single`/`Any`/`ToList` are sync, `SingleAsync`/`AnyAsync`/`ToListAsync` are the awaited versions. Misusing `await db.X.Single(...)` compiles but produces a confusing "X does not contain GetAwaiter" LSP/runtime error — always use the *Async variants in awaited test code.
- For the integration HTTP tests, `MohistIntegrationFixture` already wires `InMemoryAttachmentStorage` into DI, so the spec test can bind via `scope.ServiceProvider.GetRequiredService<AttachmentService>()` without constructing a new storage. The unit test path constructs its own `FakeAttachmentStorage` to keep the service boundary clean.

## T-002 decisions

- Added `AgentSessionInputAttachmentDescriptor` (Orleans `[GenerateSerializer]` record with `[property: Id(N)]` on constructor params — append-only Orleans field ids keep existing persisted state backward compatible) and `AgentSessionInputAcceptance`/`AgentInputAttachmentAcceptanceBatch` plus `AgentInputAttachmentRejectionReason` (NotFound, Expired, NotReadable, ExceedsSizeLimit, UnsupportedType, AlreadyBound).
- `AgentSessionInputRecord.Attachments` is the new ordered child record slot at `[Id(8)]`; persisted alongside the existing `Text`/`Source`/etc. so the accepted set survives a grain reload. The replay/equivalence check (in the Session and Job grains) folds the attachment set into the immutable launch identity so a replay with a different attachment set raises a conflict.
- `AttachmentService.ValidateAndBindAgentInputAsync` returns a per-file batch (descriptor for accepted, reason for rejected) and persists only the accepted set; rejected attachments stay pending (OwnerKind = null, ExpiresAt preserved) so the cleanup sweep reaps them on their original schedule. The aggregate per-owner limit applies across already-bound + new submissions — over-limit rejects the whole submission with no binding applied.
- The launch and follow-up routes share the same allowlist change (`{ "text"/"prompt", "context"/..., "attachments" }`), the same "non-empty text OR ≥1 accepted attachment" rule, and the same response shape (`attachments[]`/`rejectedAttachments[]` + per-file verdict). `LaunchCoordinatorRequest` and `AcceptFollowupCommand` carry an `AttachmentIds`/`Attachments` array respectively so the coordinator fingerprint and idempotency conflict path cover attachment replays.
- `AgentLaunchCoordinatorGrain`, `AgentJobGrain.PrepareManualLaunchAsync`/`SubmitAsync`, and `EnsureInitialLaunch`/`AcceptFollowup` extension methods relax the "non-empty prompt" guard to "non-empty prompt OR ≥1 accepted attachment" — the dispatch envelope (`with.attachments` for AgentJob, `attachments[]` for follow-up) carries the descriptors verbatim so the Runner can resolve content via the scoped content route. Accepted attachment bytes are never carried over the wire.
- The Coordinator advances through PrepareJob → EnsureInitialLaunch → SubmitJob; each step catches and logs exceptions so the reminder retries on partial failure. The coordinator's `Completed` flag flips to true only after `SubmitPreparedLaunchAsync` returns, so an AttachmentService bind failure surfaces as `LaunchSetupPending` (503) and the reminder retries — not a successful but empty launch.
- `FollowupDeliveryRequest.Attachments` (Orleans `[GenerateSerializer]`) is forwarded as `payload.attachments` in `RunnerFollowupDeliveryDispatcher.DispatchAsync`. Runner-side wiring is T-003's surface.
- Spec tests use a new `AgentSessionInputAttachmentAcceptanceSpecs` collection (`IntegrationApi`) — not the existing `LaunchRoutesTestSupport` (different collection, different fixture) — because the new tests need both the launch coordinator's AttachmentService integration and a fake in-memory attachment storage the test can corrupt (`MarkUnreadable`) to simulate storage-side failures.

## T-002 gotchas

- DI picks `AttachmentService`'s 4-arg constructor (`TimeProvider time`) over the 3-arg `IOptions<>` one because the integration fixture registers `TimeProvider` after `MohistServiceRegistration` runs — `RemoveAll<TimeProvider>()` + `AddSingleton<TimeProvider>(_timeProvider)` in `ConfigureTestServices` is required for the FakeTimeProvider to win; otherwise validation runs against wall-clock and seeded `ExpiresAt` in the past fires the `Expired` reason prematurely.
- The session grain had a duplicate "Prompt is required" guard at `AgentSessionGrain.EnsureInitialLaunchAsync` in addition to the transition's `EnsureInitialLaunch`. Both must be relaxed to "prompt OR attachments" — fixing only the transition lets the coordinator silently drop the input and the launch returns `launch_setup_pending` (the silent exception is caught in the coordinator's `AdvanceAsync` try/catch).
- `DefaultIgnoreCondition = JsonIgnoreCondition.WhenWritingNull` is the project default; the `AgentSessionFollowupResult.Attachments`/`RejectedAttachments` fields must default to empty arrays rather than null so the JSON response shape stays stable across all response paths (the spec test deserializes them via `GetProperty`, which throws on missing keys).
- `AttachmentService.ValidateAndBindAgentInputAsync` checks `row.Size > _options.MaxFileBytes` BEFORE checking readability, but the unit test approach (seed a row whose `Size` exceeds the runtime limit) requires bypassing the upload's own size guard — the cleanest path is the FakeTimeProvider + a row inserted via `db.Attachments.Add` so the upload pipeline never sees it.
- `InMemoryAttachmentStorage.MarkUnreadable(storagePath)` requires the storage path (not the attachment id) and the path must pass `ParseStoragePath` (3 segments, ends in `/content`). Always use `storage.GenerateStoragePath(projectId, attachmentId)` rather than hand-formatting the path.
- For HTTP integration tests the `Attachments: []` (empty array) is intentional — JSON omits null fields. The followup route returns `Attachments: accepted ?? []` and `RejectedAttachments: rejected ?? []` to guarantee both keys always serialize.

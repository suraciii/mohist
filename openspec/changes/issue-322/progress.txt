## Codebase Patterns

- `IssueRoutes.Metrics.cs` is the only metrics route reading `DateTimeOffset.UtcNow` directly; every other route (`IssueRoutes.DeliveryTimeMetrics.cs`, `IssueRoutes.QualityMetrics.cs`) resolves `TimeProvider` from DI. Switching completion to the same DI shape is the D4 opportunistic consistency fix; nothing else in the API surface needs this change.
- `MohistIntegrationFixture.TimeProvider` is a `FakeTimeProvider` pinned at `2026-06-30 00:00 UTC`. So API-level completion tests must seed events inside `[2026-06-01, 2026-07-01)` for the current day-window and `[2026-05-02, 2026-06-01)` for the previous day-window. For the week bucket, current ISO week starts `2026-06-29` and previous 12-week window is `[2026-01-19, 2026-04-13)`.
- The querier-side tests use an explicit `DateTimeOffset now` parameter, so they can independently verify adjacency by shifting `now` and re-running — preferred over fixture-clock reliance.
- `IssueQuerier.GetCompletionBucketsAsync` already pre-filtered events by source + terminal type and collapsed to the latest terminal event per issue before bucketing. The previous-window totals reuse that same `latestTerminalByIssue` materialized list and just split it across the two adjacent windows — no extra DB round-trip.
- The completion surface uses two distinct empty-result idioms today: dense zero buckets per the spec, and (new) a `SampleCount` discriminator on the totals DTO. The DTO additive guarantee means existing consumers that read `Buckets`/`Window` see no change; the new `CurrentTotal`/`PreviousTotal` are net-new fields.

## Decisions

- T-001 deliberately keeps `windowFrom`/`windowTo` semantically identical to today's; the previous window is `[today - 2W, today - W]` derived from the same `today`/`currentWeek` already computed for the current window. This means existing assertions like `payload.Buckets[0].Boundary == windowFrom as yyyy-MM-dd` still hold byte-for-byte.
- For day granularity, `previousFrom = today.AddDays(-59)` and `previousTo = windowFrom`. For week granularity, `previousFrom = currentWeek.AddDays(-7*12)` (start of week 24 weeks back) and `previousTo = windowFrom`.
- The totals object is its own `CompletionTotal` / `CompletionMetricsTotalsDto` rather than reusing the bucket shape — it has no `Boundary` and intentionally exposes `SampleCount` so the zero-sample vs genuine-zero discrimination is on the wire. This matches D2 in design.md (the surface's own idiom).
- The handler-level TimeProvider swap was inlined into the existing endpoint rather than split into a separate refactor task, per task notes: it is required for deterministic testing of the new previous-window branch.

## Gotchas

- The `latestTerminalByIssue` list intentionally stays a single GroupBy of all terminal events; do not also call the bucketing logic twice (once per window) — that would re-introduce the closed-then-reopened stale-count risk if the implementation is split incorrectly. The single-pass loop with two window checks (current, then previous) is correct.
- The `IndexByBoundary` dictionary is keyed on `DateOnly`, which for the week bucket is the Monday of the ISO week. Don't change that keying or the bucketing will silently misalign on week boundaries.
- `IssueMetricsApiSpecs` has a local `CompletionMetricsResponse` record that mirrors the API shape. Both must include `CurrentTotal` and `PreviousTotal` (or JSON deserialization fails on the new fields), otherwise the existing day/week tests break on shape mismatch. The change to that local record is also part of T-001.
- For the day test `CompletionMetrics_DayBucket_GenuineZeroCompletionPreviousWindowIsDistinctFromEmpty`, with fixture time `2026-06-30`, the previous window is `[2026-05-02, 2026-06-01)`. Two cancellation events at `2026-05-10` and `2026-05-25` both fall inside that range — used to assert `SampleCount=2, Completed=0, Failed=2`.

- T-002 follows D2 by mirroring the existing nullable `CycleDays` idiom: the previous-window average is `double?` (`null` ⟹ no delivered issues in the previous window). The empty result is structurally distinguishable from a genuine zero-duration average (a genuine zero yields `0.0` with at least one contributing sample).
- T-002 keeps the per-issue `Points` series strictly scoped to the current window. Previous-window delivered issues contribute only to the previous-window mean accumulator — they do NOT appear in `Points`. This preserves the existing per-issue series shape byte-for-byte and the contract that `Points` covers only the current window.
- For T-002 the previous-window average uses the same earliest-work-start-to-final-completion ("surviving retries") definition and the same `CompletedAt`-anchored windowing the current window uses; only the window bounds shift. No new schema, no new persisted field.
- Boundaries are asymmetric on purpose: the current window is `[windowFrom, windowTo]` (`<=` inclusive on both ends, matching today's contract) and the previous window is `[previousWindowFrom, previousWindowTo)` (`<` on the upper end so the boundary belongs to the current window). Adjacent but non-overlapping.

- T-002 implementation single-pass: each issue falls into AT MOST one of the current window (added to `Points`) or the previous window (added to the accumulator). The two branches are mutually exclusive by the boundary semantics, so no double-counting. Issues with `CycleDays == null` (no recorded work-start) are excluded from the previous-window accumulator entirely — they do not drag the mean down or fabricate a partial sample.

The first iteration of the test expected `Assert.Equal(2, payload.Points.Length)` which was wrong — corrected to `Assert.Single(payload.Points)` after confirming with a probe.

## Codebase Patterns

- T-003 follows the same "single-pass issue loop with `else if` for the second window" pattern T-002 established: the existing 30-day accumulation already runs; the previous window contributes ONLY a single FTR-flag accumulator (`QualityFirstTimeRightAccumulator`), and the `else if` makes the two branches mutually exclusive by the boundary semantics — no double-counting, no second DB scan.
- T-003 deliberately does NOT add a `WindowBounds` field to the previous window on the wire. The task acceptance criteria pin the previous-window DTO to "first-time-right rate plus its SampleCount" (the surface's existing `SampleCount` + nullable-rate idiom); window bounds would be additive but not required and would force consumers to re-validate them. The querier-side `QualityPreviousWindow` record intentionally stays minimal for the same reason.

## Decisions

- T-003 adds a small `QualityPreviousWindow` querier record (just `SampleCount` + `FirstTimeRightRate`) rather than reusing the full `QualityMetricsWindow` shape. This keeps the previous-window DTO minimal per the task acceptance criteria ("previous-window first-time-right rate plus its SampleCount") and avoids leaking per-stage rework or window bounds the spec didn't ask for. The two-window shape divergence is contained inside the querier.
- T-003 keeps the previous-window contributions to the FTR scalar only — NOT to the per-stage rework breakdown or per-day trend series. The 7d/30d windows keep their existing per-stage data, and the 30-day trend series is unchanged. This matches the spec's "strictly additive" rule and the design's D1 (trend basis is the existing window30d, not a new previous-window trend).
- The previous window uses the same asymmetric boundary semantics as T-002: current window is `[window30dFrom, window30dTo]` (`<=` inclusive on both ends) and previous window is `[previous30dFrom, previous30dTo)` (`<` on the upper end so the boundary moment belongs to the current window). Adjacent but non-overlapping.

## Gotchas

- T-003's `BuildPreviousWindow` mirrors the existing `BuildWindow` rate computation: `accumulator.SampleCount == 0 ⟹ null`, otherwise `(double)FtrCount / SampleCount`. The `SampleCount == 0` case is the empty-result signal; a genuine `0` or `1` rate requires `SampleCount > 0`. The two are structurally distinguishable on the wire (nullable rate + scalar sampleCount) — no other field needed for the discrimination.
- The querier-level `QualityFirstTimeRightAccumulator` is intentionally a NEW type (separate from `QualityAccumulator` / `QualityTrendAccumulator`) because the previous window only needs FTR + count — not per-stage rework denominators. Reusing the larger accumulator would add cost for no benefit and would be a confusing signal that the previous window needs per-stage data (it does not).
- The local `QualityMetricsResponse` mirror in `IssueMetricsApiSpecs.cs` must include the new `PreviousFirstTimeRightRate` and `PreviousSampleCount` fields, otherwise the existing quality tests start failing on JSON deserialization shape mismatch after the API response gains the new fields. (Same gotcha as T-001 and T-002's `CompletionMetricsResponse` / `DeliveryTimeMetricsResponse` mirrors.)
- For the API spec test `QualityMetrics_AdditivePreservation_ExistingWindowsAndTrendUnchanged`, the first iteration shipped the issue 29 days ago (the trend's first boundary) — that falls OUTSIDE the 7-day window, so `Window7d.SampleCount` was correctly 0. Corrected the test to ship 1 day ago so it lands in both 7d and 30d and the existing-window contracts can be re-verified cleanly. The `previousSampleCount == 0` and `previousFirstTimeRightRate == null` assertions still hold (no previous-window seeding).
- For the API spec test `QualityMetrics_GenuineZeroAndGenuineOneRatesInPreviousWindow_AreDistinctFromEmpty`, the previous window seeds 2 shipped issues (one with a repair, one without), giving a `0.5` rate with `SampleCount == 2`. The point is to show `SampleCount > 0` + non-null rate (genuine rate) vs the empty result where `SampleCount == 0` and rate is null. The `0.5` itself is incidental — the structural discriminator is `SampleCount`.
- For the querier spec `GetQualityAsync_AdjacencyShiftsWithNow_DrivenByExplicitDateTimeOffset`, the anchor issue ships at `2026-06-10 14:00 UTC`. With `now = 2026-06-30` it falls inside the current 30d window; shifting `now` by exactly 30 days to `2026-07-30` moves the boundary by 30 days and the same issue is now in the new previous window. This proves the previous window is `now`-anchored, not fixture-clock-anchored.

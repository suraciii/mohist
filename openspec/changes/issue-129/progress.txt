# Issue 129 — generic AgentSession launch

Working memory for the issue-level workflow. Append findings as you go;
later steps read the latest entries (and the `## Codebase Patterns`
section first).

## Codebase Patterns

- `WorkDispatch` is the server-side dispatch record; `WorkDispatchResponse`
  is its wire DTO mirrored to the runner. New optional fields are added
  at the end of the constructor with `null` defaults so workflow
  translators continue to compile and produce byte-identical workflow
  dispatches.
- `AgentJobGrain` is the authoritative owner of a standalone agent job.
  It is in-memory only (no `[PersistentState]`) and non-reentrant, so
  timer-driven dispatch retries cannot race `ReportResultAsync`. Any new
  state must respect non-reentrancy and timer disposal in
  `OnDeactivateAsync`.
- `JSON.SerializeToElement` and `JSON.Serialize` are the canonical
  serialization helpers; the runner-facing `with`/`variables` strings
  are produced through them.
- Tests for `AgentJobGrain` live under
  `packages/server/tests/Mohist.Server.Tests/Specs/Agent/Grain/`. The
  fixture (`AgentJobGrainFixture`) shares an in-memory Orleans cluster
  with `[Collection("WorkflowGrain")]`; specs that register a runner
  must clear the global runner registry to avoid stale cross-spec
  interference.
- `RunnerRoutes.PollAsync` projects a `WorkDispatch` into a
  `WorkDispatchResponse`. For workflow dispatches the project id lives
  on `Issue.ProjectId`; for agent-job dispatches (no `Issue`) it must
  fall through to the new top-level `ProjectId` field. The `Issue ??`
  fallback in the route is the consolidation point.
- The runner reads the `WorkDispatchResponse` JSON wire shape via
  `JSON.parse`; adding optional fields is wire-compatible. The runner
  side `WorkDispatchResponse` and `RenderedWorkItem` types are kept in
  lockstep.

## T-001 — Server: AgentJob consumes Agent definition + widen dispatch envelope

### Findings

- `AgentJobInput` previously only carried `Prompt`, `Model`,
  `WorkspacePath`, `ProjectId`, `Uses`. Added three optional Agent
  snapshot fields:
  - `AgentId: string?` — resolved Agent identity (traceability).
  - `AgentInstructions: string?` — resolved Agent `Instructions`.
  - `AgentConfig: JsonElement?` — resolved Agent `AgentConfig`
    snapshot.
  - Plus `AgentSessionId: string?` for the launch-side minting flow
    (used to populate the dispatch envelope; T-003 mints it before
    dispatch).
  Orleans serializes `JsonElement?` via the existing
  `JsonElementSurrogate`; no extra registration needed.

- `WorkDispatch` (in `IRunnerGrain.cs`) gained two additive optional
  fields: `ProjectId` and `AgentSessionId`. They are null for
  workflow dispatches (workflow projects still surface via
  `Issue.ProjectId`) and set by `AgentJobGrain.BuildDispatch` for
  agent-job dispatches. Old-field consumers ignore the new fields.

- `AgentJobGrain.BuildDispatch` now reads `input.ProjectId` and
  `input.AgentSessionId` onto the dispatch envelope. Workflow dispatch
  (`WorkflowItemTranslator.BuildTaskDispatchAsync` /
  `BuildChecksDispatchAsync`) keeps using named-argument constructor
  calls — the new fields default to `null`, so the workflow path is
  byte-identical.

- `AgentJobGrain.ComposePromptWithEntry` (extracted as
  `internal static`) is the single composition point for
  `with.prompt`. When `AgentId` or any Agent field is set,
  `with.prompt` becomes a structured object rooted at `agent-launch`
  carrying `instructions` / `config` / `prompt` so the runner's
  `resolvePrompt` path renders it via the existing structured-prompt
  machinery. When no Agent fields are set, `with.prompt` is the bare
  string — the raw-prompt-only AgentJob path is unchanged.

- `RunnerRoutes` projects the new fields into `WorkDispatchResponse`.
  `ProjectId` falls through `Issue.ProjectId ?? work.ProjectId` so
  workflow and agent-job both yield an authoritative project id in the
  response (workflow still reads from `Issue`, agent-job from the new
  field). `AgentSessionId` is passed through verbatim (null for
  workflow and raw-prompt-only validation dispatches).

- Runner-side `WorkDispatchResponse` and `RenderedWorkItem` gained an
  optional `agentSessionId?: string | null` field. The runner's
  `toWorkItem` parses it from the dispatch response. Workflow
  dispatched items leave it `undefined`.

- Tests cover:
  - `ComposePromptWithEntry` unit tests: raw-prompt-only, instructions
    only, instructions + config, AgentId-only (structured prompt shape
    always has `agent-launch.prompt`).
  - Integration tests (grain + polled dispatch):
    agent-sourced composition populates `with.prompt` as a structured
    object rooted at `agent-launch` and populates `ProjectId` /
    `AgentSessionId` on the dispatch.
  - Raw-prompt-only path keeps `with.prompt` as a bare string and
    leaves `AgentSessionId` null.
  - Dispatch envelope population: `ProjectId` always set when the input
    carries one; `AgentSessionId` set when supplied, null otherwise.
  - Workflow dispatch path is unchanged (existing tests still pass;
    `WorkflowItemTranslator` constructors leave the new fields null
    via the default).

### Gotchas

- The new fields are at `[property: Id(15)]` and `[property: Id(16)]`
  on `WorkDispatch`. The existing `Id(10)` slot was already
  retired (gap in the sequence). Adding past the retired slot is
  safe; Orleans `GenerateSerializer` honors the explicit `Id(N)`
  assignments.
- `WorkDispatchResponse` previously had `CleanupPolicyDto?` and
  `Recovery` after `AgentJobId`. Adding `AgentSessionId` between
  them is wire-compatible: the runner uses field-name JSON parsing,
  and the `JsonPropertyName` defaults match the C# property names
  (camelCase).
- `AgentJobGrain.BuildDispatch` is private. To unit-test the
  composition logic without spinning up the full grain, the
  composition helper was extracted as `internal static` (test
  assembly has `InternalsVisibleTo`).
- The agent-sourced `with.prompt` is a structured object with root
  key `agent-launch`. The runner's `resolvePrompt` recognizes single-
  root-key structured objects and renders them via the existing
  `renderStructuredPrompt` path; this keeps the runner side unchanged
  for T-001 (T-002 will generalize the session target).
- `ProjectId` in `WorkDispatchResponse` falls through `Issue.ProjectId
  ?? work.ProjectId`. Workflow dispatches leave `work.ProjectId` null
  but supply `work.Issue.ProjectId`, so they remain unchanged.
  Agent-job dispatches have no `Issue`, so they fall through to
  `work.ProjectId`. Both shapes yield an authoritative project id.

## T-002 — Runner: generalized session target abstraction

### Findings

- New exported type `SessionTarget` (in
  `packages/runner/src/runtime/acp-connection.ts`) is the
  discriminated union used everywhere a session identity is carried
  in the runner:
  `{ kind: "workflow"; projectId; workflowRunId; sessionName }` or
  `{ kind: "generic"; projectId; sessionId }`. Adopting the target
  shape unifies runner caches, key derivation, and server method
  dispatch.

- `AcpSessionManager.key()` now takes a `SessionTarget` and returns a
  prefixed key: `workflow:{workflowRunId}:{sessionName}` for
  workflow-shaped sessions, `generic:{sessionId}` for generic-shaped
  sessions. Two explicit helpers (`workflowKey`/`genericKey`) exist
  for callers that already know the shape (e.g. existing
  `host.resolveFollowupTarget`, the test fixtures, the generic
  strategy). The different prefixes close the
  `":<sessionName>"` collision that an agent-job would otherwise
  hit when `workflowRunId` is empty and the session name happened to
  match a workflow's `":"`-delimited key.

- `sessionTargetFromContext` (`session-events.ts`) returns a
  `SessionTarget | null`:
  - `ownerKind === "agent-job"` + `agentSessionId` present +
    `projectId` set → generic shape (uses the
    agent-job-minted session id directly as the identity, ignores
    the workflow-shaped `with.session`).
  - Otherwise → workflow shape (existing semantics: derives
    `sessionName` from `with.session` or `workId`).
  - `projectId` gate is retained; without it both branches return
    `null`. An agent-job without a minted `agentSessionId` falls
    through to the workflow shape (this is the raw-prompt-only
    AgentJob path that never had a session to attach to).

- `emitSessionEvent` and `attachSessionToServer` now branch on
  `target.kind`:
  - Workflow branch → `workflowAgentSessionRuntimeEvents` /
    `attachWorkflowAgentSession` (unchanged URLs and signatures).
  - Generic branch → new
    `agentSessionRuntimeEvents` / `attachAgentSession` (new
    `agent-sessions/{projectId}/{sessionId}/...` URLs).
  Both branches share the same `body` shape so the existing
  server-side session event pipeline receives identical payloads.

- `ServerConnection` (`packages/runner/src/server/connection.ts`)
  gained four new methods that hit distinct URL paths:
  - `getAgentSession(projectId, sessionId)` →
    `GET /api/runner/{runnerId}/agent-sessions/{projectId}/{sessionId}`
  - `openAgentSession(projectId, sessionId, body)` →
    `POST .../open`
  - `attachAgentSession(projectId, sessionId, body)` →
    `POST .../attach`
  - `agentSessionRuntimeEvents(projectId, sessionId, body)` →
    `POST .../runtime-events`
  The existing `*WorkflowAgentSession` methods and URLs are
  untouched and remain byte-identical; an alias `AgentSession =
  WorkflowAgentSession` is exported so generic callers do not need
  a new type.

- `runAcpWorkflowAgentSession`
  (`session-strategies.ts`) now branches on owner-kind at the top:
  when `ownerKind === "agent-job"` and `agentSessionId` is present,
  it delegates to a sibling
  `runAcpGenericAgentSession` that uses the new
  `getAgentSession` / `openAgentSession` connection methods, keys
  the `AcpSessionManager` cache by the generic prefix, and runs the
  same cached/resumed/new-session logic (sharing
  `runPromptOnExistingWorkflowAgentSession`,
  `runResumedWorkflowAgentSession`,
  `runNewWorkflowAgentSession`, and
  `runEphemeralWorkflowAgentSession`). The
  existing `runAcpWorkflowAgentSession` body — including all the
  call sites in `acp-agent.ts` — is unchanged for workflow-shaped
  work items, so call sequence and wire shape are byte-identical.
  The generic path falls back to the ephemeral path only when
  `manager` / `serverConnection` / `projectId` / `agentSessionId`
  are missing (same fail-mode contract as the workflow path).

- `ActionContext` (`packages/runner/src/core/types.ts`) gained
  `ownerKind?: string | null` and `agentSessionId?: string | null`
  fields, propagated from `RenderedWorkItem` by
  `baseContext` in `packages/runner/src/runtime/executor.ts`. These
  are set by the server for agent-job dispatches (T-001) and the
  raw-prompt-only AgentJob validation path leaves them null.

- Tests added:
  - `tests/acp-connection.spec.ts` — `AcpSessionManager keys` block
    (prefixed keys, helpers, workflow-vs-generic coexistence
    without collision).
  - `tests/acp/session-target.spec.ts` — new spec; covers generic
    vs workflow target derivation across
    owner-kind / agentSessionId / projectId / session-name
    combinations, including the "agent-job without
    sessionId falls through to workflow shape" edge case
    (raw-prompt-only AgentJob).
  - `tests/server-connection-generic-session.spec.ts` — new spec;
    covers each new `*AgentSession` connection method's URL path
    and body, distinctness from the workflow URL space, and the
    404 / 500 contracts.
  - `tests/acp/session-strategies-generic.spec.ts` — new spec;
    covers generic dispatch routing
    (agent-job → `getAgentSession` / `openAgentSession` /
    `attachAgentSession` / `agentSessionRuntimeEvents` only,
    no workflow call),
    workflow dispatch routing (unchanged),
    cached-entry under the `generic:` key,
    and runtime-event delivery to the generic URL.

- Existing test fixtures updated for the new `key()` signature:
  `tests/acp-agent.spec.ts` and `tests/acp/support.ts` now use
  `acpSessionManager.workflowKey(...)` when populating the cached
  session entry. `host.resolveFollowupTarget` (which still knows
  the caller is a workflow followup) was updated to call
  `workflowKey`.

### Gotchas

- The URL substring check `/sessions/project-1/...` collides with
  `/agent-sessions/project-1/...` (the generic URL contains the
  workflow URL as a substring). New tests assert the full runner-
  prefixed URL via regex, not `toContain`, to avoid the
  false-positive on the workflow path.

- The `mock.calls[N]` index is shared across `fetchMock` invocations
  in a test — when capturing the URL of the second call, use
  `mock.calls[1]`, not `mock.calls[0]`. Easy to misread when the
  variable name doesn't reflect the call order.

- The existing `*WorkflowAgentSession` server methods are NOT
  changed; the agent-job wire path now goes to the new
  `*AgentSession` endpoints, and an older server that has not yet
  shipped the generic endpoints will return 404 for an agent-job
  dispatch. This is a coordinated T-002/T-003 change on the server
  side; T-003 mints the `AgentSession` and adds the endpoints.

- `acp-agent.ts` continues to call
  `runAcpWorkflowAgentSession`; the function itself
  internally dispatches to the generic strategy. The agent-job
  call sequence in `acp-agent.ts` is unchanged.

- `acpSessionManager.set(workflowKey(...))` in the existing
  shared-session fixture used to be
  `acpSessionManager.set(key("workflow-1", "shared-session"))`,
  which previously produced `workflow-1:shared-session`. After
  T-002 the same fixture produces
  `workflow:workflow-1:shared-session`. The
  `AcpSessionManager` cache lookup in
  `runAcpWorkflowAgentSession` was updated to use
  `manager.workflowKey(...)` so both sides agree on the new
  prefix. The cache-hits-test in the
  `session-strategies-reuse.spec.ts` continues to work because
  the lookup and the pre-seeded entry both use the prefixed form.

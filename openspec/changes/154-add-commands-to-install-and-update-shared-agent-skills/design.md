## Context

Mohist currently has an internal skill system under `.mohist/skills` that `SkillService` scans and runs through Mohist workflows. The requested commands manage a different artifact class: coder agent skills under `.agents/skills`, consumed directly by coding agents such as opencode, Codex, and Claude Code.

The CLI already uses grouped Commander modules for local configuration commands such as `providers`, and not every command requires the Mohist server. Installing shared agent skills is a filesystem operation on a target repository, so it should run locally without server state, database access, or `SkillService` involvement.

## Goals / Non-Goals

**Goals:**

- Add `mo skills install [--force] [--path <repo>]` and `mo skills update [--path <repo>]` as local CLI commands.
- Write only `mohist` and `mohist-explore` AgentSkills to `.agents/skills/<name>/SKILL.md`.
- Keep generated files compliant with AgentSkills frontmatter: directory name equals `name`, and each `SKILL.md` includes `name` and `description`.
- Make repeated runs idempotent for files generated by Mohist.
- Protect user-modified files unless `install --force` is used.
- Clearly communicate that `.agents/skills` is separate from `.mohist/skills`.

**Non-Goals:**

- Do not change `SkillService`, `.mohist/skills` scanning, skill execution, or issue generation.
- Do not add server APIs, database tables, or background jobs.
- Do not install `mohist-walkthrough` by default.
- Do not support per-agent directories such as `.opencode/skills`, `.codex/skills`, or `.claude/skills` in this change.

## Decisions

### D1: Implement as a Local CLI Command Group

Add `packages/cli/src/cli/commands/skills.ts` with `setupSkillsCommands(program)`, then register it from `packages/cli/src/cli/index.ts`. The command group should not call `requireServer()` because the operation only writes files in the target repository.

**Alternatives considered:** Reusing `/api/skills` or adding a server route would couple agent skill installation to the internal Mohist skill runtime and require server availability for a local file copy operation. Adding the commands under `project` would hide the distinction between project registration and agent skill distribution.

### D2: Hide Generation and Safety Rules Behind One Utility

Create a small module such as `packages/cli/src/agent-skills/shared-agent-skills.ts` that exposes a narrow API, for example `installSharedAgentSkills({ projectPath, force })` and `updateSharedAgentSkills({ projectPath })`. The module owns the list of distributed skill names, template rendering, marker/checksum handling, file status detection, and write results.

This keeps the Commander module shallow: parse options, call the utility, format the result, set a non-zero exit code when protected files block an operation.

**Alternatives considered:** Keeping templates and overwrite checks directly inside the CLI command file is simpler initially but leaks generation policy into command wiring and makes tests depend on console behavior. A class-based service is unnecessary because there is no persistent state or dependency graph.

### D3: Use Built-In TypeScript Templates Instead of Reading `.agents/skills` at Runtime

Store the `mohist` and `mohist-explore` `SKILL.md` contents as built-in template strings in source, or in adjacent source modules that are bundled with the CLI. The templates should be the single source of truth for generated content and include a Mohist-generated marker plus a checksum of the template body.

**Alternatives considered:** Copying from the repository's `.agents/skills` directory at runtime would fail when Mohist is installed as a package without the source checkout layout. External template files would require extra packaging rules; they are only worthwhile if templates become large or numerous.

### D4: Detect User Edits With a Generated Marker and Checksum

Generated files should include a comment marker near the top, for example `<!-- Generated by Mohist. checksum: <sha256> -->`. On install/update, treat an existing file as Mohist-generated only when the marker exists and the stored checksum matches the file content after excluding the marker line.

If the file is missing, create it. If it is generated and unchanged, refresh it when the current template differs. If it exists without a valid marker/checksum, report it as protected and skip it unless `force` is true. With `force`, overwrite protected files and replace them with a marked generated file.

**Alternatives considered:** A marker-only check is easier but would overwrite files that users edited below the marker. A sidecar manifest adds extra files and more cleanup questions. A checksum in the file keeps the ownership signal local to the artifact and avoids hidden state.

### D5: Define `install` and `update` Semantics Narrowly

`install` creates missing skills and refreshes Mohist-generated skills. It refuses protected user-edited files unless `--force` is provided. `update` refreshes only existing Mohist-generated skills and creates missing distributed skills as needed so users can repair partial installations; it never overwrites protected files because it has no `--force` option.

Both commands write the same fixed set: `mohist` and `mohist-explore`. Both commands should be idempotent: a second run over current generated files reports no changes and leaves file contents unchanged.

**Alternatives considered:** Making `update` skip missing files would preserve a stricter distinction between install and update, but it would make recovery from partially deleted generated skills less useful. Adding `--force` to update is possible later, but keeping force only on install makes destructive intent explicit.

### D6: Keep Output Human-Readable and Test Results Programmatic

The utility should return per-skill results such as `created`, `updated`, `unchanged`, `skipped-protected`, and `overwritten`. The CLI should print target path, affected files, and a short explanation when files are skipped. Help text for the command group should explicitly say these commands manage `.agents/skills` for coding agents, not `.mohist/skills` for Mohist internal skill execution.

**Alternatives considered:** Printing from the utility would reduce plumbing but make tests more brittle and mix filesystem policy with terminal formatting.

## Risks / Trade-offs

- [Risk] Existing generated files from before this marker format will look user-modified and be skipped. → Mitigation: `install --force` provides an explicit migration path, and the skip message should explain why the file was not overwritten.
- [Risk] Embedded templates can drift from the repository's checked-in `.agents/skills` examples. → Mitigation: add tests that assert generated files contain required frontmatter and only the allowed skill names; optionally compare against fixture snapshots if the project adopts them.
- [Risk] Users may expect these commands to affect Mohist internal skills. → Mitigation: command descriptions and help text must name `.agents/skills` and mention `.mohist/skills` is not touched.
- [Risk] Checksum normalization can create false positives or false negatives if implemented inconsistently. → Mitigation: centralize marker insertion and checksum calculation in one module and test unchanged, edited, and template-updated cases.
- [Risk] `--path` may target a non-repository directory. → Mitigation: only require a writable target directory; create `.agents/skills` beneath it. Avoid adding a Git dependency unless specs later require repository validation.

## Migration Plan

1. Add the shared agent skill generation utility and templates.
2. Add the `skills` Commander module and register it from the CLI entry point.
3. Add tests for first install, repeat install/update idempotency, template refresh, protected user edits, forced overwrite, custom `--path`, AgentSkills frontmatter validity, and absence of `mohist-walkthrough`.
4. Update CLI help or docs to describe `.agents/skills` versus `.mohist/skills`.
5. Rollback is removing the command registration and generation module; generated files in user repositories are regular markdown files and do not require database or server cleanup.

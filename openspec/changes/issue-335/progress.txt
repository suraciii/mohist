## Codebase Patterns

- **C# 14 union + persistence convention**: `IssueEvent` is a tagged union; the
  persisted `IssueEvents.Type` column stores the `IssueEventSerializer.BusType`
  value (reverse-DNS string), not the CLR name. A rename point in `BusType`
  moves both the bus type and the persisted `Type` together.
  `IssueEventSerializer.Type()` (the CLR-name helper) is dead but kept for
  storage-facing traceability; it derives from `Unwrap(payload).GetType().Name`
  and tracks the rename for free.
- **Catalog vs serializer routing**: `EventCatalog.ReverseDns.Issue*` constants
  own the reverse-DNS strings. Terminal ids (IssueCompleted / IssueCancelled)
  must be sourced from those constants in `BusType` so the serializer and
  catalog cannot drift; non-terminal ids may stay as inline literals if the
  acceptance criterion only requires the terminal pair to be sourced.
  `EventCatalog.All` is the documentation/introspection list, distinct from
  `ReverseDns`; adding constants to `ReverseDns` does not require adding them
  to `All` (and the issue's non-goal says "don't fix the broader catalog
  drift").
- **Historical migration immutability**: EF migrations are immutable history;
  `20260629120000_BackfillIssueCompletedAt.cs` references the legacy ids
  (`work-completed`/`closed`) in both SQL and comments. Per design D6, that
  file MUST NOT be edited — its SQL only runs once on historical data, and on
  fresh databases it is a no-op on empty rows. The associated test
  (`BackfillIssueCompletedAtMigrationSpecs`) intentionally mirrors the
  migration's legacy-id SQL to validate the historical backfill; these legacy
  id strings are exempt from the sweep.
- **Indentation in C# doc-comment blocks**: when applying structured patches
  that rewrite large doc-comment regions in `EpicAutoDoneHandler.cs`,
  `EpicReconciliationService.cs`, `InboxProjectionHandler.cs`, prefer replacing
  the entire `/// <summary>…</summary>` block in one edit. Per-line edits
  easily introduce indentation drift (the in-progress patch leaked 4 extra
  spaces into each line of the rewritten `<summary>` block of `Epic*` files).
- **Subscription attribute is pipe-separated**: the single
  `[Subscription(Type = "a|b|c")]` allows one handler to subscribe to multiple
  event ids. The id list concatenates string literals and
  `EventCatalog.ReverseDns.*` constants: `"com.mohist.x|" + ReverseDns.Y + "|…"`
- **Constrained renaming via const reference**: when a public/internal const is
  renamed (`WorkCompletedType → CompletedType` / `ClosedType → CancelledType`)
  and is referenced by name in many files, a sweeping replace-all pattern is
  safe and faster than per-site rewrites.

## Decisions

- **T-001 decision — D-impl-1**: keep `EventCatalog.All` minimal (the two
  terminal ids plus pre-existing entries); do not add all 13 issue event
  constants to `All`. The proposal's non-goal says the broader "catalog lists
  4 of 13" drift is out of scope. Adding them to `ReverseDns` is necessary
  only where the serializer routes through the constant; this task only routes
  the terminal pair through constants, so no new constants are added beyond
  preserving the existing terminal ones.
- **T-001 decision — D-impl-2**: the historical migration
  `20260629120000_BackfillIssueCompletedAt.cs` and its dedicated test
  `BackfillIssueCompletedAtMigrationSpecs.cs` are intentionally not swept.
  Per design D6, that file is immutable history; its SQL still references the
  legacy ids because it ran once on historical data and is now no-op. The
  test mirrors the migration's SQL (with seeded legacy-id rows) to validate
  idempotency on historical data. Renaming that test to use canonical ids
  would change what the test exercises.
- **T-001 decision — D-impl-3**: kept `IssueQuerier.WorkStartedType` and the
  bare `"com.mohist.issue.reopened"` literal in `IssueStageAttribution`,
  `StagePopulationSnapshotService`, and `IssueQuerier` as inline constants —
  the rename scope is terminal ids only. Non-terminal ids remain literal
  strings rather than be migrated to `EventCatalog.ReverseDns.*` constants,
  because adding new `ReverseDns` constants is outside T-001 scope.

## Decisions (T-002)

- **T-002 decision — D-impl-4**: pure data backfill modeled on
  `20260629120000_BackfillIssueCompletedAt` — no `BuildTargetModel` override,
  no Designer partial, no model-snapshot update. `[Migration]` attribute
  lives on the partial class in the same .cs file. The spec
  (`MigrationClass_DoesNotOverrideBuildTargetModel`) guards the invariant
  by reflecting on the derived type and asserting the resolved method
  declares on `Microsoft.EntityFrameworkCore.Migrations.Migration` (the
  base), not on `BackfillIssueEventsTerminalTypeRename`. A genuine override
  on the derived class would imply a model change, which would need a
  Designer partial and a snapshot update — the test catches that drift.
- **T-002 decision — D-impl-5**: timestamp `20260702120000` chosen over a
  tighter alternative because it (a) is strictly later than
  `20260629120000_BackfillIssueCompletedAt`, satisfying the design D4
  requirement, and (b) follows the same day-of-publication convention as
  the prior raw-SQL migration (`120000` mid-day suffix).
- **T-002 decision — D-impl-6**: Down is symmetric (canonical→legacy
  rewrite), unlike `BackfillIssueCompletedAt` whose Down is a no-op
  (additive completedAt). Per design D4 / open question 2, the symmetric
  Down is the chosen posture for this rename; pre-rename rows return to
  legacy AND post-rename rows are also rewritten back, so a clean
  rollback of mixed-era data is possible. The
  `UpThenDown_RoundTripsTerminalTypes_AcrossEras` spec exercises the
  mixed-era rollback path explicitly.

## Gotchas (T-002)

- `Migration.BuildTargetModel` is virtual on the EF base, so a naïve
  `GetMethod("BuildTargetModel")` reflection check always returns
  non-null. The right invariant is "no override on the derived class" —
  check `method.DeclaringType == typeof(Migration)` instead of asserting
  the method is null. (First pass on the spec used the null check and
  failed for this reason.)
- `dotnet test --filter FullyQualifiedName~BackfillIssue…` against the
  full suite does not pick up the new spec until after a clean
  `dotnet build` — the test binary is keyed to the test assembly build
  output, so a stale build silently filters the new spec out.
- The historical `20260629120000_BackfillIssueCompletedAt` migration and
  its dedicated spec were intentionally NOT touched (per T-001 D-impl-2
  and design D6). On a fresh DB both migrations are no-ops on empty
  data; on an already-migrated DB only the new migration runs.

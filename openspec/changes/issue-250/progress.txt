# Issue #250 progress

## T-001 — extract acp/process.ts + acp/session-events.ts

### Codebase patterns

- All runtime/agent protocol code lives under `packages/runner/src/actions/`. The single fat file `acp-agent.ts` (1552 lines) is being decomposed into a focused module group at `acp/` plus a slim entry.
- Tests live under `packages/runner/tests/`. ACP support helpers (e.g. `support/fake-acp.ts`) are imported by both `acp-agent.spec.ts` and `acp-tool-noise.spec.ts`. The `fake-acp.ts` `AcpProcessHandle` type is imported from `acp-agent.ts`.
- Public surface imported by external consumers (`executor.ts`, `registry.ts`, `rebase.ts`, `tests/support/fake-acp.ts`, `tests/acp-tool-noise.spec.ts`, `tests/acp-agent.spec.ts`):
  - `acpAgentAction`
  - `setAcpProcessFactoryForTest`
  - `AcpProcessHandle` (type)
  - `defaultCompactionConfig`
  - `resolveCompactionConfig`
  - `AcpProcessFactory` (type, supporting)
  - `CompactionConfig` (type, supporting)
  - `CompactionStrategy` (type, supporting)
- Import paths must stay byte-identical at the entry; module re-exports handle the rest.

### Gotchas / decisions

- `extractCompactionEventFromUpdate` is listed in the design under `compaction.ts` (T-002) and not under `session-events.ts` (T-001). However, it is the only consumer of `createObservabilityAwareEmitter` (in `session-events.ts`). To make the observability emitter work as a self-contained module, the function is kept as a **private (non-exported) helper** in `session-events.ts` for T-001. T-002 can lift it to `compaction.ts` and have `session-events` import it back, or restructure the observability emitter.
- `buildLivenessEventPayload` accepts the liveness state structurally; the consumer `emitLivenessStatusEvent` (newly added) and the liveness state machine in `acp-agent.ts` pass the same shape. `LivenessFailureReason` is still defined in `acp-agent.ts` for T-001 (moves to `liveness.ts` in T-003) — `buildLivenessEventPayload` types `failureReason` as `string` to avoid pulling the type from a module that will move.
- `hasPostProbeActivity` belongs to the liveness state machine and stays in `acp-agent.ts` for T-001 (moves to `liveness.ts` in T-003). It is **not** re-exported.
- The slim entry uses `export type` for the two type-only re-exports (`AcpProcessFactory`, `CompactionStrategy`). `AcpProcessHandle` and `setAcpProcessFactoryForTest` keep value-style `export` — but `AcpProcessHandle` is in fact only used as a type by tests; the value-style re-export is harmless and keeps the shape of the original module identical. `CompactionConfig` (an interface) stays defined inline in `acp-agent.ts` for T-001; T-002 will move it to `compaction.ts` and the entry re-export will switch to `export type`.
- `emitLivenessStatusEvent` is a thin wrapper around `buildLivenessEventPayload` + `emitSessionEvent` + the `SESSION_LIVENESS_EVENT` constant. It logically lives next to the payload builder and the constant, so it was added to `session-events.ts` (not in the T-001 D1 list, but its natural home and the only way to keep `acp-agent.ts` from holding the constant or the payload builder).

## T-002 — extract acp/compaction.ts + acp/model-resolution.ts + acp/agent-config.ts

### Codebase patterns

- The 3 new modules follow the **leaf / one-way dependency** rule: `compaction → core`, `model-resolution → session-events`, `agent-config → compaction`. None of them reach back into `acp-agent.ts` or other acp submodules.
- The slim entry continues to use the **byte-identical public surface** pattern: `defaultCompactionConfig`, `resolveCompactionConfig`, and types `CompactionConfig`, `CompactionStrategy` are now re-exported from `./acp/compaction.js`. Test imports and external consumer imports remain unchanged.
- The `applyRequestedModel` log lines and setSessionConfigOption→unstable_setSessionModel fallback ordering were kept byte-identical; only their home moved. The diagnostic-context object shape (`workflowRunId/workId/stage/sessionName/requestedModel/requestedModelSource`) is unchanged.
- `resolveAgentConfig` retains the two-path parsing (nested `agent.*` keys vs top-level `with.*` keys); only the call site changes (was inline in `acp-agent.ts`, now imported from `./acp/agent-config.js`).
- The 4 compile-time constants used by `compaction.ts` (`DEFAULT_COMPACTION_THRESHOLD = 0.8`, `DEFAULT_COMPACTION_STRATEGY = "summary"`, `COMPACTION_META_KEY = "opencode.compaction"`) move with the module and stay module-private.

### Gotchas / decisions

- `extractCompactionEventFromUpdate` is a **pure extraction** (no JSON helper deps from session-events). Per the AC, it stays pure: it inlines a tiny `numberField` helper (`typeof === "number" && Number.isFinite(value)`) so it has no runtime dep on `session-events`. This keeps the dependency graph strictly one-way: `session-events` doesn't need to import `compaction` at runtime.
- `session-events.ts` keeps `import type { CompactionEventPayload, CompactionStrategy } from "./compaction.js"`. This is a **type-only import** — erased at compile time, no runtime cycle. The observability emitter's two extractors (`extractCompactionEventFromUpdateLocal`, `extractResolvedModelFromConfigUpdateLocal`) are local helpers that mirror the logic of `compaction.ts` / `model-resolution.ts`. This is a tiny (~50 line) duplication, intentional to preserve session-events as a runtime leaf.
- `errorMessage` is folded into `model-resolution.ts` per D1 — its only consumer is `applyRequestedModel`. It is **not** exported (no other module needs it).
- The `extractResolvedModelFromConfigUpdate` extraction moved from `session-events.ts` (private) to `model-resolution.ts` (exported). It is unused by other modules right now but exposed for future callers; the observability emitter in session-events duplicates the logic inline (`extractResolvedModelFromConfigUpdateLocal`).
- `buildSessionMeta` in `compaction.ts` returns the same `[COMPACTION_META_KEY]: { threshold, strategy }` object as before. The `newSession` / `resumeSession` callers in `acp-agent.ts` import it from the new module.
- The `numberInput` import in `acp-agent.ts` is now the only JSON helper still imported directly from `core/json.js` (used by `expectationRepairLimit` and the run-* timeout resolution). The other two helpers (`stringInput`, `objectInput`) are no longer needed in `acp-agent.ts`.

## T-003 — extract acp/liveness.ts

### Codebase patterns

- The new `liveness.ts` module follows the **one-way leaf / single dependency** rule: depends on `core/types` (leaf), `runtime/opencode-log-diagnostics` (leaf), `acp/process` (leaf per D2), and `acp/session-events` (the only acp submodule dep). No reverse edges.
- All four concurrency primitives folded into liveness per design.md D1: `timeout` (exported, shared with `session-strategies` to-be), `aborted` (module-private, only `monitorPrompt` uses it), `cancelAndReturn` (exported, `monitorPrompt` calls it), `toError` (module-private, only `monitorPrompt` uses it).
- The two compile-time constants `CANCEL_TIMEOUT_MS = 5_000` and `PROBE_PROMPT` (string) are module-private to `liveness.ts`. They were previously module-private in `acp-agent.ts`.
- `LivenessProbeState` (interface) stays **module-private** in `liveness.ts` — it's only used as a transient shape inside `monitorPrompt` (the `probeState` literal passed into the diagnostic message and event payload). T-001's note predicted it might be needed externally; it isn't. `SessionLivenessState`, `LivenessFailureReason` are `export` because they're part of the public signature of `monitorPrompt` (its options object) and the `AcpSessionResult` / `AcpPromptRunResult` types in `acp-agent.ts`.
- `monitorPrompt`'s parameter `livenessState: SessionLivenessState` is structurally the same shape as the liveness state object passed to `emitLivenessStatusEvent` (which already accepts a structural type). No coupling change — `emitLivenessStatusEvent` was already designed for structural acceptance per T-001 (the `failureReason` extras field is typed `string`, not `LivenessFailureReason`, to keep the dependency graph clean).
- `acp-agent.ts` keeps the `AcpSessionResult` / `AcpPromptRunResult` interfaces (they reference `LivenessFailureReason` via type-only import) and the `failureCategory` plumbing. These move to `session-strategies.ts` in T-004.

### Gotchas / decisions

- `OpencodeProviderErrorDiagnostic` stays as a **type-only** import in `acp-agent.ts` because `AcpSessionResult.failureCategory` and `AcpPromptRunResult.failureCategory` both still reference it. The runtime functions (`appendOpencodeDiagnostic`, `findOpencodeProviderErrorDiagnostic`) are no longer imported in `acp-agent.ts` — they moved with `monitorPrompt`.
- `buildUsageUpdatePayload`, `emitSessionEvent`, `hasUsageUpdateContent` from `session-events.ts` are imported by `liveness.ts` (used inside `emitPromptUsageIfAppropriate`). `emitLivenessStatusEvent` is also imported from `session-events.ts` (was added in T-001 — perfect home for the payload builder + constant).
- `acp-agent.ts` now imports `timeout` from `./acp/liveness.js` for the 3 `Promise.race` calls in `runResumedWorkflowAgentSession` / `runNewWorkflowAgentSession` / `runEphemeralWorkflowAgentSession` (against `connection.resumeSession` / `newSession` / `initialize` / `newSession`). This is the D1 wiring — T-004 will move these 3 run-* functions into `session-strategies.ts` and re-import `timeout` from `liveness` there. For now `acp-agent.ts` re-exports nothing new (the public surface stays frozen at 5 exports).
- The `cancelled` flag in `cancelAndReturn` is set via `.then(() => { cancelled = true })` rather than awaiting — same logic, byte-identical to original.

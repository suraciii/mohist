## Codebase Patterns

- `OtelDb` is `sealed`; tests use the internal `InMemoryOtelDb.Create()` factory that constructs an `OtelDb` with explicit connection strings plus a keeper `SqliteConnection` to keep the shared-cache in-memory DB alive. New columns / indices must be mirrored both in `OtelDb.EnsureInitialized` AND in `InMemoryOtelDb.Create()`'s DDL list, otherwise tests that use the in-memory factory won't see the new schema.
- `IOtelMaintenanceCallback` is invoked by `OtelDiagnosticsSampler` only while `_enabled` is true. The sampler is the off-switch; callbacks trust the sampler.
- Maintenance tests are spec tests in `packages/server/tests/Mohist.Server.SpecTests/Specs/Telemetry/` and use `InMemoryOtelDb.Create()` + `FakeTimeProvider` (no wall clock, no real filesystem). xunit v3 / Microsoft.Testing.Platform runner is invoked by the built binary with `-class` / `-method` filters.
- Test seeding for traces uses ISO 8601 UTC text formatted via `instant.ToString("yyyy-MM-ddTHH:mm:ss.fffffffZ", CultureInfo.InvariantCulture)`, matching production and lexicographic ordering.
- All time logic flows through `TimeProvider.GetUtcNow()`.

## T-001 decisions and gotchas

- One maintenance invocation is one bounded transaction and deletes at most the batch size. Cancellation rolls back the in-flight batch; the next invocation resumes from the oldest remaining aged Trace.
- Time retention filters `end_time` and orders by `start_time ASC`; a growing Trace whose end time is current is not removed.
- DI registration uses `TryAddEnumerable` with singleton `IOtelMaintenanceCallback` descriptors so callbacks can stack.
- Statement observers count SQL commands without rewriting `OtelDb`; cost assertions compare equal work with little and much unrelated history.

## T-002 decisions and gotchas

- Size eviction re-probes after each bounded delete batch and reclaims before the next batch; the loop continues toward the 80% low watermark while each iteration remains bounded.
- A blocked reclaim result is explicit through `IOtelStorageReclaimer`; maintenance arbitrates with `reclamationBlocked: true` so admission closes even if a fake probe reports below the high watermark.
- `RuntimeObservability.RecordIngest` preserves an active `storage_budget_exhausted` reason when rejected spans arrive; generic telemetry rejection must not overwrite the budget cause while the guard remains closed.
- The full-VACUUM regression assertion matches the standalone `VACUUM` command, not the substring in `incremental_vacuum`.
- The shared server `JSON.Options` must serialize the marker; a local `JsonSerializerOptions` field violates the architecture rule.

## T-003 decisions and gotchas

- Recovery runs as an `IOtelMaintenanceCallback` (`OtelStorageRecoveryMaintenance`) alongside the existing retention and storage callbacks. It owns a one-shot gate (`Interlocked.CompareExchange`) so the rebuild decision fires only on the first post-start tick; subsequent ticks short-circuit before probing.
- The rebuild threshold is strictly above 100% of `StorageBudgetBytes`, so the online eviction from T-002 (90% high watermark) gets the first chance to reclaim. In practice this means a store that eviction can clear never hits the rebuild path.
- The file-deletion set is `OtelDb.ObservationStoreFiles()` which exposes the four paths (.db, -wal, -shm, .meta). Constants `OtelDb.WalSidecarSuffix` / `OtelDb.ShmSidecarSuffix` are exposed so the probe and the recovery reference the same suffixes; `OtelStorageGuard.MarkerSuffix` stays internal and is reused for the .meta path.
- `IOtelDbPool` (`ClearAll()`) is a new seam that produces to `SqliteConnection.ClearAllPools()`. `SqliteOtelDbPool` is the production implementation; specs inject a `RecordingPool` for verification.
- `OtelDb.ResetInitialization()` clears the in-process `_initialized` flag under the existing `_initGate` lock so the next `OpenReadWriteConnection` re-runs `EnsureInitialized` against a (presumed fresh) on-disk file with `auto_vacuum=INCREMENTAL`. No connection is touched during the reset itself.
- `storage_data_reset` is published on `DegradationSource.StorageWrite` (same lifecycle as the existing `storage_unverified`) and cleared by the first committed production write through `RecordIngest`'s `ClearsStorageWrite` channel. The method `RuntimeObservability.PublishStorageDataReset` mirrors `PublishStorageBudgetExhausted`'s state-lock pattern but on the StorageWrite source.
- A rebuild failure (exception in pool clear / file delete / open) is contained: it logs an error, still publishes `storage_data_reset` so operators see the store is unusable, and surfaces as a non-throwing `OtelStorageRecoveryOutcome.RebuildFailed` for specs. The maintenance loop's existing `catch` swallows the rest.
- `InMemoryServerFileSystem` grew a `DeletedPaths` property (additive, no contract change) so spec tests can assert the exact deletion ordering on rebuild without bringing in a fake-of-a-fake wrapper.

# Issue 531 T-001 Progress

## Codebase Patterns

- **AgentJobGrain** uses `[PersistentState<AgentJobState>]` for durability + best-effort
  mirror to `AgentJobStore` (JSON only). This is the "Orleans-state-plus-best-effort-mirror"
  path T-001 replaces.
- **`AgentJobState`** is serialized as JSON in `AgentJobs.State`. Computed columns
  `ProjectId`, `AgentId`, `Status`, `SubmittedAt`, `TerminalAt` are projected via
  `json_extract(...)` STORED.
- **AgentJob admission today** is a push: `AgentJobGrain.TryAssignToRunnerAsync`
  → `RunnerGrain.AssignAgentJobAsync` → `RunnerWorks` row + Orleans `RunnerWorksState`.
- **`AgentJobs` row** is read by `AgentJobQuerier` (Status filter, ordering by SubmittedAt).
- **`RunnerWorks` table** has `Id`, `RunnerId`, `OwnerKind`, `OwnerId`, `WorkId`,
  `TakenAt`, `Status`, `Reason` — index on `(RunnerId, Status)` and
  `(RunnerId, OwnerKind, OwnerId, WorkId)`.
- **Orleans grain non-reentrancy** is the default — no `[Reentrant]`. Per-grain
  serialization is therefore free for the AgentJobGrain key.
- **Time injection**: `TimeProvider` everywhere. Tests use `FakeTimeProvider`.
- **In-memory event bus / EventStore**: `RecordingEventStore` in tests,
  `InMemoryEventBus` provided.
- **EF migration pattern**: each migration has a `*.cs` body and a matching
  `*.Designer.cs` if the model changes. Pure data backfills can omit the
  designer (see `20260629120000_BackfillIssueCompletedAt.cs`).
- **Index naming**: `IX_<Table>_<Columns>` convention.
- **Test infra**: `TestSqliteDatabase` clones a per-process migrated template;
  `AgentJobGrainFixture` hosts an `InProcessTestCluster` with `FakeTimeProvider`.
- **Push retry → owner timeout**: existing `AgentJobBackoffSchedule` carries
  `TotalBound` (mapped to `DispatchRetryBound`). The design repurposes this
  value: measured from `ReadySince` rather than dispatch attempts.

## Decisions (this task)

- **Atomic ledger row**: extend `AgentJobRow` with scheduling columns and an
  optimistic-concurrency `Revision` (INTEGER, ETag). The grain reads/writes the
  row through a new `AgentJobLedgerRecord` shape; every state transition is
  one transaction against the row, guarded by `Revision`.
- **No Runner work record on admission**: drop the `AssignAgentJobAsync` push
  and `RunnerWorks` insert from the AgentJob admission path. `RunnerWorks`
  remains in place for backward compatibility but the AgentJob grain no longer
  creates rows there. T-003 will remove `RunnerWorks` entirely.
- **Admission outcomes**:
  - Eligible runner with capacity → `Pending` with `AssignedRunnerId`,
    `ReadySince`, `DispatchJson` written.
  - No eligible runner / every eligible runner full → terminal `Failed`,
    `runner-unavailable`, **no** `DispatchJson` / `AssignedRunnerId`.
  - The same `runner-unavailable` outcome can also be reached later via the
    readiness timeout.
- **Claim path**: `IAgentJobGrain.ClaimNextAsync(runnerId)` performs the
  atomic Pending → Running transition, validates `AssignedRunnerId == runnerId`,
  and returns the persisted dispatch. Revision-checked.
- **Report path**: `ReportResultAsync` validates `RunnerId`/`WorkId` against
  the row and either applies a terminal transition or returns stale.
- **Orleans state removed**: `AgentJobGrain` no longer uses `[PersistentState]`.
  State lives on the `AgentJobs` row and is hydrated into a private field on
  activation. The recovery reminder continues to drive terminal-delivery and
  preparation recovery; the readiness check piggybacks on the same reminder.
- **Migration**: `20260729000000_AgentJobOwnerLedger` adds columns, backfills
  from existing JSON, validates that every nonterminal row reconstructs, and
  adds indexes. The migration aborts inside a transaction when validation
  fails; no rows change.

# Issue 531 T-002 Progress

## Codebase Patterns

- `DispatchService` is the poll assembler; `RunnerGrain.TryBeginPollAsync` and
  the lifecycle gate serialize poll admission, capacity checks, and owner
  claims.
- Workflow scheduling rows expose `ReadySince` as a computed DateTime, while
  AgentJob scheduling rows expose the indexed timestamp as an optional
  DateTimeOffset. Mixed-owner ordering needs a small query candidate record;
  it does not need a persisted scheduler object.
- AgentJob owner claims update the durable row through `AgentJobStore.ClaimAsync`.
  A grain activation must clear its hydration flag before reloading after that
  write, or the durable Running transition remains hidden behind cached Pending
  state.

## Decisions (this task)

- Added a runner-gated `TryClaimAgentJobAsync` that counts running WorkflowRun
  rows and running AgentJob ledger rows together before calling the owner grain.
  Revision and reconstruction conflicts are skipped; malformed dispatch data
  fails only the exact AgentJob owner.
- `DispatchService` now reads running and pending AgentJob projections directly,
  emits all missing running work before pending claims, then merges assigned and
  unassigned WorkflowRun and AgentJob candidates by readiness time.
- Legacy Runner work staging and relay methods remain temporarily available for
  the later T-003 removal, but the poll path no longer reads or writes them.
- The focused mixed-owner specs use unique projects and clear the shared runner
  registry before each scenario because the current registry returns all
  runners regardless of project.

# Issue 531 T-003 Progress

## Codebase Patterns

- `/api/runner/{id}/report` now routes AgentJob reports through
  `IAgentJobGrain.ReportResultAsync` directly. The grain already returns
  `Accepted` for the happy path and `Reason="stale"` for late reports on
  terminal jobs, so the route maps both to the same `RunnerReportResponse`
  `Tracked=true` ack and stops retrying either branch.
- `TaskLogService.IsActiveWorkAsync` now consults
  `IAgentJobStore.ListRunningForRunnerAsync` instead of `RunnerWorkStore`.
  The store has been removed entirely, so any future regression here shows
  up as a compile error.
- `RunnerGrain.GetRuntimeStateAsync` and `CloseoutLostAsync` both project
  the runner's active agent-job list from `IAgentJobStore.ListRunningForRunnerAsync`
  and report `runner-lost` via `IAgentJobGrain.ReportResultAsync`. The
  grain no longer holds any `_worksState` field, so the push-path code
  is unrepresentable.
- The drop migration `20260730000000_DropRunnerWorksTable` lives alongside
  T-001's atomic-ledger migration; deploy them together so the
  AgentJobs ledger has been writing scheduling columns before the legacy
  table disappears.

## Decisions (this task)

- Dropped the unused `IAgentJobGrain.MarkUnknownAsync` /
  `ReconcileRunningAsync` default-only members — T-001 already routes
  the only call site (`CloseoutLostAsync`) through `ReportResultAsync`
  and the T-001 design made the timeout terminal, so the Unknown
  state machine has no production consumer. The corresponding
  observation spec was removed in lockstep.
- `RunnerWorkReportResult`, `RunnerWorkAssignmentResult`, and
  `AgentJobPollState` serializer types were removed alongside the
  grain methods, so a stale reference would fail compilation rather
  than silently call a relay that no longer exists.
- The `RunnerWorks` migration remains an explicit drop table to make
  rollback obvious: the only safe reverse is to re-run T-001 first,
  since after this cutover the AgentJobs ledger is the sole owner.

## Status (fix-ci resumed 2026-07-30)

### Root cause

`AgentJobGrainSpecs` was hanging at
`SubmitAsync_RunnerAtPersistedSlots_LeavesSecondAgentJobPending`. The
hang was the visible symptom, but the underlying regression was the
combined budget/time waste from running a long serial collection under
a 10-minute wall clock cap. Reproduced locally with `dotnet test`
(passes) vs the MTP runner (`dotnet Mohist.Server.SpecTests -class
…AgentJobGrainSpecs`): the runner produces test-by-test progress and
the failing class exited at 16 tests run / 2 failed / wall time
≈ 2.9 s. No `dotnet test` invocation completes discovery within the
budget because MTP startup alone exceeds the budget for this class.

The actual failure that consumed the verification budget was the
`AgentJobGrainSpecs` collection:
1. T-001 (`912f34974`) removed the production calls to
   `IAgentJobDispatchObserver.AssignmentPreparedAsync` and
   `RunnerAcceptedAsync` from `AgentJobGrain`. The old push path used
   these hooks to flip `State.Status = Running` synchronously after
   the runner accepted; the new poll path moves Pending → Running
   inside `_jobStore.ClaimAsync` inside `ClaimNextAsync`. The
   observer hooks were not reinstated at the new call sites, so
   every `WaitForRunningAsync` test blocked forever waiting on a
   signal that was never raised.
2. `WaitForRunningAsync` itself did not drive the runner poll that
   triggers `ClaimNextAsync`. Under the reconciliation model only a
   poll can claim an AgentJob; the test support never invoked one.
3. `SubmitAsync_RunnerAtPersistedSlots_LeavesSecondAgentJobPending`
   asserted the legacy push-retry behavior — the second job stays
   Pending until the runner frees a slot. The T-001 spec
   (`specs/work-dispatch-ledger/spec.md#Polling-prioritizes-recovery-and-enforces-shared-capacity`,
   scenario "Admission finds no capacity") defines the post-T-001
   behavior: the second job must be terminal `runner-unavailable`
   with no pending dispatch.

### Fix (this turn)

1. `AgentJobGrain` (server): inject `IAgentJobDispatchObserver`;
   fire `AssignmentPreparedAsync` after `TryAdmitOnRunnerAsync`
   persists the ledger row, and `RunnerAcceptedAsync` after
   `ClaimAsync` reloads the row into Running. These restore the
   production observation points the tests rely on.
2. `AgentJobGrainTestSupport` (spec): `WaitForRunningAsync` now
   resolves the runner id from the job snapshot, triggers a
   `DispatchService.PollAsync` against the test silo service
   provider, and then awaits the observer signal. This is the
   reconciliation-model equivalent of the runner process polling
   for a fresh claim.
3. `AgentJobGrainSpecs`: the capacity scenario was renamed
   (`SubmitAsync_RunnerAtPersistedSlots_TerminatesSecondAgentJobWithRunnerUnavailable`)
   and re-asserted against the post-T-001 spec — second job ends
   Failed with `RunnerUnavailable`, no runner assignment, runner
   still shows only the first job as active work.

### Fix #2: agent-job dispatch observer must catch throwables, and
`WaitForRunningAsync` (test-local variant) must drive a poll

Re-ran the `AgentJobGrainPersistenceSpecs` collection after the
first fix landed. Two issues surfaced:

- `AgentJobGrainPersistenceSpecs.RunnerAcceptanceCrash_ReactivationReusesSameWork`
  hung at `[STARTING]`. Under the post-T-001 design only the
  poll path calls `RunnerAcceptedAsync`; the test was waiting on
  it directly after `SubmitAsync` (no poll in between). Removed
  the obsolete wait, kept the assertion shape (state is admitted
  + Pending with the original work id preserved across
  reactivation).
- `AgentJobGrainPersistenceSpecs` carries its own private
  `WaitForRunningAsync` / `RegisterRunnerAsync` /
  `ClearRunnerRegistryAsync` (it does not derive from
  `AgentJobGrainTestSupport`). The local `WaitForRunningAsync`
  was the old observer-only waiter; replaced it with the same
  poll-driving logic the support helper uses, including a
  `WaitForAssignedRunnerAsync` helper. Updated `SubmitAsync_PersistsInputAcrossDeactivation_AndReplayResumesSameJob`
  passed.

### Fix #3: `AgentJobGrain.TryAdmitOnRunnerAsync` / `ClaimNextAsync`
must catch observer throws (replaces the OLD `TryDispatchAsync`
try/catch)

In the OLD push path `TryDispatchAsync` wrapped the dispatch in
a try/catch and logged / rescheduled on throw. The new
owner-ledger path has no equivalent catch, so a misbehaving
observer would surface as a failed `SubmitAsync` /
`EnsureSubmittedAsync`. Added
`SafeAssignmentPreparedAsync` / `SafeRunnerAcceptedAsync`
helpers that swallow the throw and log a warning, so the
ledger row / claim remain authoritative and the runner-side
polling can retry.

### Final summary

- **Root cause:** T-001 (`912f34974`) replaced the push-style
  AgentJob→Runner assignment with a poll-driven ledger model but
  did not reinstate the `IAgentJobDispatchObserver` hooks the
  tests relied on for synchronization, and the test support
  never drove the runner poll that triggers `ClaimNextAsync`.
  One `AgentJobGrainSpecs` test asserted the obsolete push-retry
  behavior; two more were rewritten to match the new spec.
- **Server fixes:** `AgentJobGrain` now injects the dispatch
  observer, fires `AssignmentPreparedAsync` after a successful
  admission row write, and `RunnerAcceptedAsync` after
  `ClaimAsync` flips the row to Running. Both observer calls are
  wrapped in `Safe{AssignmentPrepared,RunnerAccepted}Async`
  helpers that mirror the OLD `TryDispatchAsync` try/catch — a
  misbehaving observer cannot poison the ledger row or the
  claim, and the next poll can retry.
- **Spec fixes:** `AgentJobGrainTestSupport.WaitForRunningAsync`
  resolves the runner id from the job snapshot, drives a
  `DispatchService.PollAsync` against the test silo service
  provider, then awaits the observer signal. `AgentJobGrainPersistenceSpecs`
  has its own private `WaitForRunningAsync` (the class doesn't
  derive from the support class) — that helper was upgraded in
  place. Three obsolete assertions in `AgentJobGrainSpecs`
  (`SubmitAsync_RunnerAtPersistedSlots_…`,
  `SubmitAsync_NoEligibleRunner_StaysPendingAndRetriesWithBackoff`,
  `DelayedGenericJobFailure_AfterReset_DoesNotCloseTheReplacementRuntime`'s
  presence-timer interaction) were brought in line with the
  T-001 spec.
- **Verification:** `AgentJobGrainSpecs` runs in ~3 s with
  **16/16 passing**. `AgentJobGrainPersistenceSpecs.RunnerAcceptanceCrash_ReactivationReusesSameWork`
  passes (0.55 s), `…SubmitAsync_PersistsInputAcrossDeactivation_…`
  passes (0.60 s). The full `dotnet build` of
  `Mohist.Server.SpecTests` is clean.
- **One remaining failure (`PreparedAssignment_OfflineBeforeAcceptance_ReassignsStableWorkToHealthyRunner`)
  is a real spec gap, not a test defect.** When an AgentJob is
  admitted to a runner that later unregisters, the new
  owner-ledger model leaves `AssignedRunnerId` pointing at the
  dead runner and `TryAdmitAsync` short-circuits before
  re-evaluating against the replacement. `CloseoutLostAsync`
  only covers running jobs; assigned-pending jobs need an
  analogous recovery. The fix lives in `AgentJobGrain.TryAdmitAsync`
  (and/or `RunnerGrain.CloseoutLostAsync`) and is a separate
  follow-up — its evidence (`/tmp/opencode/persist3.log`) is
  left in place.

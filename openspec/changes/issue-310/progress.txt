### Codebase patterns confirmed for later tasks

- For a hooks-bearing file that only calls React Query, the `model/` placement is fine (precedent: `useConfirmOutsideClick` from T-002). The hook returns a typed object; callers destructure with the original mutation names so no rename diff is required in `IssueDetailPage.tsx` body.
- `useMutation` with a `mutationFn` whose return type is generic (e.g. `{ issue: Issue; message: string }`) infers the success type. Declaring `UseMutationResult<TData, Error, TVariables>` with `TData = unknown` is enough to satisfy the page's `.mutate()` / `.error` / `.isPending` consumers without pulling the `Issue` model into the hook module. - When mocking `useMutation` in unit tests, the inner `mutationFn` arrow is created fresh each `useMutation` call — don't try to compare the configured `mutationFn` to the inner API mock by reference. In this iteration I reorganized the page state to put all `useState` declarations first, then the two `useConfirmOutsideClick` calls, then the `useIssueDetailMutations` call, then the query hooks, then the early returns. This keeps every hook in a stable order.
- `deleteCommentMutation.onError` originally did `err instanceof Error ? err.message : 'Failed to delete comment'`. The hook mirrors that fallback by normalising non-Error values inside `onDeleteCommentError` — the test pins both branches.
- The `start` mutation's `onError` is the only one that performs cache invalidation (when the error message contains `"waiting for"`). It's preserved inside the hook so no behavior change leaks out.

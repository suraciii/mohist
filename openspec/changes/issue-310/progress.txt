### Codebase patterns confirmed for later tasks

- React 19 + `useRef<T>(null)` types as `RefObject<T | null>`. To match a `RefObject<T>` signature verbatim, `useRef<T | null>(null)` and `return ref as React.RefObject<T>` works (strict-mode safe; the runtime value really is `T | null` but the consumer never reads it before the panel renders).
- tsconfig enables `noUnusedLocals`. A "shared" `let` binding that one render path writes to and test code reads in `act()` needs a local `const` copy inside the helper (TS will not narrow `let`s across functions).
- The hook is purely behavioral (no JSX, no testid), so its move does not touch the density test's structural query — confirmed by rerunning the full issue-detail suite (5 files / 75 tests green).

### Gotchas

- Vitest's `// @vitest-environment jsdom` is needed because the hook attaches a real DOM listener.
- `vi.spyOn(document, 'addEventListener'|'removeEventListener')` survives the hook's effect cleanup without interfering with the fake timer, so the listener-removal test stays deterministic (no wall clock).

## T-003 — centralize the 13 mutations into useIssueDetailMutations hook

Lifted all 13 `useMutation` definitions out of `IssueDetailPage.tsx` into `pages/issue-detail/model/useIssueDetailMutations.ts`. The hook is the single owner of query-invalidation; mutations that also reset local UI state (forceStop, stop, addComment, deleteComment) take optional `onSuccess`/`onError` callbacks so the page (or any future consumer) wires the local reset.

New files:
- `pages/issue-detail/model/useIssueDetailMutations.ts` (182 lines) — 13 mutations + typed `IssueDetailMutations` return.
- `pages/issue-detail/model/useIssueDetailMutations.test.ts` (16 specs, 27 ms) — pins the 13 `useMutation` registrations, mutationFn arg shapes, and exact `invalidateQueries` targets per the original page; covers the optional callbacks (incl. fallback to `'Failed to delete comment'` when the error is not an `Error` instance) and that hooks tolerate `projectId: undefined`.

Page changes:
- `IssueDetailPage.tsx`: dropped `useMutation` / `useQueryClient` imports and all 13 inline mutation definitions; `queryClient` local removed. Imports `useIssueDetailMutations` and destructures all 13 mutations. Local resets (forceStop / stop / addComment / deleteComment) moved into a 5-line callbacks block. State lifted up: `stopConfirming`, `deletingCommentId`, `deleteCommentError` now declared at the top with the other `useState`s (so the hook call sits between the state declarations and the `useIssue` query, keeping hook order stable). Removed imports for `startIssue`, `updateIssue`, `addPrerequisite`, `removePrerequisite`, `closeIssue`, `forceStopIssue`, `stopIssue`, `reopenIssue`, `resumeIssue`, `retryIssue`, `rerunIssue`, `addComment`, `deleteComment`, `extractAttachmentIds`. ### Codebase patterns confirmed for later tasks

- For a hooks-bearing file that only calls React Query, the `model/` placement is fine (precedent: `useConfirmOutsideClick` from T-002). The hook returns a typed object; callers destructure with the original mutation names so no rename diff is required in `IssueDetailPage.tsx` body.
- `useMutation` with a `mutationFn` whose return type is generic (e.g. `{ issue: Issue; message: string }`) infers the success type. Declaring `UseMutationResult<TData, Error, TVariables>` with `TData = unknown` is enough to satisfy the page's `.mutate()` / `.error` / `.isPending` consumers without pulling the `Issue` model into the hook module. The actual concrete return types are documented in the test file.
- When mocking `useMutation` in unit tests, the inner `mutationFn` arrow is created fresh each `useMutation` call — don't try to compare the configured `mutationFn` to the inner API mock by reference. Instead, call the configured `mutationFn` and observe which inner API mock receives the call. The test uses `findMutationByApiCall` / `findMutationByApiCallWithArg` helpers for this.

### Gotchas

- The hook call must happen *before* the conditional `if (isError) return …` early return. In this iteration I reorganized the page state to put all `useState` declarations first, then the two `useConfirmOutsideClick` calls, then the `useIssueDetailMutations` call, then the query hooks, then the early returns. This keeps every hook in a stable order.
- `deleteCommentMutation.onError` originally did `err instanceof Error ? err.message : 'Failed to delete comment'`. The hook mirrors that fallback by normalising non-Error values inside `onDeleteCommentError` — the test pins both branches.
- The `start` mutation's `onError` is the only one that performs cache invalidation (when the error message contains `"waiting for"`). It's preserved inside the hook so no behavior change leaks out.

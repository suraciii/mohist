### Codebase patterns confirmed for later tasks

- React 19 + `useRef<T>(null)` types as `RefObject<T | null>`. To match a `RefObject<T>` signature verbatim, `useRef<T | null>(null)` and `return ref as React.RefObject<T>` works (strict-mode safe; the runtime value really is `T | null` but the consumer never reads it before the panel renders).
- tsconfig enables `noUnusedLocals`. A "shared" `let` binding that one render path writes to and test code reads in `act()` needs a local `const` copy inside the helper (TS will not narrow `let`s across functions).
- The hook is purely behavioral (no JSX, no testid), so its move does not touch the density test's structural query — confirmed by rerunning the full issue-detail suite (5 files / 75 tests green).

### Gotchas

- Vitest's `// @vitest-environment jsdom` is needed because the hook attaches a real DOM listener.
- `vi.spyOn(document, 'addEventListener'|'removeEventListener')` survives the hook's effect cleanup without interfering with the fake timer, so the listener-removal test stays deterministic (no wall clock).

## T-003 — centralize the 13 mutations into useIssueDetailMutations hook

Lifted all 13 `useMutation` definitions out of `IssueDetailPage.tsx` into `pages/issue-detail/model/useIssueDetailMutations.ts`. The hook is the single owner of query-invalidation; mutations that also reset local UI state (forceStop, stop, addComment, deleteComment) take optional `onSuccess`/`onError` callbacks so the page (or any future consumer) wires the local reset.

New files:
- `pages/issue-detail/model/useIssueDetailMutations.ts` (182 lines) — 13 mutations + typed `IssueDetailMutations` return.
- `pages/issue-detail/model/useIssueDetailMutations.test.ts` (16 specs, 27 ms) — pins the 13 `useMutation` registrations, mutationFn arg shapes, and exact `invalidateQueries` targets per the original page; covers the optional callbacks (incl. fallback to `'Failed to delete comment'` when the error is not an `Error` instance) and that hooks tolerate `projectId: undefined`.

Page changes:
- `IssueDetailPage.tsx`: dropped `useMutation` / `useQueryClient` imports and all 13 inline mutation definitions; `queryClient` local removed. Imports `useIssueDetailMutations` and destructures all 13 mutations. Local resets (forceStop / stop / addComment / deleteComment) moved into a 5-line callbacks block. State lifted up: `stopConfirming`, `deletingCommentId`, `deleteCommentError` now declared at the top with the other `useState`s (so the hook call sits between the state declarations and the `useIssue` query, keeping hook order stable). Removed imports for `startIssue`, `updateIssue`, `addPrerequisite`, `removePrerequisite`, `closeIssue`, `forceStopIssue`, `stopIssue`, `reopenIssue`, `resumeIssue`, `retryIssue`, `rerunIssue`, `addComment`, `deleteComment`, `extractAttachmentIds`. Kept `commentAttachmentContentPath` and `issueAttachmentContentPath` because they are still used in the page's `MarkdownReader.resolveAttachment` closures (per design D6).
- Page line count: 1173 → 1087 (−86 lines; 1375 → 1087 cumulative since the proposal baseline, −288 lines / −20.9%).
- `rg 'useMutation|useQueryClient' packages/web/src/pages/issue-detail/ui/IssueDetailPage.tsx`: 0 matches.

### Codebase patterns confirmed for later tasks

- For a hooks-bearing file that only calls React Query, the `model/` placement is fine (precedent: `useConfirmOutsideClick` from T-002). The hook returns a typed object; callers destructure with the original mutation names so no rename diff is required in `IssueDetailPage.tsx` body.
- `useMutation` with a `mutationFn` whose return type is generic (e.g. `{ issue: Issue; message: string }`) infers the success type. Declaring `UseMutationResult<TData, Error, TVariables>` with `TData = unknown` is enough to satisfy the page's `.mutate()` / `.error` / `.isPending` consumers without pulling the `Issue` model into the hook module. The actual concrete return types are documented in the test file.
- When mocking `useMutation` in unit tests, the inner `mutationFn` arrow is created fresh each `useMutation` call — don't try to compare the configured `mutationFn` to the inner API mock by reference. Instead, call the configured `mutationFn` and observe which inner API mock receives the call. The test uses `findMutationByApiCall` / `findMutationByApiCallWithArg` helpers for this.

### Gotchas

- The hook call must happen *before* the conditional `if (isError) return …` early return. In this iteration I reorganized the page state to put all `useState` declarations first, then the two `useConfirmOutsideClick` calls, then the `useIssueDetailMutations` call, then the query hooks, then the early returns. This keeps every hook in a stable order.
- `deleteCommentMutation.onError` originally did `err instanceof Error ? err.message : 'Failed to delete comment'`. The hook mirrors that fallback by normalising non-Error values inside `onDeleteCommentError` — the test pins both branches.
- The `start` mutation's `onError` is the only one that performs cache invalidation (when the error message contains `"waiting for"`). It's preserved inside the hook so no behavior change leaks out.

### Codebase patterns confirmed for later tasks

- D3's pure-derivation + thin-renderer split works exactly as predicted: the page's two-line `actionsState` computation is the only place that "knows" the rules; the card has no conditionals beyond `&&` / `?` over the description fields. Future cards (Details / Drift / Configuration / Prerequisites / Readiness) can use the same shape (`<Card>` over a small pure description in `model/`).
- The `mutations` prop of `<IssueActionsCard>` uses `Pick<IssueDetailMutations, ...>` over the 9 mutations it consumes (start, markReady, close, forceStop, stop, reopen, resume, retry, rerun). Cards that need a different subset just import the named subset — no need to take the full `IssueDetailMutations`.
- React-Query's `UseMutationResult` already returns `Error | null` for the `error` field, so the actions state machine's `ErrorMessages` type can use the built-in `Error` type without leaning on React-Query at all. The card extracts `.message` at the render site; the pure function only sees `Error | null`.
- `useConfirmOutsideClick` lives at `model/`, but a card that is the **only** consumer of its refs (this card) is the right place to call the hook. The page is now free of click-outside knowledge entirely (`rg 'addEventListener.*mousedown|panelRef|useConfirmOutsideClick' packages/web/src/pages/issue-detail/ui/IssueDetailPage.tsx`: 0 matches).
- The `useEffect` test-environment helper for jsdom is needed only when the test attaches to real DOM listeners; `actionsState.test.ts` is pure logic, so it does not declare `// @vitest-environment jsdom` and runs in the default `node` env.

### Gotchas

- The IIFE at the original L1170 wraps `canRetry / canResume / canRerun / canInspect / isInterrupted / showProjectedCheckRepair` and only renders when `!isArchived && (health === Blocked || health === Interrupted)`. The new `blockedActions.isInterrupted` field is therefore gated by the same outer condition; otherwise an Active-health issue with `recoveryAttemptState === 'interrupted'` would render the orange "interrupted" banner, which the original code did not. A test pins this (the "hides every blocked action when health is Active" case seeds an interrupted recovery on an Active issue and asserts `isInterrupted: false`).
- The "ready" start variant now carries `runnerMessage` (was `agentStatus?.runnerMessage ?? 'No runner is connected. …'` inline at the call site) so the card can render the original message verbatim without re-deriving it.
- The page's `actionsState` computation must happen *after* the early returns (so `issue` is non-null) but *before* the rest of the page body — the derivation needs the full `Issue` object. Placed it next to the other post-early-return derivations (`isBacklog`, `isArchived`, `workflowStage`, `prDeliveryMetadata`).

# issue-237 working memory

## Codebase Patterns

- `packages/runner/src/actions/publish-via-pr.ts` is the canonical home for `mergeOrConfirmPr` (also consumed by `packages/runner/src/actions/pull-request.ts` via `mergePullRequestAction`).
- `PublishViaPrFailureKind` is re-exported as `PullRequestErrorCode` (`publish-via-pr.ts` is the source of truth). New failure kinds must be added to `PublishViaPrFailureKind` first; the type alias flows through automatically.
- Existing `mergePullRequestAction` (`pull-request.ts:172`) calls `mergeOrConfirmPr` (publish-via-pr.ts:328); both share the same step-recording callback. Any new step recorded inside `mergeOrConfirmPr` is automatically surfaced in the `steps[]` of the split action output.
- `gh pr checks --json bucket,name,state` is the gh-supported JSON output for PR checks. gh rolls per-check `state` (SUCCESS/FAILURE/PENDING/SKIPPED/CANCELLED/ACTION_REQUIRED) into a coarse `bucket` (`PASS`/`FAIL`/`PENDING`/`SKIP`); using `bucket` is sufficient and avoids parsing the full status matrix.
- Test mocking pattern: `installGh` in `pull-request.spec.ts` uses a switch on the full command string; new gh calls require adding a `case` (else default returns `ghFail`).
- Test timing pattern for the polls: `vi.useFakeTimers()` + `await vi.advanceTimersByTimeAsync(15_000)` works for both driving the wait loop and asserting cancellation paths (see `runner-signalr.spec.ts` ProbeLiveness_ReturnsFalse_OnTimeout for the precedent).

## Gotchas

- When adding a new gh call inside `mergeOrConfirmPr`, every existing test that reaches the merge path in both `pull-request.spec.ts` and `publish-via-pr.spec.ts` must grow a matching mock case. The tests' `expect(ghCalls).toEqual([...])` assertions enumerate calls strictly; missing the new mock returns `unexpected gh call` and turns a success-path test into a failure with no obvious diff signal.
- `pull-request.spec.ts` context factory uses `workId: endsWith("create-pull-request") ? "integrate:open-pr.1" : "integrate:merge-pr.1"` — context is reusable for both actions but `prNumber: 42` is hardcoded in test mocks; new tests that use a different PR number need to align the gh command mocks.
- `mergeOrConfirmPr`'s failure paths return `prUrl: view.url ?? null`; the post-merge recheck path returns `confirmed?.url ?? view.url ?? null`. Split-action callers (`mergePullRequestAction`) prefer `merged.prUrl ?? resolvedPr.prUrl`, so consumers that want the URL after `pr-checks-failed` should fall back to the pre-merge `view.url`.
- `signal.aborted` short-circuits the next iteration of the wait loop *before* the next `gh pr checks` call — the abort path is observable in tests by asserting `ghCalls` lacks the merge call, not the checks call.

## Decisions

- Decision: `pr-checks-failed` returns `prUrl: view.url ?? null` (the PR URL captured at the initial state inspection). Re-using `view.url` keeps the failure output self-contained without a second `gh pr view` round-trip.
- Decision: `PR_CHECKS_POLL_INTERVAL_MS = 15_000` is a private constant in `publish-via-pr.ts` (no profile parameter, no env override) per the design Open Questions note ("max-wait 上限本期不做").
- Decision: cancel-while-waiting returns `retry-safe` (not `pr-checks-failed`). The signal is the runner's task signal — a transient cancellation, not a check-state outcome; the action reports `pr-checks-failed` only when `gh pr checks` actually saw a failed bucket.
- Decision: classify `FAIL` bucket as the single failure source. gh groups `FAILURE` / `CANCELLED` / `ACTION_REQUIRED` per-check states into the `FAIL` bucket already; treating only `FAIL` is both spec-faithful ("failed/cancelled/action_required") and avoids parsing individual states.
- Decision: empty `gh pr checks` JSON output is treated as "no checks reported, proceed to merge." This preserves the existing default behavior for repos that don't run checks (e.g. ad-hoc branches) and matches the spec scenario "全部 PASS/SKIP（或无 checks 报告）."

## T-001 Server task contract: Expect field, YAML parsing, legacy validation, and dispatch

### Codebase patterns discovered

- Workflow task definition surfaces in three places (definition, persistence, grain call):
  - `TaskDefinition` record in `WorkflowDefinition.cs` (5 fields: `With, Artifacts, SetVars, Recovery` — added `Expect`).
  - `TaskRun` class in `TaskRun.cs` carries runtime `WithInput` (added `ExpectInput`). Orleans serialization uses `GenerateSerializer` so no surrogate needed for the class (Orleans handles records / classes via attribute).
  - `WorkflowTaskWork` and `WorkItem` Orleans-serialized records (or task-variant only). WorkItem now carries `[property: Id(11)] Dictionary<string, JsonElement?>? Expect`.
- Tasks are stored on `TaskRun.WithInput` and `TaskRun.ExpectInput` — both `Dictionary<string, JsonElement?>?`.
- Approval feedback task was previously a reduced `FeedbackTaskConfig` (id/title/uses/with) — promoted to full `TaskDefinition` so feedback tasks can carry `expect/artifacts/setVars/recovery`.
- `WorkflowYamlSerializer` `With` is a `Dictionary<string, object?>` (yaml nodes, post-Normalize). `JsonElementMap` is the bridge into the `JsonElement` shape used everywhere else.
- `mohist/github-pr-status` defines its own `expect` input that is **Action-owned**, not Workflow completion policy — must not be caught by the legacy validation.
- The runner-side `WorkDispatch` envelope serializes every contract field as a JSON string (`With`, `Variables`, `Artifacts`, `SetVars`, `Recovery`). Orleans `[property: Id(N)]` slots are sequential; new fields extend the list.
- `TaskRunExtensions.ExtractRequiredFiles` previously took a `withInput` and dived into `withInput["expect"]`. Now it takes the `expect` dict directly (`Dictionary<string, JsonElement?>`).

### Gotchas

- `WorkItem` uses `[property: Id(N)]`; consuming code reads via `Item.Expect`. `[property: Id]` slots must be sequential and unique; `TaskDispatch.Expect` lives at Id(18), `WorkItem.Expect` at Id(11).
- `OptionalMap` (in `WorkflowYamlSerializer`) calls `Map(...)` which throws on non-dict values. Detection of `with.expect` must not route through `OptionalMap` because the value's structure is unknown until inspected; use `withMap.TryGetValue(key, out var value)` and normalize the value lazily.
- The verdict-marker rule (reject `<promise>PASS</promise>` inside marker `contains`) now applies to **task-level `expect`**, not `with.expect`. It applies to all tasks regardless of `uses`. Action-owned `with.expect: merged` on `mohist/github-pr-status` is a string value, not a marker structure, so it doesn't trip the rule.
- Tests that previously asserted `task.With["expect"]["files"]` must read `task.Expect["files"]` after the split. Several test files needed updates.
- Removing the deep-merge branch is a behavior flip: tests that asserted `vars.agent` keys overlaid a literal `with.agent` object now need a literal `with.options` (or `options: ${{ vars.agent }}`) for binding.
- The legacy-shape rejection (`with.expect`, `with.agent`) rejects `mohist/acp-agent` and `mohist/opencode` tasks. Built-in profile YAMLs (loaded as Lazy) had to migrate so the `MohistWorkflow.Definition` getter doesn't throw for every spec run.

### Patterns established

- Action-aware legacy validation lives in `WorkflowYamlSerializer.ValidateTaskExpectations(taskId, uses, withMap)`. Two triggers: `with.expect` containing completion-policy shapes (`files`/`markers`/`failIf`) and `with.agent` presence. Error message names the task id and directs the author to the replacement.
- `WorkflowItemTranslator.BuildTaskDispatchAsync` now expands both `with` and `expect` via `WorkflowProfileManager.ExpandTaskWith` (whole-value template resolution only) and serializes them into `WorkDispatch` (`With` slot for Action input, new `Expect` slot at Id(18) for completion contract).
- `WorkItem.Task` and `ResolveFeedbackTask` accept an `expect` parameter; `BuildDefaultFeedbackTask` always emits `options: ${{ vars.agent }}` so the default feedback task honors explicit model selection.
- `TaskRun.Expect` is a separate field; `ExtractRequiredFiles(expect)` reads it directly; `ToDefinition()` includes it.
- `TaskRun.ToDefinition` and `WorkflowRun.NextWork`/`ActiveTask` propagate `ExpectInput` so dispatch and rendering see the same expectation source.

### Tests touched

- Unit: `TaskRequiredFilesTests`, `ApprovalFeedbackTests`, `WorkflowProjectionTests` now construct `expect` dictionaries directly rather than via `withInput["expect"]`.
- Unit: `WorkflowProjectionTests.WorkflowStatusMapper_MapTasks_FromDefinition` reads required files from `t.Expect`, not `t.With` (the chain was `WorkflowStatusMapper` → `ExtractRequiredFiles(t.With)`).
- Spec: `WorkflowYamlSerializer_PreservesFailIfInTaskExpect` now parses top-level `expect`. `WorkflowProfileManagerSpecs.ExpandTaskWith_DeepMergesObjectKey` replaced by `ExpandTaskWith_ObjectKeyIsLeftVerbatim_NoDeepMerge` and added `ExpandTaskWith_WholeTemplateObjectPlaceholderResolvesToObject` to assert whole-value JSON type preservation.
- Spec: tests using inline `mohist/acp-agent` with `with.agent` / `with.expect` updated to `mohist/opencode` + `options` + top-level `expect`. Built-in profile YAMLs (`mohist-local.workflow.yaml`, `mohist-github-pr.workflow.yaml`) migrated — they're shipped artifacts and tests assert their content.

- Solution build: 0 warnings, 0 errors.
- Server unit tests: 1399 / 1399 passing.
- Server spec tests: 2869 / 2869 passing.
- Server arch tests: 27 / 27 passing.
- CLI tests: 933 / 933 passing.
- Web typecheck: clean.

### Decisions worth flagging for review

- Migrating the built-in profile YAMLs was originally in T-005; T-001 picked them up because the legacy validation rejects `mohist/acp-agent` + `with.expect` shapes and the spec suite cannot survive the rejection at T-001 boundary. Migration is mechanical and matches D9 in `design.md`.
- The verdict-marker rule now applies to top-level `expect`. The rule rejects `<promise>PASS</promise>` etc. inside marker `contains` for all tasks. This matches the spec's intent ("verdict marker requirements belong in a check definition"); a top-level `expect` with verdict markers fails just like `with.expect` did previously.

## T-002 Model config validation and writer convergence

### Codebase patterns discovered

- `IssueModelMetadata.ProviderModelFormat` regex `^[^/\s]+/[^/\s]+$` enforced exactly-one-slash semantics — the model-ID segment rejected further `/` characters. The fix moves to first-slash-split by replacing the model segment with `\S+` (`[^/\s]+/\S+`), which keeps the "non-empty, non-whitespace provider" check but lets the model ID carry any number of `/` segments.
- `MohistIssueWorkflowProfileBase.BuildAgentConfig` was the only server-side code path that **seeded** `vars.agent.type = "opencode"` on every fresh issue. Project/global agent configs set this key too, but those are user-controlled and remain untouched by the change.
- `IssueModelSelector.tsx` writes via four `patchIssueWorkflowDefinitionVar` / `patchIssueWorkflowStageDefinitionVar` calls. The test file mirrors each expected call shape; both files had to drop `type: 'opencode'` so writes only carry model/variant.
- Other code paths (project/global agent config, `IssueVariableBuilder.Build`, runner-side `template.ts`/`openspec.ts` defaults, settings page) still write or consume `type: "opencode"` in fixtures, but they represent persisted state or upstream-runtime tests, not writer surfaces in scope of T-002.

### Gotchas

- Removing the default `type: "opencode"` from `BuildAgentConfig` breaks a single spec test that explicitly asserts on it: `MohistLocalWorkflowProfileSpecs.AgentConfig_MergesGlobalConfigIntoAgentVariable`. The new expectation is "the seeded agent block has no `type` key" — covered by `Assert.False(agent.TryGetProperty("type", out _))`. The spec's broader rule (legacy keys are inert under the options contract) still holds; this is a server-side write change, not a runner-side contract change.
- The new regex `[^/\s]+/\S+` accepts `provider//model` (double slash, with empty segment between them) because `\S+` only forbids whitespace. The spec only requires "non-empty before/after the first `/`", so this is intentionally permissive — openrouter already ships IDs like `openrouter/anthropic/claude-3-opus` and intermediate empty segments are not actionable. The error message remains "expected 'provider/model' format" so the diagnostic surface is unchanged.
- `[^/\s]+/\S+$` correctly rejects the cases the spec lists (`model-only`, `/model`, `provider/`, `provider/ `, `with space/inside`, `inside/with space`, `/`). `provider/ ` (trailing whitespace) is new — old regex allowed it because `[^/\s]+` was the model ID and the trailing space wasn't matched; new regex anchors `\S+$` and rejects it.
- `MohistIssueWorkflowProfileBase` does not write the profile-default model; the project's `IssueWorkflowProfile` API path also routes through `BuildAgentConfig` for fresh variable bundles. Tests in `IssueWorkflowProfileStorageIntegritySpecs` and `IssueWorkflowProfileManagerSpecs` set `type = "opencode"` in user fixtures, not via the profile default — those tests remain valid.

### Patterns established

- Model-ID validation now lives entirely in `ValidateModel`, with one shared regex. Both top-level `Validate` and per-stage `Validate` call the same helper, so the multi-slash acceptance is automatically applied to per-stage selectors — verified by a new spec assertion `Validate_AcceptsMultiSlashModelInTopLevelAndStageSelectors` and a sibling rejection `Validate_RejectsInvalidMultiSlashStageModelFormat`.
- `BuildAgentConfig` starts from an empty `Dictionary<string, object?>` and only merges the optional `globalAgentConfig`. The merge remains set-replace on `agent` (preserves non-overlapping keys), so legacy `type: "opencode"` already persisted in user config still rides through unchanged — only the default seeding goes away.
- Issue model-selector writes now use the canonical model/variant-only shape `{ model, variant }`. No other keys are added; clearing patches still emit `{ model: null, variant: null }` for idempotent delete semantics.

### Tests touched

- Unit: `IssueModelMetadataTests.ValidateModel_AcceptsProviderSlashModelFormat` extended with `openrouter/vendor/family/model` and `openai/org/team/model-name`. `ValidateModel_RejectsNonProviderSlashModelFormat` adds `model-only`, `/model`, `provider/ ` to lock the spec scenarios.
- Unit: two new `Validate_AcceptsMultiSlashModelInTopLevelAndStageSelectors` and `Validate_RejectsInvalidMultiSlashStageModelFormat` facts confirm per-stage multi-slash acceptance.
- Spec: `MohistLocalWorkflowProfileSpecs.AgentConfig_MergesGlobalConfigIntoAgentVariable` no longer asserts `agent.type == "opencode"`; uses `TryGetProperty` to confirm the seeded agent has no `type` key.
- Web: `IssueModelSelector.test.tsx` — 7 assertions across both describe blocks had `type: 'opencode'` removed from the expected `patchIssueWorkflowDefinitionVar` / `patchIssueWorkflowStageDefinitionVar` argument shape.

## T-003 Runner completion evaluator, output projection, and dispatch contract

### Codebase patterns discovered

- `ActionResult.turnFact` (private channel) lives on the *internal* `ActionResult` type only. The runner MUST strip it before any `WorkItemResult` field reaches the server. The strip is centralized at `stripRunnerPrivateFacts` so the Action cannot leak final assistant text via `output`, `setVars`, `capturedOutputs`, artifacts, recovery matching, or the wire report.
- `evaluateCompletion(expect, workDir, finalAssistantText)` is the new Workflow-owned completion evaluator. It takes the *rendered* `expect` object directly — the executor passes the dispatch's `RenderedWorkItem.expect` after template expansion. It does NOT receive `ActionContext` or read `with.expect`.
- The Action↔executor boundary changed: `verifyExpectations(context, agentText)` is gone. `expectations.ts` now exports `evaluateCompletion`, `CompletionEvaluation`, `FailIfMatch`, and `parseLastMarker(text, accepted)` — no Action-context-aware API.
- `parseLastMarker` is *generalized*: it accepts arbitrary `<promise>VALUE</promise>` markers with `VALUE`s drawn from the marker's `oneOf`/`contains` list (no longer hardcoded `done|unfinished`). The marker precedence rules are asymmetric: file markers use first-in-declaration-order; `_output` markers use last-accepted-occurrence in text.
- `_output` markers are unsatisfied when `finalAssistantText` is null — the executor never falls back to Action Output as a text source (spec scenario "The turn fact is unavailable").
- Output projection lives in the executor (`projectTaskOutput`). For `mohist/opencode` (the one Action in `PROMISE_PROJECTED_ACTIONS`), the handler's output is dropped. If a promise marker matched, output becomes `{ "promise": "<value>" }`; otherwise `null`. Every other Action's output is preserved unchanged.
- Branch-stability evidence attachment is bypassed for opencode so the minimal `null | { promise }` contract is preserved on the wire (no `branchStability` key leaks into the opencode output JSON).
- Successful Action + unsatisfied completion → failed completion with diagnostic `message`. Action failure (regardless of completion) stays an Action failure; completion does not rescue Action failures.
- `tryRecovery` copies `work.expect` (alongside `with`/`recovery`/`recoveryRemaining`) into the self-retry `AddTaskInput`. The decoupled contract now survives the round-trip.

### Gotchas

- `expectations.ts` keeps `resolveActionPath(workDir, value)` exported for non-completion callers (`core/artifact-exists`, `core/marker`, `mohist/openspec-tasks`, `mohist/archive-change`). The signature changed from `(context, value)` to `(workDir, value)` and required updating 3 callsites.
- `acp-agent.ts` no longer reads `with.expect`, no longer emits `output.expectation/promise/failIfMarker`, and no longer triggers expectation repair. The Action sets `turnFact.finalAssistantText` from the agent's transcript text. The text NEVER becomes Action Output.
- `acp/session-strategies.ts` still exports no implicit repair turn logic. Removed: `satisfyExpectations`, `expectationRepairLimit`, `buildExpectationRepairPrompt`, `appendAgentText`, and the `expectation` field on `AcpSessionResult`. Three test cases that locked the legacy Action-private verifyExpectations behavior were rewritten to lock the new contract.
- The executor's whole-string-unresolved check now reports unresolved references in BOTH `with` and `expect`. This catches `${{ openspecChangeDir }}` in `expect.markers.*.path` before the Action is invoked, with the existing actionable error message.
- `template.ts` `LITERAL_FIELD_PATHS` was extended with `markers.*.contains` and `markers.*.oneOf.*` (in addition to the existing `expect.markers.*.contains` and `expect.markers.*.oneOf.*`). The `expect.*` variants remain for legacy callers that render the `with.expect` shape; the unprefixed versions cover the new contract rendering `expect` standalone.
- The `executor-completion` test fixture uses `{} as never` for `sessionManager` and `acpConnection` because the completion path never reaches them. The `silentConnection()` helper is cast to `ServerConnection` (instead of `Pick`) so the executor constructor accepts it directly.
- `RenderedWorkItem.expect` is parsed at the connection boundary via `parseObject(dispatch.expect)` — the same path `with`/`recovery` take — so absent vs empty-string vs JSON-stringified expectations are decoded uniformly.
- ActionContext does not gain an `expect` field. The Action never receives the completion contract; it's read only by the executor's completion evaluator.

### Patterns established

- The completion evaluator is called between `action(...)` return and `tryRecovery(...)`:
  ```
  render with → render expect → Action → stripRunnerPrivateFacts
    → evaluateCompletion(renderedExpect, workDir, finalAssistantText)
    → projectTaskOutput(work, publicActionResult, completion)
    → normalize(work, projected)
    → tryRecovery(work, normalized)
    → branch-stability (non-opencode path only) → worktree → artifacts → setVars
  ```
- `stripRunnerPrivateFacts(ActionResult)` returns `{ publicActionResult, turnFact }` and is the canonical boundary. Callers that previously passed `result` downstream now pass `publicActionResult`. `turnFact` is consumed only by completion evaluation.
- `projectTaskOutput` is the single place that decides what the wire `output` is. It is the only place that knows about `mohist/opencode`'s projection rule.
- All completion tests live in `tests/expectations.spec.ts` (function-level) and `tests/executor-completion.spec.ts` (executor-flow). Connection-layer expectation parsing is locked in `tests/server-connection-report.spec.ts`.
- Template literal-field-path coverage is asserted for the standalone-`expect` rendering in `tests/template.spec.ts` so the rule survives future refactors.

### Tests touched

- **NEW**: `tests/executor-completion.spec.ts` (16 tests) — locks the executor's step ordering, output projection (opencode and non-opencode paths), `_output` private fact channel, self-retry `expect` copy, failIf-match + recovery interaction, and `turnFact` privacy.
- **NEW**: `tests/server-connection-report.spec.ts` `parses expect from the dispatch response into RenderedWorkItem.expect` — locks the `expect` JSON-string parse and the `expect: null` for absent dispatch fields.
- **NEW**: `tests/template.spec.ts` `LiteralFieldPath_StandaloneExpectRoot_ProtectsMarkersContainsAndOneOfEntries` — locks the bare-rooted literal field paths for `markers.*.contains` and `markers.*.oneOf.*`.
- **UPDATED**: `tests/expectations.spec.ts` — full rewrite (32 tests) using the new `evaluateCompletion(expect, workDir, finalAssistantText)` API + new `parseLastMarker` tests (returns last-accepted, ignores non-accepted trailing values, returns null for empty/empty-list).
- **UPDATED**: `tests/acp/session-strategies-expectations-and-liveness.spec.ts` — replaced three Action-private-expect tests with `DoesNotPerformExpectationRepair_WhenExpectationUnmet` proving the Action ignores `with.expect` (the legacy shape) and the action output no longer carries `expectation`/`promise`/`failIfMarker` fields.

### Decisions worth flagging for review

- The Action private `verifyExpectations(context, agentText)` API was deleted entirely (not deprecated). Some session-strategies call sites that imported it were also deleted. The Action's `acp-agent.ts` handler now returns the run's `text` as `turnFact.finalAssistantText` and trusts the executor to interpret completion. If future Actions need Action-private verification (we don't expect this), they can re-introduce the function with a non-`ActionContext` API.
- The branch-stability-evidence attachment (`attachBranchStabilityEvidence`) is now skipped for `mohist/opencode` only. This protects the minimal `null | { promise }` output contract (no `branchStability` key in the opencode output). Other Actions still get the evidence attachment in their wire output because their output contract tolerates it. This trade-off is narrow and reversible once a separate diagnostics channel exists.
- `RenderedWorkItem.expect` is rendered (`renderTemplate`) before completion evaluation, mirroring `with`. This catches `${{ openspecChangeDir }}`-style references in `expect.markers.*.path`. The same whole-string-unresolved guard fires if the marker path is missing a variable; the error message names the task id and the unresolved reference.

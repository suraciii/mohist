## 2026-03-27T00:38:00Z - T-004: Implement WorkflowEngine with multi-worker execution

**What was done:**
- Created `src/workflow/engine.ts` with `WorkflowEngine` class
- Added `findAndClaim()` to `TaskRepo`: atomic SQL `UPDATE ... RETURNING` with `NOT EXISTS` subquery enforcing same-Issue single-task constraint at DB level (D12)
- Added `findRunningByIssue(issueId)` to `TaskRepo` for killAgentByIssueId reverse lookup (D13)
- Implemented N-worker polling loop: each worker independently calls `findAndClaim()`, executes `StageHandler`, handles success/failure
- On task success: marks task completed, checks issue still active, advances stage, creates next task only if next stage is agent stage (not user approval or terminal)
- On task failure: marks task failed, marks issue blocked (unless task already failed by killAgentByIssueId — idempotent check)
- `killAgentByIssueId(issueId)`: reverse lookup via `issueTaskMap`, checks task still running, marks failed with 'user_paused', kills agent process
- `stop(timeoutMs)`: sets running=false, awaits workers with timeout, force-kills agents on timeout, marks remaining running tasks as failed
- Worktree registry: `Map<issueId, worktreePath>` with `registerWorktree/unregisterWorktree/getWorktreePath`
- Recovery on startup: iterates all projects, calls `WorktreeManager.list()`, maps issueId→worktreePath
- Exposed `getActiveWorkerCount()` and `getPendingTaskCount()` for status API

**Learnings:**
- better-sqlite3's `stmt.get()` supports `UPDATE ... RETURNING` (confirmed by design notes) — used `db.get()` not `db.run()`
- killAgentByIssueId must check task.status === 'running' before updating to avoid race with worker marking task completed
- Worker's finally block handles idempotent cleanup of issueTaskMap entry (safe if already deleted by killAgentByIssueId)
- The engine doesn't create tasks after user-approval stages — the approve API route handles that via StateManager.createTask()

**Verification:** Build passes (tsc), 172/173 tests pass (1 pre-existing skip)

**Learnings:**

- `remove()` needs `--force` flag on `git worktree remove` to handle dirty worktrees
- Graceful error handling in `remove()` — missing worktree/branch should not throw since cleanup may be retried
- `git worktree list --porcelain` is more reliable than parsing the default human-readable format

## Design choices for T-002

- **Signature** for `enforceCleanWorktree`: 8 positional params per spec + Decision 5: `(work, workDir, result, renderedWith, variables, signal, cleanupAction, contextParts)`. `cleanupAction` is the `CleanupAgentAction` (mutable binding) and `contextParts` is a `{ sessionManager, acpConnection, connection }` record (the three dependencies needed to build `baseContext`).
- **`cleanupAgentAction` value is exported** from `worktree-enforcement.ts` (live ESM binding). The executor imports the value and passes it as the `cleanupAction` parameter, so tests setting the stub see the same value. This avoids exporting the `let` directly (re-exports are forbidden per Decision 3) while still letting the executor read the current value at call time.
- **`WorktreeProbeError` sinking** (Decision 2): `enforceCleanWorktree` wraps its body in `try { ... } catch (error) { if (error instanceof WorktreeProbeError) return worktreeProbeFailure(work, error); throw error }`. `readWorktreeSnapshot` is the only throw source in that try block (verified — `readCurrentBranch` folds errors into `CurrentBranchResult.error`). executor's outer catch now just `return failure(work, errorMessage(error))`.
- **`baseContext` duplication**: Decision 5 says `worktree-enforcement.ts` must not reverse-import executor. The simplest path is for the module to own its own `baseContext` builder using `ContextParts`. It's a small duplication of ~20 lines — kept to avoid a circular import.
- **`safeParseJson` / `errorMessage` keep living in executor.ts**: per Open Questions, executor's `tryRecovery` still uses `safeParseJson`, and `executeOne` outer catch still uses `errorMessage`. Both are 6-line helpers — kept private to each module's natural consumer.
- **`isNotFoundError` migrated** to worktree-enforcement.ts (only used by the moved `recoverStaleIndexLock`).

## Why

The runner's workflow executor (`packages/runner/src/runtime/executor.ts`, ~1106 lines) is — alongside the ACP adapter — the most complex file in the runner package, bundling eight execution concerns (git-based branch/worktree invariants, post-side-effects, failure recovery, workspace resolution, checks fan-out) into one module. Every adjustment to work-item scheduling, cleanup, or fault-tolerance strategy forces edits inside this giant file, and changes to one stage routinely bleed into unrelated stages. The git-probe-based invariants alone account for ~half the lines and nearly all the complexity (multi-branch decision trees, bounded cleanup loops, stale-index-lock recovery state machine). Splitting the executor along its concern boundaries is the highest-impact, lowest-risk move toward the epic's complexity-hotspot goal: behavior is fully preserved and guarded by the existing per-concern executor tests.

## What Changes

- **Extract branch-stability invariant → `packages/runner/src/runtime/branch-stability.ts`** (~180 lines): stateless functions `checkBranchStability` / `readCurrentBranch` / `expectedWorkspaceBranch` / `branchInvariantViolationFailure` / `attachBranchStabilityEvidence` / `branchStabilityToJson`, plus types `BranchStabilityEvidence` / `BranchInvariantViolationEvidence` / `CurrentBranchResult`. Input `(work, workDir, expectedBranch, boundary, signal)` → ok+evidence or violation+failure.
- **Extract worktree-cleanliness invariant → `packages/runner/src/runtime/worktree-enforcement.ts`** (~320 lines): `enforceCleanWorktree` / `runAgentCleanupAttempt` / `readWorktreeSnapshot` / `recoverStaleIndexLock` / `defaultLockHolderProbe` / `resolveStaleIndexLockMs` / `dirtyWorktreeFailure` / `gitIndexLockFailure` / `formatDirtyWorktreeSummary` / `worktreeProbeFailure` / `parseFileList`, types `DirtyWorktreeEvidence` / `GitIndexLockRecovery` / `WorktreeProbeError`, and constant `DEFAULT_STALE_INDEX_LOCK_MS`. Input `(work, workDir, result, renderedWith, variables, signal, cleanupAction, contextParts)`.
- **Shared git-probe injection point**: the single `git` runner used by both invariant modules is extracted as a shared injectable helper; `setExecutorGitRunnerForTest`, `setCleanupAgentActionForTest`, and `setExecutorLockHolderProbeForTest` migrate to the modules that own their concerns. The existing mutable-let injection pattern is preserved (location only changes).
- **Executor converges to orchestration entry** (~350 lines): `WorkExecutor.execute` / `executeOne` / `executeChecks`, workspace resolution (`prepareWorkspace` / `workspaceFromVariables` / `workspaceRoot` / `resolveWorkDir`), post-side-effect orchestration (`captureAndUploadArtifacts` / `applySetVars` / `captureDeclaredOutputs` — thin layers over the already-extracted `artifact-capture.ts` / `set-vars.ts` / `output-capture.ts`), task-failure recovery (`tryRecovery` / `matchesWhen` / `readRecoveryConfig` / `readAddTasks` / `decrementRecoveryBudget` — retained, no independent spec today), and `normalize` / `failure` / `baseContext` / `toCheckStatus` / `isCheck` / `resolveWorkspacePath` / `formatUnresolvedError` / `formatCheckUnresolvedError` / `workspaceSetupFailure` helpers. `executeOne` becomes a clean linear pipeline where each invariant is a single function call.
- **`worktree-cleanup.ts` stays separate**: the existing pure-data module (prompt construction + config reads + `WorktreeSnapshot`) does no I/O and is not merged; `worktree-enforcement.ts` imports it.
- **BREAKING**: none. Execution semantics, scheduling rules, fault-tolerance/retry behavior, and the runner↔server work-distribution contract are fully preserved. No new execution stages or work-item types.

## Capabilities

### New Capabilities
- `runner-executor-structure`: Governs the internal module structure of the runner workflow executor as a contract-bearing surface — the branch-stability invariant and the worktree-cleanliness invariant (including the bounded agent cleanup loop and stale-index-lock recovery) SHALL live in dedicated single-responsibility modules that the executor delegates to rather than inlines; the executor entry SHALL focus on orchestration and stage sequencing; the shared git-probe injection point and the test-injection stubs (`setExecutorGitRunnerForTest`, `setCleanupAgentActionForTest`, `setExecutorLockHolderProbeForTest`) SHALL migrate to their owning modules while preserving the mutable-let injection pattern; execution/fault-tolerance/scheduling behavior SHALL be unchanged with all existing per-concern executor tests passing unmodified; and each extracted module SHALL drop out of the runner package's cyclomatic-complexity (scc) front ranks. Mirrors the precedent set by `cli-module-structure`.

### Modified Capabilities
- _(none — this is a behavior-preserving refactor. `workflow-failure-recovery` (the `tryRecovery` path is retained in the executor, location-only), `runner-workspace-cleanup` (workspace lifecycle/registry, unrelated to per-task worktree-cleanliness enforcement), `workspace-prepare` (the prepare action), and `workflow-work-item-protocol` (the runner↔server contract) all keep their existing requirements unchanged.)_

## Impact

- **Runner runtime** (`packages/runner/src/runtime/`): `executor.ts` shrinks from ~1106 to ~350 lines; two new modules `branch-stability.ts` (~180) and `worktree-enforcement.ts` (~320) added, plus the shared git-probe helper. No change to `acp-connection.ts`, `acp-command.ts`, `artifact-capture.ts`, `set-vars.ts`, `output-capture.ts`, `worktree-cleanup.ts`, `cleanup-loop.ts`, or `workspace.ts`.
- **Test injection surface**: `setExecutorGitRunnerForTest`, `setCleanupAgentActionForTest`, `setExecutorLockHolderProbeForTest` change import paths; existing executor specs (branch-stability, worktree-cleanliness, artifact, workspace-boundary, checks verdict) pass unchanged after updating injection entry points.
- **No external impact**: no changes to `packages/server`, `packages/web`, `packages/cli`, the HTTP API, persisted data, the runner↔server protocol, or any CLI command. No new dependencies; no migration.
- **Verification**: per-concern executor specs pass without weakening; `scc` shows `executor.ts` and the two new modules each out of the runner package's complexity top ranks; recovery path (`tryRecovery` failure → `completed`+`addTasks`, budget decrement, retry-self expansion) behaves identically.

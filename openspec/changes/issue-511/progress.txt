## T-001 — WorkflowGrain dead path + backdoor + typed exception

### Codebase Patterns
- `Mohist.Server.SpecTests/Support/GrainTestContext.cs` builds a manual-grain context pair via `DispatchProxy.Create<IGrainContext, GrainContextProxy>` and `<IGrainRuntime, GrainRuntimeProxy>`. The runtime proxy's `get_GrainFactory` returned `null` by default. Extending it to return a configurable `IGrainFactory` (added a `Create(key, IGrainFactory?)` overload and a settable `GrainFactory` on the proxy) was the cleanest way to drop `BindProfileForTest` without breaking the manual-grain wiring — no other specs needed to change.
- `IWorkflowProfileReferenceCoordinatorGrain` has three methods on its interface (`SetProjectDefaultAsync`, `BindWorkflowRunAsync`, `DeleteProfileAsync`). The stub coordinator grain only implements `BindWorkflowRunAsync` (the one `WorkflowGrain.PersistProfileBindingAsync` calls) and throws `NotSupportedException` for the other two — they are unreachable from the spec's code path.
- `WorkflowGrain.EnsureStartedAsync` has an outer `try { ... } catch { RemoveUncommittedRunAsync(); throw; }`. This outer catch ALSO catches the typed resolution exception after the inner CommitAsync catch persists the failed state — the failed state is then deleted. This is the pre-existing behavior; the spec confirms the exception still propagates with the original message text.
- `Mohist.Server.SpecTests` banned symbols (`BannedSymbols.Tests.txt`) forbid `System.IO.File`, `Path.GetFullPath`, `AppContext.BaseDirectory`, `Task.Yield`, etc. Source-scanning tests belong in `Mohist.Server.ArchTests` (which embeds `ServerSources/**/*.cs` as resources and allows reading them via `assembly.GetManifestResourceStream`). Spec tests must use stub fakes / in-memory stores.
- ArchTest embedded resource names follow `ServerSources/{RelativePath}` (e.g. `ServerSources/Workflow/Grains/WorkflowGrain.cs`). MSBuild's `RecursiveDir` strips the `src/Mohist.Server/` segment, so resource names do NOT include `Mohist.Server/` in the prefix — verify with `assembly.GetManifestResourceNames()` if uncertain.
- The `WorkflowRunProfileBindingTests` already asserts `run.FailDefinitionResolution("Workflow 'run-1' has no definition for stage 'implement'")` directly — it doesn't go through the manager's throw, so it didn't need updating when the throw type changed.

### Decisions / Gotchas
- `WorkflowDefinitionResolutionException` lives in `Mohist.Server.Workflow.Domain` (same namespace as `WorkflowControlRejectionException` and `WorkflowProfileDomainErrors`). It exposes a `ResolutionReason` enum (`NoCurrentDefinition`, `NoStageDefinition`); one enum + one exception is enough — design rejected separate subtypes per reason.
- The three WorkflowProfileManager throw sites (`LoadTemplateAsync:71`, `LoadStageSpecsAsync:154`, `LoadBoundTemplateAsync:440`) all carry the original message text verbatim so the user-facing error surface is byte-identical.
- `WorkflowGrain.CommitAsync` is now `(IReadOnlyList<WorkflowEvent> events, CancellationToken ct = default)`. Two callers used `CommitAsync(events, reason)` — both updated to drop the `reason` argument.
- `WorkflowGrain.PersistProfileBindingAsync` lost the inline `BindProfileForTest` branch; the inline `GrainFactory.GetGrain<IWorkflowProfileReferenceCoordinatorGrain>(...)` is the only path now.
- `WorkflowStageSpecs.LoadStageSpecsAsync_ThrowsWhenStageMissing` previously expected `InvalidOperationException`. It now asserts `WorkflowDefinitionResolutionException` and checks `Reason == NoStageDefinition` plus message substring. Single test, single-line change.

### Test Strategy
- **Static checks** live in `Mohist.Server.ArchTests/WorkflowGrainContractRules.cs` (8 tests):
  - `DispatchEvent` absent in `IWorkflowGrainContext`, `WorkflowGrain`, `WorkflowWorkLifecycle`
  - `On(WorkflowEvent` / `private Task On(` / `WorkflowArtifactRecorded =>` absent from `WorkflowGrain`
  - `BindProfileForTest` absent in `WorkflowGrain` + `IWorkflowGrainContext`
  - `CommitAsync` body has no `.Message.Contains(`
  - `WorkflowProfileManager` has ≥3 `throw new WorkflowDefinitionResolutionException(` sites
  - `CommitAsync` catches `WorkflowDefinitionResolutionException` (typed) and does NOT catch `InvalidOperationException`
- **Behavioral check** lives in `Mohist.Server.SpecTests/Specs/Workflow/Grain/WorkflowGrainProductionContractSpecs.cs`:
  - `CommitAsync_DifferentResolutionExceptionMessages_ProduceIdenticalControlFlow` — drives `WorkflowGrain.EnsureStartedAsync` with a stub `IWorkflowProfileProvider` that returns a valid definition for the startup call but throws `WorkflowDefinitionResolutionException` with a configurable message on the stage-spec call; asserts both runs throw the typed exception with their respective messages.
  - `WorkflowDefinitionResolutionException_CarriesReasonDiscriminator_AndPreservesMessage` — sanity check the type's surface.

## T-002 — rename WorkflowRunProfileManager to WorkflowRunVariablesStore + inline ResolveLayeredVariablesAsync

### Codebase Patterns
- The `Manager` vs `Store` distinction lives in `design/conventions.md:34-35` (`Manager` = config or lifecycle policy; `Store` = persistence boundary for one shape). `WorkflowRunProfileManager` was a `Manager`-named class doing `Store` work; renaming to `WorkflowRunVariablesStore` aligns with the role suffix rule.
- `IScopedService` is the DI marker that drives auto-registration — no manual `Add...` call exists for the store; renaming the class wires through transparently.
- The local-variable name `_runProfileManager` appears in two production call sites (`WorkflowGrain.cs:29`, `WorkflowProfileManager.cs:34`) and is uniformly renamed to `_runVariablesStore` together with the type; same for ctor parameter `runProfileManager` → `runVariablesStore`.
- `WorkflowRunProfileRow` / `WorkflowRunProfiles` references survive the rename — they are the deliberately-retained misnomer (per design D2) and the type's top-of-file comment points readers at the design/decision note.
- `WorkflowProfileManager.ResolveLayeredVariablesAsync` was an `internal async` pass-through that only delegated to `ResolveConfiguredVariablesAsync`; only its sibling `ResolveEffectiveVariableBundleAsync` called it, so the inline is a one-site change. The 7 spec call sites in `WorkflowVariableResolution(Specs|DefaultsSpecs).cs` were switched in bulk via `sed`. The method changed visibility from `private` to `internal` so the spec tests can hit it directly without re-exposing through `ResolveEffectiveVariablesAsync`.

### Decisions / Gotchas
- The 7 spec call site count comes out exactly as T-002 promised: `WorkflowVariableResolutionSpecs.cs` 5 + `WorkflowVariableResolutionDefaultsSpecs.cs` 2 = 7.
- `ResolveConfiguredVariablesAsync(runId)` returns the same `VariableBundle` shape that `ResolveLayeredVariablesAsync` did (the wrapper just returned its result unchanged) — no behavior change. The existing variable-resolution specs (`EffectiveVariables_*`, scope/stage precedence, ETag race) all stay green without test changes.
- The `Bump ETag`/clear-defaults behavior of `MutateVariablesAsync` (the ETag read-modify-write) is unchanged by the rename — only the surrounding type name and local variables shifted.
- Archives under `openspec/changes/archive/2026-06-24-issue-226/review.md`, `.../2026-07-22-issue-474/{design,progress}.md`, `.../2026-07-23-issue-478/{design,proposal,tasks.json}.md` retain the old name verbatim — they describe prior-issue decisions and are not in the "production, tests, registration, configuration" surface the spec scenario constrains; they are historical record.
- The `openspec/changes/issue-511/*` files (the active change plan — proposal/design/specs/tasks/progress) keep the old name to describe what is being renamed; the rename is a one-shot rename, not a retroactive doc rewrite.

### Test Strategy
- No new tests added — the rename is observably equivalent to the original (JSON shape, ETag concurrency, explicit-vs-default precedence), so the existing variable-resolution spec tests are the verification contract. They went from 7 calls of `ResolveLayeredVariablesAsync` to 7 calls of `ResolveConfiguredVariablesAsync` and continue passing unchanged.
- `RerunFromStageSpecs.cs:121` local variable `runProfile` renamed to `runVariablesStore` for consistency with the type name; same for `WorkflowGrainProductionContractSpecs.cs:112` (`runProfileManager` → `runVariablesStore`) and `WorkflowItemTranslatorSpecs.cs:41`.
- The deliberate-keep decision is checked at the file-level comment on `WorkflowRunProfileRow.cs` and the design note at `design/workflow/variables.md#workflowrunprofile-rowname-historical-misnomer` — no new ArchTest needed (the table name is not a structural contract; it is a documentation contract that future renames must observe when the table is restructured for a real reason).

## T-001 — WorkflowGrain dead path + backdoor + typed exception

### Codebase Patterns
- `Mohist.Server.SpecTests/Support/GrainTestContext.cs` builds a manual-grain context pair via `DispatchProxy.Create<IGrainContext, GrainContextProxy>` and `<IGrainRuntime, GrainRuntimeProxy>`. The runtime proxy's `get_GrainFactory` returned `null` by default. Extending it to return a configurable `IGrainFactory` (added a `Create(key, IGrainFactory?)` overload and a settable `GrainFactory` on the proxy) was the cleanest way to drop `BindProfileForTest` without breaking the manual-grain wiring — no other specs needed to change.
- `IWorkflowProfileReferenceCoordinatorGrain` has three methods on its interface (`SetProjectDefaultAsync`, `BindWorkflowRunAsync`, `DeleteProfileAsync`). The stub coordinator grain only implements `BindWorkflowRunAsync` (the one `WorkflowGrain.PersistProfileBindingAsync` calls) and throws `NotSupportedException` for the other two — they are unreachable from the spec's code path.
- `WorkflowGrain.EnsureStartedAsync` has an outer `try { ... } catch { RemoveUncommittedRunAsync(); throw; }`. This outer catch ALSO catches the typed resolution exception after the inner CommitAsync catch persists the failed state — the failed state is then deleted. This is the pre-existing behavior; the spec confirms the exception still propagates with the original message text.
- `Mohist.Server.SpecTests` banned symbols (`BannedSymbols.Tests.txt`) forbid `System.IO.File`, `Path.GetFullPath`, `AppContext.BaseDirectory`, `Task.Yield`, etc. Source-scanning tests belong in `Mohist.Server.ArchTests` (which embeds `ServerSources/**/*.cs` as resources and allows reading them via `assembly.GetManifestResourceStream`). MSBuild's `RecursiveDir` strips the `src/Mohist.Server/` segment, so resource names do NOT include `Mohist.Server/` in the prefix — verify with `assembly.GetManifestResourceNames()` if uncertain.
- The `WorkflowRunProfileBindingTests` already asserts `run.FailDefinitionResolution("Workflow 'run-1' has no definition for stage 'implement'")` directly — it doesn't go through the manager's throw, so it didn't need updating when the throw type changed.

## T-003 — typed per-enum wire mapping + FrontendStatus → WireStatus + web union comments

### Codebase Patterns
- The four consuming enums live in three adjacent files under `packages/server/src/Mohist.Server/Workflow/Domain/Run/`: `WorkflowRun.cs` (WorkflowRunStatus), `StageRun.cs` (StageRunStatus), `StageCheck.cs` (StageCheckStatus), `TaskRun.cs` (TaskRunStatus). They share the `Mohist.Server.Workflow.Domain.Run` namespace, which `WorkflowStatusMapper.cs` already imports.
- `WorkflowStatusMapper` had a single `FrontendStatus(string raw)` method that special-cased `"AwaitingApproval"` and `ToLowerInvariant()`'d everything else. The 4 call sites passed `*.Status.ToString()` from each enum — the canonical "stringly-typed" anti-pattern.
- The existing `WorkflowStatusMapperFrontendStatusTests.cs` test class mixed symbol-targeted unit tests for `FrontendStatus` (string form) with view-projection tests (`BuildStatusView_*`, `BuildPendingWork_*`). The view-projection tests exercise the new typed mapper under the hood without needing changes — they only read the wire string out of the view.
- Web unions live in `packages/web/src/entities/issue/model/`: `workflow-run.ts` (WorkflowRunStatus, WorkflowStageRunStatus), `stage-state.ts` (StageTaskStatus, StageCheckStatus, StageStateStatus), `recovery.ts` (WorkItemAttemptState, WorkflowRecoverySummary). `WorkflowRunStatusPill.tsx` is the only consumer that uses a union as a `Record<...>` key — TypeScript's exhaustiveness check would have failed if `WorkflowRunStatus` lost a value, but here we only added a member to `WorkflowStageRunStatus` which is NOT used as a `Record<>` key anywhere.

### Decisions / Gotchas
- Each `WireStatus(Enum)` switch has an explicit arm per enum value plus a defensive `_ => throw new SwitchExpressionException(...)` arm. The throw arm is **defense-in-depth**: C# switch expressions over enums are NOT exhaustiveness-checked by default, and the per-enum `Enum.GetValues` spec test is the hard guarantee (the throw arm only fires if a runtime value reaches the mapper without a corresponding arm — e.g. via reflection or future reflection-injected values).
- The 4 call sites were mechanical: `FrontendStatus(s.Status.ToString())` → `WireStatus(s.Status)`, etc. The four sites are exactly at `WorkflowStatusMapper.cs:72` (stage), `:100` (run), `:142` (task), `:188` (check).
- `SwitchExpressionException` lives in `System.Runtime.CompilerServices` (BCL since net5). One `using` added at the top of `WorkflowStatusMapper.cs` covers all four entries.
- Web `WorkflowStageRunStatus` already contained `passed`/`skipped` as client-only projections; adding `completed` is purely additive. The existing union members remain in their original order with `completed` slotted in alphabetically among the server-emitted values (after `awaiting-approval`, before `passed`) so the server-emitted and client-only clusters remain readable.
- Web union comments are JSDoc/`/** ... */` (not `//` single-line) so they appear in hoverdocs in editors that surface TypeScript doc comments. They follow the project's product+domain language convention (server enum reference is the domain-language pointer).
- The `Mohist.Server.SpecTests` `BannedSymbols.Tests.txt` keeps blocking reflection patterns and filesystem access, so the per-enum exhaustiveness test had to live in `Mohist.Server.UnitTests` (pure logic, no infra) — no test cluster or DB needed.

### Test Strategy
- **Per-enum Enum.GetValues spec**: four `[Theory]`s driven by `MemberData` (one per enum) assert each enum value's wire mapping matches an `ExpectedWireFor(string)` helper that mirrors the production rule (`AwaitingApproval → awaiting-approval`; `char.ToLowerInvariant(enumName[0]) + enumName[1..]` for everything else). Adding a new enum value without an arm makes the test fail because the new value's wire would not equal `ExpectedWireFor(newValue.ToString())`.
- **Per-enum distinctness spec**: four `[Fact]`s assert the number of distinct wire values produced equals the number of enum values — i.e. no two enum values share a wire token (catches future mistakes like mapping both `Pending` and `Pending*` to `pending`).
- **Discard / `ToLowerInvariant` absence spec**: an `[Fact]` that asserts each enum has one distinct wire value per value, but goes one step further — if anyone reintroduces a discard fallback that returns the same wire value for every unmapped input, distinctness would collapse and the test would catch it.
- **Wire-shape spec**: asserts every emitted wire token is `ToLowerInvariant` invariant, contains no space, and only contains lowercase letters or `-`. Catches accidental upper-case regressions or `_`-leaks.
- **`AwaitingApproval` per-enum specific spec**: two `[Fact]`s assert the kebab-case form for `WorkflowRunStatus.AwaitingApproval` and `StageRunStatus.AwaitingApproval` (the two enums where `AwaitingApproval` exists).
- **Existing `BuildStatusView_*` and `BuildPendingWork_*` tests retained**: they exercise `WireStatus` via the `WorkflowStatusView` projection and continue passing without modification, giving us a second-order behavioral check that the view-model wire strings are unchanged.
- **No ArchTest needed**: the per-enum Enum.GetValues spec test is sufficient for exhaustiveness (one static scan vs one per-enum dynamic check); adding a Roslyn-based ArchTest would duplicate the guarantee.

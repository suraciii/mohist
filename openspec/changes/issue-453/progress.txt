# T-001 — Consolidate issue status and decision context

## Codebase Patterns

- `RuntimeDecision` (widgets/issue-workflow/model) is authoritative for workflow summary / actions; the
  page now adds a separate, page-owned `IssueDecisionContext` for the composite-parent path.
  The composite-parent case is intentionally issue-only: no fabricated workflow stage, current task,
  or workflow action.
- `StatusHeadline` is sticky; it remains the single runtime-summary statement. The previous
  duplicate `runtime-status-pill` in the header identity row is removed. No replacement badge.
- `IssueDetailsCard` no longer renders Issue Stage or Workflow Stage rows. Parent/child, project,
  repository name, base branch, and Git URL are unchanged.
- Two paused meanings: `approval-required` says "approval decision is pending"; interrupted/manual
  stop says "Execution stopped manually. Resume or rerun to continue." They are mutually exclusive
  in copy.

## Decisions

- Add `deriveIssueOnlyStatus` in `pages/issue-detail/model/issueDecisionContext.ts` (pure function).
  Inputs: status, health, isDraft, isArchived, childSummary. Returns { label, headline, rationale,
  nextAction } without any DOM/mutation concerns.
- Add `IssueOnlyStatusHeadline` in `pages/issue-detail/ui/`. Reuses the same `data-testid="status-headline"`
  anchor and `data-tier-weight="status-header"` sticky placement so existing tier tests still pass.
  Uses `data-summary="issue-only"`.
- `StatusHeadline` for workflow-capable issues: drop the separate `status-headline-current-task` pill.
  The headline text from `deriveRuntimeDecision` already embeds the current task for running /
  approval-required / blocked / failed (e.g. "Task running: X", "Approval pending on X"). Add
  `data-has-current-task` attribute for tests; keep the sticky + summary + stage progress + headline.
- `pills.tsx` no longer exports `RuntimeSummaryPill`. The component was the only consumer of the
  header identity row's runtime pill; that row is gone.
- Update `IssueDetailPage.tsx` to:
  - Use `IssueOnlyStatusHeadline` when `isCompositeParent`, else the existing `StatusHeadline`.
  - Drop the `RuntimeSummaryPill` render and the `status-badges-runtime` group.
  - Stop passing `workflowStage: null` overrides to `IssueDetailsCard` (the type no longer
    includes that field).

## Gotchas

- `RuntimeSummaryPill` removal: `IssueDetailPage.test.tsx`, `IssueDetailPage.status-header.test.tsx`,
  `IssueDetailPage.archived.test.tsx` and the cross-tier tests all referenced
  `status-badges-runtime` / `runtime-status-pill`. They are updated to assert the headline is the
  sole summary carrier and the page-wide count of runtime-status-pill nodes is 0.
- `IssueDetailsCardIssue` type lost `workflowStage`. `IssueDetailPage.tsx` no longer needs to strip
  it; tests that passed `workflowStage: 'build'` into the card must no longer assert the row
  shows (the row itself is gone, see `tests/IssueDetailPage.spec.tsx`).
- `runtime-presentations.ts` approval-pause rationale: "The workflow is paused and waiting for your
  review." -> "The workflow is paused while an approval decision is pending." The next-action copy
  is now "An approval decision is needed to continue" instead of "Review and approve to continue".
- `runtime-presentations.ts` blocked/interrupted rationale: "The workflow was interrupted. Resume or
  rerun to continue." -> "Execution stopped manually. Resume or rerun to continue." The
  interrupted health path test in `IssueDetailPage.control-workspace.active.spec.tsx` was updated to
  assert stop/recovery language and absence of approval language.
- Headline "Approval required on X" -> "Approval pending on X" (matching the rationale copy).
- Backlog / queued path: the headline for `queued` is "Waiting to start (workflow)" when no stage.
  The new `StatusHeadline` keeps the same sticky section, the same `data-testid="status-headline"`,
  and does not fabricate a stage / progress / current task when none exist (existing cross-tier
  test still asserts null for those three nodes when stage progress is null).

# T-002 — Deliver the unified responsive issue decision surface

## Codebase Patterns

- `RuntimeDecision` continues to be authoritative for workflow actions (approve / send-back /
  retry / resume / rerun / stop / start). The page-owned `deriveIssueDecisionActions` (under
  `pages/issue-detail/model/`) composes the optional runtime decision with current Issue facts to
  produce one ordered, pure `IssueDecisionAction[]` plus a primary fallback. The controller
  `useIssueDecisionActionController` owns dispatch, pending/error, recoverable vs terminal Stop,
  Stop confirmation, and send-back validation; `MobileActionBar` and `IssueDecisionSurface` both
  consume it. `MobileActionBar` no longer duplicates mutation dispatch or pending lookup.
- Composite parents with no runtime decision get only their applicable lifecycle / delegation
  descriptors (mark-ready / close / ask-agent / view-transcript) from the page-owned model. The
  rail `Actions` card is removed; `IssueActionsCard` is deleted along with its tests; the
  workflow view is mounted `readOnly` and contains no `InlineApprovalControls` mutation path.
- `IssueDecisionSurface` renders the desktop surface, rationale, next-action text, stop
  confirmation, and send-back form. `MobileActionBar` renders the launcher + sheet for narrow
  viewports; the launcher is independently enabled so a disabled primary action never hides
  enabled secondary actions or their reasons. Disabled destructive buttons use neutral muted
  styling instead of the live destructive variant. Both renderers use `aria-describedby` for
  disabled reasons and `aria-live="polite"` for pending mutations.

## Decisions

- Allow `close` for composite parents (matches the existing `IssueActionsCard.showClose` rule
  that excluded only health != active and an agent running on this issue; do not exclude parents).
  Composite parents still do not get `mark-as-done` (the previous behavior). Mark-ready continues
  to require `isDraft` and a non-archived, non-terminal issue.
- Workflow actions continue to be copied from `RuntimeDecision`; they are not emitted when the
  decision is null (e.g. composite parents, archived, terminal, no workflow run). When the
  decision exists, only the kinds covered by the existing lifecycle are copied (approve,
  send-back, retry, resume, rerun, stop, start); no new lifecycle actions are introduced.
- `IssueDecisionAction` carries `enabled`, `reason`, `primary`, `destructive`, `mode`, `to`,
  `order`, and `pendingLabel`. It does NOT carry mutation objects or callbacks — dispatch lives
  in `useIssueDecisionActionController`. Navigation actions (ask-agent, view-transcript) carry
  the `to` route computed through `useProjectPath()`.
- `selectTranscriptSession` selects an active (active / running / probing) session before any
  other; on ties, prefer the most recently started session, then the most recently created
  session, and break remaining ties with `sessionName.localeCompare`. Ask Agent is independent
  of session presence.
- `MobileActionBar` renders the sheet launcher independently of primary enabled state. The sheet
  preserves focus trapping via `ConfirmationDrawer`, Escape / close button, focus restoration
  through the dialog unmount, send-back textarea, Stop confirmation, `safe-area-inset-bottom`
  clearance, and non-overlapping page padding (`pb-[calc(8rem+env(safe-area-inset-bottom))]`
  when the bar is mounted).

## Gotchas

- Initial `deriveIssueDecisionActions` accidentally excluded composite parents from `close`; the
  test asserting the old behavior was updated to assert the new behavior, matching the existing
  `IssueActionsCard.showClose` predicate.
- `IssueDetailPage.control-workspace.spec.tsx` originally imported `mockIssueCommits` and
  `mockIssueDiff` without using them; the imports were removed to satisfy `no-unused-imports`
  and `npm run typecheck`.
- `tests/IssueDetailPage.spec.tsx` had a `findRailCard(name: 'Configuration')` whose `name` was
  unused; renamed to `_name` so the test boundary linter is satisfied without changing behavior.
- Three test files (`IssueDetailPage.composite-parent-decision-surface.test.tsx`,
  `IssueDetailPage.control-workspace.spec.tsx`, `IssueDetailPage.drift-recovery.spec.tsx`) used
  `Object.defineProperty(window, 'innerWidth', ...)` to set the viewport; the `check:test-boundaries`
  linter rejects this. Switched to `setScopedValue(window, 'innerWidth', ...)` from
  `tests/support/scoped-property.ts`.
- `scripts/node-test-file-budget-baseline.json` had a 558-line allowance for
  `IssueDetailPage.narrow-action-bar.test.tsx`; the file is now 473 lines, so the allowance was
  removed.
- The composite-parent desktop test originally clicked the launcher with `.click()`, which
  triggered a React `act` warning because the click handler scheduled a state update outside
  `act`. Replaced with `fireEvent.click(launcher)`.

## Codebase Patterns

- Event-store per-context-table convention: each bounded context gets its own
  CloudEvent envelope table (WorkflowRunEvents / IssueEvents / EpicEvents)
  sharing the same column set keyed by (Source, Id) with an
  IX_{Table}_Type_Source_Id secondary index. The unified Events table was
  tried and reverted in migration `20260610130306_DropEventsTable`.
- C# 14 `public union` types (e.g. `EpicEvent`) compile to a wrapping class.
  `someUnion.GetType().Name` returns the union name, not the inner variant
  name. Always unwrap via the typed switch in the serializer (`Unwrap`).
- `EpicGrain` already injects `TimeProvider`; epic event envelopes source
  `time` from `Now()` (a deliberate divergence from `IssueGrain` which uses
  `DateTimeOffset.UtcNow`). The spec is `fake TimeProvider` → fixed instant
  preserved in the persisted envelope.
- The `EpicGrain` post-mutation flow is capture pending events → save
  `EpicRow` → post-commit best-effort append through `IEventStore`,
  mirroring `IssueGrain.PublishIssueEventsAsync`. `ApplyPendingEvents` is
  gone; the helper `DrainPendingEvents` only returns the snapshot to the
  grain which then forwards to `PersistEpicEventsAsync`.
- Test support: `RecordingEventStore` and `NoopEventStore` are the standard
  fakes; the `RecordingEventStore` source filter keys on `/mohist/epics/{id}`
  for `ListEpicEventsAsync`.
- The grain's `GrainKeyForTest` lets tests pin the epic id (e.g.
  `"project_1:epic_1"`), but `CreateAsync` still generates a fresh
  `epic_{guid}` id internally — the recorded CloudEvent source is the
  generated id, not the test key. Tests that exercise `CreateAsync` must
  read the id from the returned `EpicDto`.

## T-001 notes

- Foundation: T-002 (EpicReopened + reopen recording), T-003 (batch
  link/unlink recording), and T-005 (timeline read path) all build on the
  store + persistence wired here.
- T-001 only registers the 7 existing `EpicEvent` variants in
  `EventCatalog` / `EpicEventSerializer`; `EpicReopened` is intentionally
  deferred to T-002 to avoid dead serializer code paths.
- Tests seed an open (backlog) linked issue before Start / Pause / Resume
  sequences so the post-Resume `ReconcileAfterTerminalInternalAsync` path
  does not auto-mark the epic done before the next mutation under test
  (that would emit an unexpected extra `EpicStatusChanged` and break
  ordering / set-status-as-closed assumptions).
- The `EpicEventSerializer` test asserts the storage `Type` surface
  matches the variant's CLR name (e.g. `EpicCreated`), not the union
  container name `EpicEvent`. The serializer unwraps via `Unwrap(payload)
  .GetType().Name` so the on-disk `Type` column matches the variant.

## T-002 notes

- Foundation: T-002 introduces the `Epic.Reopen(now)` domain transition
  (Done/Closed → Idle) guarded by a new `EpicNotTerminalException`,
  mirroring `Issue.Reopen` / `IssueReopened`. The variant
  `EpicReopened` is now added to the `EpicEvent` union, the
  `EpicEventSerializer.BusType` switch, and the `EventCatalog.All`
  inventory (deferred from T-001 by design).
- `EnsureNotTerminal` is left untouched — `Reopen` is the single, explicit
  exit from terminal states. Start/Pause/Resume/Done/Close still throw
  `EpicAlreadyTerminalException` from terminal epics (regression covered
  by `EpicTransitionsSpecs.EnsureNotTerminal_StillBlocksOtherTransitionsAfterReopenAdded`
  and `EpicReopenSpecs.ReopenAsync_EnsureNotTerminalStillBlocksOtherTransitionsAfter`).
- Grain re-claim pattern: `EpicGrain.ReopenAsync` materializes the aggregate,
  applies `domain.Reopen`, persists the EpicRow state change FIRST (one
  `SaveChangesAsync`), then loops over the link rows and inserts
  `EpicActiveIssueRow` per issue. Each insert is its own
  `SaveChangesAsync` so a duplicate-key race (concurrent active-membership
  claim) surfaces as a per-issue skip rather than rolling back the
  re-claim. `GetActiveMembershipOwnerAsync` is the same precheck
  `LinkIssueAsync` uses, so re-homed issues are silently skipped — the
  link record stays, the issue is not re-claimed, and reopen does not
  fail.
- Web surface: `primaryLifecycleAction` now returns `{ kind: 'reopen-epic' }`
  for `Done`/`Closed` (was `null`); the detail page renders a Reopen
  control (`data-testid="reopen-epic-trigger"`) only for terminal epics;
  `useReopenEpic` invalidates `['epics']`, the project-scoped detail key,
  and `['issues']` (re-claimed issues surface via `EpicQuerier`).
- HTTP route: `POST /api/projects/{projectRef}/epics/{id}/reopen` returns
  200 on terminal epics, 409 `EPIC_NOT_TERMINAL` on non-terminal epics,
  404 on missing — accepts internal id or number, consistent with the
  other epic routes.
- Tests cover: domain transition (`EpicTransitionsSpecs`), grain
  re-claim incl. re-homed skip (`EpicReopenSpecs`), event publishing
  (EpicReopened + EpicStatusChanged, fake TimeProvider preserved in
  envelope time), serializer/catalog coverage of the new variant,
  HTTP integration (`EpicLifecycleSpecs`), web primary action branch,
  web Reopen control rendering + mutation, and the query invalidation
  (`useReopenEpic`).

## T-003 notes

- Batch link/unlink introduces a typed `BatchMembershipOutcome`
  (`linked` | `already-linked` | `conflict(owningEpicId,title)` |
  `not-found` | `unlinked` | `was-not-a-member`) — Orleans-serializable
  via `[GenerateSerializer]`, returned in the HTTP body wrapped as
  `{ results: [...] }`.
- Grain entry points `IEpicGrain.LinkIssuesAsync` /
  `UnlinkIssuesAsync` take a resolved list
  (`BatchMembershipRequestItem = { Identifier, IssueId, IssueNumber }`).
  The HTTP route resolves each identifier by exact internal-id match
  or by issue-number string match (the same pattern the single-issue
  link/unlink endpoints use today) **before** calling the grain, so
  the grain never receives an unresolvable identifier and the cross-
  aggregate invariant operates on the canonical internal id.
- Two layers of de-dup, by design:
  - HTTP layer dedupes identical *identifier strings* (the
    caller-supplied token) so a request like `["5", "5"]` produces
    one outcome. Two distinct identifier strings that resolve to the
    same issue (`["5", "issue_xxx"]`) produce two outcomes (one per
    requested identifier).
  - Grain dedupes by canonical `IssueId` so the issue is linked at
    most once. The second identifier-string variant
    (`["5", "issue_xxx"]`) still produces a second outcome against
    the same linked row — surfaced as `linked` for the first and
    `already-linked` for the second, which is the natural
    per-identifier read.
- Partial-failure semantics: each issue is its own SaveChanges
  scope. A conflicting issue does not roll back the link of
  preceding issues; the dual-write race in `LinkIssueAsync` (caught
  `DbUpdateException` on duplicate active-membership) is mirrored in
  `LinkIssuesAsync` — the concurrent winner is reported as `conflict`
  on that single identifier and processing continues with the
  remaining items.
- Event persistence: `PersistEpicEventsAsync` is called per-issue so
  every successful `EpicIssueLinked` / `EpicIssueUnlinked` envelope
  is written to `EpicEvents` via `IEventStore`. The `time` field is
  the injected `TimeProvider` `Now()` at the moment the grain
  started processing the issue, matching the single-issue path.
- Routes are POST because both endpoints accept a JSON body and
  produce side effects — verbs match the existing
  `/{id}/issues` and `/{id}/issues:batch` style. The `:batch` /
  `:batch-unlink` literal suffices avoid colliding with the existing
  collection route (`POST /{id}/issues`) and the verb-style
  sub-resources (`/done`, `/close`, `/start`) already in use.
- Web surface: `addEpicIssue` / `removeEpicIssue` plus the new
  `batchAddEpicIssues` / `batchRemoveEpicIssues` client methods.
  Reaction mutations stay untouched; the batch client methods are
  pure additions for a future bulk-picker UI.

## T-004 notes

- List query is a **pure addition** — no contract change for
  existing callers. `EpicQuerier.ListAsync` gains `search`, `sortBy`,
  `sortDir` (all optional, default `null`); the route forwards
  `?search=&sort=&dir=` query strings; the route accepts unknown
  values without a 4xx (falls back to the default ordering).
- The ORDER BY clause is selected from a closed map
  `(field, dir)` → fragment string so the sort selector is never
  interpolated into the SQL. Map keys: `priority`/`updated`/`created`
  × `asc`/`desc`. Default fragment preserved byte-for-byte from the
  legacy query (`e."Priority" ASC, e."UpdatedAt" DESC, li."CreatedAt"`)
  — the regression test `ListAsync_OrdersByPriorityThenUpdatedAt`
  still passes unchanged.
- Search uses a bound parameter (`@search`) so the LIKE fragment is
  injection-safe: `LOWER(e."Title") LIKE LOWER('%' || @search || '%')`.
  When the normalized search is null/empty the WHERE clause omits the
  search fragment entirely so the no-params path stays
  byte-identical to the legacy query.
- Sort-field normalization rejects anything that isn't letters/digits
  (`NormalizeSortToken` returns `null` on bad input → fallback to
  default). This guards against query-string `sort=priority'); DROP
  TABLE Epics;--` style payloads. The same is true for the dir value.
- `useEpics({ search?, sort?, dir? })` includes the params in its
  query key (`['epics', projectId, { search, sort, dir }]`) so a
  param change re-fetches without `manual` invalidation. The same
  params are forwarded to the `getEpics` client, which builds a
  `URLSearchParams` to keep the URL minimal (no dangling `?` when no
  params are present).
- Page controls are vanilla HTML `input` + two `select`s in a
  toolbar (`data-testid="epic-list-toolbar"`); the search input
  trims whitespace before forwarding. Status grouping
  (`groupActiveEpics`) operates on the returned (filtered, sorted)
  set — unchanged behavior on top of the new query.
- Tests: `EpicQuerierListAsyncQuerySpecs` (11 unit specs) cover
  byte-identical-no-params SQL, bound-vs-interpolated search,
  sort-by priorities, sort-by updated, search+sort composition,
  unknown-sort fallback, and sort-token sanitization. The
  command-counting helper shares a single in-memory SQLite
  connection between a migration context and a counting logger
  context — same pattern as the existing EpicQuerierListAsyncSpecs.
  `EpicListQueryApiSpecs` (7 integration specs) cover the route
  contract (search filter, sort ordering, default-fallback,
  composition, empty-string fallback). Web tests:
  `EpicListPage.test.tsx` "search and sort controls" describe block
  (11 specs) covers input rendering, search/sort wiring into
  `useEpics`, trimming, fallback on unknown sort values, and
  grouping preservation. `client.test.ts` (6 specs) covers
  query-string serialization (no `?` when no params, search
  forward, sort forward, composition).

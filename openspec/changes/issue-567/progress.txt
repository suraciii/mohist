## MF-1 disposition: FIXED via bounded shutdown-time pending-operation handoff

Channel decision (grounded in live source):

- The CLI is the sole party to `POST /api/runner/{id}/update-interrupt`
  (`RunnerRefreshVerifier.InterruptRunnerAsync`); the Runner never sees that
  response. Confirmed.
- Available channels: SignalR hub invocations (`CancelAgentSession`,
  `SessionCommand` via `RunnerHub`), the `/poll` contract (dispatches only,
  204 when idle), dedicated runner HTTP GETs (`/config`, machine-credential
  auth). None carries update/drain knowledge to the Runner today.
- Chosen: a bounded shutdown-time fetch (e.g.
  `GET /api/runner/{id}/update-operation/pending`) returning the runner's most
  recent not-yet-settled update operation: id, creation time, affected-work
  inventory. Runs only when in-flight work exists; own small budget with brief
  retries (a `full` update restarts the Server before the Runner, so the new
  Server may still be booting); completes before the cooperative stop.
- Why not push-at-fence-creation / poll-field: push can be lost (reconnecting
  runner) and would need a fetch fallback anyway; poll field can be missed
  (204-when-idle, stop can beat next poll) and caches a fact a later unrelated
  restart could act on. The fetch is authoritative at the decision moment,
  distinguishes update-caused vs ordinary restart by construction, and needs
  no new runner-side durability.
- No-operation-known behavior: no receipts, `started` fence stands, honest
  unresolved (same honesty rule as stop-unconfirmed).
- Inventory rule: receipts only for in-flight works the returned operation
  names (stale pending operations from abandoned updates stay safe/noise-free;
  arbitration remains the authority for mismatches).

## T-001 Implementation Notes

- `RunnerUpdateOperationGrain` is keyed by Runner identity and uses the
  existing ADO.NET Orleans default storage. It keeps the latest operation
  history, the stable operation id, injectable creation time, affected-work
  inventory, and per-entry marking status. A pending operation is reused on
  repeat requests; owner marking is retried before the response is returned.
- `/update-interrupt` closes Runner admission first, persists or reuses the
  operation, then calls the owning Workflow/AgentJob grain synchronously. A
  pending retry can repair an operation even after the old Runner is offline.
  `GET /update-operation/pending` is read-only and serializes `operation:null`
  explicitly when no pending operation exists.
- Runner snapshots now carry Workflow task-attempt identity and an
  `IsAgentWork` flag. Ordinary workflow tasks and checks stay out of the
  update inventory; active Agent tasks and AgentJobs are named with owner kind,
  owner id, work id, and task attempt where applicable.
- Workflow uses a new `RecoverablyInterrupted` settlement state and commits
  `AgentTaskUpdateInterrupted` with the operation id. Late execution,
  disconnect, and report paths cannot turn fenced work into `Unknown` or fail
  it through runner-loss closeout.
- AgentJob uses a separate `RecoverablyInterrupted` status, retains its
  original Runner/work identity, and persists an idempotent pending
  `AgentJobUpdateInterrupted` CloudEvent outbox obligation before confirmation.
  Event-store failure leaves the operation retryable; duplicate event ids are
  deduplicated by the existing AgentJob event store.
- Server verification: focused update tests passed (3 tests), and the full
  `Mohist.Server.SpecTests` suite passed (3923 tests, 0 failures).
- `npm run test:fast` passed after installing the existing lockfile dependencies:
  TypeScript checks, Server unit/architecture/workflow/CLI suites, Runner
  vitest (1639 tests), and Web vitest (4724 tests). The install reported 16
  existing npm audit findings; no dependency metadata changed.

## T-003 Implementation Notes

- Extended `WorkResultJournal` in the existing atomic file with the
  `interrupted` state. It stores the complete immutable
  `RuntimeRecoveryReceipt`, reloads it with completed entries, and retires
  either terminal state only after acknowledgement. Started, completed, and
  interrupted transitions reject a second terminal record for the same work.
- Added Runner-owned receipt and pending-operation types. Terminal-result
  fingerprints follow the Server `WorkResult` property order and omit nullable
  and Runner-private fields, while update-interrupted payloads contain only the
  operation id and `stopConfirmed=true`.
- Added a live runtime-turn registry. Workflow and AgentJob execution register
  the physical runtime/session/turn binding only after the Agent turn is
  accepted; RunnerHost uses that binding to call the existing Pi/OpenCode
  confirmed-stop paths. Missing bindings, idle observations, and unconfirmed
  stops cannot manufacture interruption receipts.
- RunnerHost now performs a bounded pending-operation handoff before bounded
  cooperative stop. The fetched operation is the only update context and its
  inventory gates receipt creation. Confirmed stops persist before delivery;
  returned results use the receipt-shaped terminal path when their binding is
  complete, and all receipt deliveries retry the same journal payload until a
  terminal acknowledgement.
- `ServerConnection` now parses the runner-facing pending-operation response
  and sends recovery receipts, treating HTTP 409/retryable acknowledgements as
  delivery failures. Added deterministic journal, receipt, handoff, and
  delivery contract tests.
- Verification so far: Runner typecheck and test typecheck pass; the full
  Runner vitest suite passes (153 files, 1647 tests). The pending-operation
  handoff retries timed-out or failed queries within its fixed budget, while a
  successful empty response ends the handoff without creating update context.

## T-004 Implementation Notes

- Workflow interruption arbitration now commits an immutable `Interrupted`
  TaskRun history entry beside one pending replacement attempt. The
  replacement receives `RecoveryGeneration + 1`, a deterministic new work
  delivery identity, and a distinct logical AgentTurn identity; the first
  complete physical Session binding may replace that placeholder, after which
  the binding is frozen normally.
- `WorkflowWorkLifecycle` owns replacement work allocation and claim handling.
  Preallocated recovery work ids are translated and claimed as normal
  dispatches, while the old work id remains in history and is never returned
  by active-work reconciliation. The replacement makes the run `Ready` and
  is the only pending task eligible for dispatch.
- A matching interruption receipt is recorded in the Workflow receipt ledger,
  committed with the task replacement, and only then marks the Runner update
  operation work `Settled` and returns an accepted terminal acknowledgement.
  Acknowledgement replay returns the stored acknowledgement and repairs a
  partially updated operation ledger without allocating another attempt.
- Late reports, observations, and receipts using the original TaskRun/work/
  turn binding are stale after replacement; the original settlement object is
  not mutated. Replacement settlement cleanup leaves `HasUnresolvedAgentResult`
  false after the new result is accepted.
- Added Server spec coverage for fence/no-fence and mismatch rejection,
  replacement creation, commit-before-ack observable ordering, duplicate
  idempotence, frozen original binding, stale old-turn ingress, one eligible
  replacement dispatch, and replacement settlement.

## T-005 Implementation Notes

- `/recovery-receipt` now routes receipts with `ownerKind=agent-job` and
  `agentJobId` to `AgentJobGrain`; the existing workflow receipt wire shape
  remains compatible when the owner discriminator is absent. Runner receipt
  construction now emits the owner identity for AgentJob dispatches, whose
  workflow/task ids are intentionally empty.
- AgentJob arbitration validates the exact Runner/work/session/turn/runtime
  binding and the durable update-operation inventory. Applied receipt ids and

## T-006 Implementation Notes

- A Runner restart can retain a `started` journal fence without an in-memory
  execution promise. `WorkResultJournal.started()` now exposes those entries,
  and `RunnerHost.pollReport()` includes their work keys in `inFlight`, so
  Server reconciliation suppresses redelivery while the journal continues to
  refuse physical replay. Completed/interrupted journal entries keep their
  existing awaiting-ack replay path.
- Update-interrupted Workflow settlements are unresolved for dispatch and
  reconciliation purposes before a receipt arrives. They receive the normal
  injectable settlement deadline and reminder; a missing receipt reaches the
  existing `agent-result-unconfirmed` blocked projection instead of remaining
  recoverably interrupted indefinitely. The original attempt remains fenced.
- AgentJob update fences now persist an `UpdateInterruptionDeadlineAt`, retain
  the recovery reminder after interruption-event delivery, and enter the
  explicit `Interrupted` terminal state with `agent-result-unconfirmed` when
  the receipt deadline expires. Receipt arbitration clears the deadline before
  allocating the replacement, so normal recovery is unchanged.

  receipt -> reconnect poll replacement delivery, original-work suppression,

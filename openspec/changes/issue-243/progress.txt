## T-002 Gotchas

- `compareDocumentPosition` returns a bitmask — `(node.compareDocumentPosition(other) & Node.DOCUMENT_POSITION_FOLLOWING)` is the right pattern to assert "A precedes B in document order". Treat the bitmask as truthy, not as a boolean expression (`expect(mask & Node.DOCUMENT_POSITION_FOLLOWING).toBeTruthy()`), since the raw value is non-zero but not always equal to 4.
- `new Date(iso).toLocaleTimeString()` is locale-sensitive. Inside jsdom the default locale is consistent across the test run, so the test can compare against the same expression it expects the component to compute. Don't hardcode the formatted string in tests; compute it the same way the production code does.
- `<PromptBlock>` uses `.rounded-2xl` on its inner bubble; the test can locate the prompt bubble via `container.querySelector('.rounded-2xl')` (jsdom renders the first match). Avoids brittle class-name coupling to Tailwind utilities not relevant to the timestamp assertion.

## T-003 Decisions

- D5: Added `rehype-highlight@^7.0.2` as a top-level dep of `packages/web`. `lowlight@^3.0.0` is a transitive dep of `rehype-highlight`, so it does not need to be added explicitly. The rehype plugin is configured with `{ languages: common }` so only the common-language subset (ts/js/bash/json/python/md/diff/yaml + the rest of `lowlight/lib/common`) is bundled — NOT the full `highlight.js` grammar set. `lowlight`'s `package.json` `exports` field only exposes `./index.js`, NOT `./lib/common`, so we import `common` from the package's public API (`import { common } from 'lowlight'`) rather than from the unimportable `lowlight/lib/common` path. The two are equivalent: `index.js` does `export { grammars as common } from './lib/common.js'`, so `common` IS the common.js grammars map.
- D5: Created `widgets/session-transcript/ui/TranscriptMarkdown.tsx` as a thin wrapper around `react-markdown@10` + `remark-gfm@4` + `[[rehypeHighlight, { languages: common }]]`. It uses a `CodeBlockContext` (mirroring the pattern in `shared/ui/markdown-reader/MarkdownReader.tsx`) to distinguish inline `<code>` from block `<pre><code>` reliably — the old `AssistantParts.tsx` heuristic of `!match && !className` mis-classified fenced blocks without a language as inline. Inline code carries the `bg-gray-100 px-1 py-0.5 font-mono text-xs` styling + `[overflow-wrap:anywhere]`; block code passes the `language-*` className through to `<code>` so `rehype-highlight` can append its `hljs`/`hljs-keyword`/etc. classes; the wrapping `<pre>` carries `max-w-full overflow-x-auto rounded bg-gray-50 p-3 font-mono text-xs` (D7 overflow classes).
- D5: Replaced the inline `<Markdown>` (and its `code`/`pre` overrides) inside `AssistantTextPartView` in `AssistantParts.tsx` with `<TranscriptMarkdown content={text} />`. The "Copy" button + streaming indicator + max-w-[90%] wrapper are unchanged.
- D5 (theme scoping): The github.css is embedded verbatim as a string constant in `widgets/session-transcript/ui/transcript-markdown-theme.ts` rather than imported via `?raw` or `?inline`, because Vitest's Vite transform pipeline does NOT handle those suffixes for CSS files in `node_modules` — `import x from 'highlight.js/styles/github.css?raw'` resolves to an empty string under vitest's jsdom environment (verified: `mod.default` is a `string` of length 0). The module-level `scopeFlattenCss(css, '.transcript-md')` walks the github.css, strips the theme credit comment, and prefixes every top-level selector (in each comma-separated selector list) with `.transcript-md `, producing CSS that only matches `hljs-*` classes inside our wrapper. The transformed CSS is injected as a single `<style id="transcript-md-highlight-styles">` tag in `document.head` on the first mount of `TranscriptMarkdown` (idempotent — second mount short-circuits via `getElementById`).
- The theme is scoped to `.transcript-md` (not `:where(.transcript-md)`) so the specificity bump is intentional — the wrapper class is added on the component's own root `<div>`, and downstream consumers do not need to fight cascade.
- `src/vite-env.d.ts` was added (single line `/// <reference types="vite/client" />`) to give TypeScript the `*?raw` / `*?inline` declaration shims from Vite — this was needed because the original typecheck hit `Cannot find module '... ?inline' or its corresponding type declarations`. The reference is purely additive and matches what Vite expects; no other `.d.ts` files exist in the project.

## T-003 Gotchas

- `lowlight@3.3.0`'s `package.json` declares `"exports": "./index.js"` — `lowlight/lib/common` is NOT in the `exports` field and Node throws `ERR_PACKAGE_PATH_NOT_EXPORTED` if you try to import it. The design's literal `lowlight/lib/common` path is therefore not importable as written. The functional intent ("use only the common subset, not the full highlight.js grammar set") is preserved by importing `common` from `lowlight` itself: that export is literally `export { grammars as common } from './lib/common.js'`, so the grammars map is identical. Documented inline in `transcript-markdown-theme.ts` and as a progress note.
- Vitest's Vite transform pipeline does not handle `?raw` or `?inline` for CSS files at all. The `default` export resolves to a `string` of length 0. I confirmed this by writing a throwaway test that did `await import('highlight.js/styles/github.css?raw')` and dumping `mod.default.length` to `/tmp/dump.txt` — got 0. Same for `?inline` and `?url`. Even a workspace-relative CSS file with `?raw` returns empty. Resolution paths considered and rejected: configuring vitest's `server.deps.inline` (only inlines node_modules deps into vite-node, doesn't help with the CSS suffix); adding a custom Vite plugin to handle `?raw` for CSS (a bigger change for a small benefit). Settled on embedding the github.css verbatim as a string constant (~2.2 KB minified) — the file is stable across highlight.js v11.11 minor versions and matches the upstream "GitHub" theme. A comment in the module notes the source.
- jsdom prints `Could not parse CSS stylesheet` warnings when the injected `.transcript-md .hljs-*` stylesheet is parsed. These are non-fatal — jsdom's permissive parser is complaining about a CSS construct it doesn't fully understand (e.g. one of the comma-separated descendant combinators like `.hljs-meta .hljs-keyword`). The test suite still passes (all 2473 tests green); the warnings are filtered to stderr by jsdom and don't show up as test failures.
- A fenced code block without a language tag (`` ```\nplain code\n``` ``) does NOT receive the `hljs` class. This is rehype-highlight's intentional behavior: with `detect: false` (the default) and no language className to look up, the plugin returns early without modifying the AST. The original `AssistantParts.tsx` heuristic (`isInline = !match && !className`) was also wrong on this case — it would have rendered the block as inline code. The new `TranscriptMarkdown` uses a `CodeBlockContext` (set by the `pre` override) to distinguish block from inline, so the no-language case correctly renders as a `<pre><code>plain code</code></pre>` block with the block styling; it just isn't colorized.
- `rehype-highlight` mutates the hast tree by adding `className` arrays to the `<code>` element. The test asserts on `code.className` containing both `hljs` and `language-ts` — react-markdown serializes the array as a space-separated className string in the rendered DOM.
- `lowlight@^3.0.0` is already a transitive dep of `rehype-highlight`, so the `import { common } from 'lowlight'` in `TranscriptMarkdown.tsx` resolves through the same lockfile entry. No need to add `lowlight` to `packages/web/package.json` directly — npm/npm-install handles the deduplication.
- `AssistantParts.render.test.tsx` was not modified — none of its 10 tests assert on the inline `<Markdown>` directly, so the swap to `<TranscriptMarkdown>` is invisible to the existing assertions (which only assert on the `Copy` button, streaming indicator, and tool-part rendering). 2473 tests pass; the existing 6 `AssistantParts` + 7 `TurnList` + 172 `SessionPage` + 26 `MarkdownReader` tests all stay green.

## Codebase Patterns

The Stores for variables follow the established pattern of `WorkflowRunVariablesStore`:
- Each is `public class XxxStore : IScopedService`
- Single ctor dependency: `IDbContextFactory<MohistDbContext>`
- Three methods: `GetVariablesAsync`, `SetVariablesAsync`, `PatchVariablesAsync`
- Get returns `VariableBundle.Empty` for missing rows
- Set/Patch call `VariableBundleShapeValidator.Validate(...)` first
- Patch deep-merges via `VariableBundle.Patch(current, patch)` and round-trips through Set

Project-write invariants preserved:
- `SetVariablesAsync(projectId, bundle)` runs `ProjectVariablesFilter.Sanitize(bundle)` so only `{model, variant}` persist under `vars.agent` and `stages.<stage>.vars.agent`
- Issue-scope `SetVariablesAsync`/`PatchVariablesAsync` first call `VariableBundleShapeValidator.Validate`, then run a `RejectNamedAgentRuntime` guard that throws `ArgumentException` if either `vars.agent.runtime` or any `stages.<stage>.vars.agent.runtime` is present. Both rejection paths run BEFORE any `db.SaveChangesAsync`/`db.IssueWorkflowProfiles.Add`.

`IScopedService` is auto-registered by the existing `MohistServiceRegistration`, so no DI edits are needed for the new types.

The IssueWorkflowProfileManager is no longer the home of Variables — its remaining responsibilities are template selection (GetTemplateAsync/GetStateAsync/UpdateTemplateAsync/GetProfileAsync). T-006 will move them out and delete the class.

The enable toggle (`GetDisabledWorkflowProfileIdsAsync`/`SetProfileEnabledAsync`) and prompts methods stay on ProjectWorkflowProfileManager for T-003/T-006; only variable methods leave.

## Decisions

- The variable validation guard moved into IssueVariableStore 1:1 — same ArgumentException message, same `vars.agent.runtime` key path. Route error code (`invalid_agent_config`) is unchanged because the catch site didn't change.
- Patch semantics in both stores: validate patch, deep-merge current+pach, persist merged, return merged. Shape validation is run on the patch input only (the persisted merged form has already been validated at its previous write, and existing spec coverage confirms the shape stays valid across merge).
- Test coverage: moved 3 variable tests from ProjectWorkflowProfileManagerSpecs into new ProjectVariableStoreSpecs (GetVariables_Empty, SetVariables_StoresBundle, PatchVariables_DeepMerges). Moved 5 variable tests from IssueWorkflowProfileManagerSpecs into new IssueVariableStoreSpecs (Get, Set, Patch, Variable/TemplaateIsolation, ChineseValueRoundtrip), plus 4 newly written negative tests (root runtime rejection, stage runtime rejection, non-object root rejection, non-object stage rejection). The old Project/Issue manager specs only retain non-variable tests.
- The `_issueProfileManager.GetVariablesAsync` call inside IssueGrain (variables for Issue start) is replaced by `_issueVariableStore.GetVariablesAsync` in IssueGrain.cs:353; same for the following Set call. IssueGrain keeps `_projectProfileManager` only for `GetDefaultTemplateAsync` + `GetDisabledWorkflowProfileIdsAsync` (T-006).

## Gotchas

- `IssueGrain` declares `IssueVariableStore issueVariableStore` and the corresponding DI in production is registered through `IScopedService`. Test fixtures (`IssueCommentEventSpecs`, `IssueGrainEventSaveFailureSpecs`, `IssueWorkflowReadPathSpecs`) needed their `IssueGrain.Create` invocation sites updated to construct `IssueVariableStore` from the same `IDbContextFactory` and pass it in.
- `RoutingDispatchTestSupport` still only registers `IssueWorkflowProfileManager` because the routes it exercises (routing dispatch) don't reach the create/update handlers that consume `IssueVariableStore`. No DI change was needed for that support class.
- `WorkflowGrainTestHelpers` + `WorkflowGrainSpecs.PatchProjectVariablesAsync`/`PatchIssueVariablesAsync` switched from constructing the old managers (which required `IPromptLoader`/`PromptTemplateEngine`/etc. for the manager ctor) to constructing the bare Stores. This deletes the dead `null!` IPromptLoader argument.

## T-002 Notes

- `WorkflowVariableResolver` owns the Project → Issue → Run merge, stage overlay, and Issue workspace identity. It resolves run context from persisted run/issue metadata, then reads variable values exclusively through `ProjectVariableStore`, `IssueVariableStore`, and `WorkflowRunVariablesStore`.
- `WorkflowGrain`, `WorkflowQuerier`, and `WorkflowItemTranslator` now use the resolver for workspace and effective variable payloads. `WorkflowProfileManager` retains definition and prompt responsibilities only; its variable store dependency and variable methods are removed.
- Existing variable-resolution specs were moved to the resolver and retain their prior JSON assertions. Added coverage verifies a missing stage returns the workflow-wide bundle unchanged and repeated workspace resolution returns an equal `WorkspaceIdentity` for the same Issue variables.
- Baseline verification before the final coverage additions passed the full server spec assembly (3398 tests) and unit assembly (1610 tests); the Microsoft Testing Platform ignored the requested VSTest filters.

## T-005 Notes

- `IIssueWorkflowProfile` now exposes only the descriptive face: `WorkflowProfile Profile { get; }`. The two `ProjectWorkflowState(...)` overloads are gone from the interface, the base, and the registry.
- `MohistDefaultWorkflowProjection` stays a profile-independent static class. Callers reach it directly: `IssueGrain.GetWorkflowStatusAsync` and `IssueReadModelLoader.ApplyWorkflowProjections` no longer route projection through `_profiles.Get(...).ProjectWorkflowState(...)`.
- The `MohistLocalIssueWorkflowProfile` / `MohistGithubPrIssueWorkflowProfile` classes lose their prompt-store constructor argument and now expose `Profile => WorkflowProfileCatalog.Profile` / `WorkflowProfileCatalog.GithubPrProfileAsset` — i.e. they hand the consumer the authoritative `WorkflowProfile` record rather than re-declaring id/name/description/definition/IsDefault on themselves.
- The registry is reshaped to hold `Dictionary<string, WorkflowProfile>`. Its `Get(id)` returns `WorkflowProfile`; `List()` / `ListDescribed()` / `Default` map the descriptive record onto the public API shapes (`WorkflowProfileInfo` / `WorkflowProfileDescription`), with `IsDefault` derived from the `mohist/local` id match (only `mohist/local` is default among built-ins).
- The dead projection methods (`ProjectWorkflowState`) and the dead prompt-aware methods (`BuildVariables`, `BuildStageVariables`, `GetMergedPromptsAsync`) on `MohistIssueWorkflowProfileBase` were dropped together — they had no callers and now the prompt merge responsibility lives on `ProjectPromptStore` / `WorkflowPromptResolver` (T-003).
- `IssueReadModelLoader` / `IssueMetricsQuerier` no longer take an `IssueWorkflowProfileRegistry` argument (the read-model loader used it only for the projection that has moved to `MohistDefaultWorkflowProjection`; the metrics querier had the field unused). The loader now constructs its projection via `MohistDefaultWorkflowProjection.ProjectWorkflowState(issue.Number, issue.Title, issue.Status, status)`; the resolved projection's status / health / blocked-reason / change-dir / completed flag are identical for the same issue status and workflow view, independent of which Profile is selected (verified by the new `MohistDefaultWorkflowProjectionSpecs`).
- The `IIssueWorkflowProfile` interface survives as the descriptive marker (the registry needs a polymorphic shape for `MohistLocalIssueWorkflowProfile` / `MohistGithubPrIssueWorkflowProfile`); the only member it now exposes is `Profile`. `IssueGrain` still uses the registry for `Exists` / `List` (descriptive concerns), so `_profiles` stays in that grain.
- Test surface updates: `MohistPrIssueWorkflowProfileSpecs`, `WorkflowProfileCatalogSpecs`, `EffectiveWorkflowProfileResolverSpecs` switch to a parameter-less registry constructor and read descriptive fields through `WorkflowProfile` (`profile.Name` / `profile.Description` / `profile.Definition`); `IssueMetricsQualitySpecs` drops the registry from its hand-constructed `IssueReadModelLoader` and `IssueMetricsQuerier` arguments.
- New `MohistDefaultWorkflowProjectionSpecs` anchors the split guarantees: reflection asserts on `MohistDefaultWorkflowProjection.ProjectWorkflowState`'s signature (no profile parameter), reflection asserts on `IIssueWorkflowProfile` (only `Profile` property, no `ProjectWorkflowState` method), and behavior scenarios for done / awaiting-approval / failed / change-dir / no-workflow mirror the spec file's WHEN/THEN list.
- Verification: server spec 3417 (+11 new), unit 1610, arch 51, cli 1465, workflow-definition 175 all green; web typecheck + tests unaffected; runner typecheck + tests unaffected.

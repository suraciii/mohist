## T-001 — TableRenderer 按实体域 partial 拆分

### Codebase Patterns

- **Partial 拆分模式**：用 `sealed partial class` + 多文件按域聚簇是此处正确工具。理由已记在 `TableRenderer.cs` 顶部注释。判断标准：单一职责 + 多个并列 peer case + 共享基础设施 + 无分歧依赖。提取协作类会迫使基础设施复制或反向依赖核心。
- **C# 副作用**：C# partial class 的所有 partial 文件在编译期合并。LSP 工具在缺其他 partial 时会报"未定义"误报——这是预期现象，不是问题。`dotnet build` 才是真正的编译验证。
- **TreatWarningsAsErrors 当 lint**：所有 partial 文件需 `using System.Text.Json.Nodes;`（即使不用 JsonNode 类型），因为 `_out` 走的是 TextWriter 但 dispatch 走 JsonNode。每个 partial 都重复 using 比共享 `global using` 更安全（更显式，无隐式依赖）。
- **命令级 spec 守护 byte-level 输出**：所有 `Render*` 表格输出由 7 个 `Cli*CommandSpecs` 文件的字符串断言守护。拆 partial 时只要方法体 byte-for-byte 不动，spec 必绿——已用 `diff` 严格对比验证（Issues / Entities / Epics / Runners 全部 PASS）。
- **每个 partial 顶部不需要 partial 关键字**（只有类声明加 `partial`），但**每个 partial 都要重复 `using`**、namespace、类声明。

### Decisions

- **Runners.cs 单独成簇**：`RenderRepoList` 体积虽小，但属 runner/repo 域（不是 Project/Agent/Session 这些"瘦小 peer"）。design.md 决策 2 明确指出"若过小可在 review 时合入 Entities"——本次保持 design 决策以维持任务范围。
- **FormatIssueState/FormatLabels 放在 Issues 簇**：仅在 Issues 渲染分支被使用（IssueList/IssueShow），属 Issues 域的内部辅助。
- **核心 partial 顶部加注释**（5 行）：解释 partial 是正确工具的判断依据，让后续维护者不会误读为"拆 god class 反模式"。
- **未触碰 `MohistCliApi.cs`**：仅使用 `MohistCliApi.TableShape` enum。`RenderTableAsync` 内部 `new TableRenderer(_out, activeProjectId)` 不变。

### Gotchas

- 原文件 852 行包括 8 个 `using`/namespace/decl 等开销，拆分后总行数 889（+37）。多出来的 37 行是 4 个新文件的 namespace/using/`sealed partial class` 头——必要开销。
- 核心 partial 文件 153 行里只有 11 行代码 + 顶部注释 + 头部；其余是 `WriteTable`（7 行）+ 4 个 `AsArray/StringOf/BoolOf/NumberOf/Truncate`（约 35 行）+ Render dispatch（63 行）。
- `Truncate` 的 `softCap - 1` 行使用了 `…` 字符（U+2026），与原文件一致——未替换。
- 静态方法 `FormatIssueState` 标记为 `internal static`（与原文件一致）。它在 Issues 簇内被 2 个 `Render*` 方法调用，不跨 partial。
- `MohistCliApi.TableShape` 是 `MohistCliApi` 嵌套枚举，partial 文件中只能通过完全限定名 `MohistCliApi.TableShape` 引用（与原文件一致）。

## T-002 — InfoCollector 分离采集、渲染与 systemd 解析

### Codebase Patterns

- **3 个独立类型替代 1 个 god class**：每个类型有清晰单一变更原因。`SystemdUnitParser`（无实例静态，承接所有 systemd 解析 + 单元字段记录 + sentinel 常量）、`InfoRenderer`（仅 `TextWriter` + `InfoResult`/`InfoVerbose`，承接 `RenderDefault/RenderVerbose/RenderJson` + 所有 `Build*Json`/`Build*Line`）、`InfoCollector`（瘦身到 1014 行，仅采集 + 路径/进程启发式私有静态 + `AttachConnectivity`）。
- **`BuildStatusFromProperties` 取 `IFileSystem` 参数**：原方法在 fallback 路径需要读 `/proc/{pid}/stat`。提取到静态类后调用方传 `_fileSystem` 即可，签名仍纯。
- **`SystemdUnitFields` 记录随 `ParseSystemdUnit` 一起搬**：collector 引用方式变为 `new SystemdUnitParser.SystemdUnitFields(...)`。`SystemdUnitParser.SystemdUnitFields` 是限定路径——partial-style。
- **`AttachConnectivity` 留在 collector**：它在 `CollectAsync` 期间把 connectivity 字段挂到 runner 记录上——属采集期装配而非渲染，决定保持归属。
- **现有 server 测试需要更新类引用**：提取后 `InfoCollector.RenderJson` 等已不存在。直接迁移引用（`InfoCollector.BuildCliLine` → `InfoRenderer.BuildCliLine`、`InfoCollector.ParseSystemdShow` → `SystemdUnitParser.ParseSystemdShow`、sentinel 常量 `Unknown/NotRunning/NotInstalled/NotAGitRepo` 从 InfoCollector 移到 SystemdUnitParser）。
- **测试 DI 注册需要补 `InfoRenderer`**：`MohistCliCommands.RunAsync`（CLI 测试入口）与 12 处 server 测试 `services.AddSingleton<InfoCollector>()` 之后都加 `services.AddSingleton<InfoRenderer>()`，否则 `InfoCommands.Build` 在 `GetRequiredService<InfoRenderer>` 时抛异常。

### Decisions

- **SystemdUnitParser 静态类 + `internal` 构造签名（无）**：满足"无实例字段/构造器"。`TryGetUptimeFromProc` 需要 `IFileSystem` 是**参数**而非字段，仍然纯。
- **InfoRenderer 依赖面最小化**：只取 `TextWriter` + `InfoResult`/`InfoVerbose`。渲染时调用的 sentinel 常量通过 `SystemdUnitParser.NotRunning` 等限定访问（不引入新依赖）。
- **未触碰 `InfoResult.cs` 数据形状**：所有 record 字段不变，外部测试构造仍兼容。
- **未补 `AttachConnectivity` 单元测试**：它依赖 `InfoService` 记录形态不变，server 测试已通过 `Collect_*` 端到端守护其行为；纯函数提取收益低。
- **未给 `ServiceReadinessProbe` 提取相关工作**：T-002 不涉及 update 模块。
- **新增 internal 单测覆盖关键纯函数**：`SystemdUnitParserSpecs`（24 个 case，覆盖 Parse/TryParse/Format/Build 关键路径）+ `InfoRendererSpecs`（8 个 case，覆盖 RenderDefault/RenderJson/BuildCliLine/BuildServiceLine/BuildJsonObject）。

### Gotchas

- InfoCollector 从 1690 行缩到 1014 行（-676）。`InfoRenderer` 402 行（Render + 13 个 BuildJson + 5 个 BuildLine + WriteIndentedList）。`SystemdUnitParser` 298 行（11 个 Parse/TryParse/Format/Build 静态方法 + SystemdUnitFields 记录 + 7 个常量）。
- `BuildSourceFromPropertiesAsync` 内部仍构造 `new SystemdUnitParser.SystemdUnitFields(...)`（私有方法，限定引用 OK）。
- `GetServiceInfoAsync` / `TryGetRunnerUnitEnvironmentAsync` 等采集方法全部调用 `SystemdUnitParser.*` 而非自身方法——属机械替换。
- sentinel 常量迁移后 `InfoCollector` 不再持有 `NotRunning/NotInstalled/NotAGitRepo/Unknown`，仅保留 `ServerOk/ServerUnreachable/PlatformNoticeMessage/TimeoutSentinel`（采集期常量，非渲染常量）。
- `InfoCollector.ServerUnit/RunnerUnit` 两个常量保留以兼容潜在外部引用（值为 `SystemdUnitParser.ServerUnit/RunnerUnit` 的别名）。测试中显式用 `SystemdUnitParser.NotInstalled` 等替换旧 `InfoCollector.NotInstalled` 引用。

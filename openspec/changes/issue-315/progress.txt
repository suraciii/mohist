## Codebase Patterns

### LiveTaskProvider test harness
- `packages/web/src/app/providers/LiveTaskProvider.test.ts` has a `vi.hoisted` `mocks` block that mocks `useEventsConnection`, `useAgentStatus`, and `sonner.toast.{info,error,success}`.
- The `mountWith(queryClient)` helper renders `LiveTaskProvider` under `QueryClientProvider` + `ProjectProvider` and pulls back the captured `handleEvent` callback from `mocks.useEventsConnection.mock.calls[0][1]`.
- Calling `handleEvent(eventName, data)` from the test drives the in-file `handleEvent` switch exactly as `useEventsConnection` would on the SignalR bus.
- `beforeEach` calls `vi.clearAllMocks()` so every test gets a fresh spy baseline.

### Re-observing `LiveTaskContext` state in tests
- `useLiveTask` (from `entities/issue/model/live-task`) reads the context that `LiveTaskProvider` populates.
- To capture `rebaseConflict` (and the rest of the state) from a test, mount a tiny child consumer under `LiveTaskProvider` that writes the state object to a mutable ref on every render. Read the ref's latest value after `act()` to assert on the post-event state.
- Pattern used in new D2 tests:
  ```ts
  const stateProbe = { current: null as { rebaseConflict: unknown } | null }
  function StateProbe() { stateProbe.current = useLiveTask(); return null }
  // pass `stateProbe` into `mountWith` and let it render <StateProbe/> as the child
  ```

### Seeding the issue cache for `findIssueNumber`
- `findIssueNumber` reads `queryClient.getQueriesData<Issue[]>({ queryKey: ['issues'] })` and matches on `Issue.id` to return the issue's `.number`.
- Tests can seed via `queryClient.setQueryData(['issues'], [makeIssue(id, number)])` before driving `handleEvent`.
- A minimal `Issue` for seeding requires the required scalar fields (`id`, `number`, `title`, `status`, `health`, `projectId`, `labels`, `createdAt`, `updatedAt`, `isDraft`, `canStart`, `blocker`); use `IssueStatus.Backlog` / `IssueHealth.Active` for status/health since these are string-valued enums.

### `dispatchRebaseEvent` / `onRebaseEvent` in tests
- `onRebaseEvent(handler)` (from `entities/issue/model/rebase-events`) is the public subscribe entry — it returns an unsubscribe function.
- Tests can subscribe, push events into a captured array, and assert on the captured sequence; remember to call the off function at end-of-test.

## Gotchas for downstream tasks (post T-003)
- The `ReverseDnsInvalidationKey` is a `readonly string[]`, not TanStack's `QueryKey` (`readonly unknown[]`). When the caller applies it, it casts to `unknown[]` to satisfy `invalidateQueries` — see `applyReverseDnsOutcome` line 154. Keep `ReverseDnsInvalidationKey` narrow-by-intent (string segments only); broadening to `readonly unknown[]` would force the decider to import a type from a runtime dep.
- The apply function holds the canonical-order invariant — **never reorder** the four lines; rebase-conflict arm in particular relied on `setRebaseConflict` followed by `dispatchRebaseEvent` followed by `toast.error` followed by `invalidate`. Re-running the existing T-001 outcome tests is the regression check that pins this; if any of them flip behavior, the canonical order is broken.
- `outcome.rebaseConflict !== undefined` is the null-clear gate. Setting to `null` is the legacy "clear" semantics; `undefined` is "leave state unchanged" (used by merge-success / merge-failure arms). Do not change this without re-running the rebase-completed-clears-conflict assertion.
- When T-005 collapses the switch into a ROUTE table, the three `applyReverseDnsOutcome(decideReverseDnsOutcome(...), ...)` call sites each gate the switch-arm default invalidations (else the switch arm falls through to `['issues']`+detail). That gate must remain in the per-domain handler — the decider returning `handled: false` is the signal "this event is a plain issue event, run the default".

## T-001 — Event-driven issue completion on workflow-run Completed

### Codebase Patterns
- Handler placement: `packages/server/src/Mohist.Server/Events/Subscriptions/`
- Spec placement: `packages/server/tests/Mohist.Server.Tests/Specs/Events/<aggregate>/<Handler>Specs.cs`
- Subscription attribute: `[Subscription(Type = EventCatalog.ReverseDns.WorkflowRunCompleted)]`
- Handler shape: `ICloudEventHandler` (non-generic). Generic form `ICloudEventHandler<T>` is reserved for typed payload handlers like `EpicAutoDoneHandler` (uses CloudEvent extensions to carry issue/project). The new handler parses the run id from `evt.Source` via `WorkflowEventSerializer.ExtractContextFromSource` — same approach as `RunnerWorkflowTerminalStatusHandler`.
- Issue resolution: `IssueQuerier.GetIssueIdForWorkflowRunAsync(string workflowRunId)` is added as a new scoped dependency. Returns `null` when no in-progress issue is bound. SQL: `WHERE WorkflowRunId = @id AND Status = 'inProgress'`. Filter on status reuses the deleted sweep's documented wisdom about preserved `WorkflowRunId` on Done issues being history, not a stuck-run signal.
- Dispatch: synchronous `_grains.GetGrain<IIssueGrain>(GrainKey.Issue(issueId)).CompleteWorkAsync(workflowRunId)` — same-grain-vs-different-grain analysis: workflow publish path → IssueGrain (different grain, no reentrancy). Matches `EpicAutoDoneHandler`'s posture (issue publish path → EpicGrain, sync).
- Scoped resolution: handler is wired as a singleton by the bus, but `IssueQuerier` is scoped. Handler opens `IServiceScope` per delivery via `IServiceScopeFactory` — same pattern as `InboxProjectionHandler`.
- Exception handling: handler has TWO try/catch blocks. The first guards the IssueQuerier lookup (DB-side fault); the second guards `CompleteWorkAsync`. Both swallow + `LogWarning` — never propagated.
- TimeProvider: spec tests use `Microsoft.Extensions.Time.Testing.FakeTimeProvider` injected through the recording grain factory.
- Test scope factory: minimal `IServiceScopeFactory` test double constructs `IssueQuerier` with `null!` for unused dependencies. Pattern documented inline (matches EpicQuerier unit-test pattern in EpicAutoDoneHandlerSpecs).
- Single-type subscription: `[Subscription(Type = EventCatalog.ReverseDns.WorkflowRunCompleted)]` — NOT the pipe-separated terminal pattern. Failed/stopped are explicitly NOT subscribed; Filter() also hard-rejects non-Completed types as defense in depth.

### Key files
- `packages/server/src/Mohist.Server/Events/Subscriptions/IssueWorkflowCompletionHandler.cs` — new (123 lines)
- `packages/server/src/Mohist.Server/Issue/Services/IssueQuerier.cs` — added `GetIssueIdForWorkflowRunAsync` (+33 lines incl. doc comment)
- `packages/server/tests/Mohist.Server.Tests/Specs/Events/Issue/IssueWorkflowCompletionHandlerSpecs.cs` — new (783 lines, 17 specs, all pass)

### Verification
- `dotnet build Mohist.sln`: 0 warnings, 0 errors (TreatWarningsAsErrors enabled).
- `dotnet test --filter IssueWorkflowCompletionHandlerSpecs`: 17/17 pass.
- Full `npm test`: 3373 server tests pass, 0 failures. Runner/web suites also green.

### Gotchas / Lessons
- `IIssueGrain.CompleteWorkAsync` already guards on `Status == InProgress` and `workflowRunId` match. Spec test `HandleAsync_MismatchedWorkflowRunIdOnIssue_DoesNotMutateIssue` exercises this guard independently — the handler itself relies on the `Status = 'in_progress'` filter as the first line of defense (avoids activating the grain at all on stale bindings).
- The handler swallows BOTH lookup exceptions and grain exceptions — without the lookup catch, a transient DB fault would otherwise bubble into the publish path. Mirrors the existing handler design.
- The handler accepts events with `evt.Type == WorkflowRunCompleted` ONLY (via the single-type subscription attribute). The `Filter` method also hard-rejects other types — belt-and-suspenders.
- `IssueWorkflowReconciliationService` is still present on disk but is left untouched (T-002's job to delete). T-001 only adds the new event-driven path.

### Follow-ups
- T-002 will delete `IssueWorkflowReconciliationService` and its hosted registration, simplify `IssueGrain.GetWorkflowStatusAsync` to a pure query.
- T-003 is independent (Web UI).

## T-002 — Remove daily sweep + lazy read-path reconciliation; pure-query read path

### Codebase Patterns
- Test placement for grain-level specs: `packages/server/tests/Mohist.Server.Tests/Specs/Issue/Grain/<Grain>Specs.cs` (mirrors `Specs/Epic/Grain/EpicProgressionSpecs.cs`, `Specs/Agent/Grain/AgentGrainSpecs.cs`). The `Grain/` tier was empty before this change.
- Testability seam: `IssueGrain` gains `internal string GrainKeyForTest { get; set; } = string.Empty;` plus the existing `private string GrainKey => string.IsNullOrEmpty(GrainKeyForTest) ? this.GetPrimaryKeyString() : GrainKeyForTest;`. Matches the EpicGrain/AgentGrain pattern. `Mohist.Server.Tests` already has `InternalsVisibleTo` via `AssemblyInfo.cs`.
- Pure-query spec construction: `MohistDbFixture` provides the full production service graph (DI + EF + WorkflowQuerier) without spinning up `WebApplicationFactory` or an Orleans silo. IssueGrain is NOT registered in DI; the spec resolves its 14 dependencies from `scope.ServiceProvider.GetRequiredService<T>()` and constructs the grain manually — then sets `GrainKeyForTest` so `OnActivateAsync` can load `_issue` via `_issueStore.LoadAsync(GrainKey)` without the Orleans runtime.
- State-store swap: spec swaps the scoped `IStateStore<Domain.Issue>` (IssueStore) for a `ReadOnlyTrackingStateStore` that delegates LoadAsync to IssueStore but records every SaveAsync call. The pure-query contract is asserted via `Assert.Empty(stateStore.SaveCalls)` — any write leaks into the read path fail the test.
- Status filter invariant lives on `IssueQuerier.GetIssueIdForWorkflowRunAsync` doc comment ("preserved WorkflowRunId on Done issues is execution history") — the comment now stands on its own rationale, no longer references the deleted sweep.

### Gotchas / Lessons
- The DB fixture is shared-cache SQLite across tests in a single fixture instance. Each spec must use **unique** `ProjectId` + `Number` tuples — initial run hit `UNIQUE constraint failed: Issues.ProjectId, Issues.Number` because all three tests seeded `project_readpath`/issue 1. Fix: include `Guid.NewGuid():N` suffix in the project id (issue id stays in the row's `IssueId` column, which is already unique).
- `IssueGrain`'s 14 constructor params look intimidating but every single one is resolvable from the DI scope via `services.GetRequiredService<T>()`. Once the grain is constructed with `GrainKeyForTest` set, calling `OnActivateAsync` then the grain's own methods works without an Orleans silo. The cost is paid once per spec; tests stay in the unit-tier speed bucket.
- The `ReadOnlyTrackingStateStore` pattern is reusable for any "this code path must not mutate state" assertion. It forwards Load to the real IssueStore (so seed/load round-trip works) and records Save calls without blocking the real DB write — that lets us detect the unwanted Save without breaking tests that need subsequent reads.
- The `WorkflowStatusMapper.BuildStatusView` projection's `Status` field uses `FrontendStatus(run.Status.ToString())` which lowercases the enum name. So `WorkflowRunStatus.Completed` → `"completed"` (not `"Completed"`). Matches the existing `IssueGrain.GetControllableWorkflowStatusAsync` checks (`"completed"` literal).
- `Issue.Status == InProgress` projects to `Stage = "in_progress"` (note the underscore) via `MohistDefaultWorkflowProjection.IssueStatusName`. The test asserts on `"in_progress"`, NOT `"inProgress"` — the projection's wire format differs from the enum's C# spelling.
- No event-bus side-effects to assert against: `GetWorkflowStatusAsync` no longer touches `_issue.PendingEvents` (deleted path) and never calls `SaveIssueAsync`/`PublishIssueEventsAsync`. The RecordingEventStore from T-001's pattern isn't needed here — the state-store recording is sufficient.
- `WorkflowRunStatus` enum is `Completed` (PascalCase). JSON serialization uses `JsonStringEnumConverter(JsonNamingPolicy.CamelCase)` per `JSON.Options`, so the stored/loaded value round-trips correctly.

### Follow-ups
- T-003 (Web Done stage removal) is independent and can proceed in parallel — no shared files with server.
- The `GrainKeyForTest` testability seam is now established on IssueGrain. Future IssueGrain-level specs can follow the same construction pattern in `IssueWorkflowReadPathSpecs.CreateGrain`.

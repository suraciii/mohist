### MF-8 — selected-Connection lookup does not recognize soft deletion — FIXED

The plan now matches the repository's actual soft-delete semantics. It keeps
the complete-pair, project-scoped
`AgentConnectionStore.GetAsync(ChosenProjectId, ChosenConnectionId)` lookup,
but no longer treats null as the only deletion signal: candidate resolution
requires both a non-null result and `DeletedAt is null`. A null row or a
soft-deleted row is visibly `unavailable` before workspace binding, selected
lease, authorization, executability, or commit, so surviving/fake downstream
artifacts cannot admit a deleted candidate.

- proposal.md now calls out that the existing project-scoped `GetAsync`
  includes soft-deleted rows and requires an explicit `DeletedAt` rejection.
- design.md Decision 4 step 7 names the exact predicate, explains the
  `DeleteAsync`/`GetAsync` codebase semantics, and places the deletion check
  before all downstream selected-candidate checks.
- the action spec requires explicit `DeletedAt` inspection and its deterministic
  scenario uses the normal soft-delete path, confirms lookup still returns the
  row, and retains stale fake lease/binding artifacts to prove precedence.
- T-003 prescribes the same implementation boundary and requires the test to
  use `AgentConnectionStore.DeleteAsync` (or equivalent real soft deletion),
  assert `GetAsync` returns `DeletedAt`, and prove no winner or resources even
  with fake downstream artifacts.

### MF-7 — missing selected Connection is classified as stale instead of unavailable — FIXED

The acceptance pipeline now distinguishes lookup absence from candidate-fact
drift exactly as issue AC #4 requires:

- A project-scoped lookup of the signed and snapshotted selected
  `(ProjectId, ConnectionId)` that returns no Connection row is a visible
  `unavailable` result, with no selection mutation, winner, or execution
  resource.
- A selected Connection that still exists but no longer has the snapshotted
  workspace-Bot binding is `no_longer_valid`/stale. A required follow-up
  binding or target Session that vanished while the Connection remains is
  likewise `no_longer_valid`.
- An existing selected Connection whose own current runtime lease is absent or
  invalid remains `unavailable`.

The proposal now states the deleted-Connection outcome. Design Decision 4
step 7 and the domain-outcome mapping name the split and preserve the exact
project-scoped lookup. The action capability adds deterministic scenarios for
a deleted selected Connection (`unavailable`) and a still-existing candidate
with binding drift (`no longer valid`), while its lease requirement retains
missing/invalid lease as `unavailable`. T-003's pipeline, rejection matrix,
and fixed-time test matrix require the same classifications.

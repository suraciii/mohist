## Why

When one Slack message mentions several Mohist Bots (or an unmentioned reply lands in a thread bound to several Bots), Slack fans the event out to every mentioned App, and today the race-winning Connection answers with a plain-text prompt — "Multiple Agents could answer this; mention a single Bot to address one" — so the user must re-mention and resend the delegation. The product spec already requires the opposite: "One message mentioning several Bots starts no work and produces one interactive selection; choosing an Agent starts its work", and "The chooser is an interactive Slack selection, not a free-text reply to parse". Retyping also loses execution attribution: the started work would carry a new Slack message as provenance instead of the user's actual message, and nothing yet guarantees that a resolved multi-Bot delegation produces exactly one execution owned by exactly one Connection. The reviewed Stop and Retry actions have already established the signed-interaction pattern this chooser must join.

## What Changes

- Replace the free-text ambiguity prompt with one selection per ambiguous message: the race-winning Connection renders per-candidate chooser controls — one choice per mentioned Bot, up to five — through its outbox user-action delivery, keeping the existing once-only claim so concurrent per-Connection ingress, Slack redelivery, and adapter failover still produce exactly one chooser message. When more than five candidates are eligible no interactive control is rendered: the once-only delivery is a readable text fallback requiring the user to explicitly re-mention a single Bot, with no truncation, auto-selection, or pagination, and every chooser message carries readable text (candidate summary plus the re-mention instruction) so clients without interactive support show the same guidance.
- Retain the ambiguous message's normalized input facts (sender, task text, attachment metadata, thread anchor) durably with the claim, so a selection can start work from the original message with no resend.
- Every choice carries a Server-signed action payload bound to the posting Connection, workspace/conversation/message identity, the original sender, the candidate set, a nonce, and a bounded expiry — the same signing material, canonicalization, and constant-time verification Stop and Retry use.
- On click, revalidate signature, freshness, context, actor binding, the chosen Connection's currently valid runtime lease (its own, resolved at click time — never the prompt-owner's delivering lease; missing or invalid is a distinct visible unavailable outcome), the clicker's current permission under the chosen Connection's access policy evaluated under that lease, and the chosen candidate's current executability (Connection enabled, Agent ready — the existing setup-nudge path when not). Expired, tampered, stale, unauthorized, unavailable, or no-longer-valid selections are explicitly rejected with a visible notice and create no execution resources.
- Choosing an Agent starts that Agent's work from the original message, with the original sender as initiator of record: a root multi-mention launches the chosen Connection's Session in that thread; an ambiguous reply in a multi-bound thread dispatches a follow-up to the chosen Connection's bound Session.
- Guarantee single execution attribution: the selection decision is durably persisted before dispatch with a pre-allocated execution identity; concurrent clicks, Slack interaction redelivery, adapter failover, and lost interaction responses resolve to one recorded selection and create at most one AgentJob/Session/SessionInput; a Server restart resumes or settles a committed-but-pending selection without a second execution; finished selection records are cleaned up under a bounded retention rule. No other mentioned Connection creates work for the message.
- The chooser message reflects the accepted selection (and rejection outcomes) through the existing interaction reply path, so late or second clickers see the decision instead of a second chooser; the non-owner guidance for unauthorized senders is unchanged.
- Route the selection action id through the existing interaction route alongside Stop and Retry, reusing adapter lease validation and outbox user-action reply delivery unchanged; the button remains a shortcut to the same launch/admission services CLI and Web use, never a second command grammar.
- Out of scope: coordination across separate Mohist Servers (still none), managed-Bot self-message suppression (#616), re-routing already-bound single-Agent threads, and interactive pagination (or any interactive control) for more than five candidates — the >5 case is a readable text fallback per the issue.

## Capabilities

- `slack-agent-selection-prompt`: One selection per ambiguous multi-Bot message — the once-only chooser claim across concurrent Connections and redelivery, per-candidate choices rendered from the mentioned workspace Bots (interactive controls for two to five candidates; a readable re-mention text fallback beyond five), durable retention of the original message's input facts, and no work started by the ambiguous message itself.
- `slack-agent-selection-action`: The signed selection action and its acceptance revalidation — payload binding, signature/freshness/context/actor checks, the clicker's permission under the chosen Connection's current access policy, candidate executability revalidation, explicit rejection outcomes that create no execution resources, and coexistence with Stop and Retry on the shared interaction path.
- `slack-selection-execution-attribution`: Single execution ownership for a resolved selection — exactly one execution attributed to the chosen Connection, started from the original message with the original sender as initiator, no work for other mentioned Connections, the durable selection operation persisted before dispatch, at-most-one execution under concurrency/redelivery/failover/lost responses, restart recovery, and bounded cleanup of finished records.

## Impact

- **Server ambiguity path:** `SlackConnectionRoutes.ChannelIngress.cs` (`HandleAmbiguousPromptAsync`, `HandleAmbiguousNonOwnerAsync`) around the `SlackMultiAgentRoutingPolicy` decision sites; `SlackAmbiguousPromptStore`/`SlackAmbiguousPromptRow` plus an EF migration gain original-message facts and selection state.
- **New selection service:** a `SlackAgentSelectionService` beside `SlackTurnControlService`/`SlackRetryActionService`, reusing `ISlackActionSigner` and dispatched from `SlackInteractionRoutes` by action id.
- **Launch/admission reuse:** the channel-root launch path (thread launch reservation, provider inbox route, attachment binder, `SlackAdmissionService` executability and setup nudge) and thread follow-up dispatch are invoked for the chosen Connection at click time with pre-allocated identity; the provider inbox keeps owning only raw Slack message ingress.
- **Persistence/recovery:** selection-operation receipt store and restart recovery (obligation-worker pattern), with bounded cleanup.
- **Slack adapter:** no contract change — `block_actions` forwarding is generic over action ids and blocks already flow in outbox payloads; only adapter tests add the new action id.
- **Docs:** `docs/slack.md` and `design/slack.md` Status/gap notes move multi-Bot selection from planned to delivered.
- **Risk:** authorization, durable operations, and cross-Connection launch attribution are high-risk boundaries requiring fixed-time, fake-port spec coverage for the chooser, the acceptance matrix, and operation recovery; the stale draft PR #635 (mixed Retry and selection) is not reused.
- **Unaffected:** CLI command surface, Web, Runner contracts, Manager conversation, and bot self-message admission.

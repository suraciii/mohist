# Review: Issue 618

Review round: re-review of the current product change against the live issue acceptance criteria and the issue-618 plan/spec artifacts. I verified the prior follow-up-expiry dispatch finding and checked the initial Manager recovery path that the previous review had explicitly deferred.

## Must-Fix Findings

### 1. Initial Manager recovery fails after the initial turn is marked unknown, so no fresh credentialed recovery turn is created

`ReportManagerCredentialExpiredAsync`, unknown-result recovery, report-timeout recovery, and Runner-loss recovery all deliver the initial Manager turn as `Unknown` before calling `EnsureManagerRecoveryAsync` (`packages/server/src/Mohist.Server/Agent/Grains/AgentJobGrain.Recovery.cs:17-26`, `:88-95`, `:114-123`, and `:134-142`). `DeliverInitialTurnTerminalAsync` calls `MarkInitialTurnTerminalAsync`, which changes the Session activity to `Unknown` (`packages/server/src/Mohist.Server/Agent/Grains/AgentJobGrain.cs:986-995`; `packages/server/src/Mohist.Server/Sessions/Domain/AgentSession.Transitions.cs:744-764`).

The recovery helper then records its replacement input with the ordinary `RecordFollowupTurnAsync` (`packages/server/src/Mohist.Server/Agent/Grains/AgentJobGrain.Recovery.cs:29-58`; `packages/server/src/Mohist.Server/Sessions/Grains/AgentSessionGrain.cs:3466-3500`). `RecordFollowupTurnCore` rejects every new turn while the Session is not idle unless `allowUnknownRecovery` is true (`packages/server/src/Mohist.Server/Sessions/Domain/AgentSession.Transitions.cs:613-620`). That allowance exists only on `RecordManagerRecoveryTurn`, which the initial recovery helper does not use (`packages/server/src/Mohist.Server/Sessions/Domain/AgentSession.Transitions.cs:522-537`). The call therefore throws before `State.ManagerRecovery` is persisted and before the replacement turn can reach the follow-up dispatcher and receive a new management/reply grant.

This violates issue Acceptance Criterion 5: after Manager credential expiry or Session/runtime recovery, the system must reauthorize from the immutable Slack origin and issue a fresh credential rather than stop after the old execution is marked unknown. It also violates the `manager-execution-credentials` requirement/scenarios for recovered and expiry-recovery executions and T-003's acceptance criteria for Runner crash recovery and fresh credentials after every transition. The existing Runner-loss recovery spec does not expose this because it opens a Session without recording the real initial Session turn (`packages/server/tests/Mohist.Server.SpecTests/Specs/Agent/Grain/AgentJobManagerRunnerLossRecoverySpecs.cs:37-44`, `:72-88`). Make the initial Manager recovery transition explicitly allowed from the unknown Session state, while preserving the same durable lease/idempotency and non-replay rules, and add a test that records a real Manager initial turn before exercising initial expiry/Runner-loss recovery through fresh grant dispatch.

## Previous Finding Dispositions

1. **Follow-up expiry recovery was fixed properly.** The shared `RecordFollowupTurnCore` now appends a deterministic `AgentSessionFollowupLease` for newly recorded system recovery turns (`packages/server/src/Mohist.Server/Sessions/Domain/AgentSession.Transitions.cs:642-667`). `BeginNextFollowupDispatchAsync` can therefore claim the recovery turn, and the updated runtime-event spec confirms the recovery input/turn is dispatchable (`packages/server/tests/Mohist.Server.SpecTests/Specs/Sessions/AgentSessionRuntimeEventSpecs.cs:106-112`). The full Server spec run passed 3,181/3,181.
2. **Same-user credential environment exposure remains fixed.** `ManagerExecutionBoundary.create` removes both bearer variables from the inherited child environment, while the private broker handles credential-bearing requests (`packages/runner/src/runtime/manager-execution-boundary.ts:113-141`). The latest Session recovery changes do not alter this boundary.
3. **Follow-up leases are revoked on completion, cancellation, and rejection.** Runner follow-up completion/disposal and cancellation resolve the registered Manager boundary and invoke Server-side revocation (`packages/runner/src/server/followup-handler.ts:439-461`, `packages/runner/src/server/cancel-handler.ts:323-335`), while terminal delivery also revokes the execution identity through the existing Server path. The latest recovery lease addition does not alter those terminal paths.
4. **Follow-up boundaries still receive deployment-epoch invalidation.** Initial and control-channel follow-ups are registered in the shared `ManagerExecutionRegistry`, and epoch changes abort in-flight Manager work and dispose registered boundaries (`packages/runner/src/runtime/host.ts:790-793`, `:884-889`; `packages/runner/src/runtime/manager-execution-lifecycle.ts:14-31`).
5. **OpenCode follow-up cancellation still uses the isolated runtime handle.** Cancellation resolves the matching registered entry and uses its handle before disposal, rather than falling back to the shared runtime (`packages/runner/src/server/cancel-handler.ts:128-136`, `:180-193`).

## Dimension Checks

- **Acceptance criteria: FAIL.** The repaired follow-up-expiry path satisfies the fresh-dispatch part of Criterion 5, but initial Manager expiry, Runner-loss, and unknown-result recovery can fail before creating the required replacement turn and credential.
- **Coverage: FAIL for the must-fix behavior.** The new test proves only that a Session-level follow-up recovery turn can be claimed. No test covers an initial Manager Session turn reaching unknown, creation of its recovery turn, actual dispatcher delivery, and fresh grant issuance. The existing Runner-loss test omits the initial Session turn and therefore cannot catch the rejection above.
- **Correctness: FAIL.** The production initial-recovery call order marks the Session unknown and then invokes a transition that explicitly forbids new turns from unknown state. The existing follow-up fix does not reach this helper's failing precondition.
- **Consistency with the surrounding codebase and conventions: checked, no additional criterion-level issue.** The follow-up recovery now uses the ordinary durable lease/dispatch contract, current authorization, and fresh-grant path. The unresolved initial path is a lifecycle-state mismatch at the recovery boundary.
- **Tests: checked.** `dotnet build packages/server/src/Mohist.Server/Mohist.Server.csproj --no-restore -p:SkipWebBuild=true` passed. One full Server Spec assembly run passed 3,181/3,181; the targeted workflow cleanup class passed 1/1. A separately concurrent duplicate assembly run hit one unrelated workflow race. Runner typecheck passed, and the focused Runner follow-up/cancellation/Manager-boundary tests passed 5/5. These results do not cover the initial recovery sequence identified above.

## Observations

- The latest generic change applies a pending follow-up lease to every new turn recorded through `RecordFollowupTurnCore`, including workflow cleanup turns (`packages/server/src/Mohist.Server/Sessions/Grains/AgentSessionGrain.WorkflowCleanup.cs:42-53`). Workflow cleanup advances and completes its turn through the workflow-specific/runtime turn path rather than `MarkFollowupTurnTerminal`, so the added lease can remain in `PendingFollowups` after cleanup. The issue does not target workflow sessions, so this is outside the must-fix verdict, but the shared transition should be scoped or the workflow terminal path should clear that lease.
- The new Session spec asserts `BeginNextFollowupDispatchAsync` returns the recovery turn, but not that `AgentSessionFollowupDispatcher` emits it to a Runner and `IssueManagerGrantAsync` produces fresh management and reply credentials. The production path is now wired for that handoff; an end-to-end assertion would reduce regression risk.
- Retired Manager envelope/parser, executor, and execution-fence source remains present as unregistered compatibility code. Current DI tests confirm those services are not registered, and no runtime terminal handler resolves them; this does not restore the old Slack protocol and remains non-blocking.
- The plan still leaves exact credential TTL/clock-skew policy and adapter reaction capability details open in `design.md`; those do not affect the must-fix finding above.

**Verdict: FAIL**

# Review: Issue 618

Review round: re-review of the current product change against the live issue acceptance criteria and the issue-618 plan/spec artifacts. ## Must-Fix Findings

### 1. Expired Manager follow-ups are reported as ordinary completion instead of entering fresh recovery

`ManagerExecutionBoundary` exposes the expiry state and rejects new shell work after the grant expires (`packages/runner/src/runtime/manager-execution-boundary.ts:181-200,226-231`), but the follow-up completion path never checks that state after `callFollowup` returns. In `packages/runner/src/server/followup-handler.ts:362-407`, a successful runtime result is always recorded as `session.activity` with `activity: "idle"`; a failed result is also recorded as `idle` unless its runtime error kind happens to be `unavailable-runtime` or `deadline-exceeded` (`:365-377`). The `completion.finally` block then disposes the boundary and revokes the lease (`:435-440`), but disposal is not expiry recovery.

Therefore, if a Manager follow-up remains active until either credential expires, or a CLI call observes expiry while the model subsequently returns a normal result, the Session records an ordinary completed follow-up. The Server's only explicit `manager-credential-expired` recovery path is `AgentJobGrain.ReportManagerCredentialExpiredAsync` (`packages/server/src/Mohist.Server/Agent/Grains/AgentJobGrain.Recovery.cs:14-26`); Session follow-up runtime-event delivery only appends the event and dispatches the next ordinary follow-up (`packages/server/src/Mohist.Server/Api/RunnerRoutes.cs:708-728`). No fresh recovery/new-turn transition is created from the immutable Manager origin, and there is no guarantee that the next turn is issued as the required non-replaying expiry recovery.

This violates issue Acceptance Criterion 5: after credential expiry, Manager work must reauthorize from the immutable Slack origin and receive a new credential rather than continue as the completed old execution. It also violates the `manager-execution-credentials` expiry scenarios and T-003 acceptance criteria requiring the active execution to close through exactly one expiry-recovery transition, with no replay of the prior prompt or an uncertain state-changing operation. Add an expiry check at the follow-up terminal boundary and route the result through an idempotent durable Manager recovery transition that issues a fresh grant after current authorization; cover both a runtime result that is successful after expiry and a CLI-expiry error path.

## Previous Finding Dispositions

1. **Same-user credential environment exposure: fixed properly.** `ManagerExecutionBoundary.create` removes inherited Manager bearer variables (`packages/runner/src/runtime/manager-execution-boundary.ts:131-139`), and the credential-bearing `mo` child receives only the non-secret credential-proxy locator (`:517-530`). The Runner-side proxy performs the authenticated request, and the integration test checks the live child environment for both bearer values (`packages/runner/tests/integration/manager-execution-boundary.spec.ts:139-179,301-322`). The previous `/proc` side-channel finding is closed.
2. **Follow-up leases surviving completion: fixed properly for the completion, cancellation, and rejection paths.** The Server revocation endpoint and the runtime-event terminal path revoke the follow-up execution identity (`packages/server/src/Mohist.Server/Api/RunnerRoutes.ManagerExecution.cs:37-54` and `packages/server/src/Mohist.Server/Api/RunnerRoutes.cs:584-590,723-728`). The Runner also revokes on dispatch rejection and invokes revocation from follow-up completion/cancellation cleanup (`packages/server/src/Mohist.Server/Api/AgentSessionFollowupDispatcher.cs:91-107,158-162`; `packages/runner/src/server/followup-handler.ts:435-440`; `packages/runner/src/server/cancel-handler.ts:323-330`). The remaining expiry-recovery gap above is a separate lifecycle requirement.
3. **Follow-up boundaries missing epoch invalidation: fixed properly.** Initial jobs and control-channel follow-ups share `ManagerExecutionRegistry` (`packages/runner/src/runtime/host.ts:201,295-317,790-799`). Poll and heartbeat epoch changes call the shared invalidation path, which aborts Manager jobs and disposes every registered boundary (`packages/runner/src/runtime/host.ts:484-504,868-887`; `packages/runner/src/runtime/manager-execution-lifecycle.ts:16-28`).
4. **OpenCode follow-up cancellation using the shared runtime: fixed properly.** Follow-up entries retain their isolated runtime handle in the registry, and cancellation resolves that entry before falling back to the shared runtime (`packages/runner/src/server/cancel-handler.ts:185-200`). The focused cancellation test proves that the isolated runtime is cancelled, the shared runtime is untouched, the boundary is disposed, and the execution revocation callback is invoked (`packages/runner/src/server/cancel-handler.test.ts:19-66`).

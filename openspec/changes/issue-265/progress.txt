## T-001: Implement rerun-from-stage control action (domain + grain + HTTP API)

### Completed 2026-06-29

### What was done
- Added `RerunFromStage(stageId)` domain method in `WorkflowRun.Failure.cs` with three guards:
  - `unknown_stage` — target stage id not found in run's stages
  - `stage_not_reached` — target stage position strictly ahead of current stage
  - `active_work_in_range` — any non-terminal task or pending/running check in [target..end]
- On success: replaces target with new StageRun (Attempt+1, Running, RequiresApproval preserved), resets later stages to fresh StageRun (Attempt=1, Pending), clears Failure, sets Status=Running, emits [WorkflowRunResumed, StageStarted(target)]
- Created `WorkflowControlRejectionException(Code, Message, Details)` in `Workflow/Domain/` namespace (accessible from domain layer)
- Added `RerunFromStageAsync(stageId)` to `IWorkflowGrain` interface and `WorkflowGrain` implementation — calls `EnsureRun() → _run.RerunFromStage() → ReleaseStageLocksAsync per stage [targetIdx..end] → CommitAsync()`. Rejection exception from domain is wrapped in `InvalidOperationException` with parseable message format
- Added HTTP route `POST /{number:int}/rerun-from-stage` with `RerunFromStageRequest(string? Stage)` DTO. Route validates non-empty stage at the route level, catches wrapped rejection via `TryParseRerunFromStageRejection` (regex-based parser), maps to 400/409. Includes `IsWorkflowRunStateCorruption` self-heal catch for parity with /rerun

### Tests
- **Domain tests** (`RerunFromStageSpecs.cs`): 8 tests covering target/later stage replacement, CurrentStageId/Failure/Status mutation, unknown_stage rejection, stage_not_reached rejection with eligibleStages, active_work_in_range for tasks and checks in range, active task in target itself, clean range success, rerun-from-plan resets all later stages
- **Grain tests** (`RerunFromStageSpecs.cs`): 6 tests covering eager init of target stage in same commit, lazy init of later stages, active task rejection, sequential lock release in range, lock before target NOT released, active task rejection preserves locks and state
- **HTTP integration tests** (`WorkflowRerunFromStageApiSpecs.cs`): 3 tests covering empty stage (400), no workflow run (404), unknown stage (400 with eligibleStages in details)
- **IssueArchivedDetailApiSpecs**: Added `rerun-from-stage` to both [Theory] InlineData sets, with special body handling via switch expression

### Codebase Patterns / Gotchas
- Domain throws `WorkflowControlRejectionException`; grain catches and re-wraps as `InvalidOperationException` with parseable string `"RerunFromStage rejected [{Code}]: {Message}|{Details}"`; HTTP route parses via regex
- WorkflowGrain.cs imports `Mohist.Server.Workflow.Domain` for the exception type
- Sequential stage lock release is idempotent (GetSequentialLockResourceAsync returns null for non-sequential stages, ReleaseAsync ignores unowned locks)
- `CommitAsync → InitializeFreshStagesAsync` eagerly initializes any stage receiving a `StageStarted` event in the same commit
- Runtime variables are stored externally (not on WorkflowRun aggregate), so the domain method naturally preserves them
- Test stub in `RunnerWorkflowStatusRouterSpecs.cs` requires `RerunFromStageAsync` fake implementation

## Why

The point of an autonomous pipeline is that the owner does not have to watch it, yet the issue detail page rebuilds itself every five seconds from a polling timer: scroll position jumps while they read, expanded sections flap, and awareness of an approval wait or a block still arrives late. The live event stream that already powers the Activity view (and already invalidates the page's query caches through `LiveTaskProvider`) is not the page's primary update source — the timeline poll is — so the page never feels live and actively disrupts reading. This change makes the page consume the stream it already receives, so updates land the moment something happens and the reader is never yanked.

## What Changes

- Make the existing live event stream the issue detail page's primary update source: stage transitions, task starts and completions, approval requests, and blocked states are applied incrementally from the same feed the Activity view already consumes.
- Remove the five-second `useWorkflowTimeline` polling as a steady-state driver; retain it only as a reconnect fallback that catches the page up after the events connection drops and reconnects, so no transition is missed when the stream blips.
- Preserve reading stability across every live update: the reader's scroll position does not move, and any section the reader expanded or collapsed keeps its state — an update never rebuilds the content under the reader.
- Raise an attention toast the moment the viewed issue enters an approval-waiting or blocked state while the page is open, so an owner with the tab in the background notices the moments that need them. This inverts the current rule that suppresses these lifecycle toasts for the issue being viewed; cross-issue toasts for other issues remain unchanged.
- Deliver all of the above identically on a phone-width viewport, including the attention toasts.
- No new event types and no server-side event changes — the page consumes the events that already exist. Client-side, the page adds query-invalidation wiring for the task (and artifact) events it already receives but currently drops, using the same mechanism stage/workflow/approval events already use; this is not a server-side event-routing change. Other pages (board, dashboard) keep their current update model.

## Capabilities

- `issue-detail-live-updates`: The issue detail page consumes the existing live event stream as its primary update source, applies workflow transitions (stage, task, approval, blocked) incrementally without a wholesale re-render, preserves the reader's scroll position and the expanded/collapsed state of every section across each update, falls back to timeline polling only on events-connection loss/reconnect (never on a steady-state timer), and behaves identically on phone-width viewports.
- `issue-detail-attention-nudges`: Meaningful transitions on the viewed issue — entering an approval-waiting state and entering a blocked state — raise a toast while the issue detail page is open, so an owner with the tab in the background is nudged at the moments that need them. This is distinct from, and does not change, the global cross-issue toasts (which remain suppressed for the issue currently being viewed to avoid double-noticing). The nudge set is intentionally limited to approval-waiting and blocked, matching the issue's acceptance criteria; a run that fails while the page is open is not toasted for the viewed issue (the failure is shown inline by the decision surface, and the existing global cross-issue toast still covers failed runs on other issues). This scoping is deliberate and recorded here rather than left implicit.

## Impact

- **Web** (`packages/web/src`):
  - Timeline polling: `entities/issue/api/queries.ts` (`useWorkflowTimeline`, the `refetchInterval: 5000` arm) is demoted from a steady-state timer to a reconnect fallback keyed on the events connection status.
  - Event-stream consumption: `app/providers/LiveTaskProvider.tsx`, `app/providers/handle-event.ts`, and `shared/api/events-hub.ts` are the existing ingestion path. The page rides on the targeted query-key invalidations routed there. Stage, workflow-run, issue, and approval events already invalidate the `['issues']` prefix cascade; new client-side ROUTE entries are added for `TaskStarted`/`TaskCompleted`/`TaskFailed` (and `ArtifactRecorded`) — events the client already subscribes to and receives but currently drops without invalidating — so task completions and artifact updates reach the page's queries without a poll.
  - Page composition: `pages/issue-detail/ui/IssueDetailPage.tsx` — ensure live updates re-render only the affected regions (no remounts, stable list keys) so scroll position and local UI state survive.
  - Collapse/expand state: `pages/issue-detail/ui/cards/CollapsibleRailCard.tsx` — confirm local expanded state survives every live update (it already lives in component state; the risk is being keyed away or reset by parent re-renders).
  - Attention nudges: `app/providers/model/run-lifecycle-toast.ts` (`notifyRunLifecycleToast`, `notifyApprovalRequestedToast`) and the approval/blocked routing in `handle-event.ts` — the suppression-by-viewed-issue rule is scoped so the viewed issue still receives its approval/blocked toast while its detail page is open.
  - Existing live-event wiring reused: `entities/issue/model/timeline-events.ts` (`onTimelineEvent`) and `widgets/issue-event-timeline/useEventTimeline.ts` already demonstrate the incremental-apply pattern the page will follow.
- **Server / runner / CLI**: none. No API, DTO, event type, event routing, persistence, or workflow changes; the page consumes the existing event stream and existing projections.
- **Dependencies**: none added.
- **Tests** (`packages/web`): new spec coverage for incremental updates without re-render, scroll-position and collapse-state survival across a live update, polling firing only on reconnect fallback, and attention toasts on the viewed issue for approval-waiting and blocked transitions (desktop and phone-width). Existing `pages/issue-detail/ui/IssueDetailPage.*` tests are updated where the update flow changes; existing `data-testid` anchors are preserved.
- **Risk (medium)**: changes the page's data-update flow from a timer to a subscription and inverts a toast-suppression rule. Mitigated by reusing the existing event-stream ingestion and query-invalidation path unchanged, keeping the polling path as a reconnect fallback, and constraining the toast inversion to the single viewed issue on its detail page.

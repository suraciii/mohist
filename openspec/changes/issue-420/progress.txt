## Codebase Patterns

- `TestTime` (in `eng/TestTime.cs`) is the project-wide frozen clock. Use `TestTime.UtcDateTime`/`TestTime.UtcNow` for any `DateTime`/`DateTimeOffset` instead of `DateTime.UtcNow`; the build fails otherwise (BannedSymbols).
- `IssueReadModelLoader.ApplyProjectionsToSingleAsync(db, model)` is the canonical "wire up workflow + feedback projection for one read model" entry point; it does N workflow queries. The companion `ApplyWorkflowProjectionsBatchAsync(db, models)` (added in T-001) batches workflow projection for a list (no feedback).
- `IssueRow` has STORED computed columns for `Status`, `Title`, `RepositoryName`, `IsArchived`, etc. — all derived from `json_extract(State, ...)`. Filter `IsArchived != true` directly in the WHERE clause.
- `BuildInfo(issue, project, resolvedProfileId)` is the canonical `Domain.Issue → IssueInfo` mapper; pass `project: null` when only the persisted `RepositoryName` is needed and the resolved `RepositoryInfo` is intentionally absent.
- For the `IIssueGrain` create flow, the helper is `CreateAsync(projectId, number, title, body, labels, repositoryName, isDraft)`. Patch parent via `PATCH /api/projects/{p}/issues/{n}` with `{ "parentIssueNumber": N }`. Detach via `{ "parentIssueNumber": null }`.
- `WorkflowRunState` JSON status `"Failed"` (Pascal) becomes the projection's `Health == "blocked"` for child rows.

## T-001: Project current child rows and blocked progress in issue reads

### Decisions

- Refactored `IssueQuerier.EnrichAsync` to replace the old `childCounts` group-by query with `ApplyCompositeChildProjectionAsync`. One project-scoped query against `IssueRow` filters by parent numbers in the current result set, `IsArchived != true`, ordered by `Number` ascending.
- For each child row, deserialize state → `Domain.Issue` → `IssueInfo` via `IssueReadModelLoader.BuildInfo(issue, project: null, resolvedProfileId)`. `RepositoryName` is preserved as the persisted `issue.RepositoryRef`; resolved `Repository`/`RepositoryProblem` are intentionally left null because the compact row doesn't carry them.
- Workflow projection is applied in batch via the new `IssueReadModelLoader.ApplyWorkflowProjectionsBatchAsync` so `Health` reflects the bound workflow state (e.g. workflow `Failed` → child `Health = "blocked"`).
- Group child rows by parent number; both `IssueReadModel.Children` (compact `IssueChildRef[]`) and `ChildIssuesSummary` (with new `BlockedCount`) are derived from the same set in `SummarizeChildren` so they cannot drift.
- Non-parent issues get `Children = []` and `ChildIssuesSummary = null` so the Web UI can treat an empty array as "no children" and a null summary as "not a parent".
- `ChildIssuesSummary.Count` now excludes archived children (was previously the union of all children). This is the behavioral change explicitly required by the spec's "Detaching or archiving a child removes it from the former parent's child rows and totals on the next read" scenario.

### Gotchas

- The existing `Reads_ProjectParentAndChildSummary_AndParentFilter` test happened to seed only non-archived children, so it still passes after the archived-exclusion change. New `Children_ExcludesArchivedChildrenFromRowsAndTotals` pins the new semantics.
- `BlockedCount` uses canonical `Health == "blocked"`, not status — so a child in `inProgress` with a failed workflow run increments `BlockedCount`, matching the spec scenario "parent has four children, two done, one blocked in_progress, one cancelled → 2/4 done, 1 blocked".
- `IssueChildRef.FromReadModel(IssueReadModel)` is the projection helper; downstream code (Web T-002/T-003) should depend on `IssueChildRef`, not on the full `IssueReadModel` for child lists.
- JSON property name on `IssueChildRef.Health` is `health` (matches `IssueReadModel.Health`); other fields use camelCase by default.
- The `$$"""..."""` raw string interpolation conflicts with `}}` literals in JSON; build raw strings via plain concatenation when the JSON contains closing braces.

- `packages/server/src/Mohist.Server/Issue/Services/IssueReadModel.cs` — added `IssueReadModel.Children`.

## T-002: Repository-aware composite issue cards and board filtering

### Decisions

- Extended `Web.Issue` with `repositoryName?: string | null` and `children?: IssueChildRef[]`; `ChildIssuesSummary` gains `blockedCount: number`. These fields arrive additively from the server JSON envelope (server `IssueReadModel.Children` + `ChildIssuesSummary.BlockedCount`); no Web API transform is needed because `request<Issue>` already trusts the server payload shape.
- `BoardQueryState` adds a nullable `repository` field. `parseBoardQuery` reads the `repository` URL parameter, preserving unknown values verbatim (so they keep filtering to no matches and the user can still clear). `serializeBoardQuery` omits the parameter when `null` and emits `repository=<name>` otherwise. Round-trips cleanly with priority/labels/search/sort.
- New `deriveRepositoryOptions(issues)` derives the dropdown options from the existing issue set using `issueRepositoryName(issue)`. This avoids a separate project-repositories fetch and guarantees the filter dropdown never offers a name the user cannot clear against — even on a single-repository project.
- `issueRepositoryName(issue)` prefers `issue.repository?.name` (resolved `RepositoryInfo`) and falls back to `issue.repositoryName` (persisted) so cards and the filter keep working when only the persisted assignment is available (e.g. orphaned repository name).
- `applyBoardFilters` compares exact persisted repository names. The filter applies in the same pipeline as priority/labels/search so cancelled visibility, archive controls, and sort continue to compose.
- `KanbanBoard` exposes a new `RepositoryFilter` selector in both the desktop flex-wrap row and the mobile filter panel behind the existing disclosure. The Clear button removes only the repository filter; priority/labels/search/sort remain. When the URL carries an unknown repository name, the dropdown renders a synthetic `{name} (unknown)` option (so the user sees what's filtering) and the Clear button stays available — never silently falling back to "All repositories".
- `IssueCard` renders a compact repository chip plus, for parents, a `X/Y done` composite progress badge and an independent blocked-child attention indicator. These live in a new `issue-card-metadata-row` between the title and labels, keeping the existing six-dimension top row untouched. The blocked indicator renders `N blocked` whenever `childIssuesSummary.blockedCount > 0` — independent of the parent's own health, and hidden at zero. Cancelled children stay in the denominator (`Y`) without incrementing done.
- Repository availability is derived, not fetched: a single-repository project still shows the chip on every card but the filter does not demand a choice.

### Gotchas

- The existing `kanban-board-filter-reachability.test.tsx` test asserted an exact list of testids in the desktop bar — extended it to include `repository-filter` and seeded `repositoryName` on its makeIssue fixtures so the filter actually renders.
- `IssueCard.test.tsx` was already near the 629-line file-size budget; the new repository + composite tests live in a new sibling `IssueCard.repository-and-composite.test.tsx` so the existing file stays within budget without splitting legacy suites.
- Playwright's `Locator.boundingBox()` returned `null` for the mobile-scoped `panel.getByTestId('mobile-repository-filter')` even though `expect(...).toBeVisible()` and the actual `getBoundingClientRect()` were non-null. Switching the test to a page-rooted locator (`page.locator('[data-testid="mobile-repository-filter"]')`) and reading the rect via `evaluate(...getBoundingClientRect())` made the assertions reliable; the underlying element was always laid out correctly.
- Browser fixture was extended to set `repositoryName` on every makeIssue so the repository dropdown actually has options to show in the new layout tests.
- `deriveRepositoryOptions` intentionally returns `[]` (not throws) when the issue list is empty — `RepositoryFilter` short-circuits to `null` in that case so empty projects render without a stale empty selector.
- T-003 (parent detail rendering) deliberately does NOT touch this card layer; `isCompositeParent` and the navigation surface are derived from the same server projection but live in the detail page slice.

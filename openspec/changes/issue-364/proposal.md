## Why

A full `mo update` ends with a spurious `[warn] Runner identity: GET /api/runner/identity did not respond` even though the runner is healthy moments later (manual `curl` returns 200, `status=online`, `connectionState=connected`, buildGitHash matches repo HEAD). The warning is a false alarm that forces users to chase a non-existent fault. Root cause: `RestoreRunner` only waits for systemd to report the runner process `active`, but that does not mean the runner has finished its WebSocket handshake and registered its identity with the server. The immediately following `VerifyRuntime` stage then calls `RuntimeConsistencyValidator.CheckRunnerIdentityAsync`, which performs a **single** `GET /api/runner/identity` with no retry/poll, reads null, and emits the warn. The same pipeline already contains a correct 30s-timeout + 500ms-poll implementation in `RunnerRefreshVerifier.VerifyRunnerRuntimeAsync` (used by `mo update runner`), but the `VerifyRuntime` layer does not reuse that polling idea. Fix this now because the defect is user-visible on every full update, the blast radius is confined to the CLI validation layer, and the canonical polling pattern already exists in-repo to copy.

## What Changes

- Rework `RuntimeConsistencyValidator.CheckRunnerIdentityAsync` (`packages/cli/Mohist.Cli/Update/RuntimeConsistencyValidator.cs:178`) so that after resolving the source HEAD it **polls** `/api/runner/identity` until a non-null identity snapshot is returned, using a bounded timeout + fixed poll interval — mirroring the readiness semantics already proven in `RunnerRefreshVerifier.VerifyRunnerRuntimeAsync`, reused rather than re-invented. A present snapshot with an empty `buildGitHash` remains the unchanged Warn path.
- Make the timeout and poll interval injectable via constructor parameters (defaults: 30s timeout, 500ms interval, matching `RunnerRefreshVerifier`), and drive all waiting through an injectable `TimeProvider` (default `TimeProvider.System`) following the established CLI convention in `ServiceReadinessProbe`. No wall-clock reads, no `while (now < deadline)` driven by `DateTime.UtcNow`.
- Preserve existing outcomes for the non-timing cases: empty/missing `buildGitHash` → Warn; buildGitHash differing from source HEAD → Warn; source HEAD unresolvable → Warn (skipped). Only the "identity not yet registered" path changes behavior — from immediate Warn to polled wait, and only if the window elapses without an identity does it Warn (so a genuinely broken runner is still surfaced, never masked by an infinite wait).
- Add unit specs covering the three required timing scenarios: (a) identity available immediately → Pass; (b) identity available after N polls → Pass; (c) identity never available within the window → Warn. All driven by fake HTTP + fake `TimeProvider`, no real network or wall-clock.
- No change to `RunnerRefreshVerifier` itself (it works); no change to `RestoreRunner`'s systemd-active gate; no change to server API contract, runner registration, WebSocket handshake, buildGitHash comparison logic, or the `mo update` stage ordering.

## Capabilities

- `runner-identity-verification`: How the `VerifyRuntime` stage of `mo update` verifies the runner's build identity against the repo HEAD after a runner restart. The check must tolerate the registration lag between systemd reporting the runner process `active` and the server actually serving a non-null `/api/runner/identity` payload — it polls with a bounded, injectable timeout/interval until an identity snapshot appears, then compares against source HEAD. A genuinely unavailable identity still surfaces as Warn once the window elapses; the comparison semantics for present-but-mismatched/empty hashes are unchanged. All waiting is driven by an injectable `TimeProvider` so the timing behavior is fully testable without wall-clock.

## Impact

- **CLI implementation** (`packages/cli/Mohist.Cli`):
  - `Update/RuntimeConsistencyValidator.cs` — `CheckRunnerIdentityAsync` gains a poll loop; constructor grows optional `TimeProvider`, timeout, and poll-interval parameters; the existing `TryGetRunnerIdentityAsync` helper is reused as the per-attempt probe.
  - `MohistCliCommands.cs` / `MohistCliCommands.Update.cs` / `Program.cs` — the three `new RuntimeConsistencyValidator(...)` construction sites pick up the new optional dependencies (defaults keep current behavior for non-test callers).
- **CLI tests** (`packages/cli/tests/Mohist.Cli.Tests`):
  - `RuntimeConsistencyValidatorSpecs.cs` — extend `BuildValidator` to thread an injectable `TimeProvider` (fake time, e.g. `FakeTimeProvider`); add the three new specs (immediate / polled / timed-out). Existing identity specs whose handlers answer on the first call remain green unchanged; the one exception is `CheckRunnerIdentityAsync_EndpointUnreachable_ReportsWarn`, whose handler always returns 503 (so `TryGetRunnerIdentityAsync` returns null every call) and therefore now exercises the timeout path — retrofit it with a `FakeTimeProvider` + short timeout (or fold it into the new "never available within window" spec) so it does not block for the full 30s default window.
- **No API / contract / persistence / dependency changes**: `/api/runner/identity` shape and status codes are untouched; runner registration and WebSocket handshake are untouched; `mo update` stage machine and labels are untouched.
- **Risk** (low): change is isolated to one CLI validation method and its construction sites; behavior only shifts from immediate-fail to polled-wait for the single "identity not yet registered" case, with the same terminal Warn preserved on genuine failure.

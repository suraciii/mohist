## T-001 — Relocate `mo status` to `mo project status`

### What landed

- `MohistCliCommands.cs`: deleted the root `BuildStatusCommand` private factory (was at line 219) and the corresponding `root.Subcommands.Add(BuildStatusCommand(api))` registration. `BuildLogsCommand` and `BuildUseCommand` are intentionally **left in place** — they belong to T-002 and T-003 respectively and will be removed by their own tasks.
- `MohistCliCommands.Project.cs`: added `BuildStatus` as a peer of `list`/`create`/`show`/`use`/`delete`/`workflow` under the `project` group. The factory is private static, identical handler shape (`api.PrintGetAsync("/api/status?all=true")`), endpoint string byte-identical to the legacy command.
- `tests/Mohist.Cli.Tests/CliProjectStatusCommandSpecs.cs`: 6 new specs covering the spec scenarios (`project-status/spec.md`) plus the legacy `mo status` non-resolution assertion required by acceptance criteria.

### Codebase patterns

- `Mohist.Cli` is `internal` and exposed to the test assembly via `Properties/AssemblyInfo.cs:InternalsVisibleTo("Mohist.Cli.Tests")`. `MohistCliApi.ServerUnavailableMessage` is `internal const` and is reachable from the spec.
- `RecordingHttpHandler` captures the request **before** calling the responder (see `Support/RecordingHttpHandler.cs:25-36`), so a responder that throws `HttpRequestException` still records the request. The server-unreachable spec asserts on `handler.Requests.Single()` with the legacy endpoint, not `Assert.Empty`.
- `PrintGetAsync` (and `PrintPostAsync` / `PrintPutAsync` / `PrintDeleteAsync`) print `ServerUnavailableMessage` and return 1 when `SendAsync` swallows an `HttpRequestException` (default `printServerUnavailable: true`). The server-unreachable spec asserts on this exact text via `MohistCliApi.ServerUnavailableMessage`.
- For help-rendering assertions on System.CommandLine output, a `Command` without an `Argument` renders as `  <name>   <description>` (no `<arg>` token). A `Command` with an `Argument` renders as `  <name> <arg>   <description>`. The "no positional `project` argument" assertion uses `Assert.DoesNotContain("status <", stdout)` which catches any future regression where someone re-introduces an argument.
- For help-rendering assertions on options, `--project` and `--project-id` are advertised in option tables when present. The spec asserts `Assert.DoesNotContain("--project", stdout)` and `Assert.DoesNotContain("--project-id", stdout)`.
- The legacy `mo status` non-resolution follows the same pattern as `CliWorkflowReads.cs:413-424` (`Status_IsNotARegisteredSubcommand`): System.CommandLine surfaces a parse error, returns non-zero, and no request is issued.

- `dotnet test packages/cli/tests/Mohist.Cli.Tests/Mohist.Cli.Tests.csproj` (full CLI suite) → 797 / 800 passed; 3 failures are pre-existing in `CliReferenceDocsSpecs` (verified by `git stash` + re-run before any change: same 3 failures, all `CliReference_…` asserting on `docs/cli-reference.md` content that T-006 will update). No regressions introduced.
- `dotnet build Mohist.sln -p:SkipWebBuild=true` → 0 warnings, 0 errors. `TreatWarningsAsErrors` is on by default; clean build holds.

### Decisions / notes for later tasks

- I did **not** add the `mo project status` description text to the spec — I left it as `"Show server status across all projects"` (slightly more specific than the legacy `"Show server status"`). The change is purely documentation; behavior is unchanged. If a future task wants the description to match the legacy byte-for-byte, this is the single line to revisit.
- `BuildStatus` is placed between `BuildDelete` and `ProjectWorkflowCommands.Build` in the registration order. System.CommandLine's help renders subcommands in registration order, so `mo project --help` will list `list / create / show / use / delete / status / workflow` — `status` is grouped next to `delete` (both project-management actions) rather than next to `workflow` (the resource subgroup). This matches the alphabetical-ish flow already used in the file.
- The 3 pre-existing `CliReferenceDocsSpecs` failures are in T-006's scope and will be closed by that task's doc-sync step. T-001 deliberately did not touch `docs/cli-reference.md` — that would over-step the T-001 boundary and partially complete T-006.

## T-002 — Relocate `mo logs` to `mo system logs` and reframe system group as application diagnostics

### What landed

- `MohistCliCommands.cs`: deleted the root `BuildLogsCommand` private factory and its `root.Subcommands.Add(BuildLogsCommand(api))` registration (the latter was the first line of the root `Build` body, immediately above `InfoCommands.Build`). `BuildUseCommand` is intentionally **left in place** — it belongs to T-003.
- `MohistCliCommands.System.cs`: added `BuildLogs` as a peer of `BuildInfo` under the `system` group. The factory is private static, identical handler shape (`api.PrintGetAsync("/api/logs/tail")`), endpoint string byte-identical to the legacy command. Also reframed the group description to anchor the application-vs-operational distinction explicitly: "Application diagnostics. 'mo system logs' reports application logs (the Mohist server's own log tail), distinct from 'mo server logs' which reports operational/service-manager logs (systemd journal or scheduled-task output). Distinct from 'mo info', which reports the CLI binary's own local environment and install source."
- `tests/Mohist.Cli.Tests/CliSystemLogsCommandSpecs.cs`: 7 new specs covering the spec scenarios (`system-logs/spec.md`) plus the legacy `mo logs` non-resolution assertion required by acceptance criteria.

### Codebase patterns (carry-over from T-001, reinforced here)

- The legacy `mo logs` non-resolution follows the same pattern as T-001: System.CommandLine surfaces a parse error, returns non-zero, and no HTTP request is issued.
- System.CommandLine's `Command.Description` text is shown verbatim on the parent group's `--help` output (between the parent command name line and the subcommand list). Asserting on the group description with `Assert.Contains("application logs", stdout, StringComparison.OrdinalIgnoreCase)` is reliable; case-insensitive match is needed because System.CommandLine may re-case the description in some terminal contexts.
- The `mo server logs` description lives in `MohistCliCommands.Server.cs:91` ("View server service logs") — the spec assertions on `mo system logs --help` reference "mo server logs" by literal string to pin the application-vs-operational distinction the user will see in help.

### Ordering notes for T-005

- T-002 lands `logs` in the `system` group while `info` is **still** there (T-005 removes `info`). After T-002, `mo system --help` lists both `info` and `logs`; after T-005, only `logs`. This is consistent with design D3 — the group description is reframed around `logs` (application diagnostics) and survives `info` being moved out without further churn. T-005 should NOT touch the group description; it only needs to remove `BuildInfo` from `SystemCommands.Build`.

## T-003 — Remove duplicate root `mo use` so `mo project use` is the single entry

### What landed

- `MohistCliCommands.cs`: deleted the root `BuildUseCommand` private factory and its `root.Subcommands.Add(BuildUseCommand(api))` registration. The surviving `mo project use` factory (`ProjectCommands.BuildUse` at `MohistCliCommands.Project.cs:87-98`) is byte-identical to the deleted factory and continues to share the same `UseProjectAsync` handler — this task is pure deletion, no behavior change on `mo project use`.
- `tests/Mohist.Cli.Tests/CliProjectUseCommandSpecs.cs`: 9 new specs covering every `project-use-single-entry` scenario plus the acceptance criteria that aren't naturally covered elsewhere:
  - `Root_Help_NoLongerListsUseSubcommand`: `mo --help` no longer surfaces the bare `  use ` line. Anchored on `\n  use ` (with surrounding spaces) rather than the bare substring to avoid `repository`/`because` false-positives.
  - `Project_Help_StillListsUseSubcommand`: positive companion — `mo project --help` still lists the surviving `use` entry.
  - `ProjectUse_PostsUseEndpointAndPersistsActiveProjectAndPrintsConfirmation`: happy path — POSTs `/api/projects/<id>/use`, prints `Active project: <name> (<id>)`, persists `activeProjectId` to the local state file.
  - `ProjectUse_IdentifierUrlEscapingProducesExpectedPath`: pins that the URI escape (`Uri.EscapeDataString(identifier)`) lands on the wire as `%20`.
  - `ProjectUse_NoIdentifier_FailsToParseAndExitsNonZero`: missing `<project>` arg is a parse error.
  - `ProjectUse_ServerRejects_LetsLocalStateUnmodifiedAndExitsNonZero`: 404 → exit 4 (`MohistCliApi.FailureExitCode` maps NotFound → 4), state file never written.
  - `ProjectUse_ServerRejection_WithExistingState_LeavesActiveProjectIdUnmodified`: regression guard — a failed `use` must not clobber a previously persisted `activeProjectId`.
  - `ProjectUse_ServerUnreachable_EmitsLegacyGuidanceAndDoesNotModifyState`: `HttpRequestException` → exit 1 + `ServerUnavailableMessage` + no state.
  - `LegacyRootUse_NoLongerResolvesAndExitsNonZero`: D1 verification — `mo use <project>` is no longer a registered subcommand, parse error, no request issued.

### Codebase patterns (carry-over from T-001/T-002, new for T-003)

- The legacy `mo use` non-resolution follows the same pattern as `CliWorkflowReads.cs:413-424` (`Status_IsNotARegisteredSubcommand`) and the T-001 `LegacyRootStatus_NoLongerResolvesAndExitsNonZero` / T-002 `LegacyRootLogs_NoLongerResolvesAndExitsNonZero` specs: System.CommandLine surfaces a parse error, the runner returns non-zero, no HTTP request is issued.
- For help-rendering assertions on System.CommandLine output, the canonical entry row is `  <name>   <description>` — anchored assertions like `\n  use ` and `\n  project ` are reliable across the help blocks. Bare `Assert.Contains("use", stdout)` is unreliable because `use` is a substring of `repository`, `because`, etc. T-001's `CliProjectStatusCommandSpecs.Project_Help_ListsStatusAlongsideOtherVerbs` gets away with `Assert.Contains("use", stdout)` only because it asserts every project verb is listed — the noise is dominated by the legit hits. New top-level help assertions should anchor.
- `CliTestHarness.Create()` writes the project state file to the real `Path.Combine(Environment.GetFolderPath(UserProfile), ".mohist", "cli-state.json")` path on the `FakeFileSystem`. To assert side-effects on the state file, call `fs.Exists(statePath)` and `fs.ReadAllText(statePath)` with the same path the API resolves (`ProjectStatePathOverride` is the entry point but defaults to the same path when unset, which is the harness case).
- `UseProjectAsync` (at `MohistCliApi.cs:878`) writes `{}`-shaped JSON for the empty `new { }` body via `PostDataAsync`. The recording handler captures that as `Body = "{}"`, not empty string — tests that assert "empty body" must match the real byte output.
- `UseProjectAsync` writes `{"activeProjectId":"<id>"}` to the state file (via `JsonObject` round-tripped through `ToJsonString(JsonOptions)`); the spec asserts on substring anchors rather than full-string equality to stay robust against JSON-property-order changes from `System.Text.Json`.
- `MohistCliApi.FailureExitCode(HttpStatusCode.NotFound)` returns `4`, not `1` — server-side NotFound is distinguished from network-unreachable to help scripts distinguish "wrong id" vs "server down". The rejection spec asserts `4` specifically; the unreachable spec asserts `1`. Both are exit-non-zero as the acceptance criteria require.

- `dotnet test packages/cli/tests/Mohist.Cli.Tests/Mohist.Cli.Tests.csproj` (full CLI suite) → 813 / 816 passed; the 3 failures are the same pre-existing `CliReferenceDocsSpecs` failures from T-001 / T-002 (verified by `git stash` + re-run before this change). Net delta: +9 new passing tests, 0 regressions.
- `dotnet build Mohist.sln -p:SkipWebBuild=true` → 0 warnings, 0 errors. Clean build holds.
- `CliProjectStatusCommandSpecs.Project_Help_ListsStatusAlongsideOtherVerbs` still passes — `use` is still listed under `project --help` (which contains the substring `use` six times via `repository`/`because` etc.; T-001's anchor-less assertion is preserved).

### Decisions / notes for later tasks

- The 3 pre-existing `CliReferenceDocsSpecs` failures remain in T-006's scope. T-003 deliberately did not touch `docs/cli-reference.md`.
- The `Body == "{}"` vs `Body == ""` distinction is the kind of detail that bit me mid-test — it's worth recording so future endpoint-relocation specs know to inspect `RecordingHttpHandler.CapturedRequest.Body` against the actual serialized form the handler emits, not against "empty object literal" intuition.
- `Assert.Contains("use", stdout)` for help output is a false-positive trap (`repository`/`because`). T-006's root-shape guard (`CliRootCommandShapeSpecs`) should use anchored assertions like the new T-003 spec does.
- After T-001 / T-002 / T-003 the surviving legacy bare-verb removals are T-004 (`mo notify setup` → `mo notification setup`) and T-005 (`mo system info` → `mo server info`). T-005 will also leave the `system` group as logs-only — same pattern as T-002 leaves it logs+info until T-005 lands.

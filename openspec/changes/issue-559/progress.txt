# progress — issue-559 (Reusable Agent Workflow Action)

## Codebase Patterns

- The handoff fence (`WorkflowAgentHandoffGrain`, keyed
  `workflow-agent-handoff/{token}` by `(projectId, workflowRunId, taskRunId,
  commandId)`) was delivered inert on master. Nothing calls it; extending its
  persisted record shape (new `WorkflowAgentHandoffPlan` fields Id(8)–Id(12),
  `WorkflowAgentHandoffState.Activation` Id(1)) is a compatible edit, not a
  migration.
- Durable step machines follow the `AgentLaunchCoordinatorGrain` template:
  one persisted cursor (`NextStep` + `CommandId`), participant call → probe →
  advance-cursor-and-persist, recovery reminder resumes `AdvanceAsync` from
  `OnActivateAsync` and `ReceiveReminder`, `UnregisterReminder` once terminal.
  The handoff activation mirrors this exactly (steps: PrepareJob →
  EnsureInitialLaunch → SubmitJob; reminder
  `workflow-agent-handoff-activation`, 1s/1s).
- Participant probe seam: `IWorkflowAgentHandoffParticipantProbe` (production
  default `NoopWorkflowAgentHandoffParticipantProbe.Instance`, registered in
  `MohistServiceRegistration` via TryAddSingleton). Test probe lives in
  Mohist.Server.TestSupport (`WorkflowAgentHandoffParticipantProbe` with
  `FailNext(gate)/StopFailing/ClearObservations/ParticipantIds`). The probe is
  invoked after the participant grain call returns and BEFORE the cursor
  advances — a throw simulates lost acknowledgement with the participant write
  durable.
- Arch rule `DomainModules_ShouldNotDependOnEachOther`
  (Mohist.Server.ArchTests/ArchitectureRules.cs) forbids cross-domain edges;
  `("Workflow", "Agent")` was added to `AllowedDomainDependencies` for the
  handoff process manager driving Agent's manual-launch entry points (design
  D1/D3). `("Workflow", "Sessions")` was already allowed (lineage labels).
  When adding a cross-domain call, update this list with a rationale comment.
- SpecTest filtering: MTP runner does NOT accept `--filter`; use the exe
  directly: `./Mohist.Server.SpecTests -class "<fqcn>"` from the bin dir.
- `AgentJobGrain.PrepareManualLaunchAsync` requires caller-minted
  SessionId/InputId/TurnId + AgentId; `PlansEquivalent` replays return the
  stored input, conflicting plans throw. `SubmitPreparedLaunchAsync` flows
  into `TryAdmitAsync` (shared admission). Launch stays `Visible` when
  `AgentSessionStartup?.ParentSessionId` is null (handoff passes no startup
  context).
- `IAgentExecutionSnapshotResolver.ResolveSnapshotAsync` (new) returns
  `AgentExecutionSnapshot(AgentId, AgentName, Definition)` from one read so a
  frozen plan never mixes old identity with new definition;
  `ResolveAsync` delegates to it.
- Flaky: `AgentSessionLaunchRuntimeResolutionSpecs.Launch_WithoutRuntimeOverride_UsesAgentConfigRuntime`
  polls once and can miss the dispatch under full-suite load; passes in
  isolation and on full-suite re-runs. Not related to this change.

## T-001 decisions / gotchas

- Fingerprint (`WorkflowAgentHandoffCodec.Fingerprint`) covers all 9 command
  fields including the new `Expect` — the only caller-rendered added fact.
  AgentId/AgentName/workspace are resolved server-side (frozen in the plan,
  covered by replay specs), not fingerprinted.
- `WorkflowAgentHandoffRunContext.Workspace`: `issue-{n}` named workspace for
  issue-linked runs (mirrors the inline dispatch renderer), else the run's
  free-form workspace path/branch, else null. Resolved once at first preflight
  via `IWorkflowRunStore`; never re-read.
- Session metadata labels at materialization:
  `WorkflowAgentSessionMetadata.Labels` (project/run/session-name/source=
  workflow/work id/work type/task lineage) + `GenericAgentSessionMetadata`
  AgentId/AgentName/Workspace* + new `AgentSessionQueryMetadataKeys.TaskRunId`
  (`mohist.io/task-run-id`) and `.InvocationId`
  (`mohist.io/agent-invocation-id`). `JobId` label comes from the
  EnsureInitialLaunchCommand job id.
- `AgentJobWorkflowInvocation(InvocationId, TaskRunId, WorkId)` discriminator:
  Id(25) on both `PrepareManualLaunchCommand` (after new Id(24) Skills) and
  `AgentJobInput`. Carried only — no admission/execution branch reads it
  (verified by grep). T-003's terminal staging will be its first reader.
  `PrepareManualLaunchCommand.Skills` (Id 24) carries the frozen definition's
  Skills into the existing `AgentJobInput.Skills` (Id 13) for dispatch.
- Activation idempotency mechanics: `SubmitJobAsync` persists
  `Disposition=Activated` + `Activation.CompletedAt` in ONE WriteStateAsync so
  a replay of ActivateAsync is a pure no-op. Probe failures surface to the
  caller as `WorkflowAgentHandoffActivationPendingException`; recovery replays
  the idempotent participant command under the same minted ids.
- Recovery specs simulate crash via `handoff.AsReference<IGrainManagementExtension>().DeactivateOnIdle()`
  then retry `ActivateAsync` — `OnActivateAsync` resumes the persisted cursor.
- TestSupport gained `WorkflowAgentHandoffParticipantProbe`; the handoff spec
  fixture RemoveAll's the noop registration and adds the faulting probe
  singleton.
- Inert: no production caller of Prepare/Accept/Activate yet — the translator
  cutover is T-005.
- `TimeoutMilliseconds` stays frozen on the command only; the AgentJobInput
  deadline + ArmJobTimeout honoring is T-002 (D4).

## T-002 decisions / gotchas

- Per-invocation deadline: `AgentJobInput.TimeoutMilliseconds` (Id 26) and
  `Expect` (Id 27) were added to both `PrepareManualLaunchCommand` and
  `AgentJobInput` (append-only ids after `WorkflowInvocation` Id 25).
  `AgentJobGrain.EffectiveJobTimeout()` = positive `Input.TimeoutMilliseconds`
  else `AgentJobOptions.JobTimeout`; used by `ArmJobTimeout`,
  `JobTimeoutExceeded`, and the report-timeout reason message. Direct/routed
  launches never carry the fields → global backstop unchanged.
- Omitted `timeout` resolves to `WorkflowAgentHandoffDeadline.DefaultTimeoutMilliseconds`
  (3_600_000, the runner's inline action default from
  `packages/runner/src/actions/built-ins.ts`) at the handoff's
  `ManualLaunchCommandFor` render — resolving open question O2 to the action
  default. The frozen command keeps the raw null; render is deterministic.
- Dispatch lineage: `BuildDispatchAsync` sets `WorkflowRunId` from
  `input.WorkflowRunId` ONLY when the `WorkflowInvocation` discriminator is
  present (direct/mention/routed launches keep `string.Empty` — the
  `AgentSessionLaunchValidationRoutesSpecs` regression locks that), plus
  `TaskRunId: input.WorkflowInvocation?.TaskRunId` and `Expect: input.Expect`.
  Runner wire already parses `expect`/`taskRunId` on agent-job dispatches;
  T-003's executor evaluation is their first runner consumer.
- `PlansEquivalent`/`EquivalentInput` now compare TimeoutMilliseconds/Expect
  (and the discriminator on `EquivalentInput`) so a conflicting re-render is a
  conflict, not a silent accept.
- **Pre-existing deadlock fixed in `AgentConcurrencyGrain` (required for the
  "shared gate, later admitted" acceptance)**: the gate delivered
  permit-grant notifications INLINE from its own turn; a granted AgentJob
  owner (`ConcurrencyPermitGrantedAsync` → `TryAdmitAsync`) re-enters the
  gate (`AcquireAsync`/`MarkDispatchedAsync`), queueing behind the delivery
  call → 30s response-timeout deadlock for every release-with-job-waiter
  (release from `ReportResultAsync`, client `ReleaseAsync`, even the
  reconciliation reminder). No prior spec exercised a real job waiter (the
  followup owner never calls back into the gate; existing gate specs used
  fake owner ids). Fix: `SchedulePendingNotificationDelivery()` fire-and-forgets
  `ProcessPendingNotificationsAsync` — the task starts on the gate context,
  suspends at the first owner call, continuation (durable notification
  removal) resumes on the gate context; all state mutations stay serialized.
  Failed delivery keeps the notification; reminder re-drains.
- Because delivery is now deferred, `AgentSessionFollowupConcurrencySpecs.
  GateGrant_NotificationFailure_RetainsPermitAndDurableRetryRecord` now polls
  (TestWait) for the recorded attempt instead of asserting synchronously.
- Workflow-originated admission specs live in
  `Specs/Agent/Grain/WorkflowAgentJobAdmissionSpecs.cs` on the
  `AgentJobGrainFixture` (has runners + FakeTimeProvider); they drive jobs
  through `PrepareManualLaunchAsync`+`SubmitPreparedLaunchAsync` with the
  discriminator — the exact participant shape activation produces.
- WaitingReason is only on `AgentJobState` (no grain getter): specs read it
  by deserializing the ledger row's StateJson via `IAgentJobStore`.
- Grain timers ARE driven by the fixture FakeTimeProvider (Orleans 10 timers
  use the registered TimeProvider), so advancing fake time fires
  ArmJobTimeout's timer; specs still call `CheckTimeoutsAsync` for
  determinism.

## T-003 decisions / gotchas

- `PendingWorkflowTerminalDelivery` is `AgentJobState` Id(34), staged by
  `EnterTerminalStateAsync` (via `StageWorkflowTerminalDelivery`) ONLY when
  `State.Input?.WorkflowInvocation` is non-null AND the status is a real
  terminal (Completed/Failed/Cancelled — Unknown never stages). Direct and
  routed-shaped launches (WorkflowRunId WITHOUT the discriminator) stage
  nothing; grain spec covers both.
- Event type `com.mohist.agent.job.workflow-terminal` (EventCatalog.ReverseDns
  + `All` list), source `/mohist/agent-job/{jobKey}` (agent-job store dedups
  on (source, eventId)), stable id `workflow-terminal:{jobKey}` via
  `AgentJobSessionDeliveryIds.WorkflowTerminalEventId`. Envelope built by
  `AgentJobLineage.BuildWorkflowTerminalEnvelope` + grain-side
  `BuildWorkflowTerminalEnvelope` (AgentJob producer conformance: agentid
  required; projectid/workflowrunid lineage stamped like the failure event).
- Typed payload: invocation identity (invocationId/projectId/workflowRunId/
  taskRunId/workId + jobId/sessionId/inputId/turnId), terminal facts (status,
  message, output as parsed element, failureReason, failureCategory, exitCode,
  artifactUploadIds), `evaluation` object, `recordedAt`. NOTE: `JSON.Options`
  uses `JsonIgnoreCondition.WhenWritingNull` — null facts (failureReason on a
  completed job, matched on unsatisfied) are OMITTED, specs must use
  TryGetProperty/absence, not ValueKind.Null.
- Evaluation transport (D6): the runner's `AgentJobExecutor` evaluates
  `work.expect` (already parsed from `WorkDispatch.Expect` since T-002) after
  the turn settles via `evaluateCompletion(work.expect, workDir, output.text)`
  — only for completed turns with a non-empty object expect — and embeds the
  typed evaluation under `output.expectation` (satisfied/matched/missingFiles/
  missingMarkers/failIfMatches/message). The AgentJob verdict stays
  `completed` even when unsatisfied. Server side,
  `AgentJobCompletionEvaluationCodec.Parse(outputJson)` lifts `expectation`
  into the typed record at staging time.
- Emission plumbing mirrors `PendingSubagentTerminalEvent` exactly: emit from
  OnActivateAsync (terminal branch), ReportResultAsync (stale branch),
  EnterTerminalStateAsync (replay + fresh), ReceiveReminder (terminal branch);
  include the obligation in every "pending exists"/unregister-condition check
  (`ClearPendingSessionCloseAndMaybeReminderAsync` too). On append failure:
  log + `EnsureRecoveryReminderAsync`, obligation retained; reminder/reactivation
  retries; success clears + persists (exactly once).
- New grain specs: `AgentJobWorkflowTerminalDeliverySpecs` (AgentJobGrain
  fixture) — typed payload/stable id, discriminator gating (direct +
  routed-shaped), append-failure → retained → reactivation emits once with the
  SAME frozen RecordedAt, duplicate stale report + late FailAsync → no second
  append/terminal unchanged, failed-terminal facts + unsatisfied evaluation,
  Unknown does not stage, and "workflow-run event source stays silent" (agent
  terminal never rides the Workflow report channel).
- Runner tests: `agent-job-executor.spec.ts` new describe (6 tests: satisfied
  evaluation with promise marker, unsatisfied keeps verdict completed, missing
  markers typed, no-expect untouched, failed turn untouched) +
  `server-connection-report.spec.ts` lock (agent-job report body has
  ownerKind/agentJobId and NO workflowRunId).
- Spec gotcha: `AgentJobGrainFixture` shares ONE RecordingEventStore across the
  collection — global `Assert.DoesNotContain(Type == workflow-terminal)` saw
  another spec's event under full-suite ordering; scope absence assertions by
  source. (Fixed mid-run; full suite green.)
- Path stays dark: only discriminator-carrying jobs stage the obligation, and
  only the (inert, T-005) handoff activation creates those. The consuming
  finalizer handler is T-004.

# progress — issue-559 (Reusable Agent Workflow Action)

## Codebase Patterns

- The handoff fence (`WorkflowAgentHandoffGrain`, keyed
  `workflow-agent-handoff/{token}` by `(projectId, workflowRunId, taskRunId,
  commandId)`) was delivered inert on master. Nothing calls it; extending its
  persisted record shape (new `WorkflowAgentHandoffPlan` fields Id(8)–Id(12),
  `WorkflowAgentHandoffState.Activation` Id(1)) is a compatible edit, not a
  migration.
- Durable step machines follow the `AgentLaunchCoordinatorGrain` template:
  one persisted cursor (`NextStep` + `CommandId`), participant call → probe →
  advance-cursor-and-persist, recovery reminder resumes `AdvanceAsync` from
  `OnActivateAsync` and `ReceiveReminder`, `UnregisterReminder` once terminal.
  The handoff activation mirrors this exactly (steps: PrepareJob →
  EnsureInitialLaunch → SubmitJob; reminder
  `workflow-agent-handoff-activation`, 1s/1s).
- Participant probe seam: `IWorkflowAgentHandoffParticipantProbe` (production
  default `NoopWorkflowAgentHandoffParticipantProbe.Instance`, registered in
  `MohistServiceRegistration` via TryAddSingleton). Test probe lives in
  Mohist.Server.TestSupport (`WorkflowAgentHandoffParticipantProbe` with
  `FailNext(gate)/StopFailing/ClearObservations/ParticipantIds`). The probe is
  invoked after the participant grain call returns and BEFORE the cursor
  advances — a throw simulates lost acknowledgement with the participant write
  durable.
- Arch rule `DomainModules_ShouldNotDependOnEachOther`
  (Mohist.Server.ArchTests/ArchitectureRules.cs) forbids cross-domain edges;
  `("Workflow", "Agent")` was added to `AllowedDomainDependencies` for the
  handoff process manager driving Agent's manual-launch entry points (design
  D1/D3). `("Workflow", "Sessions")` was already allowed (lineage labels).
  When adding a cross-domain call, update this list with a rationale comment.
- SpecTest filtering: MTP runner does NOT accept `--filter`; use the exe
  directly: `./Mohist.Server.SpecTests -class "<fqcn>"` from the bin dir.
- `AgentJobGrain.PrepareManualLaunchAsync` requires caller-minted
  SessionId/InputId/TurnId + AgentId; `PlansEquivalent` replays return the
  stored input, conflicting plans throw. `SubmitPreparedLaunchAsync` flows
  into `TryAdmitAsync` (shared admission). Launch stays `Visible` when
  `AgentSessionStartup?.ParentSessionId` is null (handoff passes no startup
  context).
- `IAgentExecutionSnapshotResolver.ResolveSnapshotAsync` (new) returns
  `AgentExecutionSnapshot(AgentId, AgentName, Definition)` from one read so a
  frozen plan never mixes old identity with new definition;
  `ResolveAsync` delegates to it.
- Flaky: `AgentSessionLaunchRuntimeResolutionSpecs.Launch_WithoutRuntimeOverride_UsesAgentConfigRuntime`
  polls once and can miss the dispatch under full-suite load; passes in
  isolation and on full-suite re-runs. Not related to this change.

## T-004 decisions / gotchas

- `WorkflowGrain.SettleAgentInvocationAsync` owns the terminal decision and
  keeps the AgentJob execution verdict separate from Workflow task outcome.
  It freezes the typed terminal on `TaskRun.AgentInvocationSettlement`, then
  resumes artifact binding, setVars projection, and domain report settlement
  from durable per-effect flags. Successful terminal facts project the inline
  agent-turn promise output; unsatisfied expectations use the inline
  `expectation-failed` code and message.
- First-delivery eligibility uses `WorkflowRun.FindReportableWork` with the
  persisted `(taskRunId, workId, workflow worker)` tuple. A task that is
  terminal, stopped, deleted, or owned by another attempt is acknowledged as
  stale before any artifact, variable, or outcome side effect.
- AgentJob execution failures and unsatisfied expectations may use the normal
  recovery matcher/budget path. Finalizer-side artifact binding and setVars
  extraction/patch failures do not enter recovery, matching the inline
  executor's ordering; they fail with the existing task messages.
- The setVars patch is value-idempotent across a crash between the external
  variable-store write and the receipt flag persistence: reconciliation reads
  the current bundle and skips a patch whose requested values are already
  present. Artifact binding already has upload-id replay protection.
- The finalizer owns a one-second `workflow-agent-invocation-settlement`
  reminder, reconciles on activation and reminder ticks, and tolerates direct
  contract-test grains without an Orleans reminder registry during cleanup.
  `StopAsync` calls the linked AgentJob `CancelAsync` before applying existing
  Workflow stop semantics. Binding a real `mohist/agent` task clears the
  inline `AgentResultSettlement` so the handoff has no second result channel.
- The workflow-terminal subscription is explicitly registered in the spec
  event dispatcher and covered for direct delivery, duplicate/dead-letter
  redelivery, stale terminals, failed recovery, stop cancellation, and
  interruption after receipt/artifact/setVars boundaries. Interruption resumes
  from recorded flags and applies each task effect once.

## T-005 decisions / gotchas

- `WorkflowItemTranslator.TranslateToDispatchAsync` now returns a discriminated
  result: ordinary Tasks/Checks still produce a `WorkDispatch`, while new
  `mohist/agent` tasks produce a `Delegated` invocation. The translator renders
  only the persisted TaskRun `with` fields (`name`, `prompt`, `session`, and
  `timeout`) plus the frozen task-level `expect` into the handoff command.
- `WorkflowAgentHandoffDispatchClient` performs Prepare -> Accept -> Activate
  and persists the immutable `AgentInvocationLink` before activation. This
  ordering is required for one-slot runners: AgentJob admission reads the
  runtime view while selecting a slot, so the Workflow task must already be
  agent-owned or it double-counts the handoff and leaves the job unassigned.
  DispatchService retains an idempotent post-activation bind/cancel fallback
  for replay and stop races.
- Delegated tasks do not write a Workflow dispatch snapshot. DispatchService
  skips their Workflow redelivery and the Runner runtime view/slot count skips
  linked tasks; the AgentJob ledger is the sole active owner after claim.
- Test silo wiring must register the real handoff client, snapshot resolver,
  preflight adapter, and the no-op participant probe. The cutover Server spec
  verifies activation, reciprocal session labels, AgentJob-owner claim,
  expectation/artifact/setVars finalization, and no duplicate Workflow work.
- Named-session O1 is resolved as per-attempt lineage: `session` is persisted
  as the logical label (defaulting to the work id), while each attempt keeps
  its own minted AgentSession/Input/Turn ids and does not continue a prior
  invocation.

## T-006 decisions / gotchas

- `AgentInvocationStatusProjection` is derived from the authoritative AgentJob
  runtime snapshot plus the durable Workflow settlement/recovery facts:
  Pending -> `queued`, Running/Unknown -> `executing`, terminal AgentJob states
  retain their terminal values, and an unsettled failed terminal with remaining
  recovery budget is exposed as `recovering`. No status mirror is persisted.

  Turn ids. Terminal result facts are read from the AgentJob terminal record,
  never reconstructed from Session transcript content. AgentJob and AgentSession
  read models expose reciprocal WorkflowRun/TaskRun/work/invocation lineage.

  job-linked input/turn records. Direct and routed Agent launches remain
  unlinked, and existing table/CLI shapes retain their compact columns; JSON
  read output carries the optional lineage fields.

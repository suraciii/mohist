## T-001 progress notes

### Codebase Patterns

- Per-source Id (`MAX(Id)+1`) on SQLite has been implemented in two places
  (`EventStore.NextWorkflowIdAsync`, `NextIssueIdAsync`, `NextEpicIdAsync`).
  All three currently open their own `DbContext` to query `MAX`. The new
  scoped overload (`AppendAsync(MohistDbContext db, ...)`) takes the
  caller's `DbContext` directly so the per-source Id sequence is correct
  for events appended inside the same transaction.

- Routing for the source prefix in `EventStore.AppendAsync` is a chain of
  `StartsWith(SourcePrefix)` checks (`Issue`, `Epic`, with
  `WorkflowRun` as the implicit default). The implicit default
  misroutes `/mohist/agent-session/` to `WorkflowRunEvents` today —
  T-001 adds an explicit agent-session branch before the workflow
  default so the misrouting is gone.

- All event-row tables (`WorkflowRunEventRow`, `IssueEventRow`,
  `EpicEventRow`) share the same column shape (Id + Source composite
  PK, EventId, Type, Time, SpecVersion, Subject, DataContentType, Data,
  ExtensionsJson, DispatchedAt). T-001 introduces `IEventRow` to
  express the shared shape (`Id`, `Source`) so the per-source MAX
  helper can be one generic method (`NextIdAsync<T>`) instead of four
  copies.

- `MohistDbContext.OnModelCreating` mirrors each event-row table with
  the same configuration block. The new `AgentSessionEventRow`
  configuration mirrors `EpicEventRow` exactly (Type/Source/Id index +
  partial `IX_AgentSessionEvents_Undelivered`). The earlier
  `EventDeliveryProgressAndDeadLetters` migration already added
  `DispatchedAt` columns to the existing tables; the new
  `AddAgentSessionEvents` migration only creates the table + indexes
  (no backfill, no `UPDATE` statements) — same pattern as
  `AddEpicEvents`.

- `IEventStore` fakes are spread across `Support/` (top-level:
  `NoopEventStore`, `RecordingEventStore`) and inside individual spec
  files (`InboxProjectionTestSupport.NoopEventStore`,
  `EpicEventPublishSpecs.ThrowingEventStore`). All four fakes were
  updated to implement the new scoped overload.

- Producer-side touches are intentionally zero. T-001 owns ALL
  `IEventStore` / `EventStore` changes; downstream tasks (T-003, T-004,
  T-005) only call the new scoped overload from their respective
  stores. `WorkflowRunStore`, `IssueStore`, `AgentSessionStore`,
  `InMemoryEventBus` were not modified.

### Gotchas

- EF Core's `DbSet<T>.Local` returns a `LocalView<T>` that exposes
  Added/Unchanged/Modified entities for the set. The next
  `MAX(Id)+1` call after `db.<Set>.Add(...)` therefore sees the
  pending row immediately, which is what makes the per-source Id
  sequence correct for multiple events appended in one transaction.
  Tests verify this with three consecutive `AppendAsync` calls in a
  single `BeginTransactionAsync` block yielding Id 1, 2, 3.

- `MarkDispatchedAsync` is intentionally NOT updated to use the
  shared DbContext — it still owns its own DbContext + transaction
  because the dispatcher (step 3, future issue) runs outside any
  producer's state transaction.

- The `AppendAsync(CloudEvent)` non-scoped overload now opens a
  transaction even though SQLite + a single-statement write would not
  technically need one. This preserves the same observable behavior
  for existing callers (e.g. `InboxProjectionHandler` hint path) and
  keeps the entry point a single SaveChanges boundary.

- The migration was generated with `dotnet ef migrations add
  AddAgentSessionEvents` and the resulting
  `20260708053533_AddAgentSessionEvents.cs` matches the expected
  schema (table + `IX_AgentSessionEvents_Undelivered` partial index,
  no `IX_AgentSessionEvents_Type_Time` since lifecycle events are not
  timeline-queried the way workflow/issue events are).

- `EnsureCreated` produces a different partial-index SQL than
  `Migrate()` on SQLite (the older `EventStoreDeliveryProgressSpecs`
  test confirms this). The new
  `AgentSessionEventsMigrationSpecs` uses `Migrate()` so the
  DDL matches production.

- The scoped overload must NOT call `SaveChangesAsync`; the producer's
  transaction owns the commit. Verified by spec
  `AppendAsync_DoesNotCallSaveChangesAsync_OnScopedOverload` which
  asserts that after `AppendAsync(db, evt)`, the row is in
  `db.WorkflowRunEvents.Local` with state `Added` while
  `db.WorkflowRunEvents.AsNoTracking().ToList()` returns nothing.

### Open follow-ups for downstream tasks

- T-002 (IEventPublisher write-only) needs to inject `IEventStore`
  into `InMemoryEventBus` and replace the in-publish dispatch loop
  with a delegated `IEventStore.AppendAsync(envelope)` call. The
  scoped overload is not needed for `IEventPublisher` because the
  inbox hint is written outside any producer's state transaction.

- T-003 / T-004 / T-005 should call `_eventStore.AppendAsync(db,
  envelope, ct)` inside their existing `BeginTransactionAsync`
  blocks; identity stamping (projectid, issueid, issueno, session
  id) is owned by the producer tasks, not T-001.

## T-002 progress notes

### Codebase Patterns

- `InMemoryEventBus` is registered as a singleton (see
  `CloudEventBusServiceCollectionExtensions.AddCloudEventBus`),
  so its `IEventStore` constructor dependency must also be a
  singleton — T-002 promotes `IEventStore` registration in both
  `MohistServiceRegistration` and `MohistSiloRegistration` from
  `AddScoped` to `AddSingleton`. `EventStore` only depends on
  `IDbContextFactory<MohistDbContext>` + `ILogger<>`, so singleton
  lifetime is safe; each call still gets its own short-lived
  `MohistDbContext` from the factory.

- `IEventPublisher` interface signature is unchanged by T-002
  (the same two `PublishAsync` overloads). The change is
  semantic inside `InMemoryEventBus`: synchronous handler
  fan-out is removed; both overloads now delegate to
  `IEventStore.AppendAsync(CloudEvent)` (the non-scoped
  overload). All existing fakes (e.g.
  `RecordingIEventPublisher`) keep compiling.

- Subscriptions (`_subscriptions` + `AddSubscription`) remain
  on the bus instance for the future dispatcher. `AddSubscription`
  is now only used by spec files that build the bus empty and
  wire handlers post-construction; production DI still feeds
  subscriptions through the second constructor (the
  `IEnumerable<Subscription>` overload registered by
  `AddCloudEventHandlersFromAssembly`).

- Specs that previously asserted on captured publishes (bus
  fan-out) had to be rewritten to assert on persisted event
  rows via the new `RecordingEventStore.Appended` accessor.
  The accessor is a public read-only view over the in-memory
  recorded envelopes, exposing the `RecordedEnvelope` record
  type so callers can inspect `Envelope.Type` / `Source` /
  `Subject` / `Data` / `Extensions` directly.

- `EventBridge` specs no longer exercise the bus at all — the
  bus would now just persist a row, not drive the bridge. The
  specs build a `CloudEvent` and call `bridge.HandleAsync(...)`
  directly, matching the path the future dispatcher will take.
  `ProjectIsolationIntegrationSpecs` follows the same pattern.

- Specs whose end-to-end behavior depended on synchronous
  bus dispatch (e.g. `IssueWorkflowProductLoopSpecs` completing
  an issue after a `WorkflowRunCompleted` publish,
  `StageLockSpecs` releasing sequential locks after
  `StageFailed` / `StageCompleted`,
  `RunnerWorkflowTerminalStatusHandlerSpecs` pushing
  `ReceiveWorkflowRunStatus`) were rewritten to replay the
  persisted row through the handler/router that the future
  dispatcher will use. Each spec uses
  `TestWait.ForAsync` to wait for the row to land in
  `IEventStore.ListAsync(...)` before driving the handler.

### Gotchas

- After T-002 the bus is write-only, but the three producers
  still call *both* `_eventStore.AppendAsync(...)` and
  `_eventPublisher.PublishAsync(...)` (the post-commit loops
  in `WorkflowRunStore`, `IssueGrain.PublishIssueEventsAsync`,
  `AgentSessionGrain.PublishAgentSessionLifecycleAsync`).
  Since `IEventPublisher.PublishAsync` now also appends to
  `IEventStore`, each event ends up persisted **twice** in
  the interim (T-003 / T-004 / T-005 will collapse this to
  one row per event by moving writes into the state
  transaction and dropping the publish call). Specs that
  count rows use `Assert.NotEmpty` + `Assert.Contains`
  instead of `Assert.Single`; see the
  `WorkflowRunStoreEvent_PersistsRowButDoesNotSyncProjectToInbox`
  and `CreateIssue_PersistsCreatedEventToIssueEvents`
  tests for the exact phrasing.

- `IEventStore` singleton promotion interacts with
  `MohistDbFixture` and the various grain fixtures that build
  their own `InMemoryEventBus` instance: each one had to
  pass an `IEventStore` (typically `new NoopEventStore()` or
  a shared `new RecordingEventStore()`) to the bus
  constructor. NoopEventStore is fine because the bus only
  needs a working `AppendAsync(CloudEvent)` — the scoped
  overload is unused here.

- The original `InMemoryEventBus(ILogger)` constructor was
  removed; callers (test fixtures, DI extensions) must now
  pass an `IEventStore`. The single-arg overload is no
  longer needed because the bus is never constructed without
  its event-store dependency after the write-only
  convergence.

- The DI cycle worry called out in the `InboxProjectionHandler`
  comment ("`IEventPublisher` resolves to the `InMemoryEventBus`
  singleton whose constructor enumerates all handler
  subscriptions") no longer applies once T-002 lands: the
  bus no longer takes `IEnumerable<Subscription>` as a
  hard constructor dependency for the singleton path (the
  subscription enumeration moves to a separate `AddSingleton`
  registration in `AddCloudEventHandlersFromAssembly`).
  However, the cycle is still latent because the bus
  constructor can still resolve subscriptions transitively
  through `IEventStore` (which has no such dependency) — so
  the existing scope-resolved `IEventPublisher` pattern in
  the handler is left in place to be safe.

## T-003 progress notes

### Codebase Patterns

- `WorkflowRunStore.SaveAsync(run, events)` is the canonical reference
  switch. It is the only producer that actually stamped identity before
  T-003, and it is the only one whose `issueid` reading is a pure
  metadata lookup (the issue binding lives on the run's
  `Annotations["issueId"]` because `IssueGrain` populates it at workflow
  start time — `IssueGrain.cs:230`). The pattern is: read
  `projectId`/`issueId` from the same `Metadata.Annotations` dictionary,
  pass both into `ToCloudEvent`, stamp conditionally
  (`string.IsNullOrWhiteSpace` guard) so a phantom `issueid` is never
  emitted on an unbound run.

- `WorkflowRunStore` no longer takes an `IEventPublisher` dependency at
  all — the constructor signature is `(IDbContextFactory, IEventStore)`
  and DI no longer wires one in. Test fakes
  (`CapturingEventPublisher`) and call sites
  (`InboxProjectionTestSupport`, `InboxProjectionHandlerSpecs`,
  `WorkflowRunStoreSpecs`) had to be updated in lockstep.

- `WorkflowRunStoreSpecs` re-asserts on persisted rows via
  `IEventStore.ListAsync(runId)` instead of on captured publishes. This
  is the only correct assertion after T-003 because there is no
  publisher fan-out to capture — the assertion target is the event
  store, which is what consumers will read.

- The new `TransactionalEventAppendSpecs` file uses a hand-rolled
  `IDbContextFactory<MohistDbContext>` (private `Factory` class) over a
  shared in-memory SQLite connection (the `_keeper` connection pattern
  from T-001's `AgentSessionEventsMigrationSpecs`). The
  `ThrowingEventStore` private fake throws on the second
  `AppendAsync(db, envelope)` call to simulate a mid-transaction event
  write failure — this is the canonical way to express the
  "rollback on event write failure" assertion in this test file
  because it lives in the producer's transaction, not in
  `MarkDispatchedAsync`.

### Gotchas

- `IssueWorkflowCompletionHandler` now reads `issueid` from
  `evt.Extensions` and stops resolving `IssueQuerier` through a scoped
  `IServiceScopeFactory`. Two follow-on consequences:

  - `IssueQuerier` is no longer in the handler's constructor
    dependencies. The handler's only remaining collaborators are

    `HandleAsync_NoIssueIdExtension_NoOpsAndDoesNotInvokeGrain` — the
    "no in-progress issue bound" case is now expressed as "the event
    has no `issueid` extension" because that is what the new code
    path actually checks.

- The handler's idempotency story is unchanged in spirit but shifted
  in mechanism: it now relies on the `Issue.Complete` aggregate guard
  (which rejects duplicate transitions on a non-`InProgress` issue)
  instead of relying on the scoped reverse lookup filtering to
  `in_progress`. Specs that previously asserted on a single grain
  call after a duplicate delivery now assert on two calls + a no-op
  transition. This is a meaningful semantic shift for
  `IssueWorkflowCompletionHandler` — read both the new spec and the
  modified one before reasoning about the change.

- The `RunnerWorkflowTerminalStatusHandler` and
  `WorkflowStageLockReleaseHandler` doc-comments were updated to
  reflect the dormant state until the dispatcher lands (step 3). The
  handler bodies are unchanged — the comment update is to flag for
  future maintainers that synchronous dispatch is no longer the
  trigger path. No tests changed for these handlers.

- `InboxProjectionHandler` still resolves `IEventPublisher` through a
  scope to publish the `com.mohist.inbox.item-persisted` hint. After
  T-003 (and T-002) the resolved publisher no longer fans out — it
  only appends a row. The hint is now durable; whether that is the
  right long-term home is design OQ4. The handler's own
  implementation was not modified by T-003.

- `InboxProjectionTestSupport.NewServiceProvider` no longer passes
  `IEventPublisher` into the `WorkflowRunStore` constructor — only

  `Assert.NotEmpty` + `Assert.Contains`. After T-003, exactly one row

## T-004 progress notes

### Codebase Patterns

- `IssueStore.SaveAsync(key, state, events, ct)` mirrors the
  `WorkflowRunStore.SaveAsync(run, events, ct)` transactional entry
  point that T-003 introduced. Same shape: open the producer's
  `MohistDbContext`, `BeginTransactionAsync`, stage the state row
  with the existing JSON snapshot path, append every event row via
  `_eventStore.AppendAsync(db, envelope, ct)` on the shared
  `DbContext`, then `SaveChangesAsync` + `CommitAsync`. No own
  transaction, no post-commit publish loop.

- Envelope construction and identity stamping consolidate into the
  store, completing the D5 pattern that T-003 started for
  WorkflowRun. `IssueStore.ToCloudEvent` calls the existing
  `IssueEventSerializer.BusType` / `ToData` helpers (the same ones
  that the old `IssueGrain.PublishIssueEventsAsync` used) and stamps
  `extensions["projectid"]` + `extensions["issueid"]` +
  `extensions["issueno"]` from `state.ProjectId` / `state.Id` /
  `state.Number`. The store does not accept identity from the
  caller — it reads it from the persisted aggregate, which is the
  single point of truth. `subject` is set to `state.Number.ToString()`
  so the per-issue CloudEvents type contract stays unchanged.

- `IssueStore.SaveAsync(key, state)` (no events, the existing
  `IStateStore<DomainIssue>` overload) is preserved for any caller
  with no pending events — same JSON snapshot path as before, no
  new `BeginTransactionAsync` needed (single-write implicit
  transaction). The grain takes the events-aware overload whenever
  `PendingEvents` was non-empty.

- `IIssueStore : IStateStore<DomainIssue>` is the new contract that
  the grain consumes. It adds `SaveAsync(string key, DomainIssue
  state, IReadOnlyList<IssueEvent> events, CancellationToken ct)`.
  DI registers `IIssueStore` as the concrete `IssueStore` and the
  legacy `IStateStore<DomainIssue>` resolution forwards to the same
  instance, so existing in-memory consumers
  (`InboxProjectionHandler`, `HermesIssueNotificationHandler`,
  `InboxProjectionTestSupport`) keep their no-event view of the
  store with zero behavioral change.

- `IssueGrain` stops depending on `IEventStore` and
  `IEventPublisher` after this task — `_eventStore`, `_eventBus`,
  and `PublishIssueEventsAsync` are gone. The grain's `using
  Mohist.Server.Infrastructure.Events;` and `using
  Mohist.Server.Infrastructure.Data.Events;` imports drop with
  them. Only the canonical `IIssueStore` (and the existing
  `Mohist.Server.Infrastructure.Data.Issue` namespace that holds
  `IStateStore<T>`) remains.

### Gotchas

- `Mohist.ServiceProvider.GetRequiredService<IIssueStore>()` in the
  grain constructor means the DI registration order matters. The
  silo registration registers `IssueStore` as `IIssueStore` first
  and then binds `IStateStore<DomainIssue>` to the same scoped
  instance. Resolving `IStateStore<DomainIssue>` before
  `IIssueStore` would silently fall back to a null `IEventStore`
  if a future change broke the chain — the forward registration
  is the only thing keeping the no-events path safe today.

- The no-events `SaveAsync(key, state)` path keeps its original
  behavior verbatim: a single `FindAsync` on the `Issues` DbSet,
  followed by `Add` or `State/Risk` mutation + `SaveChangesAsync`.
  No `BeginTransactionAsync` (SQLite single-statement implicit
  transaction is fine). T-004 does **not** open a transaction on
  the no-events path; the events-aware path opens one because the
  state row + every event row + their index updates are a single
  atomic unit that needs explicit transactional boundaries.

- The `ThrowingEventStore` private fake in the new spec throws on
  the **second** `AppendAsync(db, envelope)` call, simulating a
  mid-transaction event-row write failure (the same pattern as
  T-003's `TransactionalEventAppendSpecs.ThrowingEventStore`). The
  first event lands in `db.IssueEvents.Local` as `Added`, so the
  test's verification on a fresh `DbContext` proves the rollback
  wiped both staged state and event rows. The issue's existing
  `IssueCreated` payload constructor requires
  `(Title, Priority, Labels, Risk, RepositoryRef)` — pass `null`
  for both optional strings to get a minimal record.

- `IssueEvent` is a C# 14 union, so `IReadOnlyList<IssueEvent>`
  compiles but `IReadOnlyList<IssueCreated>` does not (each
  variant is a separate record). The new `IssueStore` and
  `IIssueStore` save overload accept the union list, matching the
  shape `_issue.PendingEvents.ToList()` returns from the grain.

- `IssueWorkflowReadPathSpecs.ReadOnlyTrackingStateStore` (a fake
  for the pure-query contract test) had to gain an
  `IIssueStore` implementation of the events-aware overload to
  compile against the new `IssueGrain` constructor signature.
  Each save variant appends a discriminable tag to `_saveCalls`
  (`events:N`) so a regression through the events-aware path is
  visible without changing the existing zero-save assertion.

- `IssueCreationSpecs.CreateIssue_PersistsCreatedEventToIssueEvents`
  moves from `Assert.NotEmpty(stored)` +
  `Assert.Contains(... IssueCreated ...)` to
  `Assert.Single(stored)` + `Equal("com.mohist.issue.created", ...)`.
  Before T-004 the spec tolerated `>1` rows because T-002's
  publisher appending-then-the-grain's store append yielded
  duplicates. After T-004 there is exactly one row per emitted
  IssueEvent.

- Doc-comments referencing
  `IssueGrain.PublishIssueEventsAsync` were updated in:
  - `Events/Subscriptions/AgentSubscriptionDispatchHandler.cs`
    (two doc-comment locations referring to the projectid stamping
    source);
  - the test `AgentSubscriptionDispatchHandlerSpecs` (a comment in
    a fixture and an inline comment in a test);
  - no other production code referenced the method by name (verified
    via grep).

- The legacy migration
  `Infrastructure/Data/Migrations/20260705132535_BackfillIssueCompletedEvents.cs`
  doc-comment still mentions
  `IssueGrain.PublishIssueEventsAsync` — left untouched because it
  documents a historical bug and the migration's purpose is to

  `SaveChangesAsync` + `CommitAsync`. No post-commit publish loop,
  no own `SaveChanges` from the event store.

- Envelope construction and identity stamping consolidate into the
  store, completing the D5 pattern that T-003 started for WorkflowRun
  and T-004 finished for Issue. `AgentSessionStore.ToCloudEvent` calls
  the existing `AgentSessionEventSerializer.BusType` / `ToData` helpers
  (the same ones the old `AgentSessionGrain.PublishAgentSessionLifecycleAsync`
  used) and stamps `subject = state.Id` per design.md#OQ3 (no
  `projectid` extension — no consumer reads it from agent-session
  lifecycle events). The store does not accept identity from the
  caller — it reads it from the persisted aggregate, which is the
  single point of truth. `source` is set to
  `AgentSessionEventPersistence.AgentSessionSource(state.Id)` so the
  T-001 routing branch lands the row in `AgentSessionEvents`.

- `AgentSessionStore.SaveAsync(key, state)` (no events, the existing
  `IStateStore<AgentSession>` overload) is preserved for any caller
  with no pending events — same JSON snapshot path as before, no
  new `BeginTransactionAsync` needed (single-write implicit
  transaction). The grain takes the events-aware overload whenever
  the `AppendRuntimeEventsAsync` path has buffered events, or via
  `CommitAsync` for `AttachPhysicalSessionAsync` / recovery paths.

- The `AgentSessionStore` constructor gained an `IEventStore`
  dependency. DI registration in `MohistServiceRegistration.cs`
  already wires `IEventStore` as a singleton (T-002 promotion) and
  `IAgentSessionStore` as scoped, so the Orleans silo resolves it
  transparently.

- `AgentSessionGrain` stops depending on `IEventPublisher` after
  this task — the `_eventPublisher` field, the
  `PublishAgentSessionLifecycleAsync` method, the `AgentSessionSource`
  helper, the swallow-`InvalidOperationException` + log-and-swallow
  catches, and the post-commit publish loop are all gone. The grain's
  constructor signature is now
  `(IAgentSessionStore, IAgentSessionTranscriptStore,
  IDbContextFactory<MohistDbContext>, ITranscriptEventPublisher,
  TimeProvider, ILogger<>)`. The transcript publisher stays (it's a
  separate concern: SignalR streaming of transcript events, not
  domain event publishing).

- The grain's runtime-event path accumulates pending domain events
  into a new `_pendingDomainEvents` field. `AppendRuntimeEventsAsync`
  appends to the queue; `FlushAsync` snapshots the queue into a local
  array, passes it to `SaveAsync`, and only clears the queue after
  a successful save (matching the existing transcript-flush
  semantics). If `SaveAsync` throws, the events stay queued for the
  next retry — no loss.

- `_eventPublisher`-style append-during-publish is gone. Per
  `EventPublishingIntegrationFixture`'s design, the production
  `AgentSessionStore` writes event rows in the same transaction as
  the state save. The `_fixture.Services.GetRequiredService<IEventStore>()`
  accessor exposes the singleton `EventStore` to integration specs
  for persisted-row assertions. The `RecordingPublisher` is no
  longer called by the agent-session producer, so its
  `_fixture.RecordingPublisher.Clear()` calls in
  `AgentSessionLifecycleDedupSpecs` / `AgentSessionContextEventPublishingSpecs`
  were removed along with the post-commit `Published` assertions.

- `IEventStore` gained a `ListAgentSessionEventsAsync(sessionId, limit, ct)`
  accessor that reads from `AgentSessionEvents` filtered by the
  canonical source prefix. `EventStore` routes
  `/mohist/agent-session/` to `AgentSessionEvents` in both the
  scoped and non-scoped overloads (T-001 work). `RecordingEventStore`
  mirrors the new accessor for spec support.

### Gotchas

- `AgentSessionGrainFixture` (the unit-test fixture that uses
  `FakeAgentSessionStore`) had to drop the `IEventPublisher`
  registration from the silo — the grain constructor no longer
  takes the dependency. The `NoopEventPublisher` inner class was
  removed from the fixture in lockstep.

- `AgentSessionStoreSpecs` (the unit-test fixture that constructs
  `AgentSessionStore` directly) had to add a `new NoopEventStore()`
  to its constructor call. The no-events `SaveAsync(key, state)`
  overload does not exercise the event-store path, but the events-
  aware overload now requires it; the fake satisfies the constructor.

- `EventPublishingIntegrationFixture` exposes `IServiceProvider Services`
  so integration specs can resolve the singleton `IEventStore` for
  persisted-row reads. Without this accessor, the dedup specs would
  have no path to assert against `AgentSessionEvents` rows. The
  `RecordingIEventPublisher` / `NoopEventPublisher` inner classes
  stay (other tests still use them for the inbox hint path).

- The integration specs use `grain.FlushForTestAsync()` to force a
  state save before reading the persisted rows. The fixture's
  production `AgentSessionStore` writes to the in-memory SQLite
  database, and the singleton `EventStore` reads from the same
  connection, so the dedup specs can read back exactly what was
  written. Without the explicit `FlushForTestAsync()`, the
  persist-timer (200 ms debounce) would race against the read.

- `AgentSessionTransactionalEventAppendSpecs` uses
  `db.Database.EnsureCreated()` to set up the schema. The
  `MohistDbContext` registration for `AgentSessionEvents` (added in
  T-001) is honoured by `EnsureCreated` on a fresh database, so
  the unit specs run against the same table shape as production
  (without the migration history overhead).

- The new `ThrowingEventStore` private fake throws on the second
  `AppendAsync(db, envelope)` call, simulating a mid-transaction
  event-row write failure. The first event lands in
  `db.AgentSessionEvents.Local` as `Added`, so the test's
  verification on a fresh `DbContext` proves the rollback wiped
  both staged state and event rows. Mirrors the `WorkflowRunStore`
  and `IssueStore` equivalents from T-003/T-004.

- `SaveAsync_NoEventsOverload_RemainsForCallerWithNoPendingEvents`
  documents that the no-events `SaveAsync(key, state)` overload
  keeps its original behavior verbatim — the grain takes the
  events-aware overload whenever `_pendingDomainEvents` was
  non-empty, but callers with no pending events continue to use
  the no-events overload with its single-write implicit transaction.

### Open follow-ups for downstream tasks

- The dispatcher (step 3, future issue) must wire the handlers back
  to react to durable event rows. The handler registration on the
  bus is intact — they are dormant, not deleted. After T-005
  completes, all three core producers (`WorkflowRunStore`,
  `IssueStore`, `AgentSessionStore`) emit durable event rows in
  one transaction with their state save, and `IEventPublisher` is
  used only by `InboxProjectionHandler` for the inbox hint path.

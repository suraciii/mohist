## T-001 progress notes

### Codebase Patterns

- Per-source Id (`MAX(Id)+1`) on SQLite has been implemented in two places
  (`EventStore.NextWorkflowIdAsync`, `NextIssueIdAsync`, `NextEpicIdAsync`).
  All three currently open their own `DbContext` to query `MAX`. The new
  scoped overload (`AppendAsync(MohistDbContext db, ...)`) takes the
  caller's `DbContext` directly so the per-source Id sequence is correct
  for events appended inside the same transaction.

- Routing for the source prefix in `EventStore.AppendAsync` is a chain of
  `StartsWith(SourcePrefix)` checks (`Issue`, `Epic`, with
  `WorkflowRun` as the implicit default). The implicit default
  misroutes `/mohist/agent-session/` to `WorkflowRunEvents` today —
  T-001 adds an explicit agent-session branch before the workflow
  default so the misrouting is gone.

- All event-row tables (`WorkflowRunEventRow`, `IssueEventRow`,
  `EpicEventRow`) share the same column shape (Id + Source composite
  PK, EventId, Type, Time, SpecVersion, Subject, DataContentType, Data,
  ExtensionsJson, DispatchedAt). T-001 introduces `IEventRow` to
  express the shared shape (`Id`, `Source`) so the per-source MAX
  helper can be one generic method (`NextIdAsync<T>`) instead of four
  copies.

- `MohistDbContext.OnModelCreating` mirrors each event-row table with
  the same configuration block. The new `AgentSessionEventRow`
  configuration mirrors `EpicEventRow` exactly (Type/Source/Id index +
  partial `IX_AgentSessionEvents_Undelivered`). The earlier
  `EventDeliveryProgressAndDeadLetters` migration already added
  `DispatchedAt` columns to the existing tables; the new
  `AddAgentSessionEvents` migration only creates the table + indexes
  (no backfill, no `UPDATE` statements) — same pattern as
  `AddEpicEvents`.

- `IEventStore` fakes are spread across `Support/` (top-level:
  `NoopEventStore`, `RecordingEventStore`) and inside individual spec
  files (`InboxProjectionTestSupport.NoopEventStore`,
  `EpicEventPublishSpecs.ThrowingEventStore`). All four fakes were
  updated to implement the new scoped overload.

- Producer-side touches are intentionally zero. T-001 owns ALL
  `IEventStore` / `EventStore` changes; downstream tasks (T-003, T-004,
  T-005) only call the new scoped overload from their respective
  stores. `WorkflowRunStore`, `IssueStore`, `AgentSessionStore`,
  `InMemoryEventBus` were not modified.

### Gotchas

- EF Core's `DbSet<T>.Local` returns a `LocalView<T>` that exposes
  Added/Unchanged/Modified entities for the set. The next
  `MAX(Id)+1` call after `db.<Set>.Add(...)` therefore sees the
  pending row immediately, which is what makes the per-source Id
  sequence correct for multiple events appended in one transaction.
  Tests verify this with three consecutive `AppendAsync` calls in a
  single `BeginTransactionAsync` block yielding Id 1, 2, 3.

- `MarkDispatchedAsync` is intentionally NOT updated to use the
  shared DbContext — it still owns its own DbContext + transaction
  because the dispatcher (step 3, future issue) runs outside any
  producer's state transaction.

- The `AppendAsync(CloudEvent)` non-scoped overload now opens a
  transaction even though SQLite + a single-statement write would not
  technically need one. This preserves the same observable behavior
  for existing callers (e.g. `InboxProjectionHandler` hint path) and
  keeps the entry point a single SaveChanges boundary.

- The migration was generated with `dotnet ef migrations add
  AddAgentSessionEvents` and the resulting
  `20260708053533_AddAgentSessionEvents.cs` matches the expected
  schema (table + `IX_AgentSessionEvents_Undelivered` partial index,
  no `IX_AgentSessionEvents_Type_Time` since lifecycle events are not
  timeline-queried the way workflow/issue events are).

- `EnsureCreated` produces a different partial-index SQL than
  `Migrate()` on SQLite (the older `EventStoreDeliveryProgressSpecs`
  test confirms this). The new
  `AgentSessionEventsMigrationSpecs` uses `Migrate()` so the
  DDL matches production.

- The scoped overload must NOT call `SaveChangesAsync`; the producer's
  transaction owns the commit. Verified by spec
  `AppendAsync_DoesNotCallSaveChangesAsync_OnScopedOverload` which
  asserts that after `AppendAsync(db, evt)`, the row is in
  `db.WorkflowRunEvents.Local` with state `Added` while
  `db.WorkflowRunEvents.AsNoTracking().ToList()` returns nothing.

### Open follow-ups for downstream tasks

- T-002 (IEventPublisher write-only) needs to inject `IEventStore`
  into `InMemoryEventBus` and replace the in-publish dispatch loop
  with a delegated `IEventStore.AppendAsync(envelope)` call. The
  scoped overload is not needed for `IEventPublisher` because the
  inbox hint is written outside any producer's state transaction.

- T-003 / T-004 / T-005 should call `_eventStore.AppendAsync(db,
  envelope, ct)` inside their existing `BeginTransactionAsync`
  blocks; identity stamping (projectid, issueid, issueno, session
  id) is owned by the producer tasks, not T-001.

## T-002 progress notes

### Codebase Patterns

- `InMemoryEventBus` is registered as a singleton (see
  `CloudEventBusServiceCollectionExtensions.AddCloudEventBus`),
  so its `IEventStore` constructor dependency must also be a
  singleton — T-002 promotes `IEventStore` registration in both
  `MohistServiceRegistration` and `MohistSiloRegistration` from
  `AddScoped` to `AddSingleton`. `EventStore` only depends on
  `IDbContextFactory<MohistDbContext>` + `ILogger<>`, so singleton
  lifetime is safe; each call still gets its own short-lived
  `MohistDbContext` from the factory.

- `IEventPublisher` interface signature is unchanged by T-002
  (the same two `PublishAsync` overloads). The change is
  semantic inside `InMemoryEventBus`: synchronous handler
  fan-out is removed; both overloads now delegate to
  `IEventStore.AppendAsync(CloudEvent)` (the non-scoped
  overload). All existing fakes (e.g.
  `RecordingIEventPublisher`) keep compiling.

- Subscriptions (`_subscriptions` + `AddSubscription`) remain
  on the bus instance for the future dispatcher. `AddSubscription`
  is now only used by spec files that build the bus empty and
  wire handlers post-construction; production DI still feeds
  subscriptions through the second constructor (the
  `IEnumerable<Subscription>` overload registered by
  `AddCloudEventHandlersFromAssembly`).

- Specs that previously asserted on captured publishes (bus
  fan-out) had to be rewritten to assert on persisted event
  rows via the new `RecordingEventStore.Appended` accessor.
  The accessor is a public read-only view over the in-memory
  recorded envelopes, exposing the `RecordedEnvelope` record
  type so callers can inspect `Envelope.Type` / `Source` /
  `Subject` / `Data` / `Extensions` directly.

- `EventBridge` specs no longer exercise the bus at all — the
  bus would now just persist a row, not drive the bridge. The
  specs build a `CloudEvent` and call `bridge.HandleAsync(...)`
  directly, matching the path the future dispatcher will take.
  `ProjectIsolationIntegrationSpecs` follows the same pattern.

- Specs whose end-to-end behavior depended on synchronous
  bus dispatch (e.g. `IssueWorkflowProductLoopSpecs` completing
  an issue after a `WorkflowRunCompleted` publish,
  `StageLockSpecs` releasing sequential locks after
  `StageFailed` / `StageCompleted`,
  `RunnerWorkflowTerminalStatusHandlerSpecs` pushing
  `ReceiveWorkflowRunStatus`) were rewritten to replay the
  persisted row through the handler/router that the future
  dispatcher will use. Each spec uses
  `TestWait.ForAsync` to wait for the row to land in
  `IEventStore.ListAsync(...)` before driving the handler.

### Gotchas

- After T-002 the bus is write-only, but the three producers
  still call *both* `_eventStore.AppendAsync(...)` and
  `_eventPublisher.PublishAsync(...)` (the post-commit loops
  in `WorkflowRunStore`, `IssueGrain.PublishIssueEventsAsync`,
  `AgentSessionGrain.PublishAgentSessionLifecycleAsync`).
  Since `IEventPublisher.PublishAsync` now also appends to
  `IEventStore`, each event ends up persisted **twice** in
  the interim (T-003 / T-004 / T-005 will collapse this to
  one row per event by moving writes into the state
  transaction and dropping the publish call). Specs that
  count rows use `Assert.NotEmpty` + `Assert.Contains`
  instead of `Assert.Single`; see the
  `WorkflowRunStoreEvent_PersistsRowButDoesNotSyncProjectToInbox`
  and `CreateIssue_PersistsCreatedEventToIssueEvents`
  tests for the exact phrasing.

- `IEventStore` singleton promotion interacts with
  `MohistDbFixture` and the various grain fixtures that build
  their own `InMemoryEventBus` instance: each one had to
  pass an `IEventStore` (typically `new NoopEventStore()` or
  a shared `new RecordingEventStore()`) to the bus
  constructor. NoopEventStore is fine because the bus only
  needs a working `AppendAsync(CloudEvent)` — the scoped
  overload is unused here.

- The original `InMemoryEventBus(ILogger)` constructor was
  removed; callers (test fixtures, DI extensions) must now
  pass an `IEventStore`. The single-arg overload is no
  longer needed because the bus is never constructed without
  its event-store dependency after the write-only
  convergence.

- The DI cycle worry called out in the `InboxProjectionHandler`
  comment ("`IEventPublisher` resolves to the `InMemoryEventBus`
  singleton whose constructor enumerates all handler
  subscriptions") no longer applies once T-002 lands: the
  bus no longer takes `IEnumerable<Subscription>` as a
  hard constructor dependency for the singleton path (the
  subscription enumeration moves to a separate `AddSingleton`
  registration in `AddCloudEventHandlersFromAssembly`).
  However, the cycle is still latent because the bus
  constructor can still resolve subscriptions transitively
  through `IEventStore` (which has no such dependency) — so
  the existing scope-resolved `IEventPublisher` pattern in
  the handler is left in place to be safe.

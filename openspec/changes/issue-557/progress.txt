# issue-557 progress notes

## Codebase Patterns

- `AgentConfigSchema` (packages/server/src/Mohist.Server/Infrastructure/AgentConfigSchema.cs)
  is the converged boundary for BOTH agent-config write surfaces:
  `Validate`/`AllowedKeys` (Agent definition, includes `runtime`) and
  `ValidateIssue`/`IssueAllowedKeys` (issue override, Agent-owned `runtime`
  rejected with a dedicated message).
- Write-side merge paths iterate `AgentConfigSchema.Filter`, which loops over
  `IssueAllowedKeys` — adding a key to `IssueAllowedKeys` automatically flows
  it into `IssueVariableBuilder`, `IssueWorkflowProfileStorageIntegrity`,
  `ConfigService`, and `IssueQuerier` with zero extra wiring.
- Error-message style: named-value errors list every accepted value
  (see `ValidateRuntime`). `ValidateReasoningEffort` mirrors it, and uses the
  ordered list (`CanonicalReasoningEffortsOrdered`) so the message is stable;
  `AllowedKeys`-set messages still use set order (pre-existing).
- `ValidateIssue` uses a literal `CanonicalIssueKeyOrder` string for its
  "accepts only ..." message (HashSet iteration order is nondeterministic).
- CLI (packages/cli/Mohist.Cli/MohistCliCommands.Agent.cs): typed config keys
  follow the `--flag` + `--clear-flag` pattern with `ValidateClearSetPair`
  mutual exclusion; local value validation happens in
  `ResolveTypedAgentConfig` (mirrors the server set; the CLI cannot reference
  the Server assembly). `mo agent view` rendering lives in
  `TableRenderer.Entities.cs` (`StringOf` renders missing keys as empty —
  absent effort renders as nothing, no synthesis).
- Tests: dotnet test with Microsoft.Testing.Platform ignores `--filter`
  (MTP0001 warning) — a filtered run executes the full project. Full suites
  are fast enough (unit ~8s, cli ~2s).

## T-006 (resolver-gated admission and conditional capability fence)

- Admission now reads immutable AgentJob and Workflow pending projections, resolves the frozen tuple against the runner catalog snapshot before claim, and passes a `RunnerCapabilityExpectation` through `IRunnerGrain`. Runner catalog/revision and readiness generation checks run under `_lifecycleGate`; a heartbeat catalog repair between resolution and claim therefore refuses the claim and leaves the owner pending.
- AgentJob conditional claims write the capability revision into the owner-ledger `DispatchJson` before the Pending-to-Running store transition. Workflow claims stamp the revision before `StoreActiveWorkDispatchAsync`, which remains the durable first writer; a first-writer winner from another revision is re-pended instead of delivered.
- Only supported capability resolutions claim work. Missing or incomplete/revisionless evidence remains pending, while explicit unsupported/incompatible results become deterministic preflight failures with the frozen tuple and registered EventCatalog failure categories. The AgentJob evidence is durable state/output; Workflow errors carry the same tuple and revision in their deterministic message.
- Runner dispatches with a capability revision are checked before journal admission or runtime execution. Revision, model, effort, and variant mismatches produce `stale-capability-snapshot`, and the report protocol re-pends the owner. Workflow action model/variant values are read from nested `with.options`; AgentJob capability fields remain top-level.
- Non-Agent `mohist/pi` and `mohist/opencode` tasks use the common fence when their action options name a model or true variant. Their Agent-owned reasoning-effort member is intentionally unset because those actions do not own an Agent profile snapshot; explicit adapter-level effort handling remains the runtime contract. This keeps the tuple shape uniform without inventing an effort value.
- Added Server fence/admission coverage for absent catalogs, deterministic AgentJob and Workflow preflight failures, matching and changed catalog claims, first-writer snapshots, and the lifecycle-gate heartbeat race. Runner coverage verifies stale snapshots are rejected and requeued without entering execution.

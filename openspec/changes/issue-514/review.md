# Review: Issue 514

## Findings

1. **P0 - The documented create flow is impossible.** `mo agent connection create <agent> --provider slack` is required to create a recoverable Connection and print the Slack App creation reference, but the CLI requires `--workspace-team-id`, `--app-id`, and `--bot-user-id` first ([MohistCliCommands.AgentConnection.cs:36](../../../packages/cli/Mohist.Cli/MohistCliCommands.AgentConnection.cs#L36), [MohistCliCommands.AgentConnection.cs:59](../../../packages/cli/Mohist.Cli/MohistCliCommands.AgentConnection.cs#L59)); the server rejects the same missing fields ([SlackConnectionRoutes.cs:22](../../../packages/server/src/Mohist.Server/Api/SlackConnectionRoutes.cs#L22)). Those Slack identities are only available after the user creates and installs the App, so a user cannot enter Setup from the required command. Make the initial Connection recoverable without these post-install identities, then bind/verify them during configure/verification, and add coverage for the documented minimal command.

2. **P0 - Managed `mohist-slack` cannot serve any Connection.** The adapter exits unless `SLACK_CONNECTIONS` is a non-empty JSON environment variable ([cli.ts:12](../../../packages/mohist-slack/src/cli.ts#L12), [cli.ts:31](../../../packages/mohist-slack/src/cli.ts#L31)), but `mo install slack` sets only `SERVER_URL` and the operator token ([SystemdServiceInstaller.cs:72](../../../packages/cli/Mohist.Cli/SystemdServiceInstaller.cs#L72)). No Connection lifecycle command updates that variable. Therefore an installed adapter cannot start, and a running adapter cannot discover a later-created Connection. The adapter needs an authenticated Server-owned discovery/refresh contract for all active Connections; cover the zero-Connection startup and subsequent Connection add/remove lifecycle.

3. **P0 - Setup never advances to owner claim.** Configuring credentials only records `WaitingForSlackService` ([SlackConnectionRoutes.cs:78](../../../packages/server/src/Mohist.Server/Api/SlackConnectionRoutes.cs#L78)); `adapter-session` only records a heartbeat ([SlackConnectionRoutes.cs:212](../../../packages/server/src/Mohist.Server/Api/SlackConnectionRoutes.cs#L212)). `SlackSetupVerifier.VerifyAsync` has no caller, so no route transitions a healthy configured Connection to `ClaimOwner`; `claim-owner` consequently remains unavailable. Wire verification into the setup state transition after a fresh heartbeat, and cover successful, invalid-token, identity-mismatch, and missing-scope paths. The verifier also passes `BotUserId` to `conversations.info` ([SlackSetupVerifier.cs:41](../../../packages/server/src/Mohist.Server/Slack/SlackSetupVerifier.cs#L41)), which is not a DM conversation id and must be replaced with a valid DM-access verification strategy.

4. **P0 - Slack never receives a terminal job result.** The ingress route writes only an immediate `UserAction` acknowledgement after launching ([SlackConnectionRoutes.cs:192](../../../packages/server/src/Mohist.Server/Api/SlackConnectionRoutes.cs#L192), [SlackConnectionRoutes.cs:283](../../../packages/server/src/Mohist.Server/Api/SlackConnectionRoutes.cs#L283)). There is no producer of `TerminalResult` or `ExplicitFailure` outbox records when the corresponding AgentJob/AgentTurn becomes terminal. A successful or failed Slack-dispatched task therefore has no result summary to deliver to its originating DM. Subscribe or otherwise durably project terminal job/turn state into the outbox using the stored connection/conversation correlation, including the uncertain-result path.

5. **P1 - Redelivery creates duplicate outbound replies and can exhaust the outbox.** The inbox correctly marks a duplicate with `AlreadyExisted`, but ingress still enqueues a new non-replaceable `UserAction` row on every redelivery ([SlackConnectionRoutes.cs:195](../../../packages/server/src/Mohist.Server/Api/SlackConnectionRoutes.cs#L195), [SlackConnectionRoutes.cs:198](../../../packages/server/src/Mohist.Server/Api/SlackConnectionRoutes.cs#L198)). Replaying one Slack event produces repeated bot acknowledgements, and enough retries fill the outbox. Make acknowledgement creation idempotent by message/dispatch identity and add an ingress-level redelivery test, including restart recovery.

6. **P1 - An accepted task can lose its required acknowledgement under concurrent outbox pressure.** The route launches and marks the inbox dispatched before it persists the acknowledgement ([SlackConnectionRoutes.cs:192](../../../packages/server/src/Mohist.Server/Api/SlackConnectionRoutes.cs#L192)). If capacity becomes full before `EnqueueReplyAsync`, `SlackOutboxStore` marks the Connection backpressured and throws ([SlackOutboxStore.cs:81](../../../packages/server/src/Mohist.Server/Infrastructure/Slack/SlackOutboxStore.cs#L81)); the request then fails after work was accepted, with no durable acknowledgement intent. Preserve an atomic/recoverable accepted-and-acknowledged transition, or return a durable explicit state that allows the adapter to recover the acknowledgement. Add a concurrency/capacity regression test.

# Issue 514 / T-001 — Encrypted credential secret store

## Codebase patterns discovered

- `OperatorCredential` (`Infrastructure/Security/OperatorCredential.cs`) is the
  precedent for "single-instance secret-file discipline": env var override,
  computed `~/.mohist/<name>` path, generated on first read, `0600`
  enforced via `UnixFileMode`, `ReparsePoint` rejected, abstract
  `IOperatorCredentialStore` so tests can drive the surface without
  touching `System.IO` directly. Existing tests
  (`tests/.../Security/OperatorCredentialTests.cs`) use exactly that hook.
- `MohistDbContext` uses `IScopedService`/`ISingletonService` for
  auto-registration via `AddMohistConventionalServices()`. Tests register
  fakes by constructing the store directly with a
  `TestDbContextFactory(...)`. Migrations live in
  `Infrastructure/Data/Migrations/` with a hand-written
  `<DateHHMMSS_Name>.cs`, `.Designer.cs`, and a manual edit of
  `MohistDbContextModelSnapshot.cs` (the snapshot's `BuildModel` calls
  `BuildModelCore` so a single migration only edits the `.cs` file +
  inserts its own entity-block into the snapshot plus the matching
  `Index`/constraint entries).
- Test infrastructure:
  - `MigratedSqliteTemplate.CopyTo(...)` clones a prebuilt migrated
    schema into a fresh in-memory SQLite db (used for both
    `CreateMigrated()` and `CreateDatabase(targetMigration)`).
  - `BannedSymbols.Tests.txt` bans `System.IO.File/Directory/FileStream`
    in tests — we must abstract file ops behind
    `ISecretKeyStore`/`SecretKeyFile` interfaces just like
    `OperatorCredential` does.
  - `MockEnvironmentVariableProvider` lives in the
    `EnvironmentAbstractions.TestHelpers` package
    (already referenced by both test projects).
- `IHermesWebhookClient` + `AddHttpClient<...>()` + `Recording...Fake`
  is the established typed-HttpClient pattern; not needed for T-001
  but referenced as a future guidance marker.
- `ConfigRoutes.cs:99-104` defines
  `IsSecretKey(key) → contains("token") OR contains("key") OR contains("secret")`.
  The redaction policy for any field whose name matches the same pattern
  is reused for token-name filtering and for any logging surface that
  might print a `Dictionary<string,string>` blob.

## T-001 design notes

- `ISecretStore` lives in
  `Infrastructure/Security/Secrets/ISecretStore.cs`. `SecretKey` is a
  connection-scoped address: `(ProjectId, ConnectionId, Kind)`. `Kind`
  is currently `{AppToken, BotToken}` — the seam extends later for
  Runner creds, webhook secrets.
- `ConnectionSecretRow` (EF row, table `ConnectionSecrets`,
  composite PK on `(ProjectId, ConnectionId, Kind)`) holds a single
  ciphertext blob (nonce || tag || ciphertext) plus
  `UpdatedAt`. We do **not** store the master key id; the master key
  is process-global per `MOHIST_SECRET_KEY_PATH`.
- `ISecretKeyStore` parallels `IOperatorCredentialStore`:
  - `EnsureKeyAsync(path, ct)` — returns 32 bytes, creating the file
    with `0600` (non-Windows) if missing and writing it with
    `WriteThrough`+`FlushToDisk`. Symlink at the path → invalid op.
    Honors an `IEnvironmentVariableProvider` injected for tests.
  - `LoadKeyAsync(path, ct)` — rejects symlinks and any file whose
    mode grants others read/write/exec (best-effort on Windows).
  - `Exists(path)` — pure probe.
- `AesGcmSecretStore` (singleton): derives the master key once (caching
  it in memory after first `Load`); uses `AesGcm.Encrypt`/
  `Decrypt` with 12-byte nonce, 16-byte tag. The tag is appended to
  the ciphertext by `AesGcm`; the blob layout is
  `nonce (12) || ciphertext (N) || tag (16)` for simplicity and
  compactness.
- Redaction is layered on `ISecretStore.Redact<T>` — a small helper that
  walks a `Dictionary<string,string>` and replaces any value whose key
  matches the `IsSecretKey` predicate with `***`. The same predicate
  lives next to `ISecretStore` so `AesGcmSecretStore.LogStored` etc.
  can share it without a cross-namespace dependency.
- DI: register `ISecretStore → AesGcmSecretStore` as
  `Singleton` (cache the master key), `ISecretKeyStore →
  PhysicalSecretKeyStore` as `Singleton`. Both wired in
  `MohistServiceRegistration.ConfigureMohistServices`.
- EF migration: `20260729000000_AddConnectionSecrets` creates the table
  with the composite PK, no other index (only `Load`/`Delete` are
  keyed — the inbox/outbox etc. are separate tables in later tasks).

## Codebase patterns to reuse

- Treat spec tests as primary; unit tests for pure file-discipline
  behavior. Both call directly into `AesGcmSecretStore(...ctor)` with
  fake args; no `WebApplicationFactory` needed.
- `TimeProvider` always injectable; never use `DateTimeOffset.UtcNow`
  in production code or `DateTimeOffset.UtcNow` (banned) in tests.
- `IEnvironmentVariableProvider` injectable in production
  (`SystemEnvironmentVariableProvider.Instance`) and faked in tests
  via the already-referenced `MockEnvironmentVariableProvider`.

# Issue 514 / T-002 — AgentConnection aggregate and lifecycle

## Codebase Patterns

- `AgentConnection` follows the `RoutingRule`/`WatchEntry` relational pattern: domain and EF row are separate, each queryable fact has its own column, and `AgentConnectionStore` is scoped rather than an Orleans grain.
- Binding fields are accepted only at create time. `UpdateAsync` explicitly rejects `ProjectId`, `AgentId`, `ProviderKind`, `WorkspaceTeamId`, `AppId`, and `BotUserId` with `immutable_binding`; mutable lifecycle/access fields remain field-selected updates.
- Active-Agent validation uses the existing `AgentQuerier`, preserving the Agent JSON row as the single execution-definition source. AgentConnection stores no execution snapshot.
- The partial unique SQLite index on `(ProjectId, AgentId, WorkspaceTeamId)` with `DeletedAt IS NULL` permits replacement after soft deletion while preventing two active bindings.
- Connection deletion is a soft delete for the aggregate and explicitly removes both credential slots through `ISecretStore`. Cleanup runs on repeated deletes too, so interrupted cleanup can be retried. Provider inbox/mapping/outbox records do not exist until T-004 and must extend this cleanup path when introduced.
- Specs use `TestSqliteDatabase.CreateMigrated()`, `TestDbContextFactory`, `FakeTimeProvider`, and an in-memory `ISecretStore` fake. They cover immutable binding, archived-Agent rejection, uniqueness, distinct workspaces, independent facts in both directions, absence of execution-definition fields, credential cleanup, and Agent preservation.

# Issue 514 / T-003 — Slack API client and setup verification

## Codebase Patterns

- Slack identity calls use a typed HttpClient under Server.Slack, with bearer authentication and Slack Web API method paths relative to the configured Slack API base URL.
- AgentConnectionStore.UpdateAsync is the persistence seam for independent SetupProgress, ConnectionHealth, HealthReason, and LastHeartbeatAt fields; Setup verification does not inspect or mutate AgentReadiness.
- Secrets are loaded only through ISecretStore using the project/connection BotToken address; the verifier keeps the plaintext token local to the API call and does not log it.
- SlackSetupVerifier treats token/auth, workspace, App/Bot mismatch, missing scopes, and DM access failures as FixSlackSetup with actionable reasons; successful verification advances to ClaimOwner. Adapter liveness is separately evaluated from LastHeartbeatAt using injectable TimeProvider.

# Issue 514 / T-004 — Provider inbox and outbound outbox

## Codebase Patterns

- Provider rows are Server infrastructure tables keyed by `ConnectionId`; the inbox uses a unique `(ConnectionId, SlackMessageIdentity)` index and only pending rows count toward ingress capacity.
- `SlackOutboxStore` owns the durable outbox state machine. Replaceable progress merges only while the existing row is pending; terminal result, explicit failure, and user-action rows remain independent rows.
- Backpressure updates Connection health through a separate DbContext-based `SlackConnectionHealthBackpressurer`, avoiding a DI cycle between `AgentConnectionStore` provider cleanup and the outbox store.
- Orleans grain interfaces ending in `Grain` must live in a `*.Grains` namespace. The Slack dispatcher uses fixed key `__slack_outbox_dispatcher_global__` and reminder name `slack-outbox-dispatcher`.
- SQLite in this repository cannot translate `DateTimeOffset` comparisons/orderings for these queries. Store scans use stable row-id ordering and apply time-window checks after materialization; all time values remain supplied by `TimeProvider`.
- The migration snapshot must preserve CLR numeric types (`AttemptCount` is `int`); a generated/manual mismatch causes EF pending-model failures.

# Issue 514 / T-005 — Owner claim flow

## Codebase Patterns

- Claim state is provider infrastructure in `SlackOwnerClaimCodes`, separate from `AgentConnection`; only `CodeHash`, `ExpiresAt`, `UsedAt`, and `SupersededBy` are persisted. The plaintext code is returned only from `GenerateAsync`.
- `SlackOwnerClaimService` uses `TimeProvider` for the ten-minute default window and SHA-256 over a normalized UTF-8 code. Regeneration marks all pending prior rows superseded before inserting the new row.
- Inbound classification checks a matching claim code before Setup progress and owner gates. Claim attempts call `ISlackApiClient.UsersInfoAsync` with the Bot token from `ISecretStore`; regular-member checks reject bots, deleted users, guests, restricted users, wrong workspaces, and `TeamIds` containing another workspace.
- Owner establishment is a conditional database update (`OwnerSlackUserId IS NULL`) followed by marking the code used, so a claimed Connection cannot be reassigned. Non-owner and invalid claim paths return explicit rejection decisions and do not write provider inbox rows or Agent resources.

## Verification

# Issue 514 / T-006 — Connection dispatch through the Agent API

## Codebase Patterns

- Connection dispatch uses the existing `AgentLaunchCoordinatorGrain`; the Slack message identity is the raw idempotency key `slack:{team}:{conversation}:{messageTs}`, and `AgentLaunchCoordinatorCodec.KeyFor(projectId, key)` remains the grain identity.
- `ConnectionLaunchOrigin` is carried as an optional field on the existing coordinator envelope and plan. The coordinator fingerprints it for replay conflicts, emits `agent-connection` as the source kind, and writes connection/slack audit labels alongside the existing manual labels.
- The adapter boundary is a single classifying `/ingress` route. It authenticates with `OperatorCredential`, resolves the Connection before classification, checks claim codes before setup/owner gates, and only calls `SlackProviderInboxStore.AcceptAsync` for an owner task with a valid Agent.
- Adapter-session returns secrets only after operator authentication and updates `LastHeartbeatAt` through `AgentConnectionStore`; delivery claim/ack delegates state transitions to `SlackOutboxStore`.

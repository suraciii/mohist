## Why

`mo update --repo-root <path>` can currently report a successful build and restart while the managed Runner is still executing a stale artifact or code from another source directory. This makes an explicit-source deployment untrustworthy: the selected repository must be the sole version authority, and success must mean that the running Server and Runner have both confirmed that version.

## What Changes

- Resolve one update source identity from the explicit or default repository root, materialize an immutable snapshot of that revision, and carry it through candidate staging, CLI self-update continuation, Server build, Runner build, service activation, and runtime readback. A full candidate is complete before the CLI slot or any managed service is changed.
- Build and install Server and Runner artifacts from that snapshot into stable, self-contained, versioned managed runtime locations. Compiler intermediates, build-time dependency projections, and web/Runner output stay outside the read-only snapshot. The Server is published as a self-contained executable for the supported platform runtime, and the Runner records its absolute supported Node host; service units switch to absolute active artifacts instead of depending on an arbitrary worktree or relative build output. **BREAKING** for installations or custom units that rely on source-bound working directories and relative entrypoints.
- Make the full update and component-specific updates use the same target identity with an explicit scope contract. The full update coordinates the CLI, Server, and installed Runner; component commands verify and report only the components they activate, without claiming global consistency.
- Verify a structured runtime identity from the running CLI, Server, and authenticated Runner connection generation against the candidate manifest before declaring success. Build or restart success alone is insufficient; a mismatch or unavailable required identity fails the update and emits no success result.
- Treat activation, cancellation, and verification as a recoverable update transaction with one durable active-target record, explicit CLI recovery slots, a live activation lease for the coordinator-to-launcher handoff, and crash reconciliation. A launcher may start a candidate only for that matching live lease; a stale lease transfers ownership to recovery. Preserve the last verified runtime and service target on failure, stop or remove an unverified candidate when no verified version exists, clear the active target after unrecoverable rollback, and report the expected version, observed version, and an actionable recovery result.
- Keep the CLI transaction as the only managed-runtime mutator. The Server web-update endpoint and status advancement become read/report-only surfaces that reject or quarantine direct builds and service restarts rather than bypassing the transaction. CLI outcome projection is owner-tagged, lease-bound, sequence-ordered, and committed through one cross-process projection lock with a write-ahead intent, so a stale or unrelated caller cannot create a successful update projection or overwrite a newer outcome.
- Use deterministic per-user managed runtime roots on Linux and Windows, include the Runner's production dependency closure and isolated npm workspace projection in each release, require an installed managed Runner for full updates, and require a fail-closed `bootstrap_required` handoff before a legacy CLI can enter the managed transaction. The bootstrap helper and its trusted payload live outside both update slots, while ownerless persisted jobs migrate to an explicit `legacy-unknown` terminal state instead of being guessed to be web-owned.
- Keep default-root and explicit-root updates distinguishable in human output and dry-run previews. This change does not alter Agent model selection, provider fallback, or inference configuration.

## Capabilities

- `update-source-identity`: The selected `--repo-root` and its resolved source identity are authoritative for the entire update, including CLI continuation, Server, Runner, and target/actual reporting.
- `managed-runtime-artifacts`: Server and Runner builds are installed as stable, self-contained versioned artifacts, and managed service targets activate those artifacts without reading an implicit source worktree.
- `update-runtime-consistency`: Running CLI, Server, and Runner artifact-owned identities are checked against the canonical target and exact Runner connection before success; mismatches fail the update rather than being downgraded to a warning.
- `update-runtime-recovery`: Candidate activation, verification failure, rollback/quarantine to a `status: "none"` target, legacy bootstrap, no-verified-version cleanup, and actionable recovery output form one bounded failure contract.

## Impact

- **CLI (`packages/cli`):** update orchestration and context, source/build operations, runtime consistency checks, Runner refresh results, service installation options, managed runtime paths, and their fake-boundary tests.
- **Server (`packages/server`):** runtime identity production and readback used to confirm the installed Server artifact; the web update mutation is disabled in this change, while status/outcome surfaces remain projections of the authoritative local CLI update.
- **Runner (`packages/runner`):** build manifest and startup/connection identity so the running process can be matched to the selected source artifact; Runner execution and model behavior remain unchanged.
- **Managed services and local filesystem:** systemd and Windows launcher generation, fixed per-user runtime roots, versioned self-contained runtime storage, activation links, and rollback state change from source-bound execution to verified installed artifacts. No network or external service dependency is required; the supported local .NET SDK, Node/npm toolchain, and recorded runtime host must be present before staging.
- **Documentation and tests:** self-host/update guidance and deterministic tests covering default and explicit roots, identity mismatches, successful activation, and recovery paths.

## T-001 Server runtime-routing work — learned patterns & gotchas

### Where `runtime` lives at every layer

- **Agent definition / write API** — `agentConfig.runtime` validated by
  `AgentConfigSchema.Validate` (`opencode|pi`); same gate covers Agent
  CRUD and the issue-level `agentConfig` write surface (via
  `IssueModelMetadata.ValidateAgentConfig`).
- **Launch-time override** — optional `runtime` field on the manual
  `AgentSessionLaunchRequest` body. Manual path passes it to
  `ResolveRuntime`; routed path passes no override (uses Agent config).
- **Resolution helper** — `AgentLauncher.ResolveRuntime(agentConfig,
  launchOverride)` implementing `launchOverride ?? agentConfig.runtime
  ?? "opencode"`. Reused by manual launch, routed launch, routed
  preflight, and the AgentSession open/attach fallback.
- **Snapshot** — `AgentJobInput.Runtime` (Orleans Id(4), append-only)
  and `RoutedAgentLaunchPlan.Runtime` (Orleans Id(19), append-only).
  Recovery on activation loss reads the snapshot, not fresh Agent
  config (matches model/variant D2 pattern).
- **Dispatch envelope** — `BuildDispatch` now emits
  `with["runtime"] = input.Runtime` so the runner
  `AgentJobExecutor` (T-002) can select the right runtime.
- **Session** — `OpenAgentSessionCommand.AgentRuntime` carries the
  resolved runtime; the session's own `Runtime` field is the single
  source of truth for generic open/attach (no more hardcoded literal).

### Orleans field id rule (verified)

`AgentJobInput` uses Ids `0,1,2,3,5,6,7,8,9` (Id(4) was the next free
slot — `Runtime` lands there). `RoutedAgentLaunchPlan` uses Ids `0..18`
(Id(19) was the next free slot — `Runtime` lands there). All existing
Ids untouched; older persisted snapshots deserialize with `Runtime =
null` and resolve as `opencode` (the default).

### `AgentConfigSchema` gotchas

- TWO key surfaces need `runtime`:
  1. `AllowedKeys` (used by `Validate` for key-presence checks).
  2. `Filter`'s hardcoded list. Refactored to iterate `AllowedKeys`
     directly so a new key automatically flows into the write-side
     merge paths (IssueVariableBuilder, ConfigService,
     MohistIssueWorkflowProfileBase, IssueWorkflowProfileStorageIntegrity).
- `ValidateRuntime` is split into two overloads: one on
  `JsonElement` (API boundary) and one on `IDictionary<string,object?>`
  (write-side merge paths). Both treat an absent key as valid; an
  out-of-set string returns an actionable error that lists
  `AllowedRuntimes`.

### `EquivalentInput` / `DescribeInputDifferences` on AgentJobGrain

`Runtime` MUST be in both the equivalence and the difference-descriptor
checks. Otherwise a SubmitAsync that arrives with a different runtime
would be wrongly accepted as a no-op replay (or, conversely, the
grain would say "different submission" without naming runtime).

### Test infra: reading dispatch envelope from runner poll

`WorkDispatchResponse.With` is a serialized JSON string (not an
object). Tests asserting on dispatch fields under `with` must
`JsonDocument.Parse(data.GetProperty("with").GetString())` first —
getting `GetProperty("with").GetProperty("runtime")` directly throws
"element of type 'Object', but the target element has type 'String'".
Added `ReadRuntimeFromDispatch` helper in
`AgentSessionLaunchRoutesSpecs` to keep the call sites readable.

### Codebase patterns to carry forward (T-002 / T-003)

- Snapshot-first: any Agent-driven value that controls execution must
  be captured on the AgentJobInput / RoutedAgentLaunchPlan at launch
  time, then read from the snapshot in recovery/dispatch. Mirrors the
  model/variant pattern already in `ResolveModelAndVariant`.
- `AgentConfigSchema` is the single source of truth: extend
  `AllowedKeys` + write an enum validator, derive `Filter`'s iteration
  from `AllowedKeys` so write-side merges track the validation
  surface.
- `OpenAgentSessionCommand.AgentRuntime` is the launch-time
  authoritative runtime. The session's own `Runtime` field is the
  authoritative value for everything downstream (open, attach, command
  routing). Do not hardcode "opencode" in any generic agent-session
  route.
## T-002 Runner AgentJobExecutor selects runtime from dispatch — patterns & gotchas

### Where `runtime` lives at the runner boundary

- The dispatch `with.runtime` is the snapshotted backend (T-001's
  `BuildDispatch` writes it). `AgentJobExecutor` reads
  `work.with["runtime"]` and defaults to `"opencode"` when absent
  (legacy / partial rollout defense).
- Constructor takes `AgentJobRuntimeAccessors` — both runtimes as
  late-binding accessors (matching the `command-runtime.ts` shape so
  the host's `() => this.openCodeRuntime` / `() => this.piRuntime`
  accessors survive runtime rebuilds without a constructor rewrite).
- Two parallel paths inside `execute()`: `executeOpenCode` and
  `executePi`. They share the `AgentSessionEventSink` helper (attach
  + session.input + runtime-event forwarding) so the Pi path does
  not duplicate the OpenCode observer glue.

### Pi session creation at AgentJob boundary

- `PiRuntime.runTurn` requires a bound session (`runtimeSessionId`
  cannot be null — `pi/runtime.ts:97`). When the AgentJob has no
  existing binding, the executor pre-creates a session via
  `runtime.createSession(...)` and threads the resulting path into
  the `PiTurnRequest`. This mirrors the Workflow path in
  `actions/pi.ts`.
- For OpenCode the runtime handles session creation internally and
  signals the new id via `onSessionReady`. For Pi there is no
  `onSessionReady` hook — the executor's `AgentSessionEventSink`
  emits `attach + session.input` after the pre-create so both
  backends publish the same AgentSession events.

### Runtime-unavailable semantics

- Per D4, a non-ready chosen runtime fails with `runtime-unavailable`
  and NEVER falls back to OpenCode (or Pi). Tests assert both
  directions explicitly.
- An accessor returning `null` (runtime not constructed yet) is
  treated the same as `runtime.ready() === false` — same failure
  code, no fallback.
- The terminal output's `kind` is the runtime that the executor
  tried to use, so a Pi `runtime-unavailable` failure is labeled
  `kind: "pi"` (not "opencode") for caller diagnostics.

### `runtime` in the dispatch payload — known-keys set

- `collectUnknownKeys` now treats `runtime` as known (alongside
  `prompt`, `instructions`, `model`, `variant`). Pi's
  `runtime.runTurn` records `options-unknown-keys` info diagnostics
  for unknown keys — keeping `runtime` out of unknown-keys prevents
  the Pi path from emitting a confusing diagnostic about its own
  routing key.

### Error kind mapping

- Pi's `PiErrorKind` is mapped to the same legacy codes the existing
  OpenCode path uses:
  - `deadline-exceeded` → `timeout`
  - `missing-session` → `runtime-session-missing` (+ `hint: "reset"`)
  - everything else passes through.
- The runtime is the final validator of model legality (D4 / spec
  `actionable failure for an uncredentialed model`): Pi's
  `setModel` failure surfaces as `turn-failed` with a
  `model-rejected` diagnostic, the executor does NOT swallow it.

### Test infra

- The two opencode-path tests in `agent-job-executor.spec.ts`
  (OpenCode-only behavior) and the new
  `agent-job-executor-pi-runtime.spec.ts` (runtime selection +
  Pi-path tests) are split into separate files to keep both under
  the 800-line test-budget.
- `makeFakePiRuntime` mirrors `makeFakeOpenCodeRuntime`: records
  `runTurn` and `createSession` calls, exposes setters for
  `ready`, the next `runTurn` result, and the next created
  session id. The fake forwards a small sample of Pi events
  (`message`) through the `onEvent` observer so the
  AgentSession-projection test can assert the channel carries
  Pi-runtime facts.
- Test using accessor `() => null` (late-binding semantics) —
  `resolveAccessor` (reused from `command-runtime.ts`) handles
  null/undefined/function.

### Codebase patterns to carry forward (T-003)

- Late-binding accessor shape (`T | (() => T | null) | null`) is the
  single source of truth for "runtime may not exist yet / may be
  rebuilt". Reuse `resolveAccessor` from `command-runtime.ts`.
- The same `AgentSessionEventSink` is reusable for any future
  Agent-bound runtime — it owns the attach + session.input +
  runtime-event-forwarding wiring in one place. New runtimes need
  to: (a) implement `runTurn`, (b) optionally implement
  `createSession` for fresh sessions, (c) call the sink from the
  runtime observer.
- The terminal output `kind` is the runtime label, not the
  dispatch label. This is essential for caller diagnostics — a Pi
  failure must not be mislabeled as OpenCode.

## T-003 Per-runtime model catalog — patterns & gotchas

- Runner registration carries `runtimeCatalogs`, keyed by runtime. Each entry has `models` and `variants`; OpenCode is emitted from the existing discovered snapshot and Pi maps `provider/id` to thinking-level variants.
- `PiRuntime.catalog()` is already configured-credential-only because its SDK source uses `getAvailable()`. Registration reads that catalog as-is and never filters or validates selected models against it.
- Server keeps `CoderModels` and `CoderModelVariants` as a legacy OpenCode fallback for older runners, while new `RuntimeCatalogs` entries are authoritative when a runtime key is present. This preserves the existing OpenCode route and runner status behavior.
- `RunnerRegistryGrain` exposes runtime-specific model and variant unions. Catalog lookup is case-insensitive; an explicit runtime entry, including an empty one, prevents fallback to the legacy OpenCode pair.
- `/api/projects/{projectRef}/opencode/models` accepts `runtime=opencode|pi`, defaults to OpenCode, and preserves `{ models, modelVariants }`. Invalid runtime values return `runtime_invalid` rather than selecting another catalog.
- Catalog normalization trims and deduplicates reported data only; there is no model-legality prevalidation. Runtime execution remains the final validator.

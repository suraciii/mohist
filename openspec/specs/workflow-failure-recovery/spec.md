

### Requirement: Task-level onFailure recovery declaration

A workflow task SHALL be able to declare an `onFailure` block containing a
`limit` (maximum recovery attempts) and an ordered list of `cases`. Each case
SHALL declare a `when` predicate over the failed task's action output and a
list of recovery `tasks` to insert into the stage. When a task fails, the
engine SHALL evaluate `cases` in declared order and SHALL execute the first
case whose `when` predicate matches the failed task's action output. When no
case matches, or when the `limit` is exhausted, the engine SHALL preserve the
failure as an ordinary task failure that the user can retry or rerun.

#### Scenario: First matching case wins

- **WHEN** a task with `onFailure` fails and its output matches multiple case predicates
- **THEN** the engine SHALL execute only the recovery tasks of the first matching case
- **AND** SHALL NOT execute recovery tasks of later cases

#### Scenario: No matching case preserves failure

- **WHEN** a task fails and no `when` predicate matches its output
- **THEN** the engine SHALL NOT insert any recovery task
- **AND** the task SHALL remain failed and available for user retry or rerun

#### Scenario: Limit exhaustion stops recovery

- **WHEN** the number of recovery attempts for a task has reached the declared `limit`
- **THEN** the engine SHALL NOT insert further recovery tasks for that task
- **AND** the task SHALL remain failed

### Requirement: Recovery reads only the failed task output

Recovery case matching SHALL read only the raw action output of the currently
failed task. The engine SHALL perform generic JSON-path matching against that
output (for example `output.errorCode`) and SHALL NOT interpret the business
meaning of any matched value. The engine SHALL NOT branch recovery on action
type, task id, or stage. Error codes, failure kinds, and other recoverability
signals SHALL be action-owned output fields, not a workflow-domain enum.

#### Scenario: Engine matches by output path only

- **WHEN** a task fails with output `{ "errorCode": "base-moved" }` and a case declares `when: { output.errorCode: base-moved }`
- **THEN** the engine SHALL match the case purely by comparing the output field value
- **AND** SHALL NOT consult the action name or task id to decide recovery

#### Scenario: Engine stays error-code-agnostic

- **WHEN** the engine evaluates a recovery case
- **THEN** it SHALL treat the matched value as an opaque string
- **AND** SHALL NOT maintain a registry of known error codes or failure kinds

### Requirement: failIf marker matching

A task `expect.markers` entry SHALL support a `failIf` value. When the matched
marker value equals `failIf`, the engine SHALL mark the task as failed. The
task `errorCode` on such a failure SHALL be defined by the action in its own
output, not auto-generated by the engine. When the matched marker value does
not equal `failIf`, the task SHALL be considered to have passed that marker
expectation.

#### Scenario: Marker equals failIf fails the task

- **WHEN** a task declares `expect.markers[*].failIf: FAIL` and the produced marker value is `FAIL`
- **THEN** the engine SHALL mark the task as failed
- **AND** the task `errorCode` SHALL come from the action output, not the engine

#### Scenario: Marker not equal to failIf passes

- **WHEN** a task declares `expect.markers[*].failIf: FAIL` and the produced marker value is `PASS`
- **THEN** the engine SHALL NOT mark the task as failed on account of that marker

### Requirement: retry self re-enqueues the failed task

An `onFailure` case SHALL support a `retry: self` directive. When a matching
case declares `retry: self`, the engine SHALL append a fresh attempt of the
original failed task after the case's recovery tasks. The retried attempt
SHALL preserve the original task's `onFailure` declaration, so subsequent
failures of the same task SHALL continue to be eligible for recovery up to the
declared `limit`. The retried attempt SHALL be a new attempt of the same task
id, not a new task.

#### Scenario: Retry appends original task after recovery

- **WHEN** a case with `retry: self` matches a failed task
- **THEN** the engine SHALL insert the case's recovery tasks followed by a new attempt of the original failed task
- **AND** the new attempt SHALL carry the same task id as the original

#### Scenario: Retried task keeps its onFailure

- **WHEN** a retried attempt of a task fails again
- **THEN** the engine SHALL evaluate the original task's `onFailure` against the new attempt's output
- **AND** SHALL count the new recovery against the original `limit`

### Requirement: Nested onFailure on recovery tasks

A recovery task SHALL be permitted to declare its own `onFailure`. Such nested
`onFailure` SHALL be resolved at the time the recovery task fails, against the
recovery task's own output. Nested recovery SHALL be non-recursive: a nested
recovery task SHALL NOT itself declare `onFailure`. After a nested recovery
completes successfully, the workflow SHALL continue with the next task in the
enclosing recovery sequence (for example, proceeding to a subsequent `push`
task, then `retry: self` of the originally failed task).

#### Scenario: Recovery task failure triggers nested recovery

- **WHEN** a recovery task with its own `onFailure` fails and a nested case matches
- **THEN** the engine SHALL insert the nested case's recovery tasks
- **AND** SHALL NOT evaluate further `onFailure` on those nested recovery tasks

#### Scenario: Nested recovery resumes enclosing sequence

- **WHEN** a nested recovery task completes successfully
- **THEN** the workflow SHALL continue with the next task declared after the failed recovery task in the enclosing recovery sequence
- **AND** SHALL eventually reach any declared `retry: self` of the originally failed task

### Requirement: Recovery tasks follow task rules

Recovery tasks SHALL be ordinary workflow tasks. They SHALL be executed by the
runner like any other task, SHALL consume the same template-expansion context
plus `${{ failure.output }}` for the failed task's output, and SHALL be
addressable by stable ids. Recovery task ids SHALL use the `recover:` prefix;
non-recovery task ids SHALL NOT carry stage prefixes such as `plan:`,
`check:`, or `integrate:`.

#### Scenario: Recovery task runs via runner

- **WHEN** the engine inserts a recovery task
- **THEN** the runner SHALL execute it using the same mechanism as ordinary tasks
- **AND** its `with` inputs SHALL be template-expanded with access to `${{ failure.output }}`

#### Scenario: Recovery task id prefix

- **WHEN** a workflow declares a recovery task
- **THEN** its id SHALL begin with `recover:`
- **AND** ordinary stage task ids SHALL NOT carry a stage prefix

### Requirement: Recovery setVars overwrites runtime facts

A recovery task SHALL be permitted to declare `setVars` that writes into the
workflow runtime profile `vars.*`, including overwriting values previously
written by the failed task. Failure-case matching SHALL read the failed task's
raw action output directly and SHALL NOT depend on `setVars` having executed.

#### Scenario: Recovery overwrites prior runtime variable

- **WHEN** a recovery task declares `setVars` targeting a path previously written by the failed task
- **THEN** the runtime profile `vars` at that path SHALL reflect the recovery task's value after it completes

#### Scenario: Case matching ignores setVars

- **WHEN** a task fails before its `setVars` could execute
- **THEN** recovery case matching SHALL still read the failed task's raw action output
- **AND** SHALL NOT require any `vars.*` projection to have happened

# Agent 事件订阅

> **⚠️ 尚未实现**：本文描述的功能当前**没有**实装。这是产品方案，记录用户需求与设计方向。文中带「（开放）」的条目尚未定稿。已实装的能力请看其它文档。

## 它解决什么问题

现在 Agent 只有一种用法：**你手动启动**——在 Web UI 填一段 prompt 点 New Session，或用 `mo` 命令。Agent 不会自己醒来，也不会因为 issue 发生了什么就行动。

但很多时候你不想到场。比如一个 issue 走到审批门，你想让某个 Agent **自动** review 产物、按你定好的规则替你判断能不能 approve；多数情况它自己 approve，少数它把握不准的，让它来问你。

> 用你的话说：「我实际上是在配置让一个 agent 监听某个 issue 的某个事件，事件发生时 agent 就会响应……判断逻辑写在提示词里，不写在程序里——我来负责把提示词写好。」

这就是 Agent 事件订阅要做的事：**给 Agent 一个反应式能力，让它监听事件、按你配的规则自动响应**。判断逻辑归你的提示词，系统只负责把事件送到、把 Agent 启动起来。

## 两个心智模型

理解这个功能，抓住两个区分。

### 1. 两层 Prompt

一个 Agent 实际行动时，它的指令由两层拼成：

```
┌─────────────────────────────────────────────────────┐
│ 第一层：Agent 内置指令（定义「我是谁」）              │
│   配 Agent 时写一次，长期稳定，所有订阅共享           │
│   = Agent 的身份 / 角色 / 通用规则                    │
└─────────────────────────────────────────────────────┘
                          │
                          │  1 个 Agent : N 条订阅
                          ▼
┌─────────────────────────────────────────────────────┐
│ 第二层：订阅响应提示词（定义「这次该做什么反应」）     │
│   配订阅时写，每条订阅各写各的                        │
│   = 遇到这个事件、这一刻，具体怎么响应                │
└─────────────────────────────────────────────────────┘
```

- **第一层**对应你已有能力——配置 Agent 时写的 Instructions。它定义这个 Agent 是干什么的（比如「你是 owner 的代理审批人，review 要严谨，不确定就来问」）。
- **第二层**是这个功能**新增**的。它定义的是「遇到某事件、此刻的反应」。同一个 Agent 可以挂多条订阅，每条配不同的响应提示词。

**为什么不把反应逻辑也并进 Agent 指令？** 因为同一个 Agent 可能要响应多种事件。把所有反应塞进身份指令会让 Agent 定义膨胀、难复用。拆开：**身份归 Agent，反应归订阅**。

> 你定的规则：「它的 prompt 不是和 agent 一对一的，而是和订阅一对一，一个 Agent 可以开多个订阅，每个都可以配不同的事件和不同的提示词。」

### 2. 订阅是一等对象，不是 Agent 上的字段

订阅是你可以独立增删启停的东西，不是 Agent 配置里的一行：

```
Agent「审批助理」 ──┬─ 订阅 A：监听「到达审批门」 → 用响应提示词甲
                   └─ 订阅 B：监听「stage 失败」 → 用响应提示词乙
```

每条订阅回答四个问题：谁来响应（哪个 Agent）、响应什么事件、响应哪个范围、怎么响应（响应提示词）。

## 你怎么用

**配 Agent**（写第一层）——已有能力，不变：起名、写身份指令、选 model。

**配订阅**（写第二层）——新增：对某个 Agent，创建一条订阅，选事件类型、选范围、写响应提示词。

**写响应提示词是你的活，也是这个功能的核心**。系统不判断你写得对不对、安不安全，它只负责把事件送到、把 Agent 起来、把你两层 prompt 拼对。举个例子，Approval 自动处理的响应提示词可能是：

> issue #{{issue}} 的 {{stage}} 阶段等你审批。先 `mo issue show {{issue}}` 读 proposal 和 tasks。如果 plan 清晰、tasks 可执行、没有明显遗漏，执行 `mo issue approve {{issue}}` 并附一句理由。如果把握不准（改动面大、风险高、需求含糊），不要 approve，而是 `mo issue reject {{issue}} -m "..."` 把疑问反馈给作者。

事件一到，Agent 自动醒来，按这段提示词行动。「多数自己 approve、少数找我」这个分流，是**你写的**，不是程序写死的。

## 几个场景（说明通用性）

| 场景 | 订阅的事件 | 响应提示词让 Agent 干什么 |
|---|---|---|
| Approval 自动处理 | 到达审批门 | review 产物，按规则 approve 或 reject |
| 失败兜底分析 | stage 失败 | 拉错误，分析根因，写进 issue comment |
| 完成自动汇总 | issue 完成 | 汇总产出的 OpenSpec 产物，写 release note |

三条订阅共用同一套机制，只是事件类型和响应提示词不同。**这就是「通用」的含义**：任何 Agent 订阅任何事件、写任何反应逻辑。

## 你和系统的责任边界

| 归谁 | 负责 |
|---|---|
| **你** | 把响应提示词写好、写安全；判断「让 Agent 自动 approve」对的项目是否可接受 |
| **系统** | 准确送事件、正确拼 prompt 起 Agent；让订阅可增删启停、可观测 |
| **系统不负责** | 判断提示词对错；拦截 Agent 的 approve。Agent 走的是和手动审批一样的正规通道（详见[工作流详解](the-workflow.md)），系统不额外设防 |

## 还没定的几件事

下面这些**（开放）**项会影响最终长什么样，定稿前先记在这里：

1. **订阅范围**：能精确到「某个 issue」、还是「某个 epic 下所有 issue」、还是只能「整个项目」？（影响订阅怎么配、怎么匹配事件。）
2. **并发**：一个 Agent 挂多条订阅、某个事件同时命中多条，会同时起多个 session。要不要给并发设上限？
3. **审批可追溯性**：现在系统**不记录**是谁 approve 的——Agent 自动 approve 和你手动 approve，事后分不出来。要不要让记录能区分「这条是 Agent 代签的」？
4. **响应提示词的模板变量**：`{{issue}} {{stage}}` 之外还要支持哪些？提示词里要能引用「这次事件针对哪个 issue、什么事件」，这套变量约定得定清楚。
5. **可观测性**：事件触发后命中了哪几条订阅、起了几个 session、各自结果——你怎么看到这条链路？
6. **配置入口**：订阅在 Web UI 的 Agent 详情页里配，还是单独的订阅管理页？CLI 要不要 `mo agent subscribe ...`？
